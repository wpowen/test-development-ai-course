# 02 术语表

约定：**中文名（English）** —— 一句话定义 —— *在本方法论中的具体用法*。带 ⚠ 的条目是最常被混用、必须辨析的术语。

## 2.1 测试基础

| 术语 | 定义 | 用法 |
| --- | --- | --- |
| 测试依据（Test Basis） | 判断"对不对"所依据的全部文档与规则来源 | S1 阶段必须冻结成带版本与 hash 的 Test Basis Pack |
| 测试条件（Test Condition） | 一个值得验证的可检查项，尚未变成用例 | 由风险推导，是需求与用例之间的中间层 |
| 测试用例（Test Case） | 输入、前置、步骤、期望结果的完整组合 | 必须绑定 test condition 与 risk id |
| ⚠ 预言 / 判定器（Test Oracle） | 判断实际结果是否正确的**独立**依据 | 不是"期望值"，而是"期望值从哪里来"；见 05 章六层模型 |
| ⚠ 断言（Assertion） | 代码中的检查语句 | 断言是 Oracle 的**实现**，不是 Oracle 本身 |
| 等价类划分（Equivalence Partitioning, EP） | 把输入域切成"同类同行为"的分区 | 枚举/数值域首选 |
| 边界值分析（BVA） | 在分区边界与其邻域取值 | 有序域必用；AI 场景扩展到 token 长度、上下文窗口边界 |
| 决策表（Decision Table） | 条件组合 → 动作的完整枚举 | 规则条数 ≥3 且互相影响时使用 |
| 状态转换测试（State Transition） | 覆盖合法转换、非法转换、状态不变量 | 订单/审批/Agent 会话必用 |
| 成对组合（Pairwise / N-wise） | 保证任意两（N）个参数的取值组合都被覆盖 | 参数多且交互风险高时替代全组合 |
| 属性测试（Property-based Testing） | 断言"对任意输入都成立的性质"而非具体值 | 契约、序列化、幂等性验证 |
| ⚠ 变形测试（Metamorphic Testing） | 断言输入变换与输出变换之间的关系 | **没有标准答案时的核心武器**，AI 测试主力方法 |
| 变异测试（Mutation Testing） | 故意在被测代码/数据中植入缺陷，看测试能否杀死 | 证明测试**检测力**的唯一客观手段 |
| 杀死 / 存活（Killed / Survived） | 变异被测试发现 / 未被发现 | `survived` 不自动等于产品缺陷，需人工分类 |
| 故障注入（Fault Injection） | 在环境/依赖/数据层制造受控故障 | 与变异测试互补：一个改被测物，一个改环境 |
| 探索式测试（Exploratory Testing） | 边设计边执行的有目的试探 | 规范不足时使用，须标记较低可重复性 |
| 错误猜测（Error Guessing） | 基于经验直接构造高风险输入 | 作为补充，不作为覆盖依据 |
| 冒烟 / 回归 / 验收 | 最小可用检查 / 防止旧功能损坏 / 确认满足需求 | 三者进入不同门禁层，不可互相替代 |
| 孤儿测试（Orphan Test） | 无法追溯到任何需求或风险的测试 | 只能标 `EXPLORATORY`，**不计入需求覆盖** |

## 2.2 流程与治理

| 术语 | 定义 | 用法 |
| --- | --- | --- |
| 准入准则（Entry Criteria） | 允许开始某阶段的前置条件 | 每阶段必须显式写，见 `templates/11` |
| ⚠ 准出准则（Exit Criteria） | 允许结束某阶段的判定条件 | 不是"用例都跑完了"，而是"风险已被覆盖到约定深度" |
| 门禁（Gate / Quality Gate） | 不满足即阻断下游的自动检查 | fail-closed：不确定时阻断，不是放行 |
| ⚠ 豁免（Waiver） | 明知不满足门禁但批准通过的记录 | 必须含：负责人、原因、补偿控制、**过期时间**、回滚条件 |
| 剩余风险（Residual Risk） | 已知但选择不消除的风险 | 发布决定书必列；无剩余风险清单不得发布 |
| 追溯矩阵（Traceability Matrix） | source → requirement → risk → condition → case → oracle → result 的双向图 | 正向查覆盖，反向查"这个结果说明了什么" |
| 运行收据（Run Receipt） | 一次执行的完整可复现记录 | 见 `schemas/run-receipt.schema.json` |
| 沿革（Lineage） | 一个分数能回到当时的全部版本 | 数据/Prompt/模型/工具/Scorer 五要素 |
| 状态被推翻（Superseded） | 旧结论被更新的可复现证据取代 | 冲突时以较新证据为准，并显式标注旧状态过期 |
| 影子发布 / 金丝雀（Shadow / Canary） | 不影响用户地跑 / 小流量放量 | AI 变更强烈建议先影子后金丝雀 |
| 缺陷分级（Severity） | 缺陷造成的**后果**严重程度 | S1–S4，见 05 章 |
| ⚠ 优先级（Priority） | 修复的**紧急**程度 | 与 Severity 正交；不得合并成一个字段 |
| 逃逸缺陷（Escaped Defect） | 上线后才被发现的缺陷 | 每一个都必须转成回归用例（Trace-to-Regression） |

## 2.3 AI 系统基础

| 术语 | 定义 | 用法 |
| --- | --- | --- |
| Token | 模型处理文本的最小单位 | 计费、上下文限制、截断的度量单位 |
| 上下文窗口（Context Window） | 单次调用可容纳的 token 上限 | 边界值测试的重要维度 |
| ⚠ 温度 / Top-p（Temperature / Top-p） | 采样随机性控制 | temperature=0 **不等于**完全确定；仍需重复运行 |
| 非确定性（Non-determinism） | 同输入可能得到不同输出 | 一次 PASS 不构成结论；必须报告分布 |
| 结构化输出（Structured Output） | 模型按给定 Schema 产出 | 只解决可解析性，见公理 2 |
| 提示词包（Prompt Package） | 版本化的 system/task/critic + 输入夹具 + Schema + eval + mutation | 是**工程输入**，不是聊天记录 |
| 嵌入（Embedding） | 文本到向量的映射 | 检索质量的底座；换模型即需重建索引并重测 |
| 检索增强生成（RAG） | 检索证据后再生成 | 被测面 = 语料 + 检索 + 生成 + 引用 |
| 分块（Chunking） | 把文档切成检索单元 | 分块策略变化会显著改变召回，属受控变量 |
| 工具调用（Tool Calling / Function Calling） | 模型请求执行外部函数 | 模型只能**提出候选调用**，授权在工具边界 |
| 智能体（Agent） | 自主决定下一步的循环系统 | 判据是"路径由谁决定"，不是产品命名 |
| 工作流（Workflow） | 由代码固定路径的编排 | 用分支覆盖测；与 Agent 测法不同 |
| 工作者（Worker） | 异步执行单元 | 必测重复投递、并发、超时、幂等 |
| 轨迹（Trajectory / Trace） | Agent 完整的决策与调用序列 | 三层 Oracle 之一（见 07.3） |
| 跨度（Span） | 轨迹中的单个可观测片段 | 定位"首个错误"的最小单位 |
| 交接（Handoff） | 任务在 Agent / 人 / Worker 间转移 | 必测：交接目标错误、权限扩大、状态丢失 |
| 记忆（Memory） | 跨会话保留的状态 | 必测：污染、越权读取、过期、跨租户泄露 |
| 模型上下文协议（MCP） | 工具/资源接入协议 | 投毒与协议漂移是专项攻击面 |

## 2.4 评测与度量

| 术语 | 定义 | 用法 |
| --- | --- | --- |
| 评测契约（Eval Contract） | 先写清"要回答哪个发布问题"再选指标 | 所有评测集的第一份文件 |
| 数据集切分（Split） | train / dev / test 的划分 | AI 测试中主要关心 dev 与 sealed holdout |
| ⚠ 封存集（Sealed Holdout） | 只在发布判断时开封一次的数据 | 反复用于调优的集合**不再是** holdout |
| 切片（Slice） | 按业务维度划分的子集 | 平均分必须被切片 blocker 覆盖 |
| 污染（Contamination） | 评测数据泄漏进训练/调优 | 隐藏测试集也不是万能防护 |
| ⚠ LLM 评委（LLM-as-judge） | 用模型给输出打分 | 使用前必须**先测人人一致性**再测 Judge 偏差 |
| 复合 Oracle（Composite Oracle） | 规则 + 语义 + 人工的组合判定 | 关键金额/权限/状态不得由单一 Judge 放行 |
| 忠实度（Faithfulness） | 回答是否被检索证据支持 | RAG 核心指标；与"正确"不是同一件事 |
| 引用准确率（Citation Accuracy） | 引用是否真实存在且相关 | 必须校验引用**存在性** |
| pass@k | k 次采样中至少一次成功的概率 | 衡量"有没有可能做对" |
| ⚠ pass^k | k 次采样**全部**成功的概率 | 衡量"能不能稳定做对"；生产可靠性看这个 |
| 首 token 时延（TTFT） | 请求到首个 token 的时间 | 流式体验核心指标 |
| 每 token 时延（TPOT / ITL） | 生成阶段每 token 平均间隔 | 与 TTFT 分开报告 |
| 有效吞吐（Goodput） | 满足 SLO 前提下的成功吞吐 | 比裸 QPS 更能反映容量 |
| 单位成功成本（Unit Success Cost） | 每个**成功完成**的任务花费 | AI 系统的核心经济指标 |
| 漂移（Drift） | 模型/数据/行为随时间变化 | 需持续评估而非一次性验收 |

## 2.5 安全与合规

| 术语 | 定义 | 用法 |
| --- | --- | --- |
| 提示注入（Prompt Injection） | 通过输入内容劫持模型指令 | 直接注入（用户输入）/ 间接注入（网页、邮件、知识库） |
| 过度代理权（Excessive Agency） | 模型获得超出必要的行动能力 | 用最小权限 + 写前授权治理 |
| 爆炸半径（Blast Radius） | 一次失控可影响的最大范围 | 沙箱设计的核心指标 |
| 跨租户泄露（Cross-tenant Leakage） | A 租户数据出现在 B 租户结果中 | 任何一次出现均为 blocker |
| 数据防泄漏（DLP） | 输出侧敏感信息过滤 | 是最后一道，不能替代授权 |
| 幂等键（Idempotency Key） | 保证重复请求只产生一次副作用 | 所有可写工具必备 |
| 最小权限（Least Privilege） | 只授予完成任务所必需的权限 | 按 tool × scope × tenant 三维授予 |
| 信任边界（Trust Boundary） | 数据从不可信进入可信区的界线 | 检索内容、工具返回值一律视为不可信 |

## 2.6 三组最容易混淆的辨析

**① 期望值 vs Oracle vs 断言**
期望值是"这次应该等于 200"；Oracle 是"200 这个数从 OpenAPI v7 的契约里来"；断言是 `assert resp.status == 200` 这行代码。只有 Oracle 独立于被测实现，测试才有意义。

**② 覆盖率 vs 检测力**
行覆盖 90% 说明代码被执行过，不说明缺陷会被发现。检测力只能由变异杀死率证明。AI 生成的用例最典型的失败是"覆盖率很高、杀死率极低"。

**③ 可靠性 vs 能力**
pass@k 高说明模型"能做到"；pass^k 低说明它"做不稳"。给用户的承诺基于 pass^k，宣传材料常引用 pass@k。写验收标准时必须指明是哪一个。
