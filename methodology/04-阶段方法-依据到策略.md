# 04 阶段方法：S1 依据冻结 → S4 风险与策略

贯穿案例：**订单取消与退款**。买家可取消未发货订单；已支付订单取消后异步退款。案例中故意保留一处冲突：PRD 禁止已发货订单取消，旧技术方案仍写 `SHIPPED` 可取消。

---

## S1 测试依据冻结

### 目的

让"对不对"这个问题有一个**唯一、可复现、可引用**的答案来源。没有 S1，后面所有产物都建在流沙上：用例越完整，返工越大。

### 输入清单（最小集）

| 输入 | 必须记录 | 下游用途 |
| --- | --- | --- |
| PRD | 版本、段落 ID、产品 owner、生效日期 | 业务目标、范围、规则 |
| 技术方案 | 提交 SHA、接口/状态引用、技术 owner | 实现约束、依赖、副作用 |
| OpenAPI / 事件 Schema | 规范版本、文件 hash | 请求、响应、错误、契约测试 |
| 状态机 / 数据模型 | 版本、合法转换集 | 状态测试与不变量 |
| 业务术语表 | 版本 | 消除歧义，供模型归一 |
| 变更范围 | 关联 MR/需求 ID | 回归选择 |
| 历史缺陷 | 缺陷 ID、影响版本、复现证据 | 风险权重、回归集 |
| **AI 侧依据** | 模型 ID/版本、Prompt 版本、知识库快照 ID、工具清单与版本 | AI 系统的"需求"同样需要冻结 |

网页链接不能只存当前地址，必须同时保存**访问日期**或**提交版本**。

### 关键动作：分配稳定坐标

不要把 80 页 PDF 直接丢给模型。先按标题与语义段落切分，分配不可变 `source_ref`：

```text
PRD-v3#R17          PRD 第 3 版第 17 条规则
TECH-a13f#S04       技术方案提交 a13f 的第 4 节
OPENAPI-v7#/cancel  OpenAPI v7 的 /cancel 路径
```

模型输出的**每一条事实**必须引用这些坐标；没有引用的事实一律删除。

### 优先级规则（必须写下来，不能靠默契）

```text
业务语义      由已批准 PRD 决定
实现细节      由当前技术方案与接口契约决定
任意语义冲突  进入评审，不得自动覆盖
```

### 准出检查

- [ ] 所有文件可访问，版本唯一
- [ ] `source_ref` 稳定且不随文档重排变化
- [ ] 优先级规则已由产品与技术 owner 确认
- [ ] 敏感数据已脱敏或标注访问级别
- [ ] 已识别的冲突已进入 `conflicts[]` 且 `status=BLOCKED`

**未通过时的状态**：`BLOCKED`。关键文件缺失或冲突责任人不明确，流程停在这里。

模板：`templates/03-test-basis-pack.md`、`schemas/source-manifest.schema.json`

## S2 需求契约化

### 目的

把自然语言变成**下游程序可以直接消费**的结构。一段"需求摘要"生成不了可靠测试；下游需要稳定字段、可追溯引用和停止状态。

### 字段设计原则

字段不是为了让 JSON 看起来专业，而是为了支持后续的风险分析、用例生成、执行与变更回归。缺少任一字段，对应的下游能力就不存在。

| 字段 | 支持的下游能力 |
| --- | --- |
| `actors` | 权限测试、越权用例 |
| `preconditions` | 前置状态构造、非法前置用例 |
| `state_transitions` | 状态转换测试、非法转换用例 |
| `invariants` | 属性测试、变形测试、账本对账 |
| `exceptions` | 负例设计、错误码契约 |
| `side_effects` | 幂等测试、副作用观察点 |
| `nfrs` | 性能/容量/可用性测试 |
| `unknowns` | 阻断下游、生成待确认清单 |
| `source_refs` | 追溯矩阵、变更影响分析 |

### 两道独立门禁

```text
门禁 A（结构）  PASS_SCHEMA
  · 字段、类型、枚举、必填项
  · source_refs 在当前 baseline 中存在
门禁 B（语义）  PASS_SEMANTIC
  · statement 与不变量是否被原文支持
  · AI 是否越权补充了业务决定
  · 关键金额/权限/状态由领域 owner 逐项确认
```

A 通过不代表 B 通过。把两者合并成一个"通过"是本阶段最常见的事故来源。

### 提取任务的权限声明（可直接抄进 System Prompt）

```text
角色：需求证据提取器。你只整理已提供的资料，不决定业务规则。
规则：
1. 每项事实必须给出 source_refs；没有引用则删除该事实。
2. 文档没有说明的内容写入 unknowns，不得补写。
3. 两个有效来源冲突时写入 conflicts，status=BLOCKED。
4. 只输出给定 JSON Schema；不要输出摘要、建议或测试用例。
5. 不处理任何生产密钥、真实支付账号或未脱敏个人信息。
```

⚠ 禁止出现的表述："综合判断后采用更合理的规则"。这会抹掉冲突，并把模型变成没有授权的产品负责人。

### 准出检查

- [ ] Requirement Contract 能被程序读取（`PASS_SCHEMA`）
- [ ] 每个关键规则有 `source_ref` 或明确 `UNKNOWN`
- [ ] 结构通过与业务确认分成两道门禁并分别留痕
- [ ] `conflicts[]` 非空时下游生成已被阻断

模板：`schemas/requirement-contract.schema.json`、`examples/requirement-contract.json`

## S3 技术契约化

### 目的

需求说明业务结果，技术文档说明**结果如何发生、在哪里观察**。只读 PRD 会漏掉重试、幂等、并发、异步、回滚和可观测性；只读设计又可能把实现选择误当业务规则。

### 六类可测试对象

| 技术对象 | 订单取消例子 | 测试要观察什么 |
| --- | --- | --- |
| 组件与依赖 | 订单服务、退款 Worker、支付网关 | 责任边界与失败传播 |
| 接口与事件 | `POST /cancel`、`refund.requested` | Schema、错误码、兼容性 |
| 状态与数据 | `PAID→CANCEL_PENDING→CANCELLED` | 合法/非法转换、账本不变量 |
| 异步与失败恢复 | 消息重投、重复取消 | 至多一次副作用、safe terminal |
| 安全与权限 | 买家/客服/管理员 | 越权、跨租户、字段级授权 |
| 可观测证据 | `trace_id`、退款事件、审计记录 | 受理、处理、最终结果三段可区分 |

### 失败与恢复必须成组提问

不要只问正常调用链。对每个同步/异步边界逐项检查：

```text
超时 → 取消 → 重试策略 → 退避 → 幂等身份 → 并发竞争
     → 死信 → 补偿 → 回滚 → 最终状态 → 告警 → 人工恢复路径
```

再确认：日志、指标、Trace、事件或存储**能否区分这些结果**。关键状态或副作用不可观察时，状态为 `BLOCKED`——不可观察即不可测。

### 需求—技术一致性矩阵

矩阵要同时暴露两个方向的问题：

- **实现缺口**：需求存在但没有组件/接口/观察点承接；
- **越界实现**：设计中存在但需求未授权的行为。

缺少映射不能写成"研发自行处理"，要形成带 `owner` 和 `close_with` 的可关闭问题。

```json
{
  "requirement_id": "REQ-CANCEL-001",
  "technical_refs": ["TECH-a13f#S02", "OPENAPI-v7#/cancel"],
  "components": ["order-service", "refund-worker"],
  "states": ["PAID", "CANCEL_PENDING", "CANCELLED"],
  "observations": ["refund.requested", "refund_count", "audit.cancel_id"],
  "coverage": "PARTIAL",
  "gap": "publisher retry exhaust 后的 safe terminal 未定义",
  "owner": "tech-b",
  "close_with": "TECH v-next 补充 safe terminal 定义并给出观察字段"
}
```

### 准出检查

- [ ] 需求与组件/接口/状态/观察点双向可追踪
- [ ] 每个异步边界的幂等语义与 safe terminal 有 owner
- [ ] 关键技术缺口会阻断风险与用例生成，而不是记在会议纪要里

## S4 风险分析与测试策略

### 目的

决定**测什么、在哪一层测、测到多深**。这是测试开发唯一独占的裁决权，也是最常被"用例数量"和"工具清单"顶替的一步。

### 风险识别的四个来源

1. **需求契约**：`invariants`、`exceptions`、`side_effects` 每一条都是候选风险；
2. **技术契约**：`gap`、不可观察点、异步边界；
3. **历史缺陷**：同模块、同类型、同 owner 的复发倾向；
4. **AI 特有风险源**（传统项目没有的三类）：
   - 非确定性风险：同输入不同输出导致的不可复现失败
   - 数据/模型漂移风险：上线后行为随时间变化
   - 注入与越权风险：不可信内容进入执行链

### 风险打分（RPN 变体）

```text
Risk Priority Number = 影响(I) × 可能性(L) × 探测难度(D)
```

| 维度 | 1 | 2 | 3 | 4 | 5 |
| --- | --- | --- | --- | --- | --- |
| **影响 I** | 体验轻微 | 单用户功能受损 | 多用户/数据错误 | 资金/权限/合规 | 不可逆资金损失或大范围泄露 |
| **可能性 L** | 极少路径 | 少数路径 | 常规路径 | 高频路径 | 每次请求都经过 |
| **探测难度 D** | 立即报错 | 日志可见 | 需要专门断言 | 需要跨系统对账 | 只有用户投诉才知道 |

分档与测试深度的映射（**占位示例，必须按你的业务重设**）：

| RPN | 档位 | 最低测试深度 |
| --- | --- | --- |
| 60–125 | 关键 | 独立 Oracle + 变异证明检测力 + 故障注入 + 人工复核 + 生产监控项 |
| 27–59 | 高 | 独立 Oracle + 自动化回归 + 负例集 |
| 12–26 | 中 | 自动化用例 + 边界值 |
| 1–11 | 低 | 冒烟或探索式，允许不自动化 |

**没有被降级理由记录的风险，不允许降档。** 降档记录进《测试策略》的"残余风险"一节。

### 测试层级分配

每条风险必须被指派到**恰好一个主责层级**（可有辅助层级）。层级选择依据是"缺陷在哪一层最早、最便宜、最稳定地暴露"。

| 层级 | 适用 | 不适用 | AI 系统上的对应物 |
| --- | --- | --- | --- |
| 单元 | 纯函数、算法、边界计算 | 跨服务契约 | 提示词模板渲染、Schema 校验、Scorer 逻辑 |
| 契约 | 服务间接口兼容性 | 业务编排 | 工具调用 Schema、结构化输出契约 |
| 集成 | 组件协作、状态流转、幂等 | 端到端体验 | 检索+生成链路、Agent 与工具的联调 |
| 系统/E2E | 关键用户旅程 | 大量分支 | 完整任务成功率、轨迹三层判定 |
| 评测（AI 特有） | 概率性输出质量 | 确定性逻辑 | 数据集 + Oracle + 重复运行 + 切片 |
| 性能/容量 | SLO、拐点 | 功能正确性 | TTFT/TPOT/Goodput/单位成功成本 |
| 安全 | 越权、注入、泄露 | 功能覆盖 | 攻击集 + 权限矩阵 + 爆炸半径 |
| 生产 | 真实分布、漂移 | 发布前判断 | 在线抽样 + 持续评估 |

反模式：把所有东西堆到 E2E。E2E 用例的定位成本最高、稳定性最差；它只应承载**关键旅程**，不承载分支覆盖。

### 测试方法选择矩阵

按 **输入形态 × 风险类型 × Oracle 可得性** 选择，而不是按工具或经验偏好。

| 如果…… | 首选方法 | 辅助方法 | Oracle 来源 |
| --- | --- | --- | --- |
| 输入是数值域或枚举 | 等价类 | 边界值 | 契约/规则 |
| 输入有序且边界敏感 | 边界值 | 属性测试 | 契约 |
| 3 条以上规则互相影响 | 决策表 | pairwise | PRD 规则 |
| 存在状态与非法转换 | 状态转换 | 属性（不变量） | 状态机 |
| 参数多且交互风险高 | pairwise / N-wise | 组合爆炸分析 | 契约 |
| 有明确不变量但无唯一答案 | **属性测试** | 变形测试 | 不变量本身 |
| **没有标准答案**（AI 生成内容） | **变形测试** | 复合 Oracle | 输入变换↔输出变换关系 |
| 需要证明用例有检测力 | **变异测试** | 故障注入 | 杀死率 |
| 依赖不可控外部系统 | 契约测试 + 录制回放 | 故障注入 | 契约 |
| 规范不足或时间极紧 | 探索式 + 错误猜测 | 检查表 | 经验（须标注低可重复性） |
| 已知实现且需结构覆盖 | 白盒 | 变异 | 代码结构 |

**变形关系示例（AI 场景最有用的一栏）**：

| 变换输入 | 期望输出关系 |
| --- | --- |
| 同义改写问题 | 结论应保持一致 |
| 增加无关上下文 | 结论不应改变 |
| 打乱候选顺序 | 判定结果不应改变（Judge 位置偏差探针） |
| 删除关键证据 | 应转为"无法回答"而非编造 |
| 把金额乘以 10 | 审批路径应升级 |
| 切换到无权限身份 | 应拒绝，且不泄露存在性 |

### 不可行组合与残余风险

有些方法在你的条件下跑不动（没有环境、没有数据授权、没有 Oracle）。这**必须显式记录**，而不是悄悄不做：

```text
风险 R-014（跨租户数据泄露）
  计划方法：多租户攻击集 + 字段级授权断言
  不可行原因：测试环境只有单租户数据授权
  当前替代：单租户越权用例 + 代码审查
  残余风险：跨租户路径未验证（HIGH）
  接受人：<姓名/角色>   复评日期：<日期>
```

### 准出检查

- [ ] 每条高风险有指定层级、方法与 Oracle 来源
- [ ] 方法选择有记录，不是"因为我们一直用这个工具"
- [ ] 不可行组合与残余风险已具名接受
- [ ] 策略中没有出现"用例数量"作为质量判据
