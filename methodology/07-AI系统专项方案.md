# 07 AI 系统专项测试方案

先做一件事：**判断你的被测对象属于哪一类**。分类错误会导致整套方法用错。

## 7.0 被测对象分类决策树

```text
系统里有大模型调用吗？
├─ 没有 ──────────────► 传统测试（见 04–06 章），本章不适用
└─ 有
   ├─ 只有单次调用，输入输出一进一出 ────────────► 7.1 LLM 应用
   ├─ 调用前会检索外部知识 ───────────────────► 7.2 RAG（叠加 7.1）
   ├─ 模型能决定"下一步做什么"并调用工具 ──────► 7.3 Agent（叠加 7.1/7.2）
   ├─ 路径由代码固定，模型只填内容 ────────────► 7.4 Workflow
   └─ 你测的是模型服务本身（吞吐/延迟/容量）──► 7.5 Serving
```

**判据是"路径由谁决定"，不是产品命名。** 一个叫"智能客服"的产品可能同时包含固定路由 Workflow、自主 Agent 和异步 Worker——必须分别按对应方案测。

## 7.1 LLM 应用测试方案

### 失败模型（先知道它怎么坏）

| 失败模式 | 表现 | 首选检测手段 |
| --- | --- | --- |
| 幻觉 | 输出无来源支持的事实 | 来源层 Oracle（L3）+ 引用存在性校验 |
| 指令不遵循 | 忽略格式/约束要求 | Schema 校验 + 规则断言 |
| 结构漂移 | 字段缺失、类型错误 | JSON Schema（L2） |
| 拒答错误 | 该答的拒答 / 该拒的答了 | 期望拒答集 |
| 截断 | 超长被截断 | 长度边界样本 + `finish_reason` 断言 |
| 非确定性 | 同输入结果波动超预期 | 重复运行分布 |
| 上下文丢失 | 长上下文中间信息被忽略 | 位置探针（信息放在首/中/尾） |
| 敏感输出 | 泄露密钥、个人信息 | 输出 DLP |
| 成本回归 | 质量持平但 token 暴涨 | 单位成功成本 |

### 必测清单

```text
□ Schema 契约：字段、类型、枚举、必填、额外字段策略
□ 边界：上下文窗口 ±、最大输出长度 ±、空输入、超长输入、多语言、特殊字符
□ 拒答/截断：显式状态而非空结果；finish_reason 必须被断言
□ 确定性：同参数重复 N 次（N≥5），报告分布而非单值
□ 参数敏感性：temperature / top_p / seed 改变时的行为边界
□ 变形关系：同义改写、无关上下文注入、顺序打乱、证据删除
□ 版本 A/B：一次只改一个变量（模型 | Prompt | 参数）
□ 成本与延迟：token 数、TTFT、总时长
□ 安全：直接注入、敏感信息输出
```

### 度量与 Oracle 组合

| 检查项 | Oracle 层 | 说明 |
| --- | --- | --- |
| 可解析性 | L2 | Schema pass rate |
| 引用真实性 | L3 | citation existence rate |
| 规则符合 | L4 | 不变量违反数（**blocker**） |
| 内容质量 | L5 | Judge 分数（仅参考，不放行 blocker） |
| 高风险正确性 | L6 | 人工抽检一致率 |

### Prompt 作为受版本控制的工程输入

一个可交付的 Prompt Package 至少包含：

```text
prompt-package/
├── manifest.json          版本、模型、参数、hash、状态(NOT_RUN/RUN)
├── system-v1.md           权限与失败语义（照抄 01 章 1.3 表）
├── task-v1.md             任务与输出契约
├── critic-v1.md           独立复核提示（不得由生成者自评）
├── input.json             输入夹具
├── output.schema.json     输出 Schema
├── eval.json              评测集（五类样本）
└── mutation.json          负例：缺引用、自批准、越权、先写后授权
```

⚠ 聊天记录不是 Prompt Package。没有 Schema 和 eval 的提示词无法进入门禁。

### LLM-as-judge 的使用纪律

```text
使用前必须完成：
  1. 先测人人一致性（两名领域标注员独立标注）
  2. 再测 Judge 与人的一致性
  3. 偏差探针：位置翻转、长度膨胀、风格美化、自偏好
  4. 明确划分：可自动评分 / 需抽检 / 必须人工审批 三个区间
更换 Judge 模型或版本后，必须重新校准，不得沿用旧阈值。
```

对应课程页：TD-F02–TD-F04、TD-T01–TD-T04、TD-T13–TD-T14

### 从概念到可审计的 Judge 与 Gold-set

在落地前复制并填写 [`governance/tevv/judge-card.template.yaml`](../governance/tevv/judge-card.template.yaml) 与 [`governance/tevv/gold-set-card.template.yaml`](../governance/tevv/gold-set-card.template.yaml)。前者固定 Judge 的构念、盲法、位置/风格/同模型族偏差探针、人工 sentinel 和暂停条件；后者固定样本来源、开发/校准/封存集隔离、匿名多标注、分歧和仲裁。

模板状态为 `TEMPLATE_NOT_RUN`，不代表已校准。真正的结论必须在逐样本收据中报告类别分布、适用的一致性统计量（两人不等同于三人及以上）、per-class P/R/F1、置信区间、UNKNOWN 与人审裁决。单一 κ 或单一总分都不能成为发布结论，更不能覆盖事实、权限、安全或副作用 blocker。

## 7.1.1 TEVV 覆盖矩阵：不要只测模型文本

生成式系统的风险穿过模型、检索、工具、应用与人类决策五层。使用 [`governance/tevv/ai-tevv-coverage-matrix.yaml`](../governance/tevv/ai-tevv-coverage-matrix.yaml) 把 `GOVERN / MAP / MEASURE / MANAGE` 与 `DEFINE / BUILD / EVALUATE / RELEASE / OPERATE` 串起来。每个单元必须留 `risk → scenario → oracle → data → owner → evidence → monitor → rollback`，无证据写 `NOT_RUN/BLOCKED`，不适用写 `N/A` 和理由。

它是设计和取证清单而不是 20 个已完成验证。真实模型、集成、从业者盲评、目标学员研究及生产观察应当分别使用 [`governance/validation-receipts/`](../governance/validation-receipts/) 中的模板；在授权执行和独立复核之前，模板必须保持 `NOT_RUN`。

## 7.2 RAG 测试方案

RAG 的被测面是**四段**，任何一段坏了都表现为"回答不对"。必须分段定位，不能只看最终答案。

```text
语料治理 ──► 检索 ──► 生成 ──► 引用与呈现
```

### 分段失败模型与专属指标

| 段 | 失败模式 | 指标 | Oracle |
| --- | --- | --- | --- |
| 语料 | 过期、重复、权限错配、分块破坏语义 | 语料新鲜度、重复率、权限标注覆盖率 | 语料清单 + 权限矩阵 |
| 检索 | 召回不到、排序靠后、切片偏差 | Recall@k、MRR/nDCG、按查询切片的召回 | 人工标注相关性 |
| 生成 | 有证据但结论矛盾、编造 | Faithfulness、无答案正确率 | 证据蕴含判定（L4+L5） |
| 引用 | 引用不存在、引用不相关 | Citation existence / relevance | 指针存在性校验（L3，可自动） |

### 必测清单

```text
□ 语料版本与快照 ID 已冻结；重建索引即视为新版本
□ 分块策略作为受控变量（改分块 = 改系统，需重测）
□ 权限：不同身份检索到的集合必须不同；跨租户为 blocker
□ 检索评测独立于生成评测（先证明检索没问题，再谈生成）
□ 查询切片：常见问 / 长尾问 / 歧义问 / 无答案问 / 越权问
□ 无答案场景：语料确实没有时必须说"没有"，不得编造
□ 引用存在性：每条引用必须能在检索结果中找到（可完全自动）
□ 忠实度：回答的每个事实点被引用证据支持
□ 端到端 Gate：检索 blocker + 引用 blocker + 权限 blocker 分别设置
```

### 关键设计：无答案样本

**最容易被漏掉、也最容易出事故的一类。** 评测集中必须有一批"语料里确实没有答案"的问题，正确行为是明确说明无法回答并给出下一步（转人工/建议提问方式），而不是用相关但不正确的内容拼一个答案。

### 换嵌入模型 = 全量重测

嵌入模型、分块策略、索引参数任一变化，检索分布就变了。此时**不能**只跑冒烟，必须重跑检索评测与端到端评测，并与旧版本做同数据集对照。

对应课程页：TD-T09–TD-T12

## 7.3 Agent 测试方案

Agent 的核心特征：**模型决定下一步并调用工具**，其中一些工具有不可逆副作用。因此 Agent 测试的重心不是"回答好不好"，而是"**它做了什么，被授权了吗，能不能撤销**"。

### 三层 Oracle（必须分别判定，禁止用总分吞掉）

| 层 | 判断 | 典型失败 |
| --- | --- | --- |
| **Outcome** 最终结果 | 业务最终状态是否正确 | 结果对但过程越权 |
| **Step** 单步动作 | 每次工具调用的工具/参数/权限/前置是否合法 | 调用了禁止工具 |
| **Trajectory** 完整轨迹 | 状态、重试、Handoff、终止原因是否可接受 | 死循环、预算耗尽、孤儿任务 |

> 经典案例：Agent 最终正确回复"转人工"，但此前已调用一次退款接口并被后端拒绝。只评最终文本 = 假绿。

**不要**把一条黄金轨迹当唯一正确答案——那会惩罚合法替代路径。正确做法：写**不变量 + 禁止副作用 + 必要检查点**，只在强流程约束场景才要求精确顺序。

### 八个测试维度（D0–D7）

| 维度 | 测什么 | 关键判据 |
| --- | --- | --- |
| **D0 评估可信** | 先测 Judge 本身 | 未校准的 Judge 不能作为门禁 |
| **D1 单体能力** | 单 Agent 智能与轨迹质量（含 Span 首错归因） | Trace 完整性；无 Trace 即不可测 |
| **D2 编排协作** | 交接、隔离、级联失败、熔断、上下文工程 | 一个子 Agent 失败不得污染全局 |
| **D3 交互协同** | 多轮、多模态、人机、可解释 | 确认次数过多 = 人会闭眼点同意 |
| **D4 鲁棒可靠** | `pass@k` vs `pass^k`、分布与长时程衰减 | 承诺用户的是 `pass^k` |
| **D5 安全对抗** | 注入、MCP 投毒、越权、记忆、沙箱、爆炸半径 | 授权在工具边界，不在 Prompt |
| **D6 效率经济** | 延迟、成本、并发、可观测、预算护栏 | 单位成功成本 |
| **D7 业务治理** | 规则、审计、四维版本、ROI | 模型/Prompt/工具/策略四维成组版本 |

### 工具调用的写前授权链（可直接实现）

```text
用户身份验证 → 租户判定 → 最小 scope 检查 → 参数 Schema 与边界
  → 幂等键检查 → 前置状态检查 → 人工审批（高风险）→ 执行 → 审计留痕
```

任一环节失败即拒绝，并保存 `reason` / `trace_id` / `policy_version`。

**测试时禁止连真实可写后端。** 用录制沙箱观察"策略是否先于执行生效"，并断言零真实写入。

### 必测清单

```text
□ 三层 Oracle 分别判定并分别报告
□ 工具契约：Schema、最小权限、副作用、幂等键、审批条件逐个声明
□ 故障注入：不存在的工具、越界参数、错误身份、重复调用、缺少前置步骤
□ 沙箱证明：assert_no_side_effect —— 真实写入次数必须为 0
□ 注入攻击：直接注入 + 间接注入（污染知识文档/网页/邮件）
□ 跨租户：任一次跨租户读取即 blocker
□ 预算护栏：迭代数、时间、token、成本上限，且必须留下 stop_reason
□ 恢复：checkpoint 丢失、消息重复投递、Handoff 目标错误
□ 可靠性：同任务重复 k 次，报告 pass@k 与 pass^k
□ 长时程：多轮任务的衰减曲线
□ 人机接管：中断点是否有效、接管后状态是否一致
```

### 自愈（Healer）的红线

| Healer **可以**改 | 必须**人工审批** | **绝对禁止** |
| --- | --- | --- |
| 非语义定位器属性 | 等待策略调整 | 删除断言 |
| 元素选择器候选 | 新增步骤 | 修改期望值 |
| — | — | 跳过业务步骤 |
| — | — | 无限扩大等待 |

**任何 healer 候选修复，必须在原业务变异下仍然失败**，否则拒绝合并。历史通过率不是修复正确性的依据。

对应课程页：TD-T15–TD-T19、TD-AG-00–TD-AG-10

## 7.4 Workflow / Worker 测试方案

路径由代码固定 → 用**分支覆盖**测；异步执行 → 用**幂等与恢复**测。这两点与 Agent 完全不同。

### 必测清单

```text
□ 状态机：合法转换全覆盖 + 非法转换全部拒绝
□ 分支覆盖：每个决策点的真/假分支
□ 幂等：同一 idempotency key 重复投递，副作用只发生一次
□ 重复投递：至少一次语义下的重放
□ 并发：同一实体的并发操作（乐观锁/悲观锁行为）
□ 超时与重试：退避策略、重试上限、耗尽后的 safe terminal
□ 死信：进入 DLQ 的条件与人工恢复路径
□ Checkpoint：崩溃后从正确位置恢复，不重复已提交副作用
□ Handoff：目标错误、权限不得扩大、状态不得丢失
□ 终止条件：预算/迭代/时间上限必须有 stop_reason
□ 孤儿任务：无人认领的任务能被发现并告警
□ 补偿与回滚：失败后的补偿动作可执行且可验证
```

### 经典故障注入序列

```text
① 崩溃点注入：worker 写审计后、确认消息前崩溃
   期望：重投后幂等键阻止第二次写入，从 checkpoint 恢复
② 移除终止信号
   期望：预算护栏在上限内停止 Agent 并产生告警与 stop_reason
③ Handoff 目标错误
   期望：拒绝并升级人工，下游权限不得扩大
```

对应课程页：TD-W01–TD-W03

## 7.5 AI Serving 测试方案

被测对象是**模型服务本身**。与传统 API 性能测试的关键区别：输出长度可变，因此"一次请求"的成本与耗时高度分散。

### 指标定义（不得混用）

| 指标 | 定义 | 注意 |
| --- | --- | --- |
| **TTFT** | 请求到首 token 的时间 | 决定流式体验 |
| **TPOT / ITL** | 生成阶段每 token 间隔 | 与 TTFT 分开报告 |
| **E2E Latency** | 总时长 | ≈ TTFT + 输出长度 × TPOT |
| **Throughput** | 裸吞吐（tokens/s 或 req/s） | 单独看会误导 |
| **Goodput** | **满足 SLO 前提下**的成功吞吐 | 容量判断用这个 |
| **单位成功成本** | 每个成功任务的费用 | 经济性核心 |

### 负载建模：必须先建 token 分布

传统压测用 QPS 就够；AI Serving 必须同时建模：

```text
输入 token 分布（p50/p90/p99）
输出 token 分布（p50/p90/p99）
并发到达模式（泊松 / 突发 / 阶梯）
prompt 缓存命中率
流式 vs 非流式比例
```

用固定长度做压测得到的容量结论**不可用于生产**。

### 必测清单

```text
□ 阶梯加压找 SLO 拐点（不是找最大 QPS）
□ 排队行为：队列深度、排队延迟、超时丢弃
□ KV Cache：命中率、显存占用、逐出行为
□ 长输出场景：p99 输出长度下的尾延迟
□ 限流：触发阈值、返回码、客户端可重试性
□ 超时与重试：重试风暴防护（重试预算）
□ 熔断与降级：降级到小模型/缓存/静态回复时的质量下限
□ Fallback：主模型不可用时的路由正确性与质量差异
□ 冷启动：扩容后的首请求延迟
□ 成本：不同负载下的单位成功成本曲线
```

### 阶段诊断顺序

```text
排队 → 网关/限流 → 调度 → GPU 计算 → KV Cache/显存 → 后处理 → 网络
```

一次只改一层，否则无法归因。

对应课程页：TD-A01–TD-A06、TD-AP01–TD-AP08

## 7.6 五类对象的方案速查

| | LLM | RAG | Agent | Workflow | Serving |
| --- | --- | --- | --- | --- | --- |
| 主 Oracle | Schema + 规则 + 变形 | 引用存在性 + 忠实度 | 三层（Outcome/Step/Trajectory） | 状态机 + 幂等 | SLO 区间 |
| 核心风险 | 幻觉、结构漂移 | 检索失败、权限错配 | 越权副作用 | 重复副作用 | 容量拐点 |
| 必须重复运行 | 是 | 是 | 是 | 否（确定性） | 是 |
| 必须沙箱 | 否 | 否 | **是** | 是 | 否 |
| 数据是受控版本 | 是（评测集） | **是（语料+索引）** | 是 | 否 | 是（token 分布） |
| 主要成本指标 | token/任务 | 检索+生成成本 | 单位成功成本 | — | Goodput/成本曲线 |
| 回滚需成组的对象 | 模型+Prompt | +索引+分块 | +工具+策略 | 代码 | 模型+配置 |
