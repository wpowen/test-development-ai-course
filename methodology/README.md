版本：v1.0 ｜ 建立日期：2026-08-12 ｜ 适用职业：测试开发 / 质量工程 / AI 质量工程

## 这份手册解决什么问题

103 页课程页面回答的是"某一个具体动作怎么做"。本手册回答的是它们之间缺失的那一层：

- 这些动作**按什么顺序**组成一条完整的测试流程；
- 每个环节的**输入、输出工件、准入准出、负责人**分别是什么；
- 哪些判断**可以交给 AI**，哪些**必须由具名人类**做；
- 一个团队从零开始，**90 天内**按什么次序落地。

课程页面 = 训练场；本手册 = 现场作业规程。两者共用同一套证据语义与状态词，不允许互相冒充成熟度。

## 三条阅读路径

**路径 A｜新人（第 1 周）**：02 术语表 → 03 生命周期总览 → 01 公理与责任模型 → 用 `templates/02-test-plan.md` 复写一次你手上的需求。

**路径 B｜测试负责人（接手一个新项目）**：03 → 04 → 08 度量体系 → 09 RACI → 12 路线图；先产出《测试策略》和《风险登记册》两份工件，再谈自动化。

**路径 C｜要测 AI 系统的工程师**：01 → 07 专项方案（找到你的被测对象类别）→ 05 Oracle 与数据 → 11 安全；先固定 Oracle 和数据集，再写第一条评测。

## 证据边界（先读这一条）

本手册是**方法综合**，不是行业统计结论。手册中所有：

- **数值阈值**（覆盖率、通过率、延迟、成本）一律是**占位示例**，必须由你的业务 owner 按风险重新设定；
- **工具名称**只作为类别举例，不构成推荐或背书；
- **组织职级、年限、晋升周期**一律进入"组织适配器"，缺 owner 时保持 `INTERNAL-UNKNOWN`。

手册配套的校验脚本与贯穿案例是**确定性离线夹具**（`fixture-tested`）。它证明流程可运行、冲突能阻断、预埋缺陷能被发现；**不**证明真实模型准确率、企业系统集成效果或生产收益。详见 [14-证据边界与状态语义.md](14-证据边界与状态语义.md)。
