# 00 完整测试方案总览

版本 v1.0 ｜ 2026-08-12 ｜ 适用：测试开发 / 质量工程 / AI 质量工程

> 这份文档回答一个问题：**把前面所有内容装配起来，得到的是什么。**
> 它不重复各章细节，只给出架构、逻辑、流程与交互，让人能在一页之内判断该从哪里进入。

## 0.1 这套方案由四层构成

```text
┌─ 第 4 层  交付面 ────────────────────────────────────────────┐
│  103 页学习页 · 13 模块 · 静态站点 · 教程 JSON · 发布候选包    │
└───────────────────────────▲──────────────────────────────────┘
                            │ 投影（两个生成器）
┌─ 第 3 层  内容源 ────────────────────────────────────────────┐
│  methodology/dimensions/_sources/*.json（11 份，唯一事实来源） │
│  每页：术语 · 判断表 · 反例 · 诊断树 · 演练 · 带走物            │
└───────────────────────────▲──────────────────────────────────┘
                            │ 依据
┌─ 第 2 层  方法论 ────────────────────────────────────────────┐
│  methodology/（14 篇）九阶段生命周期 · 六层 Oracle · 五级成熟度│
│  methodology/dimensions/（11 个维度，108 篇）                  │
└───────────────────────────▲──────────────────────────────────┘
                            │ 约束
┌─ 第 1 层  契约与门禁 ────────────────────────────────────────┐
│  Skill 34 份 reference · 8 道机器门禁 · 5 个可运行 lab         │
└──────────────────────────────────────────────────────────────┘
```

**四层的关系是单向的**：契约约束方法论，方法论产生内容源，内容源投影成交付面。反向修改（直接改交付面）会在下一次生成时被覆盖，这是设计意图。

## 0.3 八道机器门禁：什么会被拦下

| # | 门禁 | 检查什么 | 当前阈值 | 失败即 |
| --- | --- | --- | --- | --- |
| 1 | 内容结构 | 块数、outcomes、practice、completion、来源、架构图、材料存在 | 固定 | 阻断 |
| 2 | **正文深度** | 学习者散文的中文字符数 | **≥ 1600** | 阻断 |
| 3 | **判断表** | 每页方法表 / 反例表 / 诊断表 | **≥ 3 张** | 阻断 |
| 4 | **跨页原创性** | 模块内句级重复率（声明的脚手架除外） | **≤ 20%** | 阻断 |
| 5 | 可执行性 | 命令与 manifest 逐字一致、路径已发布、cwd 显式 | 102/102 | 阻断 |
| 6 | 材料闭包 | canonical → public → static → ZIP 四跳字节一致 | 16 bundles | 阻断 |
| 7 | 目录与晋级 | 117 canonical topic、逐页 promotion receipt | `problems=[]` | 阻断 |
| 8 | 发布候选 | 结构、清单哈希、视觉源、状态登记 | `structure_valid` | 阻断 |

第 2、3、4 道是本项目新增的。它们的共同作用是：**让「研究做没做」之外，「研究到没到页面」也变成机器可判定的事**。

**四个人工交互点**（其余全自动）：

| 交互点 | 谁 | 决定什么 | 不做会怎样 |
| --- | --- | --- | --- |
| S2 语义门禁 | 产品 owner | 需求语义是否被正确理解 | 结构通过冒充语义通过 |
| S5 关键 Oracle | 领域 owner | 金额、权限、状态的判据 | 语义层放行了 blocker |
| S9 风险接受 | 发布 owner | 剩余风险是否接受 | 无人为发布负责 |
| 回滚 | SRE | 是否回滚、怎么回滚 | 事故时无人有权决定 |

## 0.5 AI 系统的五类被测对象与选择流程

```text
系统里有大模型调用吗？
├─ 没有 ──────────────────────────────► 传统测试（04–06 章）
└─ 有
   ├─ 单次调用，一进一出 ──────────────► LLM 应用（07.1）
   ├─ 调用前检索外部知识 ──────────────► RAG（07.2，叠加 07.1）
   ├─ 模型决定下一步并调工具 ──────────► Agent（07.3，叠加前两者）
   │      └─ 高风险（不可逆/资金/时效）─► + 高风险适配器（维度 12）
   ├─ 路径由代码固定，模型只填内容 ────► Workflow（07.4）
   └─ 测的是模型服务本身 ──────────────► Serving（07.5）
```

**判据是「路径由谁决定」，不是产品命名。** 一个产品常常同时包含固定路由 Workflow、自主 Agent 和异步 Worker，必须分别按对应方案测。

## 0.6 学习者交互路径

课程不是线性读物。三条路径对应三种真实处境：

| 路径 | 处境 | 起点 → 终点 | 出口工件 |
| --- | --- | --- | --- |
| **A 新人** | 刚接手，术语都不熟 | 02 术语表 → 03 生命周期 → TD-F01 → TD-P01–P08 | Test Basis Pack + 需求契约 |
| **B 测试负责人** | 接手新项目要定策略 | 03 → 04 → 08 度量 → 09 RACI → 12 路线图 | 测试策略 + 风险登记册 |
| **C 要测 AI 系统** | 已有工程能力，缺 AI 判据 | 01 公理 → 07 分类决策树 → 对应维度 → 05 Oracle | Metric Card + 攻击集 |

页面内部的固定交互顺序（每页六段）：

```text
术语前置 ──► 方法判断表 ──► 反例（先遮住第三列自己判断）
   │                              │
   │                              ▼
   └──────────► 诊断树 ──► 演练（0/1/0 或手工步骤）──► 带走物
```

**反例段设计成「先遮住第三列」**，是因为只给正例学不会判断。判断不出来的那一条，就是当前团队最可能踩的坑。

## 0.10 本文档的证据边界

架构、逻辑与流程是**工程综合（Inference）**，由各章证据推导而来，需项目 owner 接受。
所有阈值（1600 字、3 张表、20% 重复率）是**分阶段实测值**，记录了当时的全站分布，不是行业基准。
整体成熟度 L1；L2–L5 全部 `NOT_RUN`，不得由本文档的完整性推断为已验证。
