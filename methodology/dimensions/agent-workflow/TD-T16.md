## TD-T16

### 参数错误比工具错误危险得多，而多数测试只测了工具选对没有

Agent 调错工具通常会失败得很响——报错、返回空、流程中断。调对工具但参数错了则会安静地成功，并把错误的结果写进系统。

第三条是金融与交易场景的核心风险。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 只测工具选择正确率，不测参数精确匹配 | 工具选择正确率 95% 听起来可接受，但参数精确匹配若只有 90%，实际正确执行率是两者的乘积约 85% | 把工具选择的达标读成动作执行的达标 |
| 靠 system prompt 约束高危动作 | 提示层约束在提示注入下可被击穿，实测攻击成功率在多数流行 Agent 上超过 60% | 以为写了「不要执行超过 X 的交易」就有了限额，实际限额根本不存在 |
| 不可逆动作没有幂等键 | 重试机制存在时，缺幂等键的转账类动作重复执行的概率不为 0；一次重复即构成资金事故 | 把「重试是为了可靠性」当成纯粹的好事 |

> 共同解法：把约束从提示层下沉到工具层与策略引擎，并把这些控制本身当成被测对象。

### 工具授权的四个词

工具调用是 Agent 唯一能对外造成真实影响的地方。这四个词决定它是否受控。

| 术语 | 一句话解释 |
| --- | --- |
| 最小 scope | 这个工具在这次调用中被授予的最小权限范围 |
| 参数边界 | 参数允许的取值范围；金额、数量、时间窗都属于此类 |
| 幂等键 | 保证重复调用只产生一次副作用的标识 |
| 写前授权 | 在副作用发生之前完成的检查链；它必须在模型之外 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[modelcontextprotocol/modelcontextprotocol](https://modelcontextprotocol.io/)*

### 工具选对了只是第一步，参数错误的破坏力大得多

多数 Agent 测试停在「有没有选对工具」这一层：该查订单时调了查订单接口，就算通过。但真正造成事故的通常不是选错工具，而是选对了工具、填错了参数——把退款金额多写一个零、把查询范围从单个用户扩大到全表、把删除条件写成永真。

参数错误更危险的原因是它更容易通过表面检查：工具名对、调用成功、返回 200，从轨迹上看一切正常。只有对参数本身做边界断言，才能把这类问题变成可检出的。

最小 scope 是从设计侧压缩这个风险面的手段：给 Agent 的工具不应该是「数据库查询」，而应该是「按用户 id 查该用户的订单」。能力越窄，参数错误的破坏上限就越低。这比事后检查参数更可靠，因为它把风险从运行时移到了设计时。

写前授权是不可逆动作的最后一道闸：任何有副作用的调用，在执行前必须经过一次独立于模型的检查——scope 是否允许、参数是否在边界内、幂等键是否存在。这道检查必须在代码里，不能写在提示词里，因为提示词是模型可以被说服绕过的东西。

*依据：[modelcontextprotocol/modelcontextprotocol](https://modelcontextprotocol.io/) · [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/)*

### 写前授权链的四个环节，缺一个就等于没有

这四个环节必须全部在代码路径上，不能有任何一个依赖模型自觉。第三列写的是「放在提示词里会怎样」——答案一律是可以被绕过。

MCP 的 schema 提供了前两环的机器可读基础，但它明确不覆盖后两环，那部分必须自己实现。

| 环节 | 检查什么 | 为什么不能靠提示词 | 边界 |
| --- | --- | --- | --- |
| 工具 scope | 这个会话是否被授权调用这个工具 | 提示词约束可被注入内容说服绕过 | scope 划分需按业务角色设计，不是技术分层 |
| 参数边界 | 金额上限、查询范围、条件是否可能命中全表 | 模型不保证第二次生成同样的参数 | 边界要人写；写不出边界说明业务规则本身没定义 |
| 幂等键 | 不可逆动作是否携带幂等键 | 重试会重放整条工具链，模型不保证走同一路径 | 幂等键要求下游真的实现了幂等，否则只是形式 |
| 写前放行 | 以上三项在执行前由代码统一裁决 | 写在提示词里等于把闸门交给被测对象 | 只覆盖被登记为「有副作用」的工具 |

> 四环合起来是一句话：模型可以决定做什么，但不能决定自己被允许做什么。

*依据：[modelcontextprotocol/modelcontextprotocol](https://modelcontextprotocol.io/) · [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/) · [protectai/llm-guard](https://protectai.github.io/llm-guard/)*

### 这张图的 6 个节点，本页各交付什么

这张图的每个节点都是一道可以被单独测试的控制。本页的核心主张是：测试对象是这些控制，而不是模型的服从性——服从性在注入下可以被击穿。

「Idempotency store」是唯一一个纯工程节点，但它承担的风险最高：它是不可逆动作重复执行的唯一防线。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| Identity verifier | 验证动作以谁的身份执行，测试身份伪造与委托链越权 | 身份与委托链测试集 |
| Tool registry | 维护工具清单及其描述 hash，检测工具定义变更 | 工具清单与 hash 台账 |
| Policy engine | 在工具层实施白名单与限额，测试限额本身而非模型服从性 | 策略规则与验证结果 |
| Sandbox adapter | 让高危动作在沙箱中执行，验证沙箱边界不可逃逸 | 沙箱逃逸测试结果 |
| Idempotency store | 为不可逆动作提供幂等键，验证重复执行被拦截 | 幂等性测试结果 |
| Human approval | 为不可逆且影响面大的动作强制人工确认，测试确认不可被绕过 | 人工确认绕过测试 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 写前授权链的七个环节

每个可写工具在执行前都要走完这条链。任一环缺失，都会在提示注入或参数错误时暴露。

右列写的是这一环缺失时会发生什么——每一条都对应一类真实事故。

| 环节 | 检查什么 | 缺失时会发生 |
| --- | --- | --- |
| 身份验证 | 调用者是谁 | 代他人执行操作 |
| 租户判定 | 属于哪个租户 | 跨租户操作 |
| 最小 scope | 是否有此工具的权限 | 越权调用 |
| 参数 Schema | 类型与必填 | 脏数据写入 |
| 参数边界 | 金额、数量是否越界 | 10 元变 1000 元被成功执行 |
| 幂等键 | 是否重复 | 重复退款 |
| 人工审批 | 高危动作是否已确认 | 不可逆动作无人知晓 |

> 七环全部在模型之外。模型只能提出候选调用，不能跳过其中任何一环。

*依据：[modelcontextprotocol/modelcontextprotocol](https://modelcontextprotocol.io/)*

### 这一页的验收口径：测控制，不测服从性

原因是它们都属于「一次即事故」的类别：一次越权、一次逃逸、一次重复转账，都不能用「99.9% 情况下没发生」来安慰。

T16-1 的参数精确匹配阈值高于工具选择，正是因为参数错误的失败是安静的——它不报错，只是做错。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| T16-1 | 动作正确性 | 工具选择正确率 ≥ 95%；参数精确匹配率 ≥ 98% | 每次发布 |
| T16-2 | 越权拦截 | 身份与委托链越权尝试的拦截率 = 100% | 每次发布 + 每周 1 次 |
| T16-3 | 沙箱边界 | 沙箱逃逸成功次数 = 0 | 每次发布 |
| T16-4 | 不可逆动作保护 | 重复提交时幂等拦截率 = 100%；高危动作二次确认率 = 100% | 每次发布 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在控制工具、实际控制不住的做法

这两种做法都写在很多 Agent 项目的设计文档里，评审时也很难被反对。

它们的共同问题是控制点在模型内部。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 在系统提示里写明不得调用退款工具，测试确认模型会拒绝 | 约束明确，测试也确实验证了模型的行为 | 提示约束在注入下可被击穿。要测的是绕过模型直接给工具发调用时，授权层拦不拦得住 |
| 工具返回 200 即认为调用成功 | 外部系统确认收到并处理了 | 返回码不代表业务状态正确。要断言的是副作用本身：写了几次、金额对不对、幂等键是否生效 |

> 两条的共同修法：把断言点从模型行为移到工具边界与业务状态。

### 出现意外副作用时按什么顺序查

意外副作用几乎总是授权链缺环。按七环顺序倒查，通常两三步就能定位。

定位之后的修复是补一环，而不是加强提示词。

| 症状 | 先怀疑哪一环 | 下一步 |
| --- | --- | --- |
| 数据被写了两次 | 幂等键 | 检查键的生成方式与作用域 |
| 金额或数量异常 | 参数边界 | 补上下界断言并测边界值 |
| 操作了别人的数据 | 租户判定 | 确认租户在授权层强制而非查询条件 |
| 不该发生的高危动作 | 人工审批 | 确认审批在执行前而非事后通知 |

> 四行的修复都在工具层。任何形式的「加强提示词」都不在这张表里。

### 绕过模型直接测授权链：约 45 分钟

这个演练的关键是不通过模型。直接构造工具调用，看授权层的反应。

1. 选一个可写工具，列出它的七环授权检查当前实现在哪里（代码位置或中间件）。
2. 绕过模型，直接构造一个越权调用：换一个没有权限的身份。断言它在执行前被拒绝。
3. 构造一个越界参数调用：金额取上界加一。断言被拒绝且不产生副作用。
4. 构造一次重复调用：同一幂等键连发两次。断言副作用只发生一次。
5. 检查拒绝时是否留下了原因、trace_id 与策略版本——没有留痕的拒绝无法审计。

**期望结果**：典型结果是七环里有两到三环并未实现，或者实现在模型提示里。这三次调用会把它们一次性暴露出来。

> ⚠ 演练必须在录制沙箱或隔离环境进行，并断言真实写入次数为零。不要在共享测试环境直接测可写工具。

### 这一页的出口判据

这一页的红线不接受任何统计式的辩解。越权与逃逸不是概率事件，是控制有没有生效的二元问题。

第三段要接受的是限额取值：单笔上限定在多少是业务决策，不是测试决策。测试负责证明这个限额真的会生效。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 越权尝试拦截率 < 100% 时阻断<br>沙箱逃逸成功次数 > 0 或幂等拦截率 < 100% 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 参数精确匹配率按工具类型分片给出 95% CI，单片 < 30 条时只报区间<br>攻击集样本 < 100 条时越权与逃逸结论记为证据不足，不得宣布通过 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 单笔限额与影响面上限的取值，由业务 owner 签字确定<br>未纳入沙箱的工具清单，由安全 owner 逐个列出并接受其风险 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/)*

### 带走一张工具授权链实现位置表

表的每一行写清这一环实现在哪里。写不出位置的环，就是当前不存在的环。

这张表同时是安全评审的输入：评审只需要问「这七环分别在哪」。

- 七环全部在模型之外实现
- 绕过模型直接测授权，不测模型服从性
- 断言副作用本身，不断言工具返回码

  - 能证明：LLM 应用的高频风险分类（提示注入、敏感信息泄露、供应链、过度代理权限等），可作为安全测试的风险起点与覆盖度检查表。
  - 不能证明：清单是风险分类不是验收标准，也不按你的业务排优先级。
  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理
- **[LLM Guard：模型输入输出的确定性管控层](https://protectai.github.io/llm-guard/)** — AI 侧防护实现
  - 能证明：一部分安全判定可以从「靠模型自我约束」移到模型之外的确定性代码路径上：输入侧的注入检测与脱敏、输出侧的敏感信息与有害内容过滤。移出来之后这层才是可测、可度量、可回归的。
  - 不能证明：过滤层本身有漏判与误判，两类错误率都必须单独度量。把它当成「加了就安全」是把一个概率组件当成了确定性边界。
  - `protectai/llm-guard` · 版本 v0.3.16 · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Model Context Protocol 规范](https://modelcontextprotocol.io/)** — 工具契约规范
  - 能证明：模型可调用的工具有了机器可读契约：名称、输入 schema、描述、错误返回。这让「Agent 能调什么工具」从代码里的隐含事实变成可审计、可版本化、可做契约测试的工件。
  - 不能证明：规范描述接口不描述权限。哪些工具允许被哪个会话调用、不可逆动作要不要二次确认，规范里没有，必须在工具调用层自己实现并验证。
