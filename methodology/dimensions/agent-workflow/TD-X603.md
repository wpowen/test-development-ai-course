## TD-X603

### 长期记忆是唯一一个会把今天的错误带到明天的组件

其余组件的错误随会话结束而消失。记忆不会——一条被污染的记忆会在此后每一次检索中继续生效，而且没有任何报错。

下面三条是记忆治理缺位的三种形态，第三条在多租户产品里是合规红线。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 记忆写入没有 TTL | 无 TTL 的偏好记忆会无限期生效；用户 6 个月前的 1 次临时选择仍在影响今天的输出 | 把「个性化不准」归因为模型，实际是记忆过期机制不存在 |
| 记忆投毒后无检测手段 | 污染注入的成功次数必须是 0，污染存活轮数也必须是 0；一条存活的污染记忆会持续影响后续所有会话 | 把间歇性的异常输出当成模型波动 |
| 语义缓存不区分租户 | 缓存键不含租户维度时，跨租户命中是必然而非偶然；1 次命中即构成数据泄露 | 缓存命中率很高被当成性能优化成果 |

> 解法是给记忆的每一次写入都附上同意、目的、TTL 与租户，并让删除产生可验证的回执。

### 长期记忆治理的四个词

记忆让 Agent 变得个性化，也让一次污染可以跨会话存活。这四个词是治理的基础。

| 术语 | 一句话解释 |
| --- | --- |
| 同意与目的 | 这条记忆是基于什么授权、为什么目的写入的 |
| 用户隔离 | 一个用户的记忆绝不能出现在另一个用户的上下文里 |
| TTL | 记忆的有效期；没有过期的个性化会持续放大早期误判 |
| 删除回执 | 用户要求删除后，可证明确实删掉的记录 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[evidentlyai/evidently](https://docs.evidentlyai.com/)*

### 长期记忆是唯一一个会把今天的错误带到明天的组件

无状态系统的错误是一次性的：这次答错了，下次重新开始。长期记忆改变了这个性质——一条错误结论被写进记忆之后，会在后续所有会话里被当成已知事实反复使用，而且越用越像真的。

这带来一个传统测试里不存在的被测属性：**错误的持久性**。测试必须覆盖「错误写入后多久会被发现、被发现后怎么清除、清除之后受影响的历史结论要不要回溯」。这三个问题在无状态系统里都不存在。

用户隔离是另一条硬边界。记忆按用户存储时，任何一个跨用户泄漏都是数据事故，且极难在功能测试中被发现——因为泄漏表现为「回答里出现了不该知道的信息」，而这在功能上看起来完全正常。

TTL 与删除回执把记忆纳入合规范围。用户要求删除时，系统必须能证明删除已经发生且不可恢复；仅从检索结果里过滤掉不算删除。这一条是记忆治理里唯一有外部法律约束的部分，因此它的判据必须是可审计的回执而不是日志。

*依据：[evidentlyai/evidently](https://docs.evidentlyai.com/) · [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/)*

### 记忆生命周期的五个环节与各自的检查

五个环节按时间顺序排列。前两环决定什么能进记忆，中间两环决定它能存多久、被谁看到，最后一环决定它怎么出去。

最容易缺的是第一环与第五环：写入没有校验，删除只做了过滤。两者都不会在功能测试里暴露。

| 环节 | 检查什么 | 验证手段 | 缺失的后果 |
| --- | --- | --- | --- |
| 写入准入 | 什么内容允许进入长期记忆，是否经过校验 | 构造带错误结论的会话，断言不被写入或被标记为低置信 | 错误一旦写入会在后续所有会话里被复用 |
| 用户隔离 | 记忆是否严格按用户隔离 | 跨用户探测：用 A 的记忆内容向 B 提问 | 泄漏在功能上看起来完全正常，极难被发现 |
| TTL 与时效 | 记忆是否有生效期，过期是否失效 | 时间推进测试，断言过期记忆不再被检索 | 陈旧数据加正确推理等于错误结论 |
| 纠错与回溯 | 错误记忆被发现后如何清除、历史结论是否回溯 | 注入错误记忆，验证清除路径与影响范围 | 清除了但基于它产生的结论仍在流通 |
| 删除回执 | 用户请求删除时能否证明已删除且不可恢复 | 删除后从存储层直接核验，不看应用层过滤 | 仅做检索过滤不构成删除，存在合规风险 |

> 五环里只有第二环和第三环有现成工具可用，其余三环都是工程约定——这是记忆治理容易被跳过的原因。

*依据：[evidentlyai/evidently](https://docs.evidentlyai.com/) · [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/) · [protectai/llm-guard](https://protectai.github.io/llm-guard/)*

### 记忆生命周期的五个环节与各自的检查

记忆的问题不在写入那一刻，而在它长期存在的过程中。五个环节各有各的失效方式。

右列的检查都可以做成自动断言，不需要人工审查每条记忆。

| 环节 | 失效方式 | 可自动化的检查 |
| --- | --- | --- |
| 写入 | 把不该记的记下来 | 写入前的目的与同意校验 |
| 检索 | 跨用户召回 | 按用户与租户强制过滤 |
| 使用 | 陈旧记忆影响当前判断 | 检查记忆时间戳与 TTL |
| 更新 | 旧误判被不断强化 | 记录来源与置信度 |
| 删除 | 删了但缓存里还有 | 删除回执 + 缓存失效验证 |

> 最后一行最容易被漏：主存删了，语义缓存和向量索引里往往还留着。

*依据：[OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/)*

### 这一页的验收口径：隔离、过期、可删除

本页四条指标里有三条要求绝对值，因为它们都涉及跨用户的数据边界——这类问题不存在「大部分情况下没发生」这种说法。

X603-2 的污染存活轮数是记忆特有的指标：它测的不是能否注入，而是注入之后能存活多久，后者决定了实际危害。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| X603-1 | 租户隔离 | 跨租户记忆与缓存命中次数 = 0 | 每次发布 + 每周 1 次 |
| X603-2 | 记忆投毒 | 污染注入成功次数 = 0；污染存活轮数 = 0 | 每次发布 |
| X603-3 | TTL 有效性 | 到期记忆仍被检索命中的次数 = 0 | 每次发布 |
| X603-4 | 删除可验证 | 删除请求产生可核对回执的比例 = 100%；删除后残留命中次数 = 0 | 每次发布 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在做记忆治理、实际留有通道的做法

这两种做法都实现了删除功能，也通过了功能测试。

问题是删除的范围不完整。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 用户请求删除后从记忆库删除对应记录，返回成功 | 功能实现完整，也返回了确认 | 语义缓存与向量索引里的副本通常不会被同步删除。下一次相似提问仍可能命中已删除的内容 |
| 记忆按用户 ID 隔离，查询时带上用户条件 | 隔离逻辑清晰，代码里也确实过滤了 | 隔离必须在授权层强制，而不是依赖查询条件。一次遗漏的查询就会造成跨用户召回，且很难被测试覆盖 |

> 两条的共同要求：删除与隔离都要覆盖全部副本与全部访问路径。

### 怀疑记忆污染或泄露时按什么顺序查

记忆问题的证据分散在多个存储里。下表给出逐个排查的顺序。

排查前先确认哪些地方存了记忆的副本——通常比设计文档里列的多。

| 症状 | 先查什么 | 验证方式 |
| --- | --- | --- |
| 用户看到别人的信息 | 检索层的隔离 | 用另一用户身份重放同一查询 |
| 删除后仍然出现 | 缓存与索引副本 | 逐个存储确认删除 |
| 早期误判一直被强化 | 更新逻辑与置信度 | 查该条记忆的来源链 |
| 个性化越来越不准 | 缺 TTL | 检查最老的活跃记忆时间 |

> 第一行的验证方式最有效：换个身份重放，比读代码更快也更可靠。

### 做一次删除完整性验证：约 45 分钟

重点是找到所有副本，而不是验证删除接口本身。

1. 列出记忆可能存在的全部位置：主库、向量索引、语义缓存、会话上下文、日志。
2. 写入一条带唯一标识的测试记忆，确认它出现在上述每个位置。
3. 调用删除接口，然后逐个位置检查是否真的消失。
4. 用一个语义相近但措辞不同的提问触发检索，确认不会命中已删除内容。
5. 把结果写成删除回执格式：删了哪些位置、哪些位置确认无残留、由谁验证。

**期望结果**：典型结果是主库删除成功，但缓存或索引里仍有残留。这个残留通道就是本次演练最有价值的产出。

> ⚠ 测试记忆要用明显的唯一标识，避免与真实数据混淆。演练结束后确认它在所有位置都已清除。

### 这一页的出口判据

记忆相关的门禁全部是红线型的，因为它的失败具有持久性：一次污染或泄露不会随会话结束而消失。

第三段要接受的是个性化质量与记忆保守程度之间的取舍：TTL 越短越安全，个性化效果也越弱。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 跨租户记忆或缓存命中次数 > 0 时阻断，并按数据事件流程上报<br>污染存活轮数 > 0 或到期记忆命中次数 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 跨租户命中率按攻击集样本给出 95% CI 上界；样本 < 100 条时结论记为证据不足<br>记忆命中质量按用户分层统计，禁止用整体命中率代替分层结论 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | TTL 取值在安全性与个性化效果之间的取舍，由产品 owner 签字确定<br>已知无法完全删除的派生数据范围，由数据 owner 列出并接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[evidentlyai/evidently](https://docs.evidentlyai.com/)*

### 带走一张记忆副本位置清单

清单列出记忆存在的每一个位置。删除与隔离的验证都要覆盖清单上的全部条目。

清单会随架构演进增加条目——新增任何缓存或索引时都要更新它。

- 隔离在授权层强制，不靠查询条件
- 删除要覆盖全部副本并出具回执
- 给记忆设 TTL 并记录来源与置信度
