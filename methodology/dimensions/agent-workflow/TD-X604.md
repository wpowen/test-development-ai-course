## TD-X604

### Fallback 是为了可用性设计的，它同时也是权限检查最容易被绕过的地方

路由与 fallback 的设计目标是「主路径不可用时还能继续」。这个目标如果实现得过于彻底，就会连带绕过为主路径设置的那些检查。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| Fallback 路径未重新做权限与区域检查 | 主路径的合规检查在 fallback 上缺失时，越权与跨区域调用的拦截率会从 100% 掉到 0 | 「已实现多 Provider 容灾」被当成纯粹的可靠性提升 |
| 工具 Schema 静默变更 | 工具清单的 hash 校验若未启用，工具描述在连接后被修改（rug-pull）的检出率 = 0 | 把参数错误归因于模型，实际是工具定义变了 |
| Provider 切换后幂等语义不一致 | 不同 Provider 对重试与幂等的实现可能不同；切换后副作用重复发生的风险不为 0 | 容灾演练只测了「能不能切过去」，没测「切过去之后语义是否一致」 |

> 本页的做法：把每一次路由、fallback、协议变更都当成一次需要重新验收的变更，而不是一次配置调整。

### 路由与漂移的四个词

多模型、多 Provider、多工具的系统里，每一次切换都是一次未经测试的组合。

| 术语 | 一句话解释 |
| --- | --- |
| 模型路由 | 按任务、成本或可用性把请求分给不同模型 |
| Fallback | 主路径不可用时的替代；它的能力边界与主路径不同 |
| 协议漂移 | 工具或 Provider 的接口、Schema、语义在版本间变化 |
| 能力矩阵 | 每个模型或工具在各能力维度上的实际表现；它必须实测 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[stanfordnlp/dspy](https://dspy.ai/)*

### Fallback 是为可用性设计的，也是权限检查最容易被绕过的地方

模型路由与 fallback 的动机是可用性：主模型超时或限流时自动切到备用模型，请求不至于失败。这个设计本身没问题，问题在于切换路径通常是后加的，因此它经常绕过了主路径上已经建好的检查。

具体形态是：主路径有输出过滤、有工具授权检查、有敏感词拦截，而 fallback 路径为了「尽快返回」直接调了模型 API。于是同一个请求走主路径被拦、走备用路径通过——攻击者只需要制造一次超时。

协议漂移是第二类风险：不同模型的结构化输出能力、工具调用格式、停止条件语义都不同。主模型能稳定返回合法 JSON，备用模型可能返回带解释文字的 JSON——下游解析随之失败，而这个失败只在切换时出现，日常测试碰不到。

因此每次切换都必须被当成一次新的调用来完整检查，而不是复用主路径的结论。能力矩阵就是这件事的工件：把每个候选模型在结构化输出、工具调用、上下文长度、安全策略上的能力逐项列出，切换前先比对差异。

*依据：[stanfordnlp/dspy](https://dspy.ai/) · [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/)*

### 每次切换必须重新检查的四项

这张表的前提是：fallback 不是「同一个请求换个地方跑」，而是一次全新的调用。任何在主路径上成立的结论，都不能自动迁移过去。

第四列写的是不重新检查的具体后果，全部是实际发生过的形态而不是理论风险。

| 检查项 | 为什么切换后要重查 | 验证手段 | 不重查的后果 |
| --- | --- | --- | --- |
| 安全与过滤链 | fallback 路径通常为了快而绕过主路径的检查 | 强制触发 fallback，重跑全套安全用例 | 攻击者制造一次超时即可绕过全部拦截 |
| 结构化输出 | 不同模型的 JSON 能力与格式不同 | 在 fallback 模型上重跑结构断言 | 下游解析失败，且只在切换时出现 |
| 工具调用格式 | 工具调用协议与参数序列化方式各家不同 | 在 fallback 模型上重跑工具契约测试 | 工具调用静默失败或参数被截断 |
| 能力矩阵比对 | 上下文长度、停止条件、安全策略都可能不同 | 切换前逐项比对候选模型能力矩阵 | 长上下文请求在备用模型上被截断，回答看似正常 |

> 四项的共同点：它们在主路径上都已经被验证过，因此最容易被认为不必再验证一次。

*依据：[stanfordnlp/dspy](https://dspy.ai/) · [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/) · [python-jsonschema/jsonschema](https://python-jsonschema.readthedocs.io/) · [modelcontextprotocol/modelcontextprotocol](https://modelcontextprotocol.io/)*

### 这张图的 7 个节点，本页各交付什么

这张图的核心主张体现在「Fallback 再授权」这个节点上：fallback 不是绕过检查的快捷路径，它必须重新走一遍授权。

最右侧的「Trace/回滚」保证任何一次路由决策都可追溯，这是事后归因的前提。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 请求合同 | 定义请求的能力要求、区域要求与权限要求，作为路由判据 | 请求合同定义 |
| 能力/区域/权限 | 验证候选 Provider 是否满足合同，不满足则不得作为 fallback | 候选合规矩阵 |
| Provider 路由 | 验证路由决策可复现且被记录 | 路由决策日志 |
| 协议/Schema | 校验工具与接口 Schema 的 hash，检测静默变更 | Schema hash 台账 |
| Fallback 再授权 | 验证 fallback 路径重新执行了全部授权检查 | fallback 授权验证 |
| 副作用门禁 | 验证切换后幂等与副作用语义一致 | 跨 Provider 幂等验证 |
| Trace/回滚 | 记录路由与切换全过程，并验证回滚可执行 | 切换 trace 与回滚演练 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 每次切换必须重新检查的六项

切换不是配置变更，是换了一个被测系统。下表六项每次都要重查。

右列写的是跳过检查时的典型后果——多数在切换后的第一次高峰暴露。

| 切换后重查什么 | 为什么 | 跳过的后果 |
| --- | --- | --- |
| 能力边界 | 不同模型擅长的任务不同 | fallback 后质量骤降无人知晓 |
| 区域与合规 | 数据可能被路由到不同区域 | 合规违规 |
| 权限与配额 | 不同 Provider 的权限模型不同 | 越权或限流 |
| Schema 与字段 | 工具版本间字段可能变化 | 静默的数据丢失 |
| 幂等语义 | 不同实现的幂等保证不同 | 重复副作用 |
| 副作用范围 | 同名工具在不同实现下影响面不同 | 超出预期的影响 |

> 六项里前两项属于治理，后四项属于工程。全部通过后这次切换才算被测试过。

*依据：[python-jsonschema/jsonschema](https://python-jsonschema.readthedocs.io/)*

### 这一页的验收口径：fallback 与主路径同等严格

X604-1 是本页唯一需要记住的一条：fallback 路径的权限拦截率必须与主路径完全一致。任何低于主路径的数字都意味着存在一条绕过检查的通路。

X604-2 的 Schema hash 校验成本极低而收益很高——它是检测工具描述被静默修改的唯一低成本手段。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| X604-1 | fallback 授权一致 | fallback 路径的权限与区域拦截率 = 100%，与主路径完全一致 | 每次发布 + 每次路由变更 |
| X604-2 | 协议漂移检测 | 工具与接口 Schema hash 校验覆盖率 = 100%；未声明的 Schema 变更放行次数 = 0 | 每次连接 + 每日 |
| X604-3 | 跨 Provider 语义一致 | 切换后副作用重复发生次数 = 0；幂等语义差异项数 = 0 | 每次 Provider 变更 |
| X604-4 | 回滚可执行 | 回滚演练成功率 = 100%；回滚耗时 ≤ 5 分钟 | 每季度 1 次 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在做高可用、实际引入未测组合的做法

这两种做法都提高了可用性数字，架构上也很标准。

问题是替代路径本身没有被当作一个被测系统。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 主模型不可用时自动切到备用模型，可用性显著提升 | 故障转移是标准高可用做法，切换也确实生效 | 备用模型的能力边界、区域、权限与幂等语义都不同。切过去之后系统进入了一个从未被完整测试的状态 |
| 工具升级到新版本，接口兼容所以无需回归 | 接口签名没变，兼容性声明也支持 | 语义可能变了：同名字段含义改变、幂等窗口缩短、副作用范围扩大。接口兼容不等于语义兼容 |

> 两条的共同修法：把每个替代路径与每次工具升级当作一次需要完整回归的变更。

### 切换后出现异常时按什么顺序查

切换相关的问题有明显特征：在特定时间段或特定流量比例下集中出现。

按下表六项顺序逐个排除，通常两三步内定位。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 某段时间质量集体下降 | fallback 被触发 | 查路由日志中的实际去向 |
| 部分请求报权限错误 | Provider 权限模型不同 | 比对两侧的 scope 定义 |
| 字段偶尔为空 | Schema 漂移 | 比对新旧版本的字段语义 |
| 出现重复副作用 | 幂等语义不同 | 确认新实现的幂等窗口 |
| 合规审计告警 | 区域路由 | 查数据实际经过的区域 |

> 第一行的查法最关键：很多团队的路由日志不记录实际去向，导致这类问题无法归因。

### 给一条 fallback 路径做完整回归：约 60 分钟

把 fallback 当作主路径来测一遍——这正是它被触发时的角色。

1. 强制把流量路由到 fallback 路径，而不是等待故障发生。
2. 在 fallback 上跑一遍主路径的完整测试集，记录哪些用例失败。
3. 逐项检查六项：能力边界、区域、权限、Schema、幂等、副作用范围。
4. 对失败的用例判断：是 fallback 能力不足，还是配置差异导致。
5. 为 fallback 单独设一条质量下限，低于它时宁可返回明确失败也不返回低质结果。

**期望结果**：典型结果是 fallback 上有一批用例失败，而此前从未有人跑过。这批失败就是它被触发时用户会遇到的问题。

> ⚠ 强制路由演练要限定时长与流量比例，并提前通知相关方。fallback 路径的容量通常低于主路径。

### 这一页的出口判据

这一页的门禁把「变更」的定义扩大了：换 Provider、换 MCP server、工具描述改一个字，都算变更，都要重新验收。

第三段要接受的是容灾能力与验收成本之间的取舍：Provider 越多可用性越高，需要验收的组合也越多。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | fallback 路径权限拦截率 < 100% 时阻断<br>未声明的 Schema 变更放行次数 > 0 或跨 Provider 副作用重复次数 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 各 Provider 的质量指标分别给出 95% CI，禁止用主 Provider 的数据代表全部<br>单 Provider 样本 < 30 条时该 Provider 结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 纳入 fallback 的 Provider 范围与验收成本，由架构 owner 签字确定<br>各 Provider 之间已知的质量差异，由产品 owner 在知情前提下接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/)*

### 带走一份 fallback 能力矩阵

矩阵按能力维度列出主路径与每条 fallback 的实测表现，而不是供应商宣称的能力。

它同时定义了 fallback 的质量下限：低于下限时，明确失败比低质结果更安全。

- 每条 fallback 跑一遍主路径的完整测试集
- 六项逐一重查，接口兼容不等于语义兼容
- 为 fallback 单独设质量下限与可见的降级标记

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[jsonschema：JSON Schema 校验实现](https://python-jsonschema.readthedocs.io/)** — 结构断言实现
  - 能证明：结构层断言可以脱离具体框架独立运行，包括在 LLM 结构化输出上——这是传统 Schema 校验能力迁移到 AI 系统时最直接的一条通路。
  - 不能证明：校验通过只说明形状对。LLM 返回一个字段齐全、类型正确但内容编造的 JSON，Schema 校验会放行。
  - `python-jsonschema/jsonschema` · 版本 v4.26.0（2026-01-07） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/)** — AI 侧风险清单
  - 能证明：LLM 应用的高频风险分类（提示注入、敏感信息泄露、供应链、过度代理权限等），可作为安全测试的风险起点与覆盖度检查表。
  - 不能证明：清单是风险分类不是验收标准，也不按你的业务排优先级。
  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理

  - 能证明：模型可调用的工具有了机器可读契约：名称、输入 schema、描述、错误返回。这让「Agent 能调什么工具」从代码里的隐含事实变成可审计、可版本化、可做契约测试的工件。
  - 不能证明：规范描述接口不描述权限。哪些工具允许被哪个会话调用、不可逆动作要不要二次确认，规范里没有，必须在工具调用层自己实现并验证。
  - `modelcontextprotocol/modelcontextprotocol` · 版本 2026-07-28（2026-07-28） · NOASSERTION · 许可证未能自动判定，按最保守口径只链接不搬代码
- **[DSPy：把 Prompt 当作可编译、可优化的程序](https://dspy.ai/)** — Prompt 工程结构
  - 能证明：Prompt 可以与签名（输入输出规格）和优化器分离：签名声明要什么，优化器根据指标自动搜索具体措辞。这把「调 Prompt」从手工试错变成有目标函数、可复现的过程。
  - 不能证明：优化目标就是你给的指标。指标写错时，它会非常高效地把系统优化到错误方向。
  - `stanfordnlp/dspy` · 版本 3.3.0（2026-08-03） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
