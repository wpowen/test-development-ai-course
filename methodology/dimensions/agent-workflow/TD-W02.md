## TD-W02

### 长流程最贵的失败不是做错，是不停下来

短流程的失败会很快暴露。长流程的失败可以持续很久而没人发现，因为它看起来还在工作——这类失败的成本按时间累积，而不是按次数累积。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 没有步数、时间、成本三重熔断 | 缺熔断时失控循环可以持续很久：公开案例中出现过 Agent 在对账任务里连续运行 11 天 | 把「还在处理中」当成正常状态，账单出来才发现 |
| 重试机制没有幂等保护 | 队列的至少一次投递语义下，缺幂等键的 Worker 重复执行是必然而非偶然；1 次重复扣款即构成资金事故 | 把重复扣款归因为「偶发 bug」，实际是投递语义的必然结果 |
| 交接时信息丢失 | 每经过 1 跳交接就损失一部分上下文；走完 3 跳后源头埋入的 5 个可验证事实通常存活不足一半 | 把下游的错误归给下游模型，实际是上游没把信息传下去 |

> 三条对应三类必测故障：不终止、重复执行、交接失真。本页的演练就是逐一注入它们。

### 长流程可靠性的四个词

长流程的失败几乎都发生在中断与恢复处。这四个词描述它们。

| 术语 | 一句话解释 |
| --- | --- |
| checkpoint | 可恢复的状态快照；崩溃后从这里继续而不是从头开始 |
| 至少一次语义 | 消息可能被重复投递；这是队列的常态而非异常 |
| Handoff | 任务在组件或人之间转移；权限不得随之扩大 |
| stop_reason | 停止的机器可读原因；没有它就分不清正常完成与撞上限 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[langchain-ai/langgraph](https://langchain-ai.github.io/langgraph/)*

### 长流程最贵的失败不是做错，是不停下来

短流程的失败模式是「做错了」，它会报错、会有异常、会被监控抓到。长流程多了一种更贵的失败模式：不收敛。系统没有报错，每一步看起来都在正常工作，只是永远到不了终点——而账单在持续累积。

监控看不到它，因为从任何单点指标看都正常：错误率是零，延迟是正常的，服务是健康的。唯一的异常信号是「这个任务还在跑」，而这在长流程系统里本来就是常态。

因此长流程必须自带三重熔断：步数上限、时间上限、成本上限。三者缺一不可——只设步数，一个慢工具就能把时间拖长；只设时间，高频廉价循环仍会烧掉预算。而且每一重都必须被单独注入验证过真的会触发，配置了不等于生效。

checkpoint 与至少一次语义是另一半：长流程必然会遇到重启，而重启点如果没有幂等保护，恢复本身就会重复执行副作用。stop_reason 则是让这一切可诊断的字段——每次终止都必须记录是正常完成、达到哪一重上限、还是被外部中断。

*依据：[langchain-ai/langgraph](https://langchain-ai.github.io/langgraph/) · [resilience4j/resilience4j](https://resilience4j.readme.io/docs)*

### 四类故障注入与各自的期望行为

这张表是长流程测试的最小集合。四类注入对应四类真实故障，每一类的期望行为都必须被明确断言，而不是「没崩就算过」。

第三列写的是期望行为——这是本页最需要提前与业务确认的部分，因为「超时之后应该怎么办」通常没有现成答案。

| 注入什么 | 模拟的真实故障 | 期望行为 | 验证手段 |
| --- | --- | --- | --- |
| 工具持续返回可重试错误 | 依赖抖动、限流 | 触发重试预算上限后停止，stop_reason 记录原因 | WireMock 构造持续 5xx |
| 中途进程重启 | 部署、OOM、节点故障 | 从最近 checkpoint 恢复，已提交副作用不重复执行 | 强制杀进程 + 幂等键断言 |
| 模型持续返回不收敛的下一步 | 任务本身无解或提示词有缺陷 | 步数 / 时间 / 成本任一上限触发即停 | 构造无解任务，断言三重熔断各自会触发 |
| Handoff 目标不可用 | 下游服务宕机、人工队列积压 | 明确失败并保留完整上下文，不静默丢弃 | 关闭下游，检查上下文是否完整保留 |

> 四行的共同要求是：终止必须是显式的、带原因的。静默停止与静默继续，是长流程系统里两种同样糟糕的结局。

*依据：[langchain-ai/langgraph](https://langchain-ai.github.io/langgraph/) · [wiremock/wiremock](https://wiremock.org/docs/) · [resilience4j/resilience4j](https://resilience4j.readme.io/docs) · [Shopify/toxiproxy](https://github.com/Shopify/toxiproxy#readme)*

### 四类故障注入与各自的期望

长流程测试的价值全在故障注入。不注入故障，测的只是晴天路径。

右列写的是正确行为——注意每一条都要求留下可观察的痕迹。

| 注入什么 | 期望行为 | 必须留下的痕迹 |
| --- | --- | --- |
| 写入后崩溃再重投 | 副作用只发生一次 | 幂等键命中记录 |
| checkpoint 丢失 | 从上一个有效点恢复 | 恢复位置日志 |
| Handoff 目标错误 | 拒绝并升级人工，权限不扩大 | 拒绝原因与升级记录 |
| 移除终止信号 | 在预算内停止 | stop_reason 与预算类型 |

> 四类都要求「留下痕迹」。没有痕迹的正确行为无法与侥幸区分。

*依据：[resilience4j/resilience4j](https://resilience4j.readme.io/docs)*

### 这一页的验收口径：三重熔断必须逐一验证

W02-3 要求的不是「设置了熔断」，而是「验证了熔断会触发」。这两者的差距在真实项目里非常大——配置存在但不生效是常见形态。

W02-4 的交接保真率用一个可验证的方法测量：在源头埋入 5 个可验证事实，走完全部交接后检查存活几个。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| W02-1 | 状态恢复 | 注入状态丢失后可恢复继续执行的比例 ≥ 95%；不可恢复的须能安全终止 | 每次发布 |
| W02-2 | 幂等性 | 重复投递下副作用重复发生的次数 = 0 | 每次发布 |
| W02-3 | 熔断有效性 | 步数 / 时间 / 成本三重熔断各自的实测触发率 = 100%（逐一注入验证） | 每次发布 |
| W02-4 | 交接保真 | 源头埋入 5 个可验证事实，走完全部交接后存活率 ≥ 95% | 每次发布 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在提高可靠性、实际在放大风险的做法

这两种做法在故障发生后往往是第一反应，短期也确实有效。

问题是它们把风险推到了更贵的地方。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 失败就重试，重试次数从三次提到十次，成功率提升 | 成功率确实上去了，实现成本也低 | 没有幂等保护时，重试次数就是重复副作用的次数。而且依赖抖动时十次重试会把故障放大成雪崩 |
| 为避免中断，把任务超时从十分钟延长到两小时 | 长任务确实需要更长时间，延长很自然 | 延长超时会让失控循环跑得更久。正确做法是设步数与成本上限，并保证撞上限时留下 stop_reason |

> 两条的共同修法：先保证幂等与预算护栏，再谈重试与超时。

### 长流程偶发异常时按什么顺序查

长流程的异常往往在中间态，而中间态默认不被记录。下表给出各症状的补采集点。

补齐之后，「偶发」通常会变成可稳定复现。

| 症状 | 先怀疑 | 查什么 |
| --- | --- | --- |
| 数据重复 | 幂等失效 | 幂等键的作用域与过期时间 |
| 任务卡住不动 | checkpoint 丢失 | 恢复点日志与队列可见性超时 |
| 下游拿到不该有的权限 | Handoff 扩权 | 交接时的身份与 scope 变化 |
| 任务跑很久才停 | 无预算护栏 | 是否有步数、时间、成本上限 |
| 无法区分完成与被砍 | 缺 stop_reason | 补机器可读的停止原因 |

> 最后一行影响所有统计：把撞上限算成完成，成功率会被系统性高估。

### 做一次崩溃恢复演练：约 55 分钟

核心是让崩溃发生在写入之后、确认之前——这是最容易出重复副作用的窗口。

1. 选一条含写操作的长流程，找到写入与消息确认之间的那个瞬间。
2. 在这个位置注入崩溃，让消息未被确认。
3. 让队列重新投递同一条消息，观察副作用是否发生第二次。
4. 检查恢复位置：是从 checkpoint 继续，还是从头开始重跑。
5. 最后移除终止信号，验证步数或成本上限会停止流程并写下 stop_reason。

**期望结果**：产出是四项结果：副作用次数、恢复位置、幂等键是否命中、stop_reason 是否写入。任一项不理想都对应一个明确修复。

> ⚠ 演练要在独立队列上做。共享队列上注入崩溃会影响其他消费者，也会污染结果。

### 这一页的出口判据

这一页的门禁全部依赖故障注入。没有注入就没有证据——一个从未被触发过的熔断，和不存在的熔断在工程上等价。

第三段要接受的是熔断阈值：步数上限、时间上限、成本上限定在多少，是业务与成本的取舍，测试只负责证明它们生效。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 三重熔断中任一项的实测触发率 < 100% 时阻断<br>重复投递下副作用重复发生次数 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 状态恢复率与交接保真率给出 95% CI 下界与阈值比较<br>故障注入样本 < 30 条时该项结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 步数、时间、成本三个上限的取值，由业务 owner 签字确定<br>不可恢复但可安全终止的场景比例，由产品 owner 知情接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[langchain-ai/langgraph](https://langchain-ai.github.io/langgraph/)*

### 带走一份故障注入清单与恢复证据

清单四行，每行写明注入方式、期望行为与必须留下的痕迹。

它同时是发布准出的一部分：改动过状态机或队列配置后，这四条要重跑。

- 崩溃点选在写入后确认前
- 断言副作用次数而不是最终状态
- 预算护栏必须留下 stop_reason

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[WireMock：HTTP 依赖打桩与故障注入](https://wiremock.org/docs/)** — 依赖隔离与故障注入
  - 能证明：把上游依赖替换成可编程的桩，让超时、5xx、慢响应、错误 body 这些平时碰不到的路径变成可稳定重复的用例。稳定性专项里绝大多数场景需要它才能构造。
  - 不能证明：桩的行为是你编的。真实依赖的失败形态可能与你的假设完全不同——桩测试通过不代表真实降级路径有效。
  - `wiremock/wiremock` · 版本 3.13.2（2025-11-14） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Resilience4j：熔断、限流、重试与舱壁](https://resilience4j.readme.io/docs)** — 稳定性专项实现
  - 能证明：熔断器的状态机（CLOSED / OPEN / HALF_OPEN）、滑动窗口统计、以及重试与熔断组合时的相互作用。它把「降级」从口号变成有明确状态与阈值的可测对象。
  - 不能证明：配置了熔断不等于降级路径正确。熔断打开后返回什么、业务是否可接受，必须单独验证。
  - `resilience4j/resilience4j` · 版本 v2.4.0（2026-03-14） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Toxiproxy：TCP 层网络故障注入代理](https://github.com/Shopify/toxiproxy#readme)** — 故障注入
  - 能证明：延迟、带宽限制、连接中断、慢关闭这些网络层故障可以按需注入且可编程开关，让超时与重试逻辑真正被执行到，而不是只存在于配置文件里。
  - 不能证明：注入的是网络层症状，不是依赖服务的真实故障语义（如半提交、脏数据）。
