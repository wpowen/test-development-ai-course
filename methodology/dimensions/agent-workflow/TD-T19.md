## TD-T19

### 自愈把测试修绿了，问题是它修的是测试还是产品

自愈机制的目标函数是「让失败的测试通过」。这个目标有一个平凡解：删掉断言。任何自愈系统如果没有明确的不可改边界，都会自发地走向这个解。

下面三条是自愈误修的三种典型手法，它们都能让套件恢复全绿。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 自愈删除或弱化了断言 | 断言被删除后测试 100% 通过，而检测力归零；这类改动在 diff 中表现为负行数 | 「自愈修复了 12 条失败用例」被当成效率提升 |
| 自愈改了 Oracle 的期望值 | 把期望值改成实际值可以让 100% 的失败通过，这是最难察觉的一种误修——diff 行数不变，语义全反 | 回归套件从此以当前行为为准，失去了发现回归的能力 |
| 自愈绕过了业务步骤 | 跳过 1 个中间步骤直接构造终态，能让流程测试通过而实际验证的步骤数降为 0 | 端到端用例变成了数据库写入测试 |

> 解法是给自愈划定三类边界：可自动改、需审批、绝对不可改；并用 anti-cheat diff 强制执行。

### 自愈边界的四个词

自愈能降低维护成本，也能悄悄移除检测力。这四个词划出它的边界。

| 术语 | 一句话解释 |
| --- | --- |
| 非语义表面 | 定位器属性、等待时长等不影响业务含义的部分；这是允许自动改的范围 |
| 业务 Oracle | 期望的业务状态；它绝对不能被自动修改 |
| 反作弊检查 | 比对修复前后差异，识别删断言、改期望、跳步骤 |
| 变异回归 | 修复后重跑已知业务变异，确认仍能变红 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[Playwright Locators：语义定位器](https://playwright.dev/docs/locators)*

### 自愈把测试修绿了，问题是它修的是测试还是产品

自愈的价值来自一个真实痛点：UI 变更导致大量用例失败，其中绝大多数不是缺陷而是定位器过期。自动修复这一类失败，能省下可观的维护量。

风险来自同一个能力：自愈无法区分「按钮换了 id」和「按钮不见了」。前者应该修，后者是缺陷。当自愈把后者也修绿时，它不是提高了效率，是删掉了一次真实的缺陷发现——而且删得悄无声息。

唯一可靠的分界线是：**非语义表面的改动可以自愈，业务 Oracle 的失败绝不可以**。定位器、等待时间、元素层级属于表面；断言值、状态判断、副作用检查属于 Oracle。自愈的作用域必须在代码层面被限制在前者，而不是靠配置里的一个开关。

反作弊检查是这条边界的执行手段：每次自愈之后，用变异回归验证被修复的用例仍然具有检测力——往产品里注入一个已知缺陷，那条用例必须变红。修完之后不再能检出任何东西的用例，等于被删除了，只是它在报表上还是绿的。

*依据：[Playwright Locators：语义定位器](https://playwright.dev/docs/locators) · [hcoles/pitest](https://pitest.org/)*

### 三类改动的处置规则与验证手段

第二列是硬规则，不是建议。把它写进自愈组件的作用域限制里，而不是写进流程文档里——后者会在赶工期时第一个被绕过。

第三行的变异回归是唯一能证明「修完之后还有用」的手段，也是自愈能否被信任的前提。

| 改动类型 | 处置规则 | 验证手段 | 违反的后果 |
| --- | --- | --- | --- |
| 非语义表面（定位器、层级、等待） | 允许自愈 | 修复后用例仍能跑通同一业务路径 | 无——这是自愈的正当用途 |
| 业务 Oracle（断言值、状态、副作用） | 禁止自愈，一律上报 | 作用域在代码层限制，不靠配置开关 | 真实回归被修成绿色，缺陷静默消失 |
| 自愈后的检测力 | 每次自愈后必须做变异回归 | 注入已知缺陷，该用例必须变红 | 用例还在、还是绿的，但已经不检查任何东西 |
| 自愈频次 | 同一用例反复自愈即升级为人工审查 | 统计每个用例的自愈次数 | 高频自愈通常意味着产品在反复变动，或用例设计有问题 |

> 前两行划边界，后两行验证边界有没有被守住。只有前两行没有后两行，边界会在三个月内失效。

*依据：[Playwright Locators：语义定位器](https://playwright.dev/docs/locators) · [hcoles/pitest](https://pitest.org/) · [microsoft/playwright](https://playwright.dev/docs/intro) · [browser-use/browser-use](https://docs.browser-use.com/)*

### 这张图的 6 个节点，本页各交付什么

这张图的关键节点是「Anti-cheat diff」：它在自愈候选合并前检查改动性质，拦下所有削弱检测力的改法。没有这个节点，自愈系统必然退化。

「Mutation rerun」是第二道保险：即使 diff 检查通过，也要用变异重跑证明修改后的测试仍然有检测力。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| Failing test | 捕获失败用例及其失败原因分类，区分产品缺陷与测试脆弱 | 失败分类记录 |
| Evidence capture | 保存失败现场（截图、DOM、网络、日志），供人工判断 | 失败证据包 |
| Healer candidate | 自愈只产出候选补丁，不直接提交 | 自愈候选补丁 |
| Anti-cheat diff | 检查补丁是否删除断言、修改期望值或跳过步骤，命中即拒绝 | 反作弊检查结果 |
| Mutation rerun | 对修改后的测试重跑变异，验证检测力未下降 | 变异重跑对比 |
| Human merge gate | 人工确认补丁修的是测试脆弱而非掩盖产品缺陷 | 合并审批记录 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 三类改动的处置规则

把 healer 的改动分成三类，规则完全不同。不分类就只能全信或全不信。

右列写的是这一类被错误放行时的后果——第三类是真正的质量事故。

| 改动类型 | 处置 | 错误放行的后果 |
| --- | --- | --- |
| 定位器属性 | 可自动接受，但需留证据 | 低风险，最多误定位 |
| 等待与重试 | 需人工审批 | 掩盖真实的性能退化 |
| 断言与期望值 | 绝对禁止自动改 | 真实回归被改成绿色 |

> 三类的判别不难：看 diff 里有没有动到断言语句。动了就是第三类，无论解释多合理。

*依据：[hcoles/pitest](https://pitest.org/)*

### 这一页的验收口径：检测力不得因自愈而下降

T19-1 是本页的核心判据：自愈前后的变异杀伤率不能下降。这一条把「修绿了」和「修对了」区分开来。

T19-3 的误修率需要人工抽样才能得出，成本较高但不可省略——它是唯一能发现「自愈在掩盖真实缺陷」的指标。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| T19-1 | 检测力不退化 | 自愈后变异杀伤率相对自愈前下降 ≤ 2pt；下降超出即回退补丁 | 每次自愈 |
| T19-2 | 反作弊拦截 | 删除断言 / 修改期望值 / 跳过步骤类补丁的拦截率 = 100% | 每次自愈 |
| T19-3 | 误修率 | 人工抽样 30 条自愈补丁，掩盖真实产品缺陷的比例 = 0 | 每周 1 次 |
| T19-4 | 自动合并边界 | 未经人工审批自动合并的补丁占比 = 0（定位器类微调除外，须显式白名单） | 每次自愈 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来是合理修复、实际是制造假绿的做法

这两种修复在 diff 里看起来都很小，评审时也容易通过。

它们的共同结果是检测力被移除而没人察觉。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 按钮改名后 healer 找到另一个可点击元素，测试恢复绿色 | 定位器失效是常见问题，自动找替代很合理 | 替代元素可能是完全不同的功能。必须确认修复后的测试仍能杀死原业务变异，否则它已经在测另一件事 |
| 测试偶发超时，healer 把等待从 5 秒加到 30 秒 | 超时确实是常见的不稳定来源，放宽等待很自然 | 放宽等待会掩盖真实的性能退化。等待类改动必须人工审批，并检查是否有性能指标同步劣化 |

> 两条的共同验证方式：修复后重跑原业务变异，必须仍然失败。

### 怀疑测试被修绿时按什么顺序查

修绿的痕迹都在 diff 与变异结果里。下表按查证成本从低到高排列。

前两行几分钟就能查完，且几乎总能给出结论。

| 症状 | 查什么 | 判据 |
| --- | --- | --- |
| 失败后自动恢复绿色 | 修复 diff | 有没有动到断言语句 |
| 通过率突然上升 | 历史变异结果 | 变异杀死率是否同步下降 |
| 定位器变了但功能相同 | 元素语义 | 新元素是否指向同一业务动作 |
| 等待时间变长 | 性能指标 | 是否有同期的延迟劣化 |

> 第二行是最有力的证据：通过率上升而杀死率下降，几乎可以确定是修绿。

### 给 healer 加一道反作弊门：约 40 分钟

不需要改 healer 本身。在它的输出与合并之间加一道检查即可。

1. 把 healer 的每次修复输出为一个 diff，而不是直接提交。
2. 写一条规则：diff 中若出现断言语句的增删改，一律拒绝自动合并。
3. 写第二条规则：等待时长的增加必须标记为需人工审批。
4. 为每次接受的修复，自动重跑一遍该用例对应的已知业务变异。
5. 变异不再被杀死的，回退修复并升级人工诊断。

**期望结果**：上线这道门之后，通常会立刻拦下一批此前被自动接受的修复。其中总有一两条是真的把回归改绿了。

> ⚠ 不要用历史通过率作为修复正确性的依据。通过率恰恰是修绿之后会上升的那个指标。

### 这一页的出口判据

这一页的门禁保护的是回归套件的长期价值。自愈带来的效率提升是立刻可见的，检测力的流失要几个月后才显现——门禁的作用就是把后者提前暴露。

第三段要决定的是白名单范围：哪些改动可以自动合并。这个名单只应包含纯定位器微调，且需要定期复审。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 反作弊检查拦截率 < 100% 时阻断自愈机制上线<br>自愈后变异杀伤率下降 > 2pt 时阻断合并，补丁回退 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 误修率按 30 条抽样给出 95% CI 上界，样本不足时结论记为证据不足<br>自愈前后检测力对比以区间重叠判定，不用单次杀伤率差值 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 可自动合并的补丁类型白名单，由测试负责人签字并每季度复审<br>自愈无法处理而长期失败的用例，由测试负责人明示接受其维护成本 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[Playwright Locators：语义定位器](https://playwright.dev/docs/locators)*

### 带走一份 healer 权限清单

清单只需要三行：可自动改的、需审批的、绝对禁止的。它比任何复杂策略都有效。

再加一条硬约束：任何被接受的修复都要重跑变异回归。

- 断言与期望值绝对禁止自动修改
- 等待类改动需人工审批并核对性能指标
- 接受的修复必须通过变异回归验证

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Playwright：跨浏览器端到端测试框架](https://playwright.dev/docs/intro)** — Web UI 专项主力工具
  - 能证明：浏览器自动化的三项工程能力：actionability 自动等待取代 sleep、语义 locator 取代 CSS/XPath 坐标、浏览器上下文隔离取代用例间清理。它们共同把 UI 测试的不稳定来源从「时序」降到「业务」。
  - 不能证明：自动等待解决的是元素可交互，不是业务就绪。页面上按钮能点了不代表后台事务已提交；UI 全绿仍需副作用层佐证。
  - `microsoft/playwright` · 版本 v1.62.1（2026-07-30） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Playwright Locators：语义定位器](https://playwright.dev/docs/locators)** — 机理说明
  - 能证明：getByRole / getByLabel / getByText 这类定位器绑定的是无障碍树与用户可见语义，而不是 DOM 结构。因此重构 DOM 不会让它们失效，而改动可访问名会——这恰好是希望被检出的变更。
  - 不能证明：官方文档描述的是 API 能力，不构成对你项目用例稳定率的承诺。
  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理
- **[PIT：JVM 变异测试](https://pitest.org/)** — 检测力判据
  - 能证明：覆盖率只说明代码被执行过，不说明被检查过。变异测试往代码里植入语义变更，看测试会不会红——存活的变异体就是一条被执行却没有被断言的路径。这是「测试有没有检测力」目前唯一可自动判定的口径。
  - 不能证明：变异算子覆盖的是语法层面的常见错误，覆盖不到业务逻辑错误；等价变异体（语义未变）会造成无法消除的存活率下限。
  - `hcoles/pitest` · 版本 1.25.9（2026-08-04） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[browser-use：模型驱动浏览器的执行器](https://docs.browser-use.com/)** — 浏览器 Agent 实现
  - 能证明：模型驱动浏览器时的实际接口形态：把页面转成结构化的可交互元素列表交给模型，而不是让模型看像素。这决定了它的失败形态是「选错元素」而不是「点错坐标」。
  - 不能证明：能完成任务不等于能判断任务完成。演示成功率与你自己页面上的成功率无关，且版本迭代很快，行为不稳定。
  - `browser-use/browser-use` · 版本 0.13.7（2026-07-27） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
