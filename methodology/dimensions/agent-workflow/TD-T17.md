## TD-T17

### 攻击面已经从用户输入转移到运行时数据通道

把提示注入理解成「用户在输入框里写坏话」，会让你的防线建在错误的位置。真正的注入来自 Agent 在运行时读进上下文的东西：检索到的文档、工具返回、网页内容、工单正文。

下面三条描述这个转移带来的三类新失效。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 只在用户输入侧做注入防护 | 工具描述与工具响应直接进上下文且无等价检查，这个信任落差是主要攻击面；实测多数流行 Agent 攻击成功率超过 60%，最高达 72% | 输入过滤做得很完善，而攻击根本不走输入 |
| 按轮次而不是按轨迹评估护栏 | 延迟触发与跨会话攻击把风险证据分散在整条轨迹上，单轮窗口内每一轮都正常 | 逐轮护栏全绿，攻击在第 5 轮才激活 |
| 能力更强的模型被默认更安全 | 更强的指令遵循让模型对恶意元数据更顺从；MCPTox 在 45 个真实 MCP server、353 个真实工具上实测，多数流行 Agent 攻击成功率超过 60%，最高 72%，且能力更强的模型往往更差 | 升级模型被当成安全改进，实际扩大了攻击面 |

> 解法是把注入测试建成可回放的攻击集，并按轨迹级而不是轮次级评估护栏。

### 注入攻击的四个词

攻击进入的通道是数据，不是输入框。这四个词描述它怎么进来。

| 术语 | 一句话解释 |
| --- | --- |
| 直接注入 | 用户在输入里写「忽略之前的指令」；最容易想到也最容易防 |
| 间接注入 | 恶意指令埋在检索文档、网页、邮件或工具返回值里；用户全程无恶意 |
| 过度代理权 | Agent 拥有超出任务所需的行动能力；它把小漏洞放大成大事故 |
| 纵深防御 | 输入、检索、模型、工具、输出五层各自独立拦截 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/)*

### 攻击面已经从用户输入转移到运行时数据通道

传统输入校验的假设是：不可信数据从用户那里来，从一个已知的入口进入系统。Agent 打破了这个假设——它会主动去读网页、文档、邮件、数据库记录、工具返回值，而这些内容全部进入同一个上下文，与系统指令混在一起。

这就是间接注入：攻击者不需要接触用户，只需要在 Agent 会读到的某份文档里埋一句话。防御难点在于，模型在架构上无法区分「这段文字是指令」和「这段文字是数据」——它们在上下文里是同一种东西。

因此单点防御必然不够，必须纵深：输入侧做检测与隔离标注、上下文里做来源标记与信任分级、工具调用层做权限裁决、输出侧做敏感信息过滤、动作层对不可逆操作要求人工确认。每一层都会漏，但它们漏的方式不同。

过度代理权是把注入变成事故的放大器。同样一次成功注入，如果 Agent 只有只读权限，后果是信息泄露；如果它有转账权限，后果是资损。因此收紧权限的收益远高于提高检测准确率——前者是确定的，后者是概率的。

*依据：[OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/) · [NVIDIA/garak](https://docs.garak.ai/)*

### 五层防御各自能拦什么、必然漏什么

这张表的用途是提醒一件事：没有任何一层能单独成立。设计时要问的不是「这层够不够」，而是「这层漏掉的那部分由哪一层接住」。

第五行的权限收敛不是检测手段，而是把所有检测失败的后果上限压低——它是唯一一条确定性的防御。

| 防御层 | 拦什么 | 必然漏什么 | 工具 |
| --- | --- | --- | --- |
| 输入检测 | 已知模式的直接注入 | 改写、编码、多语言变体 | LLM Guard 输入侧扫描 |
| 来源标记 | 让上下文里的外部内容带上不可信标记 | 模型仍可能被说服忽略标记 | 自建上下文组装约定 |
| 工具授权 | 越权调用与超出边界的参数 | 在授权范围内的滥用 | MCP schema + 写前授权链 |
| 输出过滤 | 敏感信息外泄、有害内容 | 语义变体与间接泄露 | LLM Guard 输出侧扫描 |
| 权限收敛 | 把任何一次成功注入的后果上限压低 | 不拦攻击，只限后果 | 最小 scope 设计（工程约定） |

> 前四行都是概率性的，只有第五行是确定性的。资源有限时先做第五行。

*依据：[OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/) · [NVIDIA/garak](https://docs.garak.ai/) · [protectai/llm-guard](https://protectai.github.io/llm-guard/) · [modelcontextprotocol/modelcontextprotocol](https://modelcontextprotocol.io/)*

### 这张图的 6 个节点，本页各交付什么

这张图是一条纵深防御链：不可信内容进来后，依次经过检索隔离、模型边界、工具授权、输出 DLP 四道独立控制。任何一道都不足以单独承担防御。

本页要验证的不是「有没有这四道」，而是「每一道单独失效时其余三道能不能兜住」——这是纵深防御的定义。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| Untrusted content | 标记所有运行时进入上下文的外部内容，构造注入语料 | 不可信内容清单与攻击语料 |
| Retrieval isolation | 把检索内容与指令区隔离，验证检索内容不能改变指令语义 | 检索隔离测试结果 |
| Model boundary | 测试模型层面对注入的抵抗力，作为纵深中的一层而非唯一一层 | 模型层 ASR 测量 |
| Tool authorization | 验证即使模型被说服，工具授权层仍会拦下越权调用 | 工具授权拦截结果 |
| Output DLP | 在输出侧检测敏感数据外泄，作为最后一道 | 输出侧泄露检测结果 |
| Security review | 对新增工具与新增数据源做人工安全评审 | 安全评审记录 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 五层防御各自能拦什么

单层防御在间接注入面前会失效。五层的意义是：任一层被绕过时，仍有下一层。

右列写的是这一层的固有局限——理解局限才知道为什么不能只靠它。

| 层 | 能拦什么 | 固有局限 |
| --- | --- | --- |
| 输入过滤 | 已知模式的直接注入 | 换个说法就绕过 |
| 检索隔离 | 跨租户与越权文档 | 拦不住租户内的污染文档 |
| 模型拒绝 | 明显的恶意请求 | 可被精心构造的措辞绕过 |
| 工具授权 | 越权与越界的实际调用 | 拦不住授权范围内的滥用 |
| 输出过滤 | 敏感字段外泄 | 是最后一道，不能替代授权 |

> 第四层是唯一在模型完全被劫持时仍然有效的一层。安全结论应当主要建立在它上面。

*依据：[NVIDIA/garak](https://docs.garak.ai/)*

### 这一页的验收口径：按轨迹算，不按轮次算

T17-2 是本页最容易被忽略的一条：延迟触发与跨会话持久化必须单独建套件，因为它们在任何单轮评估里都表现正常。

T17-4 的纵深有效性是一个不常见但重要的指标：它测的是「单层失效时整体是否仍然安全」，这正是纵深防御与多层堆叠的区别。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| T17-1 | 直接与间接注入 | 攻击成功率 ASR ≤ 1%；高危动作类 ASR = 0 | 每次发布 + 每周 1 次 |
| T17-2 | 延迟与跨会话攻击 | 延迟触发攻击集单独建套件，检出率 ≥ 95%；跨会话污染存活轮数 = 0 | 每次发布 |
| T17-3 | 数据外泄 | 输出侧敏感数据外泄次数 = 0 | 每次发布 |
| T17-4 | 纵深有效性 | 单层控制被禁用时整体拦截率仍 ≥ 90%，用于验证防御不是单点 | 每季度 1 次 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在测注入、实际覆盖不到主要通道的做法

这两种做法都能产出一份有数据的安全报告。

问题是攻击面的选择和报告的口径。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 构造两百条恶意用户输入，模型全部拒绝，判定安全 | 样本量大，拒绝率也确实是 100% | 主要攻击通道不是用户输入。检索到的文档、工具返回值、工具描述里的注入完全没测到 |
| 报告攻击成功率为零，结论是系统安全 | 数据真实，结论也符合数据 | 没有写明被哪一层拦下。全靠模型拒绝的零成功率，与靠授权层拦下的零成功率，安全等级完全不同 |

> 两条的共同修法：按通道覆盖攻击面，按拦截层统计结果。

### 怀疑被注入但查不出来时按什么顺序查

间接注入的证据分散在轨迹上，单轮日志看不出来。下表给出各通道的查法。

查之前先确认 trace 记录了工具返回值原文——很多系统只记了摘要。

| 症状 | 先怀疑哪个通道 | 查什么 |
| --- | --- | --- |
| Agent 做了没被要求的事 | 检索文档污染 | 查当次检索到的文档原文 |
| 前几轮正常后突然越界 | 多轮延迟触发 | 查完整轨迹而不是当前轮 |
| 清空会话后仍然复现 | 记忆污染 | 查长期记忆写入记录 |
| 某个工具后行为异常 | 工具返回值注入 | 查该工具返回的原文 |

> 四行都要求 trace 保留原文。只记摘要的系统在这类事故上基本无法取证。

### 构造一次间接注入并验证纵深防御：约 60 分钟

重点是把载荷放进数据通道，而不是用户输入。

1. 在一份测试用的知识文档正文里埋入一段指令，要求 Agent 调用某个越权工具。
2. 用完全正常的用户问题触发检索，让 Agent 读到这份文档。
3. 记录发生了什么：模型是否服从、是否发起了工具调用、调用是否被授权层拦下。
4. 把结果按五层归类：被哪一层拦下的，就记在哪一层。
5. 重复一次，但这次把载荷放在工具返回值里而不是文档里，比较两者的拦截层是否相同。

**期望结果**：常见结果是模型确实服从了文档中的指令，但工具授权层拦住了它。这正是纵深防御应有的表现，也说明只测模型拒绝会给出错误结论。

> ⚠ 演练必须在隔离环境进行，且工具必须是录制沙箱。真实越权调用一旦成功，损失不可撤销。

### 这一页的出口判据

安全门禁在本课程里是唯一一道贯穿全部执行环的：它不是发布前的一次检查，而是持续对抗。攻击语料会过时，护栏会退化。

第三段要接受的是未知攻击面：攻击集只能覆盖已知手法，新手法的存在是确定的，未知的只是它什么时候出现。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 高危动作类攻击成功率 > 0 时阻断<br>输出侧敏感数据外泄次数 > 0 或跨会话污染存活轮数 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | ASR 按攻击类型分片给出 95% CI 上界，与阈值比较用上界不用点估计<br>攻击集样本 < 200 条时 ASR 结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 攻击集未覆盖的手法范围，由安全 owner 列出并签字接受<br>为可用性而放宽的护栏项，由产品 owner 在知情前提下接受其风险 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/)*

### 带走一份按通道组织的攻击集

攻击集按通道组织而不是按载荷组织，才能保证覆盖。载荷可以无限多，通道只有那么几个。

报告必须按拦截层统计——这是判断安全等级的唯一依据。

- 按数据通道覆盖攻击面，不只测用户输入
- 报告写明被哪一层拦下
- trace 保留工具返回值与检索文档原文

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[garak：LLM 漏洞探测器](https://docs.garak.ai/)** — 传统安全测试 × AI 的实际结合点

  - 不能证明：探测覆盖的是已知攻击模式库，且模型行为具随机性——单次未命中不等于不存在。结论必须带重复次数与命中率，不能报「已通过」。
  - `NVIDIA/garak` · 版本 v0.16.0（2026-08-04） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点

  - 能证明：LLM 应用的高频风险分类（提示注入、敏感信息泄露、供应链、过度代理权限等），可作为安全测试的风险起点与覆盖度检查表。
  - 不能证明：清单是风险分类不是验收标准，也不按你的业务排优先级。
  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理
- **[LLM Guard：模型输入输出的确定性管控层](https://protectai.github.io/llm-guard/)** — AI 侧防护实现
  - 能证明：一部分安全判定可以从「靠模型自我约束」移到模型之外的确定性代码路径上：输入侧的注入检测与脱敏、输出侧的敏感信息与有害内容过滤。移出来之后这层才是可测、可度量、可回归的。
  - 不能证明：过滤层本身有漏判与误判，两类错误率都必须单独度量。把它当成「加了就安全」是把一个概率组件当成了确定性边界。

  - 不能证明：规范描述接口不描述权限。哪些工具允许被哪个会话调用、不可逆动作要不要二次确认，规范里没有，必须在工具调用层自己实现并验证。
