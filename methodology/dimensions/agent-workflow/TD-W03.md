## TD-W03

### 多 Agent 比单 Agent 好，这个结论多数时候来自不公平的对照

多 Agent 架构天然消耗更多 token、更多时间、更多调用。如果对照实验不固定预算，多 Agent 几乎一定会赢——赢的是资源，不是架构。

下面三条是这类对照里最常见的三处不公平。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 不固定 token 与时间预算 | 多 Agent 方案的 token 消耗常达单 Agent 的 3～5 倍；不固定预算的对照实际比的是投入 | 「多 Agent 效果更好」被当成架构结论，实际是花了更多钱 |
| 两侧用了不同的工具集或提示 | 任何一侧多 1 个工具就可能改变可解任务的范围，这类差异会被 100% 归给架构 | 架构决策建立在一个混杂了工具差异的对比上 |
| 单次运行就下结论 | 多 Agent 的方差通常高于单 Agent，单次运行的差异有很大概率来自随机性 | 看到一次 8pt 的领先就重构了整个系统 |

> 公平对照的三个必要条件：同一冻结任务集、同一预算上限、同一重复次数。

### 公平对照的四个词

多 Agent 是不是更好，只有在同预算下比较才有答案。这四个词是公平的前提。

| 术语 | 一句话解释 |
| --- | --- |
| 同预算 | 两组共享相同的总 token、时间、重试与人工干预额度 |
| 混杂 | 两组之间有多于一个变量不同，结论无法归因 |
| 协作失败 | 多 Agent 特有的失败：重复工作、信息丢失、互相等待 |
| 单位成功成本 | 每个成功任务的总花费；架构决策的核心可比量 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/)*

### 多 Agent 比单 Agent 好，这个结论多数来自不公平的对照

多 Agent 架构的对照实验里有一个几乎总是被忽略的变量：预算。多 Agent 天然消耗更多 token 与更多调用，如果对照的单 Agent 没有拿到同样的预算，那么比较的不是架构而是算力。

同预算对照的做法是：给单 Agent 同样的 token 上限、同样的步数上限、同样的重试次数，甚至可以让它多跑几轮取最优。很多时候这样一比，多 Agent 的优势会显著缩小甚至消失——这个结果本身就是有价值的结论。

第二类混杂是提示词工程量。多 Agent 方案通常被精心调过，而对照的单 Agent 用的是最朴素的提示词。这个差异会被记在架构头上。控制它的办法是两边都投入可比的调优工作量，并把工作量本身记录下来。

报告口径同样重要：除了成功率，必须报单位成功成本（每完成一个任务的总花费）与协作失败率（因交接、冲突、重复工作导致的失败占比）。多 Agent 的真实代价通常藏在后两个数字里，而它们不出现在成功率对比图上。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/) · [SWE-bench/SWE-bench](https://www.swebench.com/)*

### 必须锁定的四项与必须报告的四项

上半张表是实验设计，下半张表是报告口径。两者缺一，结论都不可用：设计不公平则结果无意义，口径不全则代价被隐藏。

「必须报告」那四项里，后两项是多 Agent 特有的代价，单 Agent 对照组里它们恒为零——这正是它们必须被报出来的原因。

| 类别 | 项目 | 为什么 | 不做的后果 |
| --- | --- | --- | --- |
| 锁定 | token 与调用预算 | 多 Agent 天然消耗更多，不锁定则在比算力 | 架构优势被算力优势冒充 |
| 锁定 | 提示词调优工作量 | 多 Agent 方案通常被精调，对照组用朴素提示词 | 调优投入被记在架构头上 |
| 锁定 | 模型版本与解码参数 | 任一变化都会改变结果 | 混杂，结论无法归因 |
| 锁定 | 评测集 | 实验期间不得更新 | 分数变化里混着题目变简单 |
| 报告 | 成功率与置信区间 | 点估计无法支持决策 | 区间重叠时被当成有差异 |
| 报告 | 单位成功成本 | 多 Agent 的代价主要在这里 | 成本优势/劣势完全不可见 |
| 报告 | 协作失败率 | 交接、冲突、重复工作导致的失败 | 多 Agent 特有的失败被混入总失败率 |
| 报告 | p95 端到端时延 | 多 Agent 的串行环节会显著抬高尾部 | 只看均值时尾部代价被平均掉 |

> 八项做全，「多 Agent 更好」才是一个可以进架构决策的结论，而不是一张演示图。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/) · [SWE-bench/SWE-bench](https://www.swebench.com/) · [UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/)*

### 这张图的 6 个节点，本页各交付什么

这张图是一个标准的对照实验设计：两条实验臂共享冻结任务集与预算，各自重复运行，最后由人做架构决策。

「Shared budget」是整张图的关键约束。去掉它，这个实验就退化成了「谁花的钱多谁赢」。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| Frozen task set | 冻结任务集并锁版本，两条臂使用完全相同的输入 | 冻结任务集版本号 |
| Single-agent arm | 单 Agent 实验臂，记录其完整轨迹与资源消耗 | 单 Agent 结果与消耗 |
| Multi-agent arm | 多 Agent 实验臂，工具集与提示保持与单 Agent 可比 | 多 Agent 结果与消耗 |
| Shared budget | 为两条臂设定相同的 token、时间、调用次数上限 | 共享预算配置 |
| Repeated trials | 两条臂按同一 k 值重复运行，保留原始记录 | 重复运行原始记录 |
| Architecture decision | 基于区间与成本共同决定是否采用多 Agent | 架构决策记录 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 必须锁定的六项与必须报告的四项

对照实验的可信度取决于锁定了什么。下表左侧是实验前要固定的，右侧是实验后要报告的。

任一项锁定失败，结论就是关于那一项的，而不是关于架构的。

| 必须锁定 | 为什么 | 失守时结论变成 |
| --- | --- | --- |
| 模型与版本 | 能力差异会被算成架构收益 | 关于模型的结论 |
| 工具集合 | 工具多的一方天然占优 | 关于工具的结论 |
| 任务集 | 难度分布不同则不可比 | 关于任务的结论 |
| 总 token 预算 | 多 Agent 天然消耗更多 | 关于预算的结论 |
| 重试次数 | 重试提高成功率 | 关于重试的结论 |
| 人工干预 | 有人救场就不是自动化对比 | 关于人的结论 |

> 六项全部锁定后，剩下的差异才可能来自架构本身；此时报告成功率分布、协作失败、延迟与单位成功成本四项。

*依据：[UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/)*

### 这一页的验收口径：同预算下的可重复收益

W03-1 是本页的核心判据：在预算相同的条件下，多 Agent 的置信区间必须与单 Agent 不重叠，才能说它带来了收益。

W03-4 引入了一个常被忽略的成本：架构复杂度本身的维护成本。统计上的小幅领先未必值得多一套编排层的长期负担。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| W03-1 | 同预算收益 | 两条臂 95% CI 不重叠才判定多 Agent 有收益；重叠时结论为「未测出差异」 | 每次架构评估 |
| W03-2 | 预算对等 | 两条臂的 token 与时间预算差异 = 0（硬性对齐） | 每次实验 |
| W03-3 | 工具集对等 | 两条臂可用工具集与提示模板的差异项数 = 0 | 每次实验 |
| W03-4 | 重复充分性 | 两条臂重复次数 k ≥ 5；多 Agent 臂的变异系数 CV ≤ 0.2 | 每次实验 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来证明了多 Agent 更好、实际没有的对照

这两种对照在技术分享里很常见，数据也都是真的。

问题是两组之间不止一个变量不同。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 多 Agent 组成功率 78%，单 Agent 组 61%，判定多 Agent 更优 | 同任务集、同模型，差距也足够大 | 多 Agent 组通常消耗数倍 token 与时间。同预算下重跑，单 Agent 可以多试几次，差距往往消失 |
| 多 Agent 引入了 reviewer 角色，质量明显提升 | 增加审查环节提升质量，符合直觉 | reviewer 常常重复 planner 的工作。要看的是每个角色的边际贡献，而不是整体是否变好 |

> 两条的共同修法：同预算重跑，并按角色拆分边际贡献。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/)*

### 对照结果不稳定时按什么顺序查

架构对照的结论方差通常很大。先排除实验设计问题，再解读结果。

四行按出现频率排列。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 每次跑结论不同 | 重复次数不足 | 增加重复直到区间可区分 |
| 多 Agent 明显更好 | 预算未对齐 | 按总 token 对齐后重跑 |
| 差异很小但被宣布获胜 | 区间重叠 | 区间重叠时结论是无差异 |
| 某类任务差异极大 | 收益集中在特定切片 | 按任务类型分别报告 |

> 最后一行往往是最有价值的结论：只在复杂跨服务任务上启用编排，其余保持单 Agent。

### 设计一次同预算架构对照：约 90 分钟

设计比执行重要。锁定项写不清楚，跑再多次也得不到可用结论。

1. 固定模型版本、工具集合、任务集与成功判据，并逐项记录取值。
2. 计算两组的总预算：token、时间、重试次数、人工干预次数，确保完全一致。
3. 两组各重复运行足够次数，直到成功率区间能被区分或明确重叠。
4. 记录四项：成功率分布、协作失败次数、端到端延迟、单位成功成本。
5. 按任务类型分别统计，找出多 Agent 真正有收益的那个切片。

**期望结果**：常见结果是整体差异不显著，但在某一类复杂任务上多 Agent 明显更好。这个切片结论比一个整体结论有用得多。

> ⚠ 不要在对照中允许人工救场。一旦有人干预，测的就是人加架构，而不是架构。

### 这一页的出口判据

这一页的门禁会拒绝大多数现有的多 Agent 对比结论。这不是苛刻——架构决策的成本很高，值得一次真正公平的实验。

第三段是本页真正的产物：即使多 Agent 统计上更好，是否值得承担编排复杂度、调试难度与故障面扩大，只能由人决定。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 两条臂的预算差异 > 0 或工具集差异项数 > 0 时阻断，实验结果不可用<br>任一臂重复次数 k < 3 时阻断，结论不得写入架构评审材料 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 以预注册效应量/非劣界和配对或聚类 bootstrap 95% CI 判定收益，禁止用点估计差值或两个 CI 是否重叠宣布多 Agent 更优<br>多 Agent 臂 CV > 0.2 时须加大 k 值重跑，否则结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 多 Agent 带来的编排复杂度与调试成本，由架构 owner 签字接受<br>统计显著但幅度较小的收益是否值得采纳，由技术负责人署名决定 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Inspect：任务 / solver / scorer 分层的模型评测框架](https://inspect.aisi.org.uk/)** — 评测框架
  - 能证明：评测可以拆成三个独立可替换的部件：dataset 定义问什么、solver 定义怎么问、scorer 定义怎么判。三者分离之后，换模型不用改判据，改判据不用改数据集——这是把一次性评测脚本变成可回归资产的结构条件。
  - 不能证明：框架不提供判据。scorer 写得对不对、数据集有没有覆盖你的风险切片，框架一概不管，全绿只说明流程跑通了。
  - `UKGovernmentBEIS/inspect_ai` · 版本 release/2025-11-28 · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[HELM：多场景、多指标的整体性评测](https://crfm.stanford.edu/helm/)** — 评测方法学
  - 能证明：单一准确率无法描述模型能力。HELM 的做法是把场景（scenario）与指标（metric）做成正交的两维，同一个场景同时报准确率、校准度、鲁棒性、公平性、效率——「模型 A 比 B 好」这句话必须指明在哪个场景的哪个指标上。
  - 不能证明：覆盖的是公开场景，不覆盖你的业务分布。榜单名次不能迁移到企业任务上。
  - `stanford-crfm/helm` · 版本 v0.5.16（2026-04-30） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[SWE-bench：以真实仓库 issue 为任务的 Agent 基准](https://www.swebench.com/)** — 任务级基准
  - 能证明：任务级评测的判据可以完全确定：补丁应用后跑原仓库的测试，通过即算解决。这比模型评判可靠得多，也说明「只要任务本身自带 oracle，评测就不需要 judge」。
  - 不能证明：任务来自公开仓库，训练数据污染无法排除；单次成功率也不代表在你私有代码库上的表现。执行成本高，不适合做每次提交的门禁。
  - `SWE-bench/SWE-bench` · 版本 v4.1.0 · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
