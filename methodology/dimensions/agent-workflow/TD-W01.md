## TD-W01

### 判据是路径由谁决定，不是产品叫什么名字

「我们的 Agent」这个说法在多数产品里同时指三种不同的东西：固定路由的 Workflow、自主决策的 Agent、异步执行的 Worker。它们的失败模式与测试方法完全不同。

下面三条说明混为一谈的代价。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 三种结构混在一起算总成功率 | 一个总体 92% 的成功率里，自主 Agent 部分可能只有 71%，而固定 Workflow 有 99% | 整体看起来达标，风险最高的那部分从未被单独看见 |
| 把 Workflow 当 Agent 测 | 路径固定的流程不需要 pass^k 这类重复运行指标，把它们套上去会把测试成本抬高 5～10 倍而无额外信息 | 预算花在了不产生信息的重复上 |
| 把异步 Worker 当同步调用测 | 入口返回 2xx 而后台任务失败的场景，同步视角 100% 漏过 | 可用性指标很好看，用户的任务实际没完成 |

> 本页只做一件事：给每个被测单元贴上正确的结构标签，后面所有方案按标签选择。

### 分类的四个判据词

产品叫什么不重要。这四个问题的答案决定它是什么，也决定该怎么测。

| 术语 | 一句话解释 |
| --- | --- |
| 路径决定权 | 下一步由代码、模型还是队列决定 |
| 状态持有者 | 状态存在哪里：进程内、数据库、还是消息里 |
| 副作用提交点 | 真正写数据的那一步在哪个组件 |
| 终止条件 | 什么时候算结束；没有明确终止的系统一定会有死循环 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[langchain-ai/langgraph](https://langchain-ai.github.io/langgraph/)*

### 判据是路径由谁决定，不是产品叫什么名字

「这是不是一个 Agent」在选型讨论里通常是个营销问题。在测试设计里它必须是个技术判断，因为答案直接决定了要不要建轨迹断言——而那是这个模块最大的一笔成本。

唯一可靠的判据是路径决定权：下一步做什么，是代码写死的，还是模型当场决定的。代码写死就是 Workflow，模型决定就是 Agent。中间形态（模型在有限选项里选）按 Agent 处理，因为它同样不保证两次走同一条路。

第二个判据是状态持有者：状态在调用方手里（每次请求自带全部上下文）还是在系统内部累积。后者意味着存在跨请求的污染路径，需要单独测试隔离与清理。

第三个判据是副作用提交点：副作用是在流程结束时一次提交，还是在中途逐步发生。中途发生意味着失败时无法整体回滚，必须设计补偿——这一条决定了故障注入测试的形态。

*依据：[langchain-ai/langgraph](https://langchain-ai.github.io/langgraph/) · [modelcontextprotocol/modelcontextprotocol](https://modelcontextprotocol.io/)*

### 三个判据决定三类测法

先用三个判据定性，再选测法。反过来做——先选了一套测法再往上套——会得到一份既贵又漏的测试设计。

第三列写的是「判成这一类之后必须增加什么」，这是成本估算的直接依据。

| 判据 | 两种取值 | 取值决定了什么 | 对应工具 |
| --- | --- | --- | --- |
| 路径决定权 | 代码写死 / 模型当场决定 | 模型决定时必须建轨迹断言，成本大幅上升 | LangGraph 状态图使路径可枚举 |
| 状态持有者 | 调用方自带 / 系统内部累积 | 内部累积时必须测跨请求隔离与清理 | 会话隔离测试 + 记忆治理检查 |
| 副作用提交点 | 结束时一次提交 / 中途逐步发生 | 中途发生时必须设计补偿并做故障注入 | 副作用账本 + 故障注入（WireMock、Toxiproxy） |
| 终止条件 | 有明确边界 / 由模型自行判断 | 模型自行判断时必须加步数、时间、成本三重熔断 | 调用层熔断（工程实现） |

> 四行全部判完，才能知道这个组件要花多少测试成本。跳过这一步的排期，通常低估三到五倍。

*依据：[langchain-ai/langgraph](https://langchain-ai.github.io/langgraph/) · [modelcontextprotocol/modelcontextprotocol](https://modelcontextprotocol.io/) · [wiremock/wiremock](https://wiremock.org/docs/) · [Shopify/toxiproxy](https://github.com/Shopify/toxiproxy#readme)*

### 这张图的 6 个节点，本页各交付什么

这张图把三种结构并排画出来，共享右侧的状态存储与 owner。它要传达的是：同一个产品里这三者通常同时存在，且共享状态——这正是最容易出问题的地方。

分类的判据只有三个：路径由谁决定、状态存在哪里、何时终止。回答完这三个问题，标签就确定了。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| Deterministic router | 识别路径由代码固定的部分，按传统流程测试处理 | 确定性路径清单 |
| Autonomous agent loop | 识别路径由模型决定的部分，按 Agent 方案处理（含 pass^k 与轨迹） | 自主决策边界清单 |
| Async queue | 识别异步边界，标出入口成功与业务终态的落差点 | 异步边界清单 |
| Worker | 识别后台执行单元，验证其幂等性与重试语义 | Worker 幂等性要求 |
| State stores | 标出三种结构共享的状态，这是跨结构故障的主要传播路径 | 共享状态清单 |
| Human owner | 为每个结构指定 owner，防止边界地带无人负责 | 结构 owner 登记 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 三类组件的判别与对应测法

同一个产品里通常三类都有。分别识别、分别用对应方法测，才不会漏掉整类问题。

右列的测法互不通用：用分支覆盖测 Agent 会漏掉自主路径，用不变量测 Workflow 会漏掉分支。

| 组件 | 路径由谁决定 | 主要测法 |
| --- | --- | --- |
| 固定 Workflow | 代码 | 分支覆盖、状态机、非法转换 |
| 自主 Agent | 模型 | 不变量、禁止副作用、攻击集、重复运行分布 |
| 异步 Worker | 队列 | 幂等、重复投递、并发、超时、死信 |

> 三类的共同要求只有一条：副作用提交点必须明确，且有幂等保护。

*依据：[langchain-ai/langgraph](https://langchain-ai.github.io/langgraph/)*

### 这一页的验收口径：分类的完整性与正确性

本页的指标全部关于分类本身。它们不测质量，测的是「你有没有搞清楚在测什么」。

W01-4 的共享状态清单容易被忽略，但跨结构的故障几乎都通过共享状态传播——一个 Worker 写坏的状态会让 Agent 在下一轮做出错误决策。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| W01-1 | 分类覆盖 | 被测单元的结构分类覆盖率 = 100%，未分类数量 = 0 | 每次立项 |
| W01-2 | 分类判据一致 | 分类依据记录了「路径由谁决定 / 状态在哪 / 何时终止」三项的比例 = 100% | 每次立项 |
| W01-3 | 分结构出分 | 评测报告按结构分别出分的比例 = 100%，禁止跨结构合并总分 | 每次评测 |
| W01-4 | 共享状态识别 | 跨结构共享状态清单完整度经人工复核确认，遗漏数 = 0 | 每次架构变更 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来分类清楚、实际漏掉整类问题的做法

这两种分类方式听起来都很合理，也常见于架构文档。

问题是它们用的判据不决定测法。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 按是否调用大模型来分类：调了就是 Agent | 判据清晰，一眼就能分 | 调模型的固定流程仍然是 Workflow，用不变量测会漏掉大量分支；不调模型的编排器仍然需要熔断测试 |
| 按同步异步分类：异步的都算 Worker | 符合工程直觉，也便于分工 | 异步的 Agent 仍然是 Agent，需要攻击集与三层 Oracle。同步的编排器也可能有死循环 |

> 两条的共同修法：用「路径由谁决定」作为唯一判据，它直接决定测法。

*依据：[modelcontextprotocol/modelcontextprotocol](https://modelcontextprotocol.io/)*

### 测试覆盖看起来全但仍出事时按什么顺序查

整类问题被漏掉，通常是因为组件被分错类了。按下表核对。

核对方式是打开 trace，看下一步实际由什么决定。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 分支从未被测到 | Agent 里混着固定路由 | 把固定部分单独按分支覆盖测 |
| 出现重复副作用 | Worker 未做幂等测试 | 补重复投递与幂等键测试 |
| 死循环烧掉预算 | 无终止条件测试 | 注入无终止信号验证预算护栏 |
| 权限在某处被放大 | 跨组件共享高权限身份 | 按组件切分身份与最小权限 |

> 四行的共同前提是能看到 trace。产品文档上的架构图通常与运行时不一致。

### 给一个真实系统做组件分类：约 35 分钟

打开一条真实 trace，逐步标注，比看架构图准确得多。

1. 取一条完整的端到端 trace，把它的每一步列出来。
2. 对每一步问：下一步由代码、模型还是队列决定？标上 W、A 或 Q。
3. 标出状态在每一步存在哪里，以及副作用在哪一步真正提交。
4. 按标注结果把系统切成若干组件，每个组件归入三类之一。
5. 对照现有测试，检查每类组件是否用了对应的测法——通常会发现某一类完全没测。

**期望结果**：产出是一张带标注的组件图。多数团队会发现自己的系统是三类混合，而测试只覆盖了其中一类。

> ⚠ 不要依据产品命名或架构文档做分类。它们描述的是设计意图，trace 描述的是实际行为。

### 这一页的出口判据

这道门禁很轻，但它决定了后面所有模块对你适不适用。分类错误在后期表现为「方案很完整但没解决我们的问题」。

第三段要接受的是边界模糊：总有一些单元介于 Workflow 与 Agent 之间，这时按更严格的一侧处理，并记录这个选择。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 未分类被测单元数量 > 0 时阻断<br>评测报告跨结构合并总分的次数 > 0 时阻断，须拆分重报 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 各结构的成功率分别给出 95% CI，禁止用合并样本计算区间<br>单结构样本 < 30 条时该结构结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 介于两种结构之间的单元的归类选择，由架构 owner 署名确定<br>共享状态带来的跨结构耦合风险，由架构 owner 明示接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一张按控制权划分的组件图

图上每个组件标注三件事：路径由谁决定、状态在哪、副作用在哪提交。

这三项确定后，该用哪套测法就不需要讨论了。

- 用路径决定权分类，不用是否调模型或同步异步
- 三类各用各的测法，不互相替代
- 分类依据来自 trace，不来自架构文档

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[WireMock：HTTP 依赖打桩与故障注入](https://wiremock.org/docs/)** — 依赖隔离与故障注入
  - 能证明：把上游依赖替换成可编程的桩，让超时、5xx、慢响应、错误 body 这些平时碰不到的路径变成可稳定重复的用例。稳定性专项里绝大多数场景需要它才能构造。
  - 不能证明：桩的行为是你编的。真实依赖的失败形态可能与你的假设完全不同——桩测试通过不代表真实降级路径有效。
  - `wiremock/wiremock` · 版本 3.13.2（2025-11-14） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Toxiproxy：TCP 层网络故障注入代理](https://github.com/Shopify/toxiproxy#readme)** — 故障注入
  - 能证明：延迟、带宽限制、连接中断、慢关闭这些网络层故障可以按需注入且可编程开关，让超时与重试逻辑真正被执行到，而不是只存在于配置文件里。
  - 不能证明：注入的是网络层症状，不是依赖服务的真实故障语义（如半提交、脏数据）。
  - `Shopify/toxiproxy` · 版本 v2.12.0（2025-03-18） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Model Context Protocol 规范](https://modelcontextprotocol.io/)** — 工具契约规范
  - 能证明：模型可调用的工具有了机器可读契约：名称、输入 schema、描述、错误返回。这让「Agent 能调什么工具」从代码里的隐含事实变成可审计、可版本化、可做契约测试的工件。
  - 不能证明：规范描述接口不描述权限。哪些工具允许被哪个会话调用、不可逆动作要不要二次确认，规范里没有，必须在工具调用层自己实现并验证。
  - `modelcontextprotocol/modelcontextprotocol` · 版本 2026-07-28（2026-07-28） · NOASSERTION · 许可证未能自动判定，按最保守口径只链接不搬代码
- **[LangGraph：把 Agent 表达成显式状态图](https://langchain-ai.github.io/langgraph/)** — 编排结构参考
  - 能证明：把 Agent 从「一个循环加一堆 if」变成显式的节点与边之后，状态、分支、中断点、检查点都成为可枚举对象——可枚举才可测。这是长流程可靠性测试能开展的结构前提。
  - 不能证明：结构清晰不等于行为正确。节点内部仍由模型驱动，同一条边上的两次执行可能走出完全不同的结果。
  - `langchain-ai/langgraph` · 版本 1.2.11（2026-08-11） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
