## TD-T18

### AI 生成的浏览器测试最容易犯的错，是把「页面能跑通」当成「业务做对了」

Browser Agent 生成测试的速度极快，通过率也很高。但它默认优化的目标是「让脚本跑绿」，而不是「验证业务发生了」——这两个目标在大多数时候一致，在最关键的时候不一致。

下面三条给出这个偏差的三种表现。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 生成的断言只检查元素存在 | 只断言元素存在的测试，其业务变异体杀伤率通常低于 30% | 「生成了 80 条 E2E 且全绿」被当成覆盖充分 |
| 直接接受生成代码不做人工评审 | 生成脚本中包含硬等待、绝对定位、跳过步骤等反模式的比例不低；这些会在 1～2 个版本后集中失效 | 初期维护成本很低，半年后套件不可维护 |
| 用页面状态而非业务状态做判据 | 前端显示成功而后端未落库的场景，纯 UI 断言 100% 漏过 | 把「提示了下单成功」当成「订单已创建」 |

> 解法与 TD-T06 同源：生成的测试保持候选状态，用业务变异体证明它真的能发现问题。

### 浏览器测试 Agent 的四个角色词

生成测试的 Agent 通常拆成三个角色。分不清角色，就分不清该审查什么。

| 术语 | 一句话解释 |
| --- | --- |
| planner | 从需求与风险产出测试计划；它决定测什么 |
| generator | 把计划变成可执行代码；它决定怎么测 |
| healer | 失败后修复测试；它是风险最高的角色 |
| 业务 Oracle | 判断业务状态是否正确的依据；它不能由生成方决定 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[microsoft/playwright-mcp](https://github.com/microsoft/playwright-mcp#readme)*

### AI 能把页面跑通，判断不了业务是否做对

模型驱动浏览器的能力已经足够完成「登录、搜索、下单」这类流程。问题出在验收：模型看到页面跳到了成功页，就报告任务完成——而成功页可能是缓存的、可能金额是错的、可能后台事务根本没提交。

这不是模型不够聪明，是结构问题：让生成动作的组件同时判断动作是否正确，等于取消了独立判据。它与「用接口的读方法验证写方法」是同一个错误，只是换了一层皮。

所以三个角色必须分开审查。planner 产出的是步骤，审查点是步骤覆盖了业务路径没有；generator 产出的是可执行脚本，审查点是定位器与等待是否稳定；healer 产出的是修复，审查点是它修的是测试还是产品——后者是最危险的一个。

业务 Oracle 必须由人定义并固定下来，不能由生成脚本的同一个模型顺手生成。这条判据的来源可以是数据库状态、账本、事件，也可以是一份人工确认过的期望值清单，但它必须独立于生成过程。

*依据：[microsoft/playwright-mcp](https://github.com/microsoft/playwright-mcp#readme) · [browser-use/browser-use](https://docs.browser-use.com/)*

### 三个角色的产出物与各自的审查重点

把 AI 生成的浏览器测试当成一个整体来审，会审不出东西。拆成三个角色之后，每个角色的失败形态是具体的、可检查的。

第四行不是角色，是把前三行接住的那条独立判据——缺了它，前三行做得再好也只是自证。

| 角色 | 产出什么 | 审查重点 | 典型失败 |
| --- | --- | --- | --- |
| planner | 测试步骤与覆盖范围 | 步骤是否覆盖了真实业务路径与异常分支 | 只覆盖主流程，异常分支一条没有 |
| generator | 可执行脚本 | 定位器是否语义化、等待是否基于状态 | 用文案定位、加固定 sleep，短期能跑长期腐烂 |
| healer | 失败后的修复 | 修的是测试还是产品——这是最危险的一条 | 把真实回归「修」成绿色，缺陷被静默吞掉 |
| 业务 Oracle | 独立于生成过程的判据 | 来源是否独立：数据库、账本、事件或人工确认清单 | 由生成脚本的同一模型顺手生成，等于没有判据 |

> 三个角色可以由 AI 承担，第四行不能。这条分界是这一页唯一必须记住的东西。

*依据：[microsoft/playwright-mcp](https://github.com/microsoft/playwright-mcp#readme) · [browser-use/browser-use](https://docs.browser-use.com/) · [microsoft/playwright](https://playwright.dev/docs/intro)*

### 这张图的 6 个节点，本页各交付什么

这张图的三个 AI 角色（Planner、Generator、Healer 中的前两个）职责必须分开：planner 决定测什么，generator 决定怎么写。混在一起时，模型会倾向于生成它容易写对的用例，而不是该测的用例。

「Business mutation」是本页的验收关口，与 TD-T06 的 mutation 是同一个原理在 E2E 层的应用。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| Risk/PRD | 从风险与需求出发确定测什么，不由生成器决定测试范围 | 风险驱动的测试计划 |
| Planner | 把风险转成测试意图，输出用例意图而非代码 | 测试意图清单 |
| Generator | 把意图实现为脚本，产出保持候选状态 | 测试脚本候选 |
| Sandbox browser | 在隔离环境执行，禁止对生产数据产生副作用 | 隔离执行环境配置 |
| Business mutation | 注入业务逻辑变异体，验证脚本真的会失败 | 业务变异测试报告 |
| Human test review | 人工评审反模式与断言强度，通过后才进套件 | 评审记录与准入决定 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 三个角色各自的审查重点

三个角色产出的东西不同，审查方式也不同。用同一套标准审查全部，会漏掉最危险的那部分。

右列是这个角色最典型的失效——healer 那一行是三者中后果最严重的。

| 角色 | 审查重点 | 典型失效 |
| --- | --- | --- |
| planner | 计划是否绑定风险 ID 与来源 | 按页面元素罗列而非按风险 |
| generator | 断言是不是业务状态而非元素可见 | 只断言按钮存在就算通过 |
| healer | 改动是否只涉及非语义表面 | 删断言或改期望值让测试变绿 |

> 三行的审查成本递增，风险也递增。healer 的产出必须逐条人工确认，不能自动合并。

*依据：[browser-use/browser-use](https://docs.browser-use.com/)*

### 这一页的验收口径：断言强度而不是脚本数量

T18-1 是本页唯一真正的质量指标：脚本能不能在业务被改坏时失败。其余三条都是保证这个指标可信的前提。

T18-3 的反模式检查可以完全自动化，成本极低而收益很高——硬等待和绝对定位是 E2E 套件腐坏的两个主要来源。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| T18-1 | 业务断言强度 | 业务逻辑变异体杀伤率 ≥ 70%；核心交易路径 ≥ 90% | 每次生成 |
| T18-2 | 业务状态判据 | 以后端业务状态断言的用例占比 ≥ 80%，纯 UI 断言用例须标注其局限 | 每次生成 |
| T18-3 | 反模式拦截 | 硬等待、绝对 XPath、跳过校验步骤等反模式在准入脚本中的数量 = 0 | 每次生成 |
| T18-4 | 人工准入 | 未经人工评审直接进回归套件的脚本数 = 0 | 每次生成 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在用 AI 提效、实际在积累假绿的做法

这两种做法都能显著提高测试数量与通过率。

问题是通过率上升的原因不是质量提升。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| Agent 生成的测试全部通过，截图也正常，直接合并 | 跑通了、有截图、覆盖也增加了 | 页面可见不等于业务正确。生成测试常常只断言元素存在。必须注入后端业务故障，确认它会变红 |
| healer 自动修复失败测试，流水线恢复绿色 | 维护成本大幅下降，绿色也确实恢复了 | healer 可能改的是断言而不是定位器。必须比对 diff，并让修复后的测试在原业务变异下仍然失败 |

> 两条的共同判据是同一个：注入一个已知业务缺陷，看它会不会变红。

*依据：[microsoft/playwright-mcp](https://github.com/microsoft/playwright-mcp#readme)*

### 生成测试很多但缺陷没少时按什么顺序查

这类问题的根因几乎总是断言层次太浅。按下表逐项查。

查完之后通常需要重写断言，而不是增加用例。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 测试全绿但线上有问题 | 断言只到页面层 | 注入后端状态故障验证 |
| 改版后大批测试失败 | 定位器脆弱 | 改用稳定属性并加显式等待 |
| healer 修完仍然全绿 | 断言被删或期望被改 | 比对 diff 并重跑业务变异 |
| 无法判断测的是什么 | 计划未绑定风险 | 要求 planner 输出风险 ID |

> 第三行是最危险的：流水线绿色，而检测力已经被悄悄移除。

### 验证一批生成测试的真实检测力：约 50 分钟

不需要重新生成。拿现有的生成测试，注入一个业务故障就够了。

1. 选一批 AI 生成的、当前全绿的端到端测试。
2. 在后端注入一个有业务含义的故障，例如把需要人工复核的状态直接改成已完成。
3. 重跑这批测试，统计有多少条变红。
4. 对没有变红的用例，检查它们的断言——多数只断言了页面元素而没有断言业务状态。
5. 把断言改到业务状态层，重跑一次，确认现在会变红。

**期望结果**：典型结果是只有少数用例变红。这个比例就是这批生成测试的真实检测力，通常远低于覆盖率给人的印象。

> ⚠ 注入故障要选有业务含义的，不要选会导致页面报错的。页面报错时所有测试都会红，测不出断言层次。

### 这一页的出口判据

这一页的门禁全部作用在脚本进入回归套件之前。进了套件再治理的成本要高一个量级，因为此时它已经开始产生「维护债」。

第三段要接受的是自动化覆盖的边界：有些场景（第三方跳转、真实支付）不适合自动化，这些必须显式列出而不是默默不测。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 准入脚本中反模式数量 > 0 时阻断<br>未经人工评审的脚本进入回归套件的数量 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 变异体杀伤率按业务模块分片给出 95% CI，变异体 < 30 个时结论记为证据不足<br>与上一版本比较以区间重叠判定，不用点估计差值 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 不适合自动化的场景清单，由测试负责人列出并签字接受人工覆盖<br>纯 UI 断言用例的局限，由产品 owner 知情接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一条生成测试的合并门槛

门槛只有一条：在注入的业务故障上会变红。跑通、有截图、覆盖高都不能替代它。

healer 的产出额外加一条：修复后仍须在原业务变异下失败。

- 断言业务状态，不断言页面元素可见
- 合并前用业务故障验证检测力
- healer 的改动逐条比对 diff 后人工合并

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Playwright：跨浏览器端到端测试框架](https://playwright.dev/docs/intro)** — Web UI 专项主力工具
  - 能证明：浏览器自动化的三项工程能力：actionability 自动等待取代 sleep、语义 locator 取代 CSS/XPath 坐标、浏览器上下文隔离取代用例间清理。它们共同把 UI 测试的不稳定来源从「时序」降到「业务」。
  - 不能证明：自动等待解决的是元素可交互，不是业务就绪。页面上按钮能点了不代表后台事务已提交；UI 全绿仍需副作用层佐证。
  - `microsoft/playwright` · 版本 v1.62.1（2026-07-30） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Playwright MCP：把浏览器能力暴露给模型的 MCP server](https://github.com/microsoft/playwright-mcp#readme)** — 传统 UI 自动化 × AI 的实际结合点
  - 能证明：模型驱动浏览器时使用的是可访问性快照而非截图像素，动作走 Playwright 既有的 actionability 机制。这说明 AI 层是叠加在传统自动化能力之上的，不是替代它——底层定位与等待仍是那一套。
  - 不能证明：模型能操作浏览器不等于它能判断对错。断言仍必须由确定性 oracle 提供；把模型的「看起来成功了」当结论，就是本模块 TD-PS04 反例表的第一行。
  - `microsoft/playwright-mcp` · 版本 v0.0.79（2026-08-06） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[browser-use：模型驱动浏览器的执行器](https://docs.browser-use.com/)** — 浏览器 Agent 实现
  - 能证明：模型驱动浏览器时的实际接口形态：把页面转成结构化的可交互元素列表交给模型，而不是让模型看像素。这决定了它的失败形态是「选错元素」而不是「点错坐标」。
  - 不能证明：能完成任务不等于能判断任务完成。演示成功率与你自己页面上的成功率无关，且版本迭代很快，行为不稳定。
