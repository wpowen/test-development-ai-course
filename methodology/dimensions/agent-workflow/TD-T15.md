## TD-T15

### 只看最后一句回答，你会漏掉九成发生在中途的失败

Agent 与单次模型调用最大的差别是：它在给出回答之前做了十几个决定，而每个决定都可能错。只对终局打分的评估，对这十几个决定完全无感。

第一条的数量级是本页存在的全部理由。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 只对最终输出打分 | 只评终局的评估会漏掉约 90% 发生在执行中途的失败模式 | 「答案对了」被当成「过程对了」，而 Agent 可能是靠 3 次多余的写操作凑出来的 |
| 轨迹不落盘就下安全结论 | 缺轨迹级评估会系统性漏掉约 44% 的安全违规与约 13% 的鲁棒性失败 | 把「没测出安全问题」当成「没有安全问题」 |
| 答对了但过程做错了事 | 同一任务的最优步数与实际步数之比（步骤效率比）低于 0.5 时，说明一半以上的动作是无效或有害的 | 验收通过，上线后出现大量「结果对但顺便改坏了别的」的工单 |

> 解法是把 Agent 质量拆成三层分别出分：业务终态、每一步动作、完整轨迹——三层缺一层就有一类失败看不见。

### 三层判定的四个词

Agent 的「对不对」有三个互不替代的层次。混在一起判，就会出现结果正确但过程越权的假绿。

| 术语 | 一句话解释 |
| --- | --- |
| Outcome | 业务最终状态是否正确；它是用户看到的那一层 |
| Step | 每次工具调用的工具、参数、权限、前置条件是否合法 |
| Trajectory | 整条决策序列的状态、重试、交接与终止原因是否可接受 |
| 禁止副作用 | 无论路径如何都不允许发生的动作；它比黄金路径更好用 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[langchain-ai/langgraph](https://langchain-ai.github.io/langgraph/)*

### 终局判定为什么必然漏掉大部分失败

只看最后一句回答，等价于只验收结果不审计过程。对单次调用这没问题——过程就是一步。对 Agent 就完全不同：一个正确的终局可以由一条充满错误的路径产生，而那条路径上的每一个错误都可能已经在真实世界留下了后果。

具体形态包括：多调了三次付费接口（成本），读取了本不该访问的数据（越权），把一条错误结论写进了长期记忆（污染下一次），对同一个不可逆动作重试了两次（副作用重复）。这四类在终局判定下全部不可见，因为终局确实是对的。

因此判定必须分三层：Outcome 判终局对不对，Step 判每一步的工具选择与参数对不对，Trajectory 判整条路径是否合理——有没有绕圈、有没有做多余的事、有没有在该停的时候停。三层各自能发现的失败类型不重叠。

「禁止副作用」是横切三层的一条独立判据：某些动作在测试环境中无论如何都不应该发生。它不是「做对了没有」，而是「有没有发生」，因此它是布尔的、硬红线的，且必须在 Step 层就拦下，不能等到 Outcome。

*依据：[langchain-ai/langgraph](https://langchain-ai.github.io/langgraph/) · [open-telemetry/semantic-conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/)*

### 三层判定各自靠什么观测

三层的观测手段不同，因此接入成本也不同。Outcome 层几乎零成本，Trajectory 层需要完整的 trace 与状态快照。

第四行单独列出，因为它是唯一一条不看「对不对」只看「有没有」的判据，也是唯一必须做成硬红线的。

| 判定层 | 判什么 | 靠什么观测 | 漏什么 |
| --- | --- | --- | --- |
| Outcome | 终局结果是否正确 | 与单次调用相同的结构与语义断言 | 过程中的成本、越权、记忆污染、重复副作用全部不可见 |
| Step | 每一步的工具选择与参数是否正确 | 工具调用契约（MCP schema）+ 参数边界断言 | 单步都对，整条路径仍可能绕圈或做多余的事 |
| Trajectory | 整条路径是否合理、是否在该停时停 | 状态图 + 完整 trace（LangGraph、OTel GenAI） | 路径合理不代表业务结果正确，仍需 Outcome 层 |
| 禁止副作用 | 某些动作有没有发生（不问对错） | 副作用账本 + 调用层拦截 | 只覆盖列举出来的动作，没想到的不会被拦 |

> 四行是并列不是递进：任何一层单独使用都会漏掉另外三层能发现的东西。

*依据：[langchain-ai/langgraph](https://langchain-ai.github.io/langgraph/) · [modelcontextprotocol/modelcontextprotocol](https://modelcontextprotocol.io/) · [open-telemetry/semantic-conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/)*

### 这张图的 6 个节点，本页各交付什么

这张图把 Agent 的可观测面分成三层：最下面是业务终态（对不对），中间是逐步动作（怎么做的），上面是完整轨迹（决策链是否合理）。

「Policy blockers」横跨三层：它记录的是那些无论结果对错都必须阻断的动作，比如越权写操作。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| Business outcome | 以业务状态变化而非模型自述判定任务是否完成 | 业务终态断言集 |
| Tool step ledger | 逐次工具调用落盘，记录工具名、参数、返回与耗时 | 工具调用台账 |
| State snapshots | 在关键步骤前后快照系统状态，用于判断副作用 | 状态快照序列 |
| Trajectory graph | 把执行过程还原成决策图，用于逐 span 打标 | 轨迹图与 span 标注 |
| Policy blockers | 记录违反策略的动作，无论最终结果对错一律阻断 | 策略违规记录 |
| Human decision | 对轨迹质量做人工判断，机器只提供证据不下结论 | 轨迹评审记录 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 三层各自判什么、各自漏什么

三层必须分别判定并分别报告。用一个总分把它们合起来，最贵的那类失败会被平均掉。

右列写的是只看这一层时会漏掉什么——三行合起来就是为什么必须三层都要。

| 层 | 判什么 | 只看这一层会漏掉 |
| --- | --- | --- |
| Outcome | 最终业务状态与禁止副作用 | 中途越权、成本失控、死循环 |
| Step | 工具、参数、权限、前置条件 | 单步都合法但组合起来越权 |
| Trajectory | 状态、重试、交接、终止原因 | 最终结果正确掩盖的过程问题 |

> 三层的失败会在报告里表现为不同的行。任何把它们合并成一个分数的做法，都会让 Step 层的越权消失。

*依据：[langchain-ai/langgraph](https://langchain-ai.github.io/langgraph/)*

### 这一页的验收口径：三层分别出分

T15-2 的逐 span 打标是本页的核心动作：对每一步打四类标签（工具选择、参数构造、观测利用、步骤必要性），才能得出首错位置分布。

首错位置分布比总成功率更有行动价值：它把「73% 成功」这个无法行动的数字，变成「失败集中在第 3 步和第 7 步」这个可以派活的结论。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| T15-1 | 轨迹完整性 | trace 完整率 = 100%；任一 trace 可完整重放的比例 ≥ 95% | 每次评测 |
| T15-2 | 逐步打标覆盖 | span 级打标覆盖执行步骤的比例 ≥ 90% | 每次评测 |
| T15-3 | 步骤效率 | 步骤效率比（最优步数 / 实际步数）≥ 0.6；无效循环率 ≤ 2% | 每次发布 |
| T15-4 | 终态判定口径 | 以业务状态断言判定完成的比例 = 100%，以模型自述判定的比例 = 0 | 每次评测 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在评轨迹、实际还是在评终局的做法

这两种做法都读了完整轨迹，比只看最后一句话进步很多。

问题是判定方式仍然是单点的。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 把整条轨迹交给评审模型打一个总分 | 读了全部过程，评分也考虑了中间步骤 | 一个总分无法定位第几步坏的，也会把一次越权调用平均成小幅扣分。三层必须分别出结论 |
| 用一条人工写的标准轨迹逐步比对 | 有明确参照，判定客观，实现简单 | 它会把合法的替代路径判成失败。先查订单再读政策与反过来可能都正确。应写不变量与禁止副作用 |

> 两条的共同修法：用「禁止什么」和「必须满足什么」代替「必须怎么走」。

*依据：[modelcontextprotocol/modelcontextprotocol](https://modelcontextprotocol.io/)*

### 结果对但心里不踏实时按什么顺序查

「结果是对的但总觉得不对劲」通常是真的有问题。下表把这种感觉换成四个可查的项。

四行都可以从现有 trace 直接查，不需要新增采集。

| 症状 | 先查哪一层 | 下一步 |
| --- | --- | --- |
| 最终回复正确但用户投诉 | Step 层 | 查有没有未授权的工具调用 |
| 同样任务耗时差异极大 | Trajectory 层 | 查步骤数与重试次数分布 |
| 合法路径被判失败 | Oracle 写法 | 改为不变量加禁止副作用 |
| 失败但说不清哪步 | 轨迹完整性 | 检查 trace 是否记录了每次调用 |

> 第一行是最典型的：Outcome 绿、Step 红，而报告只报了 Outcome。

### 给一个真实任务写三层判据：约 40 分钟

不需要跑测试。把判据写清楚，本身就能暴露当前测试漏了哪一层。

1. 选一个含写操作的真实 Agent 任务，写下业务最终状态的判定条件。
2. 列出禁止副作用：无论路径如何都不允许发生的动作，通常与资金、权限、对外通知有关。
3. 列出必要检查点：必须发生的前置动作，例如写操作前必须验证身份。
4. 列出允许的替代路径集合，确认它们都能通过你写的判据。
5. 对照现有测试，标出三层各覆盖了哪些——多数团队会发现 Step 层几乎为空。

**期望结果**：产出是一份三层判据表。最有价值的一栏通常是「禁止副作用」——写出来之后会发现现有测试完全没有断言它们。

> ⚠ 不要把「效率低」写成禁止副作用。禁止的应当是不可接受的动作，而不是不优雅的路径。

### 这一页的出口判据

这一页的门禁拦的是证据不足，而不是质量不佳。没有轨迹就下 Agent 质量结论，等于用一张照片评价一部电影。

第三段要接受的是轨迹评审的人力成本：逐 span 打标很贵，抽样比例是成本与信心之间的显式取舍。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | trace 完整率 < 100% 时阻断，缺失轨迹的任务不计入结论<br>以模型自述判定任务完成的用例数 > 0 时阻断，须改为业务状态断言 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 步骤效率比与无效循环率按任务类型分片给出 95% CI，单片 < 30 条时只报区间<br>首错位置分布的样本 < 50 条失败时结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 逐 span 打标的抽样比例，由测试负责人根据成本签字确定<br>已知但暂不修复的低效轨迹模式，由产品 owner 明示接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一份三层判据表

三层判据表的作用是让报告能同时回答三个问题：结果对吗、过程合法吗、整体可接受吗。

它也让「合法替代路径」这件事第一次被显式表达，而不是靠评审时临时讨论。

- 三层分别判定、分别报告，不合成总分
- 用不变量加禁止副作用代替黄金路径
- 把允许的替代路径显式列出来

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[OpenTelemetry 语义约定（含 GenAI 约定）](https://opentelemetry.io/docs/specs/semconv/gen-ai/)** — 传统可观测性 × AI 的关键结合点
  - 能证明：模型调用的 trace 属性已经有了标准命名：模型标识、token 用量、请求参数、结束原因等被纳入与 HTTP、数据库同一套语义约定体系。这意味着 LLM 调用不需要另建一套观测体系，而是接进既有链路。
  - 不能证明：GenAI 部分的约定仍在演进，字段名可能变更；且约定只规定怎么记，不规定记了之后如何判断质量。
  - `open-telemetry/semantic-conventions` · 版本 v1.44.0（2026-08-04） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Model Context Protocol 规范](https://modelcontextprotocol.io/)** — 工具契约规范
  - 能证明：模型可调用的工具有了机器可读契约：名称、输入 schema、描述、错误返回。这让「Agent 能调什么工具」从代码里的隐含事实变成可审计、可版本化、可做契约测试的工件。
  - 不能证明：规范描述接口不描述权限。哪些工具允许被哪个会话调用、不可逆动作要不要二次确认，规范里没有，必须在工具调用层自己实现并验证。
  - `modelcontextprotocol/modelcontextprotocol` · 版本 2026-07-28（2026-07-28） · NOASSERTION · 许可证未能自动判定，按最保守口径只链接不搬代码
- **[LangGraph：把 Agent 表达成显式状态图](https://langchain-ai.github.io/langgraph/)** — 编排结构参考
  - 能证明：把 Agent 从「一个循环加一堆 if」变成显式的节点与边之后，状态、分支、中断点、检查点都成为可枚举对象——可枚举才可测。这是长流程可靠性测试能开展的结构前提。
  - 不能证明：结构清晰不等于行为正确。节点内部仍由模型驱动，同一条边上的两次执行可能走出完全不同的结果。
  - `langchain-ai/langgraph` · 版本 1.2.11（2026-08-11） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
