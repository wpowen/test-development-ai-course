## TD-B06

### 公共 Benchmark 测的是通用能力，你要发布的是具体业务

公共 Benchmark 的价值是方法而不是分数。直接拿它的分数做发布判断，等于用一场通用考试的成绩决定一个具体岗位的录用。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 用公共分数直接做选型决策 | 公共任务与业务任务的分布距离通常很大；指标与业务结果相关性低于 0.6 时该指标不具备决策价值 | 选了榜单第一的模型，上线后在自己场景里表现不如第二 |
| 只借分数不借方法 | 公共 Benchmark 真正可迁移的是任务设计、协议控制与报告规范这 3 类方法，分数本身不可迁移 | 花了很多精力追榜，内部却没有一套可复用的评测规范 |
| 内部基准没有维护 owner | 无 owner 的内部基准通常在 2～3 个版本后停止更新，随后与业务分布脱节 | 内部基准还在跑，但它测的已经不是现在的业务了 |

> 本页的做法：借公共 Benchmark 的方法，建自己的业务风险基准，并给它指定长期 owner。

### 从公共榜单迁移到企业基准的四个词

公共 Benchmark 的价值不在分数，在方法。这四个词决定你能迁移到什么程度。

| 术语 | 一句话解释 |
| --- | --- |
| 任务分布 | 你的业务真实遇到的任务构成；它与任何公共榜单都不同 |
| 风险加权 | 按失败成本给任务加权，而不是按数量平均 |
| 内部基准 | 用自己的任务、数据与 Scorer 建立的基准；它不与外部可比，也不需要 |
| 人工基线 | 同样任务由人完成的成本与质量；没有它，ROI 无法计算 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/)*

### 公共 benchmark 里可迁移的是方法，不是分数也不是任务

公共 benchmark 的分数不可迁移：它测的是通用能力，而你要发布的是一个具体业务。榜单第一的模型在你的任务上可能不如第三名，这不是例外情况而是常态——因为你的任务分布与榜单任务分布几乎没有交集。

可迁移的是三样东西：评测的结构（数据集 / 执行 / 判据三层分离）、指标的定义方式（分母写清楚、区间带上）、以及防污染与防过拟合的纪律（四种数据集角色、封存 holdout、敏感性分析）。这些是方法论，与具体任务无关，因此迁移成本很低、收益很高。

企业基准的构造起点不是「抄一个公共 benchmark 的任务格式」，而是从真实工单、真实会话、真实文档里抽任务，并按失败成本加权。加权是关键：公共 benchmark 每题等权，而你的业务里不同错误的代价可以相差几个数量级。

最后必须补一条人工基线：同样的任务，一个熟练员工做得怎么样。没有这条线，「85% 准确率」既可能是巨大成功也可能是完全不可接受——因为你根本不知道人做是多少。这条基线的缺失，是企业 AI 评测里最常见也最致命的空白。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/) · [open-compass/opencompass](https://opencompass.readthedocs.io/) · [SWE-bench/SWE-bench](https://www.swebench.com/)*

### 六项里哪些能从公共基准搬过来，哪些必须自建

第二列只有三个取值：能、不能、必须补。这张表的用途是在启动企业基准前，先把预期钉死在正确的位置上。

注意最后两行——它们是工作量的大头，而且没有任何工具能替代，需要业务与一线员工直接参与。

| 迁移对象 | 能不能迁 | 怎么做 | 边界 |
| --- | --- | --- | --- |
| 分数与榜单名次 | 不能 | —— | 通用能力不预测你的业务表现，交集通常接近零 |
| 评测结构（数据 / 执行 / 判据分离） | 能 | 用 Inspect 这类分层框架落地 | 框架不提供判据，scorer 仍要自己写 |
| 指标定义与分母纪律 | 能 | 每个指标写清分母、排除项与区间 | 定义清楚不代表指标选对了 |
| 防污染与防过拟合纪律 | 能 | 四种数据集角色 + 封存 holdout + 敏感性分析 | 间接泄漏仍然无法排除 |
| 任务来源 | 不能，必须自建 | 从真实工单 / 会话 / 文档抽取，按失败成本加权 | 需要业务参与定义成本，工具替代不了 |
| 人工基线 | 必须补 | 同一批任务由熟练员工做一遍 | 人的表现也有方差，需多人多次才能作为基线 |

> 六行里有四行能迁，但工作量集中在不能迁的那两行。低估这一点是企业基准项目最常见的排期失误。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/) · [open-compass/opencompass](https://opencompass.readthedocs.io/) · [SWE-bench/SWE-bench](https://www.swebench.com/) · [UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/)*

### 公共 Benchmark 的哪些部分可以迁移

可以迁移的是方法与结构，不是数据也不是阈值。下表逐项区分。

右列写的是迁移时必须替换的内容——照搬这些会让内部基准失去业务意义。

| 公共 Benchmark 的组成 | 能否迁移 | 迁移时必须替换什么 |
| --- | --- | --- |
| 任务分类方式 | 可以 | 换成你的业务任务族 |
| 协议设计（几次机会、怎么问） | 可以 | 按你的产品实际交互方式 |
| 逐题记录与聚类统计 | 可以 | 无需替换，直接沿用 |
| 数据集 | 不可以 | 必须用自己的任务采样 |
| 绝对分数与阈值 | 不可以 | 必须自己实测重设 |
| 排行榜排名 | 不可以 | 内部基准不需要排名 |

> 能迁移的三项都是方法，不能迁移的三项都是数值——这正是「借鉴方法不借鉴数字」的具体含义。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/)*

### 这一页的验收口径：内部基准的有效性

B06-1 的相关性是内部基准是否成立的唯一判据：它与业务结果的相关性不足时，无论设计多精巧都不该用于发布决策。

B06-4 的更新节奏是防腐措施。业务分布会漂移，一个半年不更新的内部基准，其结论的适用性需要重新评估。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| B06-1 | 业务相关性 | 内部基准核心指标与业务结果的相关性 ≥ 0.6 | 每季度 1 次 |
| B06-2 | 风险覆盖 | 业务风险目录中被基准覆盖的比例 ≥ 90%，未覆盖项须显式列出 | 每次基准更新 |
| B06-3 | 协议一致性 | 各候选模型使用同一协议的比例 = 100%；适配层差异项数 = 0 | 每次比较 |
| B06-4 | 维护时效 | 内部基准更新间隔 ≤ 90 天；超期未更新时结论标记为可能过期 | 每季度 1 次 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在建内部基准、实际在抄榜单的做法

这两种做法都能很快产出一份看起来专业的内部评测报告。

问题是这份报告无法支撑任何业务决定。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 直接采用某公共榜单的数据集作为内部基准 | 数据质量高、标注规范、社区认可 | 它的任务分布不是你的业务分布。高分不能推出「在我们场景可用」，低分也不能推出不可用 |
| 按公共榜单的阈值设定内部准出线 | 阈值来自权威来源，有据可依 | 公共阈值对应的是公共任务的失败成本。你的退款场景失败一次的代价与之完全无关，阈值必须按你的风险重设 |

> 两条的共同错误：把外部数字当成外部权威，而外部权威只存在于方法层面。

### 内部基准建了但没人用时按什么顺序查

内部基准最常见的结局不是不准，是没人看。原因通常在设计而不在数据。

四行按出现频率排列。

| 症状 | 先怀疑 | 下一步检查 |
| --- | --- | --- |
| 结果无法支撑决定 | 没有绑定具体发布问题 | 为每个指标写清它回答哪个决定 |
| 高风险场景被平均掉 | 按数量平均而非风险加权 | 改为风险加权并单列 blocker 切片 |
| 跑一次成本太高 | 任务集过大 | 分冒烟集与完整集 |
| 没有对照 | 缺人工基线 | 补同任务集的人工基线 |

> 第一行是根本问题：一个不改变任何决定的基准，无论多准确都不会被使用。

### 用你的真实任务建一个最小内部基准：约 90 分钟

最小不是简陋。它只需要覆盖一个高风险任务族，但每一层都必须完整。

1. 选一个高风险任务族，从生产中抽取一批真实任务并脱敏。
2. 为每条标注期望结果与失败成本等级；成本等级用于后续的风险加权。
3. 设计协议：怎么问、给几次机会、允许用哪些工具，全部固定并记录。
4. 选 Scorer：能用规则判定的部分用规则，剩余部分才用模型判分，并记录 Scorer 版本。
5. 跑一次基线，同时记录同任务集的人工完成时间与质量，作为对照。

**期望结果**：产出是一个覆盖单一任务族的完整基准，包含数据、协议、Scorer、风险加权与人工基线。它比一个覆盖十个任务族但没有人工基线的基准有用得多。

> ⚠ 不要一开始就追求覆盖全部业务。先让一个任务族的完整链路跑通，再横向复制。

### 这一页的出口判据

这是 TD-M06 的出口门禁，它判断的是「你有没有一套属于自己的、可信的评测能力」，而不是「你在公共榜单上排第几」。

第三段要接受的是覆盖缺口与维护成本：内部基准永远覆盖不全，且需要持续投入，这两件事必须被明确接受而不是被默认。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 内部基准与业务结果相关性 < 0.6 时阻断其作为唯一发布依据<br>候选模型间协议不一致项数 > 0 时阻断比较，结论作废 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 相关性估计基于至少 30 个历史发布点，样本不足时标注为未验证<br>候选比较预注册效应量/非劣界并报告配对或分层 bootstrap 95% CI；不以两个 CI 是否重叠或点估计排名判定 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 业务风险目录中未被基准覆盖的部分，由业务 owner 列出并签字接受<br>内部基准的维护投入与更新节奏，由测试负责人承诺并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[SWE-bench/SWE-bench](https://www.swebench.com/)*

### 带走一个能改变决定的最小基准

判断内部基准是否成立只有一个标准：它的结果会不会改变某个具体的决定。

如果答案是否，那它只是一份定期产出的报表，无论数字多漂亮。

- 只迁移方法与结构，数据与阈值必须自建
- 按失败成本加权，不按任务数量平均
- 补上人工基线，否则 ROI 无法计算

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Inspect：任务 / solver / scorer 分层的模型评测框架](https://inspect.aisi.org.uk/)** — 评测框架
  - 能证明：评测可以拆成三个独立可替换的部件：dataset 定义问什么、solver 定义怎么问、scorer 定义怎么判。三者分离之后，换模型不用改判据，改判据不用改数据集——这是把一次性评测脚本变成可回归资产的结构条件。
  - 不能证明：框架不提供判据。scorer 写得对不对、数据集有没有覆盖你的风险切片，框架一概不管，全绿只说明流程跑通了。
  - `UKGovernmentBEIS/inspect_ai` · 版本 release/2025-11-28 · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[HELM：多场景、多指标的整体性评测](https://crfm.stanford.edu/helm/)** — 评测方法学
  - 能证明：单一准确率无法描述模型能力。HELM 的做法是把场景（scenario）与指标（metric）做成正交的两维，同一个场景同时报准确率、校准度、鲁棒性、公平性、效率——「模型 A 比 B 好」这句话必须指明在哪个场景的哪个指标上。
  - 不能证明：覆盖的是公开场景，不覆盖你的业务分布。榜单名次不能迁移到企业任务上。
  - `stanford-crfm/helm` · 版本 v0.5.16（2026-04-30） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[OpenCompass：面向中文与多语言的评测体系](https://opencompass.readthedocs.io/)** — 评测执行器
  - 能证明：评测配置（数据集、模型、推理参数、后处理）可以完全声明式表达并版本化，使跨模型、跨版本的对照在配置层面就可审计，而不是靠人记得当时怎么跑的。
  - 不能证明：中文基准同样存在污染与分布偏移问题；配置可复现不等于结论可迁移。
  - `open-compass/opencompass` · 版本 0.5.3（2026-06-29） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[SWE-bench：以真实仓库 issue 为任务的 Agent 基准](https://www.swebench.com/)** — 任务级基准
  - 能证明：任务级评测的判据可以完全确定：补丁应用后跑原仓库的测试，通过即算解决。这比模型评判可靠得多，也说明「只要任务本身自带 oracle，评测就不需要 judge」。
  - 不能证明：任务来自公开仓库，训练数据污染无法排除；单次成功率也不代表在你私有代码库上的表现。执行成本高，不适合做每次提交的门禁。
  - `SWE-bench/SWE-bench` · 版本 v4.1.0 · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
