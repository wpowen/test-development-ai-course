## TD-B03

### Accuracy、Pass@k、Resolved Rate 的分母不同，混着讲就是在比不同的东西

这三个指标经常出现在同一份报告里，读者默认它们可比。实际上它们的分母、重复次数与成功定义都不同，混讲会产生看似合理实则错误的结论。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 用 pass@1 代表可靠性 | pass@1 与 pass^k 的差距在长流程任务上可以非常大：公开结果中出现过 pass@1 为 61% 而 pass^8 仅 25% | 「六成能做对」被读成「六成用户能用」 |
| resolved rate 的分母含未尝试项 | 分母是否包含模型主动放弃的样本，会让同一份结果的 resolved rate 相差 5～15pt | 两份报告数字不同，团队以为是模型差异，实际是分母定义不同 |
| Judge 打分与确定性断言混在一个平均里 | 确定性部分的正确率可达 100%，Judge 部分受 κ 限制；混算会让 Judge 的不确定性被稀释看不见 | 总分很稳，实际其中一半的不确定性完全没被报告 |

> 解法是从逐题原始记录出发，分别计算各指标并各自声明分母，不做跨指标平均。

### 四个最容易被混讲的指标

这四个指标经常出现在同一张表里，但它们的分母与含义完全不同，直接比较没有意义。

| 术语 | 一句话解释 |
| --- | --- |
| Accuracy | 逐题判对的比例；分母是题数，适合有唯一答案的任务 |
| Pass@k | k 次采样中至少一次成功的比例；它衡量能力上限，不衡量稳定性 |
| Resolved rate | 端到端解决问题的比例；分母是任务数，通常远低于逐步 accuracy |
| Judge score | 模型判分的连续得分；它是估计值，误差取决于 Judge 校准 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[SWE-bench/SWE-bench](https://www.swebench.com/)*

### 指标的分母决定了它在回答什么

Accuracy 的分母是全部样本，它回答「整体对了多少」。Pass@k 的分母是任务数、分子是「k 次尝试中至少成功一次的任务数」，它回答「给足重试机会能不能做到」。Resolved rate 的分母通常是可解任务数，排除了环境失败——它回答「在能跑起来的任务里做到了多少」。

分母不同意味着它们衡量的根本不是同一件事，混着报会产生非常大的误导。Pass@10 高而 Pass@1 低，说明能力存在但不稳定；把 Pass@10 当成「准确率」引用，会让读者以为系统一次就能做对，而这两种情况对应的产品设计完全不同。

Judge score 更特殊：它的分母是样本数，但每个样本的分值来自一个有误差的估计。它可以描述趋势，不能与前三个并列比较，也不适合单独作为硬门禁——因为门禁需要的是判决，而它给的是估计。

选指标的实用规则只有两条：动作可重试就看 Pass@k，动作不可逆就只能看 Pass@1 或 pass^k；报告里必须写清分母排除了什么。第二条比第一条更常被违反。

*依据：[SWE-bench/SWE-bench](https://www.swebench.com/) · [stanford-crfm/helm](https://crfm.stanford.edu/helm/)*

### 五个指标的分母、适用范围与误用后果

读这张表时先看第二列。分母一栏相同的指标才可以放在一起比，分母不同的必须分开报。

第五行单独列出来，是因为它在实践中最常被混进前四行——而它的每一个数值都带着一个未被度量的误差。

| 指标 | 分母是什么 | 适合回答 | 误用后果 |
| --- | --- | --- | --- |
| Accuracy | 全部样本 | 整体正确比例 | 类别不平衡时被多数类主导，掩盖关键切片的失败 |
| Pass@k | 任务数（k 次中至少一次成功） | 允许重试时的可达性 | 用于不可逆动作会严重高估真实能力 |
| Resolved rate | 可解任务数（已排除环境失败） | 在可跑任务里的完成度 | 不写清排除了什么，则无法与任何其他数字比较 |
| pass^k | 任务数（连续 k 次全成功） | 稳定性 | k 未声明时数字完全不可比 |
| Judge score | 样本数，但每个分值是有误差的估计 | 趋势与相对变化 | 与前四项并列比较，或单独当硬门禁 |

> 同一份实验通常需要同时报其中三到四个。只报一个的报告，多半是挑了最好看的那个。

*依据：[SWE-bench/SWE-bench](https://www.swebench.com/) · [stanford-crfm/helm](https://crfm.stanford.edu/helm/) · [confident-ai/deepeval](https://deepeval.com/docs/getting-started)*

### 这张图的 7 个节点，本页各交付什么

这张图的关键顺序是：先落原始记录，再分流到确定性 Oracle 与 Judge 两条判分路径，最后才聚合。反过来（先聚合再分析）就无法回溯。

「Raw Ledger」是本页的地基：只要它在，换任何一种指标定义都可以重算历史；它不在，历史就只剩下一个数字。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 逐题多次 Runs | 按 k 值对每题重复运行，保留每次的完整结果 | 重复运行配置与结果 |
| Raw Ledger | 逐题逐次原始记录落盘，不做任何聚合 | 原始记录台账 |
| 确定性 Oracle | 对可断言部分用确定性判据，正确率不受判分器不确定性影响 | 确定性判分结果 |
| Judge/校准 | 对开放式部分用 Judge，并附带其 κ 与校准日期 | Judge 判分结果与 Judge Card |
| Metric Calculator | 分别计算 accuracy、pass@k、pass^k、resolved rate，各自声明分母 | 指标计算结果与分母定义 |
| Slice/Confidence | 按切片聚合并计算置信区间 | 切片区间报告 |
| Decision Gate | 基于区间而非点估计做判断 | 发布判断记录 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 四个指标各自适合回答什么问题

选错指标比算错指标更常见。下表按「你想回答什么问题」来选，而不是按「哪个数字好看」。

右列的常见误用都在真实报告里出现过，且多数不是故意的。

| 指标 | 适合回答 | 常见误用 |
| --- | --- | --- |
| Accuracy | 有唯一答案的任务做对了多少 | 用在开放生成任务上 |
| Pass@k | 这个模型有没有可能做对 | 当成可靠性承诺给用户 |
| Resolved rate | 端到端能解决多少真实问题 | 与逐步 accuracy 混在一张表比较 |
| Judge score | 开放任务的相对质量 | 不报 Judge 校准就直接引用 |

> 报告里必须写清每个指标的分母是什么——分母不同的数字放在一起排序，是最常见的误导。

*依据：[SWE-bench/SWE-bench](https://www.swebench.com/)*

### 这一页的验收口径：分母、重复、区间

B03-1 的分母声明是本页最容易被跳过的一条，也是最能消除报告歧义的一条。两份数字不同的报告，八成差在分母上。

B03-3 把确定性判分与 Judge 判分分开报告，目的是让 Judge 引入的不确定性可见，而不是被确定性部分的高分稀释掉。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| B03-1 | 分母声明 | 每个指标显式声明分母定义的比例 = 100% | 每次报告 |
| B03-2 | 重复充分性 | pass^k 的 k ≥ 3；k < 3 时不得报告 pass^k | 每次评测 |
| B03-3 | 判分方式分离 | 确定性判分与 Judge 判分分别出分的比例 = 100%，混合平均次数 = 0 | 每次评测 |
| B03-4 | 区间完整 | 所有对外指标附 95% CI 的比例 = 100% | 每次报告 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/)*

### 两种看起来统计规范、实际不能支撑结论的报告

这两种报告都有区间、有样本量，看起来比只报一个数字严谨得多。

它们的问题在分母与独立性假设。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 每题跑 5 次共 500 个样本，按 500 算置信区间 | 样本量大，区间自然更窄，统计上更可信 | 同一题的 5 次采样高度相关。按 500 算会把区间算得远比真实窄，聚类单位应当是题目而不是采样 |
| Pass@5 达到 92%，可以对外承诺 | 这是重复采样后的结果，比单次更稳健 | Pass@k 衡量的是「有没有可能做对」。用户每次只会得到一个答案，承诺应当基于每次都对的口径 |

> 两条都在同一个位置出错：把「多次机会」的宽松口径当成了用户实际体验。

### 两份报告结论矛盾时按什么顺序查

同一个模型两份报告结论相反，多数不是造假，是口径不同。按下表逐项对齐即可定位。

对齐之后往往会发现，两份报告其实都对，只是在回答不同问题。

| 先对齐什么 | 为什么 | 不一致时的处理 |
| --- | --- | --- |
| 指标定义与分母 | 分母不同则不可比 | 换算到同一分母或放弃比较 |
| 采样次数 k | k 越大 Pass@k 越高 | 统一 k 后重算 |
| 聚类单位 | 按采样算会低估不确定性 | 改为按题目聚类 |
| Scorer 版本 | Scorer 变了尺度就变 | 锁定同一 Scorer 重跑 |
| 数据集版本 | 样本变了绝对值就变 | 比较必须同版本 |

> 五项全部对齐后仍然矛盾的情况很少见；那时才需要怀疑执行本身。

### 用同一份逐题记录算出四个指标：约 40 分钟

关键是从逐题原始记录出发，而不是从别人算好的汇总数字出发。

1. 取一份逐题、逐次采样的原始记录，至少包含题号、第几次采样、是否成功。
2. 分别算出 accuracy（按题）、pass@k、每次都成功的比例，以及三者的分母各是什么。
3. 以题目为聚类单位算置信区间，再故意以采样为单位算一次，比较两个区间的宽度差异。
4. 检查样本量是否足以支撑结论；不足时把结论写成 EVIDENCE-INSUFFICIENT。
5. 把四个指标写进一张表，每行注明分母、k 值与聚类单位。

**期望结果**：你会看到同一份数据下三个指标的差距，以及两种聚类方式下区间宽度的差异。后者通常比预期大得多。

> ⚠ 不要用汇总数字反推逐题结果。汇总丢掉了每题的成功次数分布，而那正是区分能力与稳定性的信息。

### 这一页的出口判据

这一页的门禁拦的是歧义而不是低分。一个分母不明的 85%，其信息量低于一个分母清楚的 62%。

第三段要接受的是 Judge 部分的不确定性上限：它由 κ 决定，无法通过增加样本消除。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 指标未声明分母的数量 > 0 时阻断报告发布<br>确定性判分与 Judge 判分混合平均的次数 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | pass^k 与 accuracy 分别给出 Wilson 95% CI，同任务多次重复须做聚类修正<br>样本 < 100 条时结论记为证据不足，不得作为发布依据 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | Judge 部分受 κ 限制的不确定性上限，由测试负责人签字接受<br>选择 k 值时的成本取舍，由评测 owner 写明理由并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一张写清分母的指标表

指标表的每一行都要写明分母、k 值与聚类单位。缺任一项，这个数字就无法被第二个人正确解读。

对外承诺只能基于每次都成功的口径，Pass@k 留给内部判断能力上限。

- 从逐题原始记录出发，不从汇总数字出发
- 聚类单位是题目，不是采样次数
- 样本不足时写 EVIDENCE-INSUFFICIENT

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[DeepEval：pytest 风格的 LLM 评测框架](https://deepeval.com/docs/getting-started)** — AI 侧断言执行器
  - 能证明：LLM 评测可以直接寄生在 pytest 生态里：用例、fixture、参数化、CI 集成全部复用既有工程习惯，降低把评测接进流水线的成本。
  - 不能证明：指标默认阈值是框架给的示例值，不是你业务的验收线。
  - `confident-ai/deepeval` · 版本 v4.1.7（2026-07-29） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[HELM：多场景、多指标的整体性评测](https://crfm.stanford.edu/helm/)** — 评测方法学
  - 能证明：单一准确率无法描述模型能力。HELM 的做法是把场景（scenario）与指标（metric）做成正交的两维，同一个场景同时报准确率、校准度、鲁棒性、公平性、效率——「模型 A 比 B 好」这句话必须指明在哪个场景的哪个指标上。
  - 不能证明：覆盖的是公开场景，不覆盖你的业务分布。榜单名次不能迁移到企业任务上。
  - `stanford-crfm/helm` · 版本 v0.5.16（2026-04-30） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[SWE-bench：以真实仓库 issue 为任务的 Agent 基准](https://www.swebench.com/)** — 任务级基准
  - 能证明：任务级评测的判据可以完全确定：补丁应用后跑原仓库的测试，通过即算解决。这比模型评判可靠得多，也说明「只要任务本身自带 oracle，评测就不需要 judge」。
  - 不能证明：任务来自公开仓库，训练数据污染无法排除；单次成功率也不代表在你私有代码库上的表现。执行成本高，不适合做每次提交的门禁。
  - `SWE-bench/SWE-bench` · 版本 v4.1.0 · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
