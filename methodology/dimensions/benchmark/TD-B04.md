## TD-B04

### 固定模型只改协议，分数照样会动——这件事必须先量出来

在比较两个模型之前，你需要知道一件事：你的评测框架本身有多敏感。如果只改一个超时设置分数就动了 5 个点，那么模型之间 3 个点的差距没有意义。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 同时改动多个协议变量 | 同时改 2 个变量时，归因所需实验从 1 次增加到至少 3 次；不做单变量实验就无法归因 | 分数变了，归给了其中一个变量，实际来自另一个 |
| 未量化 harness 敏感性就做模型比较 | 若协议变量的影响可达 5pt 而模型差距只有 3pt，则模型比较的结论完全被噪声淹没 | 宣布 A 模型优于 B，实际是 A 的提示模板更适配这个 harness |
| 超时与重试设置未记录 | 超时从 30s 改到 60s 可以让长任务的完成率显著变化，而这个参数常常不在报告里 | 两次评测结果不一致，排查了 2 天才发现是超时配置不同 |

> 本页的方法是一次只改一个协议变量，做配对比较，输出一张敏感性表——它决定了你的评测能分辨多小的差异。

### Harness 敏感性相关的四个词

「换了 Harness 分数就变」不是玄学，它有四个具体的变化来源。

| 术语 | 一句话解释 |
| --- | --- |
| 协议变量 | Prompt 模板、示例数量、输出格式要求等影响提问方式的设定 |
| 执行变量 | 工具集合、超时、重试次数、上下文上限等影响执行的设定 |
| 敏感性 | 固定模型与数据后，单独改一个变量导致的分数变化幅度 |
| 混杂 | 两个及以上变量同时变化，导致结果无法归因 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[EleutherAI/lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness#readme)*

### 先量出协议敏感度，再谈模型差异

固定模型、只改评测协议，分数也会变。变多少是一个可以测出来的数字，而这个数字决定了你的评测有没有分辨力：如果换个 prompt 模板分数就动 5 个点，那么两个模型 3 个点的差距毫无意义。

所以正确的顺序是先做敏感性分析：固定模型，逐个扰动 prompt 模板、few-shot 数量与顺序、解码参数、答案抽取规则，记录每一项造成的分数波动范围。这个范围就是你这套评测的噪声底线。

只有当模型间差异显著大于噪声底线时，「A 比 B 强」才成立。跳过这一步的对比，本质上是在报告噪声，而且报告得非常自信——因为数字本身看起来很精确。

混杂是另一个陷阱：同时升级了模型和 harness 版本，再把差异全部归给模型。控制变量在这里不是学术要求，而是结论能不能用的前提；harness 升级后必须重建基线，不能与旧分数直接连成曲线。

*依据：[EleutherAI/lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness#readme) · [open-compass/opencompass](https://opencompass.readthedocs.io/) · [stanford-crfm/helm](https://crfm.stanford.edu/helm/)*

### 五个扰动变量怎么测、往哪个方向偏

每一行都是一次「固定模型、只改这一项」的实验。做完这五行，你才知道自己的评测能分辨多大的差异。

第三列写的是实测中的典型方向，不是保证；你自己的任务上方向可能不同，这正是必须自己测的原因。

| 扰动变量 | 怎么测敏感度 | 典型方向 | 控制手段 |
| --- | --- | --- | --- |
| prompt 模板 | 固定模型，换三份语义等价的模板 | 措辞变化即可改变名次，且不同模型受影响程度不同 | 模板随配置一起版本化 |
| few-shot 数量与顺序 | 0 / 1 / 5-shot，并打乱示例顺序 | 数量与顺序都影响，且关系非单调 | 显式声明并固定 |
| 解码参数 | temperature / top_p 网格 | 采样越随机方差越大，均值也可能移动 | 评测一律固定，不用生产默认值 |
| 答案抽取规则 | 严格匹配 vs 宽松抽取对照 | 宽松抽取系统性抬分，且抬幅因模型而异 | 抽取规则纳入 scorer 版本管理 |
| harness 版本 | 同配置跨版本重跑 | 版本升级会改变默认行为 | 升级时重建基线，不与旧分数直接比 |

> 五行的波动范围合起来就是噪声底线。模型差异小于这条线时，正确结论是「分辨不出」，不是「差不多」。

*依据：[EleutherAI/lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness#readme) · [open-compass/opencompass](https://opencompass.readthedocs.io/) · [stanford-crfm/helm](https://crfm.stanford.edu/helm/) · [UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/)*

### 这张图的 7 个节点，本页各交付什么

这张图左侧两个节点被显式标记为 Locked：数据与模型必须固定，否则改协议的效果无法分离。这是整个实验设计的前提。

最右侧的「有限归因」是诚实性节点：单变量实验能告诉你哪个变量有影响，不能告诉你为什么——后者需要额外的机制研究。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| Locked Dataset | 固定数据集版本，实验期间禁止任何更新 | 数据集锁定声明 |
| Locked Model | 固定模型版本与温度，排除模型侧变化 | 模型锁定声明 |
| Protocol Variant A/B | 一次只改一个协议变量，构造 A/B 两侧 | 协议变体定义 |
| Harness/Tools | 记录执行框架与可用工具，两侧保持一致 | harness 配置快照 |
| Raw Runs | 两侧原始运行结果落盘，供配对分析 | 原始运行记录 |
| Paired Comparison | 做配对比较而非独立比较，提高对小差异的分辨力 | 配对比较结果 |
| 有限归因 | 写明本实验能归因到什么、不能归因到什么 | 归因边界声明 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 六个变量各自的典型敏感度方向

做敏感性分析的目的不是求精确数值，而是知道哪些变量必须在报告里写明。

右列是方向而不是幅度——幅度必须你自己测，因为它取决于任务与模型。

| 变量 | 改动方式 | 分数通常怎么动 |
| --- | --- | --- |
| Prompt 模板 | 换措辞或结构 | 方向不定，幅度常被低估 |
| 示例数量 | 增加 few-shot | 通常上升，且掩盖零样本能力 |
| 输出格式约束 | 要求严格 JSON | 可能下降，因格式失败被算作错误 |
| 工具集合 | 增减可用工具 | 上升，但可比性丧失 |
| 超时 | 放宽 | 上升，长任务受益最大 |
| 重试 | 允许多次 | 显著上升，且与 Pass@k 口径重叠 |

> 六个变量里有五个的变化方向是「放宽即上升」——这正是跨报告比较时最容易被利用的地方。

*依据：[open-compass/opencompass](https://opencompass.readthedocs.io/)*

### 这一页的验收口径：敏感性即分辨力下限

B04-2 输出的敏感性幅度有一个直接用途：它是你的评测框架的分辨力下限。小于这个幅度的模型差异，你的评测测不出来。

配对比较（B04-3）比独立比较更敏感，因为它消除了题目难度带来的方差——同样的样本量下能分辨更小的差异。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| B04-1 | 单变量纪律 | 一次实验中变动的协议变量数 = 1；多于 1 个时结论不可归因 | 每次实验 |
| B04-2 | 评测框架的分辨力下限 | 单个协议变量引起的分数波动 ≤ 2pt；超出 2pt 时，小于该波动幅度的模型差异一律判为「未测出差异」 | 每季度 1 次 |
| B04-3 | 配对分析 | 使用配对比较而非独立样本比较的比例 = 100% | 每次实验 |
| B04-4 | 配置记录 | 超时、重试、few-shot 数量等协议参数的记录缺失率 = 0 | 每次评测 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在做消融、实际得不出结论的实验

这两种实验设计都很常见，也都会产出一张对比表。

问题在于变量控制，不在执行。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 同时优化 Prompt 和工具集合，分数提升 9 个点 | 两项都是合理优化，结果也确实变好 | 无法归因也无法回滚。下次其中一项失效时，你不知道该退回哪一步。一次只改一个变量 |
| 每个变量只跑一次对比，节省算力 | 变量控制正确，成本也可控 | 单次结果落在噪声范围内时，差异可能完全是随机的。每个变量至少重复到能区分噪声为止 |

> 敏感性分析的成本主要来自重复运行；省掉重复的消融实验通常得不出可用结论。

### 复现不了别人的分数时按什么顺序查

复现失败九成来自协议与执行变量，而不是模型本身。按下表逐项对齐。

对齐过程本身就是一次敏感性分析——你会知道哪个变量最影响你的任务。

| 先对齐什么 | 常见差异 | 处理 |
| --- | --- | --- |
| Prompt 模板 | 措辞与结构不同 | 逐字对齐，包括空行与顺序 |
| 示例数量 | 零样本 vs few-shot | 统一后重跑 |
| 工具集合 | 对方多给了检索工具 | 列出工具清单逐项对齐 |
| 超时与重试 | 对方更宽松 | 统一为同一预算 |
| 模型版本 | 别名指向已变 | 改用固定版本号 |

> 最后一行最隐蔽：同一个模型别名在两个时间点可能指向不同版本。

### 对一个变量做一次单变量敏感性测量：约 60 分钟

挑你最怀疑的那个变量。固定其余全部，只改它，重复到能区分噪声。

1. 固定模型版本、数据集版本、Scorer 与聚合方式，并记录它们的取值。
2. 选一个变量（建议从超时或重试开始，它们通常影响最大）。
3. 在两个取值下各跑足够次数，直到两组结果的区间不再重叠或明确重叠。
4. 记录分数差与区间；区间重叠时结论是「无显著差异」，不是「略有提升」。
5. 把结论写成一句带条件的话：在该数据集与该模型下，该变量从 X 改到 Y，分数变化落在某区间内。

**期望结果**：你会得到一个带区间的敏感度结论，以及一个判断：这个变量是否必须写进今后的每一份报告。

> ⚠ 不要在敏感性实验中途更换模型版本。别名漂移会让整轮实验的归因失效。

### 这一页的出口判据

这一页的门禁产出的不是通过或失败，而是一个数字：你的评测能分辨多小的差异。这个数字应当写进每一份后续的模型比较报告。

第三段要接受的是归因的有限性：知道某个变量有影响，不等于知道为什么，后者往往需要额外投入。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 单次实验变动协议变量数 > 1 时阻断，结论不可归因<br>协议参数记录缺失率 > 0 时阻断，实验不可复现 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 配对比较给出差值的 95% CI，区间跨 0 即判定为未测出影响<br>配对样本 < 50 条时敏感性结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 评测分辨力下限带来的比较局限，由测试负责人签字接受并写入后续报告<br>选定的协议配置（而非其他可能配置）的理由，由评测 owner 署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[EleutherAI/lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness#readme)*

### 带走一份必须公开的变量清单

清单的作用是：今后你们发布的每一个分数，都必须附上这些变量的取值。

清单不需要长。通常三到五个变量就能解释绝大部分跨报告差异。

- 一次只改一个变量，重复到能区分噪声
- 区间重叠时结论是无显著差异
- 把高敏感变量列入报告必填项

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Inspect：任务 / solver / scorer 分层的模型评测框架](https://inspect.aisi.org.uk/)** — 评测框架
  - 能证明：评测可以拆成三个独立可替换的部件：dataset 定义问什么、solver 定义怎么问、scorer 定义怎么判。三者分离之后，换模型不用改判据，改判据不用改数据集——这是把一次性评测脚本变成可回归资产的结构条件。
  - 不能证明：框架不提供判据。scorer 写得对不对、数据集有没有覆盖你的风险切片，框架一概不管，全绿只说明流程跑通了。
  - `UKGovernmentBEIS/inspect_ai` · 版本 release/2025-11-28 · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[lm-evaluation-harness：公开基准的标准执行器](https://github.com/EleutherAI/lm-evaluation-harness#readme)** — benchmark 执行器
  - 能证明：同一个 benchmark 在不同 harness 下会得到不同分数：prompt 模板、few-shot 数量、答案抽取规则、归一化方式都会改变结果。它的存在本身就是「分数必须连同执行配置一起报」这条纪律的证据。
  - 不能证明：它保证的是执行可复现，不保证任务本身衡量了你关心的能力，也不检测数据污染。
  - `EleutherAI/lm-evaluation-harness` · 版本 v0.4.12（2026-05-11） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[HELM：多场景、多指标的整体性评测](https://crfm.stanford.edu/helm/)** — 评测方法学
  - 能证明：单一准确率无法描述模型能力。HELM 的做法是把场景（scenario）与指标（metric）做成正交的两维，同一个场景同时报准确率、校准度、鲁棒性、公平性、效率——「模型 A 比 B 好」这句话必须指明在哪个场景的哪个指标上。
  - 不能证明：覆盖的是公开场景，不覆盖你的业务分布。榜单名次不能迁移到企业任务上。
  - `stanford-crfm/helm` · 版本 v0.5.16（2026-04-30） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[OpenCompass：面向中文与多语言的评测体系](https://opencompass.readthedocs.io/)** — 评测执行器
  - 能证明：评测配置（数据集、模型、推理参数、后处理）可以完全声明式表达并版本化，使跨模型、跨版本的对照在配置层面就可审计，而不是靠人记得当时怎么跑的。
  - 不能证明：中文基准同样存在污染与分布偏移问题；配置可复现不等于结论可迁移。
  - `open-compass/opencompass` · 版本 0.5.3（2026-06-29） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
