## TD-B01

### 一个 Benchmark 分数背后有七个可变组件，报告里通常只写了一个

「模型 A 在 X 上得了 72 分」这句话省略了七件事：任务怎么定义、数据怎么切、提示怎么写、跑在什么 harness 上、谁打的分、怎么聚合、报了什么限制。换掉其中任何一个，72 都会变。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 用不同 harness 的分数横向比较 | 同一模型同一数据集在不同 harness 下的分差可达 10pt 以上，超过多数模型之间的真实差距 | 根据两份来源不同的榜单排名做选型，排的是 harness 不是模型 |
| 报告不写 Limitations | 缺少限制声明的分数无法判断适用边界；把它外推到自己场景的失败率无法估计 | 「这个模型在代码任务上 72 分」被读成「它能胜任我们的代码任务」 |
| 聚合方式未声明 | 按题平均与按类别加权平均可以产生数个百分点的差异，且方向不固定 | 两份都对的报告给出不同结论，团队争论了 3 天而争的是聚合方式 |

> 本页的产物是一张七组件拆解表：拿到任何一个分数，先把这七格填满，再判断它能说明什么。

### 读懂一个 Benchmark 分数需要的四个词

看到「模型 A 在某榜单得 78 分」时，这四个词决定你能不能判断这个数字对你有没有意义。

| 术语 | 一句话解释 |
| --- | --- |
| Harness | 跑 Benchmark 的那套执行代码：Prompt 模板、工具、超时、重试；同一模型换 Harness 分数会变 |
| Scorer | 把模型输出判定为对错的程序或模型；它本身也可能有偏差，且很少被单独评估 |
| 聚合 | 把逐题结果合成一个总分的方式；平均、加权还是按子集，决定了哪类失败会被稀释 |
| 可比性 | 两个分数能不能放在一起比较；数据、协议、Harness、Scorer 任一不同，比较就不成立 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[EleutherAI/lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness#readme)*

### 一个分数是七个组件的函数，报告里通常只写了一个

一个 benchmark 分数至少由七个可变组件共同决定：模型与权重版本、解码参数、prompt 模板、few-shot 的数量与示例、答案抽取规则、scorer 实现、聚合方式。改动其中任何一个都会让分数变化，而报告里通常只写了第一个。

这不是学术洁癖，它有直接的工程后果：两份来自不同来源、都声称测了同一个 benchmark 的分数，往往根本不可比较。基于它们做选型决策，等于在比较两个不同的实验然后宣布其中一个赢了。

所以「可比性」是一个需要被主动构造的性质，不是默认存在的。构造方法只有一条：把七个组件全部固定并记录，需要变更时逐个变更并重测。harness 的存在本身就是这条纪律的产物——它把这七项从口头约定变成了配置文件。

报分数的最低要求是：模型版本 + harness 版本 + 配置文件哈希 + n + 置信区间。缺任何一项，这个分数只能用来和自己比，不能用于跨来源比较，更不能进选型报告。

*依据：[EleutherAI/lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness#readme) · [stanford-crfm/helm](https://crfm.stanford.edu/helm/) · [UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/)*

### 七个可变组件分别由谁固定、记在哪

这张表把「分数怎么来的」拆成责任分配。每一行缺失记录，都会让分数在某个方向上无声地漂移。

最后一列写的是不记录的具体后果，而不是笼统的「不可比」——这些是实际发生过的失真形态。

| 可变组件 | 谁固定它 | 记录在哪 | 不记录的后果 |
| --- | --- | --- | --- |
| 模型与权重版本 | 部署方 | 版本 Manifest | 托管 API 的别名可能指向不同权重，分数无声变化且无人知晓 |
| 解码参数 | 评测配置 | harness 配置文件 | temperature 差 0.2 就可能改变名次 |
| prompt 模板与 few-shot | harness | harness 版本 + 配置哈希 | 同一 benchmark 在不同 harness 下分数不可比 |
| 答案抽取与 scorer | harness | 配置 + scorer 实现版本 | 抽取规则宽松会系统性抬高分数，且抬高幅度因模型而异 |
| 聚合方式 | 报告方 | 报告口径说明 | 宏平均与微平均可以给出方向相反的结论 |

> 五行都记全，一个分数才是可引用的事实；只记第一行，它就只是一个数字。

*依据：[EleutherAI/lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness#readme) · [stanford-crfm/helm](https://crfm.stanford.edu/helm/) · [open-compass/opencompass](https://opencompass.readthedocs.io/) · [UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/)*

### 这张图的 7 个节点，本页各交付什么

这张图就是那七个可变组件，从左到右是一次 Benchmark 运行的完整链路。本页的方法很简单：把每个节点的取值都记下来，分数才有解释框架。

「Report/Limitations」被画成终点节点而不是附录，是因为一份不写限制的报告，其结论强度无法被读者评估。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 任务定义 | 写清楚这个 Benchmark 测的是什么能力，以及它与你的业务任务的距离 | 任务定义与业务距离说明 |
| Dataset/Split | 记录数据来源、划分方式与版本，判断是否存在污染 | 数据集版本与划分说明 |
| Prompt/Protocol | 记录提示模板、few-shot 数量、是否允许工具等协议变量 | 协议配置快照 |
| Model/Harness | 记录模型版本与执行框架，这是横向比较最大的干扰源 | 模型与 harness 版本 |
| Scorer | 记录判分方式（确定性断言 / Judge / 人工）及其校准状态 | 判分器说明与校准记录 |
| Aggregation/CI | 声明聚合方式并给出置信区间，禁止只报单一数字 | 聚合方式与区间 |
| Report/Limitations | 写明这个分数不适用于哪些场景 | 限制声明 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 一个总分背后的七个可变组件

榜单只给你一个数字，但这个数字是七个组件共同产出的。任何一个变了，分数就变，而榜单通常只告诉你换了模型。

右列写的是这个组件变化时分数会怎么动——理解它，你才能判断一次「提升」到底提升了什么。

| 组件 | 它决定什么 | 它变化时分数怎么动 |
| --- | --- | --- |
| 任务定义 | 考什么能力 | 换任务族分数不可比 |
| 数据集 | 考哪些样本 | 样本难度分布决定绝对值 |
| 协议 | 怎么问、给几次机会 | 允许重试的分数远高于单次 |
| 运行环境 | 工具、超时、上下文 | 超时放宽通常直接抬分 |
| Scorer | 怎么算对 | 严格匹配与语义判定差距极大 |
| 聚合 | 怎么合成总分 | 加权方式决定哪类失败被稀释 |
| 报告 | 展示什么、隐藏什么 | 只报均值会掩盖切片崩塌 |

> 七个组件里只有第一、二项是「题目」，其余五项都是「怎么考」——而分数差异往往主要来自后五项。

*依据：[EleutherAI/lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness#readme)*

### 这一页的验收口径：分数的可解释性

本页的指标不测模型，测报告。一份七组件齐全的报告，即使分数不高也是可用的；一份只有分数的报告，即使分数很高也无法据以决策。

B01-4 是本课程反复出现的一条纪律：任何对外结论都必须带区间。单一数字掩盖了它自己的不确定性。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| B01-1 | 组件记录完整度 | 七个组件的取值记录缺失率 = 0 | 每次评测 |
| B01-2 | harness 可比性 | 横向比较时 harness 版本一致的比例 = 100%；不一致的比较次数 = 0 | 每次比较 |
| B01-3 | 限制声明 | 报告包含 Limitations 章节的比例 = 100%，且至少列出 3 条不适用场景 | 每次报告 |
| B01-4 | 区间报告 | 对外分数附 95% CI 的比例 = 100% | 每次报告 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在公平比较模型、实际在比较 Harness 的做法

这两种做法在技术分享里非常常见，图表也做得很专业。

它们的问题不在结论，在于把「怎么考」的差异算成了「谁更强」。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 用同一个榜单的公开分数横向对比五个模型 | 同一榜单、同一数据集，条件看起来一致 | 各家提交时用的 Harness 不同：Prompt 模板、工具、重试、超时都可能不同。你比的是七个组件的组合，不是模型 |
| 自己跑一遍 Benchmark，用官方脚本保证一致 | 用了官方脚本，确实排除了实现差异 | 官方脚本固定的是协议，固定不了模型版本、上下文长度上限与服务端批处理策略。跨时间的重跑也需要记录这些 |

> 两条的共同要求：报告分数时必须同时报出七个组件的具体取值。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/)*

### 看到一个分数时按什么顺序追问

Benchmark 素养的核心不是记住哪个榜单，而是拿到任何一个分数都能问出下面五个问题。

问不出答案的分数不能进入选型决策——它可能是对的，但你无法确认。

| 要追问什么 | 为什么重要 | 答不上来时的处置 |
| --- | --- | --- |
| 跑了几次，报的是哪个统计量 | 单次结果在非确定性系统上无意义 | 视为未测量 |
| Harness 是哪一版 | 换 Harness 分数就变 | 视为不可比 |
| Scorer 是规则还是模型 | 模型 Scorer 自身有偏差 | 要求给出 Scorer 校准数据 |
| 聚合方式与切片结果 | 均值会掩盖高风险切片崩塌 | 要求分切片报告 |
| 数据有没有污染 | 公开集可能已进训练 | 视为上界而非估计 |

> 五个问题都答上来的分数很少见；这本身就是有用的信息。

### 拆解一个你正在参考的榜单分数：约 30 分钟

挑一个你的团队最近引用过的 Benchmark 分数，按七个组件逐项去找它的取值。

1. 写下这个分数与它声称的结论（例如「模型 A 比 B 强 6 个点」）。
2. 逐一查找七个组件的取值：任务定义、数据集版本、协议、运行环境、Scorer、聚合方式、报告口径。
3. 把找不到的组件标为 UNKNOWN——通常你会发现有三到四个查不到。
4. 根据 UNKNOWN 的数量重新表述这个结论：能确定的部分与不能确定的部分分开写。
5. 最后回答一个问题：这 6 个点的差距，是否足以支撑你的选型决定？

**期望结果**：多数情况下你会得到一个更弱但更诚实的结论，例如「在该数据集、该 Harness、该 Scorer 下，模型 A 高 6 个点，未验证是否可迁移到我们的任务分布」。

> ⚠ 不要因为查不全就丢弃这个分数。榜单分数是有用的先验，只是它不能单独支撑决定。

### 这一页的出口判据

这一页的门禁作用在报告发布之前，拦的是「不可解释的分数」。分数本身高低不在这道门禁的判断范围内。

第三段要接受的是外推风险：公共 Benchmark 与你的业务任务之间总有距离，这个距离必须被估计并被接受，而不是被忽略。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 七组件记录缺失率 > 0 时阻断报告发布<br>harness 版本不一致的横向比较次数 > 0 时阻断，结论作废 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 分数以 95% CI 报告，版本或模型间比较以区间重叠判定<br>单任务类别样本 < 30 条时该类别结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 公共 Benchmark 与业务任务之间的距离，由测试负责人估计并签字接受<br>选用某一 harness 而非另一种的理由，由评测 owner 写明并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一张七组件核对表

核对表的用途不是评判榜单，而是让你的团队在引用任何分数时都先填一遍。

填不满的行就是这次引用的不确定性来源——把它写进决策记录，比假装确定要安全得多。

- 引用任何分数时同时给出七个组件的取值
- 查不到的组件标 UNKNOWN，不要默认
- 把结论限定在已知条件内再使用

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Inspect：任务 / solver / scorer 分层的模型评测框架](https://inspect.aisi.org.uk/)** — 评测框架
  - 能证明：评测可以拆成三个独立可替换的部件：dataset 定义问什么、solver 定义怎么问、scorer 定义怎么判。三者分离之后，换模型不用改判据，改判据不用改数据集——这是把一次性评测脚本变成可回归资产的结构条件。
  - 不能证明：框架不提供判据。scorer 写得对不对、数据集有没有覆盖你的风险切片，框架一概不管，全绿只说明流程跑通了。
  - `UKGovernmentBEIS/inspect_ai` · 版本 release/2025-11-28 · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[lm-evaluation-harness：公开基准的标准执行器](https://github.com/EleutherAI/lm-evaluation-harness#readme)** — benchmark 执行器
  - 能证明：同一个 benchmark 在不同 harness 下会得到不同分数：prompt 模板、few-shot 数量、答案抽取规则、归一化方式都会改变结果。它的存在本身就是「分数必须连同执行配置一起报」这条纪律的证据。
  - 不能证明：它保证的是执行可复现，不保证任务本身衡量了你关心的能力，也不检测数据污染。
  - `EleutherAI/lm-evaluation-harness` · 版本 v0.4.12（2026-05-11） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[HELM：多场景、多指标的整体性评测](https://crfm.stanford.edu/helm/)** — 评测方法学
  - 能证明：单一准确率无法描述模型能力。HELM 的做法是把场景（scenario）与指标（metric）做成正交的两维，同一个场景同时报准确率、校准度、鲁棒性、公平性、效率——「模型 A 比 B 好」这句话必须指明在哪个场景的哪个指标上。
  - 不能证明：覆盖的是公开场景，不覆盖你的业务分布。榜单名次不能迁移到企业任务上。
  - `stanford-crfm/helm` · 版本 v0.5.16（2026-04-30） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[OpenCompass：面向中文与多语言的评测体系](https://opencompass.readthedocs.io/)** — 评测执行器
  - 能证明：评测配置（数据集、模型、推理参数、后处理）可以完全声明式表达并版本化，使跨模型、跨版本的对照在配置层面就可审计，而不是靠人记得当时怎么跑的。
  - 不能证明：中文基准同样存在污染与分布偏移问题；配置可复现不等于结论可迁移。
  - `open-compass/opencompass` · 版本 0.5.3（2026-06-29） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
