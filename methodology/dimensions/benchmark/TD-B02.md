## TD-B02

### 数据集只有一类角色时，你无法同时回答「够不够好」和「有没有变差」

多数团队只维护一份评测集，并用它同时做能力评估、难例攻坚和回归防护。这三件事对数据的要求互相冲突，一份数据满足不了。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 用同一份数据反复调优 | 反复调优的数据集会逐步失去区分度；通行纪律是 sealed holdout 每个版本至多开封 1 次 | 分数持续上涨被读成能力提升，实际是对这批题的过拟合 |
| 只有难例没有代表性样本 | 全部由难例组成的数据集，其分数与真实用户体验的相关性会显著低于 0.6 的可用门槛 | 模型在难例上进步很大，用户感知不到任何变化 |
| 回归集与评估集混用 | 回归集要求 0 修改、只增不删，评估集要求随业务分布持续更新；混用时这 2 个目标每次都有 1 个被牺牲 | 要么回归失效，要么评估集永远测不到新问题 |

> 解法是把数据集拆成四类角色：representative、challenge、regression、sealed holdout，各有各的更新纪律。

### 数据集的四种角色

同一批样本用在不同角色上，结论完全不同。混用是「越调越假」的直接原因。

| 术语 | 一句话解释 |
| --- | --- |
| representative | 按真实分布抽样，回答「典型情况下表现如何」 |
| challenge | 刻意收集的难例，回答「边界在哪里」；它的绝对分数没有意义 |
| regression | 已修复缺陷转化的固定集合，回答「有没有退回去」 |
| sealed holdout | 只在发布判断时开封一次；反复开封的集合不再是 holdout |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[SWE-bench/SWE-bench](https://www.swebench.com/)*

### 一份数据集回答不了两个方向相反的问题

「够不够好」要求样本分布贴近真实流量，否则结论无法外推；「有没有变差」要求样本固定不变，否则两次结果不可比。同一份数据集不可能同时满足这两条——前者要求随流量更新，后者要求冻结。

因此至少需要四种角色：representative 贴流量、回答够不够好；challenge 贴风险、回答最坏情况能不能接受；regression 贴历史事故、回答有没有退化；sealed holdout 从不用于调优、回答有没有过拟合到评测集本身。

四者的使用纪律不同，混用会静默失效。最常见的错误是把 regression 集拿来调优——调完之后它不再能检出退化，因为系统已经针对它优化过了。这个失效没有任何报错，集合还在，用例还是绿的，只是它已经不再回答原来那个问题。

sealed holdout 的价值完全来自「从不使用」。开封一次就失效一次，因此它必须**可重建**：同样的构造规则、不同的样本。不可重建的 holdout 用完就没了，而团队通常在用完之后才想起这一点。

*依据：[SWE-bench/SWE-bench](https://www.swebench.com/) · [iterative/dvc](https://dvc.org/doc)*

### 四种角色的更新纪律与失效方式

这张表的关键列是「更新纪律」：四种角色的纪律互相冲突，这正是它们必须分开的原因。

最后一列全部是无声失效。数据集治理与代码治理最大的差别就在这里——代码坏了会报错，数据集坏了只会继续输出好看的数字。

| 数据集角色 | 回答什么 | 更新纪律 | 失效方式 |
| --- | --- | --- | --- |
| representative | 整体够不够好 | 随流量分布定期重采 | 分布漂移后结论不再外推，而漂移本身无声 |
| challenge | 最坏情况能不能接受 | 按新增风险追加，不删旧的 | 只覆盖想到的风险，没想到的那类永远没有样本 |
| regression | 有没有比上一版差 | 只增不改，绝不用于调优 | 一旦用于调优，检出退化的能力静默消失 |
| sealed holdout | 有没有过拟合到评测集本身 | 发布前开封一次，用后按同规则重建 | 开封即失效；不可重建则永久失去这条防线 |

> 四行的纪律互相冲突，因此它们必须是四份数据而不是一份数据的四个标签。

*依据：[SWE-bench/SWE-bench](https://www.swebench.com/) · [iterative/dvc](https://dvc.org/doc) · [stanford-crfm/helm](https://crfm.stanford.edu/helm/)*

### 这张图的 7 个节点，本页各交付什么

这张图的中段是四类数据角色的并列。它们的更新频率完全不同：representative 随业务分布更新，challenge 随新发现的难例增长，regression 只增不改，sealed holdout 基本不动。

「访问审计/版本」是保证 sealed holdout 有效性的唯一手段：没有访问记录，你无法知道它被看过几次。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 任务与失败池 | 从真实任务与线上失败出发建池，而不是凭想象构造 | 任务与失败池 |
| 采样/去重 | 按业务分布采样并做跨集合去重，输出污染检查结论 | 采样方案与污染报告 |
| Representative | 维护反映真实分布的代表性集合，用于回答「够不够好」 | 代表性数据集 |
| Challenge | 维护难例集合，用于回答「边界在哪」 | 难例数据集 |
| Regression | 维护只增不改的回归集，用于回答「有没有变差」 | 回归数据集 |
| Sealed Holdout | 封存集合，严格限制开封次数，用于最终验收 | 封存集与开封记录 |
| 访问审计/版本 | 记录每次访问与版本变更，保证封存有效 | 访问审计日志 |

### 四种角色的构建方式与使用纪律

把一批样本随机切三份不叫数据集设计。四种角色的抽样方式、更新频率与使用场合都不同。

右列的使用纪律是最容易被违反的部分——尤其是 holdout 的开封次数。

| 角色 | 怎么构建 | 使用纪律 |
| --- | --- | --- |
| representative | 按生产分布分层抽样 | 分布漂移时重建，不做增量补丁 |
| challenge | 从事故、投诉、红队收集 | 不与 representative 混算总分 |
| regression | 每个逃逸缺陷转一条 | 只增不减，删除需 owner 批准 |
| sealed holdout | 从 representative 独立抽取并封存 | 开封次数计数，超约定即作废重建 |

> 四类的样本可以来自同一来源，但一旦分配角色就不能互换——互换等于用考过的题重新考一次。

*依据：[iterative/dvc](https://dvc.org/doc)*

### 这一页的验收口径：四类角色各自的纪律

B02-2 的 sealed holdout 开封纪律是本页最重要的一条。它保护的不是数据，是你对自己系统能力的判断——holdout 一旦被反复使用，你就失去了唯一的无偏估计。

B02-4 的分布距离用 KL 散度监控，目的是及时发现代表性集合与线上分布脱节。脱节的代表性集合会给出乐观且无法察觉的偏差。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| B02-1 | 跨集合污染 | 四类数据集之间的重合与近重复的污染率 = 0 | 每次数据集变更 |
| B02-2 | 封存纪律 | sealed holdout 每版本开封次数 ≤ 1；累计开封 ≥ 3 次即整体重建 | 每次发布 |
| B02-3 | 回归集单调性 | 回归集条目被修改或删除的次数 = 0（只增不改） | 每次变更 |
| B02-4 | 代表性维持 | representative 集与线上分布的 KL 散度环比变动 > 20% 时触发重采样 | 每季度 1 次 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来数据很规范、实际会越调越假的做法

这两种做法都写在很多团队的评测规范里，也都通过过评审。

它们的共同结果是：分数持续上升，真实能力没有变化。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 每次迭代都在同一评测集上验证改进，趋势清晰 | 固定评测集保证了可比性，趋势也确实在涨 | 反复在同一集合上调优，模型或 Prompt 会拟合这个集合。涨的是这个集合上的分数，不是能力。必须有一个从未参与调优的封存集 |
| 把难例加进评测集提高区分度，分数下降说明更严格 | 难例确实提高了区分度，也更贴近真实痛点 | 把 challenge 混进 representative 之后，总分不再代表典型情况，也不再能跨版本比较。两类必须分开算、分开报 |

> 两条都指向同一条纪律：角色一旦分配就不能混算。

### 分数在涨但用户没感觉时按什么顺序查

「指标涨、体验不变」是评测体系最典型的失效信号。先查数据集，再查指标。

四行里前两行占了绝大多数情况。

| 症状 | 先怀疑 | 下一步检查 |
| --- | --- | --- |
| 同一集合上分数持续上升 | 过拟合评测集 | 用从未开封的 holdout 重测一次 |
| 评测分高但投诉不变 | representative 分布过时 | 用近期生产采样重建分布 |
| 难例分数很难看 | challenge 被算进总分 | 把两类分开报告 |
| 修过的缺陷又出现 | regression 集合被删过 | 检查删除记录与 owner 批准 |

> 第一行的验证成本很低——开封一次 holdout 就能知道，但很多团队从未准备过这个集合。

### 给现有评测集分配角色并封存一份 holdout：约 60 分钟

不需要新增标注。多数团队已有的评测集里，其实混着四种角色的样本。

1. 把现有评测集逐条标注来源：是按分布抽的、是从事故来的、还是修缺陷时补的。
2. 按来源分配角色：分布抽样归 representative，事故与红队归 challenge，缺陷转化归 regression。
3. 从 representative 中独立抽取一部分作为 sealed holdout，写入封存记录并指定开封审批人。
4. 分别计算四类的规模与分布，检查 representative 是否还能代表当前生产分布。
5. 建立开封台账：每次开封记录时间、目的、批准人与开封后的处置。

**期望结果**：产出是四类角色的样本清单加一份封存记录。多数团队会在这一步发现 representative 的分布已经落后于生产好几个月。

> ⚠ holdout 抽取必须在任何调优之前完成。从已经用过的集合里事后划出一部分，它不是 holdout。

### 这一页的出口判据

数据集的门禁必须在评测前执行。评测跑完再发现污染，此前所有分数都要作废重跑，成本高一个量级。

第三段要接受的是覆盖缺口：四类数据集加起来仍然覆盖不了全部真实场景，这个缺口要被写下来。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 跨集合污染率 > 0 时阻断评测启动<br>sealed holdout 同版本开封次数 ≥ 2 时阻断，该轮验收结论作废 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 各数据集上的分数分别给出 95% CI，禁止跨角色合并计算<br>单类别样本 < 30 条时该类别结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 四类数据集未覆盖的场景范围，由数据 owner 列出并签字接受<br>sealed holdout 重建带来的历史不可比，由评测 owner 明示接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[SWE-bench/SWE-bench](https://www.swebench.com/)*

### 带走一份带角色与封存记录的数据集清单

清单的关键不是样本数量，而是每个样本属于哪个角色、以及 holdout 被开封过几次。

开封次数是评测可信度的直接指标——它超过约定时，所有基于 holdout 的结论都要重新审视。

- 四种角色分开构建、分开计算、分开报告
- holdout 在调优之前抽取并封存
- 开封台账记录时间、目的与批准人

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[HELM：多场景、多指标的整体性评测](https://crfm.stanford.edu/helm/)** — 评测方法学
  - 能证明：单一准确率无法描述模型能力。HELM 的做法是把场景（scenario）与指标（metric）做成正交的两维，同一个场景同时报准确率、校准度、鲁棒性、公平性、效率——「模型 A 比 B 好」这句话必须指明在哪个场景的哪个指标上。
  - 不能证明：覆盖的是公开场景，不覆盖你的业务分布。榜单名次不能迁移到企业任务上。
  - `stanford-crfm/helm` · 版本 v0.5.16（2026-04-30） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[SWE-bench：以真实仓库 issue 为任务的 Agent 基准](https://www.swebench.com/)** — 任务级基准
  - 能证明：任务级评测的判据可以完全确定：补丁应用后跑原仓库的测试，通过即算解决。这比模型评判可靠得多，也说明「只要任务本身自带 oracle，评测就不需要 judge」。
  - 不能证明：任务来自公开仓库，训练数据污染无法排除；单次成功率也不代表在你私有代码库上的表现。执行成本高，不适合做每次提交的门禁。
  - `SWE-bench/SWE-bench` · 版本 v4.1.0 · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[DVC：数据与流水线的版本控制](https://dvc.org/doc)** — 数据版本
  - 能证明：评测集必须与代码一样可版本化：同一个 commit 能取回当时用的那份数据。缺了这一条，历史评测分数之间不可比，回归判断也就不成立。
  - 不能证明：版本可追不代表数据集设计合理；污染与分布偏移不会因为版本化而消失。
  - `iterative/dvc` · 版本 3.67.1（2026-03-31） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
