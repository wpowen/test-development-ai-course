## TD-PS05

### 像素级视觉回归遇到生成内容会 100% 失败，但放弃视觉回归又会让布局问题全部漏过

视觉回归的价值在于它能发现所有人都没想到要断言的东西。它的代价是对变化极度敏感——而 AI 生成的内容每次都在变。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 对含生成内容的区域做像素快照 | 生成文本长度每次不同会导致整块区域重排，像素比对的误报率接近 100%，团队随后会关掉这项检查 | 从「视觉回归太吵」直接走到「不做视觉回归」，布局问题从此无人发现 |
| 无障碍只检查对比度 | 对比度是自动化工具最容易查的一项，但键盘不可达与可访问名称错误这两类占实际障碍的大头，且 100% 不体现在对比度上 | 自动化扫描 0 违规，屏幕阅读器用户完全无法完成任务 |
| 国际化只验证文案存在 | 德语等语言的文本长度常比英文长 30% 以上，容器溢出与截断在纯字符串检查中 100% 漏过 | 翻译全部就位，界面在部分语言下按钮文字被切掉一半 |

> 解法是把视觉回归的范围从「整页像素」缩小到「布局骨架」，把无障碍判据从对比度扩展到语义与键盘路径。

### 兼容性与无障碍的四个词

这三类问题的共同特征是：功能测试全过，但部分用户完全无法使用。

| 术语 | 一句话解释 |
| --- | --- |
| 键盘可达 | 不用鼠标能否完成全部关键操作 |
| 响应式 | 不同屏幕尺寸下布局是否可用，而不只是不错位 |
| 国际化文本 | 不同语言下文本长度变化导致的布局问题 |
| 视觉回归 | 界面变化的自动比对；它需要区分有意变更与意外变更 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[Web Content Accessibility Guidelines (WCAG) 2.2](https://www.w3.org/TR/WCAG22/)*

### 无障碍能自动化到哪一步，剩下的为什么必须人来

无障碍规则可以分成两类。一类的判据完全落在 DOM 与计算样式上：对比度比值、是否有可访问名、ARIA 角色与属性的组合是否合法、标题层级有没有跳级。这一类能被规则引擎精确判定，不需要理解页面在讲什么，因此自动化收益极高。

另一类的判据依赖语义与流程：这张图的替代文本描述得对不对、焦点顺序是否符合阅读顺序、错误提示是否被及时朗读、键盘能不能走完整个流程而不被困住。规则引擎能看到元素存在，看不到它是否讲得通——这不是引擎不够好，是这类判断本身需要理解内容。

好的引擎会把这条界线明说出来：除了 violations 和 passes，还有一类 incomplete——机器判不了、需要人看。把 incomplete 当成「暂时忽略」是这一页最常见的错误，它等于把最需要判断的部分静默丢掉，然后拿一个零 violations 的报告去声称合规。

视觉回归是同一条界线的另一面。它能可靠检出「像素变了」，判断不了「变了是对是错」。因此它的正确位置是变更探测器而不是通过/失败门禁：阈值调高会漏，调低会天天红，两条路最终都会让它被关掉。真正让它可用的前提是先把不稳定源冻住——动画、时间、随机数据、字体渲染，这四项不处理，比对结果没有意义。

### 视觉与无障碍验收在 AI 界面上变成了什么

这一项的变化最直观：被测对象从「固定的界面」变成了「结构固定、内容不定的界面」。方法必须相应地区分这两层。

另一个变化来自无障碍：当界面文字由模型生成时，可访问名称也由模型生成，它第一次成为一个需要评测的模型输出。

| 传统做法 | 在 AI 系统里为什么不够用 | 融合后的新做法 |
| --- | --- | --- |
| 整页像素级快照比对 | 生成内容的长度与换行每次不同，会导致下方元素整体位移，像素比对无法区分「布局坏了」和「文字变长了」 | 视觉回归只锁布局骨架：容器边界、栅格对齐、关键控件位置；生成内容区用占位内容渲染后再比对 |
| 无障碍用扫描工具跑一遍 | 自动化扫描覆盖的是静态属性，而模型生成的可访问名称是运行时产物，扫描工具看到的是模板不是实际输出 | 把可访问名称纳入模型输出的评测项，与视觉标签做一致性断言；键盘可达性按真实任务路径逐条走通 |
| 国际化检查翻译是否齐全 | 文案由模型按语言生成时，问题不再是「有没有翻译」，而是「不同语言的语义是否等价、长度是否会撑破容器」 | 按 locale 建立任务矩阵，分别验证语义等价与布局承受，禁止用英文结果外推 |
| 视觉差异由人工逐张确认 | 生成内容让差异张数大幅上升，人工逐张确认不可持续，最终会退化成全部批准 | 先用骨架比对把差异总量压下来，剩余差异按变更类型分类，只有未分类的才进人工队列 |

> 左列不是要被淘汰的东西，右列也不是新工具清单。真正变化的是中间那一列——被测对象的性质变了，于是同一个目的需要换一种达成方式。

*依据：[dequelabs/axe-core](https://github.com/dequelabs/axe-core/blob/develop/doc/API.md) · [Web Content Accessibility Guidelines (WCAG) 2.2](https://www.w3.org/TR/WCAG22/)*

### 这些地基不变

下面这些不因为被测对象换成 AI 系统而失效。它们是上面那张表里「融合后的新做法」能够成立的前提——地基塌了，新做法只是换了个说法的空话。

- 键盘可达：所有功能必须能只用键盘完成，这一条与内容是否由 AI 生成无关
- 语义结构：正确的标题层级、地标区域与表单标签是屏幕阅读器的唯一依据
- 响应式断点：容器在极端内容长度下不得溢出或截断
- 焦点管理：动态内容出现时焦点去向必须是设计出来的，不能是浏览器默认

### 这三类检查各自拿什么执行

无障碍、视觉回归、跨浏览器差异是三件不同的事，常被合并成一句「兼容性测试」，于是三者的边界也一起模糊掉。

重点看第一行和第三行的边界列：它们分别标出了「机器判不了的部分」和「判得出变化但判不出对错」，这两条限制决定了这一页的门禁怎么写。

| 检查类型 | 工具 | 它负责什么 | 边界 |
| --- | --- | --- | --- |
| 可机器判定的无障碍规则 | axe-core | 对比度、可访问名缺失、ARIA 误用、结构层级，并把结果分成 violations / incomplete / passes 三类而不是简单的通过失败 | 只覆盖 WCAG 中可自动判定的部分；incomplete 必须人工消化，忽略它等于把最需要判断的部分丢掉 |
| 合规判据来源 | WCAG 2.2 | 提供权威条款与 A/AA/AAA 分级，使合规结论可以引条款号，而不是引某个工具的输出 | 标准不指定测试方法。哪些条款能自动化、哪些必须人工，映射要自己做 |
| 视觉回归 | Playwright 截图比对 | 内建截图与差异阈值，与既有用例共用同一套运行、重试与 trace 机制，不需要另建一条流水线 | 只能检出像素变化，判断不了变化是否正确；不先冻住动画与随机数据则结果无意义 |
| 跨浏览器差异 | Playwright | 同一套用例在 Chromium / Firefox / WebKit 三引擎执行，暴露引擎级渲染与行为差异 | 引擎覆盖不等于真机覆盖；移动端 WebView 与实际设备仍需单独验证 |

> 三类检查的自动化上限都低于直觉：前两行受限于可判定性，后两行受限于「变化 ≠ 缺陷」。把它们当成探测器而不是判决器，是这一页最重要的口径。

*依据：[dequelabs/axe-core](https://github.com/dequelabs/axe-core/blob/develop/doc/API.md) · [Web Content Accessibility Guidelines (WCAG) 2.2](https://www.w3.org/TR/WCAG22/) · [microsoft/playwright](https://playwright.dev/docs/intro)*

### 四类检查各自的判据

这四类都不能用功能测试覆盖，需要各自的判据与工具。

右列是可以自动化的部分——其余需要人工。

| 检查 | 判据 | 可自动化部分 |
| --- | --- | --- |
| 键盘可达 | 关键操作全部可用键盘完成 | 焦点顺序与可聚焦性 |
| 无障碍名称 | 辅助技术能读出有意义的名称 | 属性存在性检查 |
| 响应式 | 目标尺寸下无内容截断与重叠 | 布局溢出检测 |
| 国际化 | 最长语言下不破版 | 文本长度模拟 |
| 视觉回归 | 无意外的视觉变化 | 像素或结构比对 |

> 五行里前两行的自动化只能覆盖存在性，「读出来是否有意义」仍然需要人。

### 这一页的验收口径：三类判据各自达标

PS05-2 的键盘可达率必须是 100%，不设容忍区间：存在一个只能用鼠标完成的功能，就意味着一部分用户完全无法使用该功能。

PS05-4 的误报率是视觉回归能否长期存活的关键——误报太多时它一定会被关掉，而被关掉的检查等于不存在。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| PS05-1 | 语义结构 | 标题层级错误、缺失表单标签、可访问名称与视觉标签不一致的数量均 = 0 | 每次 UI 变更 |
| PS05-2 | 键盘可达 | 关键任务的键盘可达率 = 100%；焦点丢失次数 = 0 | 每次 UI 变更 |
| PS05-3 | 布局承受 | 各 locale 在最长文本下容器溢出或截断的数量 = 0 | 每次文案或语言变更 |
| PS05-4 | 视觉回归可用性 | 骨架比对的误报率 ≤ 5%；超出即缩小比对范围而不是关闭检查 | 每周 1 次 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来做了无障碍与兼容、实际没覆盖的做法

这两种做法都有工具支撑，也确实产出了报告。

问题是它们检查的是属性存在，不是实际可用。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 用自动化工具扫描无障碍问题，零告警即合格 | 工具覆盖了大量规则，也确实拦下了明显问题 | 自动化工具只能检查属性存在与否，不能判断名称是否有意义。一个 aria-label 写着「按钮」的控件能通过扫描，但读屏用户完全不知道它是干什么的 |
| 视觉回归全部通过，说明界面没有意外变化 | 像素比对客观、灵敏，也确实拦下了变化 | 高灵敏度会让每次正常改版都产生大量差异，团队最终会批量确认全部差异。要区分有意变更与意外变更，需要按区域设置不同灵敏度 |

> 两条的共同修法：自动化负责筛选，人工负责判断有意义与否。

*依据：[dequelabs/axe-core](https://github.com/dequelabs/axe-core/blob/develop/doc/API.md)*

### 部分用户反馈无法使用时按什么顺序查

这类反馈往往来自少数用户，容易被当成个例。按下表逐项排查。

前两行不需要专门设备，用键盘和浏览器就能查。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 用键盘无法完成操作 | 焦点顺序或可聚焦性 | 用纯键盘走一遍关键旅程 |
| 读屏用户不知道控件作用 | 无障碍名称无意义 | 逐个听一遍关键控件的读出内容 |
| 某语言下按钮文字被截断 | 国际化文本长度 | 用最长语言模拟 |
| 小屏幕下内容重叠 | 响应式断点 | 在目标尺寸下检查溢出 |

> 第二行必须实际听一遍。属性存在性检查通过不代表读出来的内容有意义。

### 用纯键盘和读屏走一遍关键旅程：约 45 分钟

不需要任何专门工具。拔掉鼠标，打开系统自带读屏即可。

1. 选一条关键旅程，全程只用键盘完成，记录卡住的位置。
2. 打开系统读屏，重新走一遍，记录读出内容无意义的控件。
3. 把界面切换到文本最长的目标语言，检查是否有截断或破版。
4. 在最小目标屏幕尺寸下重走一遍，检查内容溢出与重叠。
5. 把四项发现按严重程度排序，最严重的通常是键盘完全无法完成的步骤。

**期望结果**：典型结果是关键旅程中有一到两步无法用键盘完成，且若干控件的读出内容是「按钮」这类无意义文本。

> ⚠ 这个演练要用真实的读屏工具，不能用属性检查代替。两者发现的问题完全不同。

### 这一页的出口判据

这一页的门禁里有两条是合规性质的：键盘可达与可访问名称一致。它们不参与和其他质量目标的权衡。

第三段要接受的是矩阵裁剪：浏览器 × 视口 × locale 的组合数增长很快，全覆盖不现实，测了哪些必须写清楚。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 键盘可达率 < 100% 或可访问名称不一致数量 > 0 时阻断<br>任一 locale 出现容器溢出或文本截断数量 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 视觉回归误报率按周统计给出 95% CI 上界，与 5% 比较用上界<br>单 locale 样本 < 30 条时该 locale 结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 浏览器、视口与 locale 矩阵的裁剪范围，由产品 owner 根据真实用户分布签字确定<br>已知但暂不修复的视觉差异，由设计 owner 逐条批准并留痕 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一份键盘与读屏可用性记录

记录的价值在于它是用户视角的：能不能完成，而不是属性是否存在。

自动化扫描继续跑，但它只负责筛选，不负责判定可用。

- 用纯键盘走关键旅程，记录卡住的位置
- 实际听读屏输出，不只检查属性存在
- 视觉回归按区域设灵敏度，区分有意变更

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Playwright：跨浏览器端到端测试框架](https://playwright.dev/docs/intro)** — Web UI 专项主力工具
  - 能证明：浏览器自动化的三项工程能力：actionability 自动等待取代 sleep、语义 locator 取代 CSS/XPath 坐标、浏览器上下文隔离取代用例间清理。它们共同把 UI 测试的不稳定来源从「时序」降到「业务」。
  - 不能证明：自动等待解决的是元素可交互，不是业务就绪。页面上按钮能点了不代表后台事务已提交；UI 全绿仍需副作用层佐证。
  - `microsoft/playwright` · 版本 v1.62.1（2026-07-30） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[axe-core：无障碍规则引擎](https://github.com/dequelabs/axe-core/blob/develop/doc/API.md)** — 无障碍专项工具
  - 能证明：一组可自动判定的无障碍规则（对比度、名称缺失、ARIA 误用、结构层级），并区分 violations / incomplete / passes 三类结果。incomplete 这一类是它诚实的地方：明确标出机器判不了、需要人工看的项。
  - 不能证明：自动化规则只覆盖 WCAG 中可机器判定的一部分，键盘陷阱、焦点顺序合理性、屏幕阅读器实际朗读效果多数落在自动化之外。零 violations 不等于无障碍合规。

- **[Web Content Accessibility Guidelines (WCAG) 2.2](https://www.w3.org/TR/WCAG22/)** — 无障碍判据来源
  - 能证明：无障碍要求的权威条款与分级（A / AA / AAA），以及每条成功准则的判定方式。合规结论必须引条款号，而不是引工具输出。
  - 不能证明：标准不指定实现与测试方法。哪些条款能自动化、哪些必须人工，需要自己映射。
