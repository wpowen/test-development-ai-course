## TD-PS02

### Schema 通过和语义正确是两件事，生成式接口让这个差距变得致命

结构化输出让人产生一种安全感：字段齐全、类型正确、枚举合法。但这些只证明了形状对，没证明内容对——而模型最擅长的恰恰是产出形状正确的错误内容。

下面三条说明只做 Schema 校验时漏掉了什么。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 把 Schema 校验通过当成结果正确 | Schema 层能拦住的是格式类错误；金额算错、币种搞反、状态取了合法但错误的枚举值，这三类 100% 通过 Schema | 「结构化输出已经保证了可靠性」——这是引入结构化输出后最常见的误判 |
| 只测正例不测坏请求 | 缺反例时接口的错误处理路径覆盖率接近 0，而生产流量里坏请求的占比从来不是 0 | 上线后大量 5xx，且错误信息泄露内部结构 |
| Schema 变更没有破坏性检测 | 移除必填字段、收窄枚举、改类型这 3 类变更会直接打断已有消费方，而 Schema 文件本身不会报错 | 改了一个字段，下游三个服务同时开始报错 |

> 本页的做法是给每个 Schema 配一组业务属性断言，并用 Schema 变异证明这组断言真的有检测力。

### Schema 与属性测试的四个词

格式校验和业务校验是两件事，混在一起会产生大量假覆盖。

| 术语 | 一句话解释 |
| --- | --- |
| Schema 变异 | 故意破坏请求或响应结构，看校验是否生效 |
| 属性 | 对任意合法输入都应成立的性质，如金额守恒 |
| 破坏性变更 | 会让现有消费者失败的接口变化，如删字段、改类型 |
| 假覆盖 | 测试跑了很多但只验证了格式的状态 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[OAI/OpenAPI-Specification](https://spec.openapis.org/oas/latest.html)*

### 属性测试凭什么能发现例子测试发现不了的缺陷

例子测试的检出能力上限，等于作者想得到的输入集合。作者没想到的输入，在测试套件里就不存在——覆盖率再高也不会改变这一点，因为覆盖率统计的是被执行的代码行，不是被考察的输入空间。

属性测试换掉的是这个前提：不枚举输入，而是声明一条对所有合法输入都必须成立的性质，再让引擎去找反例。作者的工作从「想出可能出错的例子」变成「说清什么情况下算对」，后者要难得多，但它的覆盖不依赖想象力。

让这件事真正可用的不是随机采样，而是收缩。随机采样找到的反例通常又长又乱，读不出原因；收缩会自动把反例削减到仍然失败的最小形态，把「某次随机跑挂了」变成「这个最小输入必然挂」。没有收缩的随机测试，调试成本会高到让团队最终把它关掉。

属性从哪里来，才是这项能力真正的门槛。OpenAPI 里已经声明的类型、枚举、边界可以直接变成属性，这是免费的第一层；而真正值钱的属性——往返一致、幂等、守恒、排序稳定——必须由人从业务里提炼。工具不知道你的系统有哪些不变量，写不出属性时，它只是一个更贵的随机测试。

### Schema 与属性测试在生成式接口上变成了什么

属性测试的核心思想——不断言具体值，断言必须恒成立的性质——恰好是应对非确定性输出的最佳工具。这项传统能力在 AI 时代不是被削弱，而是找到了它最合适的场景。

变化在于：Schema 从「接口文档」变成了「模型输出的约束条件」，它同时是测试对象和被测系统的一部分。

| 传统做法 | 在 AI 系统里为什么不够用 | 融合后的新做法 |
| --- | --- | --- |
| Schema 用于校验请求与响应格式 | 在生成式接口里 Schema 同时是给模型的约束（结构化输出的定义），它一改，模型行为也跟着变，测试对象和被测配置耦合在一起 | Schema 版本进入模型版本 manifest；改 Schema 视为一次需要重新评测的变更，而不是文档更新 |
| 断言具体的期望值 | 生成内容不可预测，逐值断言无法编写；但完全不断言又等于放弃校验 | 改断言恒成立的业务属性：金额非负、借贷相等、状态转移合法、引用的 id 必须存在 |
| 用正反例覆盖输入空间 | 模型输入是自然语言，输入空间无法枚举；传统等价类划分在这里失去了边界定义 | 反例改为按失败模型构造：指令冲突、超长上下文、混入指令的数据、空检索结果 |
| Schema 校验通过即放行 | Schema 合法但语义错误的输出无法被格式校验发现，而这正是模型最典型的错误形态 | 引入 PASS_SCHEMA 与 PASS_SEMANTIC 两个独立状态，前者通过不代表后者通过，报告必须分别标注 |

> 左列不是要被淘汰的东西，右列也不是新工具清单。真正变化的是中间那一列——被测对象的性质变了，于是同一个目的需要换一种达成方式。

*依据：[HypothesisWorks/hypothesis](https://hypothesis.readthedocs.io/en/latest/) · [confident-ai/deepeval](https://deepeval.com/docs/getting-started)*

### 这些地基不变

下面这些不因为被测对象换成 AI 系统而失效。它们是上面那张表里「融合后的新做法」能够成立的前提——地基塌了，新做法只是换了个说法的空话。

- 属性优于样例：能写成不变量的就不要写成样例，这条在非确定性系统上收益更大
- 变异证明检测力：一组断言有没有用，只能靠故意破坏被测对象来证明
- 破坏性变更检测：移除必填、收窄枚举、改类型永远是破坏性的
- 错误路径与正常路径同等重要，且错误信息不得泄露内部结构

### 属性从哪来，各由什么执行

这张表按「属性的来源」分行，而不是按工具分行。工具是可替换的，属性来源决定了你能发现哪一类缺陷。

前两行是传统专项的核心，后两行是同一套思路作用在模型输出上的形态——注意它们用的是同一个判据结构，不是另一套方法论。

| 属性来源 | 工具 | 它负责什么 | 边界 |
| --- | --- | --- | --- |
| OpenAPI 已声明的约束 | Schemathesis | 把类型、枚举、必填、格式直接当属性执行，零额外成本拿到第一层覆盖，并自动构造违反声明的负向请求 | 判据全部来自 Schema，业务语义完全不可见 |
| 人工提炼的业务不变量 | Hypothesis | 提供采样策略与自动收缩，把偶发的随机失败变成最小可复现反例，并用 example database 记住历史反例 | 属性要人写。写不出不变量时，它只是更贵的随机测试 |
| 结构约束（模型输出） | jsonschema | 结构层判据脱离测试框架独立运行，可直接校验 LLM 的结构化输出是否满足下游程序的消费契约 | 形状对不等于内容对；编造的字段值会通过校验 |
| 语义约束（模型输出） | DeepEval | 让语义层判据寄生在 pytest 生态里，复用既有 fixture、参数化与 CI 集成，降低把评测接进流水线的成本 | 内建指标的默认阈值是框架示例值，不是你业务的验收线 |

> 四行的共同结构是「先说清什么算对，再让引擎去找反例」。换成模型输出之后这个结构没变，变的只是判据从确定性扩展到了语义。

*依据：[schemathesis/schemathesis](https://schemathesis.readthedocs.io/) · [HypothesisWorks/hypothesis](https://hypothesis.readthedocs.io/en/latest/) · [python-jsonschema/jsonschema](https://python-jsonschema.readthedocs.io/) · [confident-ai/deepeval](https://deepeval.com/docs/getting-started)*

### 这张图的 7 个节点，本页各交付什么

这张图有两条并行的判据链：Schema 校验器负责结构，业务属性 Oracle 负责语义。它们必须分别出分，合并会让语义问题被结构的高通过率掩盖。

「Mutation 控制器」是本页的验收关口：它故意破坏被测 API，用来证明上面两条判据链真的会红。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| OpenAPI 版本 | 锁定本轮测试依据的 Schema 版本，变更即视为一次重新评测 | Schema 版本号 |
| 例生成器 | 按失败模型生成正例与反例，包含指令冲突与超长输入 | 用例生成配置与 seed |
| Schema 校验器 | 执行结构校验，输出 PASS_SCHEMA 状态 | 结构校验结果 |
| 业务属性 Oracle | 执行业务不变量断言，输出 PASS_SEMANTIC 状态 | 语义断言结果 |
| 被测 API | 在固定配置下接受请求，配置随结果一起记录 | 被测配置快照 |
| Mutation 控制器 | 注入变异体验证两条判据链的检测力 | 变异测试报告 |
| 报告与门禁 | 分别报告结构与语义结论，禁止合并成单一通过率 | 分状态报告 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 三类检查各自负责什么

三类检查覆盖不同的失败面，缺任何一类都会留下整片盲区。

右列是这一类的典型缺陷——注意它们互不重叠。

| 检查 | 负责 | 典型能抓到的缺陷 |
| --- | --- | --- |
| 正反例 | 已知输入的正确处理 | 错误码不对、边界处理错 |
| Schema 变异 | 校验是否真的生效 | 缺字段被静默接受 |
| 属性测试 | 任意输入下的不变量 | 特定组合下金额不守恒 |

> 第二类最容易被跳过：多数团队假设 Schema 校验一定生效，从不验证它。

*依据：[schemathesis/schemathesis](https://schemathesis.readthedocs.io/) · [HypothesisWorks/hypothesis](https://hypothesis.readthedocs.io/en/latest/)*

### 这一页的验收口径：结构与语义分开计分

PS02-1 与 PS02-2 是本页的核心：两个状态必须分别报告。把它们合成一个通过率，等于用结构层的高分掩盖语义层的问题。

PS02-3 的变异杀伤率决定了前两条数字可不可信——一组杀不死变异体的断言，通过率再高也没有意义。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| PS02-1 | 结构合规 | PASS_SCHEMA 通过率 = 100%；破坏性 Schema 变更漏检次数 = 0 | 每次提交 |
| PS02-2 | 语义正确 | PASS_SEMANTIC 通过率 ≥ 98%；金额与状态类不变量违反次数 = 0 | 每次发布 |
| PS02-3 | 断言检测力 | Schema 与业务属性变异体的杀伤率 ≥ 80% | 每次断言变更 |
| PS02-4 | 反例覆盖 | 按失败模型构造的反例覆盖率 = 100%，遗漏类别数 = 0 | 每次发布 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在验证契约、实际验证不到的做法

这两种做法都基于 OpenAPI，工具链也成熟。

问题是它们只验证了声明与实现的一致性，没验证约束是否生效。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 用 OpenAPI 生成请求，响应符合 Schema 即通过 | 声明与实现一致，自动化程度也高 | 这只验证了正常路径。要验证校验是否生效，必须发送不符合 Schema 的请求并断言被拒绝——很多服务其实并不校验 |
| 接口签名没变就认为是兼容变更 | 签名一致是兼容性的常见判据 | 字段语义变化不改签名：同一个字段从「含税」变成「不含税」，签名完全一样但消费者全部算错 |

> 两条的共同修法：主动发送坏请求验证校验，主动比对字段语义而不只是签名。

*依据：[schemathesis/schemathesis](https://schemathesis.readthedocs.io/)*

### 契约测试全绿但联调出错时按什么顺序查

按下表逐项排查。前两行是最常见的假覆盖来源。

验证方式都是主动构造异常，而不是等异常发生。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 坏请求被接受了 | Schema 校验未生效 | 主动发送缺字段请求验证 |
| 字段还在但含义变了 | 语义漂移 | 比对字段的业务定义而非签名 |
| 特定组合下金额算错 | 缺属性测试 | 写守恒类不变量并用生成器覆盖 |
| 消费者升级后失败 | 破坏性变更未识别 | 做消费者驱动的契约验证 |

> 第三行需要属性测试：具体组合无法穷举，只能用不变量覆盖。

### 给一个接口做 Schema 变异与属性测试：约 55 分钟

两类检查各写几条，就能暴露此前的假覆盖。

1. 从正常请求出发，构造四类变异：缺必填字段、类型错误、枚举越界、多余字段。
2. 逐个发送，断言服务返回明确的错误而不是静默接受。
3. 写出这个接口的业务属性，如「退款总额不超过实付金额」。
4. 用生成器构造大量合法输入组合，验证属性在所有组合下成立。
5. 失败时保存最小反例与 seed，确保可复现。

**期望结果**：典型结果是四类变异里至少一类被静默接受，且属性测试会在某个组合上失败——那个组合通常是人工用例想不到的。

> ⚠ 属性测试的生成器要覆盖业务边界。默认生成器倾向于生成中间值，测不到边界组合。

### 这一页的出口判据

这一页的门禁最容易被简化成「Schema 校验通过就放行」。那样做的代价是把语义错误全部放到线上去发现。

第三段要接受的是属性覆盖的不完整：不是所有业务规则都能写成不变量，写不出来的部分必须显式交给人工或规则引擎。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 金额与状态类业务不变量违反次数 > 0 时阻断<br>破坏性 Schema 变更漏检次数 > 0 时阻断发布 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | PASS_SEMANTIC 通过率给出 95% CI 下界与阈值比较，不用点估计<br>变异体 < 30 个时检测力结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 无法表达为业务不变量的规则清单，由业务 owner 列出并指定人工兜底方式<br>PASS_SCHEMA 与 PASS_SEMANTIC 之间的残余差距，由测试负责人签字接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走四类变异与一组业务属性

四类变异是固定套路，可以对所有接口复用。

业务属性是接口特有的，写出来的过程本身就是一次业务梳理。

- 主动发送坏请求验证 Schema 校验是否生效
- 比对字段语义，不只比对签名
- 属性测试保存最小反例与 seed

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[OpenAPI Specification](https://spec.openapis.org/oas/latest.html)** — 契约描述格式
  - 能证明：接口的协议表面：路径、方法、请求/响应 Schema、状态码、鉴权方案、示例。它把「接口长什么样」变成机器可读。
  - 不能证明：不描述业务不变量，也不描述副作用。规范里没有任何位置能写「退款金额不得超过实付」或「重复提交只能扣一次款」——这是四层断言里第三、四层必须由人补的根本原因。
  - `OAI/OpenAPI-Specification` · 版本 3.2.0（2025-09-19） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Schemathesis：由 OpenAPI 契约驱动的属性测试引擎](https://schemathesis.readthedocs.io/)** — 传统专项工具
  - 能证明：把 OpenAPI 里声明的类型、枚举、边界当成属性，自动生成大量合法与非法请求，检出「实现与自己声明的契约不一致」这一类缺陷——例如声明 int32 实际接受任意长度、声明 required 实际可省略、声明 404 实际返回 500。
  - 不能证明：它的判据全部来自 Schema，因此对「格式合法但业务错误」完全无能为力。金额为负、状态非法转换、退款超过实付都能通过它的全部检查。把 Schemathesis 全绿当成接口测试完成，正是本模块反复拆解的那个陷阱。
  - `schemathesis/schemathesis` · 版本 v4.24.3（2026-07-25） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Hypothesis：Python 属性测试库](https://hypothesis.readthedocs.io/en/latest/)** — 方法学实现
