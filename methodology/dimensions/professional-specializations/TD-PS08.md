## TD-PS08

### 数据迁移的规矩一条都没变，只是向量索引成了新的迁移对象

expand-contract、双写、影子读、高水位、对账——这套方法论经受住了几十年考验。引入知识库之后，它多了一个此前不存在的迁移对象：embedding 索引。

下面三条前两条是老问题，第三条是新的。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 先改 Schema 再改代码 | 破坏性变更与代码发布之间存在时间窗口，窗口内旧消费者的失败率为 100% | 把迁移事故归因为「发布顺序没协调好」，而 expand-contract 本来就是为了消除这个协调需求 |
| 回填不做守恒对账 | 分片回填在中途失败时会留下部分完成状态；不对账则差额的检出概率为 0 | 迁移「完成」，几个月后发现有一批数据从未被回填 |
| 换 embedding 模型不当作数据迁移 | 更换 embedding 模型会让全部历史向量与新查询向量不可比，必须 100% 重建索引，而这件事常被当成配置调整 | 换了模型，检索质量断崖式下降，排查方向却落在提示与 reranker 上 |

> 本页的主张：embedding 模型版本是知识库 Schema 的一部分，换它等同于一次破坏性 Schema 变更。

### 数据迁移的四个词

迁移的风险不在写代码，在切换的那一刻和回滚的可能性。

| 术语 | 一句话解释 |
| --- | --- |
| expand-contract | 先扩展兼容再收缩的迁移模式；它让每一步都可回滚 |
| 回填 | 把历史数据补齐到新结构；它通常是耗时最长的一步 |
| CDC 高水位 | 增量同步已处理到的位置；它决定了断点续传的正确性 |
| 影子读 | 同时读新旧两处并比对，但只返回旧结果 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[great-expectations/great_expectations](https://docs.greatexpectations.io/)*

### 数据测试与应用测试的根本差别：断言的是分布，不是单值

应用测试断言的是一次调用的结果：输入可控、预期唯一、失败即缺陷。数据测试面对的是一批数据：输入不可控、而且随时间变化。同一条断言昨天通过今天失败，可能是数据源变了，也可能是业务本身变了——这两种情况的处理方式完全不同，而报警信息长得一模一样。

因此数据质量断言必须先分成两类。结构性约束（非空、唯一、外键、取值域）是硬判据，违反即错；分布性约束（行数区间、空值率、类别占比）是软判据，它检出的是「和以往不一样」，而不一样未必是错。把第二类当第一类用，门禁会天天红，然后在某个周五被彻底关掉。

迁移测试的判据则是守恒：迁移前后的总量、总额与关键维度分布必须对得上，而且对账要走一条独立于迁移程序的查询路径。用迁移程序自己的日志证明迁移正确，与用接口的读方法证明写方法正确，是同一个错误的两个版本。

可回滚性是迁移里最常被跳过、事故时最贵的一项。声明了 rollback 不等于回滚可用——带数据回填的变更往往无法无损回滚。必须实际演练一次，并明确写出哪些变更是单向的、单向变更一旦出问题的止损手段是什么。这份清单本身就是本页的关键交付物。

### 数据迁移方法论在知识库上变成了什么

这一项几乎是纯粹的迁移应用：传统方法论完整适用，只需要把「表」替换成「索引」，把「字段类型」替换成「embedding 模型版本」。

把它写进课程的理由恰恰在此——很多团队没有意识到向量索引变更是一次数据迁移，于是绕过了全部既有纪律。

| 传统做法 | 在 AI 系统里为什么不够用 | 融合后的新做法 |
| --- | --- | --- |
| Schema 变更走 expand-contract | 知识库的「Schema」包含分块策略、metadata 字段与 embedding 模型，其中 embedding 模型的变更无法通过增列兼容，它使全部历史数据不可用 | 对可兼容的部分（新增 metadata）沿用 expand-contract；对 embedding 变更走全量重建并双索引并行 |
| 双写保证迁移期一致 | 向量索引的双写成本高（每条内容要跑两次 embedding），且两个索引的检索结果不可直接比对 | 双索引期间用影子读比对检索结果集重合度，而不是比对存储内容；重合度低于阈值即阻断切读 |
| 分片回填 + 高水位断点续跑 | 重建索引是计算密集任务，中断后从头再来的代价很高；同时回填期间新写入的内容也要进新索引 | 回填保留高水位并支持断点续跑，新写入同时进两个索引，切读前用高水位确认无遗漏 |
| 回滚 = 切回旧表 | 旧索引若已被删除则无法回滚；而向量索引体积大，团队倾向于尽快删除以省成本 | 旧索引保留期写入回滚方案并演练，保留时长由回滚窗口而不是存储成本决定 |

> 左列不是要被淘汰的东西，右列也不是新工具清单。真正变化的是中间那一列——被测对象的性质变了，于是同一个目的需要换一种达成方式。

*依据：[great-expectations/great_expectations](https://docs.greatexpectations.io/) · [debezium/debezium](https://debezium.io/documentation/reference/stable/index.html)*

### 这些地基不变

下面这些不因为被测对象换成 AI 系统而失效。它们是上面那张表里「融合后的新做法」能够成立的前提——地基塌了，新做法只是换了个说法的空话。

- expand-contract：先扩展兼容，再迁移，最后收缩，中间任何时刻新旧消费者都能工作
- 守恒对账：迁移前后总量必须平，这是唯一能发现静默丢失的手段
- 高水位与断点续跑：长时间任务必须可中断可恢复
- 回滚已演练：未演练的回滚方案在事故时的可用性未知

### 五类判据各自拿什么执行

这张表按判据类型分行。数据这一层最容易发生的选型错误，是拿一个擅长结构性约束的工具去承担分布性判断，或者反过来。

第四行是本页的独立判据来源：当迁移程序、应用日志和报表都说「一致」时，它是唯一一条不经过这些组件的观测路径。

| 判据类型 | 工具 | 它负责什么 | 边界 |
| --- | --- | --- | --- |
| 结构性 + 分布性断言 | Great Expectations | 把非空、唯一、取值域、分布、跨表一致性写成可版本化、可在流水线执行的 expectation，并产出人可读的验证结果 | expectation 是你写的假设；数据漂移到没问过的形态时，全绿只说明你没问那个问题 |
| 随模型走的约束 | dbt tests | unique / not_null / relationships / accepted_values 绑定在模型定义上，模型改了测试跟着改，不会脱节 | 只覆盖结构性约束；同一指标在两处定义不一致这类口径错误不会被检出 |
| 变更管理与回滚 | Liquibase | 数据库变更版本化、可重复执行、显式声明回滚动作，使迁移进入与代码同级的管理 | 声明 rollback 不等于回滚可用；带回填的变更常常无法无损回滚，必须实测 |
| 独立对账路径 | Debezium | 从事务日志捕获行级变更，为「数据到底改了什么」提供一条不经过应用代码与迁移程序的观测路径 | 至少一次投递，事件可能重复与乱序；不去重排序就当对账真值会得到错误结论 |
| 可复位演练环境 | Testcontainers | 让迁移与回滚演练能在 CI 里重复执行，而不是只能在共享库上手工做一次且做完无法还原 | 容器库不等于生产库；数据量、并发与锁行为结论不可外推 |

> 五行里只有第四行提供独立判据，其余四行都在被测系统的同一侧。缺了它，前四行全绿仍然只是「这套程序自认为做对了」。

*依据：[great-expectations/great_expectations](https://docs.greatexpectations.io/) · [dbt-labs/dbt-core](https://docs.getdbt.com/docs/build/data-tests) · [liquibase/liquibase](https://docs.liquibase.com/) · [debezium/debezium](https://debezium.io/documentation/reference/stable/index.html) · [testcontainers/testcontainers-python](https://testcontainers-python.readthedocs.io/)*

### 这张图的 8 个节点，本页各交付什么

这张图是一次标准的 expand-contract 迁移，左侧是新旧消费者，中段是双写与回填，右侧是对账与切读门禁。

把它用在向量索引上时，「双写/影子读」这一节点的比对对象从存储内容变成了检索结果集——这是唯一需要调整的地方。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 旧/新消费者 | 验证迁移全程新旧消费者都能正常工作 | 双消费者兼容测试 |
| Expand Schema | 只做兼容性扩展，禁止在此阶段做破坏性变更 | 扩展阶段变更清单 |
| 双写/影子读 | 对结构化数据比对内容，对向量索引比对检索结果集重合度 | 影子读比对报告 |
| 分片回填 | 分片执行并保留进度，验证可中断可恢复 | 回填任务与进度记录 |
| CDC 高水位 | 记录高水位，确保回填期间的新写入不遗漏 | 高水位台账 |
| 守恒对账 | 迁移前后总量守恒校验，差额必须为 0 或逐条归因 | 对账报告 |
| 切读与 Contract 门禁 | 切读前验证契约兼容与重合度达标 | 切读准入判定 |

### 迁移五步与各自的回滚可能性

按 expand-contract 拆步之后，每一步都有明确的回滚方式。跳步会让回滚变成不可能。

右列是这一步的回滚方式——最后一步是不可逆的分界线。

| 步骤 | 做什么 | 回滚方式 |
| --- | --- | --- |
| 扩展 | 新增字段或表，双写 | 停止双写即可 |
| 回填 | 补齐历史数据 | 删除新数据 |
| 影子读 | 读新旧并比对 | 关闭影子读 |
| 切换 | 读切到新结构 | 切回旧结构 |
| 收缩 | 删除旧结构 | 不可逆 |

> 第五步是唯一不可逆的。它必须在切换后观察足够长时间、确认无回滚需求之后才执行。

*依据：[great-expectations/great_expectations](https://docs.greatexpectations.io/)*

### 这一页的验收口径：守恒、重合、可回滚

PS08-1 的守恒对账是数据迁移唯一不可协商的一条：总量对不上就说明有数据在某处消失了，而它不会自己出现。

PS08-3 是向量索引特有的：新旧索引在同一批查询下的结果重合度，是判断能否切读的直接依据。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| PS08-1 | 守恒对账 | 迁移前后总量差额 = 0；未归因差额条数 = 0 | 每个回填批次 |
| PS08-2 | 兼容窗口 | 迁移全程新旧消费者的失败次数 = 0 | 每次变更 |
| PS08-3 | 索引重合度 | 新旧索引在同一查询集上的 top-5 结果重合度 ≥ 90%，低于此值阻断切读 | 切读前 |
| PS08-4 | 回滚可执行 | 回滚演练成功率 = 100%；旧索引保留期 ≥ 回滚窗口 | 每次切读前 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来迁移很稳、实际风险很高的做法

这两种做法都能更快完成迁移，也确实减少了中间状态。

问题是它们放弃了回滚能力。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 在一次发布里完成结构变更与数据迁移 | 一次做完减少了中间状态，也缩短了周期 | 出问题时无法回滚：旧结构已经不在，新结构又有问题。必须拆成可回滚的多步 |
| 回填完成后抽样比对，一致即切换 | 抽样验证是常见做法，成本也可控 | 抽样可能漏掉特定条件下的数据。切换前应当用影子读在真实流量上比对，覆盖真实的读取模式 |

> 两条的共同修法：拆步保留回滚能力，用影子读在真实流量上验证。

### 迁移后数据对不上时按什么顺序查

按迁移五步倒查，通常在回填或增量同步环节找到原因。

查之前先确认新旧两处的数据都还在。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 历史数据缺失 | 回填未覆盖全部分片 | 检查回填的分片范围与失败记录 |
| 新数据缺失 | 双写未生效 | 检查写路径是否覆盖全部入口 |
| 部分数据滞后 | CDC 高水位异常 | 检查增量同步的位点与延迟 |
| 特定条件下不一致 | 转换逻辑边界 | 用影子读定位差异模式 |
| 无法回滚 | 已执行收缩步骤 | 确认收缩前的观察期是否足够 |

> 第二行的常见原因是有旁路写入口未被覆盖，比如后台管理界面或定时任务。

### 给一次迁移设计影子读比对：约 55 分钟

影子读是切换前最有价值的验证手段，成本也不高。

1. 在读路径上同时查询新旧两处，但只返回旧结果给用户。
2. 比对两处结果，记录不一致的记录及其特征。
3. 按不一致的特征分类：是回填遗漏、转换逻辑边界、还是增量同步滞后。
4. 逐类修复后继续观察，直到不一致率降到可接受水平。
5. 切换后保持旧结构一段时间，确认无回滚需求后再执行收缩。

**期望结果**：影子读通常会发现抽样比对没发现的不一致，且它们集中在少数几类边界条件上。

> ⚠ 影子读会增加读负载。要评估对生产的影响，必要时按比例采样而不是全量比对。

### 这一页的出口判据

这一页的门禁全部在切读之前执行。切读之后再发现问题，回滚窗口可能已经关闭，代价从「重跑一次回填」变成「数据丢失」。

第三段要接受的是重合度不足的部分：新旧索引不可能完全一致，差异中哪些是改进、哪些是退化需要人来判断。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 守恒对账差额 > 0 且未逐条归因时阻断切读<br>回滚演练成功率 < 100% 或旧索引保留期短于回滚窗口时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 索引重合度按查询切片给出 95% CI 下界与阈值比较<br>查询样本 < 200 条时重合度结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 新旧索引结果差异中被判定为改进的部分，由检索 owner 逐类签字<br>旧索引的存储成本与保留时长的取舍，由架构 owner 确定并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[liquibase/liquibase](https://docs.liquibase.com/)*

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Testcontainers：用真实依赖容器做集成测试](https://testcontainers-python.readthedocs.io/)** — 副作用层基础设施
  - 能证明：副作用断言需要一个可复位的真实数据库或消息队列。Testcontainers 让「调完接口直接查库」成为可在 CI 里稳定重复的动作，而不是只能在共享测试环境上手工做一次。
  - 不能证明：容器里的数据库不等于生产数据库。版本、扩展、参数、数据量与并发都不同，性能与锁行为结论不能外推。
  - `testcontainers/testcontainers-python` · 版本 testcontainers-v4.15.0（2026-07-24） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Great Expectations：数据质量断言框架](https://docs.greatexpectations.io/)** — 数据专项工具
  - 能证明：数据可以像代码一样被断言：非空、唯一、取值域、分布、跨表一致性都能写成可版本化、可在流水线中执行的 expectation，并产出可读的验证结果。
  - 不能证明：expectation 是你写的假设。数据漂移到一个你没想到的形态时，全绿只说明你没问那个问题。
  - `great-expectations/great_expectations` · 版本 1.20.0（2026-08-07） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点

  - 能证明：数据模型的血缘与测试可以绑定在一起：unique / not_null / relationships / accepted_values 这些通用断言随模型定义走，模型改了测试跟着改。

- **[Debezium：变更数据捕获（CDC）](https://debezium.io/documentation/reference/stable/index.html)** — 数据迁移与副作用观测
  - 能证明：从数据库事务日志捕获行级变更并投递为事件，使「数据到底改了什么」可被独立于应用代码地观测。迁移对账与副作用取证都可以据此建立独立查询路径。
  - 不能证明：CDC 是至少一次投递，事件可能重复与乱序。把 CDC 流直接当成对账真值而不做去重与排序，会得到错误结论。
  - `debezium/debezium` · 版本 v3.7.0.Alpha2 · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Liquibase：数据库变更管理](https://docs.liquibase.com/)** — 迁移与回滚
  - 能证明：数据库变更可以版本化、可重复执行、并显式声明回滚动作。可回滚性是迁移测试里最常被跳过、事故时最贵的一项。
  - 不能证明：声明了 rollback 不等于回滚可用。带数据回填的变更往往无法无损回滚，必须实际演练。
