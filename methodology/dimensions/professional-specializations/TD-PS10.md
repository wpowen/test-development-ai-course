## TD-PS10

### 重试在传统系统里几乎免费，在 Agent 系统里每一次都在烧钱并可能重复执行副作用

超时、重试、熔断、限流、降级——这套稳定性模式的前提是「重试的代价可以忽略」。在 Agent 系统上这个前提不成立：一次重试会重放整条工具链。

下面三条是沿用旧假设的后果。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 按次数设置重试预算 | 同样是 3 次重试，短请求与长上下文任务的成本可能相差 1～2 个数量级，次数无法表达真实预算 | 重试配置在测试环境合理，在生产上把成本预算打穿 |
| 重试不区分动作是否可逆 | 对不可逆动作的重试会重复执行副作用；缺幂等保护时重复的发生概率不为 0 | 把重试当成纯粹的可靠性手段，而它同时是一个事故来源 |
| 缺失步数/时间/成本三重熔断 | 只有单一熔断条件时失控循环仍可能长时间持续；公开案例中出现过 Agent 连续运行 11 天 | 监控看到的是「任务仍在处理中」，直到账单出来 |

> 本页的做法：重试预算用 token 与成本计量，熔断做成步数、时间、成本三重，并逐一验证会触发。

### 稳定性机制的四个词

这四个机制配合起来才能在故障时保住可用性，单独任一个都不够。

| 术语 | 一句话解释 |
| --- | --- |
| deadline 传播 | 上游的剩余时间要传给下游；否则下游会做无用功 |
| 重试预算 | 一次请求允许的重试总量，在请求级分配 |
| 熔断 | 连续失败后主动断开，给下游恢复时间 |
| 降级 | 主动降低能力保住核心可用性 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[resilience4j/resilience4j](https://resilience4j.readme.io/docs)*

### 重试、超时、熔断为什么必须一起设计

这三件事单独看都是「提高可用性」的手段，合在一起却可能互相放大成事故。重试在依赖变慢时会成倍增加它的负载；超时如果设得比上游还长，请求就会堆在自己这里；熔断打开后若降级路径没准备好，等于把局部故障升级成整体不可用。三者都配了、但没有一起设计，比一个都不配更危险。

决定它们能否成立的是预算而不是次数。重试预算限制的是「整体请求里最多有多少比例是重试」，而不是「每个请求最多重试几次」——后者在故障期间会让重试总量随失败率线性增长，正好在系统最脆弱的时候加压。这个区别在配置文件上只差一个字段，在事故曲线上差一个数量级。

超时必须从下往上收敛：调用链上每一层的超时都要小于它的调用方，否则调用方已经放弃、被调用方还在执行，资源被占住却没有任何人在等结果。这条约束可以被静态检查，是稳定性里少数能在代码评审阶段就拦下来的项，值得优先做成规则。

熔断的状态机（关闭 / 打开 / 半开）提供的是「停止踩踏」的能力，它的价值完全取决于打开之后返回什么。配置了熔断但降级路径未经测试，事故时的表现是从「慢」变成「全错」——这比不熔断更糟。因此这一页真正必须实测的不是熔断会不会打开，而是打开之后业务是否还能接受。

### 稳定性模式在 Agent 系统上变成了什么

稳定性模式是传统专项里迁移得最完整的一套：deadline 传播、熔断、限流、降级的思想全部适用，只是每一项的计量单位需要改。

新增的部分是降级形态：Agent 有了传统服务没有的降级路径——降到更小的模型、降到只读、降到人工。

| 传统做法 | 在 AI 系统里为什么不够用 | 融合后的新做法 |
| --- | --- | --- |
| 按次数配置重试预算 | 一次长上下文任务的重试成本可能是短任务的上百倍，次数这个单位无法约束真实开销 | 重试预算改用 token 与金额计量，并与任务级总预算共享同一个额度 |
| 超时后重试直到成功或次数耗尽 | Agent 的重试会重放整条工具链，其中的不可逆动作可能被重复执行，而模型不保证第二次走同一条路径 | 重试前检查动作可逆性：不可逆动作必须携带幂等键，否则只能失败上报不得重试 |
| 熔断基于错误率与响应时间 | Agent 的失控形态是「一直在正常地工作」——不报错、不超时，只是不收敛，错误率与响应时间都不会触发熔断 | 增加步数上限与成本上限两个熔断维度，并逐一注入验证它们真的会触发 |
| 降级返回缓存或默认值 | 生成式功能没有有意义的默认值，返回缓存内容可能给出与当前上下文矛盾的回答 | 降级路径改为：切更小模型、退到检索直出、转只读、转人工；每条路径单独定义并验证其质量下限 |

> 左列不是要被淘汰的东西，右列也不是新工具清单。真正变化的是中间那一列——被测对象的性质变了，于是同一个目的需要换一种达成方式。

*依据：[App-vNext/Polly](https://www.pollydocs.org/) · [Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)*

### 这些地基不变

下面这些不因为被测对象换成 AI 系统而失效。它们是上面那张表里「融合后的新做法」能够成立的前提——地基塌了，新做法只是换了个说法的空话。

- deadline 传播：上游的截止时间必须一路传到最底层，不能在中途被重置
- 重试要有退避与抖动，否则会在故障恢复瞬间制造二次冲击
- 熔断必须验证会触发：未演练的熔断等同于不存在
- 限流与负载卸除：过载时拒绝一部分请求，好过让全部请求都超时

### 四类机制、五种执行方式

前两行是弹性机制的实现，中间两行是让这些机制真正被执行到的故障注入手段，最后一行是把实验管起来的平台。

顺序不能颠倒：没有故障注入，前两行的配置永远停留在配置文件里，红绿都无从谈起——这是稳定性专项与其他专项最大的差别。

| 机制 | 工具 | 它负责什么 | 边界 |
| --- | --- | --- | --- |
| 熔断状态机 | Resilience4j | 提供 CLOSED / OPEN / HALF_OPEN 状态机与滑动窗口统计，使「降级」从口号变成有明确状态与阈值的可测对象 | 配置熔断不等于降级正确；打开之后返回什么、业务能否接受，必须单独验证 |
| 重试与退避 | Polly | 指数退避、抖动、超时、回退与策略组合顺序的显式参数化——顺序错会把重试放大成雪崩，而这是可以静态检出的 | 客户端弹性修复不了服务端容量不足；重试预算不受控时它会加剧而非缓解故障 |
| 网络层故障注入 | Toxiproxy | 按需注入延迟、带宽限制、连接中断与慢关闭，让超时与重试逻辑真正被执行到而不只是被配置 | 注入的是网络层症状，不是依赖服务的真实故障语义（半提交、脏数据） |
| 应用层故障打桩 | WireMock | 构造 5xx、畸形响应、慢响应等应用层故障，覆盖网络层注入不到的路径 | 桩的行为是你编的；真实依赖的失败形态可能完全不同 |
| 编排级实验 | Chaos Mesh | 声明式故障实验，限定爆炸半径与自动终止条件，作为 CRD 纳入版本管理——这是混沌实验与线上乱搞的分界线 | 平台提供注入能力不提供假设；没有稳态定义与终止条件的实验，注入再多也不产生结论 |

> 五行里前两行是「配置了什么」，后三行是「证明了什么」。稳定性专项的成熟度基本等于后三行做到了哪一步。

*依据：[resilience4j/resilience4j](https://resilience4j.readme.io/docs) · [App-vNext/Polly](https://www.pollydocs.org/) · [Shopify/toxiproxy](https://github.com/Shopify/toxiproxy#readme) · [wiremock/wiremock](https://wiremock.org/docs/) · [chaos-mesh/chaos-mesh](https://chaos-mesh.org/docs/)*

### 四个机制的触发顺序与各自职责

四者有明确的触发顺序。顺序错了会互相干扰，比如重试把熔断的恢复期填满。

右列是这个机制失效时的表现。

| 机制 | 何时触发 | 失效时的表现 |
| --- | --- | --- |
| deadline 传播 | 请求进入时 | 下游在上游已放弃后继续处理 |
| 重试预算 | 单次失败后 | 重试放大导致雪崩 |
| 熔断 | 连续失败达阈值 | 故障持续传播，下游无法恢复 |
| 降级 | 熔断后或负载过高 | 直接对用户报错 |

> 四者的顺序是：先看剩余时间够不够重试，再看预算够不够，再看熔断是否已断开，最后才降级。

*依据：[resilience4j/resilience4j](https://resilience4j.readme.io/docs)*

### 这一页的验收口径：预算、熔断、降级

PS10-2 的三重熔断要求的不是「配置存在」，而是「逐一注入验证过会触发」。配置存在但不生效是这个领域最常见的形态。

PS10-3 为每条降级路径设质量下限，防止降级变成「悄悄给出更差的结果而没人知道」。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| PS10-1 | 预算计量 | 重试预算以 token 与金额表达；以次数表达的重试配置项数 = 0 | 每次配置变更 |
| PS10-2 | 三重熔断 | 步数 / 时间 / 成本三重熔断的实测触发率各为 100%（逐一注入验证） | 每次发布 |
| PS10-3 | 降级质量下限 | 每条降级路径定义质量下限并实测达标；未定义下限的降级路径数 = 0 | 每次发布 |
| PS10-4 | 恢复窗口 | 依赖恢复后系统回到正常路径的时间 ≤ 5 分钟；残留降级状态数 = 0 | 每次演练 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在做稳定性、实际加剧故障的做法

这两种做法都是为了提高成功率，出发点正确。

问题是它们在故障时会让情况更糟。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 每层独立配置重试，提高整体成功率 | 每层都容错，整体更健壮 | 多层重试会相乘。四层各三次就是最坏 81 次调用，依赖抖动时它会把小故障放大成雪崩 |
| 熔断后立即重试探测，尽快恢复服务 | 快速恢复是好事，探测也很轻量 | 立即重试会把下游刚恢复的容量再次打满。熔断后需要半开状态与退避，用少量请求探测而不是全量恢复 |

> 两条的共同修法：重试预算在请求级统一分配，熔断恢复走半开与退避。

### 故障扩散时按什么顺序查

扩散几乎总是重试放大加熔断缺失。按下表逐项核对配置。

核对时把最坏调用次数算出来，这个数字通常令人意外。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 下游稍慢就雪崩 | 多层重试放大 | 算最坏次数并收到请求级 |
| 下游恢复不了 | 熔断后立即全量重试 | 改为半开状态与退避 |
| 上游超时但下游还在跑 | deadline 未传播 | 把剩余时间传给下游 |
| 降级后用户仍看到报错 | 降级路径未实现 | 定义并测试降级返回内容 |

> 第三行造成的浪费很难被发现：下游资源被已经放弃的请求占用，而监控上看起来一切正常。

### 算清重试预算并验证熔断：约 50 分钟

前半是算术，后半是一次故障注入。

1. 把各层的重试次数与超时值抄下来，相乘得到最坏调用次数。
2. 把最坏总耗时与请求 deadline 比较，超出的部分即必然发生的超时。
3. 注入下游持续失败，验证熔断是否在预期次数内触发。
4. 熔断后观察恢复行为：是立即全量重试，还是半开探测。
5. 验证降级路径：熔断期间用户看到的是明确的降级结果还是错误页。

**期望结果**：典型结果是最坏调用次数远超预期，且熔断恢复采用了立即全量重试。这两项都是雪崩的直接成因。

> ⚠ 熔断验证要在隔离环境做。在共享环境注入持续失败会影响其他调用方。

*依据：[Shopify/toxiproxy](https://github.com/Shopify/toxiproxy#readme)*

### 这一页的出口判据

这一页的门禁完全依赖故障注入。没有注入就没有证据——稳定性是唯一一个必须靠制造问题来验证的质量属性。

第三段要接受的是降级带来的体验损失：每一条降级路径都意味着用户拿到的东西变差了，这个取舍必须被明示。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 三重熔断中任一项的实测触发率 < 100% 时阻断<br>对不可逆动作在无幂等键情况下发生重试的次数 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 降级路径的质量下限按 95% CI 下界与阈值比较<br>故障注入样本 < 30 次时该故障类型结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 各降级路径的质量下限取值，由产品 owner 签字确定并承担体验后果<br>未纳入故障注入的依赖清单，由架构 owner 列出并接受其风险 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)*

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

  - 不能证明：桩的行为是你编的。真实依赖的失败形态可能与你的假设完全不同——桩测试通过不代表真实降级路径有效。
  - `wiremock/wiremock` · 版本 3.13.2（2025-11-14） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
