## TD-PS01

### HTTP 200 从来就不等于业务成功，接上 AI 之后这个落差变得更大

退款 API 返回 200 只说明请求被接受了。钱有没有动、账本平不平、事件有没有发出去，都在响应体之外。这个老问题在 AI 系统里被放大：模型还会用自然语言告诉你「已为您退款」。

下面三条是只测协议层时漏掉的东西。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 只断言状态码与响应 Schema | 协议层断言能覆盖的失败类型不足全部失败的一半；账本不平、事件未发这两类 100% 漏过 | 接口测试全绿，对账在月底才发现差额 |
| 把模型的自述当成执行结果 | 模型说「已完成」与业务状态真的变更之间没有任何强制关系；这类不一致的检出率在只看文本时为 0 | 「Agent 说退款成功了」被记为用例通过 |
| 重试路径没有幂等键 | 网关重试在超时场景下必然发生；缺幂等键时重复退款的发生概率不为 0，1 次即资金事故 | 把重复退款当成偶发缺陷，实际是重试语义的必然结果 |

> 三条指向同一个改变：判据必须落在账本与事件上，而不是落在响应体或模型措辞上。

### API 业务契约的四个词

状态码 200 只说明请求被接受了，说明不了业务发生了什么。

| 术语 | 一句话解释 |
| --- | --- |
| 协议层 | HTTP 状态码、头、编码；它只回答「通了吗」 |
| Schema 层 | 字段、类型、必填；它只回答「格式对吗」 |
| 业务不变量 | 无论怎么调用都必须成立的约束，如退款不超过实付 |
| 副作用 | 接口调用在系统里留下的真实改变；它才是业务发生的证据 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[OAI/OpenAPI-Specification](https://spec.openapis.org/oas/latest.html) · [RFC 9110：HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html)*

### 四层断言这个划分凭什么有效

分层断言的有效性来自一个朴素事实：一次接口调用会在四个不同位置留下痕迹，而这四个位置的可信度是递增的。响应体由被测服务自己生成，它说什么完全取决于实现；账本与事件是调用产生的后果，不受实现自述影响。断言点越靠近后果，测试与实现共享同一个 bug 的概率越低。

这也解释了为什么「断言响应体的关键字段」这种看起来已经很严格的做法仍然不够：它只是换了个位置去读同一个实现的自述。真正的独立性要求判据来自另一条路径——直接查库、消费事件、核对账本，而不是再调一次这个服务的读接口。同一个实现的读写共享同一份领域模型，也就共享同一个 bug。

第三层的业务不变量是唯一不随调用次数变化的判据。协议、Schema、副作用回答的都是「这一次调用对不对」，不变量回答的是「无论调用多少次都必须成立」。幂等、并发、补偿这三类最贵的缺陷最终都落在这一层，这是它值得单独占一层的原因。

HTTP 规范本身把这个分界写得很清楚：它定义了哪些方法应当幂等，但明确不包含 POST。取消、退款这类以 POST 表达的不可逆动作，幂等性必须由应用层自己引入幂等键来提供——协议不会替你保证，因此测试也不能假设它成立。

### API 契约测试在 AI 系统上变成了什么

API 测试是最老的专项之一，也是迁移代价最小的一个——因为它本来就不该只看响应体。AI 只是把这条一直存在的纪律变成了硬要求。

下表左列是传统 API 测试的标准动作，右列是同一个目的在 AI 系统上的实现方式。

| 传统做法 | 在 AI 系统里为什么不够用 | 融合后的新做法 |
| --- | --- | --- |
| 断言响应体字段等于期望值 | 生成式接口的响应文本每次措辞都不同，逐字段等值断言会 100% 失败；而放宽成模糊匹配又等于没断言 | 响应体只做结构断言（字段存在、类型、枚举范围），业务正确性一律断言在账本与事件上 |
| 用状态码区分成功与失败 | Agent 类接口常常在 200 里返回「我无法完成」，也常常在后台异步失败而入口已经 2xx，状态码与业务终态脱钩 | 定义允许终态集合（成功、转人工、安全拒绝），以终态而非状态码判定，并显式声明每种终态算不算完成 |
| 用固定请求做回归 | 同一请求的模型路径可能不同，单次通过无法说明稳定性；一次绿不代表下一次绿 | 关键接口按 pass^k 重复执行，回归判据取区间下界而不是单次结果 |
| 超时后由调用方重试 | 重试在 Agent 场景里会重放整条工具链，副作用可能被执行多次，而模型不保证第二次走同一条路径 | 幂等键从「可选优化」升级为不可逆动作的准入条件，并单独验证重复提交只产生一次副作用 |

> 左列不是要被淘汰的东西，右列也不是新工具清单。真正变化的是中间那一列——被测对象的性质变了，于是同一个目的需要换一种达成方式。

*依据：[RFC 9110：HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html) · [The Idempotency-Key HTTP Header Field（IETF 草案）](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/) · [promptfoo/promptfoo](https://www.promptfoo.dev/docs/intro/)*

### 这些地基不变，而且比以前更重要

下面这些不因为被测对象换成 AI 系统而失效。它们是上面那张表里「融合后的新做法」能够成立的前提——地基塌了，新做法只是换了个说法的空话。

- 分层断言：协议层、Schema 层、业务不变量层、副作用层各自独立，任一层不得替代另一层
- 账本守恒：进出必须平，这是唯一不依赖任何模型行为的判据
- 幂等设计：重试是分布式系统的常态，AI 只是让重试的代价变高
- 契约版本化：接口变更必须可被消费方检测，这一条在工具调用上同样成立

### 这四层各自拿什么工具执行

工具按断言层归位，不按品牌罗列。选错层的工具再好也证明不了那一层的事，而这正是「接口测试很完整却漏掉资金事故」的技术原因。

版本锚点、许可证与能力边界在页尾引用卡里可点击核对；这张表只回答它在这一层负责什么。

| 断言层 | 工具 | 它在这一层负责什么 | 它证明不了什么 |
| --- | --- | --- | --- |
| 协议 + Schema | Schemathesis | 按 OpenAPI 自动生成合法与非法请求，检出「实现与自己声明的契约不一致」——声明 int32 实际接受任意长度、声明 required 实际可省略、声明 404 实际 500 | 值的业务正确性。退款金额为负、状态非法转换都能通过它的全部检查 |
| Schema（模型输出） | jsonschema | 把结构断言从测试框架里独立出来，同一套校验既用于普通接口，也直接用于 LLM 的结构化输出 | 字段齐全、类型正确但内容编造的响应会被放行 |
| 跨服务兼容 | Pact | 消费方声明自己实际依赖的字段与交互，提供方在自己的流水线上回放验证，两边不需要同时部署 | 只覆盖被写进 pact 的交互。没人声明的字段，提供方删掉也不会红 |
| 副作用 | Testcontainers | 提供可复位的真实数据库与消息队列，使「调完接口直接查库」能在 CI 里稳定重复，而不是只能在共享环境手工做一次 | 容器里的数据库不等于生产库，性能与锁行为结论不可外推 |
| 终态判定（AI 接口） | promptfoo | 把确定性断言与语义断言组合在同一个用例里，让措辞不固定的生成式响应也能进入红绿流程 | 模型评判本身有误差，需与人工标注校准后才能作为门禁判据 |

> 五行覆盖四层：协议与 Schema 的自动化程度最高，副作用与终态判定最需要自己搭——而后两者才是资金类缺陷的实际发生地。

*依据：[schemathesis/schemathesis](https://schemathesis.readthedocs.io/) · [python-jsonschema/jsonschema](https://python-jsonschema.readthedocs.io/) · [pact-foundation/pact-python](https://docs.pact.io/) · [testcontainers/testcontainers-python](https://testcontainers-python.readthedocs.io/) · [promptfoo/promptfoo](https://www.promptfoo.dev/docs/intro/)*

### 这张图的 7 个节点，本页各交付什么

这张图从调用方一直画到发布门禁。它要说明的是：一次退款的正确性证据分布在四个地方——响应、账本、事件、Trace，缺任何一个都无法证明这次退款是对的。

「订单/退款账本」是唯一不依赖任何模型行为的判据来源，因此它是本页最重要的节点。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 调用方与幂等键 | 构造带幂等键的请求，并验证重复提交只产生一次副作用 | 幂等性测试集 |
| API Gateway | 验证鉴权、限流与超时在网关层生效，且超时不会静默吞掉后台任务 | 网关行为断言 |
| 订单领域服务 | 验证业务规则在服务层执行，而不是依赖调用方自律 | 业务规则断言集 |
| 订单/退款账本 | 以账本守恒作为最终判据，进出必须平 | 账本对账断言 |
| 事件总线与消费者 | 验证事件真的发出且可被消费，包含重复与乱序场景 | 事件契约测试 |
| Trace/日志/指标 | 验证一次调用可被完整追溯，缺字段的调用判为不可归因 | 可追溯性检查 |
| 发布门禁 | 汇总四层证据，任一层缺失即阻断 | 发布判定记录 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 四层断言各自能发现什么

只做前两层是最常见的 API 测试形态，也是漏测最多的形态。

右列写的是只做到这一层时会漏掉的具体缺陷。

| 层 | 断言什么 | 只做到这层会漏掉 |
| --- | --- | --- |
| 协议 | 状态码、头 | 返回 200 但业务失败 |
| Schema | 字段与类型 | 字段齐全但值是错的 |
| 业务不变量 | 约束是否成立 | 单次正确但多次调用破坏约束 |
| 副作用 | 数据与事件的实际改变 | 接口成功但数据没写或写了两次 |

> 第三与第四层是分界线：做到它们，测试才从「接口能用」变成「业务正确」。

*依据：[OAI/OpenAPI-Specification](https://spec.openapis.org/oas/latest.html)*

### 这一页的验收口径：四层断言各自的达标线

下面四条对应架构图上的四层证据。它们不能互相折抵：响应层 100% 通过而账本层不平，结论是不通过。

PS01-4 的可追溯性看起来像运维要求，但它决定了失败时能不能归因——不可归因的失败无法进回归集，会一直复发。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| PS01-1 | 协议与结构层 | 状态码与响应 Schema 断言通过率 = 100% | 每次提交 |
| PS01-2 | 业务不变量层 | 账本守恒校验失败次数 = 0；金额精度偏差 = 0 | 每次发布 |
| PS01-3 | 副作用层 | 重复提交下副作用重复发生次数 = 0；允许终态覆盖率 = 100% | 每次发布 |
| PS01-4 | 可追溯层 | 调用可完整追溯（含幂等键、终态、事件 id）的比例 ≥ 99% | 每周 1 次 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来接口测试很完整、实际只测了传输的做法

这两种做法都能产出高覆盖率的接口测试套件。

问题是断言层次停在了协议与格式上。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 按 OpenAPI 自动生成契约测试，字段全覆盖 | 覆盖率高、自动化好、维护成本低 | Schema 校验不检查值的业务正确性。退款金额是负数、状态转换非法，都能通过 Schema 校验 |
| 断言响应体里的关键字段等于预期值 | 检查了返回内容，比只看状态码严格得多 | 响应正确不等于副作用正确。数据库可能没写、事件可能没发、或者写了两次。必须直接断言副作用 |

> 两条的共同修法：把断言点从响应扩展到副作用与不变量。

*依据：[schemathesis/schemathesis](https://schemathesis.readthedocs.io/)*

### 接口测试全绿但业务出错时按什么顺序查

按四层从下往上查，通常在第三或第四层找到缺口。

查法很简单：调一次接口，然后直接看数据与事件。

| 症状 | 缺哪一层 | 补什么 |
| --- | --- | --- |
| 返回成功但数据没变 | 副作用 | 调用后直接查数据状态 |
| 重复调用产生两条记录 | 不变量 + 幂等 | 断言记录数与幂等键 |
| 金额或状态出现非法值 | 业务不变量 | 补约束断言 |
| 事件未发出但接口成功 | 副作用 | 断言事件已投递 |

> 四行的共同做法是「调完之后去看」，而不是只看接口返回了什么。

### 给一个接口补齐四层断言：约 45 分钟

挑一个有写操作的接口，逐层往上加断言。

1. 选一个含写操作的接口，先跑现有测试，记录它断言到了哪一层。
2. 加第三层：写出这个接口涉及的业务不变量，如金额上限、状态转换合法性。
3. 加第四层：调用后直接查询数据状态与事件，断言它们符合预期。
4. 构造一次重复调用，断言副作用只发生一次。
5. 构造一次会破坏不变量的调用，确认被拒绝且不留下任何副作用。

**期望结果**：补完第四层后通常会立刻发现一到两个问题，最常见的是重复调用产生重复记录。

> ⚠ 断言副作用时要用独立的查询路径，不要用同一个接口的读方法。同一实现的读写可能共享同一个 bug。

### 这一页的出口判据

这一页的门禁把「接口测试通过」重新定义为四层同时通过。它会让通过变难，也会让通过这件事重新有意义。

第三段要接受的是异步终态的观测延迟：入口返回与业务终态之间总有时间差，这个窗口内的不一致必须被承认。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 账本守恒校验失败次数 > 0 时阻断<br>重复提交下副作用重复发生次数 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 关键接口按 pass^k（k ≥ 3）执行，回归判定以 95% CI 是否重叠为准<br>样本 < 100 次调用时可追溯率结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 入口成功与业务终态之间的观测窗口长度，由架构 owner 签字确定<br>不做幂等保护的低风险接口清单，由业务 owner 逐条列出并接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[The Idempotency-Key HTTP Header Field（IETF 草案）](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)*

### 带走一份四层断言清单

清单按接口列出四层各自断言了什么。只到第二层的接口就是待补清单。

第四层的断言要走独立查询路径，这一点常被忽略。

- 断言扩展到副作用与业务不变量
- 重复调用必须断言副作用只发生一次
- 副作用用独立查询路径验证

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[OpenAPI Specification](https://spec.openapis.org/oas/latest.html)** — 契约描述格式
  - 能证明：接口的协议表面：路径、方法、请求/响应 Schema、状态码、鉴权方案、示例。它把「接口长什么样」变成机器可读。
  - 不能证明：不描述业务不变量，也不描述副作用。规范里没有任何位置能写「退款金额不得超过实付」或「重复提交只能扣一次款」——这是四层断言里第三、四层必须由人补的根本原因。
  - `OAI/OpenAPI-Specification` · 版本 3.2.0（2025-09-19） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Schemathesis：由 OpenAPI 契约驱动的属性测试引擎](https://schemathesis.readthedocs.io/)** — 传统专项工具
  - 能证明：把 OpenAPI 里声明的类型、枚举、边界当成属性，自动生成大量合法与非法请求，检出「实现与自己声明的契约不一致」这一类缺陷——例如声明 int32 实际接受任意长度、声明 required 实际可省略、声明 404 实际返回 500。
  - 不能证明：它的判据全部来自 Schema，因此对「格式合法但业务错误」完全无能为力。金额为负、状态非法转换、退款超过实付都能通过它的全部检查。把 Schemathesis 全绿当成接口测试完成，正是本模块反复拆解的那个陷阱。
