## TD-PS04

### UI 自动化最大的成本从来不是写，是维护——AI 生成的界面让这件事更难

一套 E2E 套件的价值在半年后才显现，也在半年后才崩塌。崩塌的原因几乎总是同一个：定位器绑在了会变的东西上。当界面里出现模型生成的文本时，「会变的东西」占比大幅上升。

下面三条是 UI 自动化的三种典型腐坏方式。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 用可见文本作为定位器 | 模型生成的界面文案每次措辞都可能不同，文本定位器在这类区域的失效率接近 100% | 把用例失败归因为「页面又改了」，实际是文案本来就不该被当成锚点 |
| 用硬等待代替条件等待 | 流式输出的首字延迟波动很大，固定等待要么不够要么浪费；1 条硬等待在套件里会被复制到几十处 | 套件跑得越来越慢，且仍然间歇性失败 |
| 断言停在界面提示上 | 界面显示「已提交」而后端未落库的场景，纯 UI 断言 100% 漏过 | E2E 全绿而订单没创建 |

> 本页的做法：定位器绑语义角色与稳定属性，等待绑可观测条件，断言落到业务状态。

### UI 关键旅程的四个词

UI 测试不稳定的根因通常在三处：定位器、状态隔离、网络。

| 术语 | 一句话解释 |
| --- | --- |
| 关键旅程 | 用户完成一个业务目标的完整路径；它不是页面元素的集合 |
| 定位器策略 | 如何找到页面元素；它决定了测试对改版的敏感度 |
| 状态隔离 | 每个测试自建自清数据，不依赖执行顺序 |
| 网络控制 | 主动控制外部请求的响应，让测试摆脱外部依赖 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[Playwright Locators：语义定位器](https://playwright.dev/docs/locators)*

### 语义定位器与自动等待凭什么把 UI 不稳定压下去

UI 测试的不稳定几乎全部来自两个源头：定位到了错误的元素，或者在元素还不能交互时就动手。传统方案对这两件事都靠人补——写更精确的 XPath、加更长的 sleep，而这两条路都会随页面演进持续腐烂，且腐烂是静默的。

语义定位器把定位依据从 DOM 结构换成无障碍树：按角色、可访问名、标签文本找元素。它的稳定性来自一个副产品——DOM 重构不改变可访问名，而改变可访问名的变更本来就应该被测试发现。定位器因此从「维护负担」变成了「变更探测器」，这是它相对 XPath 的根本差异，不是写法偏好。

自动等待则把等待条件从时间换成状态：元素可见、位置稳定、可接收事件、未被遮挡，全部满足才执行动作，并持续轮询直到超时。这消除了整整一类时序不稳定，代价是它有一条必须记住的边界——它保证的是动作可以发生，不保证动作产生了正确的业务结果。

把模型接进来之后，这两条机制没有被替换，而是被复用了。模型驱动浏览器时读的是可访问性快照而不是截图像素，动作仍然走同一套 actionability 检查。也就是说 AI 层叠在传统自动化能力之上——底层定位与等待做得越扎实，模型驱动的稳定性越高；底层是一堆 sleep 和 XPath 时，接上模型只会让不稳定更难归因。

### UI 自动化在含 AI 的界面上变成了什么

UI 自动化的困难历来来自「界面会变」。AI 把这个变化从「每次迭代变一次」提高到「每次渲染都可能变」，于是那些一直被推荐但常被跳过的做法，现在变成了硬性前提。

同时 AI 也在反向增强这项能力：生成测试、自愈定位器。但这两件事都需要新的门禁来约束。

| 传统做法 | 在 AI 系统里为什么不够用 | 融合后的新做法 |
| --- | --- | --- |
| 用文本或 XPath 定位元素 | 含生成内容的区域文本不稳定，DOM 结构也可能随内容长度变化，两类定位器同时失效 | 定位器绑定语义角色（role/name）与显式测试属性；生成内容区只定位容器，不定位其中的文字 |
| 用固定等待时间同步 | 流式响应的首字延迟与完成时间都不确定，固定等待既可能不够也一定浪费，且会掩盖真实的性能退化 | 等待绑定可观测条件：首个 token 出现、流结束标记、业务状态变更事件 |
| 断言界面显示的结果 | 界面文案由模型生成，它可能在业务未发生的情况下声称已完成，界面与后端状态之间没有强制一致性 | 关键旅程的最终断言落在后端业务状态上，界面断言只用于验证呈现层 |
| 人工编写并维护全部用例 | AI 生成脚本能大幅降低编写成本，但它默认优化的是「让脚本跑绿」，最省事的做法是弱化断言 | 生成脚本保持候选状态，必须通过业务变异测试证明检测力，并经人工评审反模式后才进回归套件 |

> 左列不是要被淘汰的东西，右列也不是新工具清单。真正变化的是中间那一列——被测对象的性质变了，于是同一个目的需要换一种达成方式。

*依据：[microsoft/playwright-mcp](https://github.com/microsoft/playwright-mcp#readme) · [Playwright Actionability：动作前置条件](https://playwright.dev/docs/actionability)*

### 这些地基不变

下面这些不因为被测对象换成 AI 系统而失效。它们是上面那张表里「融合后的新做法」能够成立的前提——地基塌了，新做法只是换了个说法的空话。

- 测试隔离：每条用例自带数据、互不依赖、可任意顺序执行
- 网络控制：第三方依赖必须可 stub，否则套件的稳定性取决于别人的服务
- 失败可回放：截图、DOM 快照、控制台、网络日志缺一不可
- 浏览器矩阵：跨浏览器差异不因为内容由 AI 生成而消失

### UI 这一层实际用什么，各自管到哪

四行里前两行是执行与定位，第三行是把模型接进来的实际接口，第四行是同一次跑批里顺带拿到的无障碍结论。

注意第三行的边界列——它是本页反例表第一行的技术依据：模型能操作浏览器，和模型能判断对错，是两件完全不同的事。

| 能力 | 工具 | 它负责什么 | 边界 |
| --- | --- | --- | --- |
| 跨浏览器执行 | Playwright | 三引擎统一 API、浏览器上下文隔离取代用例间清理、网络拦截构造后端状态、trace 录制供失败回放 | 浏览器行为一致不等于业务一致；UI 全绿仍需副作用层佐证 |
| 语义定位 | Playwright Locators | 绑定无障碍树而非 DOM 结构：重构不失效，而语义变更会失效——后者正是希望被检出的 | 页面本身缺少无障碍属性时会退化成文本匹配，稳定性随之下降 |
| 模型驱动浏览器 | Playwright MCP | 把浏览器能力以可访问性快照形式暴露给模型，动作仍走既有 actionability 机制，不是截图点坐标 | 模型能操作不等于能判断。断言必须由确定性 oracle 提供 |
| 无障碍规则 | axe-core | 在同一次 UI 跑批里附带可自动判定的无障碍规则，并区分 violations / incomplete / passes | 只覆盖 WCAG 中可机器判定的部分，零 violations 不等于合规 |

> 四行共用同一套底层机制。这正是重点：接入 AI 不需要另起一套 UI 自动化，需要的是把定位与等待这两件老事做扎实。

*依据：[microsoft/playwright](https://playwright.dev/docs/intro) · [Playwright Locators：语义定位器](https://playwright.dev/docs/locators) · [microsoft/playwright-mcp](https://github.com/microsoft/playwright-mcp#readme) · [dequelabs/axe-core](https://github.com/dequelabs/axe-core/blob/develop/doc/API.md)*

### 三类不稳定来源与对应做法

UI 测试的维护成本主要来自这三类。逐项处理之后，稳定性会有质的变化。

右列是具体做法，不是原则。

| 不稳定来源 | 表现 | 做法 |
| --- | --- | --- |
| 定位器脆弱 | 改版后大批失败 | 用稳定语义属性而非样式或位置 |
| 状态污染 | 单跑通、批量跑挂 | 每个测试自建自清数据 |
| 外部依赖抖动 | 偶发超时 | 用网络控制固定外部响应 |
| 异步等待 | 偶发找不到元素 | 用显式等待条件而非固定延时 |

> 第四行的固定延时是最常见的临时解法，也是最大的隐性成本来源：它既拖慢测试又掩盖真实的性能退化。

*依据：[Playwright Actionability：动作前置条件](https://playwright.dev/docs/actionability)*

### 这一页的验收口径：稳定性与检测力

PS04-1 的 flaky 率是 UI 套件唯一真正重要的健康指标：超过阈值后团队会开始忽略失败，此时套件的实际价值归零。

PS04-3 把 AI 生成脚本纳入同一条判据——不管谁写的，都要证明它在业务被改坏时会红。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| PS04-1 | 套件稳定性 | 同一提交连续跑 5 次的 flaky 率 ≤ 1% | 每日 |
| PS04-2 | 定位器健壮性 | 依赖可见文本定位的关键旅程步骤数 = 0；硬等待出现次数 = 0 | 每次提交 |
| PS04-3 | 检测力 | 关键旅程的业务变异杀伤率 ≥ 90% | 每次发布 |
| PS04-4 | 失败可回放 | 失败用例保存完整现场（截图 + DOM + 控制台 + 网络）的比例 = 100% | 每次运行 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在提高 UI 测试稳定性、实际掩盖问题的做法

这两种做法都能立刻减少失败次数，效果立竿见影。

问题是它们把不稳定藏起来而不是消除。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 给不稳定的用例加重试，失败率明显下降 | 重试处理偶发问题是常见做法，成本也低 | 重试会把真实的偶发缺陷一起掩盖。而且不稳定的根因（状态污染或异步等待）仍然存在，只是被多跑几次盖住了 |
| 把等待时间统一延长，超时问题消失 | 延长等待确实减少了超时，改动也简单 | 固定延时既拖慢整个测试套件，又让真实的性能退化不可见。正确做法是等待具体条件，如元素可交互或请求完成 |

> 两条的共同修法：找到不稳定的具体来源并消除，而不是用重试或延时覆盖。

*依据：[microsoft/playwright-mcp](https://github.com/microsoft/playwright-mcp#readme)*

### UI 测试不稳定时按什么顺序查

按下表逐项排除，前两行覆盖多数情况。

判断依据是「单跑和批量跑表现是否一致」。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 单跑通批量跑挂 | 状态污染 | 让每个测试自建自清数据 |
| 改版后大批失败 | 定位器依赖样式或位置 | 改用稳定语义属性 |
| 偶发找不到元素 | 固定延时不够 | 改用显式等待条件 |
| 偶发超时 | 外部依赖抖动 | 用网络控制固定响应 |
| 跨浏览器结果不同 | 浏览器特性差异 | 在矩阵中显式声明支持范围 |

> 第一行的验证方法很简单：把测试顺序打乱重跑一遍，失败率变化就说明有状态污染。

### 稳定化一条关键旅程：约 60 分钟

选一条最常失败的旅程，按三类来源逐个处理。

1. 把该旅程单独跑十次，记录失败率；再打乱顺序批量跑十次，比较两个失败率。
2. 两者差异明显时先处理状态污染：让测试自建数据、结束时清理。
3. 检查定位器：把依赖样式、位置或文案的改为稳定语义属性。
4. 把所有固定延时改为显式等待条件，如等待请求完成或元素可交互。
5. 用网络控制固定外部依赖的响应，消除外部抖动。

**期望结果**：四步做完后失败率通常从个位数百分比降到接近零，且套件总耗时下降——因为固定延时被移除了。

> ⚠ 消除固定延时后可能暴露真实的性能问题。那不是新引入的缺陷，是此前被延时掩盖的。

### 这一页的出口判据

这一页的门禁保护的是套件的长期可用性。flaky 率与硬等待这两条看起来是工程卫生，实际决定了半年后还有没有人相信这套测试。

第三段要接受的是自动化边界：第三方跳转、真实支付、需要真机的场景通常不适合自动化，这些必须显式列出。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 关键旅程中硬等待出现次数 > 0 或文本定位步骤数 > 0 时阻断<br>flaky 率 > 3% 时阻断，先修稳定性再加用例 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | flaky 率按连续 5 次运行统计并给出 95% CI 上界，与阈值比较用上界<br>变异体 < 30 个时检测力结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 不适合自动化的场景清单与人工覆盖方式，由测试负责人签字接受<br>浏览器矩阵的裁剪范围，由产品 owner 根据真实用户分布确定并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一条稳定的关键旅程作为模板

模板的价值是它示范了三类来源的处理方式，其余旅程可以照着改。

关键是不用重试和固定延时——它们是稳定性问题的症状而非解法。

- 每个测试自建自清数据，不依赖执行顺序
- 定位器用稳定语义属性，不用样式或位置
- 用显式等待条件替代固定延时

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Playwright：跨浏览器端到端测试框架](https://playwright.dev/docs/intro)** — Web UI 专项主力工具
  - 能证明：浏览器自动化的三项工程能力：actionability 自动等待取代 sleep、语义 locator 取代 CSS/XPath 坐标、浏览器上下文隔离取代用例间清理。它们共同把 UI 测试的不稳定来源从「时序」降到「业务」。
  - 不能证明：自动等待解决的是元素可交互，不是业务就绪。页面上按钮能点了不代表后台事务已提交；UI 全绿仍需副作用层佐证。
  - `microsoft/playwright` · 版本 v1.62.1（2026-07-30） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Playwright Locators：语义定位器](https://playwright.dev/docs/locators)** — 机理说明
  - 能证明：getByRole / getByLabel / getByText 这类定位器绑定的是无障碍树与用户可见语义，而不是 DOM 结构。因此重构 DOM 不会让它们失效，而改动可访问名会——这恰好是希望被检出的变更。
  - 不能证明：官方文档描述的是 API 能力，不构成对你项目用例稳定率的承诺。
  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理
- **[Playwright Actionability：动作前置条件](https://playwright.dev/docs/actionability)** — 机理说明
  - 能证明：每个动作在执行前需要满足哪些条件（visible、stable、enabled、receives events、editable），以及它们如何被自动轮询等待。这是理解「为什么不该写 sleep」的机制层依据。
