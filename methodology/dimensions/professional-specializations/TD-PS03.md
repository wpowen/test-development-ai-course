## TD-PS03

### 跨服务边界一直是最贵的缺陷来源，多 Agent 只是又加了一层没有 Schema 的边界

契约测试解决的是「我以为你会给我这个字段」。这个问题在微服务里已经很贵，在多 Agent 编排里更贵——因为 Agent 之间的交接根本没有 Schema，全靠自然语言。

下面三条覆盖两类边界：服务之间和 Agent 之间。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 只测自己这一侧的接口 | 单侧测试对跨侧不兼容的检出率为 0；消费者驱动契约存在的全部理由就是补这个 0 | 两个服务各自测试全绿，集成时才发现字段名对不上 |
| Agent 之间的交接不做契约校验 | 在源头埋 5 个可验证事实，走完 3 跳交接后存活率常常不足一半，而每一跳自己看都正常 | 把下游 Agent 的错误归因于下游模型，实际是上游没把信息传下去 |
| 事件消费不测重复与乱序 | 至少一次投递语义下重复必然发生；不测时重复消费的副作用在生产上是必然事件，而 1 次重复扣减就足以让账本对不平 | 把重复扣减当成偶发 bug 修了一次又一次 |

> 本页的主张：把 Agent 之间的每一条 A→B 交接，当成一条消费者驱动契约来测。

### 跨服务边界的四个词

服务之间的兼容性问题不在单个服务内部，在它们的约定上。

| 术语 | 一句话解释 |
| --- | --- |
| 消费者契约 | 由调用方定义的期望；它比提供方的声明更能反映实际依赖 |
| 版本兼容 | 新版本能否让旧消费者继续工作 |
| 重复投递 | 消息可能被送达多次；这是至少一次语义的常态 |
| 补偿 | 失败后撤销已完成部分的动作；它本身也需要被测试 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[pact-foundation/pact-python](https://docs.pact.io/) · [asyncapi/spec](https://www.asyncapi.com/docs)*

### 消费者驱动契约凭什么比集成环境更早、更便宜

端到端集成环境确实能发现兼容性问题，但发现得太晚也太贵：它要求两边都部署到位，失败时还要先花时间判断是谁的问题。更糟的是它的结论不稳定——环境里任何一个无关服务出问题，都会盖住真正的契约破坏。

消费者驱动契约把这件事拆开：消费方在自己的单元测试里声明「我实际用到这些字段、这些交互」，生成一份 pact 文件；提供方在自己的流水线上回放这份文件。两边都在各自的快速反馈环里跑，不需要共享环境，也不需要同时可用。

关键在于它约束的是**实际依赖**而不是**全部接口**。提供方可以自由改动没有任何消费方使用的字段，只有真正被消费的部分受保护。这让契约既能拦住破坏性变更，又不至于把接口冻死——后者是「接口一改就一堆测试红」这种反模式的根源。

代价与收益在同一处：没有被任何消费方写进 pact 的字段，提供方删掉也不会红。契约测试证明的是兼容性，不是正确性。这两件事在事件驱动系统里尤其容易混淆，因为事件的消费方往往不止一个，而且可能是在契约建立之后才加进来的。

### 契约测试在多 Agent 编排上变成了什么

契约测试是本模块里迁移得最自然的一项：它的核心动作——由消费方声明期望、由提供方验证——在 Agent 交接上完全适用，只是契约的载体从 JSON Schema 变成了「必须传递哪些事实」。

变化的不是方法，是边界的数量和它们的可见性。

| 传统做法 | 在 AI 系统里为什么不够用 | 融合后的新做法 |
| --- | --- | --- |
| 为每对服务定义消费者驱动契约 | 多 Agent 系统里的交接边界不出现在任何接口定义里，它藏在编排代码和提示词中，因此边界本身要先被识别出来 | 先画出编排拓扑，把每条 A→B 边登记为一条契约，再为每条边定义必传事实与格式约束 |
| 用 Schema 校验交接内容 | Agent 之间传递的是自然语言与半结构化上下文，没有 Schema 可校验，字段级比对无从下手 | 改用信息衰减测试：在源头埋入可验证事实，在每一跳后检查存活率，把保真率变成可测数字 |
| 版本兼容通过接口版本号管理 | Agent 的行为由模型、提示、工具清单共同决定，任一变化都可能改变交接内容，而没有任何版本号会跟着变 | 把四维版本（模型/提示/工具清单/记忆）作为交接契约的版本，任一维度变化触发交接回归 |
| 死信队列兜住消费失败 | Agent 失败往往不是抛异常，而是给出一个看起来合理的错误结果，它不会进死信队列 | 为交接结果增加业务校验，校验不过的显式失败并进入补偿路径，禁止让可疑结果继续向下游流动 |

> 左列不是要被淘汰的东西，右列也不是新工具清单。真正变化的是中间那一列——被测对象的性质变了，于是同一个目的需要换一种达成方式。

*依据：[pact-foundation/pact-python](https://docs.pact.io/) · [asyncapi/spec](https://www.asyncapi.com/docs)*

### 这些地基不变

下面这些不因为被测对象换成 AI 系统而失效。它们是上面那张表里「融合后的新做法」能够成立的前提——地基塌了，新做法只是换了个说法的空话。

- 消费者驱动：由使用方定义期望，而不是由提供方声明「我提供了什么」
- 重复与乱序：至少一次投递下这两件事必然发生，任何消费方都必须能承受
- 补偿路径：分布式事务不存在，只有可补偿的操作序列
- 租户隔离：跨边界传递时权限上下文必须一起传递，不能在中途丢失

### 三类边界各自拿什么工具守

跨服务边界不是一种，是三种：同步调用、异步事件、身份与授权。三者的失败形态不同，能守住它们的工具也不同。

第四行的 CDC 不是契约工具，它解决的是另一个问题——当上面三层都说「我发出去了」时，谁来独立证明数据真的变了。

| 边界类型 | 工具 | 它负责什么 | 边界 |
| --- | --- | --- | --- |
| 同步 HTTP 契约 | Pact | 消费方声明实际依赖，提供方在自己流水线回放验证，跨团队不需要同时部署或共享环境 | 只覆盖被声明的交互，且证明的是兼容性不是正确性 |
| 异步事件契约 | AsyncAPI | 把 channel、message payload、schema 与协议绑定变成机器可读工件，事件结构不再靠口头约定与截图传递 | 不描述投递语义。重复、乱序、死信这些真正让事件测试变难的性质要自己设计场景 |
| 依赖打桩与故障注入 | WireMock | 把上游依赖替换成可编程的桩，让超时、5xx、慢响应、畸形 body 这些平时碰不到的路径变成可稳定重复的用例 | 桩的行为是你编的。真实依赖的失败形态可能与你的假设完全不同 |
| 副作用独立观测 | Debezium | 从数据库事务日志捕获行级变更，为「数据到底改了什么」提供一条不经过应用代码的独立查询路径 | 至少一次投递，事件可能重复与乱序；不去重排序就直接当对账真值会得到错误结论 |

> 前三行守边界，第四行提供独立判据。缺了第四行，前三行全绿仍然只是「各方都声称自己做对了」。

*依据：[pact-foundation/pact-python](https://docs.pact.io/) · [asyncapi/spec](https://www.asyncapi.com/docs) · [wiremock/wiremock](https://wiremock.org/docs/) · [debezium/debezium](https://debezium.io/documentation/reference/stable/index.html)*

### 跨边界必须验证的六项

六项覆盖了跨服务集成的主要失败面。缺任何一项，问题都会在联调或生产暴露。

右列写的是这项缺失时的典型故障。

| 验证项 | 检查什么 | 缺失时的故障 |
| --- | --- | --- |
| 消费者契约 | 调用方实际依赖哪些字段 | 提供方删了字段才发现有人在用 |
| 版本兼容 | 旧消费者在新版本下是否工作 | 升级后下游集体失败 |
| 租户隔离 | 跨租户数据是否被隔离 | 看到别的租户的数据 |
| 重复投递 | 同一消息处理多次 | 重复副作用 |
| 乱序 | 消息顺序颠倒 | 状态机进入非法状态 |
| 补偿 | 失败后能否撤销 | 部分完成的事务留在系统里 |

> 第一项与第二项常被合并，但它们不同：契约说明谁依赖什么，兼容性说明变更会不会破坏它。

*依据：[pact-foundation/pact-python](https://docs.pact.io/)*

### 这一页的验收口径：两类边界共用一套判据

PS03-2 的交接保真率是本页新增的核心指标，它把「信息在多 Agent 之间有没有传丢」这个此前只能靠感觉判断的问题变成了一个数字。

测量方法很朴素：在源头埋入 5 个可验证事实，走完全部交接后数还剩几个。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| PS03-1 | 服务间契约 | 消费者驱动契约双侧验证覆盖率 = 100%；未验证的边数 = 0 | 每次提交 |
| PS03-2 | Agent 交接保真 | 源头埋入 5 个可验证事实，走完全部交接后存活率 ≥ 95% | 每次发布 |
| PS03-3 | 重复与乱序 | 重复投递下副作用重复次数 = 0；乱序场景业务不变量违反次数 = 0 | 每次发布 |
| PS03-4 | 权限传递 | 跨边界权限上下文丢失或放大的次数 = 0 | 每次发布 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在保证兼容、实际保证不了的做法

这两种做法都是常见的兼容性实践，也确实避免了一部分问题。

问题是它们没有覆盖真实的依赖关系。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 只增不删字段，保证向后兼容 | 这是接口演进的标准原则，也确实避免了删字段的问题 | 新增字段可能改变消费者的解析行为（严格模式下多余字段会报错），而字段语义变化更是不改结构就能破坏兼容 |
| 集成测试跑通即认为跨服务没问题 | 端到端验证了真实链路，最贴近生产 | 集成测试通常只跑正常路径。重复投递、乱序、补偿这三类只在故障时出现，而它们是跨服务最主要的失败面 |

> 两条的共同修法：用消费者契约表达真实依赖，用故障注入覆盖异常路径。

### 跨服务数据不一致时按什么顺序查

数据不一致的根因通常在四类异常路径之一。按下表逐项排除。

排查前先确认消息本身是否被完整保存。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 数据重复 | 重复投递无幂等 | 检查幂等键与作用域 |
| 状态非法 | 消息乱序 | 检查顺序判定与暂存逻辑 |
| 部分完成后卡住 | 补偿未实现 | 补失败后的撤销路径 |
| 下游升级后失败 | 版本兼容 | 做消费者驱动的契约验证 |
| 看到别租户数据 | 租户隔离 | 确认隔离在授权层强制 |

> 五行都要求能重放消息。做不到重放时，这些问题只能靠猜。

*依据：[wiremock/wiremock](https://wiremock.org/docs/)*

### 给一条跨服务链路做三类故障注入：约 60 分钟

重复、乱序、失败补偿三类各注入一次，覆盖主要异常路径。

1. 选一条含事件传递的跨服务链路，确认可以在隔离环境重放消息。
2. 注入重复投递：同一条消息发两次，断言副作用只发生一次。
3. 注入乱序：把两条有先后关系的消息颠倒顺序发送，观察状态机是否拒绝或正确暂存。
4. 注入中途失败：让链路在第二步失败，验证补偿动作是否执行且执行完整。
5. 记录三次的结果与留下的痕迹，缺痕迹的补采集。

**期望结果**：典型结果是重复投递被幂等挡住，但乱序和补偿两项没有对应实现。这两项通常是设计时被假设不会发生的。

> ⚠ 注入要在独立的消息通道上做。在共享通道注入会影响其他消费者，也会污染结果。

### 这一页的出口判据

这一页的门禁同时作用在两类边界上。它们的实现方式不同，但判据是同一个：跨过这条边界之后，该带的东西还在不在。

第三段要接受的是编排拓扑的完整性：Agent 编排常常是动态的，能登记的边未必是全部的边。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 重复投递下副作用重复次数 > 0 时阻断<br>跨边界权限上下文丢失或放大的次数 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 交接保真率按 95% CI 下界与阈值比较；交接样本 < 50 条时结论记为证据不足<br>版本间交接质量对比以区间重叠判定，不用点估计差值 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 动态编排中无法预先登记的交接边范围，由架构 owner 列出并签字接受<br>补偿而非回滚所留下的中间态窗口，由业务 owner 知情接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一份跨边界验证清单

清单六项，每项写明检查方式与必须留下的痕迹。

最容易缺的是乱序与补偿两项，它们只在故障时暴露，但那正是最需要它们正确的时候。

- 用消费者契约表达真实依赖，不看提供方声明
- 重复、乱序、补偿三类必须故障注入验证
- 租户隔离在授权层强制，不靠查询条件

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[OpenAPI Specification](https://spec.openapis.org/oas/latest.html)** — 契约描述格式
  - 能证明：接口的协议表面：路径、方法、请求/响应 Schema、状态码、鉴权方案、示例。它把「接口长什么样」变成机器可读。
  - 不能证明：不描述业务不变量，也不描述副作用。规范里没有任何位置能写「退款金额不得超过实付」或「重复提交只能扣一次款」——这是四层断言里第三、四层必须由人补的根本原因。
  - `OAI/OpenAPI-Specification` · 版本 3.2.0（2025-09-19） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Pact：消费者驱动契约测试](https://docs.pact.io/)** — 跨服务契约
  - 能证明：消费方把自己实际依赖的字段与交互写成 pact 文件，提供方在自己的流水线上回放验证。它检出的是「提供方改了字段，消费方会挂」这类破坏性变更，且不需要把两边部署到一起。
  - 不能证明：只覆盖消费方声明过的交互。没人写进 pact 的字段，提供方删掉也不会红。它证明的是兼容性，不是正确性。
