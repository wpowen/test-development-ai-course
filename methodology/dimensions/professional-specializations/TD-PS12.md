## TD-PS12

### 安全测试的每一条老规矩都还在，只是多了一个会被说服的执行者

身份、授权、输入校验、秘密管理、数据分类——这些一条都没过时。AI 引入的是一个新的攻击面：一个拥有权限、并且可以被自然语言说服的执行者。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 把授权检查放在模型提示里 | 提示层约束在注入下可被击穿，实测多数流行 Agent 的攻击成功率超过 60%，最高 72% | 以为写了「只能查询自己的订单」就实现了授权，实际授权根本没有实施点 |
| 只防用户输入侧的注入 | 攻击已转向运行时数据通道：工具描述、工具返回、检索内容 3 类都直接进上下文且无等价检查，而入口过滤对它们的覆盖率 = 0 | 输入过滤做得很完善，攻击从检索到的工单正文进来 |
| 对象级授权由业务代码自行判断 | Agent 调用工具时携带的身份若是服务身份而非用户身份，对象级授权的实际生效率为 0 | 把越权访问归因于「模型不听话」，实际是权限根本没往下传 |

> 本页的主张：把模型当成不可信输入源，把工具层当成授权的实施点。

### 安全测试的四个词

AI 应用的安全边界比传统应用多了两条：提示边界与工具边界。

| 术语 | 一句话解释 |
| --- | --- |
| 威胁模型 | 谁可能攻击、攻击什么、能得到什么；它决定测试范围 |
| 对象级授权 | 不只检查角色，还要检查这个用户能否操作这个具体对象 |
| 提示边界 | 不可信内容进入模型上下文的位置 |
| 数据分类 | 哪些字段属于敏感信息；它决定输出过滤规则 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[OWASP/ASVS](https://owasp.org/www-project-application-security-verification-standard/)*

### 扫描器能覆盖什么，越权为什么必须靠用例设计

安全扫描器擅长的是模式化缺陷：注入、缺失的安全响应头、已知的危险配置、过期组件。这类缺陷有稳定的特征，可以在完全不理解业务的前提下被检出，因此自动化收益极高，应当尽早接进流水线。

它不擅长的是业务逻辑缺陷，其中最典型的是越权。判断「用户 A 能不能看用户 B 的订单」需要知道谁是 A、谁是 B、什么是订单、谁应该能看——这些信息不在流量里，只在业务规则里。扫描器看到的只是两个都返回 200 的请求，它没有任何依据判定其中一个是事故。

因此越权测试的正确形态是矩阵而不是扫描：把角色 × 资源 × 操作展开，对每个组合断言「允许」或「拒绝且零副作用」。这条设计里最容易漏掉的是拒绝路径的副作用——请求被拒绝，但记录已经写了一半、事件已经发出去了。这是横向越权之外第二常见的形态，也是扫描器结构上不可能发现的。

把 LLM 接进系统后，这条界线的位置没变，但两侧都变大了。传统扫描器的 probe / detector 结构可以原样迁移到模型上：构造诱导输入、判定是否触发不期望行为。而业务侧新增了一类过去不存在的越权——模型被诱导去调用它本不该调用的工具。这类越权的判定必须落在工具调用层，而不是靠模型的自我约束，因为后者是概率的、不可回归的。

### 安全测试在 Agent 系统上变成了什么

这一项的迁移最需要被讲清楚，因为它最容易被误读成「AI 安全是一个全新领域」。实际上大部分风险是经典问题在新执行者上的再现：混淆代理、提权路径、注入。

真正新增的只有一件事：攻击载体从结构化输入变成了自然语言，而自然语言无法被穷举过滤。

| 传统做法 | 在 AI 系统里为什么不够用 | 融合后的新做法 |
| --- | --- | --- |
| 在入口做输入校验与过滤 | 自然语言的攻击载荷无法枚举，基于模式的过滤只能拦住已知写法；而运行时进入上下文的外部内容根本不经过入口 | 放弃「过滤干净」的目标，改为把模型输出当成不可信输入：所有工具调用在执行前重新校验参数与权限 |
| 用角色权限矩阵管理授权 | Agent 常以服务身份调用工具，用户身份在中途丢失，角色矩阵定义得再细也没有实施点 | 委托链贯穿：每次工具调用携带原始用户身份，对象级授权在工具层执行并单独测试越权拦截 |
| 秘密通过配置中心注入，不落代码 | 模型上下文会把配置内容当成普通文本处理，秘密一旦进入上下文就可能出现在输出里 | 秘密不进上下文：工具在服务端持有凭证，模型只能引用工具名而拿不到凭证本身 |
| 渗透测试在发布前做一轮 | 攻击语料会过时，模型会更新，工具清单会变；一次性测试的有效期很短 | 红队常态化：攻击集版本化并纳入 CI，工具清单 hash 变更触发重测 |

> 左列不是要被淘汰的东西，右列也不是新工具清单。真正变化的是中间那一列——被测对象的性质变了，于是同一个目的需要换一种达成方式。

*依据：[NVIDIA/garak](https://docs.garak.ai/) · [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/)*

### 这些地基不变

下面这些不因为被测对象换成 AI 系统而失效。它们是上面那张表里「融合后的新做法」能够成立的前提——地基塌了，新做法只是换了个说法的空话。

- 最小权限：每个工具只拿完成任务必需的权限，这一条在 Agent 上更重要因为调用者会被说服
- 对象级授权：能访问接口不等于能访问这条数据，判断必须在服务端
- 秘密管理：不落代码、不进日志、可轮转
- 数据分类：知道哪些字段是敏感的，才谈得上保护它们

### 五类检查：哪些能自动化，哪些必须自己设计

前两行是传统 Web 安全，后三行是模型接进来之后新增的面。注意它们的结构是同构的：都是「一份风险清单 + 一个探测执行器」。

这张表里没有任何一行能覆盖越权——那是刻意的。越权只能靠角色 × 资源 × 操作的矩阵用例，工具在这里帮不上忙。

| 检查类型 | 工具 | 它负责什么 | 边界 |
| --- | --- | --- | --- |
| 模式化 Web 缺陷 | ZAP | 被动扫描观察既有功能测试流量，主动扫描构造攻击请求，可复用已有的登录态与业务路径 | 对业务逻辑漏洞几乎无能为力；越权必须靠用例矩阵设计 |
| 需求与覆盖度判据 | OWASP ASVS | 分级、可逐条验证的安全需求清单，使结论变成「V2.1.x 已验证、V4.2.x 未覆盖」这种可审计陈述 | 是需求清单不是测试方法；条款到用例的映射要自己做 |
| 模型侧探测 | garak | 把 probe / detector 结构迁移到模型上：构造诱导输入，判定是否触发越狱、信息泄露或有害输出 | 覆盖的是已知攻击模式库，且模型有随机性——单次未命中不等于不存在，结论必须带重复次数与命中率 |
| 模型侧风险清单 | OWASP Top 10 for LLM | 提示注入、敏感信息泄露、供应链、过度代理权限等风险分类，作为安全测试的起点与覆盖度检查表 | 是风险分类不是验收标准，也不按你的业务排优先级 |
| 输入输出管控 | LLM Guard | 把一部分判定从「模型自我约束」移到模型之外的确定性代码路径：输入侧注入检测与脱敏、输出侧敏感与有害内容过滤 | 过滤层本身有漏判与误判，两类错误率都必须单独度量 |

> 第五行是这一页最重要的工程主张：能移出模型的判定就移出去。留在模型里的判定不可回归，移出来的才进得了门禁。

*依据：[zaproxy/zaproxy](https://www.zaproxy.org/docs/) · [OWASP/ASVS](https://owasp.org/www-project-application-security-verification-standard/) · [NVIDIA/garak](https://docs.garak.ai/) · [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/) · [protectai/llm-guard](https://protectai.github.io/llm-guard/)*

### 这张图的 7 个节点，本页各交付什么

这张图的核心是一条纵深链：身份在网关校验，非可信输入进入模型，授权在对象层实施，工具层做 allowlist 与参数校验，账本记录结果。

「Agent/Prompt 非可信输入」这个节点的命名是刻意的：本页要求把模型的输出当成来自外部的不可信数据，而不是内部组件的返回值。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 用户/token | 构造越权、伪造、过期 token 的攻击集 | 身份攻击集 |
| Gateway 身份校验 | 验证身份在入口被校验且原始身份继续向下传递 | 身份传递验证 |
| Agent/Prompt 非可信输入 | 把模型输出视为不可信，构造直接与间接注入语料 | 注入攻击集 |
| 对象与功能授权 | 验证对象级授权在服务端执行，越权尝试全部拦截 | 对象级授权测试 |
| 工具 allowlist/参数校验 | 验证工具白名单与参数校验在执行前生效 | 工具授权测试 |
| 订单/退款账本 | 以账本作为副作用的最终证据，验证无未授权变更 | 账本审计结果 |
| 脱敏 Trace 与安全门禁 | 保存脱敏证据并汇总安全结论 | 安全门禁报告 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 五类安全检查各自的确定性判据

安全测试要尽量用确定性判据，把主观判断留给必要的部分。

右列是可以程序化断言的判据——它们比人工评审更可靠也更可复用。

| 检查 | 确定性判据 |
| --- | --- |
| 身份验证 | 未认证请求必须被拒绝 |
| 角色授权 | 越权角色的操作必须被拒绝 |
| 对象级授权 | 操作他人对象必须被拒绝，且不泄露存在性 |
| 提示边界 | 注入载荷不得导致越权工具调用 |
| 数据分类 | 输出中不得出现敏感类字段 |

> 第三行的「不泄露存在性」常被忽略：返回「无权限」和返回「不存在」泄露的信息量不同。

*依据：[OWASP/ASVS](https://owasp.org/www-project-application-security-verification-standard/)*

### 这一页的验收口径：拦截率与实施点

本页四条指标全部要求绝对值。安全类失败属于「一次即事故」，用百分比表达容忍度在这里没有意义。

PS12-2 是本页最重要的一条：它检查授权是否真的有实施点，而不是只写在提示或文档里。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| PS12-1 | 注入抵抗 | 高危动作类攻击成功率 = 0；总体 ASR ≤ 1% | 每次发布 + 每周 1 次 |
| PS12-2 | 授权实施点 | 对象级授权在服务端执行的比例 = 100%；仅靠提示约束的授权项数 = 0 | 每次发布 |
| PS12-3 | 委托链完整 | 工具调用携带原始用户身份的比例 = 100%；越权尝试拦截率 = 100% | 每次发布 |
| PS12-4 | 秘密隔离 | 模型上下文中出现凭证的次数 = 0；日志中出现凭证的次数 = 0 | 持续 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来安全测试完整、实际有盲区的做法

这两种做法都覆盖了传统 Web 安全的主要面。

问题是它们没有覆盖 AI 特有的两条边界。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 按角色测试权限矩阵，各角色只能访问自己的功能 | 角色权限是权限设计的核心，矩阵也覆盖完整 | 角色对了不代表对象对了。同一角色的两个用户互相访问对方数据，在角色矩阵上完全看不出来 |
| 对用户输入做安全过滤，防止注入 | 输入过滤是标准防线，也确实拦下了直接攻击 | AI 应用的主要注入通道是检索内容与工具返回值，它们不经过用户输入过滤。必须把提示边界纳入威胁模型 |

> 两条的共同修法：补对象级授权测试，把提示边界与工具边界纳入威胁模型。

*依据：[zaproxy/zaproxy](https://www.zaproxy.org/docs/)*

### 发现越权或泄露时按什么顺序查

按五类检查逐项定位。前三类是传统面，后两类是 AI 特有面。

定位之后的修复都在授权层或输出层，不在提示词。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 访问了他人数据 | 对象级授权缺失 | 在数据访问层强制对象归属检查 |
| 通过错误信息推断出数据存在 | 存在性泄露 | 统一无权限与不存在的响应 |
| 模型执行了文档里的指令 | 提示边界未防护 | 把授权移到工具层 |
| 输出里出现敏感字段 | 数据分类未覆盖 | 补字段分类与输出过滤 |
| 某角色能做超出范围的事 | 角色授权配置 | 核对权限矩阵与实现 |

> 第三行的修复不是加强提示词，而是确保工具层授权在模型之外强制执行。

### 做一次对象级授权与提示边界测试：约 60 分钟

两类都是最常缺失的，且都能用简单构造暴露。

1. 用两个同角色的不同用户 A 和 B，让 A 尝试访问 B 的具体对象。
2. 断言被拒绝，并检查响应是否泄露了该对象存在。
3. 把一段要求越权操作的指令埋进检索文档中，用正常问题触发检索。
4. 观察模型是否服从，以及工具层是否拦下——两者要分别记录。
5. 检查输出中是否出现了数据分类中标记为敏感的字段。

**期望结果**：典型结果是对象级授权存在缺口，且注入指令虽被模型服从但被工具层拦下。后者说明纵深防御生效。

> ⚠ 测试必须在隔离环境用测试账号进行。用真实用户数据做越权测试本身就是一次数据事故。

### 这一页的出口判据

这一页的门禁不接受统计式的辩解。越权与凭证泄露不是概率问题，是控制有没有实施点的二元问题。

第三段要接受的是未知攻击面：攻击集只覆盖已知手法，新手法一定会出现，问题只是什么时候。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 越权尝试拦截率 < 100% 或高危动作类攻击成功率 > 0 时阻断<br>模型上下文或日志中出现凭证的次数 > 0 时阻断，并立即轮转相关凭证 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | ASR 按攻击类型分片给出 95% CI 上界，与阈值比较用上界<br>攻击集样本 < 200 条时安全结论记为证据不足，不得宣布通过 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 攻击集未覆盖的手法范围，由安全 owner 列出并签字接受<br>为可用性而放宽的护栏项，由产品 owner 与安全 owner 共同署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[NVIDIA/garak](https://docs.garak.ai/)*

### 带走一份含 AI 边界的威胁模型

模型在传统面之外增加两条：提示边界与工具边界。它们是 AI 应用的主要新增攻击面。

五类检查尽量用确定性判据，便于进入自动化门禁。

- 对象级授权单独测试，不只测角色
- 无权限与不存在的响应要统一
- 注入防护验证工具层拦截，不验证模型服从

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[ZAP：Web 应用安全扫描代理](https://www.zaproxy.org/docs/)** — 安全专项工具
  - 能证明：被动扫描（观察流量）与主动扫描（构造攻击请求）的区别，以及如何把安全检查作为代理挂在既有功能测试流量上，复用已有的登录与业务路径。
  - 不能证明：扫描器擅长已知模式（注入、配置、头缺失），对业务逻辑漏洞几乎无能为力。越权、跨租户数据泄露必须靠带身份的用例设计。
  - `zaproxy/zaproxy` · 版本 v2.17.0（2025-12-15） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[OWASP 应用安全验证标准（ASVS）](https://owasp.org/www-project-application-security-verification-standard/)** — 安全判据来源
  - 能证明：分级的、可逐条验证的安全需求清单。它把「做了安全测试」变成「V2.1.x 已验证、V4.2.x 未覆盖」这种可审计陈述。
  - 不能证明：标准是需求清单不是测试方法。每条如何验证、用什么证据，仍需自己设计。

- **[garak：LLM 漏洞探测器](https://docs.garak.ai/)** — 传统安全测试 × AI 的实际结合点
  - 能证明：把安全扫描的 probe / detector 结构原样迁移到模型上：probe 构造诱导输入，detector 判定是否触发了不期望行为（越狱、泄露、有害输出）。传统扫描器的架构在这里是可复用的。
  - 不能证明：探测覆盖的是已知攻击模式库，且模型行为具随机性——单次未命中不等于不存在。结论必须带重复次数与命中率，不能报「已通过」。

- **[OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/)** — AI 侧风险清单
  - 能证明：LLM 应用的高频风险分类（提示注入、敏感信息泄露、供应链、过度代理权限等），可作为安全测试的风险起点与覆盖度检查表。

- **[LLM Guard：模型输入输出的确定性管控层](https://protectai.github.io/llm-guard/)** — AI 侧防护实现
  - 能证明：一部分安全判定可以从「靠模型自我约束」移到模型之外的确定性代码路径上：输入侧的注入检测与脱敏、输出侧的敏感信息与有害内容过滤。移出来之后这层才是可测、可度量、可回归的。
  - 不能证明：过滤层本身有漏判与误判，两类错误率都必须单独度量。把它当成「加了就安全」是把一个概率组件当成了确定性边界。
