## TD-PS06

### Android 测试的老难题是生命周期与同步，端侧模型把这两件事同时变难了

Activity 重建、进程被杀、权限被撤销——这些是 Android 自动化一直要处理的。端侧推理加入之后，它们各自多了一种新的失败形态：推理中途被打断。

它们都建立在老问题之上。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 按页面加载完成作为同步条件 | 流式生成的首字延迟波动常在 1～5 秒区间，页面已加载而内容仍在流入；固定等待在这种场景下的失败率显著上升 | 把间歇失败归因为「设备慢」，实际是同步条件选错了对象 |
| 进程被杀后不验证恢复 | 低内存时系统回收进程是常态；推理中途被杀时若无检查点，用户的输入与已生成内容 100% 丢失 | 把用户投诉的「说了一半没了」当成偶发 |
| 设备矩阵不含端侧模型维度 | 同一应用在不同芯片上可能走不同的推理后端，行为与耗时差异不为 0，而矩阵里没有这一维 | 在测试机上正常，在某类芯片的机型上大量超时 |

> 本页的做法：把同步条件绑到可观测事件，把端侧模型版本与推理后端纳入设备矩阵。

### Android 自动化的四个词

移动端的不稳定主要来自生命周期与同步，而不是脚本写法。

| 术语 | 一句话解释 |
| --- | --- |
| 生命周期 | 应用在前后台、被回收、重建时的状态变化 |
| 同步 | 等待界面真正就绪的机制；固定延时在移动端尤其不可靠 |
| 权限 | 运行时权限的授予与拒绝路径；两条都要测 |
| 设备矩阵 | 要覆盖的系统版本与屏幕组合；它必须有明确取舍依据 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

### 移动端不稳定的真正来源，与两类同步策略的分界

移动 UI 测试比 Web 更不稳定，根源不是「移动端更难」这种含糊说法，而是异步源更多且更不可见：主线程消息队列、动画、图片解码、后台线程池、WorkManager、网络回调、系统弹窗——任何一个还没结束就动手，用例就会失败，而失败信息通常只是「找不到元素」。

进程内自动化的做法是直接观察这些异步源：等主线程消息队列空闲、等已注册的 IdlingResource 全部空闲，然后才执行下一步。这是它比黑盒方案稳的机制原因——它不猜时间，它看状态。

代价是它只能看见被注册的异步源。自定义线程池、第三方 SDK 的后台任务、未接入的 WorkManager，都会让它照样提前动手。所以「Espresso 很稳」这个经验的准确表述是：那个工程把异步源都注册了。这决定了引入进程内方案时，真正的工作量在应用侧而不在测试侧。

跨进程自动化看不到进程内部，只能从外部观测界面状态，因此改用轮询与重试吸收抖动。它的优点是不侵入应用、能跨应用操作系统弹窗与权限对话框；缺点是等待条件是启发式的，稳定性上限低于进程内方案，必须用更明确的稳态判据和用例级重试来补，而不是靠加长等待时间。

### 移动端自动化在含端侧推理的应用上变成了什么

移动端测试的三大难题——生命周期、同步、设备碎片化——没有一个因为 AI 而消失，它们各自多了一个维度。

值得注意的是方向：不是「移动端测试被 AI 取代」，而是「移动端测试要多管一类新的不确定性来源」。

| 传统做法 | 在 AI 系统里为什么不够用 | 融合后的新做法 |
| --- | --- | --- |
| 以页面/控件出现作为同步条件 | 流式生成时控件早已出现而内容仍在变化，以控件出现为条件会在内容尚未稳定时就开始断言 | 同步条件改绑可观测事件：首 token 到达、流结束标记、业务状态写入完成 |
| 生命周期测试覆盖旋转与后台切换 | 端侧推理是长耗时任务，进程被回收时中断的不只是界面状态，还有正在进行的生成过程与其占用的内存 | 在推理进行中注入进程回收，验证检查点恢复或安全终止，并确认模型内存被正确释放 |
| 设备矩阵按系统版本与屏幕划分 | 端侧推理的后端由芯片能力决定，同一系统版本在不同芯片上可能走完全不同的执行路径，耗时相差数倍 | 矩阵增加推理后端与端侧模型版本两维，并按真实用户机型分布确定覆盖范围 |
| 权限测试覆盖授予与拒绝 | 端侧模型可能访问相册、麦克风等敏感数据用于推理，权限被撤销时需要的是安全降级而不是崩溃或静默继续 | 为每项 AI 功能定义权限缺失下的降级行为，并验证降级路径不会把数据发往云端作为替代 |

> 左列不是要被淘汰的东西，右列也不是新工具清单。真正变化的是中间那一列——被测对象的性质变了，于是同一个目的需要换一种达成方式。

*依据：[Espresso：Android 进程内 UI 测试](https://developer.android.com/training/testing/espresso) · [mobile-dev-inc/Maestro](https://docs.maestro.dev/)*

### 这些地基不变

下面这些不因为被测对象换成 AI 系统而失效。它们是上面那张表里「融合后的新做法」能够成立的前提——地基塌了，新做法只是换了个说法的空话。

- 生命周期正确性：旋转、后台、进程回收后状态可恢复，这是 Android 测试的第一性问题
- 同步优于等待：始终等待可观测条件，不使用固定时长
- 权限的完整矩阵：授予、拒绝、永久拒绝、运行时撤销四种状态都要覆盖
- 设备矩阵按真实分布裁剪，并写明裁掉了什么

### 两类同步策略，四种执行方式

选工具在这一页等价于选同步策略。进程内还是跨进程，决定了你能拿到什么稳定性上限，以及工作量落在应用侧还是测试侧。

第四行不是工具而是协议：它界定哪些能力是标准命令、哪些是某个 driver 的扩展，直接决定用例能不能跨平台复用。

| 同步策略 | 工具 | 它负责什么 | 边界 |
| --- | --- | --- | --- |
| 进程内观察 | Espresso | 观察主线程消息队列与 IdlingResource，在应用真正空闲时才执行下一步，把时序不稳定从根上消掉 | 只覆盖被注册的异步源；未注册的后台任务仍会造成提前动手 |
| 跨进程轮询 | Appium（UiAutomator2） | 基于 W3C WebDriver 协议从外部驱动，可跨应用、可操作系统弹窗与权限对话框 | 等待是启发式的，稳定性上限低于进程内方案 |
| 声明式流程 | Maestro | 用 YAML 表达流程，内建重试与等待吸收渲染与动画抖动，脚本维护成本显著低于命令式脚本 | 内建等待处理的是渲染时序，不是业务异步；业务未就绪照样会误判 |
| 协议边界 | W3C WebDriver | 界定哪些是标准命令、哪些是 driver 扩展，决定用例的可移植范围与跨平台复用成本 | 厂商扩展不保证跨实现可用，也不保证长期稳定 |

> 前两行是同一个问题的两种答案：要稳定性就接受侵入应用，要非侵入就接受更低的稳定性上限。没有第三条路，选型时先认这一点。

*依据：[Espresso：Android 进程内 UI 测试](https://developer.android.com/training/testing/espresso) · [appium/appium](https://appium.io/docs/en/latest/) · [mobile-dev-inc/Maestro](https://docs.maestro.dev/) · [WebDriver 2（W3C Working Draft）](https://www.w3.org/TR/webdriver2/)*

### 这张图的 7 个节点，本页各交付什么

这张图跟着一次扫码收货走完全程：从设备上的操作，经过 Activity 与权限层，落到本地队列，再同步到库存 API 与账本。

「本地状态/队列」是移动端特有的关键节点：离线场景下它承担了业务正确性，而它的失败通常在恢复联网后才暴露。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 收货员与设备 | 覆盖真实使用姿势与设备矩阵，含推理后端维度 | 设备与后端矩阵 |
| Android Activity/Process | 注入旋转、后台、进程回收，验证恢复或安全终止 | 生命周期测试结果 |
| 扫描与权限层 | 覆盖权限四态，并验证权限缺失下的降级不外传数据 | 权限矩阵测试结果 |
| 本地状态/队列 | 验证离线写入的持久化、去重与恢复联网后的同步 | 离线队列测试结果 |
| 库存 API | 验证同步请求的幂等性，防止重复上报 | 幂等性验证 |
| 库存账本 | 以账本守恒作为最终判据 | 账本对账结果 |
| logcat/Trace/报告 | 保存崩溃、ANR 与推理耗时，保证失败可归因 | 失败证据与耗时报告 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 四类移动端特有失败与对应验证

这四类在桌面端很少见，在移动端是主要失败来源。

右列是构造方式——多数可以用系统提供的开发者选项直接触发。

| 失败类型 | 表现 | 怎么构造 |
| --- | --- | --- |
| 进程被回收 | 切回应用后状态丢失 | 开启「不保留活动」后切换应用 |
| 权限被拒绝 | 功能静默失效 | 在设置里手动拒绝权限 |
| 低内存 | 界面重建异常 | 用系统开发者选项限制后台进程 |
| 网络切换 | 请求中断后状态错乱 | 在操作中途切换网络类型 |

> 第一行是移动端最典型也最容易漏测的：开发者选项里的「不保留活动」能稳定复现它。

### 这一页的验收口径：生命周期、离线与推理

PS06-1 与 PS06-2 是移动端一直以来的判据，阈值不因为引入 AI 而放宽。

PS06-4 是新增的一条：端侧推理的耗时必须按机型分层统计，用整体均值会把低端机型的体验完全掩盖。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| PS06-1 | 生命周期恢复 | 旋转 / 后台 / 进程回收后状态可恢复或安全终止的比例 = 100% | 每次发布 |
| PS06-2 | 离线正确性 | 离线写入去重后重复上报次数 = 0；恢复联网后账本守恒失败次数 = 0 | 每次发布 |
| PS06-3 | 权限降级 | 权限缺失时崩溃次数 = 0；降级路径把数据发往云端的次数 = 0 | 每次发布 |
| PS06-4 | 端侧推理耗时 | 按机型分层统计首 token 延迟，最低档机型的 p95 ≤ 3 秒；禁止只报整体均值 | 每次模型或后端变更 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来覆盖了移动端、实际漏掉主要失败的做法

这两种做法都能产出可运行的移动端测试，覆盖率也不低。

问题是它们只覆盖了应用一直在前台的场景。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 在模拟器上跑完整的功能测试套件 | 模拟器成本低、可并行、覆盖也全 | 模拟器不会真实发生进程回收、低内存与网络切换。移动端最主要的三类失败在模拟器上很难自然出现，必须主动构造 |
| 用固定延时等待界面加载完成 | 实现简单，也确实能让大部分用例通过 | 移动端设备性能差异极大。同一个延时在高端机上浪费时间，在低端机上仍然不够。必须等待具体的界面就绪条件 |

> 两条的共同修法：主动构造生命周期事件，用条件等待替代固定延时。

### 移动端测试偶发失败时按什么顺序查

按下表逐项排除。前两行是移动端特有的，桌面端经验容易忽略。

排查时注意区分设备差异与真实缺陷。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 切回应用后失败 | 进程被回收后状态未恢复 | 开启不保留活动重现 |
| 低端机上失败率高 | 固定延时不足 | 改用界面就绪条件等待 |
| 某功能静默失效 | 权限被拒绝路径未处理 | 手动拒绝权限后重走 |
| 特定系统版本失败 | 设备矩阵覆盖不足 | 明确支持范围并声明未测组合 |

> 最后一行的正确处置不是无限扩大矩阵，而是明确声明支持范围与未测组合。

*依据：[appium/appium](https://appium.io/docs/en/latest/)*

### 构造三类移动端特有故障：约 55 分钟

全部用系统开发者选项即可触发，不需要额外工具。

1. 在设备上开启「不保留活动」，走一遍关键旅程，观察切换应用后状态是否正确恢复。
2. 手动拒绝一个关键权限，重走旅程，确认应用给出明确提示而不是静默失效。
3. 在操作进行中切换网络类型，观察请求中断后的状态处理。
4. 把三类的结果记录下来，标出哪些是真实缺陷、哪些是未实现的处理路径。
5. 对使用固定延时的用例，改为等待具体的界面就绪条件并重跑。

**期望结果**：典型结果是进程回收后状态恢复不完整，且权限拒绝路径未被处理。这两项在正常测试中几乎不会暴露。

> ⚠ 证据边界要写清楚：如果只在模拟器上跑过，就不能声称在真机上验证过。设备差异是真实存在的。

### 这一页的出口判据

这一页的门禁有一条与隐私直接相关：权限被拒时不得改用云端推理作为替代。这是产品设计问题，但只有测试能发现它是否真的被遵守。

第三段要接受的是设备矩阵的裁剪——机型分布是长尾的，全覆盖不可能，覆盖到哪里必须是明示决策。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 权限缺失时把数据发往云端的次数 > 0 时阻断<br>进程回收后既不能恢复也不能安全终止的场景数 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 端侧推理耗时按机型分层给出 95% 分位，禁止用整体均值代替分层结论<br>单机型样本 < 30 次时该机型结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 设备与推理后端矩阵的裁剪范围，由产品 owner 依据真实机型分布签字确定<br>低端机型上已知的体验差距，由产品 owner 在知情前提下接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一份移动端特有故障清单

清单四类，每类写明构造方式。它们都能用系统自带能力触发，成本很低。

设备矩阵要明确声明支持范围与未测组合，而不是假装全覆盖。

- 主动构造进程回收与权限拒绝两条路径
- 用界面就绪条件替代固定延时
- 明确声明设备矩阵的支持范围与未测组合

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

  - 不能证明：内建等待处理的是渲染与动画时序，不处理业务异步。设备矩阵、权限弹窗、系统版本差异仍需真机验证。
  - `mobile-dev-inc/Maestro` · 版本 cli-2.8.0（2026-07-31） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
