## TD-PS11

### 可观测性一直缺一类信号，AI 系统让这个缺口无法再忽略

Trace、指标、日志三件套解决的是「系统在做什么」。它们回答不了「系统做得对不对」——传统系统里这个问题靠测试在发布前回答，而 AI 系统的质量会在运行时漂移。

下面三条说明这个缺口的后果。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 只监控延迟、错误率与吞吐 | 质量漂移不改变任何一项传统信号；上线后停止质量评估的团队在 30～60 天内必然出现质量退化 | 监控面板一片绿，用户投诉持续上升 |
| Trace 不覆盖模型与工具 span | 缺 generation 与 tool span 时，一次失败无法定位到是模型、检索还是工具，归因成功率接近 0 | 问题只能描述为「AI 有时候不太行」 |
| 成本不进 SLO | 成本是长尾分布，失控案例可比中位数高 2～3 个数量级；只看均值时异常任务完全不可见 | 月底账单超支，而所有监控指标都在阈值内 |

> 本页的做法：把质量与成本加为第四、第五类信号，并按 gen_ai 语义约定给 span 打标。

### 线上可观测性的四个词

生产上的 AI 质量问题，能不能被发现完全取决于采集了什么。

| 术语 | 一句话解释 |
| --- | --- |
| 脱敏 Trace | 移除敏感信息但保留结构的运行记录 |
| 质量回流 | 把生产样本回流到评测集的机制 |
| 托管模型盲区 | 供应商内部不可见的部分；它必须被显式标注为未知 |
| SLO 链 | 从用户体验指标到具体组件指标的连接 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[open-telemetry/opentelemetry-specification](https://opentelemetry.io/docs/specs/otel/)*

### 模型调用为什么不该另建一套观测体系

可观测性的价值来自关联，不来自记录量。一次用户请求横跨网关、服务、数据库、队列和模型调用，只有当这些环节共享同一个 trace context 时，你才能回答「这一次为什么慢、为什么错」。任何独立记录、无法与主链路关联的日志，在归因的那一刻等于不存在。

这正是把 LLM 调用接进既有 trace 而不是单独建表的原因。语义约定已经把模型标识、token 用量、请求参数、结束原因纳入与 HTTP、数据库同一套命名体系——这意味着模型调用是链路上的一个 span，不是另一个世界，也不需要另一套查询方式和另一批人来看。

分开建体系的代价只在事故时显现：你有一份 AI 平台的调用记录，有一条 APM 的链路，两边时间戳对不上、请求 ID 不通，于是只能靠人眼拼。这类成本不体现在建设期，全部集中在最不该有额外成本的时刻——这是本页最值得提前决策的一件事。

但接入了也不等于可归因。采样率过低、span 属性缺失、上下文在异步边界断掉，都会让链路恰好在最需要的地方断开。因此可观测性的验收判据不能写成「已接入 OpenTelemetry」，而要写成「可完整追溯的调用比例」——后者是一个能测出来、能设阈值、能持续回归的数字。

### 可观测性在 AI 系统上变成了什么

三件套的骨架没有变化，变化的是 span 的语义、信号的种类，以及一个新的现实：托管模型的内部对你是不可见的。

最后这一点决定了 AI 可观测性的边界——有些问题你只能观测到症状，观测不到原因，这个边界必须被写进设计而不是被反复撞上。

| 传统做法 | 在 AI 系统里为什么不够用 | 融合后的新做法 |
| --- | --- | --- |
| Trace 记录服务间调用 | AI 系统的关键耗时与失败发生在模型生成、检索、工具调用内部，而这些在传统 span 划分里是一次普通的出站调用 | 按 gen_ai 语义约定划分 span：generation、tool、retrieval 各自成 span，并记录 token 数与模型版本 |
| 指标覆盖延迟、错误率、吞吐 | 质量漂移不改变这三类指标中的任何一个，它是一类完全独立的信号，且只能通过评估而不是计数得到 | 把在线质量评分作为第四类信号，用与开发阶段相同的评估器给采样流量打分 |
| 日志用于事后排查 | AI 系统的日志包含用户输入与模型输出，直接落盘会带来数据合规问题，而不落盘又无法归因 | 日志分级脱敏后落盘，敏感字段用不可逆方式处理；原始内容只在隔离区短期保留 |
| 异常通过错误率告警 | Agent 的失控形态是持续正常工作但不收敛，错误率不变而成本飙升，传统告警完全静默 | 成本进入 SLO 并设多窗口 burn-rate 告警，步数与耗时超限单独告警 |

> 左列不是要被淘汰的东西，右列也不是新工具清单。真正变化的是中间那一列——被测对象的性质变了，于是同一个目的需要换一种达成方式。

*依据：[open-telemetry/semantic-conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/) · [langfuse/langfuse](https://langfuse.com/docs)*

### 这些地基不变

下面这些不因为被测对象换成 AI 系统而失效。它们是上面那张表里「融合后的新做法」能够成立的前提——地基塌了，新做法只是换了个说法的空话。

- Trace 完整性：一次请求的所有 span 必须能拼成完整链路，缺一段即不可归因
- 脱敏在落盘之前完成，不能依赖下游消费方自觉
- SLO 与错误预算：先定义什么算好，再谈告警
- 告警要指向 runbook，无处置动作的告警最终会被忽略

### 四类信号一条链路：各自负责什么

这张表的排列本身就是本页的主张：模型调用和 HTTP、数据库并列在同一张表里，而不是单起一节。

第四行是唯一的 AI 专属组件，注意它的定位是样本回流而不是判断——它记录得再全，评测器不可信时结论依然不可信。

| 信号 | 工具 | 它负责什么 | 边界 |
| --- | --- | --- | --- |
| 链路 | OpenTelemetry Specification | 统一 trace / metric / log 的数据模型与上下文传播机制，使跨服务、跨语言归因成为可能 | 接入不等于可归因；采样与断链会让链路恰好在最需要的地方断开 |
| 模型调用属性 | OTel GenAI 语义约定 | 把模型标识、token 用量、请求参数、结束原因纳入与 HTTP、数据库同一套语义命名体系 | 该部分约定仍在演进，字段名可能变更；且它只规定怎么记，不规定记完怎么判断质量 |
| 指标 | Prometheus | 直方图与分位数的正确计算与聚合，避免跨实例平均分位这类在数学上就不成立的报表 | 聚合信号回答不了单次失败发生了什么 |
| 模型侧样本回流 | Langfuse | 把模型调用的输入输出、成本、延迟与评分持久化为可检索 trace，使线上样本回流成为常规动作而非一次性导出 | 记录不等于判断；平台里的 score 仍来自你配置的评测器，评测器本身的可信度要单独证明 |
| 判据框架 | Google SRE Workbook | SLI / SLO / 错误预算，把「接了监控」变成「达没达到目标」这种可判定陈述 | 示例阈值是示例，不是你的阈值 |

> 五行共用同一个 trace context，这是整页的核心结论：AI 时代的可观测性不是新增一个体系，而是让既有体系覆盖新的 span 类型。

*依据：[open-telemetry/opentelemetry-specification](https://opentelemetry.io/docs/specs/otel/) · [open-telemetry/semantic-conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/) · [prometheus/prometheus](https://prometheus.io/docs/practices/histograms/) · [langfuse/langfuse](https://langfuse.com/docs) · [Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)*

### 这张图的 7 个节点，本页各交付什么

这张图从用户请求走到发布门禁，中段的三个节点是三类信号的采集点，右侧两个节点是它们的用途：告警与回归。

「回归集与发布门禁」这个终点很重要：可观测性的产物不该只是告警，还应该是回归用例——线上发现的问题要变成不会复发的测试。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 用户请求/风险切片 | 按风险切片采样，保证高风险场景的观测密度足够 | 采样策略与切片定义 |
| Gateway 与 Trace | 在入口建立 trace 根，保证全链路可拼接 | trace 根与传播规范 |
| 模型/检索/工具 Span | 按 gen_ai 语义约定划分 span 并记录 token 与版本 | span 语义规范 |
| 日志与指标 | 分级脱敏后落盘，敏感字段不可逆处理 | 脱敏规则与验证 |
| 质量/成本评测 | 用与开发阶段相同的评估器给线上采样打分 | 在线质量与成本信号 |
| 告警与版本冻结 | 多窗口 burn-rate 告警，触发后先冻结版本 | 告警规则与冻结流程 |
| 回归集与发布门禁 | 线上问题固化为回归用例后事件才关闭 | 线上问题回归闭环 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 四类信号各自能回答什么

四类信号覆盖不同的问题。缺任何一类，对应的问题在生产上就无法回答。

右列写的是缺这类信号时无法回答的问题。

| 信号 | 回答什么 | 缺失时无法回答 |
| --- | --- | --- |
| Trace | 这次调用发生了什么 | 失败在哪一步 |
| 指标 | 整体趋势如何 | 什么时候开始变差 |
| 日志 | 具体错误信息 | 为什么失败 |
| 质量回流 | 生产上的答案对不对 | 线上质量到底如何 |

> 第四类最常缺失：多数系统监控了性能与错误率，但从不知道线上回答的质量如何。

*依据：[open-telemetry/opentelemetry-specification](https://opentelemetry.io/docs/specs/otel/)*

### 这一页的验收口径：五类信号与可归因率

PS11-2 的可归因率是本页最有价值的一条：它直接衡量「出问题时能不能找到原因」，而这决定了修复速度。

PS11-4 明确要求承认不可见边界——托管模型的内部无法观测，把这一点写进报告比假装能观测更有用。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| PS11-1 | Trace 完整性 | trace 完整率 = 100%；缺 generation 或 tool span 的调用数 = 0 | 每日 |
| PS11-2 | 失败可归因 | 线上失败可定位到模型 / 检索 / 工具 / 编排之一的比例 ≥ 80%，其余标记 UNKNOWN | 每周 1 次 |
| PS11-3 | 质量与成本信号 | 在线质量采样覆盖率 ≥ 1% 且高风险动作 = 100%；成本 p99 纳入 SLO | 持续 |
| PS11-4 | 脱敏合规 | 落盘日志中未脱敏敏感字段数 = 0 | 持续 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

*依据：[Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)*

### 两种看起来可观测性完善、实际发现不了质量问题的做法

这两种做法都建立了完整的监控体系，也确实能发现故障。

问题是它们发现不了 AI 特有的质量退化。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 监控错误率与延迟，两者正常即认为服务健康 | 这是服务监控的标准做法，也确实覆盖了可用性 | AI 服务在质量下降时错误率和延迟都可能完全正常。回答变差不会产生 5xx，必须专门做质量采样 |
| 用托管模型时，供应商的指标面板就够了 | 供应商的数据更接近模型内部，也更权威 | 供应商面板只覆盖它自己那一段，看不到你的检索、工具与业务链路。而且模型内部的部分对你是盲区，必须显式标注为未知 |

> 两条的共同修法：补质量采样，并把托管模型的盲区显式记录下来。

### 生产质量问题被用户先发现时按什么顺序查

用户先发现说明监控没有覆盖质量维度。按下表逐项补齐。

补齐顺序按成本从低到高；任何不可见字段都保持 UNKNOWN。

| 症状/缺口 | 先怀疑 | 下一步检查 |
| --- | --- | --- |
| 只有错误率与延迟 | 无质量采样 | 按风险切片抽样并自动打分 |
| 关键失败没有 Trace | 采样或传播缺口 | 检查 root、tool、terminal 覆盖与高危全量记录 |
| Judge 稳定但正确率下降 | 检索版本或输入分布 | 按 slice 对比 retrieval_ids、输入长度和知识库版本 |
| 成本突然升高 | 重试或上下文变长 | 按 task 对账 token、attempt、prompt_hash 与工具路径 |
| 问题无法进入评测集 | 无质量回流 | 建立脱敏生产样本回流并记录人工判定 |
| 把托管模型盲区当正常 | 未标注 UNKNOWN | 列出不可见 GPU/内部分数并冻结推断 |

> 诊断先补证据完整性，再讨论模型或业务原因；未知不能被补写成正常。

### 给生产加一条最小质量采样链：约 60 分钟

最小可行的质量监控只需要三步，不需要完整的评测平台。

1. 选一个高风险切片，按固定比例抽取生产样本。
2. 用与开发阶段相同的评估器给这些样本打分，确保口径一致。
3. 设定一个基线：上线时的分数分布，作为后续对比的参照。
4. 把明显低分的样本回流到评测集，作为下一轮回归的输入。
5. 显式列出托管模型中你看不到的部分，标注为已知盲区。

**期望结果**：上线后第一周通常就能看到分数分布的波动，其中一部分是此前完全不知道的质量问题。

> ⚠ 采样要脱敏后再打分。把含敏感信息的生产样本发给外部评估模型，是常见的数据外发事故。

### 这一页的出口判据

这一页的门禁保证的是「出问题时你能看见」。它不改善质量，但没有它，其余所有质量工作都失去了运行时的反馈来源。

第三段要接受的是不可见边界：托管模型内部、第三方工具内部都无法观测，这部分只能靠输入输出推断。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 落盘日志中未脱敏敏感字段数 > 0 时阻断，并按数据事件流程上报<br>trace 完整率 < 100% 时阻断发布，缺失链路无法支撑归因 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 可归因率按 95% CI 下界与阈值比较；样本 < 100 起失败时结论记为证据不足<br>在线质量信号与离线评估的一致性定期比对，偏离超出区间时先校准评估器 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 托管模型与第三方工具的不可观测范围，由架构 owner 列出并签字接受<br>采样率与观测成本的取舍，由 SRE 与测试负责人共同确定并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一条最小质量采样链

三步：抽样、用同一评估器打分、与上线基线对比。它比完整的评测平台便宜得多，但能发现的问题不少。

盲区清单同样重要：它把「不知道」和「没问题」区分开。

- 线上采样用与开发阶段相同的评估器
- 高危动作 100% 记录 trace，不采样
- 显式列出托管模型的盲区，不当成正常

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)** — 判据框架
  - 能证明：SLI/SLO/错误预算的定义方式，以及为什么用分位而非均值、为什么阈值必须来自业务而非工具默认值。性能与稳定性两页的验收口径都建立在这套框架上。
  - 不能证明：书里的示例数字是示例。任何直接照抄的 SLO 都没有经过你自己业务成本的校准。
  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理
- **[OpenTelemetry Specification](https://opentelemetry.io/docs/specs/otel/)** — 可观测性协议
  - 能证明：trace / metric / log 三类信号的统一数据模型与上下文传播机制。跨服务、跨语言归因之所以可能，依赖的是同一个 trace context 而不是同一个日志格式。
  - 不能证明：接入 OTel 不等于可归因。采样率、缺失的 span 属性、断掉的上下文传播都会让链路在最需要的时候断在中间。
