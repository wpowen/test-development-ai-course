## TD-PS07

### iOS 的老问题是权限、签名与状态残留，端侧模型让隐私边界第一次进入测试范围

改期预约这类流程本来就要处理系统权限与状态清理。加入端侧推理后，多了一个此前不必回答的问题：这次推理用到的数据去了哪里。

下面三条把老问题和新问题接在一起。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 用例之间不清理状态 | iOS 模拟器的钥匙串与 UserDefaults 跨用例保留，残留导致的假通过在无清理策略时占比不为 0 | 单跑通过、全量跑失败，被当成「测试不稳定」而不是状态污染 |
| 只在模拟器上验证 | 签名、真机权限弹窗、后台限制这 3 类行为在模拟器上与真机不一致，模拟器对它们的覆盖率为 0 | 模拟器全绿，上架审核或真机首启即失败 |
| 端侧推理的数据流向未被断言 | 隐私声明写了「数据不离开设备」，而验证它的测试数为 0 时，这句话没有任何证据支撑 | 把隐私承诺当成已实现的事实，而它只是一份文档 |

> 本页的做法：状态清理做成前置条件而非收尾动作，隐私声明变成可断言的网络行为。

### iOS 自动化的四个词

iOS 的特殊性集中在可访问性标识、系统权限弹窗与状态残留。

| 术语 | 一句话解释 |
| --- | --- |
| 可访问性标识 | 用于定位元素的稳定标识；它需要开发侧显式设置 |
| 系统权限弹窗 | 由系统而非应用弹出的对话框；它不在应用视图层级里 |
| 动画同步 | 等待动画结束再操作；提前操作会导致点击落空 |
| 状态残留 | 上次运行留下的登录态、缓存与权限设置 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[XCUITest：iOS 用户界面测试](https://developer.apple.com/documentation/xctest/user_interface_tests)*

### 可访问性标识为什么是 iOS 稳定定位的唯一可靠锚点

XCUITest 通过可访问性层看应用：它拿到的不是完整视图层级，而是被暴露为 accessibility element 的那一部分。因此定位稳不稳，取决于开发有没有给关键控件设置 accessibilityIdentifier——这是一件测试侧无法单方面解决的事。

用可见文案定位是最常见的替代做法，也是最脆的：文案会因本地化、A/B 实验和产品文案调整而变，而这些变化并不代表功能回归。identifier 与展示文案解耦，因此它一旦失效就一定意味着结构真的变了——和 Web 侧语义定位器的逻辑完全一致。

元素查询是惰性求值的：query 本身不触发查找，直到访问属性或执行动作时才解析，配合 expectation 完成等待。理解这一点才能解释一个高频困惑——提前把 element 存进变量、稍后再用，经常拿到的是过期引用。

但真正让 iOS 用例不稳的通常不在这一层：签名与证书过期、系统权限弹窗、键盘遮挡、上一条用例残留的登录态与本地缓存。这些在官方文档里几乎没有位置，却占了实际失败的大头。所以 iOS 专项的重点是环境与状态治理，不是定位语法——这一条与直觉相反，但它决定了投入该往哪放。

### iOS 自动化在含端侧推理的应用上变成了什么

iOS 测试的既有关注点——可访问性标识、系统权限、签名、动画同步、状态残留——一条都没有减少。端侧模型增加的是隐私边界这一维。

这一维之所以落在测试身上，是因为它是唯一能把「我们不上传数据」从声明变成证据的环节。

| 传统做法 | 在 AI 系统里为什么不够用 | 融合后的新做法 |
| --- | --- | --- |
| 用可访问性标识定位控件 | 生成内容区的可访问标识可能由模型产出，它既是定位依据又是被测输出，二者混在一起会让定位失败与内容错误无法区分 | 定位只使用开发者显式设置的静态标识；模型产出的可访问名称转为断言对象，不作为定位依据 |
| 等待动画结束后再断言 | 流式生成期间界面持续更新，没有传统意义上的「动画结束」时刻，等待条件失去锚点 | 以流结束事件与业务状态写入作为同步锚点，界面稳定性单独作为呈现层指标观测 |
| 权限测试覆盖授予与拒绝 | 端侧推理可能访问照片、麦克风、健康数据；权限被拒时若改走云端，隐私声明即被破坏，而功能表现完全正常 | 为每项 AI 功能断言权限缺失下的降级路径，并用网络层断言证明没有替代性的云端上传 |
| 用模拟器覆盖主要回归 | 端侧推理的性能与内存表现依赖真机芯片，模拟器跑的是完全不同的执行路径，其耗时数据没有参考价值 | 功能回归留在模拟器，推理耗时与内存必须在真机矩阵上取数，并按芯片档位分层报告 |

> 左列不是要被淘汰的东西，右列也不是新工具清单。真正变化的是中间那一列——被测对象的性质变了，于是同一个目的需要换一种达成方式。

*依据：[XCUITest：iOS 用户界面测试](https://developer.apple.com/documentation/xctest/user_interface_tests) · [appium/appium](https://appium.io/docs/en/latest/)*

### 这些地基不变

下面这些不因为被测对象换成 AI 系统而失效。它们是上面那张表里「融合后的新做法」能够成立的前提——地基塌了，新做法只是换了个说法的空话。

- 状态清理是前置条件：每条用例开始前重置钥匙串、UserDefaults 与文件沙箱
- 权限四态全覆盖：未询问、已授予、已拒绝、运行时撤销
- 签名与配置文件问题只在真机暴露，不能靠模拟器代替
- 可访问性标识由开发显式提供，不依赖界面文案

### iOS 这一层实际用什么，瓶颈在哪

前三行是执行与协议，第四行不是工具而是这一页真正的瓶颈：状态复位。多数 iOS 用例的不稳定发生在第四行，而团队的注意力往往全在前三行。

选 XCUITest 还是 Appium 是个真实取舍：前者与构建链集成最紧、能力最全，后者用一套客户端代码覆盖两个平台。两者的等待与手势语义并不等价。

| 能力 | 工具 | 它负责什么 | 边界 |
| --- | --- | --- | --- |
| 原生 UI 测试 | XCUITest | 通过可访问性层暴露元素、惰性查询、expectation 等待，与 Xcode 构建与真机调度集成最紧密 | 只能测自己签名的应用；跨应用与系统层能力受限 |
| 跨平台驱动 | Appium | 以 W3C WebDriver 封装 XCUITest，使同一套客户端代码可同时覆盖 iOS 与 Android | 跨平台的是 API 不是行为；等待、权限与手势语义两端都不同，必须分别验证 |
| 协议边界 | W3C WebDriver | 界定标准命令与厂商扩展，决定用例的可移植性与迁移成本 | 扩展能力不保证跨实现可用或长期稳定 |
| 状态与环境复位 | 签名 / 权限 / 缓存治理 | 登录态、系统权限、本地缓存与键盘状态的复位——这是 iOS 用例稳定性的实际瓶颈 | 模拟器与真机在权限、性能、相机与推送等能力上不等价，结论不可互相外推 |

> 第四行没有一个现成工具能包办，这恰恰是它值得单独占一行的原因：它需要在应用里留出可复位入口，是工程约定不是工具选型。

*依据：[XCUITest：iOS 用户界面测试](https://developer.apple.com/documentation/xctest/user_interface_tests) · [appium/appium](https://appium.io/docs/en/latest/) · [WebDriver（W3C 推荐标准）](https://www.w3.org/TR/webdriver2/)*

### 四类 iOS 特有问题与处理

这四类在 iOS 上尤其突出，处理方式与 Android 也不完全相同。

右列是可执行的处理方式。

| 问题 | 表现 | 处理 |
| --- | --- | --- |
| 缺可访问性标识 | 只能靠文案定位，改文案就失败 | 要求开发侧显式设置标识 |
| 系统权限弹窗 | 脚本找不到该元素 | 用系统级交互接口处理 |
| 动画未结束 | 点击落空或点错 | 等待动画完成而非固定延时 |
| 状态残留 | 第二次运行行为不同 | 每次运行前重置应用状态 |
| 模拟器与真机差异 | 模拟器通过真机失败 | 声明各自的验证范围 |

> 第一行需要开发配合。没有可访问性标识时，UI 测试的维护成本会随每次文案调整持续上升。

### 这一页的验收口径：状态、权限、隐私、耗时

PS07-3 是本页唯一的新增判据，也是最值得建立的一条：它把隐私声明变成了一个可以被网络层证伪的断言。

PS07-4 要求按芯片档位分层，理由与 Android 相同：整体均值会把老机型的体验完全掩盖。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| PS07-1 | 状态隔离 | 用例乱序执行的通过率与顺序执行一致，差异 = 0 | 每次运行 |
| PS07-2 | 权限四态 | 四种权限状态的覆盖率 = 100%；权限缺失下崩溃次数 = 0 | 每次发布 |
| PS07-3 | 隐私边界 | 端侧推理场景下向外部域发起的请求数 = 0（网络层断言） | 每次发布 |
| PS07-4 | 真机推理耗时 | 按芯片档位分层，最低档位首 token 延迟 p95 ≤ 3 秒；禁止只报整体均值 | 每次模型变更 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在做 iOS 测试、实际不可维护的做法

这两种做法在项目初期都能快速产出测试，进度也很好看。

问题是维护成本会随时间迅速上升。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 用界面上显示的文案作为元素定位依据 | 不需要开发配合，实现快，可读性也好 | 文案会随产品迭代和国际化不断变化。每次文案调整都会导致大批测试失败，且失败原因与业务无关 |
| 在模拟器上跑通全部用例即视为通过 | 模拟器稳定、快速、可并行，覆盖也完整 | 模拟器不涉及真实的签名、推送、相机、传感器与性能特征。这些差异不是边缘情况，而是移动应用的核心能力 |

> 两条的共同修法：要求可访问性标识，并显式声明模拟器与真机各自验证了什么。

### iOS 测试不稳定时按什么顺序查

按下表逐项排除。第一行和第四行是最常见的两类。

注意区分「测试问题」与「应用问题」。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 点击没生效 | 动画未结束 | 改为等待动画完成 |
| 找不到元素 | 定位依赖文案 | 改用可访问性标识 |
| 系统弹窗卡住流程 | 未处理系统级对话框 | 用系统交互接口处理 |
| 第二次运行行为不同 | 状态残留 | 每次运行前重置应用 |
| 真机上失败 | 模拟器差异 | 在真机上单独验证并记录 |

> 第四行的处理很简单但常被忽略：每次运行前重置，比在测试里到处清理更可靠。

*依据：[appium/appium](https://appium.io/docs/en/latest/)*

### 处理状态残留与系统弹窗：约 50 分钟

两项都是一次性投入，做好之后能消除大部分偶发失败。

1. 连续运行同一个测试两次，比较两次行为是否一致；不一致即存在状态残留。
2. 在测试启动前加入应用状态重置，重新连续运行两次验证。
3. 找出流程中会触发系统权限弹窗的位置，确认脚本能通过系统级接口处理它。
4. 把所有依赖文案的定位改为可访问性标识，缺标识的提交给开发侧补。
5. 分别在模拟器与真机上跑一遍，记录两者结果差异。

**期望结果**：处理完状态残留后，连续运行的一致性通常会显著改善。真机与模拟器的差异记录会成为证据边界的一部分。

> ⚠ 证据边界必须写清：模拟器验证不能声称为真机验证。签名、推送、相机等能力只有真机能验证。

### 这一页的出口判据

这一页的红线里有一条是隐私性质的：声明数据不出设备时，网络层必须能证明这一点。声明与证据不一致属于合规问题，不参与权衡。

第三段要接受的是真机矩阵成本：真机测试昂贵，覆盖到哪个档位是资源决策。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 端侧推理场景下向外部域发起的请求数 > 0 时阻断<br>权限缺失导致崩溃的次数 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 推理耗时按芯片档位给出 95% 分位，禁止用整体均值代替分层结论<br>单档位真机样本 < 30 次时该档位结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 真机矩阵覆盖的档位范围与成本，由测试负责人签字确定<br>老机型上已知的体验差距，由产品 owner 在知情前提下接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Appium：基于 W3C WebDriver 的跨平台移动自动化](https://appium.io/docs/en/latest/)** — 移动专项工具

  - 不能证明：跨平台的是客户端 API，不是行为。同一段脚本在两个平台上的等待、权限与手势语义都不同，必须分别验证。
  - `appium/appium` · 版本 appium@3.6.0（2026-07-25） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[WebDriver（W3C 推荐标准）](https://www.w3.org/TR/webdriver2/)** — 协议边界
  - 能证明：浏览器与移动自动化共同依赖的协议命令集与错误模型。理解它才能判断某个能力是标准行为还是某个 driver 的扩展。
  - 不能证明：标准之外的厂商扩展不保证跨实现可用，也不保证长期稳定。
  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理
- **[XCUITest：iOS 用户界面测试](https://developer.apple.com/documentation/xctest/user_interface_tests)** — 机理说明

  - 不能证明：文档描述 API 行为，不覆盖签名、权限弹窗、系统对话框与状态残留这些真实工程中最常见的失败源。
  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理
