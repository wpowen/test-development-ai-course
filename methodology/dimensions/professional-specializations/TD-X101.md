## TD-X101

### 供应链门禁挡住了依赖包，没挡住工具描述——而后者现在直接进模型上下文

SBOM、provenance、签名、扫描这套供应链纪律是为代码依赖建立的。Agent 引入了一类新的外部组件：MCP server 与工具，它们的描述会进入上下文并影响模型行为，却不在任何 SBOM 里。

下面三条说明这个盲区。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 工具与 MCP server 不纳入 SBOM | 工具描述直接进上下文并影响模型决策，其影响力不低于一个代码依赖，而它在 SBOM 中的覆盖率通常为 0 | 供应链治理「已覆盖全部依赖」，而影响模型行为的那部分完全在管控之外 |
| 工具描述只在连接时审一次 | 连接后描述被修改（rug-pull）在缺 hash 校验时的检出率 = 0；这正是工具投毒的主要利用路径 | 首次接入评审通过，此后的任何变更都不再被看见 |
| AI 生成代码绕过依赖门禁 | 生成代码引入的依赖若不过同一道门禁，供应链缺口的引入速度随生成量线性上升；1 个未审依赖就足以让整条 SBOM 失去意义 | 把 AI 提效当成纯收益，而它同时提高了引入未审依赖的速率 |

> 本页的做法：工具清单 hash 进 SBOM，rug-pull 做成持续检测，AI 生成代码走同一道门禁。

### 供应链门禁的四个词

代码之外的风险：依赖、构建产物与它们的来源证明。

| 术语 | 一句话解释 |
| --- | --- |
| SBOM | 软件物料清单；它列出构建产物里包含了什么 |
| provenance | 构建来源证明；它说明这个产物是由谁、用什么源码、在哪构建的 |
| 签名 | 对产物的密码学签名；它防止产物在传输中被替换 |
| 例外 owner | 扫描发现被豁免时的责任人；无 owner 的例外等于无人负责 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[anchore/syft](https://github.com/anchore/syft#readme)*

### 静态门禁的价值来自左移，代价来自误报

静态分析的独特价值是它不需要运行系统：在代码合并之前就能给出结论，因此单次发现的修复成本最低。这是它值得占一个门禁位的唯一理由——如果它的结论要等到发布前才可用，那这个位置应该让给测试。

但静态门禁有一个特有的失败模式：误报会导致整条门禁被关掉。一个天天红、且大部分红是噪声的检查，最终一定会被加白名单、被跳过、或者干脆从流水线里删掉——而删掉之后，它原本能拦下的真问题也一起没了。所以静态门禁的设计目标不是「发现最多」，是「发现的每一条都值得修」。

两类工具的取舍正来自这里。模式匹配型贴近源码语法，误报低、易于表达团队专属约定，但看不到跨函数的数据流；污点追踪型能发现跨文件的注入路径，代价是需要可编译视图、分析慢、对动态特性无能为力。它们不是替代关系，覆盖的是不同缺陷类别——同时用两个不是浪费，是分工。

供应链侧的同一个问题更尖锐：漏洞库按版本区间匹配，会报出大量「存在但不可达」的问题。可利用性判断必须进入流程，否则门禁会被噪声淹没然后被整体关掉。相比之下 SBOM 的价值更稳定——它让「这次发布里到底装了什么」成为可存档、可比对的工件；事后追溯时，它比任何一份扫描报告都值钱。

### 供应链与静态门禁在 AI 工程上变成了什么

这一项的方法论完全不需要重建：SBOM、provenance、签名、例外 owner 这套机制适用于任何外部组件。需要做的只是把「外部组件」的定义扩大。

同时 AI 也在反方向增加压力：生成代码提高了依赖引入速率，门禁必须跟上这个速率而不是成为瓶颈。

| 传统做法 | 在 AI 系统里为什么不够用 | 融合后的新做法 |
| --- | --- | --- |
| SBOM 覆盖代码依赖 | MCP server、工具定义、提示模板、模型端点都是能改变系统行为的外部输入，却不在依赖清单里，因此不受任何门禁约束 | 扩展 SBOM 定义：工具清单及其描述 hash、模型端点版本、外部提示模板一并纳入并版本化 |
| 依赖引入时做一次安全评审 | 工具描述可在连接后被修改，一次性评审对这类变更的检出率为 0；模型端点也可能被供应商静默更新 | 把一次性评审改为持续校验：工具描述 hash 每次连接比对，模型端点每周跑哨兵集检测漂移 |
| 静态扫描发现代码缺陷 | AI 生成代码的缺陷模式与人写代码不同，且生成速率远高于评审速率，扫描规则与人力都会成为瓶颈 | 生成代码强制走同一道门禁且不豁免；同时统计生成代码的门禁拦截率，用它衡量生成质量 |
| 例外由 owner 审批后长期存在 | 长期例外会让门禁逐渐空心化，而 AI 提高了申请例外的频率，空心化速度随之加快 | 所有例外强制带到期时间，到期自动失效并重新申请；无到期时间的例外数量必须为 0 |

> 左列不是要被淘汰的东西，右列也不是新工具清单。真正变化的是中间那一列——被测对象的性质变了，于是同一个目的需要换一种达成方式。

*依据：[semgrep/semgrep](https://semgrep.dev/docs/) · [google/osv-scanner](https://google.github.io/osv-scanner/)*

### 这些地基不变

下面这些不因为被测对象换成 AI 系统而失效。它们是上面那张表里「融合后的新做法」能够成立的前提——地基塌了，新做法只是换了个说法的空话。

- 信任边界要画出来：哪些东西来自外部、由谁负责，是一切供应链治理的前提
- 签名与来源证明：知道这个东西是谁构建的、有没有被改过
- 例外必须具名且有期限：无 owner 无期限的例外等于把门禁关掉
- 门禁以非零退出码阻断：不阻断的检查只是一份报告

### 六类门禁各自拦什么，各自会误报什么

前两行是代码侧，中间三行是依赖与制品侧，最后一行是构建过程本身。六行覆盖的是同一条链上的不同位置，不是六个可替换的选项。

每一行的边界列都指向同一个风险：误报会让门禁被关掉。设计这一层时，「这条规则误报了怎么办」和「这条规则能发现什么」同样重要。

| 门禁类型 | 工具 | 它负责什么 | 边界 |
| --- | --- | --- | --- |
| 模式化规则 | Semgrep | 以贴近源码的语法模式表达团队专属约定：禁用某 API、必须带超时、密钥不得硬编码——这类规则别的工具写不出来 | 没有完整数据流理解，跨文件跨函数的污点传播会漏；低误报是靠限制规则范围换来的 |
| 污点追踪 | CodeQL | 把源码编译成关系数据库后用查询语言表达 source → sink 可达性，发现跨函数、跨文件的注入路径 | 依赖可编译视图；动态特性、反射与运行时配置之外的路径不可见 |
| 依赖漏洞 | OSV-Scanner | 以统一漏洞数据库为源，按锁文件精确匹配受影响版本区间，减少按包名粗匹配造成的误报 | 报出漏洞不等于可利用；不做可达性判断，门禁会被噪声淹没 |
| 成分清单 | Syft | 从镜像与文件系统生成 SPDX / CycloneDX SBOM，使「这次发布里装了什么」成为可存档、可比对的工件 | 描述成分不描述风险，也不保证完整——静态链接与运行时下载的内容可能不在清单里 |
| 统一扫描 | Trivy | 把依赖漏洞、IaC 配置错误、密钥泄露与 SBOM 生成收敛到一处执行、一份报告，降低流水线复杂度 | 覆盖广度以深度为代价，每一类的判定精度都不如该领域的专用工具 |
| 构建完整性 | SLSA | 把供应链安全从含糊目标变成可声明的等级：来源可证明、构建过程可复现、防篡改 | 评价的是构建过程可信度，不评价依赖本身有没有漏洞 |

> 六行里只有第四行的产物在事故之后仍然有用。扫描结论会随漏洞库更新而变化，SBOM 是那一刻的事实快照——这是它值得单独存档的原因。

*依据：[semgrep/semgrep](https://semgrep.dev/docs/) · [github/codeql](https://codeql.github.com/docs/) · [google/osv-scanner](https://google.github.io/osv-scanner/) · [anchore/syft](https://github.com/anchore/syft#readme) · [aquasecurity/trivy](https://trivy.dev/latest/docs/) · [slsa-framework/slsa](https://slsa.dev/spec/v1.0/levels)*

### 五道静态门禁各自拦什么

这五道都在代码合并前执行，成本低且确定性高。

右列写的是这道门禁缺失时会放进来的风险。

| 门禁 | 检查什么 | 缺失时放进的风险 |
| --- | --- | --- |
| diff 检查 | 改动是否触及敏感路径 | 权限或安全配置被顺手改掉 |
| 架构边界 | 依赖方向是否违规 | 模块间产生循环或越层依赖 |
| SBOM | 依赖清单是否完整 | 不知道产物里有什么 |
| provenance 与签名 | 产物来源是否可证 | 被替换的产物进入发布 |
| 扫描与例外 | 已知漏洞是否被处理 | 漏洞被无声忽略 |

> 最后一道的关键不在扫描本身，而在例外管理：无 owner、无过期时间的例外会永久累积。

*依据：[github/codeql](https://codeql.github.com/docs/)*

### 这一页的验收口径：覆盖、检测、例外治理

X101-1 的 SBOM 覆盖率是本页的核心变更：它把工具与模型端点纳入了原本只管代码的清单。

X101-4 的例外到期治理防止门禁空心化——这是所有门禁体系最常见、也最难察觉的失效方式。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| X101-1 | SBOM 覆盖 | 代码依赖 / 工具清单 / 模型端点三类组件的 SBOM 覆盖率 = 100% | 每次发布 |
| X101-2 | 漂移检测 | 工具描述 hash 校验覆盖率 = 100%；未声明变更放行次数 = 0 | 每次连接 + 每日 |
| X101-3 | 生成代码同规 | AI 生成代码豁免门禁的次数 = 0 | 每次提交 |
| X101-4 | 例外治理 | 无到期时间的例外数量 = 0；到期未处理的例外数量 = 0 | 每周 1 次 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在管供应链、实际管不住的做法

这两种做法都引入了扫描工具，也确实发现了问题。

问题是发现之后的处理机制。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 引入漏洞扫描，高危漏洞阻断合并 | 扫描覆盖全面，阻断也足够严格 | 没有例外流程时，团队会通过降级告警或加白名单绕过。例外必须显式记录、指定 owner 并设过期时间，否则它会变成隐形的永久豁免 |
| 锁定依赖版本，保证构建可复现 | 版本锁定是供应链安全的基础实践 | 锁定版本不等于验证来源。依赖仓库被投毒或产物被替换时，版本号完全一致但内容不同。需要 provenance 与签名验证 |

> 两条的共同修法：例外要有 owner 与过期时间，来源要有可验证的证明。

*依据：[google/osv-scanner](https://google.github.io/osv-scanner/)*

### 供应链问题事后追查时按什么顺序查

按下表逐项核对，多数问题出在记录缺失而不是检查缺失。

记录缺失时，任何追查都只能到猜测为止。

| 问题 | 查什么 | 缺失时 |
| --- | --- | --- |
| 产物里有什么不清楚 | SBOM | 无法评估影响范围 |
| 产物来源不明 | provenance | 无法确认是否被替换 |
| 漏洞为什么没拦 | 例外记录 | 无法追责也无法复盘 |
| 谁批准的例外 | 例外 owner | 无人负责 |
| 例外什么时候到期 | 过期时间 | 永久豁免 |

> 后三行都属于例外管理。它是这一层最容易建立也最容易被忽略的能力。

### 给现有流水线补例外管理：约 45 分钟

扫描通常已经有了，缺的是发现之后的处理机制。

1. 列出当前所有被忽略或加白名单的扫描发现。
2. 为每一条补三项：为什么忽略、谁批准、什么时候复评。
3. 补不出 owner 的条目，说明它是被静默忽略的——这些优先处理。
4. 把例外记录做成有过期时间的结构，到期自动重新阻断。
5. 检查产物是否有 SBOM 与来源证明；没有的列为待补。

**期望结果**：典型结果是白名单里有相当数量的条目补不出 owner 与理由。它们是此前无人负责的风险敞口。

> ⚠ 补 owner 时不要写团队名。例外的责任必须落到具体的人，否则到期时无人处理。

### 这一页的出口判据

这一页的门禁是本模块的收尾：它守的是「进入系统的每一个外部组件都被登记、验证过，并且有人负责」。

第三段要接受的是扫描的假阴性：任何静态工具都有覆盖边界，未发现不等于不存在。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 工具描述未声明变更的放行次数 > 0 时阻断<br>无到期时间的例外数量 > 0 时阻断发布 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 生成代码与人写代码的门禁拦截率分别统计并给出 95% CI，禁止合并报告<br>变更样本 < 50 次时拦截率结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 静态扫描的已知覆盖边界与假阴性风险，由安全 owner 签字接受<br>每一条例外的到期时间与理由，由具名 owner 逐条批准 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[slsa-framework/slsa](https://slsa.dev/spec/v1.0/levels)*

### 带走一份带过期时间的例外台账

台账三列：理由、owner、过期时间。缺任一列的例外应当立即失效。

SBOM 与来源证明是下一步，但例外管理成本更低、见效更快。

- 每条例外记录理由、具名 owner 与过期时间
- 到期自动重新阻断，不靠人记
- 产物补 SBOM 与来源证明，版本锁定不等于来源可信

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Semgrep：模式化静态分析](https://semgrep.dev/docs/)** — 静态门禁工具
  - 能证明：以贴近源码的语法模式表达规则，使团队专属约定（禁用某 API、必须带超时、密钥不得硬编码）能被写成可执行规则并纳入门禁。
  - 不能证明：模式匹配没有完整数据流理解，跨文件跨函数的污点传播会漏。低误报是靠限制规则范围换来的。
  - `semgrep/semgrep` · 版本 v1.173.0（2026-08-13） · LGPL-2.1 · LGPL-2.1：著佐权许可，只链接与转述，不搬代码
- **[CodeQL：把代码当数据库查询的静态分析](https://codeql.github.com/docs/)** — 静态门禁工具
  - 能证明：污点追踪型分析：把源码编译成关系数据库后用查询语言表达 source → sink 的可达性，能发现跨函数、跨文件的注入路径。
