## TD-PS09

### QPS 在 Agent 系统上不再是一个有意义的指标

传统性能测试的分母是请求。Agent 的一次任务可能包含十几次模型调用与工具调用，用请求做分母会得到一个既好看又无用的数字。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 用入口 QPS 衡量容量 | 入口返回 2xx 时任务可能仍在后台执行；用请求做分母的容量结论在生产上通常高估 2～5 倍 | 按压测结论扩容，上线后仍然排队 |
| 按平均输入输出长度压测 | 输出长度是长尾分布，按均值压测时 p99 长上下文带来的显存与延迟压力完全没有出现 | 容量数字漂亮，真实流量下 KV Cache 打满 |
| 只报吞吐不报质量 | 提高并发通常会让质量下降，只报吞吐时这个代价不可见；两者必须联合判定 | 把「吞吐提升 40%」当成纯收益，而成功率同时掉了 6 个点 |

> 本页的口径改变：分母从 request 变成 good task，指标从 QPS 变成 Goodput。

### 性能与容量的四个词

AI 场景的性能测试要同时看质量，否则容量结论没有意义。

| 术语 | 一句话解释 |
| --- | --- |
| 到达率 | 单位时间进入系统的请求数；固定它才能观察排队 |
| 尾延迟 | p95、p99 等高分位；均值在长尾分布下无参考价值 |
| Goodput | 满足 SLO 的成功吞吐；它是容量的正确定义 |
| 单位成功成本 | 每个成功任务的花费；它把性能与经济性连起来 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[grafana/k6](https://grafana.com/docs/k6/latest/) · [Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)*

### 开放模型与封闭模型：固定并发压测为什么会掩盖容量拐点

压测有两种负载模型。封闭模型固定并发用户数：每个虚拟用户发完一个请求，等到响应回来再发下一个。开放模型固定到达率：不管系统响应多慢，都按既定速率往里发。这看起来只是参数选择，实际上决定了结论是否成立。

封闭模型有一个致命的自我保护效应：系统一变慢，虚拟用户就自动发得更慢，到达率随之下降——系统给自己降了压。于是你测到的是一条平缓曲线，看不到真实的容量拐点，也永远复现不了生产上那个最贵的场景：流量不降反升，请求开始排队，延迟指数级恶化。

真实用户是开放模型：用户不会因为你的系统慢就少下单，反而经常因为慢而重复点击。因此容量结论必须用固定到达率压出来，并观察队列长度与尾延迟如何随到达率增长而爆炸。这是压测里最常见也最难在报告上看出来的方法论错误——两种模型产出的图表长得很像。

报告口径要一起纠正。平均延迟会掩盖尾部，而用户感知的卡顿和超时全部发生在尾部；更关键的是分位数在数学上不可加——把多个实例的 p95 求平均得到的数，不是任何东西的 p95。分位必须从原始直方图聚合，不能从已经算好的分位再聚合，否则报表上的每一个 p95 都是错的。

### 性能与容量测试在 Agent 系统上变成了什么

性能测试的方法论——固定负载、逐级加压、找拐点、按分位报告——完全适用。变化的是被测单位与指标定义。

这一项是本模块里迁移幅度最大的：几乎每个指标都需要重新定义分母。

| 传统做法 | 在 AI 系统里为什么不够用 | 融合后的新做法 |
| --- | --- | --- |
| 以 request 为压测单位，报 QPS | 一次 Agent 任务包含多次模型与工具调用，请求数与业务完成量之间没有固定比例，QPS 无法换算成业务容量 | 压测单位改为 task，指标改为 Goodput（单位时间内达到质量标准的完成任务数） |
| 用 p95/p99 端到端延迟描述体验 | 流式响应下用户在首字出现时就开始获得价值，端到端时长与体感延迟脱钩 | 延迟拆成 TTFT（首字）与 TPOT（逐字）分别设阈值，端到端时长只用于容量核算 |
| 按固定请求体压测 | 输入输出长度分布直接决定显存占用与批处理效率，固定长度压测测不出真实瓶颈 | 用生产采样重建长度分布，把 workload 版本化并打 hash，换任一变量视为换了一次实验 |
| 以资源利用率判断容量上限 | GPU 利用率高不等于有效产出高，失败重试同样消耗算力；KV Cache 是新的、传统指标看不见的瓶颈 | 容量拐点以 Goodput 不再上升为准，并用 queue/prefill/decode/KV Cache 分段信号归因 |

> 左列不是要被淘汰的东西，右列也不是新工具清单。真正变化的是中间那一列——被测对象的性质变了，于是同一个目的需要换一种达成方式。

*依据：[grafana/k6](https://grafana.com/docs/k6/latest/) · [prometheus/prometheus](https://prometheus.io/docs/practices/histograms/)*

### 这些地基不变

下面这些不因为被测对象换成 AI 系统而失效。它们是上面那张表里「融合后的新做法」能够成立的前提——地基塌了，新做法只是换了个说法的空话。

- 开放负载与封闭负载要分开：控制到达率与控制并发得到的结论不同，混用会掩盖协调遗漏
- 报分位不报均值：长尾分布下均值没有意义
- 逐级加压找拐点：容量结论必须来自压到失效，而不是压到目标就停
- workload 版本化：不可复现的性能数字不可复用

### 负载建模、执行与聚合口径各由什么承担

这一页的选型不是「用哪个压测工具」，而是「用哪种负载模型」。工具只是模型的执行器，选错模型时工具再好也只会得到一条漂亮但无效的曲线。

第三行常被忽略：压测跑完之后，指标怎么聚合决定了报告可不可信，而这一步的错误比压测本身的错误更难被发现。

| 负载建模 | 工具 | 它负责什么 | 边界 |
| --- | --- | --- | --- |
| 固定到达率（开放模型） | k6 | 以 constant-arrival-rate 表达开放模型，使容量拐点可以被真正观察到，而不是被虚拟用户的自我降压掩盖 | AGPL-3.0，本课程只作为外部工具引用不搬代码；客户端观测也不等于系统真实容量 |
| 带状态的业务流程 | Locust | 用普通 Python 表达带鉴权、带分支、带思考时间的真实流程，而不是只对单个接口打流量 | 脚本表达的是你以为的用户行为；流量画像与生产分布不符时结论整体无效 |
| 指标聚合口径 | Prometheus | 直方图与分位数的正确计算与聚合方式，避免跨实例平均分位这一类数学上就不成立的做法 | 指标是聚合信号，回答不了单次失败发生了什么，归因必须回到 trace |
| 判据框架 | Google SRE Workbook | SLI / SLO / 错误预算的定义方式，以及为什么阈值必须来自业务成本而不是工具默认值 | 书中示例数字是示例；照抄等于跳过了校准这一步 |

> 四行按「先定模型、再选执行器、再定聚合口径、最后定判据」排列。倒着做——先选工具再补判据——是这一页最常见的返工来源。

*依据：[grafana/k6](https://grafana.com/docs/k6/latest/) · [locustio/locust](https://docs.locust.io/en/stable/) · [prometheus/prometheus](https://prometheus.io/docs/practices/histograms/) · [Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)*

### 这张图的 7 个节点，本页各交付什么

这张图从到达率一直画到成本门禁，中段的四个节点对应延迟的四段分解——排队、首字、逐字、工具。归因必须落在其中某一段上。

「质量/Goodput」被放在成本之前，是因为不达质量标准的完成不计入产出，成本核算的分母必须是 good task。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| Workload/到达率 | 用生产采样重建任务类型与长度分布，版本化并打 hash | 版本化 workload |
| 队列与调度 | 测量排队时间，区分排队与执行两类延迟 | 排队指标 |
| Prefill/TTFT | 测量首字延迟，作为用户体感的主指标 | TTFT 分位数据 |
| Decode/TPOT | 测量逐字延迟，作为生成速度指标 | TPOT 分位数据 |
| 工具与检索 | 测量工具调用与检索的耗时占比，常被忽略却占比很高 | 工具耗时分解 |
| 质量/Goodput | 以达到质量标准的完成任务数作为有效产出 | Goodput 曲线 |
| 成本与容量门禁 | 以单位成功成本与容量拐点联合判定 | 容量与成本判定 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 四个维度必须联合观察

单看任一维度都会得出错误结论。四个维度必须在同一次测量中同时采集。

右列写的是只看这一维时的典型误判。

| 维度 | 看什么 | 单看它的误判 |
| --- | --- | --- |
| 吞吐 | 每秒完成数 | 并发上去了但成功率掉了 |
| 尾延迟 | p95/p99 分位 | 均值正常但长尾极差 |
| 质量 | 风险切片成功率 | 性能达标但答案变差 |
| 成本 | 单位成功成本 | 吞吐提升靠的是烧钱 |

> 第三行是 AI 场景特有的：传统性能测试不需要同时看质量，因为传统系统在高负载下只会变慢不会变笨。

*依据：[grafana/k6](https://grafana.com/docs/k6/latest/)*

### 这一页的验收口径：Goodput 与分段延迟

PS09-1 是本页的核心口径变更：容量结论必须以 Goodput 表达，且明确声明质量标准是什么。没有质量标准的吞吐数字不可用。

PS09-4 把成本纳入性能判据，因为在 AI 系统上性能与成本是同一个资源问题的两面。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| PS09-1 | 有效产出 | 容量结论以 Goodput 表达并声明质量标准；以 request QPS 表述的容量结论数 = 0 | 每次容量评估 |
| PS09-2 | 体感延迟 | TTFT 的 p95 < 2 秒；TPOT 的 p95 满足可读速度要求 | 每次发布 |
| PS09-3 | 延迟归因 | 端到端延迟可分解到排队 / prefill / decode / 工具四段的比例 = 100% | 每次评估 |
| PS09-4 | 单位成功成本 | 单个 good task 的成本 p99 ≤ 预算上限；成本变异系数 CV ≤ 0.3 | 每次容量评估 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

*依据：[prometheus/prometheus](https://prometheus.io/docs/practices/histograms/)*

### 两种看起来在测性能、实际结论不可用的做法

这两种做法沿用了传统性能测试的方法，在传统系统上完全正确。

问题是 AI 系统多了一个会随负载变化的维度：质量。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 压出最大 QPS 作为容量上限 | 这是性能测试的标准产出，也有明确数据支撑 | 最大 QPS 点上延迟往往已超 SLO，质量也可能下降。容量应当报满足 SLO 且质量达标的 Goodput |
| 性能测试只关注延迟与吞吐，质量由功能测试负责 | 职责划分清晰，两边各自专业 | AI 系统在高负载下可能降级到更小的模型或缩短输出。这时延迟达标但质量下降，而两边的测试都发现不了 |

> 两条的共同修法：性能测试期间同时采集质量指标，容量定义包含质量约束。

*依据：[Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)*

### 性能达标但用户不满时按什么顺序查

AI 场景的这类问题多半是质量随负载下降，而性能测试没看质量。

按下表逐项排查。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 高峰期回答变差 | 负载下触发了降级 | 压测时同时采集质量指标 |
| 均值正常但投诉多 | 尾延迟未看 | 看 p95/p99 而非均值 |
| 吞吐达标但成本超支 | 靠重试撑起的吞吐 | 看单位成功成本 |
| 压测与生产不符 | 负载模型偏乐观 | 用生产 token 分布重压 |

> 第一行是 AI 性能测试与传统性能测试最大的区别，也是最容易被漏掉的一项。

### 做一次质量与性能联合压测：约 70 分钟

关键是在同一次压测中同时采集四个维度的数据。

1. 用生产采样重建 token 分布，构造贴近真实的负载。
2. 阶梯加压，每级同时记录：吞吐、p95/p99 延迟、风险切片质量、单位成功成本。
3. 找出第一个违反 SLO 的台阶，同时检查该台阶上的质量是否已经下降。
4. 比较「延迟拐点」与「质量拐点」的位置——它们常常不在同一个负载水平。
5. 把容量定义为两个拐点中更靠前的那一个。

**期望结果**：典型结果是质量拐点出现在延迟拐点之前。这意味着按延迟定的容量实际上已经超出了可用范围。

> ⚠ 质量采样要覆盖风险切片。用平均质量作为判据时，高风险切片的下降会被完全掩盖。

### 这一页的出口判据

这一页的门禁拒绝以 request 为单位的容量结论。这不是措辞洁癖：用错分母得到的扩容决策会直接反映在账单和排队上。

第三段要接受的是压测与生产的分布差距——合成 workload 永远不等于真实流量，这个差距要被估计而不是被忽略。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 以 request QPS 表述的容量结论数 > 0 时阻断，须按 Goodput 重述<br>workload 文件的 hash 缺失率 > 0 时阻断；结论不可复现即作废 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 延迟与成本一律报分位，均值不得作为判据<br>单档位压测样本 < 500 个任务时该档位结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 合成 workload 与真实流量分布的已知差距，由容量 owner 估计并签字接受<br>质量标准的取值（即什么样的完成算 good task），由产品 owner 确定并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一个包含质量约束的容量定义

容量 = 满足延迟 SLO 且质量达标的最大负载。两个条件缺一不可。

两个拐点的位置差异是这次压测最有价值的产出。

- 压测时同时采集质量指标，不只测延迟
- 容量取延迟拐点与质量拐点中更靠前的
- 质量采样覆盖风险切片，不用平均值
