## TD-F03

### 一次 PASS 证明不了任何事，而这正是绝大多数评测在做的事

传统软件里，同样输入返回不同结果是 bug；在模型驱动的系统里这是正常行为。把布尔判定套在非确定性系统上，得到的不是宽松的结论，是错误的结论。

下面三条给出一次判定会漏掉什么。第二条的数量级差距是本页存在的全部理由。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 用单次通过率当发布依据 | τ-bench 公开结果中，GPT-4o 在零售 Agent 任务上 pass@1 为 61%，pass^8 仅 25% | 「六成能做对」被读成「六成用户能用」，实际连续 8 次全对的只有四分之一 |
| 只固定 prompt 不测语义等价改写 | 同一意图的 5 个改写变体常常落在不同的解码分支上，一致率低于 95% 时用户会遇到「换个说法就不行」 | 把用户投诉归给「用户不会提问」，而不是系统对表述过敏 |
| 评测不记录 temperature 与随机种子 | 缺这 2 个字段时，同一条用例的重跑结果无法与历史比较，重复运行的全部成本白花 | 看到分数波动就加大样本量，而波动来源是配置没锁 |

> 三条指向同一个改变：本页之后，本课程所有指标都从「一个数」变成「一个分布」。

### 非确定性的四个词

一次 PASS 不够，不是因为运气，是因为这四个机制。

| 术语 | 一句话解释 |
| --- | --- |
| Token 预算 | 输入与输出可用的 token 上限；超出即截断，而截断常常无声 |
| 上下文位置 | 信息在提示中的位置会影响它被使用的程度 |
| 解码配置 | temperature、top_p、seed 等控制采样的参数 |
| 运行波动 | 批处理、缓存、硬件差异带来的输出变化；即使 temperature=0 也存在 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[EleutherAI/lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness#readme)*

### 非确定性从哪来，为什么单次 PASS 不构成证据

同一个输入两次结果不同，来源有四层，可控程度递减：解码采样（temperature / top_p，完全可控）、批处理与并行归约顺序（部分可控，因为浮点加法不满足结合律）、服务端版本与路由（不可控）、上下文长度带来的位置效应（设计上可控）。

把 temperature 设成 0 只消掉第一层。剩下三层意味着即使贪心解码也不保证逐字节一致——这是很多团队第一次做回归对比时最困惑的现象，它不是 bug，也不是配置错误。

因此结论必须建立在分布上而不是单次结果上。pass^k（连续 k 次全对）衡量稳定性，pass@k（k 次中至少一次对）衡量可达性，两者回答的问题方向相反，混用会得到完全相反的发布决策。

样本量决定了你能说什么。n 次运行得到的通过率是一个估计，必须带区间；两个版本的区间重叠时，正确结论是「证据不足」而不是「没有差异」。这两句话导向的行动完全不同：前者是加样本，后者是可以发布了。

*依据：[UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/) · [EleutherAI/lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness#readme)*

### 四层不确定性各自能被压到什么程度

这张表回答一个具体问题：把能固定的都固定之后，还剩多少波动。剩下的那部分是你的噪声底线，所有版本对比都必须显著大于它才成立。

注意第二、三行——它们无法被消除，只能被记录。承认这一点比试图消除它更有用。

| 不确定性来源 | 控制手段 | 能压到什么程度 | 残留 |
| --- | --- | --- | --- |
| 解码采样 | 固定 temperature / top_p / seed | 可完全消除采样带来的差异 | 只覆盖这一层，其余三层不受影响 |
| 批处理与并行归约 | 固定批大小与并发度 | 可显著降低，通常无法消除 | 浮点加法不满足结合律，逐字节一致不可保证 |
| 服务端版本与路由 | 记录模型别名的实际解析结果 | 无法控制，但可以被记录与事后检出 | 托管 API 的权重变更通常不通知，只能靠记录发现 |
| 统计口径 | 重复运行 + 置信区间（harness 内建） | 把单次结果变成可判定的区间结论 | 区间重叠时结论是「证据不足」，不是「无差异」 |

> 前三行决定噪声有多大，第四行决定你怎么在噪声之上说话。跳过第四行，前三行做得再好也只是把噪声测得更准。

*依据：[UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/) · [EleutherAI/lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness#readme) · [open-telemetry/semantic-conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/)*

### 这张图的 7 个节点，本页各交付什么

这张图从左到右是一次推理的真实路径。非确定性不是在某一个节点产生的，它在 Tokenizer、Context 截断、解码策略三处分别引入，且互相放大。

本页的做法是：对每个引入点单独设计边界用例，再用多次运行把三者叠加后的分布测出来。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 原始输入 | 构造语义等价的 5 个改写变体，作为稳定性探针的输入侧 | 改写变体集（每条用例 5 个） |
| Tokenizer | 验证同一文本在换版本后 token 数是否变化，检测计费与截断口径漂移 | tokenizer 版本与 token 数基线 |
| 有限 Context | 设计恰好越界、恰好不越界的边界用例，测截断策略而非模型能力 | Context 边界用例矩阵 |
| 模型 Logits | 标出这一层不可直接观测，说明为什么只能用输出分布反推 | 不可观测边界声明 |
| 解码策略 | 把 temperature、top_p、seed 固定并记录，另跑一组 temperature > 0 的变异性探针 | 解码配置快照 + 变异性探针结果 |
| 多次 Raw outputs | 按 k 次重复保存原始输出，不做任何聚合，聚合放到下一节点 | 重复运行原始记录（raw run ledger） |
| 分布与人工 Gate | 计算 pass@1、pass^k、变异系数，由人判断这个分布能否上线 | 重复运行报告与发布判断 |

> 第一列的节点名与页面架构图逐字一致，由门禁校验；改图必须同步改这张表，否则构建失败。

### 四个机制各自对应的测试手法

这四个机制不能靠「多测几次」覆盖，各有各的构造方式。

右列写的是不测这一项时会漏掉的具体失败。

| 机制 | 测试手法 | 不测会漏掉 |
| --- | --- | --- |
| Token 预算 | 构造接近上限与超限的输入 | 长输入下的静默截断 |
| 上下文位置 | 把关键信息分别放在首、中、尾 | 中段信息被忽略 |
| 解码配置 | 固定参数并单独跑变异性探针 | 参数变化被当成模型能力变化 |
| 运行波动 | 同输入重复 N 次并报告分布 | 把一次好结果当成稳定表现 |

> 第二行最容易被跳过，也最容易在长上下文场景造成事故：关键约束放在中段时被忽略的概率明显更高。

*依据：[UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/)*

### 这一页的验收口径：把「一个数」换成「一个分布」

下面四条是本课程后续所有可靠性指标的母版。注意 F03-1 不是一个阈值而是一张 k 值表——重复次数按任务风险分档，这是成本与结论强度之间的显式取舍。

pass^k 的定义是「k 次重复全部成功的比例」，它永远不高于 pass@1；两者的差距就是一致性缺口。上线看 pass^k，改进看首错位置。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| F03-1 | 重复次数 k 的取值 | P0 任务 k = 10，P1 任务 k = 5，P2 任务 k = 3；k < 3 的结论不得写入报告 | 每次评测 |
| F03-2 | 一致性缺口 | pass^k 的 95% CI 下界 ≥ 阈值才放行；只报 pass@1 的报告判为不完整 | 每次发布 |
| F03-3 | 运行间波动 | 变异系数 CV ≤ 0.15；超出说明配置未锁或存在隐藏输入 | 每次评测 |
| F03-4 | 表述稳定性 | 语义等价改写一致率 ≥ 95%，每条用例至少 5 个变体 | 每次发布 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来控制了随机性、实际没有的做法

这两种做法都出现在很多团队的评测规范里，也确实减少了一部分波动。

问题是它们把「减少」当成了「消除」。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 把 temperature 设为 0，结果就确定了，跑一次即可 | 采样随机性确实被关掉了，同样输入通常给同样输出 | 批处理组合、缓存命中与硬件差异仍会造成输出变化。temperature=0 只是减少了一个来源，不等于确定性 |
| 用固定 seed 保证可复现，无需重复运行 | seed 固定后同环境下确实可复现 | seed 只在同一部署配置下有效。换机器、换批大小、供应商更新推理栈都会让它失效。可复现不等于稳定 |

> 两条的共同修法：无论参数怎么固定，都要重复运行并报告分布。

### 结果不稳定时按什么顺序查

不稳定有四个来源，排查成本从低到高。前两行不需要跑任何实验。

查完之后，剩下的波动才是真正需要用分布来表达的部分。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 长输入时才不稳 | 接近 token 上限 | 统计实际 token 数与截断标记 |
| 改了提示顺序结果就变 | 上下文位置敏感 | 把关键信息放到首尾各测一次 |
| 参数没动结果却变 | 批处理或缓存 | 记录批大小与缓存命中率 |
| 换环境后结果不同 | 部署配置差异 | 比对两处的完整配置 |

> 第三行需要供应商提供的信息；拿不到时，正确做法是把它记为已知的不可控来源，而不是假装不存在。

### 做一次位置敏感性与重复运行实验：约 45 分钟

两个实验都很小，但结论会改变你写提示词与写测试的方式。

1. 构造一条包含关键约束的长输入，把约束分别放在开头、中间、结尾三个位置。
2. 三个版本各跑若干次，比较约束被遵守的比例。
3. 固定所有参数，同一输入重复运行至少五次，记录结果差异。
4. 统计差异类型：是措辞不同，还是结论不同。只有后者才是质量问题。
5. 把结论写成一句话：在这个任务上，位置影响多大、重复运行的结论差异率是多少。

**期望结果**：典型结果是中段位置的遵守率明显低于首尾，且重复运行有一定比例的结论差异。这两个数字应当直接影响你的提示词结构与测试重复次数。

> ⚠ 比较时要区分措辞差异与结论差异。把措辞不同算成失败，会让所有生成任务都不可测。

### 这一页的出口判据

这一段是全课程门禁范式的第一次出现：从「通过率 ≥ X 就放行」改成三段顺序判定。后面每一个模块都会复用这个形状。

最关键的一条在第二段：样本量不足时结论是「证据不足」，不是「通过」。把证据不足记成通过，是所有评测体系里最常见也最贵的一次撒谎。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 重复次数 k < 3 时阻断，结论不得写入任何发布材料<br>temperature 与随机种子的记录缺失率 = 0，缺任一字段即阻断且该轮全部数字作废 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | pass^k 取 Wilson 95% CI 下界与阈值比较，不用点估计<br>与上一版本对比时，两个 CI 不重叠才判定为真回归；重叠即判为无显著差异 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | pass@1 与 pass^k 的差距（一致性缺口）由产品 owner 签字接受<br>选择 k = 3 而非 10 的成本取舍，须由测试负责人写明理由并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[EleutherAI/lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness#readme)*

### 带走两个可以直接用的数字

一个是位置敏感度：关键约束放在中段时的遵守率下降幅度。它决定你的提示词结构。

另一个是结论差异率：同输入重复运行时结论不同的比例。它决定你的测试重复次数。

- 关键约束放首尾，不放中段
- temperature=0 仍需重复运行
- 区分措辞差异与结论差异，只把后者算失败
