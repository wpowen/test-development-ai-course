## TD-F04

### 把 Agent 当 LLM 测，会漏掉九成发生在中途的失败

这一页是分类页，看起来是概念课。它实际上决定了后面所有模块对你是否适用——分类错了，方案整套都是错的。

判据是「路径由谁决定」，不是产品叫什么名字。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 把多步 Agent 当单次 LLM 调用测，只评最终输出 | 只对最终输出打分的评估会漏掉约 90% 发生在执行中途的失败模式 | 线上一堆「答案看起来对但做错了事」的投诉，而评测报告一片绿 |
| 轨迹不透明就下安全结论 | 缺轨迹级评估会系统性漏掉约 44% 的安全违规与约 13% 的鲁棒性失败 | 把「没测出安全问题」当成「没有安全问题」 |
| 按产品名而不是控制权分类 | 一个产品里常常同时存在固定路由 Workflow、自主 Agent、异步 Worker 3 种结构，混在一起算总分会互相稀释 | 整体成功率 92% 很好看，其中不可逆动作那一类实际只有 71% |

> 共同根因：把「模型在其中扮演什么角色」这个结构问题，当成了「用了什么模型」这个选型问题。

### 判断被测边界的四个词

从 LLM 到 Agent，被测面每扩张一层，就要补一层 Trace 和一道 Gate。

| 术语 | 一句话解释 |
| --- | --- |
| 控制权 | 下一步由代码、模型还是队列决定；它是分类的唯一判据 |
| 状态 | 会话状态存在哪里：请求内、数据库、还是长期记忆 |
| 副作用 | 对外产生的真实影响；它决定风险等级 |
| Trace 层次 | 要观察到哪一级：调用级、步骤级还是任务级 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[modelcontextprotocol/modelcontextprotocol](https://modelcontextprotocol.io/)*

### 控制权在谁手里，决定了要测什么

区分 LLM、RAG、工具调用、Agent 的实用标准只有一条：控制权在谁手里。单次 LLM 调用里控制权全在调用方，输入输出都是一次性的；Agent 里控制权交给了模型，由它决定下一步调什么、调几次、什么时候停。

控制权一旦转移，三样东西随之出现：状态（跨步骤累积，且可能被污染）、副作用（中途已经发生，失败时无法整体回滚）、轨迹（正确性分布在过程里而不只在终局）。这三样在单次调用里根本不存在，因此也没有对应的断言。

所以「把 Agent 当 LLM 测」漏掉的不是某些用例，是整整三类被测对象。终局对了不代表过程对了——过程里多调了一次付费接口、读了不该读的数据、把错误状态写进了长期记忆，终局都可能仍然正确。

判断自己在测哪一种，只需要问一句：谁决定下一步？答案是代码，就是前两种；答案是模型，就是后两种。这个判断直接决定要不要建轨迹断言，而建不建轨迹断言是这个模块最大的成本分界。

*依据：[modelcontextprotocol/modelcontextprotocol](https://modelcontextprotocol.io/) · [langchain-ai/langgraph](https://langchain-ai.github.io/langgraph/)*

### 四种形态各自新增了什么被测对象

每往下一行，被测对象就多一类，且新增的那一类无法用上一行的手段覆盖。这是这一页最需要记住的结构。

第四行的成本远高于前三行——不是因为工具贵，而是因为轨迹断言必须逐条业务地写，没有通用模板。

| 被测形态 | 新增了什么被测对象 | 用什么观测 | 边界 |
| --- | --- | --- | --- |
| 单次 LLM 调用 | 无新增：输入输出都是一次性的 | 结构断言 + 语义断言（jsonschema、promptfoo） | 判据停在单次响应上，说不了过程 |
| 检索增强 | 上下文来源与忠实度 | 检索指标 + 忠实度评分（Ragas、TruLens） | 指标多由模型计算，未经人工校准前绝对值不可当验收线 |
| 工具调用 | 权限与副作用 | 工具契约（MCP schema）+ 调用层权限断言 | 规范描述接口不描述权限，授权判定要自己实现 |
| Agent | 轨迹、跨步状态、中断点 | 状态图 + 分布式 trace（LangGraph、OTel GenAI） | 结构可枚举不代表行为正确；同一条边两次执行可能走出不同结果 |

> 四行是累加不是替换：测 Agent 时前三行的断言一条都不能省，否则「过程对了」的结论建立在没有验证的基础上。

*依据：[python-jsonschema/jsonschema](https://python-jsonschema.readthedocs.io/) · [explodinggradients/ragas](https://docs.ragas.io/) · [modelcontextprotocol/modelcontextprotocol](https://modelcontextprotocol.io/) · [langchain-ai/langgraph](https://langchain-ai.github.io/langgraph/) · [open-telemetry/semantic-conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/)*

### 这张图的 7 个节点，本页各交付什么

这张图画的是被测边界随结构扩张的过程：从「用户目标到模型决策」这一段是 LLM，加上检索是 RAG，加上工具与状态是 Agent，把路径固定下来是 Workflow。

每向右扩一层，就多一个必须补的 Trace 和一个必须补的 Gate。本页的产物就是这张分层证据图。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 用户目标 | 把「用户想达成什么」与「系统输出了什么」分开，前者才是 Agent 的判定单位 | 任务级判定口径定义 |
| 检索·Context | 标出 RAG 相对纯 LLM 新增的失败面：检索错、检索对但没用上 | RAG 增量证据要求 |
| 模型决策 | 判断路径是模型决定还是代码决定——这是 Agent 与 Workflow 的分界线 | 结构分类决策记录 |
| 工具策略 Gate | 列出模型可调用的工具及其权限，标注哪些动作不可逆 | 工具权限与可逆性清单 |
| Worker·队列 | 标出异步执行引入的新断点：入口成功而后台失败 | 异步终态核对规则 |
| 业务状态 Verifier | 确认判定依据是业务状态变化，而不是模型自述「我已完成」 | 状态断言清单 |
| 人工升级·补偿 | 为不可逆动作定义人工确认点与补偿路径 | 升级与补偿设计 |

### 四种形态的边界扩张与新增要求

每往下一行，被测面就扩张一次，同时新增一类必须补的观察与门禁。

右列是新增项——它们不能沿用上一层的做法。

| 形态 | 控制权 | 新增被测面 | 必须补的观察与门禁 |
| --- | --- | --- | --- |
| LLM 应用 | 代码 | 模型行为 | 重复运行分布、拒答与截断断言 |
| RAG | 代码 | 检索与语料 | 引用存在性、忠实度、权限过滤 |
| 固定 Workflow | 代码 | 分支与状态 | 分支覆盖、非法转换、幂等 |
| Agent | 模型 | 工具与轨迹 | 三层 Oracle、写前授权、预算护栏 |
| Worker | 队列 | 异步与恢复 | 重复投递、checkpoint、死信 |

> 五行的共同要求只有一条：副作用提交点必须明确且有幂等保护。其余都随形态变化。

*依据：[langchain-ai/langgraph](https://langchain-ai.github.io/langgraph/)*

### 这一页的验收口径：四类结构各自的最小证据集

分类的意义在于它改变了「测到什么程度算测过」。同样一句「已完成测试」，对 LLM 和对 Agent 是完全不同的证据要求。

下表右两列是硬性的：分类为 Agent 却只有最终输出证据的，一律判为未测。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| F04-1 | 结构分类的明确性 | 每个被测单元归入 LLM / RAG / Agent / Workflow / Serving 之一，未分类比例 = 0 | 每次立项 |
| F04-2 | Agent 类的轨迹覆盖 | trace 完整率 100%，且逐 span 打标覆盖 ≥ 90% 的执行步骤 | 每次发布 |
| F04-3 | 异步 Worker 类的终态核对 | 入口 2xx 与业务终态的一致率 ≥ 99%，差额必须逐条归因 | 每日 |
| F04-4 | 不可逆动作的识别 | 不可逆动作清单覆盖率 100%，遗漏 1 条即视为该清单无效 | 每次工具清单变更 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在测复杂系统、实际漏掉整层的做法

这两种做法都覆盖了系统的主要功能，报告也很完整。

问题是它们用一种形态的测法覆盖了全部形态。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 整个系统用端到端测试覆盖，通过即合格 | 端到端最接近用户，也确实覆盖了全链路 | 端到端只验证一条路径。固定 Workflow 的分支、Agent 的替代路径、Worker 的重投递都不会被覆盖，而它们是各自形态最主要的失败面 |
| 系统里有 Agent，所以统一按 Agent 的方法测 | 方法更严格，覆盖也更全面 | 固定路由部分用不变量测会漏掉分支；异步部分用轨迹测会漏掉重复投递。方法要按形态选，不是按最严格的选 |

> 两条的共同修法：先按控制权把系统切成组件，再给每类组件配对应测法。

*依据：[modelcontextprotocol/modelcontextprotocol](https://modelcontextprotocol.io/)*

### 覆盖看起来很全但仍出事时按什么顺序查

整层被漏掉时，症状通常是「某类问题从来没被测试发现过」。按下表核对。

核对依据是 trace，不是架构文档。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 某些分支从未被测 | 固定 Workflow 被当成 Agent | 把固定部分单独做分支覆盖 |
| 出现重复副作用 | Worker 层未被单独测 | 补重复投递与幂等测试 |
| 引用的内容不存在 | RAG 层未被单独测 | 补引用存在性校验 |
| 结果对但过程越权 | Agent 层只测了 Outcome | 补 Step 层授权断言 |
| 无法判断在哪一层坏的 | Trace 层次不够 | 把观察补到步骤级 |

> 最后一行是前四行的前提：Trace 只到调用级时，其余四类问题都无法定位。

### 给你的系统画一张形态边界图：约 40 分钟

用一条真实 trace 逐步标注，比读架构文档准确。

1. 取一条完整的端到端 trace，把每一步列出来。
2. 对每一步标注控制权：代码、模型还是队列。
3. 按标注把系统切成组件，每个组件归入五种形态之一。
4. 对每个组件，对照上表列出它必须补的观察与门禁。
5. 统计当前已有哪些、缺哪些——通常会发现某一整类形态完全没有对应的测试。

**期望结果**：产出是一张标注了形态与缺口的边界图。多数系统是三到四种形态混合，而测试只覆盖了其中一两种。

> ⚠ 不要按产品命名或团队分工来切分组件。切分依据只有一个：下一步由什么决定。

### 这一页的出口判据

分类页的门禁看起来轻，实际上是全课程最省钱的一道：在这里花两小时分对类，能省掉后面用错方案的两周。

红线两条都与不可逆动作有关。原因很简单：其余分类错了是浪费，这一类分类错了是事故。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 存在未分类被测单元时阻断，未分类比例必须 = 0<br>不可逆动作清单覆盖率 < 100% 时阻断，不得进入任何执行类测试 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 入口 2xx 与业务终态一致率取 95% CI 下界与 99% 比较<br>span 打标覆盖率低于 90% 时结论为「轨迹证据不足」，不得据此下安全结论 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 同一产品内多结构混合的部分，由架构 owner 确认拆分口径并署名<br>暂不做轨迹级评估的模块，须由发布 owner 明示接受约 44% 安全违规不可见的风险 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一张形态与缺口对照图

图的作用是把「我们的 AI 系统测得挺全」变成「这五类形态里，我们覆盖了哪几类」。

缺口通常集中在异步与固定分支两类——它们不够新，容易被忽略。

- 按控制权切分组件，不按产品命名
- 每类形态配对应测法，不用最严格的覆盖全部
- Trace 至少到步骤级，否则无法定位层次

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[jsonschema：JSON Schema 校验实现](https://python-jsonschema.readthedocs.io/)** — 结构断言实现
  - 能证明：结构层断言可以脱离具体框架独立运行，包括在 LLM 结构化输出上——这是传统 Schema 校验能力迁移到 AI 系统时最直接的一条通路。
  - 不能证明：校验通过只说明形状对。LLM 返回一个字段齐全、类型正确但内容编造的 JSON，Schema 校验会放行。
  - `python-jsonschema/jsonschema` · 版本 v4.26.0（2026-01-07） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[OpenTelemetry 语义约定（含 GenAI 约定）](https://opentelemetry.io/docs/specs/semconv/gen-ai/)** — 传统可观测性 × AI 的关键结合点
  - 能证明：模型调用的 trace 属性已经有了标准命名：模型标识、token 用量、请求参数、结束原因等被纳入与 HTTP、数据库同一套语义约定体系。这意味着 LLM 调用不需要另建一套观测体系，而是接进既有链路。
  - 不能证明：GenAI 部分的约定仍在演进，字段名可能变更；且约定只规定怎么记，不规定记了之后如何判断质量。
  - `open-telemetry/semantic-conventions` · 版本 v1.44.0（2026-08-04） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Ragas：RAG 指标的参考实现](https://docs.ragas.io/)** — RAG 指标实现
  - 能证明：忠实度、答案相关性、上下文精确率/召回率这些 RAG 专属指标可以被拆成可计算的定义，而不是停留在「回答质量好不好」这种不可判定的说法上。
  - 不能证明：多数指标本身由模型计算，因此指标带有与被测系统同源的误差；未经人工标注校准前，它的绝对值不能当验收线，只能看趋势。
  - `explodinggradients/ragas` · 版本 v0.4.3（2026-01-13） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Model Context Protocol 规范](https://modelcontextprotocol.io/)** — 工具契约规范
  - 能证明：模型可调用的工具有了机器可读契约：名称、输入 schema、描述、错误返回。这让「Agent 能调什么工具」从代码里的隐含事实变成可审计、可版本化、可做契约测试的工件。
  - 不能证明：规范描述接口不描述权限。哪些工具允许被哪个会话调用、不可逆动作要不要二次确认，规范里没有，必须在工具调用层自己实现并验证。
  - `modelcontextprotocol/modelcontextprotocol` · 版本 2026-07-28（2026-07-28） · NOASSERTION · 许可证未能自动判定，按最保守口径只链接不搬代码
- **[LangGraph：把 Agent 表达成显式状态图](https://langchain-ai.github.io/langgraph/)** — 编排结构参考
  - 能证明：把 Agent 从「一个循环加一堆 if」变成显式的节点与边之后，状态、分支、中断点、检查点都成为可枚举对象——可枚举才可测。这是长流程可靠性测试能开展的结构前提。
  - 不能证明：结构清晰不等于行为正确。节点内部仍由模型驱动，同一条边上的两次执行可能走出完全不同的结果。
  - `langchain-ai/langgraph` · 版本 1.2.11（2026-08-11） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
