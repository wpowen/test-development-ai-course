## TD-F02

### 不画责任图，你会把 7 个阶段的错误都记在同一个人头上

模型生命周期有 7 个可能出错的阶段，但线上暴露出来的往往只有一个现象：答案不对。没有责任图时，团队的默认动作是「找算法调 Prompt」——这个动作对其中 5 个阶段无效。

下面三条不是风险提示，是已经发生过的事故形态。每一条都带一个可核查的数字，你可以拿去对照自己的系统。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 供应商在同一模型名下静默更新权重 | 公开复盘中出现过 judge 与人工一致性 κ 从 0.72 跌到 0.58 而团队数周无感知 | 把模型漂移读成「最近这批数据变难了」，于是去改数据集，问题原封不动 |
| 没有版本 Manifest，历史评测结果失去可比性 | Agent 版本由模型、system prompt、工具清单、记忆快照 4 个维度共同决定，任一维度变化都会让旧分数失效 | 拿上个月的 87 分和这周的 84 分直接比，得出「质量下降」，实际是换了 tokenizer |
| 一条失败 trace 无法重放 | 重放需要同时记下模型版本、temperature、随机种子、完整 system prompt、工具清单 hash 共 5 类字段，缺一即不可复现 | 归因停在「偶发」，缺陷进不了回归集，同一个 bug 每个版本复发一次 |

> 三条的共同根因是同一个：把「模型」当成一个不变的黑盒，而它其实是一个每天都在变的多维版本体。

### 模型生命周期的四个词

一次错误可能来自六个阶段中的任何一个。这四个词帮你分清责任在哪。

| 术语 | 一句话解释 |
| --- | --- |
| 预训练 | 模型的基础能力来源；测试开发通常无法干预，但要知道它决定了能力上限 |
| 后训练 | 指令微调与对齐；同一基座的不同后训练版本行为差异可能很大 |
| 部署配置 | 上下文上限、采样参数、安全策略；它常常是行为变化的真实原因 |
| 版本 Manifest | 把上述各阶段的标识固定下来的记录；没有它，错误无法归属 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[mlflow/mlflow](https://mlflow.org/docs/latest/)*

### 为什么必须先画责任图，才能归因一次失败

一次糟糕的回答可能来自六个不同阶段：预训练数据、后训练对齐、检索语料、系统提示词、解码参数、下游后处理。它们的修复方式、修复者与修复周期完全不同——把它们记在同一个人头上不是管理问题，是归因失效。

区分它们的唯一可靠办法是控制变量：固定其余、只改一处，看结果是否变化。这要求每一处都可版本化、可单独回放。版本 Manifest 就是这件事的工件形态：模型 id、权重版本、系统提示词版本、检索索引版本、解码参数、后处理版本，六项齐全才谈得上归因。

实际工程里最容易缺的是解码配置与后处理版本。它们既不在模型仓库里也不在提示词仓库里，通常散落在应用代码或环境变量中——于是「同一个模型、同样的提示词，结果不一样」这件事永远查不清，而团队会把它归因成「模型不稳定」。

责任图的作用不是分锅，是决定「这个问题该由谁在什么周期修」。预训练阶段的问题修复周期以月计，提示词阶段以小时计。把二者混在同一个缺陷池里，会让所有人都在等一个不可能到来的修复。

*依据：[mlflow/mlflow](https://mlflow.org/docs/latest/) · [iterative/dvc](https://dvc.org/doc)*

### 六个阶段各自靠什么留下可回放的版本

归因能力等于版本记录的完整度。这张表按阶段列出「谁负责记录它」，缺哪一行，那一阶段的问题就查不清。

第三行不是工具而是约定：解码参数与后处理版本没有现成的登记处，必须自己在应用侧留出上报入口。

| 生命周期阶段 | 工具 | 它负责什么 | 边界 |
| --- | --- | --- | --- |
| 模型与实验登记 | MLflow | 把模型、参数、数据版本与评测结果登记成可检索的关联记录，使「这个结论对应哪次运行」成为可查询事实 | 登记的是元数据不是质量；记录齐全的模型同样可以是差模型 |
| 数据与评测集版本 | DVC | 让同一个 commit 能取回当时用的那份数据，使历史分数之间可比、回归判断成立 | 版本可追不代表数据集设计合理；污染不会因为版本化而消失 |
| 部署配置 | 版本 Manifest（本课程模板） | 把解码参数、系统提示词版本、检索索引版本这些散落项收进同一份可比对工件 | 是工程约定不是现成工具，需要在应用侧留出读取与上报入口 |
| 运行时归因 | OTel GenAI 语义约定 | 把模型标识、请求参数、结束原因写进 span，使线上一次调用能对回某个版本组合 | 约定仍在演进，字段名可能变更 |

> 四行合起来才构成一次可回放的运行。缺任何一行，控制变量就做不到，归因只能靠猜。

*依据：[mlflow/mlflow](https://mlflow.org/docs/latest/) · [iterative/dvc](https://dvc.org/doc) · [open-telemetry/semantic-conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/)*

### 六个阶段各自能产生什么错误

把「模型答错了」拆到阶段上，才知道该找谁、能不能修。下表给出每个阶段的典型错误与你的可干预程度。

右列很重要：三分之二的阶段你无法直接修，但都可以通过测试暴露并绕开。

| 阶段 | 典型错误 | 你能做什么 |
| --- | --- | --- |
| 数据 | 知识缺失或过时 | 补检索，不要指望模型自己知道 |
| 预训练 | 基础能力不足 | 换模型或降低任务难度 |
| 后训练 | 过度拒答或过度顺从 | 换版本并重新校准评测 |
| 评测 | 供应商基准与你的任务不符 | 建自己的任务集 |
| 部署 | 上下文截断、参数不当 | 这是你最能直接修的一层 |
| 推理 | 并发下的行为差异 | 压测并固定批处理策略 |

> 倒数第二行是最常被忽略的：很多「模型变笨了」其实是上下文被截断或采样参数被改了。

*依据：[mlflow/mlflow](https://mlflow.org/docs/latest/)*

### 这一页的验收口径：四条可判定指标

责任图和 Manifest 都是文档，文档最容易变成摆设。下面四条把它们变成可以被检查的状态——每条都能用脚本或一次抽查得出是或否。

「复测频率」这一列比阈值本身更重要。版本类指标不是一次性达标就完的，它们会随供应商的每一次静默更新而失效。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| F02-1 | 版本 Manifest 字段完整度 | 5 类字段（模型版本 / temperature / seed / prompt 版本 / 工具清单 hash）缺失率 = 0 | 每次发布 |
| F02-2 | 失败 trace 的可重放性 | 随机抽 20 条失败 trace，可完整重放比例 ≥ 95% | 每周 1 次 |
| F02-3 | 模型端点漂移检测 | 哨兵集 20–30 条确定性任务，通过率相对上周变动 ≤ 5pt，超出即告警 | 每周 1 次 |
| F02-4 | 错误归属的可判定性 | 线上缺陷能指到唯一阶段的比例 ≥ 80%，其余必须显式标记为 UNKNOWN 而非默认归给模型 | 每月 1 次 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

*依据：[iterative/dvc](https://dvc.org/doc)*

### 两种看起来在定位模型问题、实际找错层的做法

这两种判断在团队讨论里非常常见，也听起来合理。

问题是它们跳过了更可能的原因。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 回答不准就换更强的模型 | 更强的模型在基准上确实更好 | 如果问题出在检索没给对文档或上下文被截断，换模型不会有任何改善，只会更贵。先排查部署层 |
| 模型不知道最新政策，说明训练数据过时 | 模型确实有知识截止时间，解释成立 | 这类问题应当靠检索解决而不是靠模型知道。把它归为训练数据问题，会导致团队去等下一次模型更新 |

> 两条的共同修法：先排查你能直接控制的部署与检索层，再怀疑模型本身。

### 模型表现变差时按什么顺序查

按可控性从高到低排查，前三行你都能自己修，且成本很低。

第四行开始才需要涉及模型本身。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 长输入时质量骤降 | 上下文截断 | 检查实际传入的 token 数与上限 |
| 同样问题结果波动大 | 采样参数 | 确认 temperature 与 seed 是否固定 |
| 缺少最新信息 | 检索未命中 | 查检索结果而不是怪模型 |
| 拒答变多 | 后训练版本变化 | 比对模型版本与安全策略 |
| 高峰期变差 | 推理批处理 | 看并发下的分位延迟与质量 |

> 前两行的排查成本几乎为零，却能解释大量被归因为「模型能力」的问题。

### 给一次真实错误做阶段归属：约 30 分钟

挑一个最近被归因为「模型不行」的具体案例，按六阶段逐个排除。

1. 取出这次调用的完整记录：实际传入的 prompt、上下文长度、采样参数、模型标识。
2. 检查上下文是否被截断——统计实际 token 数并与配置上限比较。
3. 检查采样参数是否与预期一致，以及是否固定了 seed。
4. 若涉及检索，打开检索结果确认需要的信息是否真的被检索到了。
5. 把结论写成阶段归属，而不是「模型不行」；写不出阶段的，标 UNKNOWN 并列出需要的信息。

**期望结果**：多数团队做完会发现相当一部分「模型问题」实际发生在部署或检索层，而这两层是可以自己修的。

> ⚠ 不要用同一个模型来判断自己的错误来自哪个阶段。阶段归属是确定性排查，靠记录不靠推理。

### 这一页的出口判据

责任图做完不等于可以进下一页。下面三段按顺序执行：红线不过就不必看统计，统计不过就不进风险接受。

第三段永远需要一个具名的人。工具可以告诉你还有哪些阶段不可归因，不能替你决定这个状态可不可以带着上线。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 版本 Manifest 的 5 类字段缺失率 = 0，缺任一字段即阻断<br>哨兵集通过率相对基线跌幅 > 5pt 时阻断，先查模型端点再查代码 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 20 条失败 trace 的可重放率取 Wilson 95% CI 下界，低于 95% 判为不达标<br>哨兵集样本 < 20 条时结论为「证据不足」，不得记为通过 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 无法归因到唯一阶段的缺陷比例，由测试负责人签字确认可接受<br>供应商不提供版本号的模型端点，须由发布 owner 明示接受不可复现风险 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一份模型版本 Manifest

Manifest 记录六个阶段的可知标识：模型、版本、后训练标记、部署配置、采样参数、检索索引版本。

它的作用是让「上周还好好的」这句话变成一次可以比对的差异。

- 先排查部署与检索层，再怀疑模型本身
- 固定模型版本号，不用浮动别名
- 把六阶段标识记进每次运行的 Manifest

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[OpenTelemetry 语义约定（含 GenAI 约定）](https://opentelemetry.io/docs/specs/semconv/gen-ai/)** — 传统可观测性 × AI 的关键结合点
  - 能证明：模型调用的 trace 属性已经有了标准命名：模型标识、token 用量、请求参数、结束原因等被纳入与 HTTP、数据库同一套语义约定体系。这意味着 LLM 调用不需要另建一套观测体系，而是接进既有链路。
  - 不能证明：GenAI 部分的约定仍在演进，字段名可能变更；且约定只规定怎么记，不规定记了之后如何判断质量。
  - `open-telemetry/semantic-conventions` · 版本 v1.44.0（2026-08-04） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[MLflow：实验、模型与版本的登记体系](https://mlflow.org/docs/latest/)** — 版本与血缘
  - 能证明：模型、参数、数据版本与评测结果可以被登记成可检索的关联记录，使「这个结论对应哪个模型的哪次运行」成为可查询事实而不是靠人记。回滚与事后归因都依赖这条记录。
  - 不能证明：登记的是元数据不是质量。记录齐全的模型同样可以是差模型。
  - `mlflow/mlflow` · 版本 v3.15.1（2026-08-03） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[DVC：数据与流水线的版本控制](https://dvc.org/doc)** — 数据版本
  - 能证明：评测集必须与代码一样可版本化：同一个 commit 能取回当时用的那份数据。缺了这一条，历史评测分数之间不可比，回归判断也就不成立。
  - 不能证明：版本可追不代表数据集设计合理；污染与分布偏移不会因为版本化而消失。
  - `iterative/dvc` · 版本 3.67.1（2026-03-31） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
