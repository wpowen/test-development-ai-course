## TD-T03

### 把所有判断都交给一个 Judge，等于把体系的可信度上限交给一个没测过的组件

整套评测依赖 Judge 打分，而 Judge 本身通常从未被测过。这是评测体系里最大的盲区：所有数字的准确性上限，取决于那个 Judge 有多准。

第一条的数字解释了为什么本页把 Judge 校准放在 Oracle 设计之前。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| Judge 未校准就投入使用 | 方差分解研究显示，Judge 分歧本身在安全分类任务中可贡献高达 44% 的总方差 | 把 Judge 的噪声读成模型的能力波动，追着调 Prompt |
| 用语义评分去测本可以用断言测的东西 | Schema、权限、金额这类判断的正确率用确定性断言可达 100%，用语义 Judge 通常落在 90% 上下 | 在完全可判定的地方引入 10% 的不确定性，还看不出来 |
| 高风险失败被平均分抵消 | 一个总分 92% 的报告里，不可逆动作类的子项可能只有 71%，而总分完全看不出 | 「整体质量良好」这个结论，恰好掩盖了唯一会出事的那一类 |

> 三条的共同解法是同一个：分层 Oracle——能断言的用断言，只有开放式判断才交给 Judge，高风险类单独出分不进平均。

### 复合 Oracle 的四个词

没有任何单一判据能覆盖 AI 输出的全部维度。组合才是常态。

| 术语 | 一句话解释 |
| --- | --- |
| 确定性 Gate | 可以用代码精确判定的部分，如格式、字段、引用存在性 |
| 业务规则 | 领域内必须成立的约束，如金额上限、状态转换 |
| 语义评分 | 模型判分；它是估计值，不是判据 |
| 人工复核 | 最终的判断者；成本最高，因此要精准投放 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[confident-ai/deepeval](https://deepeval.com/docs/getting-started)*

### 判据为什么必须分层，而不是全交给一个 Judge

单一 Judge 的问题不是它不准，是它的误差无法被独立发现。用模型判模型，两者共享大量先验；judge 说「对」的时候，你没有第二条路径可以质疑它——这与用接口的读方法验证写方法是同一个结构性错误。

分层的第一条原则是：能用确定性规则判的，绝不交给模型。格式、字段、数值范围、禁用词、引用是否真的出现在给定上下文里——这些都有确定答案，成本几乎为零，判据本身还可测。把它们放在最前面做硬 Gate，既能过滤掉大部分明显错误，也大幅降低后面昂贵判据的调用量。

语义评分只用来处理确定性规则处理不了的部分，而且它的输出应当是分数不是布尔。分数进入统计门禁，布尔进入硬红线——把语义评分当布尔用，等于把一个有误差的估计直接当成了判决。

人工复核不是「还没做完的自动化」，它是唯一能给语义评分提供校准锚点的东西。没有定期人工标注，judge 的漂移无人知晓——而 judge 本身也是一个会随模型版本变化的组件，它同样需要回归测试。

*依据：[UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/) · [confident-ai/deepeval](https://deepeval.com/docs/getting-started)*

### 四层判据的成本、可靠性与适用范围

从上到下成本递增、覆盖递宽、可靠性递减。设计判据时的目标是把尽可能多的判断挤到上面两层，而不是追求某一层做到最好。

最后一行常被当成成本项砍掉。砍掉它之后，第三层就变成了一个没有任何校准的黑盒——整个体系的可信度上限随之落到它身上。

| 判据层 | 判什么 | 工具 | 边界 |
| --- | --- | --- | --- |
| 确定性 Gate | 格式、字段、数值范围、禁用词、引用是否存在于上下文 | jsonschema、promptfoo 内建断言 | 只能判有确定答案的部分，覆盖窄但完全可信 |
| 业务规则 | 与领域约束一致：金额、状态转换、权限 | 自写规则 + 领域数据 | 规则要人写，且必须与业务 owner 确认权威性 |
| 语义评分 | 确定性规则覆盖不到的质量维度 | DeepEval、Ragas、Inspect scorer | 输出应是分数不是布尔；误差需要校准才能解释 |
| 人工复核 | 给语义评分提供校准锚点，检出 judge 漂移 | 人工标注 + 一致性统计（κ） | 成本最高、样本最少；砍掉它则上一层不可信 |

> 四层是漏斗不是并列：上层过滤掉的样本不必进入下层，这既是成本设计也是可信度设计。

*依据：[python-jsonschema/jsonschema](https://python-jsonschema.readthedocs.io/) · [promptfoo/promptfoo](https://www.promptfoo.dev/docs/intro/) · [confident-ai/deepeval](https://deepeval.com/docs/getting-started) · [explodinggradients/ragas](https://docs.ragas.io/) · [UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/)*

### 这张图的 7 个节点，本页各交付什么

这张图是一个逐层收窄的漏斗：前三个 Gate 是确定性的，能挡住的绝不往后传；语义 Judge 只处理剩下的开放式判断；人工只看分歧样本。

这个顺序不能颠倒。把语义 Judge 放在 Schema Gate 之前，等于让最不可靠的组件先做最可判定的事。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| Eval case | 为每条用例标注风险等级，决定它走哪几层 Gate | 用例风险分级表 |
| Schema Gate | 结构、字段、类型的确定性校验，通过率必须可达 100% | 结构断言集 |
| 业务规则 Gate | 金额、状态、权限的硬规则断言，违反即 blocker 不进平均 | 业务硬规则断言集 |
| 权限·副作用 Gate | 判断动作是否越权、是否不可逆，不可逆动作强制走人工 | 副作用与权限判定规则 |
| 语义 Judge | 只处理开放式质量判断，且必须与被测模型不同族以规避自偏好 | Judge Card（版本 / rubric / κ） |
| 人工校准 | 维护金标集，按月重算 κ，跌破阈值即停用 Judge 回退人审 | 金标集与月度 κ 记录 |
| 发布/升级决定 | 汇总各层结论，高风险类单独列出不并入总分 | 分层结论报告 |

> 第一列的节点名与页面架构图逐字一致，由门禁校验；改图必须同步改这张表，否则构建失败。

### 四层各自的成本、可靠性与适用范围

组合的原则是：能用便宜且可靠的层解决的，绝不上交给贵且不可靠的层。

右列的「不可用于」是硬约束，不是建议。

| 层 | 成本 | 可靠性 | 不可用于 |
| --- | --- | --- | --- |
| 确定性 Gate | 极低 | 高 | 语义正确性判断 |
| 业务规则 | 低 | 高 | 开放式内容质量 |
| 语义评分 | 中 | 低 | 放行任何 blocker |
| 人工复核 | 高 | 最高 | 大规模全量判定 |

> 第三行的约束最容易被违反：用语义评分放行涉及金额或权限的结论，是最常见的 Oracle 设计错误。

*依据：[confident-ai/deepeval](https://deepeval.com/docs/getting-started)*

### 这一页的验收口径：先测量测量系统本身

κ ≥ 0.7 这条阈值来自 Landis-Koch 一致性分级中「substantial」的下沿，是行业惯用的可用性门槛，不是本课程的发明。

T03-2 的双向成对比较容易被省略，但它是位置偏置唯一的低成本检测手段：A/B 和 B/A 各跑一次，结论不一致的样本判为无效。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| T03-1 | Judge 与人类一致性 | Cohen's κ ≥ 0.7；跌破即停用该 Judge 并回退人审 | 每月 + 每次换模型 |
| T03-2 | 位置偏置 | 成对比较双向跑，位置交换一致率 ≥ 95% | 每月 1 次 |
| T03-3 | 标注者间一致性 | 金标集 3 名标注员，标注者 κ ≥ 0.7；低于此值先改 rubric 再改 Judge | 建集时 + 每季度 |
| T03-4 | 确定性覆盖比例 | 可断言判断中实际用断言实现的比例 ≥ 95%，其余须逐条说明为何用 Judge | 每次发布 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在做分层判定、实际仍然单点的做法

这两种做法都用了多个判据，看起来比单一判据严谨。

问题是判据之间的关系设计错了。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 把四层的分数加权求和得到一个总分 | 综合了各层信息，也便于排序与对比 | 加权会让 blocker 被稀释。一次权限越界可能只让总分掉两分。硬性判据必须独立于任何加权计算 |
| 先用语义评分筛一遍，低分的再人工看 | 节省了人工成本，也确实提高了效率 | 语义评分对某些失败类型不敏感。它给高分的样本里可能恰好包含事实错误。筛选应当由确定性规则做，不由语义评分做 |

> 两条的共同修法：便宜且可靠的层负责筛选与阻断，贵且不可靠的层只负责补充。

### 评测通过但出事时按什么顺序查

按四层逐个核对，看这次的失败本应被哪一层拦下。

多数情况下会发现：本可以用确定性规则拦下的，被交给了语义评分。

| 失败类型 | 本应由哪层拦 | 当前是谁在判 |
| --- | --- | --- |
| 格式或字段错误 | 确定性 Gate | 常被语义评分吞掉 |
| 引用不存在 | 确定性 Gate | 常被当成语义问题 |
| 金额或权限越界 | 业务规则 | 常被语义评分放行 |
| 内容质量差 | 语义评分 + 人工 | 常无人负责 |

> 前三行都能用确定性方式判定。把它们交给语义层，既贵又不准。

### 给现有判据做一次分层归位：约 45 分钟

把当前所有判定逻辑列出来，逐条问它属于哪一层。

1. 列出当前评测中的全部判定逻辑，包括代码断言与评分规则。
2. 逐条归入四层之一，标注它当前实际由谁执行。
3. 找出被错误上移的：本可以用代码判定却交给了语义评分的部分。
4. 把这些下移到确定性 Gate，并验证下移后结果一致。
5. 确认没有任何 blocker 由语义评分单独放行——有的话立即改为业务规则或人工。

**期望结果**：典型结果是有一到两类判定被不必要地交给了语义评分。下移之后评测会变快、变便宜，也变准。

> ⚠ 下移时要验证结果一致。有些看似可以用规则判定的逻辑，实际有例外情况需要语义判断。

### 这一页的出口判据

这一页的红线有一条特殊性质：它作废的不是被测系统的结论，而是本轮全部评测数字。Judge 不可信时，它打出来的所有分都不可信。

如果整套体系你只能先做一件事，做 T03-1。你现在所有的评测数字，准确性上限都取决于那个 Judge 有多准，而这件事大概率还没有被量化过。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | Judge 的 Cohen's κ < 0.7 时阻断，本轮所有 Judge 打分作废<br>业务硬规则违反数 > 0 时阻断，不得以总分达标为由放行 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | κ 与位置交换一致率均按金标集样本量给出 95% CI，样本 < 200 条时标注证据不足<br>Judge 换版本视为一次变更，须与旧版本在同一金标集上做配对比较 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 语义 Judge 与被测模型同族时，由测试负责人签字接受自偏好风险<br>高风险类的残余失败率由业务 owner 在知情前提下签字接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/)*

### 带走一张判据分层归位表

表的作用是回答一个问题：每一条判定由哪一层负责，为什么不能由更便宜的层负责。

归位之后，语义评分的调用量通常会大幅下降，而准确性反而提升。

- 能用代码判定的绝不交给语义评分
- blocker 不得由语义层单独放行
- 人工复核精准投放到高风险切片

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[jsonschema：JSON Schema 校验实现](https://python-jsonschema.readthedocs.io/)** — 结构断言实现
  - 能证明：结构层断言可以脱离具体框架独立运行，包括在 LLM 结构化输出上——这是传统 Schema 校验能力迁移到 AI 系统时最直接的一条通路。
  - 不能证明：校验通过只说明形状对。LLM 返回一个字段齐全、类型正确但内容编造的 JSON，Schema 校验会放行。
  - `python-jsonschema/jsonschema` · 版本 v4.26.0（2026-01-07） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[promptfoo：Prompt 与 Agent 的断言式评测](https://www.promptfoo.dev/docs/intro/)** — AI 侧断言执行器
  - 能证明：把断言写成配置：确定性断言（contains、is-json、javascript）、语义断言与模型评判可以在同一个用例里组合，并按矩阵跑多模型多 prompt。它让「AI 输出」进入与传统测试相同的红绿流程。
  - 不能证明：模型评判本身有误差，需要与人工标注校准后才能作为门禁判据。
  - `promptfoo/promptfoo` · 版本 0.122.0（2026-08-04） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[DeepEval：pytest 风格的 LLM 评测框架](https://deepeval.com/docs/getting-started)** — AI 侧断言执行器
  - 能证明：LLM 评测可以直接寄生在 pytest 生态里：用例、fixture、参数化、CI 集成全部复用既有工程习惯，降低把评测接进流水线的成本。
  - 不能证明：指标默认阈值是框架给的示例值，不是你业务的验收线。
  - `confident-ai/deepeval` · 版本 v4.1.7（2026-07-29） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Inspect：任务 / solver / scorer 分层的模型评测框架](https://inspect.aisi.org.uk/)** — 评测框架
  - 能证明：评测可以拆成三个独立可替换的部件：dataset 定义问什么、solver 定义怎么问、scorer 定义怎么判。三者分离之后，换模型不用改判据，改判据不用改数据集——这是把一次性评测脚本变成可回归资产的结构条件。
  - 不能证明：框架不提供判据。scorer 写得对不对、数据集有没有覆盖你的风险切片，框架一概不管，全绿只说明流程跑通了。
  - `UKGovernmentBEIS/inspect_ai` · 版本 release/2025-11-28 · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Ragas：RAG 指标的参考实现](https://docs.ragas.io/)** — RAG 指标实现
  - 能证明：忠实度、答案相关性、上下文精确率/召回率这些 RAG 专属指标可以被拆成可计算的定义，而不是停留在「回答质量好不好」这种不可判定的说法上。
  - 不能证明：多数指标本身由模型计算，因此指标带有与被测系统同源的误差；未经人工标注校准前，它的绝对值不能当验收线，只能看趋势。
  - `explodinggradients/ragas` · 版本 v0.4.3（2026-01-13） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
