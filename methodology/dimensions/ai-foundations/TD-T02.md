## TD-T02

### 评测集越调越假，是因为它已经变成了训练集的一部分

数据集是评测体系里唯一一个会被自己的使用过程破坏的组件。每看一次 Holdout，它就少一分作为 Holdout 的价值。

它们的共同特征是：过程中每一步看起来都合理。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 用同一批数据反复调优 | Holdout 每被开封 1 次，其无偏性就下降一档；通行纪律是每个版本至多开封 1 次 | 分数持续上涨被读成能力提升，实际是对这批题的过拟合 |
| 训练数据污染评测集 | 污染率的唯一可接受值是 0；哪怕 1% 的重合也足以让排名失真 | 模型「表现优异」，换一批同分布新题就掉 10 个点以上 |
| 高风险切片样本太少 | 单个切片样本 < 30 条时，置信区间宽到无法区分 60% 和 85% | 把「这个切片看起来还行」当成结论，而它其实什么都没说 |

> 三条都指向同一条纪律：数据集必须有版本、有边界、有开封记录，否则它只是一堆题。

### 数据集设计的四个词

评测越调越假，根源几乎都在数据集的角色管理上。

| 术语 | 一句话解释 |
| --- | --- |
| 失败成本 | 这类样本出错的代价；它决定样本的权重而不是数量 |
| 风险切片 | 按业务风险划分的子集；平均分永远会掩盖高风险切片 |
| 时间边界 | 样本的时间范围；跨越版本变更的样本会让对比失效 |
| 封存 Holdout | 只在发布判断时开封一次的集合；反复开封即失效 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[iterative/dvc](https://dvc.org/doc)*

### 从失败成本反推样本，而不是从数据可得性正推

评测集最常见的建法是「把手头有的数据拿来标一批」。这样得到的分布等于历史流量分布，而历史流量里高频的往往恰恰是低风险的——于是评测集把绝大多数样本花在了错了也不要紧的地方。

正确的起点是失败成本：列出这个系统可能造成的损失（资损、合规、口碑、人工返工），按成本排序，再为每一类构造足够样本。这会得到一个与流量分布完全不同的评测集，而且它是**刻意不平衡**的——这一点常被误当成设计缺陷。

时间边界与封存 holdout 解决的是另一个问题：评测集一旦被用来调优，它就逐渐变成了训练集的一部分。反复在同一份数据上迭代，分数会持续上升而真实能力不变。封存一份从不用于调优、只在发布前开封一次的集合，是目前唯一能检出这种自欺的手段。

LLM 时代还多了一层污染：公开数据可能已经在预训练语料里。因此企业评测集应当优先使用内部数据、且时间戳晚于模型的训练截止日期，并把这个时间边界记录下来——它是「跨版本可比」能够成立的前提。

*依据：[iterative/dvc](https://dvc.org/doc) · [SWE-bench/SWE-bench](https://www.swebench.com/)*

### 四类样本各自的构造方式与失效方式

这张表的重点在最后一列。四类样本都会失效，但失效方式不同，而且**都不会报错**——这是数据集治理与代码治理最大的差别。

第二行没有工具：风险切片必须由业务参与定义失败成本，任何工具都推导不出你的业务里什么错误最贵。

| 数据集职责 | 构造方式 | 工具 | 失效方式 |
| --- | --- | --- | --- |
| 代表性集合 | 按真实流量分布采样，回答「整体够不够好」 | DVC 版本化 + Evidently 分布漂移检测 | 漂移无声发生，必须主动检测；而检出漂移只说明输入变了，不说明质量降了 |
| 风险切片 | 按失败成本构造，刻意不平衡 | 无（需业务参与） | 只覆盖想到的风险；没想到的那类不会有样本 |
| 回归集合 | 每个线上事故沉淀一条，只增不改 | DVC 版本化 | 一旦被用于调优，检出退化的能力静默消失 |
| 封存 Holdout | 从不用于调优，发布前开封一次 | DVC + 访问控制 | 开封即失效；不可重建则永久失去这条防线 |

> 四类的使用纪律不同，混用不会有任何报错。最常见的一次性损失是拿回归集去调优——调完之后它看起来还在，实际已经不再检出退化。

*依据：[iterative/dvc](https://dvc.org/doc) · [SWE-bench/SWE-bench](https://www.swebench.com/) · [evidentlyai/evidently](https://docs.evidentlyai.com/)*

### 这张图的 7 个节点，本页各交付什么

这张图的核心是三个集合的物理隔离：Development 可以随便看，Validation 定期看，Sealed Holdout 只在发布前开封一次。

混用这三者不会立刻报错，只会让你的分数缓慢失去意义——这是本页要防的最隐蔽的失败。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 失败与风险池 | 从真实失败与风险登记册出发采样，而不是从「典型场景」出发想象 | 失败驱动的采样清单 |
| 采样/去重 | 执行跨集合去重与近重复检测，输出污染检查结论 | 去重报告（污染率） |
| Development set | 允许反复查看和调优的集合，明确标注它不能用于任何对外结论 | 开发集及其用途声明 |
| Validation set | 定期评估用，记录每次使用时间，防止事实上变成开发集 | 验证集使用台账 |
| Sealed Holdout | 封存并记录开封次数，每个版本至多开封 1 次 | Holdout 封存与开封记录 |
| 切片报告 | 按风险切片分别出分，禁止只报总分 | 切片矩阵报告 |
| Owner adjudication | 对争议样本与标签分歧做出裁决并留痕 | 争议样本裁决记录 |

> 第一列的节点名与页面架构图逐字一致，由门禁校验；改图必须同步改这张表，否则构建失败。

### 从失败成本出发设计样本

样本数量不是设计目标，覆盖失败成本才是。下表按成本分档决定各档的处理方式。

右列写的是这一档被错误处理时的后果。

| 失败成本 | 样本处理 | 错误处理的后果 |
| --- | --- | --- |
| 不可逆资金或权限 | 单列切片并设 blocker | 被平均分稀释 |
| 数据错误可恢复 | 独立统计并设阈值 | 混入总分后趋势不可读 |
| 体验受损 | 计入总分 | 过度投入在低价值样本上 |
| 无实质影响 | 抽样即可 | 占用大量标注成本 |

> 第一档的样本数量通常很少，但它们决定发布与否。用数量加权会让它们完全消失在报告里。

*依据：[SWE-bench/SWE-bench](https://www.swebench.com/)*

### 这一页的验收口径：数据集的健康检查

T02-1 是唯一一条要求绝对值的：污染率必须是 0，不设容忍区间。原因是污染不是程度问题——有污染的排名结论直接不可用。

T02-3 决定了你的切片报告有没有意义。样本不足的切片应当显式写「证据不足」，而不是给一个漂亮但空洞的百分比。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| T02-1 | 训练/评测污染 | 跨集合重合与近重复的污染率 = 0 | 每次数据集变更 |
| T02-2 | Holdout 无偏性 | 每个版本开封次数 ≤ 1 次，累计开封 ≥ 3 次即整体重建 | 每次发布 |
| T02-3 | 切片最小样本量 | 每个风险切片样本 ≥ 30 条，不足时报告必须写「证据不足」而非给出百分比 | 每次评测 |
| T02-4 | 分布代表性 | 评测集与生产分布的 KL 散度纳入监控，环比变动 > 20% 时触发重采样 | 每季度 1 次 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

*依据：[evidentlyai/evidently](https://docs.evidentlyai.com/)*

### 两种看起来数据规范、实际会让评测失真的做法

这两种做法都符合常见的数据科学规范，也确实提高了统计稳定性。

问题是它们与业务风险脱节。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 按 7:2:1 随机切分训练、验证、测试集 | 这是标准做法，切分也无偏 | 随机切分会把高风险样本随机分散。评测集里可能只剩两三条资金相关样本，它们的失败会被完全平均掉 |
| 持续往评测集里补充新样本，保持数据新鲜 | 数据新鲜度确实重要，补充也符合直觉 | 不断变化的评测集让跨版本对比失去意义。正确做法是版本化评测集，新样本进入下一个版本而不是当前版本 |

> 两条的共同修法：按风险分层抽样，并给评测集打版本。

*依据：[iterative/dvc](https://dvc.org/doc)*

### 评测分数与实际体验脱节时按什么顺序查

脱节几乎总是数据集问题，而不是指标问题。按下表逐项查。

前两行占绝大多数。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 分数升但投诉不变 | 分布与生产不符 | 用近期生产采样重建分布 |
| 高风险问题没被发现 | 未按风险分层 | 把高成本样本单列切片 |
| 跨版本对比结论矛盾 | 评测集变过 | 给评测集打版本并锁定对比基线 |
| 分数一直在涨 | 过拟合评测集 | 用未开封的 holdout 重测 |

> 最后一行的验证成本极低——开封一次 holdout 就知道，但前提是你准备过。

### 按失败成本重构评测集：约 60 分钟

不需要新增标注。把现有样本按成本分档重新组织即可。

1. 把现有评测集的样本逐条标注失败成本等级。
2. 统计各档的样本数——通常最高成本档只有个位数。
3. 把最高成本档单列为 blocker 切片，并明确它们不参与总分平均。
4. 从代表性样本中独立抽取一份 holdout 并封存，记录抽取时间与审批人。
5. 给整个评测集打版本号，之后的新样本进入下一版本而不是当前版本。

**期望结果**：重构后总分通常会变化，因为高成本样本不再被稀释。这个变化不是退步，是此前被掩盖的部分显现出来。

> ⚠ holdout 必须在任何调优之前抽取。从已经用过的集合里事后划出一部分，它不是 holdout。

### 这一页的出口判据

数据集的门禁必须在评测之前跑完。等到分数出来再检查污染，你已经无法判断那个分数里有多少是真的。

第三段在这一页格外重要：分布代表性几乎永远不完美，问题不是有没有偏差，而是谁知道并接受了这个偏差。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 污染率 > 0 时阻断，先清洗再评测<br>Holdout 在同一版本内开封 ≥ 2 次时阻断，该轮结论作废 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 切片结论一律带 Wilson 95% CI；样本 < 30 条时只报区间不报点估计<br>版本间切片对比预注册效应量/非劣界，对同切片配对差值做任务级或聚类 bootstrap 95% CI；不以两个 CI 是否重叠判定 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 评测集与生产分布的已知偏差，由数据 owner 列出并签字接受<br>长尾切片样本长期不足时，须由发布 owner 明示接受该切片结论不可用 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一份按风险分层的数据集清单

清单按失败成本分档，每档标明样本数、是否 blocker、是否参与总分。

最高档的样本数通常很少，但它们才是决定发布的那部分。

- 按失败成本分层，不按随机比例切分
- 高成本样本单列 blocker，不参与平均
- 评测集打版本，新样本进下一版

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[SWE-bench：以真实仓库 issue 为任务的 Agent 基准](https://www.swebench.com/)** — 任务级基准
  - 能证明：任务级评测的判据可以完全确定：补丁应用后跑原仓库的测试，通过即算解决。这比模型评判可靠得多，也说明「只要任务本身自带 oracle，评测就不需要 judge」。
  - 不能证明：任务来自公开仓库，训练数据污染无法排除；单次成功率也不代表在你私有代码库上的表现。执行成本高，不适合做每次提交的门禁。
  - `SWE-bench/SWE-bench` · 版本 v4.1.0 · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[DVC：数据与流水线的版本控制](https://dvc.org/doc)** — 数据版本
  - 能证明：评测集必须与代码一样可版本化：同一个 commit 能取回当时用的那份数据。缺了这一条，历史评测分数之间不可比，回归判断也就不成立。
  - 不能证明：版本可追不代表数据集设计合理；污染与分布偏移不会因为版本化而消失。
  - `iterative/dvc` · 版本 3.67.1（2026-03-31） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Evidently：数据与模型漂移检测](https://docs.evidentlyai.com/)** — 漂移检测
  - 能证明：输入分布漂移可以在没有标注的情况下被检出，因此可以作为线上早期告警——真实质量下降往往先表现为输入分布变了，而标注要几天后才有。
  - 不能证明：漂移不等于质量下降，反之亦然。它是调查触发器，不能直接作为阻断门禁。
  - `evidentlyai/evidently` · 版本 v0.7.21（2026-03-10） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
