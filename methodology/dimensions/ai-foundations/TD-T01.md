## TD-T01

### 先选指标再想问题，是评测体系最常见的起点，也是最贵的

多数团队的评测从「我们用什么指标」开始。这个顺序保证了一件事：指标一定测得出东西，但不一定测的是你要的东西。

Eval Contract 的作用是把顺序反过来——先写清楚这次发布要回答什么问题、谁来拍板、什么情况下停下来，再选指标。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 没有 stop state，评测永远「还能再调一轮」 | 缺停止条件的评测周期普遍延长 2–3 倍，且最终仍由主观判断结束 | 把「调到大家都累了」当成「调到位了」 |
| 指标与业务结果不相关 | 指标构念效度的通行要求是指标与业务结果相关性 ≥ 0.6，低于此值的指标涨跌与业务无关 | 指标从 82 提到 89，线上投诉量没变，团队却认为改进有效 |
| 没有具名 owner | 一份发布决策至少需要 3 个具名角色：语义判定、风险接受、回滚执行，缺任一角色事故时无人有权决定 | 出事后复盘结论是「流程问题」，下一次原样重演 |

> 三条的共同点：它们都不是技术问题，但都只能在写 Contract 的时候解决，写完代码就来不及了。

### 评测合同的四个词

先写清要回答哪个发布问题，再选指标。顺序反了，指标会变成自娱自乐。

| 术语 | 一句话解释 |
| --- | --- |
| 发布问题 | 这次评测要支撑哪个具体决定；它必须是一句能回答「发不发」的话 |
| Oracle | 判定对错的独立依据；它不能来自被测系统本身 |
| stop state | 什么情况下停止评测并升级；没有它，评测会在证据不足时给出结论 |
| owner | 这份合同的负责人；阈值与例外由他裁决 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/)*

### 为什么必须先写问题，后选指标

指标是答案的形状，问题决定形状。先选指标会发生一件很隐蔽的事：你会不自觉地把问题改成这个指标能回答的样子。于是体系里所有指标都很漂亮，却没有一个对应真实的发布决定。

一份可用的评测合同必须先写死三件事：这次发布要回答的问题（例如「能不能把客服自动回复率从 30% 提到 50% 且投诉率不上升」）、判据来自哪里（谁有权说对错）、什么情况下停止。三件写完之后，指标基本是被推导出来的，而不是被挑出来的。

stop state 是最常被省略的一项。没有停止条件的评测会一直跑下去——「再调调看」，因为没有任何一条线定义了「够了」。这既在烧成本，也让评测无法进入发布流程：发布需要一个是或否，而不是一条还在上升的曲线。

owner 同样不可省略。评测输出的是证据，接受剩余风险是决定；前者可以自动化，后者必须有具名的人。合同里没有 owner 时，事故复盘会发现「所有人都看过那个报告」，等价于没有人负责。

*依据：[UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/) · [openai/evals](https://github.com/openai/evals#readme)*

### 合同的五项要素各自落成什么工件

合同不是一份文档，是五个可被下游程序消费的工件。只写文档不落工件，下一次评测仍然要从头商量一遍。

第一行刻意没有工具：把问题写清楚这件事没有工具能代劳，而它决定了后面四行是否有意义。

| 合同要素 | 落成什么工件 | 工具 | 边界 |
| --- | --- | --- | --- |
| 问题与 stop state | 版本化的评测合同文档 | 无（工程纪律） | 工具替代不了写清问题；这一项写歪，后面全部白做 |
| 数据集 | 版本化数据集 + 风险切片标注 | DVC | 版本可追不代表覆盖了你的风险切片 |
| 判据 | 可执行的 scorer | Inspect（dataset / solver / scorer 三层分离） | 框架不提供判据，scorer 写得对不对它一概不管 |
| 执行与回归 | 可复现的运行记录 | MLflow | 登记的是元数据不是质量 |
| 门禁接入 | 断言式用例 | promptfoo / DeepEval | 模型评判有误差，需与人工标注校准后才能当门禁 |

> 五行按依赖顺序排列。跳过第一行直接从第三行开始，是这一页描述的那个最贵的起点。

*依据：[UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/) · [iterative/dvc](https://dvc.org/doc) · [mlflow/mlflow](https://mlflow.org/docs/latest/) · [promptfoo/promptfoo](https://www.promptfoo.dev/docs/intro/) · [confident-ai/deepeval](https://deepeval.com/docs/getting-started)*

### 这张图的 7 个节点，本页各交付什么

这张图的方向很重要：它从「发布问题」开始，到「人工发布决定」结束，指标只是中间的一段。反过来读就是本页要纠正的错误顺序。

整张图的产物是一份可审计的 Eval Contract：任何人拿到它，都能说出这次评测适用于什么、不适用于什么。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 发布问题 | 把「这次发布要回答什么」写成一句可证伪的话，而不是「验证模型效果」 | 发布问题陈述（一句话） |
| 风险与 owner | 列出失败成本最高的三种情况，并给每种指定具名 owner | 风险登记册与 owner 署名 |
| 数据与切片 | 声明数据来源、分布与必须单独看的风险切片 | 数据与切片声明 |
| Composite Oracle | 声明每类判断由规则、语义 Judge 还是人工负责 | Oracle 分工表 |
| 指标与阈值 | 在前四项都定下来之后才选指标，并写明阈值来源 | 指标卡（含阈值来源） |
| 报告与 stop state | 写明什么条件下停止迭代——达标、证据不足、或预算耗尽 | stop state 定义 |
| 人工发布决定 | 留下具名签字，包括「接受了哪些已知失败模式」 | 发布决策记录 |

> 第一列的节点名与页面架构图逐字一致，由门禁校验；改图必须同步改这张表，否则构建失败。

### 一份合同必须写清的八项

八项缺任何一项，这次评测的结论都无法被第二个人正确解读。

右列写的是缺失时会被问倒的那个问题。

| 必写项 | 内容 | 缺失时会被问倒 |
| --- | --- | --- |
| 发布问题 | 要支撑哪个决定 | 这个分数用来干什么 |
| 被测对象 | 四维版本 | 测的是哪个版本 |
| 数据分布 | 样本来源与切片 | 这些样本代表什么 |
| Oracle | 判据与独立来源 | 期望值从哪来 |
| 阈值 | 取值与来源 | 为什么是这个数 |
| 统计口径 | 重复次数与区间方法 | 这个数有多确定 |
| stop state | 何时停止并升级 | 证据不足时怎么办 |
| owner | 负责人 | 谁决定例外 |

> 第五项的「来源」比取值本身更重要：写明它是实测 N 个周期还是结构占位，决定了别人能不能引用它。

*依据：[UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/)*

### 这一页的验收口径：Contract 本身也要被检查

Eval Contract 是文档，而文档的失败方式是「写了但没人用」。下面四条把它变成可以被机器和抽查共同验证的状态。

T01-2 是其中最容易被跳过、也最能暴露问题的一条：一个说不出与业务结果关系的指标，涨跌都没有意义。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| T01-1 | Contract 字段完整度 | 8 个必填字段（问题 / 风险 / owner / 数据 / 切片 / Oracle / 阈值来源 / stop state）缺失率 = 0 | 每次发布 |
| T01-2 | 指标构念效度 | 核心指标与业务结果的相关性 ≥ 0.6，低于此值的指标降级为参考项 | 每季度 1 次 |
| T01-3 | owner 具名率 | 3 类决策角色（语义判定 / 风险接受 / 回滚）具名率 = 100%，不接受写部门名 | 每次发布 |
| T01-4 | stop state 可判定性 | 停止条件必须能由 1 条查询或 1 次抽查得出是否成立，主观描述判为无效 | 每次发布 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在做严谨评测、实际无法支撑决定的做法

这两种做法都产出了详实的评测报告，指标也很专业。

问题是报告与决定之间没有连接。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 先选一组业界常用指标，跑出来再看结论 | 指标成熟、工具现成、结果也可比 | 指标先于问题时，你会得到一堆无法支撑任何决定的数字。应当先写发布问题，再倒推需要哪些指标 |
| 阈值参考公开基准的常见取值 | 有出处、有依据，也避免了拍脑袋 | 公开阈值对应的是公开任务的失败成本。你的场景失败一次的代价与之无关。阈值必须按自己的风险实测重设 |

> 两条的共同修法：从「这次要回答什么决定」开始，而不是从「有哪些指标」开始。

### 评测跑完但没人用时按什么顺序查

评测被忽略通常不是不准，是它不改变任何决定。按下表逐项自查。

第一行说不清的，后面几行都不用查了。

| 自查 | 不满足时的表现 | 下一步 |
| --- | --- | --- |
| 能说出它支撑哪个决定吗 | 说不出具体决定 | 下线该评测或重写发布问题 |
| Oracle 独立吗 | 期望值来自被测系统 | 换独立来源 |
| 阈值来源写了吗 | 只有数字没有出处 | 标注实测周期数或结构占位 |
| 证据不足时输出什么 | 仍然给出通过 | 补 stop state |
| 谁能批准例外 | 无人 | 指定 owner |

> 五行都答得上来的评测很少见；答不上来的那几行就是这份合同要补的内容。

### 给现有评测补一份合同：约 40 分钟

不需要改评测代码。把八项补齐，缺口自然显现。

1. 选一个正在定期跑的评测，先写出它支撑的那个发布决定——写不出来的直接标为待下线。
2. 逐项填写八项，填不出的先留空。
3. 对阈值项，写明它是实测几个周期得来的，还是从别处抄的结构占位。
4. 为 stop state 写一句话：样本量不足或 Oracle 失效时输出什么。
5. 把合同交给一位没参与的同事，请他只看合同判断这次评测能不能支撑那个决定。

**期望结果**：典型结果是八项里有三四项填不出，尤其是阈值来源与 stop state。它们正是这份评测此前无法被质疑也无法被信任的原因。

> ⚠ 填不出的项要如实留空并标注需要谁来定，不要临时编一个说法填满。空白比编造更有价值。

### 这一页的出口判据

这一页的门禁有一个不同寻常之处：它在评测开始之前执行，而不是之后。Contract 不完整时，后面跑出来的所有数字都没有解释框架。

把这道门禁放在最前面，是本课程与「先跑起来再说」的最大分歧点。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 8 个必填字段缺失率 > 0 时阻断，评测不得启动<br>3 类决策角色具名率 < 100% 时阻断，不接受以部门名代替个人 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 指标与业务结果相关性用至少 30 个历史发布点估计，样本不足时标注为未验证<br>相关性 < 0.6 的指标不得作为唯一发布依据，须并列第二指标 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 相关性未验证的新指标，由产品 owner 签字接受其解释力未知<br>stop state 选择「预算耗尽」而非「达标」时，须由发布 owner 明示这是资源约束下的妥协 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[confident-ai/deepeval](https://deepeval.com/docs/getting-started)*

### 带走一份可被第三方复核的评测合同

合同的价值在于它能被质疑：别人看完就知道这个结论适用于什么、不适用于什么。

八项里最容易缺也最关键的是「发布问题」与「阈值来源」。

- 先写发布问题，再选指标
- 阈值标注来源：实测 N 周期还是结构占位
- 写清证据不足时输出什么

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[promptfoo：Prompt 与 Agent 的断言式评测](https://www.promptfoo.dev/docs/intro/)** — AI 侧断言执行器
  - 能证明：把断言写成配置：确定性断言（contains、is-json、javascript）、语义断言与模型评判可以在同一个用例里组合，并按矩阵跑多模型多 prompt。它让「AI 输出」进入与传统测试相同的红绿流程。
  - 不能证明：模型评判本身有误差，需要与人工标注校准后才能作为门禁判据。
  - `promptfoo/promptfoo` · 版本 0.122.0（2026-08-04） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[DeepEval：pytest 风格的 LLM 评测框架](https://deepeval.com/docs/getting-started)** — AI 侧断言执行器
  - 能证明：LLM 评测可以直接寄生在 pytest 生态里：用例、fixture、参数化、CI 集成全部复用既有工程习惯，降低把评测接进流水线的成本。
  - 不能证明：指标默认阈值是框架给的示例值，不是你业务的验收线。
  - `confident-ai/deepeval` · 版本 v4.1.7（2026-07-29） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Inspect：任务 / solver / scorer 分层的模型评测框架](https://inspect.aisi.org.uk/)** — 评测框架
  - 能证明：评测可以拆成三个独立可替换的部件：dataset 定义问什么、solver 定义怎么问、scorer 定义怎么判。三者分离之后，换模型不用改判据，改判据不用改数据集——这是把一次性评测脚本变成可回归资产的结构条件。
  - 不能证明：框架不提供判据。scorer 写得对不对、数据集有没有覆盖你的风险切片，框架一概不管，全绿只说明流程跑通了。
  - `UKGovernmentBEIS/inspect_ai` · 版本 release/2025-11-28 · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[OpenAI Evals：评测样例与注册表结构](https://github.com/openai/evals#readme)** — 评测结构参考
  - 能证明：把评测注册成命名资产（registry）而不是散落的脚本，使评测可以被引用、复用与版本化，这是评测进入 CI 的前提。
  - 不能证明：仓库许可证未被自动判定，且更新已放缓；作为结构参考使用，不作为当前推荐运行时。
  - `openai/evals` · 版本 v0.1.1 · NOASSERTION · 许可证未能自动判定，按最保守口径只链接不搬代码
- **[MLflow：实验、模型与版本的登记体系](https://mlflow.org/docs/latest/)** — 版本与血缘
  - 能证明：模型、参数、数据版本与评测结果可以被登记成可检索的关联记录，使「这个结论对应哪个模型的哪次运行」成为可查询事实而不是靠人记。回滚与事后归因都依赖这条记录。
  - 不能证明：登记的是元数据不是质量。记录齐全的模型同样可以是差模型。
  - `mlflow/mlflow` · 版本 v3.15.1（2026-08-03） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[DVC：数据与流水线的版本控制](https://dvc.org/doc)** — 数据版本
  - 能证明：评测集必须与代码一样可版本化：同一个 commit 能取回当时用的那份数据。缺了这一条，历史评测分数之间不可比，回归判断也就不成立。
  - 不能证明：版本可追不代表数据集设计合理；污染与分布偏移不会因为版本化而消失。
  - `iterative/dvc` · 版本 3.67.1（2026-03-31） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
