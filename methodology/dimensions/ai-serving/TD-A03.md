## TD-A03

### 指标算错分母，比不算更危险

AI serving 的指标看起来和普通服务一样：延迟、吞吐、成功率。但它们的分母都变了，而分母的变化不会体现在指标名字上。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 用请求数做吞吐分母 | 一次任务可能包含 5～15 次生成调用，请求数与业务完成量之间没有固定比例 | 吞吐数字很高，无法换算成业务容量 |
| 把 TTFT 和端到端时长混用 | 流式场景下两者可相差 1 个数量级以上；混用会让体验结论与容量结论互相污染 | 为了压端到端时长去限制输出长度，体感并没有改善 |
| 成功率不扣除质量不达标的完成 | 完成但质量不达标的任务在成功率里被计为成功，两者差额即 Goodput 与吞吐的差距 | 成功率 95% 而用户可用率远低于此 |

> 本页把每个指标的分母写清楚：TTFT 分母是请求，Goodput 分母是达标完成的任务，成本分母是 good task。

### 四个体感指标的准确含义

这四个词经常被混用，但它们测的是用户体验的不同片段。

| 术语 | 一句话解释 |
| --- | --- |
| TTFT | 请求到首 token；用户看到「开始出字」的等待 |
| TPOT | 生成阶段每 token 平均间隔；决定出字快慢 |
| ITL | 相邻 token 的实际间隔序列；比 TPOT 多了抖动信息 |
| Goodput | 满足 SLO 前提下的成功吞吐；容量规划看它，不看裸 QPS |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[vllm-project/vllm](https://docs.vllm.ai/)*

### 指标算错分母，比不算更危险

TTFT（首 token 时间）、TPOT（每 token 时间）、ITL（token 间隔）、Goodput（有效吞吐）这四个指标看起来都在描述「快不快」，实际上分母完全不同，因此它们回答的是四个不同的问题。混着用会得到自洽但错误的结论。

TTFT 的分母是请求数，它包含排队与 prefill，反映的是「用户等了多久才看到第一个字」。TPOT 的分母是输出 token 数，反映的是「打字速度」。一个 TTFT 很差但 TPOT 很好的系统，用户体感是「卡了很久然后刷刷刷」；反过来是「立刻开始但一个字一个字蹦」。两者的修法完全不同——前者查排队与 prefill，后者查 decode 与批处理。

Goodput 是最容易被算错的一个：它的分母不是全部请求，而是**满足 SLO 的请求**。一个系统可以有很高的吞吐量和很低的 goodput——它接了很多请求，但大部分慢到用户已经放弃。只报吞吐不报 goodput，是容量报告里最常见的粉饰。

计算这四个指标的前提是有正确的时间戳事件：请求到达、开始排队、开始 prefill、首 token、每个后续 token、完成。缺任何一个事件，对应的指标就只能靠推算，而推算出来的数字通常在系统承压时误差最大——恰恰是最需要它准确的时候。

*依据：[vllm-project/vllm](https://docs.vllm.ai/) · [prometheus/prometheus](https://prometheus.io/docs/practices/histograms/)*

### 四个指标的分母与所需时间戳事件

第二列是这一页的关键。分母不同的指标不能相互替代，也不能放在同一张图上比较。

第四列写的是缺少该时间戳时会发生什么——注意它们都不是「算不出来」，而是「算出一个错的」，这更危险。

| 指标 | 分母是什么 | 需要哪些时间戳 | 缺时间戳的后果 |
| --- | --- | --- | --- |
| TTFT | 请求数 | 请求到达、首 token 产出 | 把排队时间算进 prefill，误判为模型慢 |
| TPOT / ITL | 输出 token 数（去掉首 token） | 每个 token 的产出时刻 | 只能用总时长除以 token 数，把 TTFT 摊进去，低估真实打字速度 |
| Goodput | 满足 SLO 的请求数 | 上述全部 + SLO 判定结果 | 退化成普通吞吐，掩盖「接了很多但都太慢」 |
| 排队时间 | 请求数 | 到达时刻、开始 prefill 时刻 | 变慢时无法区分资源不足与排队策略问题 |

> 四行需要的时间戳是累加的。埋点时一次埋齐，比事后为某个指标补埋要便宜得多。

*依据：[vllm-project/vllm](https://docs.vllm.ai/) · [prometheus/prometheus](https://prometheus.io/docs/practices/histograms/) · [open-telemetry/semantic-conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/) · [triton-inference-server/server](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/)*

### 从时间戳事件算出四个指标

这四个指标不能从网关日志直接得到，必须从 token 级事件时间戳算。缺少事件采集时，任何数字都是估计。

右列写的是分母——分母不写清楚，两份报告永远对不上。

| 指标 | 从哪些事件算 | 分母是什么 |
| --- | --- | --- |
| TTFT | 请求发出 → 首个 token 事件 | 请求数 |
| TPOT | (末 token 时间 − 首 token 时间) ÷ (token 数 − 1) | 请求数 |
| ITL 抖动 | 相邻 token 时间差序列的分位 | token 间隔数 |
| Goodput | 满足 SLO 的成功请求数 ÷ 时长 | 时间 |
| 单位成功成本 | 总花费 ÷ 成功完成数 | 成功数，不是请求数 |

> 最后一行最容易错：用请求数做分母会把失败请求的成本摊薄，掩盖真实浪费。

*依据：[triton-inference-server/server](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/)*

### 这一页的验收口径：每个指标都要写清分母

本页四条指标的共同要求是分母显式声明。同一个「成功率」在不同分母下可以相差十几个百分点，而报告上看不出区别。

A03-4 的切片声明同样重要：整体达标而某个切片严重不达标，是最常见也最难发现的形态。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| A03-1 | 分母声明 | 每个对外指标显式声明分母的比例 = 100% | 每次报告 |
| A03-2 | 体感延迟 | TTFT 的 p95 < 2 秒；与端到端时长分开报告 | 每次发布 |
| A03-3 | 有效产出 | Goodput 以达标完成任务计量；以请求数表述吞吐的结论数 = 0 | 每次容量评估 |
| A03-4 | 切片覆盖 | 按风险切片分别出分的比例 = 100%；仅报整体的次数 = 0 | 每次评测 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

*依据：[prometheus/prometheus](https://prometheus.io/docs/practices/histograms/)*

### 两种看起来在测体感、实际测不出体感的做法

这两种做法都用了正确的指标名，报表也很规范。

问题在测量位置与聚合方式。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 用网关的响应时间做 TTFT | 网关是统一入口，采集成本最低 | 网关记录的是整个响应完成时间，不是首 token 时间。流式场景下两者可以差几十倍 |
| 报 TTFT 与 TPOT 的平均值 | 均值是最常用的汇总方式，也便于趋势对比 | 两者都是长尾分布。平均值既不代表典型用户也不代表最差用户，必须报分位数并按任务类型分桶 |

> 两条的共同要求：采集要到 token 级，汇总要用分位数。

### 指标正常但用户抱怨慢时按什么顺序查

体感与指标脱节几乎总是测量位置或分桶问题。下表四行覆盖绝大多数情况。

查完之后通常会发现：慢的是某一类特定请求，被平均掉了。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 整体分位正常但投诉集中 | 未按任务类型分桶 | 把长输出任务单独成桶 |
| TTFT 好但用户说卡 | ITL 抖动大 | 看相邻 token 间隔的分位而不是均值 |
| 数字与网关日志对不上 | 测量位置不同 | 统一到 token 事件时间戳 |
| 吞吐涨了满意度降了 | 用了裸 QPS | 改用 Goodput，分母是满足 SLO 的成功数 |

> 第二行经常被忽略：平均出字速度正常，但每隔几个字卡一下，体感会非常差。

### 从一次真实调用的事件流算出四个指标：约 35 分钟

取一条完整的 token 级事件记录，手工算一遍。算过一次，之后看报表就知道它对不对。

1. 取一次真实调用的完整事件序列，含请求时刻与每个 token 的到达时刻。
2. 算 TTFT：首 token 时刻减请求时刻。
3. 算 TPOT：末 token 减首 token，除以 token 数减一。
4. 算 ITL 抖动：把相邻间隔排序，取 p50 与 p95，看两者差距。
5. 把这四个数与你们现有监控面板上的对应数字比较，差异超过一成的，说明采集位置不同。

**期望结果**：手算结果与面板数字往往不一致，差异来源通常是网关时间与 token 事件时间的混用。找出这个差异比新增任何指标都有价值。

> ⚠ 不要用一次调用的结果下结论。这个演练的目的是校准测量方法，不是评估性能。

### 这一页的出口判据

这道门禁拦的是分母不明的指标。一个分母不清楚的 95%，其信息量低于一个分母清楚的 78%。

第三段要接受的是「达标」这个判定标准本身——它决定了 Goodput 的分子，而它是产品决策不是技术推导。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 指标未声明分母的数量 > 0 时阻断报告发布<br>以请求数表述容量结论的次数 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 延迟与成本报分位；比例类指标附 95% CI<br>单切片样本 < 30 条时该切片只报区间不报点估计 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 「达标完成」的判定标准，由产品 owner 确定并署名<br>未单独出分的长尾切片范围，由测试负责人列出并接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一份写明测量位置与分母的指标定义

定义要写清三件事：从哪个事件算起、分母是什么、按什么分桶。

三者一致时，两个团队的报告才能放在一起比较；否则只是两组各自正确的数字。

- 采集到 token 级事件，不用网关响应时间
- 报分位数并按任务类型分桶
- 单位成功成本的分母是成功数，不是请求数
