## TD-A02

### 最终文本正确，不代表中途没出事

流式、结构化、工具调用、异步这四种协议各自有中途失败的方式，而它们的共同特点是：最终那段文本看起来完全正常。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 只断言 SSE 合并后的最终文本 | 流中途的错误事件、重复分片、提前中断在合并后 100% 不可见 | 用户看到内容突然截断，而测试全绿 |
| 结构化输出只校验 Schema | Schema 合法但语义错误的输出无法被格式校验发现；这类失败在只做结构校验时检出率为 0 | 字段齐全、类型正确，金额算错了 |
| 异步任务只看提交响应 | 提交返回 202 时任务尚未执行；不核对终态时后台失败的检出率为 0 | 提交成功率 100%，实际完成率远低于此 |

> 本页的做法：为四种协议各建一个状态机，逐状态断言而不是只断言终态。

### 四种协议形态的关键词

AI API 的四种交互形态各有各的中途失败方式，最终文本都看不出来。

| 术语 | 一句话解释 |
| --- | --- |
| SSE 流 | 服务端逐段推送；连接中断与最后一段缺失在最终拼接文本里看不出来 |
| 结构化输出 | 按 Schema 返回；结构合法不等于语义正确 |
| 工具调用 | 模型请求执行外部函数；副作用发生在你的系统里，不在模型里 |
| 异步任务 | 提交后轮询；任务 ID 丢失或状态机漏态会造成静默失败 |

### 最终文本正确，不代表中途没出事

流式接口的测试很容易退化成「把所有 chunk 拼起来，断言最终文本」。这样做等于把流式接口当成了普通接口——中途的所有状态转移都没有被检查，而事故恰恰发生在那里。

具体形态包括：事件顺序错乱（工具调用事件出现在内容事件之后）、终止事件缺失（连接关闭但没有明确的完成信号，客户端无法区分「说完了」和「断了」）、中断后仍继续计费、错误事件被夹在正常内容中间导致客户端解析崩溃。

结构化输出的流式形态更麻烦：JSON 在传输过程中始终是不完整的，客户端必须能处理部分解析。测试必须覆盖「在任意位置中断」这个场景，断言客户端不会把半个 JSON 当成完整结果处理。

异步任务形态则引入了第三种状态机：提交返回任务 id，随后轮询或回调。这里的经典问题是终态定义不清——任务状态从 running 变成 failed 之后还能不能变回 running？重试是新任务还是同一个任务？这些必须在契约里写死，否则客户端的状态机与服务端的不一致。

*依据：[huggingface/text-generation-inference](https://huggingface.co/docs/text-generation-inference/) · [vllm-project/vllm](https://docs.vllm.ai/)*

### 四种协议形态各自必须断言的状态转移

第三列是这张表的核心：每一种形态都有一个「最容易被跳过、也最容易出事」的断言点。

四种形态可能在同一个产品里同时存在，且它们的客户端处理逻辑互不通用——这是集成测试必须覆盖每一种的原因。

| 协议形态 | 关键状态转移 | 最容易被跳过的断言 | 工具 |
| --- | --- | --- | --- |
| SSE 流 | 开始 → 内容片段 → 终止事件 | 终止事件必须存在且可与连接断开区分 | 自建 SSE 事件序列断言 |
| 结构化输出 | 不完整 JSON → 完整 JSON | 任意位置中断时，客户端不得把半个 JSON 当完整结果 | jsonschema + 截断注入 |
| 工具调用 | 内容 → 工具调用 → 工具结果 → 内容 | 事件顺序与工具结果回填的时序 | MCP 契约 + 事件顺序断言 |
| 异步任务 | 提交 → running → 终态 | 终态是否不可逆；重试是新任务还是同一任务 | 状态机断言 + 幂等键 |

> 四行的共同纪律：断言状态转移序列，而不只是最终结果。最终结果对了但序列错了，客户端仍然会挂。

*依据：[huggingface/text-generation-inference](https://huggingface.co/docs/text-generation-inference/) · [python-jsonschema/jsonschema](https://python-jsonschema.readthedocs.io/) · [modelcontextprotocol/modelcontextprotocol](https://modelcontextprotocol.io/) · [RFC 9110：HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html)*

### 四种形态各自必须断言的状态转移

每种形态都有一个状态机。不按状态机测，就只能测到 happy path。

右列是这一形态最典型的中途失败——它们在最终结果上要么看不出来，要么被当成模型能力问题。

| 形态 | 必须断言的状态 | 典型中途失败 |
| --- | --- | --- |
| SSE 流 | 首包、增量、结束事件、异常终止 | 流中断后拼接文本仍然通顺，无法察觉 |
| 结构化输出 | Schema 校验、必填、枚举、finish_reason | 被截断的 JSON 恰好合法 |
| 工具调用 | 请求、授权、执行、结果回填、失败回退 | 授权通过但执行失败，模型继续按成功推理 |
| 异步任务 | 已提交、处理中、成功、失败、超时、取消 | 任务丢失后无人发现，用户一直等 |

> 四行的共同点：最终返回值正常，而中途已经发生了不可接受的事情。

*依据：[modelcontextprotocol/modelcontextprotocol](https://modelcontextprotocol.io/)*

### 这一页的验收口径：逐状态而非只看终态

A02-1 到 A02-3 分别对应三种协议的中途失败。它们的共同点是：都需要在过程中断言，事后无法补测。

A02-4 要求结构与语义分别出分，理由与 TD-PS02 相同——合并后语义问题会被结构的高通过率掩盖。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| A02-1 | 流式完整 | 流中断、重复分片、错误事件的检出率 = 100% | 每次发布 |
| A02-2 | 工具调用保护 | 工具调用前完成权限校验与幂等检查的比例 = 100% | 每次发布 |
| A02-3 | 异步终态核对 | 以业务终态而非提交响应判定完成的比例 = 100%；两者不一致率 ≤ 1% | 每日 |
| A02-4 | 结构语义分离 | PASS_SCHEMA 与 PASS_SEMANTIC 分别出分的比例 = 100% | 每次评测 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来测了流式与工具、实际只测了终态的做法

这两种做法在联调阶段都能通过，也确实覆盖了主要路径。

问题是断言点全在最后。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 把 SSE 流拼接成完整文本后断言内容 | 这是用户最终看到的东西，断言它最直接 | 流在中途断开时，已收到的部分往往仍然通顺。必须断言结束事件是否收到，以及增量序号是否连续 |
| 断言工具被调用了且返回 200 | 调用发生了、外部系统也返回成功 | 要断言的是副作用本身：数据真的写了吗、写了几次、幂等键起作用了吗。工具返回 200 不等于业务状态正确 |

> 两条都指向同一件事：断言点必须放在中途，不能只放在最后。

### 偶发的用户投诉查不到日志时按什么顺序查

四种形态的中途失败在常规日志里往往不留痕。下表给出各自的补采集点。

补齐采集之后，多数「偶发」会立刻变成可复现。

| 症状 | 先怀疑 | 补什么采集 |
| --- | --- | --- |
| 回答突然中断但无报错 | SSE 流异常终止 | 记录结束事件与增量序号 |
| JSON 解析偶尔失败 | 输出被截断 | 记录 finish_reason 与输出长度 |
| 数据写了两次 | 工具重试无幂等 | 记录幂等键与调用次数 |
| 用户说提交了没结果 | 异步任务丢失 | 记录任务 ID 全生命周期状态 |

> 四行都是采集问题而不是分析问题——采集补齐前，任何分析都是猜。

### 给一种协议形态补齐状态断言：约 50 分钟

挑你系统里用得最多的那一种，先把它的状态机画出来。

1. 选一种形态（建议从流式或工具调用开始），画出它的完整状态机，含异常分支。
2. 对照现有测试，标出哪些状态转移已经被断言、哪些没有。
3. 为未覆盖的异常分支各写一条测试：流中断、输出截断、工具失败、任务超时。
4. 对工具调用类，追加副作用断言：写入次数、幂等键生效、失败后是否回滚。
5. 跑一遍，确认这些新用例在正常路径上是绿的，在注入对应故障时会变红。

**期望结果**：典型结果是：现有测试覆盖了状态机的正常路径，异常分支覆盖率接近零。补完之后会立刻抓到一到两个此前不知道的问题。

> ⚠ 异常分支测试必须真的注入异常，不能用 mock 直接返回异常状态。mock 会跳过真正容易出错的那段处理逻辑。

### 这一页的出口判据

这道门禁作用在四种协议的中途状态上。只断言终态的测试无法进入这道门禁，因为它没有可供判定的证据。

第三段要接受的是异步终态的观测窗口：提交与完成之间总有时间差，这段窗口内的不一致必须被承认。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 工具调用前未完成权限校验或幂等检查的次数 > 0 时阻断<br>以提交响应代替业务终态判定完成的用例数 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 提交响应与业务终态的不一致率给出 95% CI 上界，与阈值比较用上界<br>异步任务样本 < 200 条时终态一致性结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 提交与完成之间的观测窗口长度，由架构 owner 签字确定<br>PASS_SCHEMA 与 PASS_SEMANTIC 之间的残余差距，由测试负责人接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[python-jsonschema/jsonschema](https://python-jsonschema.readthedocs.io/)*

### 带走四张状态机与它们的异常分支清单

状态机不需要精美，能标出异常分支即可。它的作用是让「我们测过流式」变成「我们测过流式的哪几种断法」。

异常分支清单是长期资产：每次协议升级都对照它检查一遍。

- 断言点放在中途状态，不只放在最终返回
- 工具调用断言副作用本身，不断言返回码
- 异常分支必须真的注入，不用 mock 跳过

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[jsonschema：JSON Schema 校验实现](https://python-jsonschema.readthedocs.io/)** — 结构断言实现
  - 能证明：结构层断言可以脱离具体框架独立运行，包括在 LLM 结构化输出上——这是传统 Schema 校验能力迁移到 AI 系统时最直接的一条通路。
  - 不能证明：校验通过只说明形状对。LLM 返回一个字段齐全、类型正确但内容编造的 JSON，Schema 校验会放行。
  - `python-jsonschema/jsonschema` · 版本 v4.26.0（2026-01-07） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[RFC 9110：HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html)** — 协议层权威定义
  - 能证明：幂等在 HTTP 里的准确定义：多次相同请求对服务器的预期效果与单次相同。它明确 PUT/DELETE 幂等而 POST 不幂等——这正是取消/退款这类 POST 接口必须自己引入幂等键的协议依据。
  - 不能证明：规范定义的是方法语义的期望，不强制实现遵守。你的 POST 加没加幂等键、加了是否生效，只能靠测试证明。
  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理
- **[Model Context Protocol 规范](https://modelcontextprotocol.io/)** — 工具契约规范
  - 能证明：模型可调用的工具有了机器可读契约：名称、输入 schema、描述、错误返回。这让「Agent 能调什么工具」从代码里的隐含事实变成可审计、可版本化、可做契约测试的工件。
  - 不能证明：规范描述接口不描述权限。哪些工具允许被哪个会话调用、不可逆动作要不要二次确认，规范里没有，必须在工具调用层自己实现并验证。
  - `modelcontextprotocol/modelcontextprotocol` · 版本 2026-07-28（2026-07-28） · NOASSERTION · 许可证未能自动判定，按最保守口径只链接不搬代码
- **[vLLM：高吞吐推理服务引擎](https://docs.vllm.ai/)** — 推理服务实现
  - 能证明：生成式服务的延迟由两个阶段构成：prefill 处理输入、decode 逐 token 产出。连续批处理会把不同请求混在同一批里，因此单个请求的延迟取决于同时在跑的其他请求——这是传统 QPS 模型解释不了生成式服务表现的根本原因。
  - 不能证明：引擎指标反映的是服务端状态，不等于用户体感；托管 API 通常不暴露这些指标，此时只能从客户端阶段指标推断并标记未知。
  - `vllm-project/vllm` · 版本 v0.27.1（2026-08-11） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Text Generation Inference：生成式服务的参考实现](https://huggingface.co/docs/text-generation-inference/)** — 推理服务实现
  - 能证明：生成式服务对外暴露的协议形态与参数面：流式与非流式、停止条件、最大 token、并发限制，以及它们如何共同决定尾延迟。
  - 不能证明：参考实现的默认值不是你的配置；限流与排队策略差异会让同样的硬件产出完全不同的容量曲线。
  - `huggingface/text-generation-inference` · 版本 v3.3.7（2025-12-19） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
