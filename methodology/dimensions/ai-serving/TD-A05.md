## TD-A05

### 同一个「变慢了」，可能来自五个完全不同的地方

排队、prefill、decode、KV Cache、下游依赖——这五处都会表现为延迟上升，而它们的修复手段完全不同。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 看到 TTFT 上升就加 GPU | TTFT 上升有排队、prefill、准入 3 个可能来源；不分段时归因正确率接近随机 | 扩容后延迟没有改善，因为瓶颈在准入队列 |
| 同时改多个变量做优化 | 同时改 2 个变量时归因需要至少 3 次实验；一次实验的结论不可归因 | 优化有效但不知道是哪一项起的作用，下次无法复用 |
| 忽略 KV Cache 压力 | 长上下文占用的显存随上下文长度线性增长，传统 CPU/内存指标对它的可见度为 0 | 资源指标全绿，而实际已经在因显存不足而排队 |

> 本页的做法：先按症状定位到段，再在该段内做单变量实验。

### 推理服务的四个阶段词

「慢」在推理服务里有四个完全不同的位置，修法互不相同。

| 术语 | 一句话解释 |
| --- | --- |
| 排队 | 请求已到达但尚未开始处理；表现为 TTFT 上升而生成速度正常 |
| prefill | 处理输入上下文的阶段；受输入长度影响最大 |
| decode | 逐 token 生成阶段；受输出长度与批处理影响 |
| KV Cache | 缓存注意力键值的显存区域；逐出频繁时 decode 会明显变慢 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[vllm-project/vllm](https://docs.vllm.ai/)*

### 同一个「变慢了」，来自四个完全不同的阶段

生成式服务的一次请求要经过四个阶段：排队、prefill（处理输入）、decode（逐 token 产出）、以及 KV 缓存的分配与回收。四个阶段的瓶颈信号不同、修法不同，而它们在端到端延迟上表现为同一个数字。

排队变长说明容量不足或调度策略有问题，修法是加资源或改优先级；prefill 变慢说明输入变长或批处理配置不当，修法是限制上下文长度或调整批策略；decode 变慢通常是并发请求数上升导致的批内竞争，修法是限流；KV 缓存不足会触发抢占与重算，表现为延迟突然出现长尾。

连续批处理让这件事更反直觉：单个请求的延迟取决于同时在跑的其他请求。因此「这个请求为什么慢」在生成式服务里往往不是这个请求的问题——它可能只是恰好和一批长请求排在了一起。这也是为什么传统的「重放这个慢请求看看」的排查方法在这里经常复现不出来。

把四个阶段分开观测是唯一可靠的排查路径。缺了阶段分解，团队只能在「加机器」和「换模型」之间猜，而这两个动作恰好是最贵的两个。

*依据：[vllm-project/vllm](https://docs.vllm.ai/) · [triton-inference-server/server](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/)*

### 四个阶段各自的信号与修法

这张表是排查顺序表：从上往下逐阶段排除，而不是直接跳到「模型太慢」这个结论。

第四列写的是修法，注意它们的成本差异很大——排队与批配置问题的修复成本远低于换模型。

| 阶段 | 变慢的信号 | 根因方向 | 修法 |
| --- | --- | --- | --- |
| 排队 | 队列长度上升，排队时间占端到端比例升高 | 容量不足或调度策略不当 | 加实例、改优先级、限流保护 |
| prefill | TTFT 随输入长度显著上升 | 上下文过长或批处理配置不当 | 限制上下文长度、调整批策略、启用前缀缓存 |
| decode | TPOT 上升且与并发数正相关 | 批内竞争，同时在跑的请求太多 | 限并发、分级队列、隔离长请求 |
| KV Cache | 延迟出现突发长尾，伴随抢占或重算计数上升 | 缓存容量不足触发抢占 | 扩显存、限制最大上下文、调整并发上限 |

> 四行按排查顺序排列。跳过前三行直接换模型，是这一页要避免的那个最贵的决定。

*依据：[vllm-project/vllm](https://docs.vllm.ai/) · [sgl-project/sglang](https://docs.sglang.ai/) · [triton-inference-server/server](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/) · [prometheus/prometheus](https://prometheus.io/docs/practices/histograms/)*

### 四个阶段各自的信号与修法

定位阶段靠信号组合，不靠单一指标。下表给出每个阶段最有区分度的信号。

右列的修法互不通用——排队问题加显存没用，显存问题调并发也没用。

| 阶段 | 最有区分度的信号 | 有效修法 |
| --- | --- | --- |
| 排队 | 队列深度上升、TTFT 上升、TPOT 稳定 | 调并发上限或扩容 |
| prefill | TTFT 随输入长度线性上升 | 缩短系统提示、启用前缀缓存 |
| decode | TPOT 上升、批大小下降 | 调批处理策略 |
| KV Cache | 显存接近上限、逐出计数上升 | 限制并发长上下文请求 |
| 下游依赖 | 工具 span 耗时上升而模型指标正常 | 单独压该依赖 |

> 五行的判别关键是「TTFT 与 TPOT 谁在动」：只有 TTFT 动是排队或 prefill，TPOT 动是 decode 或显存。

*依据：[sgl-project/sglang](https://docs.sglang.ai/)*

### 两种看起来在定位瓶颈、实际在猜的做法

这两种做法都会给出一个听起来合理的结论，也常常真的让指标改善了一点。

问题是结论无法被验证，下次同样的症状还得重新猜。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 延迟高就扩容，扩完确实变快了 | 扩容缓解了症状，数据也支持 | 扩容对四个阶段都有一点效果，因此它无法证明瓶颈在哪。下次流量再涨还得继续扩，成本线性上升 |
| 同时调整并发、批大小和超时，整体改善明显 | 三项都是合理参数，一起调效率更高 | 无法归因也无法回滚。其中某一项可能是负作用，被另外两项掩盖了 |

> 两条的共同修法：一次只改一层，并记录改动前后的阶段信号。

### 服务变慢时的标准排查顺序

按下表从上到下走，每一步都能用现有指标回答，不需要新增采集。

走到哪一行停下来，瓶颈就在那一层。

| 先看什么 | 如果是 | 结论 |
| --- | --- | --- |
| 队列深度是否上升 | 是 | 排队瓶颈，调并发或扩容 |
| TTFT 是否随输入长度上升 | 是 | prefill 瓶颈，缩短上下文 |
| TPOT 是否上升 | 是 | decode 或显存瓶颈 |
| 显存是否接近上限 | 是 | KV Cache 逐出，限长上下文并发 |
| 模型指标正常但总时长长 | 是 | 下游依赖瓶颈 |

> 五行按判别成本排序。前两行用现成指标就能判断，不需要进入推理引擎内部。

### 做一次单变量瓶颈验证：约 60 分钟

先用上表定位到一个候选阶段，然后只改这一层，看拐点是否右移。

1. 用上表的五步排查定位到一个候选阶段，写下判断依据。
2. 设计一个只影响该阶段的改动：排队改并发上限，prefill 缩短系统提示，decode 调批大小，显存限制长上下文并发。
3. 保持其余全部参数与 workload 不变，重压一次。
4. 比较 SLO 拐点是否右移，以及该阶段的信号是否回落。
5. 若拐点未动，说明判断错误，回到第一步换下一个候选——这也是有效结论。

**期望结果**：产出是一份带前后信号对比的瓶颈证据。判断错误同样有价值：它排除了一个候选，缩小了范围。

> ⚠ 不要在验证过程中同时更新模型版本或推理引擎版本。那会让前后对比失去意义。

### 这一页的出口判据

这道门禁拒绝没有信号支撑的瓶颈判断。诊断的价值在于它能被复核，而不在于它听起来合理。

第三段要接受的是托管服务的不可见部分：用的是别人的推理服务时，很多内部信号根本拿不到。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 单次实验变动变量数 > 1 时阻断，结论不可归因<br>五类信号采集覆盖率 < 100% 时阻断诊断结论，证据不完整 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 单变量实验以配对比较给出差值的 95% CI，区间跨 0 即判为未测出影响<br>配对样本 < 50 条时实验结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 托管推理服务内部不可观测的范围，由架构 owner 列出并签字接受<br>标记为 UNKNOWN 的症状比例，由测试负责人确认可接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。
