## TD-A01

### 把生成式接口当普通 REST 测，五个测试面里只覆盖了一个

普通 API 的契约是「同样输入给同样输出」。生成式接口没有这个契约，它有的是版本化的行为、算力约束和按量计费——这三件事在传统接口测试里都不存在。

下面三条是沿用普通 API 思路时漏掉的部分。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 只测协议层不测生成 manifest | 生成结果由模型版本、提示版本、解码参数共同决定，这 3 类字段任一变化都会让历史结果失去可比性 | 接口没改而输出变了，被归因为「模型不稳定」 |
| 不记录 token 与成本 | 生成式接口按量计费，单次调用成本可相差 1～2 个数量级；不记录时超支无法归因到具体调用 | 月底账单超预算，而所有接口指标都在阈值内 |
| 用固定断言校验响应文本 | 同一请求两次返回的措辞不同是正常行为，逐字断言的失败率接近 100% | 把正常的非确定性当成缺陷，测试很快被禁用 |

> 本页把被测面拆成五层：协议、模型行为、算力、成本、生产可靠性，各自有各自的判据。

### 分清普通 API 与生成式 API 的四个词

两者都是 HTTP，但可测量的对象完全不同。下面四个词决定你会不会用错测试方法。

| 术语 | 一句话解释 |
| --- | --- |
| 确定性响应 | 同一请求同一结果；传统 API 的默认假设，生成式 API 不成立 |
| 版本化生成服务 | 模型、Prompt、参数共同决定行为；接口不变时行为仍可能变 |
| 能力边界 | 服务能做什么与不能做什么；它不写在 OpenAPI 里，只能靠测量 |
| 单位成功成本 | 每个成功完成的调用花费；生成式服务的核心经济指标 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[vllm-project/vllm](https://docs.vllm.ai/)*

### 生成式接口与普通 REST 的差别不在协议，在契约的确定性

普通 REST 接口的契约是确定的：同样的输入必然得到同样的输出，因此断言可以写成等值比较。生成式接口的契约在语义层是确定的（回答必须正确、必须引用给定上下文、必须是合法 JSON），在字面层不是——同样的输入两次措辞不同，等值断言必然失败。

这个差别把测试面从一个扩成五个：协议与流式状态机、结构化输出的可解析性、语义正确性、资源消耗（token 与成本）、能力边界（拒答、截断、限流）。传统 REST 测试只覆盖第一面，而生产事故大量发生在后四面。

「版本化生成服务」这个词的意义在这里：一个生成式接口的行为由模型版本、提示词版本、解码参数、上下文组装逻辑共同决定。任何一项变化都是一次接口变更，尽管 OpenAPI 文档一个字都没改——这是它与普通 REST 最反直觉的一处。

单位成功成本是生成式接口独有的一等指标。普通接口的成本近似固定，可以忽略；生成式接口的单次成本可以相差两个数量级，且与输入长度、输出长度、重试次数直接相关。不测它，容量结论就是不完整的。

*依据：[vllm-project/vllm](https://docs.vllm.ai/) · [huggingface/text-generation-inference](https://huggingface.co/docs/text-generation-inference/)*

这张表按测试面分行，而不是按工具分行。同一个工具可能出现在多行，但它在每一行负责的事情不同。

| 测试面 | 工具 | 它负责什么 | 边界 |

| 结构化输出 | jsonschema | 结构层判据独立执行，可直接校验模型返回是否满足下游消费契约 | 形状对不等于内容对 |

### 同一张契约图上的五个测试面

普通 REST 只需要测协议与业务。生成式 API 多出三个面，而这三个面通常没人负责。

右列写的是这一面缺失时会在什么时候暴露——多数是在生产的第一个高峰或第一次模型更新时。

| 测试面 | 普通 REST | 生成式 AI API | 缺失时何时暴露 |
| --- | --- | --- | --- |
| 协议 | 状态码、Schema、错误 | 增加流式、工具调用、异步任务 | 联调阶段 |
| 业务 | 业务规则正确性 | 同上，但无唯一答案 | 验收阶段 |
| 模型行为 | 不适用 | 非确定性、拒答、截断、长上下文 | 上线后第一周 |
| 算力 | 不适用 | 显存、批处理、KV Cache、排队 | 第一个流量高峰 |
| 成本 | 通常可忽略 | token 长尾、重试放大、评测成本 | 第一张账单 |

> 后三面是生成式服务独有的。把它们交给「后续优化」，等于把最贵的三类问题推到生产暴露。

*依据：[vllm-project/vllm](https://docs.vllm.ai/)*

### 这一页的验收口径：五层各自达标

A01-1 是普通 API 也有的一层，其余四条是生成式接口特有的。它们不能互相折抵：协议层全绿而成本失控，结论是不通过。

A01-3 把成本设为一等指标——在按量计费的接口上，成本失控与质量失控一样会中断服务。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| A01-1 | 协议与鉴权 | 状态码、鉴权与限流断言通过率 = 100% | 每次提交 |
| A01-2 | 生成可比性 | 生成 Manifest 的 3 类版本字段缺失率 = 0 | 每次调用 |
| A01-3 | 成本可归因 | 调用级 token 与成本记录缺失率 = 0；单次调用成本 p99 ≤ 预算上限 | 每日 |
| A01-4 | 错误分类 | 错误可分类到协议 / 鉴权 / 限流 / 模型 / 下游之一的比例 ≥ 95% | 每周 1 次 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

*依据：[huggingface/text-generation-inference](https://huggingface.co/docs/text-generation-inference/)*

### 两种看起来在测 AI API、实际只测了 HTTP 的做法

这两种做法都能产出完整的接口测试报告，覆盖率也很好看。

它们的共同问题是把生成式服务当成了确定性服务。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 按 OpenAPI 生成契约测试，字段与状态码全覆盖 | 契约测试是接口质量的标准做法，自动化程度也高 | OpenAPI 描述不了非确定性、拒答、截断与能力边界。契约全绿的服务可能每三次调用就有一次给出不可用的内容 |
| 用固定 Prompt 做冒烟，返回 200 且非空即通过 | 这是最省事也最稳定的可用性探针 | 200 与非空是最弱的判据。模型完全跑题、拒答、或返回被截断的半个 JSON，都会通过这个探针 |

> 两条的共同修法：把「模型行为」当成一个独立的、必须有人负责的测试面。

### 接口测试全绿但用户投诉时按什么顺序查

生成式服务的投诉往往落在测试完全没覆盖的三个面上。下表按排查成本从低到高排列。

前两行不需要压测环境，当天就能查。

| 症状 | 先怀疑哪个面 | 下一步检查 |
| --- | --- | --- |
| 同样的问题有时好有时坏 | 模型行为 | 同输入重复 5 次，看结果分布 |
| 回答被截断或答非所问 | 模型行为 | 断言 finish_reason 与输出完整性 |
| 高峰期明显变慢 | 算力 | 看排队深度与 KV Cache 命中 |
| 账单远超预算 | 成本 | 看 token 用量 P99 与重试次数 |
| 模型更新后集体变差 | 版本化 | 检查是否用了浮动模型别名 |

> 最后一行是最隐蔽的：接口没改、代码没改、模型别名指向的版本变了。

### 给一个在用的 AI API 做五面盘点：约 30 分钟

不需要工具。把当前的测试用例按五个面分类，看哪几面是空的。

1. 列出这个 AI API 目前所有的自动化测试用例。
2. 按协议、业务、模型行为、算力、成本五个面给每条分类。
3. 统计每个面的用例数——通常后三面加起来是零。
4. 对空白的面，各写一条最小可行的检查：模型行为写重复运行分布，算力写高峰期分位延迟，成本写 token P99。
5. 确认调用时用的是固定模型版本号还是浮动别名；是别名的，列为待修。

**期望结果**：盘点结果通常是：协议与业务两面几十条，模型行为、算力、成本三面为零。这张分布图本身就是下个季度的工作计划。

> ⚠ 不要把「重复调用三次都返回 200」当作模型行为测试。它测的还是协议面。

### 这一页的出口判据

这道门禁把「接口通了」重新定义为五层同时达标。它会让通过变难，也让通过这件事重新有意义。

第三段要接受的是模型行为的不确定性——它不会因为接口设计得好而消失，只能被界定和接受。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 生成 Manifest 版本字段缺失率 > 0 时阻断，结果不可比即作废<br>调用级成本记录缺失率 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 成本与延迟一律报分位，均值不得作为判据<br>调用样本 < 500 次时成本与错误分类结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 模型行为的非确定性范围，由产品 owner 界定并签字接受<br>成本预算上限的取值，由业务 owner 确定并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一张五面覆盖分布图

分布图的价值在于它把「我们测得挺全」这个感觉换成了一个可以争论的数字。

### 来源与延伸阅读

  - 能证明：把安全扫描的 probe / detector 结构原样迁移到模型上：probe 构造诱导输入，detector 判定是否触发了不期望行为（越狱、泄露、有害输出）。传统扫描器的架构在这里是可复用的。
