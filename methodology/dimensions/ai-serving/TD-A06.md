## TD-A06

### 韧性设计如果没被注入过故障，它只是一段没运行过的代码

限流、超时、重试、熔断、降级这五件事都写在代码里，也都很少被验证真的会按预期触发。它们的共同特点是：只在故障时执行。

下面三条是未经验证的韧性设计的典型形态。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 超时层级设置反了 | 内层超时长于外层时，上游已放弃而下游仍在计费；这段浪费的算力占比不为 0 且完全不可见 | 故障时成本不降反升 |
| 重试没有退避与抖动 | 故障恢复瞬间的同步重试会造成二次冲击，峰值可达正常流量的 3 倍以上 | 系统刚恢复就被自己的重试再次打垮 |
| 降级路径从未被执行过 | 未注入验证的降级路径其实际可用性未知；这类代码的首次触发失败率不为 0，而首次触发恰好发生在故障时 | 把「设计了降级」当成「有降级」 |

> 本页的做法：逐条注入故障，验证每一层韧性机制真的会按设计执行。

### 韧性设计的四个词

AI 服务的失败是常态。这四个词决定失败之后用户看到什么。

| 术语 | 一句话解释 |
| --- | --- |
| deadline | 一次请求允许的最长总时间；所有层的超时之和必须小于它 |
| 重试预算 | 一次请求允许的重试总次数，按请求分配而非各层各设 |
| Fallback | 主路径不可用时的替代路径，如降级到小模型或缓存 |
| Degradation | 主动降低服务能力以保住可用性，如缩短输出、关闭工具 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[resilience4j/resilience4j](https://resilience4j.readme.io/docs)*

### 韧性设计如果没被注入过故障，它只是一段没运行过的代码

超时、重试、fallback、降级这四段代码有一个共同特点：正常情况下它们永远不执行。因此它们是整个系统里最容易写错、也最不容易被发现写错的部分——单元测试覆盖率可以是 100%，而真实故障路径从未被走通过。

生成式服务让这个问题更严重，因为它的故障形态更多：限流（429）、上游超时、内容被安全策略拦截、上下文超长被拒、模型返回不合法结构。这五类需要完全不同的恢复动作，而把它们统一按「重试」处理，会在限流时把情况变得更糟。

deadline 传播是这里的地基：上游剩余多少时间必须传给下游，否则下游会在调用方已经放弃之后继续消耗算力——在按 token 计费的场景里，这是直接的资损。

降级形态是生成式服务特有的一项。传统服务降级返回缓存或默认值，生成式功能没有有意义的默认值。可用的降级路径是：切更小的模型、退到检索直出、转只读、转人工。每一条都必须单独定义质量下限并验证，否则「降级成功」只是「没报错」。

*依据：[resilience4j/resilience4j](https://resilience4j.readme.io/docs) · [App-vNext/Polly](https://www.pollydocs.org/)*

### 五类错误各自的恢复动作与验证手段

第二列是决策表：把这五类分开处理，是这一页最实际的产出。统一按重试处理会在第二行直接把故障放大。

第四列的验证手段全部是故障注入——没有注入过的恢复路径不能算已实现。

| 错误类别 | 正确的恢复动作 | 错误的做法 | 验证手段 |
| --- | --- | --- | --- |
| 上游超时 | 有界重试 + 指数退避 + 抖动 | 无限重试或固定间隔重试 | Toxiproxy 注入延迟 |
| 限流 429 | 按 Retry-After 退避，不加重试 | 立即重试，把限流变成雪崩 | WireMock 返回 429 + Retry-After |
| 安全策略拦截 | 不重试，走降级或转人工 | 重试（结果一样）或改写请求绕过 | 构造被拦截的请求 |
| 上下文超长 | 裁剪上下文后单次重试 | 原样重试 | 构造超长输入 |
| 结构不合法 | 带 schema 提示重试一次，仍失败则降级 | 无限重试直到合法 | 注入不合法输出 |

> 五类的共同要求：每一条恢复路径都必须有一次注入实验证明它真的会被执行，且执行后的结果业务可接受。

*依据：[resilience4j/resilience4j](https://resilience4j.readme.io/docs) · [App-vNext/Polly](https://www.pollydocs.org/) · [Shopify/toxiproxy](https://github.com/Shopify/toxiproxy#readme) · [wiremock/wiremock](https://wiremock.org/docs/) · [python-jsonschema/jsonschema](https://python-jsonschema.readthedocs.io/) · [huggingface/text-generation-inference](https://huggingface.co/docs/text-generation-inference/)*

### 按错误类别决定恢复动作

不是所有错误都该重试。按类别决定动作，能避免把一次小故障放大成雪崩。

右列写的是错误做法——其中「全部重试」是最常见也最危险的一种。

| 错误类别 | 正确动作 | 错误做法 |
| --- | --- | --- |
| 限流 429 | 按退避重试，计入预算 | 立即重试，加剧限流 |
| 超时 | 视 deadline 余量决定是否重试 | 无条件重试，累积超过 deadline |
| 模型拒答 | 不重试，走人工或降级 | 反复重试直到「说服」模型 |
| 输出截断 | 可重试但需换参数 | 原样重试，大概率再次截断 |
| 下游 5xx | 有限重试 + 熔断 | 无限重试，拖垮下游 |
| 参数错误 4xx | 不重试，直接失败 | 重试，浪费预算 |

> 六行里只有三类适合重试。把「重试」当成通用容错手段，是延迟与成本失控的主要来源。

*依据：[App-vNext/Polly](https://www.pollydocs.org/)*

### 这一页的验收口径：每条路径都被执行过

本页四条指标的共同要求是「实测触发」而不是「配置存在」。这两者在真实项目里的差距很大。

A06-4 的恢复验证容易被忽略：系统能扛住故障，不代表它能从故障中干净地退出来。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| A06-1 | deadline 单调 | 内层 deadline 均短于外层的比例 = 100%；被重置的次数 = 0 | 每次配置变更 |
| A06-2 | 重试受控 | 重试按 token 与成本计量并共享同一预算的比例 = 100%；退避与抖动生效率 = 100% | 每次发布 |
| A06-3 | 降级可执行 | 每条降级路径实测触发成功率 = 100% 且质量达到预设下限 | 每次发布 |
| A06-4 | 恢复干净 | 依赖恢复后 5 分钟内回到正常路径；残留降级状态数 = 0 | 每次演练 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在做降级、实际在制造新问题的做法

这两种做法都能提高可用性数字，也都在事故复盘中被提出过。

问题是降级本身没有被测试。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 主模型不可用时自动降级到小模型，保住可用性 | 可用性确实提上去了，用户也拿到了回答 | 小模型的质量与安全边界不同。降级路径必须有自己的质量下限与安全断言，否则可用性上去了、正确性掉下来且无人知道 |
| 把降级算作成功，可用性指标从 97% 提到 99.9% | 降级确实返回了可用结果，不算失败 | 降级必须在指标里可见。全部算成功时，你会看到一条完美的可用性曲线，同时用户体验在持续下降 |

> 两条的共同要求：降级是一个独立的、要被测量也要被断言的状态。

### 高峰期雪崩后复盘按什么顺序查

雪崩几乎总是重试放大加上熔断缺失。按下表逐项核对，每一项都对应一个配置。

核对完之后通常会发现，最坏调用次数是设计时预期的几十倍。

| 复盘问题 | 检查什么 | 改进 |
| --- | --- | --- |
| 最坏调用次数是多少 | 各层重试次数相乘 | 预算收到请求级统一分配 |
| 超时是否逐层递减 | 各层超时值 | 内层明显小于外层 |
| 熔断有没有触发 | 熔断配置与触发记录 | 注入故障验证会触发 |
| 降级路径试过吗 | 降级演练记录 | 把演练列入发布准出 |
| 降级质量有下限吗 | 降级路径的断言 | 为降级单独设质量门禁 |

> 第五行最常缺失：降级路径通常只测「能返回」，不测「返回的东西可用」。

### 给一条主链路算清重试预算并验证降级：约 50 分钟

前半是算术，后半需要一次故障注入。两者都不需要压测环境。

1. 把网关、SDK、应用、模型客户端各层的重试次数与超时值抄下来。
2. 相乘得到最坏调用次数，乘以单次耗时上界，与 deadline 比较。
3. 超出部分即当前配置下必然发生的超时，列为待修。
4. 注入一次主模型不可用，验证 fallback 真的生效、并记录降级后的输出。
5. 对降级输出跑一遍质量与安全断言——多数团队会发现这一层根本没有断言。

**期望结果**：产出是一张重试预算表加一次降级演练记录。最常见的两个发现是：最坏调用次数远超预期，以及降级路径没有质量门禁。

> ⚠ 降级演练要在有真实流量特征的环境做。用固定测试请求演练，会让降级路径看起来比实际更可靠。

### 这一页的出口判据

这是 TD-M09 的出口门禁，全部依赖故障注入。没有注入就没有证据——韧性是唯一必须靠制造问题来验证的属性。

第三段要接受的是降级带来的体验损失，以及未纳入注入范围的依赖所含的未知风险。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 内层 deadline 长于外层的配置项数 > 0 时阻断<br>存在从未被实测触发过的降级路径时阻断，触发成功率必须 = 100% | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 降级路径的质量下限按 95% CI 下界与阈值比较<br>故障注入样本 < 30 次时该故障类型结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 各降级路径的质量下限与体验后果，由产品 owner 签字接受<br>未纳入故障注入的依赖清单，由架构 owner 列出并接受其风险 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[resilience4j/resilience4j](https://resilience4j.readme.io/docs)*

### 带走一张请求级的韧性预算表

表要写清每层分到多少次重试、多少秒超时，以及降级后进入哪个状态、该状态的质量下限是什么。

降级必须在可用性指标里可见——把它算作成功，等于用指标掩盖体验下降。

- 按错误类别决定是否重试，不要一律重试
- 重试与超时预算在请求级统一分配
- 降级是独立状态，要单独设质量与安全断言
