## TD-A04

### 压到目标就停，你只知道达标了，不知道还剩多少余量

容量测试的目的不是证明当前够用，而是找到失效点在哪。压到目标值就停的测试，无法回答「流量翻倍会怎样」。

下面三条是负载设计上的三种常见问题。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 只做封闭负载 | 封闭负载在系统变慢时自动降速，排队问题被折叠；实测中它会把排队 p99 低估数倍 | 压测一切正常，真实峰值到来时大量超时 |
| 压到目标值就停止 | 只有 1 个压力点时无法判断距离拐点还有多远；至少需要 3 个相邻档位才能看出曲线形状 | 「当前容量满足需求」被当成「还有余量」 |
| 忽略缓存命中率的影响 | 语义缓存命中率从 40% 掉到 10% 时，实际算力需求会成倍上升，而请求量没有变化 | 容量按高命中率估算，缓存失效后立刻打满 |

> 本页的做法：开闭环各跑一遍，逐级加压到失效，并把缓存命中率作为 workload 的一个维度。

### 容量测试的四个前提词

AI Serving 的容量结论极度依赖负载建模。这四个词决定结论能不能用。

| 术语 | 一句话解释 |
| --- | --- |
| Token 分布 | 输入与输出长度的实际分布；用均值压测会严重高估容量 |
| 到达率 vs 并发 | 前者固定每秒来多少，后者固定同时有多少；两者结论不同 |
| 缓存命中率 | 相同前缀的复用比例；它显著影响容量且容易在压测中失真 |
| SLO 拐点 | 开始违反 SLO 的负载点；容量指的是它，不是最大吞吐 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[grafana/k6](https://grafana.com/docs/k6/latest/)*

### 压到目标就停，你只知道达标了，不知道还剩多少余量

容量测试最常见的做法是压到目标 QPS，看指标是否达标，达标即收工。这个做法回答了「现在够不够」，但回答不了「还能扛多少」和「超过之后怎么坏」——而后两个问题才是容量规划真正需要的。

正确做法是阶梯加压直到找到 SLO 拐点：逐级提高到达率，记录每一级的延迟分位与错误率，直到某个指标越过 SLO。拐点前后的形状同样重要——是平滑劣化还是断崖式崩塌，决定了你需要多大的安全余量。

生成式服务的容量测试还有三个传统压测没有的前提必须先固定：输入输出的 token 长度分布（长请求与短请求的成本相差一个数量级）、前缀缓存命中率（共享系统提示词的请求会复用 KV 缓存）、以及到达率而非并发数的负载模型。三者任一没固定，测出来的曲线就不可复现。

前缀缓存命中率是最容易在实验室里被无意抬高的一项：压测脚本通常用同一个提示词模板反复发送，命中率接近 100%，而生产流量的命中率可能只有百分之几十。这会让实验室容量数字系统性偏高。

*依据：[grafana/k6](https://grafana.com/docs/k6/latest/) · [sgl-project/sglang](https://docs.sglang.ai/)*

### 负载模型必须固定的五项

这五项不固定，两次压测的结果就没有可比性——而不可比的压测结果，无法支持任何容量决策。

第三列写的是不固定时的典型偏差方向，全部指向同一个方向：实验室数字比生产乐观。

| 必须固定的项 | 怎么固定 | 不固定时的偏差 | 工具 |
| --- | --- | --- | --- |
| 负载模型 | 用固定到达率（开放模型），不用固定并发 | 封闭模型下系统自我降压，看不到拐点 | k6 constant-arrival-rate |
| 输入 token 分布 | 按生产实际分布构造，不用等长请求 | 等长请求掩盖长请求的 prefill 成本 | 自建请求生成器 |
| 输出 token 分布 | 控制 max_tokens 与停止条件 | 输出长度失控时吞吐数字无意义 | 服务端参数固定 |
| 前缀缓存命中率 | 按生产实际共享比例构造前缀 | 脚本复用同一模板使命中率接近 100%，容量被高估 | SGLang / vLLM 缓存指标核对 |
| 阶梯与终止条件 | 逐级加压至 SLO 拐点，记录首个失败门禁 | 压到目标即停，不知道余量与崩塌形状 | k6 阶梯场景 |

> 五项固定之后，容量曲线才是一个可以复现、可以跨版本比较的工件，而不是一次性的演示数字。

*依据：[grafana/k6](https://grafana.com/docs/k6/latest/) · [sgl-project/sglang](https://docs.sglang.ai/) · [vllm-project/vllm](https://docs.vllm.ai/) · [Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)*

### 负载模型必须固定的六项

压测结论不可复现，九成来自这六项里有几项没被记录。每一项都要写进 workload 文件并打 hash。

右列是这一项失真时结论会偏向哪一边——全部偏向乐观。

| 必须固定 | 为什么 | 失真时结论偏向 |
| --- | --- | --- |
| 输入 token 分布 | 决定 prefill 压力 | 偏乐观 |
| 输出 token 分布 | 决定 decode 时长与显存 | 严重偏乐观 |
| 到达模式 | 泊松/阶梯/突发的排队行为不同 | 偏乐观 |
| 并发上限 | 决定队列深度 | 不定 |
| 缓存命中率 | 命中高时算力压力小得多 | 严重偏乐观 |
| 质量切片 | 不同任务的失败率不同 | 掩盖高风险切片 |

> 六项里有三项失真会让结论明显偏乐观——这正是压测容量常常是生产容量数倍的原因。

*依据：[grafana/k6](https://grafana.com/docs/k6/latest/)*

### 这一页的验收口径：拐点、过载与恢复

A04-1 与 A04-2 保证容量结论有意义：双模式压测加足够档位，才谈得上「找到了拐点」。

A04-4 测的是过载之后的行为——系统在超过容量时应当拒绝一部分请求并保持其余可用，而不是整体雪崩。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| A04-1 | 双模式覆盖 | 开环与封闭均执行的比例 = 100%；仅做其一即给容量承诺的次数 = 0 | 每次容量评估 |
| A04-2 | 档位充分 | 压力档位数 ≥ 3；每档持续 ≥ 10 分钟 | 每次容量评估 |
| A04-3 | 质量不换吞吐 | 加压至拐点过程中任务达标率下降 ≤ 2pt | 每次容量评估 |
| A04-4 | 过载与恢复 | 超过拐点时系统保持部分可用的比例 ≥ 80%；压力下降后 5 分钟内恢复 | 每次容量评估 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在压容量、实际压出乐观数字的做法

这两种做法在压测报告里非常常见，曲线也很漂亮。

它们的共同结果是把生产容量高估若干倍。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 用一组固定的典型请求反复压测，保证可比 | 控制变量、结果稳定、便于跨版本对比 | 固定请求会让缓存命中率接近 100%，而生产中命中率低得多。算力压力被系统性低估 |
| 报最大吞吐作为容量上限 | 这是压出来的极限，有数据支撑 | 最大吞吐点上延迟往往已远超 SLO。容量应报 SLO 拐点，它通常显著低于最大吞吐 |

> 两条都需要同一个修正：让压测负载在分布与缓存行为上贴近生产。

### 压测容量与生产不符时按什么顺序查

按下表逐项对齐，通常前三行就能解释绝大部分差距。

对齐后重压一次，差距应显著缩小；仍不缩小时才怀疑环境差异。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 压测容量是生产数倍 | 缓存命中率失真 | 用真实前缀分布重构请求 |
| 压测无超时生产大量超时 | 输出长度按均值 | 用 p99 输出长度重压 |
| 压测延迟平稳生产抖动大 | 到达模式过于均匀 | 改用泊松或加入突发 |
| 某类请求在生产特别慢 | 未按质量切片分桶 | 把该切片单独压 |

> 第一行的修正成本最低也最有效：仅仅把请求前缀随机化，容量数字通常就会掉一大截。

### 用真实分布重建一次容量测试：约 90 分钟

需要压测环境。若暂无，可先完成前两步的负载建模，标注为未运行。

1. 从生产采样重建输入与输出 token 的分布，至少取到 p99。
2. 按真实前缀多样性构造请求，避免所有请求共享同一段系统提示导致缓存全命中。
3. 先用闭环固定并发摸出大致范围，再用开环固定到达率找 SLO 拐点。
4. 在拐点附近记录：分位延迟、成功率、Goodput、队列深度、缓存命中率。
5. 把 workload 六项与 SLO 定义一起写进容量卡，并打 hash。

**期望结果**：用真实分布重压后的容量通常明显低于此前数字。这个下降不是能力退步，是此前的高估被纠正。

> ⚠ 不要在共享推理集群上做拐点测试。邻居负载会污染结果，而且你的压测会影响他们。

### 这一页的出口判据

这道门禁要求压到失效。只压到目标值的测试不能进入这道门禁，因为它没有拐点数据。

第三段要接受的是合成负载与真实流量的差距，以及基于它做出的容量承诺所含的余量假设。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 压力档位数 < 3 时阻断，无法判断曲线形状<br>过载时系统整体不可用（部分可用比例 = 0）时阻断，先修准入与降级 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 各档位 Goodput 给出 95% CI，拐点以区间不再上升判定<br>单档位样本 < 500 个任务时该档位结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 基于合成负载给出的容量承诺及其余量假设，由容量 owner 签字<br>缓存命中率的取值假设，由架构 owner 确定并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)*

### 带走一张有 workload hash 的容量卡

容量卡必须写明六项负载参数与 SLO 定义。缺任一项，这个容量数字半年后会被当成系统属性引用。

报 SLO 拐点而不是最大吞吐——后者对应的延迟通常已经不可用。

- 用生产采样重建 token 分布与前缀多样性
- 开环找拐点，闭环定位瓶颈
- 容量卡写明 workload hash 与 SLO 定义

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[k6：以到达率为模型的负载测试工具](https://grafana.com/docs/k6/latest/)** — 性能专项工具
  - 能证明：开放模型（constant-arrival-rate）与封闭模型（VU 并发）的区别，以及为什么用固定并发数压测会掩盖真实容量拐点——并发模型下系统变慢会自动降低到达率，形成自我保护假象。
  - 不能证明：工具产出的是客户端观测。真实容量还取决于依赖、缓存命中、数据规模与限流策略；任何教学阈值都不能照抄。
  - `grafana/k6` · 版本 v2.2.0（2026-08-10） · AGPL-3.0 · AGPL-3.0：著佐权许可，只链接与转述，不搬代码
- **[Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)** — 判据框架
  - 能证明：SLI/SLO/错误预算的定义方式，以及为什么用分位而非均值、为什么阈值必须来自业务而非工具默认值。性能与稳定性两页的验收口径都建立在这套框架上。
  - 不能证明：书里的示例数字是示例。任何直接照抄的 SLO 都没有经过你自己业务成本的校准。
  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理
- **[vLLM：高吞吐推理服务引擎](https://docs.vllm.ai/)** — 推理服务实现

  - 不能证明：引擎指标反映的是服务端状态，不等于用户体感；托管 API 通常不暴露这些指标，此时只能从客户端阶段指标推断并标记未知。
  - `vllm-project/vllm` · 版本 v0.27.1（2026-08-11） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[SGLang：结构化生成与前缀复用的推理引擎](https://docs.sglang.ai/)** — 推理服务实现
  - 能证明：前缀缓存命中率会显著改变延迟分布：相同系统提示词的请求可以复用 KV 缓存。这意味着压测时构造的请求是否共享前缀，会直接决定你测出来的容量数字。
  - 不能证明：缓存收益高度依赖真实流量的前缀分布，实验室里构造的高命中率不可外推到生产。
  - `sgl-project/sglang` · 版本 v0.5.17（2026-08-08） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
