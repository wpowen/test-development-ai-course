## TD-F05

### 先选指标再想任务，是指标体系失效的标准起点

F1、Recall@k、ROUGE、延迟、QPS 都是好指标，问题在于它们各自只适合回答特定问题。从指标出发选任务，得到的一定是「测得出来的东西」而不是「该测的东西」。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 用准确率描述极不平衡的任务 | 正例占比 1% 时，全部预测为负例的准确率是 99%，而召回为 0 | 「准确率 99%」被当成效果很好，实际一个正例都没找到 |
| 用单一指标覆盖不同失败成本 | 漏检与误检的业务代价常相差 3 倍以上；用 1 个指标时两者被强行等权 | 优化了总分，最贵的那类错误反而变多 |
| 指标与业务结果不相关 | 指标构念效度的通行要求是与业务结果相关性 ≥ 0.6；低于此值时指标涨跌与业务无关 | 指标提升 7 个点，线上投诉量没有任何变化 |

> 本页的顺序是：业务任务 → 错误成本 → 数据人口 → 风险切片 → 独立 Oracle → 才轮到选指标。

### 选指标前必须先分清的四个词

「用什么指标」这个问题没有通用答案，它取决于下面四项。先问任务，再选指标。

| 术语 | 一句话解释 |
| --- | --- |
| 任务族 | 分类、检索、生成、决策、执行等；不同任务族的指标不可互换 |
| 总体 | 这个指标算在哪一群样本上；总体不同则数字不可比 |
| 失败成本 | 漏报与误报哪个更贵；它决定阈值往哪一侧偏 |
| Oracle 可得性 | 有没有独立的判对方式；没有时精确指标算不出来 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[DORA 四项关键指标](https://dora.dev/guides/dora-metrics-four-keys/)*

### 先选指标再想任务，是指标体系失效的标准起点

指标体系失效通常不是因为指标算错了，而是因为它衡量的不是这个任务真正的失败模式。而这一点的根源在顺序：先确定了要报哪些指标，再去找任务来填。

正确的顺序从任务族开始：把系统要做的事分成几类（抽取类、生成类、决策类、检索类），每一类的失败模式不同，因此判据来源也不同。抽取类有确定答案，可以用精确匹配；生成类没有唯一答案，只能用语义判据或人工；决策类可以用业务结果反推。

第二个判断维度是 Oracle 可得性：这个任务的正确答案能不能被独立获得？能，就用确定性判据；不能，就必须承认判据本身带误差，并为它设计校准机制。跳过这个判断直接选指标，会导致把有误差的估计当成判决使用。

第三个维度是失败成本：同一个任务族里，不同错误的代价可能相差几个数量级。指标必须按成本加权或分切片报告，否则一个在低成本切片上很好、在高成本切片上很差的系统，总分会看起来很正常。

*依据：[DORA 四项关键指标](https://dora.dev/guides/dora-metrics-four-keys/) · [stanford-crfm/helm](https://crfm.stanford.edu/helm/)*

### 任务族到指标的选择依据

先定位任务族，再看 Oracle 可得性，最后才选指标。这张表按这个顺序排列，用途是把选指标从偏好变成推导。

第四列写的是这一族最容易被误用的指标——它们通常是从另一族借来的。

| 任务族 | Oracle 可得性 | 适合的判据 | 最容易误用的指标 |
| --- | --- | --- | --- |
| 抽取 / 分类 | 高：有确定答案 | 精确匹配、F1、按类别分切片 | 用总体准确率掩盖少数类的失败 |
| 生成 | 低：无唯一答案 | 语义评分 + 人工校准 + 结构确定性断言 | 用 BLEU 这类字面相似度衡量语义正确性 |
| 检索 | 中：可标注 gold document | Recall@k、nDCG@k、MRR | 只看 Recall@20，忽略排序位置 |
| 决策 / 执行 | 中：可用业务结果反推 | 任务成功率 + 单位成功成本 + 副作用检查 | 只看终局成功率，忽略过程中的副作用 |

> 四行的共同结构：先问「正确答案从哪来」，再选指标。这个顺序倒过来，指标体系一定会失效。

*依据：[DORA 四项关键指标](https://dora.dev/guides/dora-metrics-four-keys/) · [stanford-crfm/helm](https://crfm.stanford.edu/helm/) · [beir-cellar/beir](https://github.com/beir-cellar/beir#readme)*

### 这张图的 8 个节点，本页各交付什么

这张图的方向就是本页的全部内容：从业务任务开始，指标出现在倒数第三个节点。反过来读就是要纠正的错误顺序。

「不确定性」被单列成一个节点，是因为一个不带区间的指标值无法支撑任何发布或调查决策。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |

| 错误成本 | 分别估计漏检与误检的业务代价，作为指标加权依据 | 错误成本估计 |
| 数据人口 | 明确指标的分母是哪一群体，避免整体掩盖切片 | 人口与分母定义 |
| 风险切片 | 列出必须单独出分的切片 | 风险切片清单 |

### 任务族到指标的选择依据

下表不是「推荐指标」，而是「在什么条件下这个指标才有意义」。条件不满足时，再流行的指标也算不出可用结论。

右列的常见误用都源自跨任务族搬运指标。

| 任务族 | 条件成立时可用 | 常见误用 |
| --- | --- | --- |
| 分类 | 有唯一标签时用 Precision/Recall/F1 | 把 F1 用在没有唯一标签的生成任务上 |
| 检索 | 有相关性标注时用 Recall@k / nDCG | 只看 top1 命中，忽略排序质量 |
| 生成 | 有变形关系或不变量时用属性检查 | 用 ROUGE 之类的表面相似度代表质量 |
| 决策 | 有独立规则时用规则符合率 | 用模型判分放行涉及金额的决定 |
| 执行 | 有业务终态时用任务成功率与 pass^k | 用步骤成功率代表任务成功率 |

> 五行的共同结构：先确认条件成立，再选指标。条件不成立时正确做法是换判据，不是换指标。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/)*

### 这一页的验收口径：指标本身的合格标准

本页的指标是关于指标的：一个指标要能被使用，它需要有明确的分母、切片、区间和对应动作。

F05-4 是最容易被忽略的一条——一个不绑定动作的指标，无论多准确都不会改变任何行为。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| F05-1 | 分母明确 | 每个指标显式声明分母与数据人口的比例 = 100% | 每次指标定义 |
| F05-2 | 切片分离 | 风险切片单独出分的比例 = 100%；仅报整体的次数 = 0 | 每次评测 |
| F05-3 | 业务相关 | 核心指标与业务结果相关性 ≥ 0.6；低于此值降级为参考项 | 每季度 1 次 |
| F05-4 | 绑定动作 | 每个指标绑定发布或调查动作的比例 = 100%；无动作指标数 = 0 | 每次指标定义 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

*依据：[beir-cellar/beir](https://github.com/beir-cellar/beir#readme)*

### 两种看起来在选指标、实际在选熟悉度的做法

这两种做法在评审中很难被反对，因为它们都引用了广为接受的指标。

问题是指标与任务的条件不匹配。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 用 F1 作为主指标，因为它平衡了查准与查全 | F1 是分类任务的标准指标，广泛使用 | F1 隐含假设漏报与误报同样重要。在退款审批这类场景里，一次误放行的代价远高于一次误拦截，应当分别设阈值而不是求平衡 |
| 用 QPS 与平均延迟衡量 AI 服务性能 | 这是服务性能的通用指标，工具原生支持 | AI 服务的输出长度可变，均值会被长尾污染。而且高 QPS 可能伴随成功率下降，容量应当看 goodput |

> 两条都在同一处出错：把通用指标的适用条件默认成了永远成立。

### 指标好看但业务没改善时按什么顺序查

这类问题几乎总是指标与决定脱节。下表把它拆成四个可核对的问题。

核对完之后，通常会有一到两个指标应该被直接下线。

| 自查问题 | 不满足时的表现 | 下一步 |
| --- | --- | --- |
| 这个指标回答哪个决定 | 说不出具体决定 | 下线该指标 |
| 总体是什么 | 分母随报告变化 | 固定总体并写进指标定义 |
| 漏报误报哪个更贵 | 阈值两侧对称 | 按失败成本重设阈值 |
| 有独立 Oracle 吗 | 用模型判分放行 blocker | 改用规则层或人工 |

> 第一行是删除依据：一个不能改变任何决定的指标，无论多准确都应当下线。

### 给现有指标做一次条件核对：约 35 分钟

不需要重新设计指标体系。先把现在在用的指标逐个过一遍四个问题。

1. 列出团队目前定期汇报的所有指标，通常在五到十个之间。
2. 对每个指标回答四个问题：回答哪个决定、总体是什么、失败成本哪侧更贵、Oracle 是否独立。
3. 把答不上第一个问题的指标标为待下线——它们占用注意力但不产生决定。
4. 对答不上第二个问题的指标，补写总体定义；这是最容易补也最容易被忽略的一项。
5. 把剩下的指标按任务族重新归类，检查是否有跨族搬运。

**期望结果**：多数团队做完会下线两到三个指标，并发现至少一个指标的总体定义在不同报告里不一致。

> ⚠ 下线指标要说明理由并通知使用方。悄悄停报会让人以为出了问题，反而增加沟通成本。

### 这一页的出口判据

这道门禁作用在指标体系设计上，执行时机在评测之前。评测跑完再发现指标选错，此前所有数字都要重来。

第三段要接受的是相关性未验证的新指标——新指标必然缺少历史数据，这个未知要被明示。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 指标未声明分母与数据人口的数量 > 0 时阻断<br>无绑定动作的指标数 > 0 时阻断，指标不得只用于汇报 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 所有指标结论附 95% CI；样本不足时结论为「证据不足」而非通过<br>相关性估计基于至少 30 个历史发布点，不足时标注为未验证 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 漏检与误检的成本比，由业务 owner 估计并签字<br>新指标相关性未验证这一事实，由产品 owner 知情接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一份条件明确的指标清单

清单的每一行都要写清适用任务族、总体、失败成本方向与 Oracle 来源。

写不出来的行不是需要补充说明，是需要下线。

- 先问任务族与 Oracle 可得性，再选指标
- 每个指标绑定它回答的那个决定
- 失败成本不对称时分别设阈值，不求平衡

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[HELM：多场景、多指标的整体性评测](https://crfm.stanford.edu/helm/)** — 评测方法学
  - 能证明：单一准确率无法描述模型能力。HELM 的做法是把场景（scenario）与指标（metric）做成正交的两维，同一个场景同时报准确率、校准度、鲁棒性、公平性、效率——「模型 A 比 B 好」这句话必须指明在哪个场景的哪个指标上。
  - 不能证明：覆盖的是公开场景，不覆盖你的业务分布。榜单名次不能迁移到企业任务上。
  - `stanford-crfm/helm` · 版本 v0.5.16（2026-04-30） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[BEIR：零样本检索评测基准套件](https://github.com/beir-cellar/beir#readme)** — 检索评测基准
  - 能证明：检索质量必须用 nDCG@k、Recall@k 这类带位置权重的指标衡量，且同一个检索器在不同领域的表现差异极大——零样本迁移能力不可假设。
  - 不能证明：公开语料上的排名不预测你私有语料上的表现；企业检索还受切分策略、元数据过滤与权限裁剪影响，这些不在基准里。
  - `beir-cellar/beir` · 版本 v2.2.0（2025-06-04） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[DORA 四项关键指标](https://dora.dev/guides/dora-metrics-four-keys/)** — 交付效能判据
  - 能证明：交付效能可以用四个互相制衡的指标描述：部署频率、变更前置时间、变更失败率、恢复时间。互相制衡是关键——只优化速度会让失败率上升，因此单看任一个都会被操纵。
  - 不能证明：衡量的是交付系统不是产品质量；四项指标全优的团队仍然可以交付没人要的功能。
  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理
