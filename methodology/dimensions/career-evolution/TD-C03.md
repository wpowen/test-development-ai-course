## TD-C03

### 自评表最常见的下场，是填完之后再也没被打开过

一张打勾的自评表本身不产生任何变化。让它产生变化的是三样东西：每条主张绑定的证据、每个缺口绑定的下一件产物、以及一个会到来的复评日期。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 自评只打勾不附证据 | 无证据的打勾无法被复核；这类自评表在复评时的可用性为 0 | 半年后回看，说不清当时为什么勾了这一项 |
| 缺口没有下一件产物 | 只写「需要加强 X」而不绑定具体产物时，缺口 3 个月后的闭合率接近 0 | 缺口清单变成一份长期不变的愿望清单 |
| 没有复评日期 | 无日期的计划不会被触发；这类计划 3 个月后的执行率接近 0 | 计划做得很好，从未被回顾 |

> 本页把自评表变成可复验的 JSON：主张 → 证据 → 缺口 → 下一件产物 → 复评日期。

### 证据计划的四个词

自评表最常见的问题是它只是一次表态。这四个词把它变成可复验的计划。

| 术语 | 一句话解释 |
| --- | --- |
| 能力主张 | 一句可被检验的陈述，如「我能独立设计带独立 Oracle 的测试策略」 |
| 证据 | 支撑主张的具体工件或记录，能被第三方打开查看 |
| 缺口路由 | 主张成立但证据不足时，明确下一步去哪里补 |
| 复评日期 | 这条主张下次被重新检验的时间；没有它，自评会长期停在旧状态 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[DORA 四项关键指标](https://dora.dev/guides/dora-metrics-four-keys/)*

### 自评表最常见的下场，是填完之后再也没被打开过

能力自评之所以很少产生实际效果，原因不在于填得不认真，而在于填完之后没有任何机制会让它再被打开。它是一次性的快照，而能力发展是持续的过程——两者不匹配。

让它持续有效需要三个绑定。第一是证据绑定：每条能力主张必须指向一个具体工件，而不是一个自评分数。「我能做评测体系设计」要绑定到一份具体的评测合同上，否则这条主张无法被验证也无法被更新。

第二是缺口路由：自评的产出不应该是一张分数表，而是一份「下一步做什么」的清单。每个缺口要指向一个具体动作（做一个什么样的工件、在什么场景下练），而不是一个学习资源列表。

第三是复评日期：每条主张都带一个到期时间。技术领域的能力主张有保质期——两年前的 Agent 测试经验与今天的实践差异很大。到期未更新的主张自动降级为「待复核」，这个机制让自评表有理由被重新打开。

*依据：[DORA 四项关键指标](https://dora.dev/guides/dora-metrics-four-keys/) · [O*NET：软件质量保证分析师与测试员职业档案](https://www.onetonline.org/link/summary/15-1253.00)*

### 一条合格的能力主张必须绑定的四项

四项缺任一项，这条主张就无法被验证、无法被更新，也就无法在半年后仍然有意义。

第三列写的是缺失时的具体后果——注意它们都不是「不严谨」，而是「这条主张会静默失效」。

| 绑定项 | 内容 | 缺失的后果 | 怎么落地 |
| --- | --- | --- | --- |
| 能力域 | 属于哪一个具体能力域，不写「测试能力」这类笼统项 | 无法与岗位要求对齐，也无法定位缺口 | 对照职业档案的能力清单逐项拆 |
| 责任状态 | 跟做 / 设计 / 裁决 / 治理 | 「会」与「能负责」被混为一谈 | 按可观察证据判定，不按自我感觉 |
| 证据工件 | 指向一个具体的、他人可验证的产出 | 主张无法被验证，等于自述 | 工件链接 + 一句话说明它证明了什么 |
| 复评日期 | 这条主张的有效期 | 两年前的经验被当成当前能力 | 到期自动降级为待复核 |

> 四项合起来，自评表才从一次性快照变成一份会被反复打开的工作清单。

*依据：[DORA 四项关键指标](https://dora.dev/guides/dora-metrics-four-keys/) · [O*NET：软件质量保证分析师与测试员职业档案](https://www.onetonline.org/link/summary/15-1253.00) · [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)*

### 这张图的 8 个节点，本页各交付什么

这张图是一条 30/60/90 天的证据链：从当前证据出发，经能力主张与缺口诊断，路由到具体页面或项目，最后在 90 天复评。

每个时间点都绑定一类产物，而不是一个学习目标——目标无法被复核，产物可以。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 当前证据 | 列出已有的可复验工件，作为自评的起点 | 当前工件清单 |
| 能力主张 | 每条主张必须指向一件具体证据 | 带证据的主张列表 |
| 缺口诊断 | 识别主张与目标之间的差距 | 缺口清单 |
| 页面/项目路由 | 把每个缺口路由到本课程的具体页面或项目 | 缺口—页面映射 |
| 30 天工件 | 第一个月产出一件可复验工件 | 30 天产物 |
| 60 天故障证据 | 第二个月为该工件补上故障注入证据 | 60 天红绿证据 |
| 90 天复评 | 第三个月由他人复评并更新主张 | 90 天复评记录 |
| 边界声明 | 写明本计划不承诺任何招聘或晋升结果 | 边界声明 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 一条合格的能力主张必须绑定的五项

自评之所以常常失效，是因为主张与证据之间没有强制绑定。下表是最小绑定集。

右列写的是缺这一项时会发生什么——多数情况是自评在半年后完全失去参考价值。

| 必须绑定 | 例子 | 缺失的后果 |
| --- | --- | --- |
| 主张 | 能独立设计带独立 Oracle 的策略 | 没有主张就无法判断证据够不够 |
| 证据 | 某项目的测试策略文档链接 | 变成自我感觉 |
| 缺口 | 关键金额 Oracle 仍依赖他人确认 | 高估自己，面试时露馅 |
| 路由 | 下个需求主动承接该部分 | 缺口永远不会被补上 |
| 复评 | 三个月后重新检验 | 自评长期停在旧状态 |

> 五项齐全时，自评表就变成了一份可执行的计划；缺任意一项它都会退回成一次表态。

### 这一页的验收口径：可复验的自评

本页的自评表是一份 JSON 而不是一张打勾表格，理由很简单：JSON 可以被脚本检查，打勾表格只能被人看。

C03-4 的复评日期是唯一能让计划真正被执行的机制——没有日期的计划不会被触发。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| C03-1 | 主张有证据 | 每条能力主张绑定证据路径的比例 = 100% | 每次自评 |
| C03-2 | 缺口有路由 | 每个缺口绑定具体页面或项目的比例 = 100% | 每次自评 |
| C03-3 | 阶段有产物 | 30/60/90 三个节点各绑定 ≥ 1 件产物 | 每次自评 |
| C03-4 | 复评有日期 | 复评日期缺失率 = 0；过期未复评的条目数 = 0 | 每月 1 次 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在做能力规划、实际无法验证的做法

这两种做法都很常见，尤其在有正式绩效流程的团队里。

它们的共同结局是：三个月后没有任何东西可以核对。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 用五分制给每个能力域打分，形成雷达图 | 可视化清晰，便于横向比较与沟通 | 分数不携带证据。三分和四分的差别无法被第三方复核，也无法指出下一步该做什么 |
| 制定学习计划：读三本书、上两门课、做一个项目 | 计划具体、可执行、有明确产出 | 输入不是证据。读完书不等于能设计 Oracle。计划应当绑定产出的工件，而不是消耗的材料 |

> 两条的共同修法：把「我学了什么」换成「我能拿出什么给人看」。

### 自评做了但没变化时按什么顺序查

自评失效有四种典型形态。下表按出现频率排列，每一行都有一个当天可做的修正。

关键判断标准只有一个：三个月后有没有新的可展示工件。

| 症状 | 先怀疑 | 下一步动作 |
| --- | --- | --- |
| 三个月后自评没变 | 缺复评日期与路由 | 为每条主张绑定日期与具体需求 |
| 主张说不清 | 主张写得太笼统 | 改写成可被检验的一句话 |
| 证据只有描述 | 没有可打开的工件 | 补一份能被第三方运行的产物 |
| 缺口列了但没动 | 缺口未绑定真实任务 | 把缺口挂到下一个需求上 |

> 第四行是最常见的：缺口被诚实地写了出来，然后放在那里再也没被碰过。

### 把自评表改写成 JSON 计划：约 50 分钟

改成结构化不是为了好看，是为了让「有没有证据」这件事无法被含糊过去。

1. 挑出三条你最想成立的能力主张，每条写成一句可被检验的陈述。
2. 为每条填写四个字段：证据（链接或路径）、缺口（还差什么）、路由（下一步在哪个真实任务里补）、复评日期。
3. 证据字段必须填可打开的东西。填不出来的，把主张降级或标记为 UNKNOWN。
4. 请一位同行读这三条，只问一个问题：不认识你的人能不能凭证据字段确认这条主张？
5. 把复评日期写进日历，到期时重新走一遍这四个字段。

**期望结果**：产出是三条带证据、缺口、路由与复评日期的结构化主张。通常会有至少一条在填证据字段时被迫降级——那正是这次自评最有价值的产出。

> ⚠ 不要把主张写得容易达成以便填满。填不出证据的主张，如实降级比强行支撑更有用。

### 这一页的出口判据

这道门禁作用在你的自评表上：它检查这张表能不能被别人复核，而不是检查你的能力高低。

第三段是本页的实质产物——一份你和复评人共同确认的、写清楚了当前边界的能力记录。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 无证据路径的能力主张数 > 0 时，该自评表不成立<br>复评日期缺失率 > 0 时不予采信，无日期的计划不会被触发 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 能力变化以工件与复评记录的增量判定，证据不足时结论为 UNKNOWN<br>自评与他评差异较大的条目须逐条说明，不取平均 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 自评与他评存在分歧的条目，由本人与复评人共同确认结论<br>本计划不承诺晋升或招聘结果这一边界，由学习者本人知情接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[DORA 四项关键指标](https://dora.dev/guides/dora-metrics-four-keys/)*

### 带走三条可被第三方复核的能力主张

三条扎实的主张比十条模糊的强项更有用，尤其是在被追问细节的场合。

复评日期是这份计划唯一的自我纠错机制；没有它，它会在三个月后变成一份过期文档。

- 主张写成可被检验的一句话
- 证据必须是能打开的工件，不是描述
- 缺口绑定真实任务并设复评日期
