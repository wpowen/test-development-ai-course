## TD-R01

### 一份不会更新的书单，三个月后就开始误导人

资源清单的价值不在于列了多少，而在于每条都写明了它适合解决什么问题、什么时候被检查过、以及它现在还成不成立。

下面三条是静态书单的三种失效。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 资源没有检查日期 | AI 领域的工具与实践变化很快；无检查日期的资源在 1 年后其有效性不可估计 | 按过期资料操作，与当前版本行为不符 |
| 不写适用范围与限制 | 同一份资料对不同背景读者的价值差别很大；缺适用说明时选错资源的概率显著上升，一次选错的代价通常是 2～4 周 | 花了几周读完，发现解决的不是自己的问题 |
| 没有替代路径 | 资源可能失效、收费或下架；无 fallback 时该条缺口的闭合率降为 0 | 计划因为一个链接失效而卡住 |

> 本页把资源清单变成带版本、检查日期、限制与替代路径的索引。

### 资源索引的四个词

书单会过期，索引不会——前提是它记录了下面四项。

| 术语 | 一句话解释 |
| --- | --- |
| 检查日期 | 上次确认这条资源仍然有效的日期；没有它无法判断是否过期 |
| 用途 | 这条资源解决什么问题；它决定要不要读，而不是评分 |
| 限制 | 它不覆盖什么、在什么条件下失效；这是最容易被省略也最有用的一栏 |
| 替代路径 | 这条资源不可得时的等价选择，如付费课程对应的开源实现 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[O*NET：软件质量保证分析师与测试员职业档案](https://www.onetonline.org/link/summary/15-1253.00)*

### 一份不会更新的书单，三个月后就开始误导人

技术资源清单的半衰期很短，而它腐烂的方式是静默的：链接还在、书还在，只是内容已经描述了一个不再存在的世界。读者按它去学，学到的是过时的做法，而且不会有任何信号提示这一点。

让资源索引保持可用的机制只有一条：每条资源都带检查日期与用途说明，过期未复查的自动标记为待核。这与引用台账的做法是同一个原理——把「谁负责保鲜」这件事变成结构性的，而不是靠人记得。

用途说明比推荐语更有价值。「这本书很好」不构成任何信息；「这本书讲清了分层断言的机理，但它的工具章节已经过时」才是可行动的。前半句告诉读者为什么要读，后半句告诉读者读到哪里要停。

替代路径是给每条资源准备的退路：当它失效时读者去哪里。官方文档改版、项目停止维护、书籍绝版，这些都会发生，而一条没有替代路径的资源在失效时会直接变成死胡同。

*依据：[O*NET：软件质量保证分析师与测试员职业档案](https://www.onetonline.org/link/summary/15-1253.00) · [DORA 四项关键指标](https://dora.dev/guides/dora-metrics-four-keys/)*

### 五类资源各自能提供什么、不能提供什么

第三列是这张表的重点：每一类资源都有它结构性提供不了的东西，而误用通常发生在这里。

最后一列的更新频率决定了复查周期——把它写进索引，比凭印象决定什么时候该更新可靠。

| 资源类型 | 能提供什么 | 结构上提供不了什么 | 复查周期 |
| --- | --- | --- | --- |
| 官方文档 | 当前版本的准确 API 与行为 | 为什么这样设计、什么时候不该用 | 随版本，建议每季度 |
| 规范与标准 | 术语、结构与可引用的条款号 | 落地方法与阈值 | 较慢，每年 |
| 开源仓库 | 可运行的参考实现与真实约束 | 它是否适合你的场景 | 跟随 release，每季度 |
| 书籍 | 系统的机理与思维框架 | 当前工具的准确用法 | 机理部分长期有效，工具部分半年即过时 |
| 会议与博客 | 新形态与一线经验 | 普适性——多数是单一场景的观察 | 随时，且必须交叉验证 |

> 五类各有其位。把书籍当工具手册用、把博客当普适结论用，是最常见的两种误用。

*依据：[O*NET：软件质量保证分析师与测试员职业档案](https://www.onetonline.org/link/summary/15-1253.00) · [DORA 四项关键指标](https://dora.dev/guides/dora-metrics-four-keys/) · [ISO/IEC/IEEE 29119 软件测试系列标准](https://www.iso.org/standard/81291.html)*

### 这张图的 8 个节点，本页各交付什么

### 五类资源各自能提供什么、不能提供什么

把资源按类型分开，是因为它们回答的问题不同。混在一张书单里会让人按流行度而不是按需要选择。

右列是这一类资源共同的局限——知道局限比知道推荐更重要。

| 资源类型 | 能提供 | 共同局限 |
| --- | --- | --- |
| 规范与标准 | 稳定的术语与结构 | 不给具体实现，更新慢 |
| 官方文档 | 准确的接口与能力边界 | 只讲能做什么，不讲什么时候不该用 |
| 开源实现 | 可运行的参考与工件形状 | 质量参差，维护状态需单独核实 |
| 论文与基准 | 方法与评测思路 | 结论受限于其数据与协议 |
| 社区讨论 | 真实痛点与失败信号 | 个例，不能作为普遍性证据 |

> 五类都需要，但不能互相替代。用社区讨论支撑能力声明，或用论文数字当作生产阈值，都是常见的错配。

*依据：[DORA 四项关键指标](https://dora.dev/guides/dora-metrics-four-keys/)*

### 这一页的验收口径：索引本身的时效与可用性

本页的指标度量的是这份索引的健康度：条目是否新鲜、是否写清了边界、是否有替代路径。

R01-4 的出口工件是把「学习」变成「可复核」的关键——学完之后手上多出来的那件东西，才是可以被别人检查的。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| R01-1 | 时效 | 资源条目最近检查日期距今 ≤ 180 天；超期条目数 = 0 | 每半年 1 次 |
| R01-2 | 限制声明 | 写明适用范围与限制的条目比例 = 100% | 每次更新 |
| R01-3 | 替代路径 | 提供 ≥ 1 条替代路径的条目比例 = 100% | 每次更新 |
| R01-4 | 出口工件 | 绑定出口工件的条目比例 = 100%；仅写「了解 X」的条目数 = 0 | 每次更新 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在建学习路线、实际会过期的做法

这两种做法产出快、看起来也很实用。

问题是它们没有自我更新机制，通常六个月后就开始误导人。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 整理一份分级书单：入门、进阶、高级 | 分级清晰，学习者容易上手 | 书单没有检查日期与限制说明。AI 领域半年就会有条目失效，而读者无法判断哪一条已经过时 |
| 按 star 数与热度筛选开源项目作为学习资源 | 热度反映社区认可，筛选成本低 | star 数是发现信号不是质量信号。需要核实的是维护状态、最近提交、issue 响应与是否有可运行示例 |

> 两条的共同修法：给每条资源加上检查日期与限制，并定期重新核对。

### 照着资源学了但用不上时按什么顺序查

学了用不上通常不是资源不好，是资源类型与当前问题不匹配。下表四行覆盖多数情况。

核对之后往往会发现，缺的不是知识而是一次动手产出。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 概念都懂但做不出来 | 缺开源实现与可运行示例 | 找一个能跑通的最小实现 |
| 工具会用但判断不了好坏 | 缺规范与评测方法 | 补方法论与评测设计 |
| 读了很多但没有产出 | 没有绑定工件 | 把每条资源绑定一个要产出的工件 |
| 资料互相矛盾 | 来源类型混用 | 按类型分开，标注各自的适用范围 |

> 第三行是最常见的：把「读完」当作完成，而没有约定读完之后要做出什么。

### 把手上的收藏夹改造成带日期的索引：约 40 分钟

不需要新增资源。把已有的收藏按四个字段重新组织即可。

1. 把现有收藏按五类资源分组：规范、官方文档、开源实现、论文基准、社区讨论。
2. 为每条补四个字段：检查日期、用途、限制、替代路径。
3. 逐条打开确认是否仍然有效；失效的直接删除，不要保留「以后可能有用」。
4. 为每条绑定一个要产出的工件——读完之后要做出什么。
5. 设一个复查周期，到期时重新走一遍前三步。

**期望结果**：改造后的索引通常会比原收藏夹短一半，但每一条都能说清为什么留着它、读完要做出什么。

> ⚠ 不要把索引做成推荐榜。加评分会让人按分数选择，而正确的选择依据是当前要解决的问题。

### 这一页的出口判据

这是 TD-M10 的出口门禁。它守的是这份索引不会悄悄过期，也不会变成一份无法行动的愿望清单。

第三段要接受的是资源本身的质量不确定性——这份索引能保证条目新鲜，不能保证内容正确。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 超过 180 天未检查的条目数 > 0 时阻断使用，先复查<br>无出口工件的条目数 > 0 时阻断，学习目标不可复核 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 资源有效性以复查记录判定，未复查条目标记为待验证而非有效<br>样本不足以判断资源效果时结论为 UNKNOWN | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 资源内容本身的质量与准确性不由本索引担保，由使用者知情接受<br>复查周期与维护投入，由索引维护人承诺并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[O*NET：软件质量保证分析师与测试员职业档案](https://www.onetonline.org/link/summary/15-1253.00)*

### 带走一份会过期提醒自己的索引

索引与书单的唯一区别是：索引记录了检查日期与限制，因此它能告诉你哪些条目该重新核对了。

每条绑定一个产出工件，是防止「读了很多没有产出」的最有效约束。

- 五类资源分开，标注各自的适用范围
- 每条记录检查日期、用途、限制与替代路径
- 每条绑定一个读完要做出的工件

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[ISO/IEC/IEEE 29119 软件测试系列标准](https://www.iso.org/standard/81291.html)** — 过程框架
  - 能证明：测试过程、文档与技术有一套国际通用的术语与结构，可用于对齐跨组织的口径，尤其在合规与外部审计场景下需要引用条款号而不是内部约定。
  - 不能证明：标准正文需付费获取，且它给的是过程框架不是有效性证明；符合标准不代表测试有检测力。本课程只引用其结构，不复制条文。
  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理
- **[O*NET：软件质量保证分析师与测试员职业档案](https://www.onetonline.org/link/summary/15-1253.00)** — 职业事实来源
  - 能证明：这个职业被官方登记的任务、技能与工作活动清单，可用于把「测试开发到底负责什么」从个人经验上升为可引用的职业描述。
  - 不能证明：反映的是美国劳动力市场的既有描述，更新有滞后，且不包含 AI 相关的新增职责；不能作为你所在市场的岗位需求预测。
  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理
- **[DORA 四项关键指标](https://dora.dev/guides/dora-metrics-four-keys/)** — 交付效能判据
  - 能证明：交付效能可以用四个互相制衡的指标描述：部署频率、变更前置时间、变更失败率、恢复时间。互相制衡是关键——只优化速度会让失败率上升，因此单看任一个都会被操纵。
  - 不能证明：衡量的是交付系统不是产品质量；四项指标全优的团队仍然可以交付没人要的功能。
  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理
