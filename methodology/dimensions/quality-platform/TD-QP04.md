## TD-QP04

### 重复事件与部分成功需要两本账

跨系统通知可能重复、乱序或响应丢失；只重试 HTTP 请求不能证明远端副作用恰好一次。

Inbox 记录接收事实，Outbox 记录发送意图，adapter receipt 与对账任务共同决定是否可恢复。

| 故障 | 错误解释 | 复验 |
| --- | --- | --- |
| 重复 CloudEvent | 重试成功 | 重复 CloudEvent 在至少一次投递语义下必然出现；无去重时重复处理次数不为 0 |
| 远端超时 | 没有创建 | 远端超时后状态未知，既不能当成功也不能当失败；缺对账时这类事件的最终状态错误率不可估计，且随重试次数放大 2 倍以上 |
| 通知已发但审计缺失 | 用户收到消息 | 通知已发而审计缺失时，事后无法证明谁在什么时候被通知了什么；合规场景对此的容忍是 0 |
| DLQ 事件丢失 | 队列已清空 | DLQ 事件丢失即失败被静默吞掉；这部分事件的可发现概率为 0 |

> Exactly-once-effect 要看业务账本，不看入口返回码。

### 跨系统事件的四个词

多系统联动的问题不在单个系统，在它们之间的消息。

| 术语 | 一句话解释 |
| --- | --- |
| 事件信封 | 统一的消息外壳：事件 ID、类型、来源、时间、幂等键 |
| 幂等键 | 保证同一事件被处理多次只产生一次副作用 |
| 重放 | 从历史事件重新推进状态；它是恢复手段也是测试手段 |
| 脱敏通知 | 对外通知中移除敏感字段；通知渠道往往是泄露的最后一公里 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[cloudevents/spec](https://cloudevents.io/)*

### 重复事件与部分成功需要两本账

跨系统事件总线的两个基本事实是：投递至少一次（因此会重复），以及消费可能部分成功（因此状态会不一致）。这两件事都不是异常情况，是常态，因此必须在设计时就有对应机制，而不是在事故后补。

重复的处理靠幂等键：消费者记录已处理的事件 id，重复到达时直接跳过。关键在于「记录」与「处理」必须在同一个事务里——分开做的话，进程在两者之间崩溃就会导致要么重复处理要么漏处理。

部分成功需要的是第二本账：一个事件触发了五个动作，其中三个成功两个失败，此时整体状态既不是成功也不是失败。把它记成失败会导致重放时重复执行那三个成功的；记成成功会漏掉那两个。正确做法是记录每个动作的独立状态，重放时只补未完成的。

事件信封的统一（来源、类型、id、时间、关联 id）是这两个机制的基础设施：没有稳定的事件 id 就没有幂等，没有关联 id 就无法把一次业务操作的多个事件串起来查。

*依据：[cloudevents/spec](https://cloudevents.io/) · [asyncapi/spec](https://www.asyncapi.com/docs)*

### 事件总线必须处理的五种情况

五种情况全部是常态而非异常。这张表的用途是逐条确认你的实现有没有对应机制，而不是等它们发生。

第三列是验证手段——每一条都必须被实际构造过一次，配置了不等于生效。

| 情况 | 正确处理 | 验证手段 | 没处理的后果 |
| --- | --- | --- | --- |
| 事件重复 | 幂等键 + 已处理集合，记录与处理同事务 | 重复投递同一事件，断言副作用只发生一次 | 重复扣款、重复通知 |
| 事件乱序 | 按业务时间戳而非到达顺序处理，或显式拒绝乱序 | 打乱顺序投递，断言最终状态正确 | 状态机进入非法状态 |
| 部分成功 | 记录每个动作的独立状态，重放只补未完成的 | 中途注入失败，重放后检查无重复执行 | 重放时重复执行已成功的动作 |
| 消费失败重试耗尽 | 进死信队列并告警，不静默丢弃 | 持续失败，断言进入死信且有告警 | 事件静默消失，业务数据不一致 |
| 敏感信息 | 事件载荷脱敏，通知里不带明文 | 检查事件载荷与通知内容 | 跨系统传播时泄露用户数据 |

> 五行的共同要求：每一条都要有一次实际构造的验证，而不是靠代码评审确认「应该处理了」。

*依据：[cloudevents/spec](https://cloudevents.io/) · [asyncapi/spec](https://www.asyncapi.com/docs) · [debezium/debezium](https://debezium.io/documentation/reference/stable/index.html) · [wiremock/wiremock](https://wiremock.org/docs/)*

### 事件总线必须处理的六种情况

事件驱动的系统里，这六种情况都是常态而非异常。不显式处理，它们会在生产以数据不一致的形式出现。

右列写的是正确行为——注意每一条都要求留下可查的痕迹。

| 情况 | 正确行为 | 必须留下的痕迹 |
| --- | --- | --- |
| 重复投递 | 按幂等键跳过 | 命中记录 |
| 乱序到达 | 按业务规则决定接受或暂存 | 顺序判定依据 |
| 处理失败 | 进重试或死信 | 失败原因与次数 |
| 回写目标不可用 | 暂存并重试，不丢事件 | 暂存队列深度 |
| 需要重放 | 从指定位点重新推进 | 重放范围与执行人 |
| 对外通知 | 脱敏后发送 | 脱敏规则版本 |

> 六行的共同点：都要求事件本身可以被重新处理。做不到重放的系统，故障恢复只能靠人工补数据。

*依据：[asyncapi/spec](https://www.asyncapi.com/docs)*

### 这一页的验收口径：去重、不丢、可对账

QP04-1 与 QP04-2 是分布式集成的基本功：至少一次投递语义下，重复必然发生、失败必须可见。

QP04-4 的对账是承认前两条不可能做到完美之后的兜底——它的价值在于把「不一致」从不可见变成可发现。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| QP04-1 | 幂等去重 | 重复事件被重复处理的次数 = 0 | 每日 |
| QP04-2 | 失败可见 | 失败事件进入 DLQ 的比例 = 100%；被静默丢弃的数量 = 0 | 每日 |
| QP04-3 | 通知与审计成对 | 已发通知均有对应审计记录的比例 = 100% | 持续 |
| QP04-4 | 对账闭环 | 周期对账发现的状态不一致条目在 1 个工作日内修复的比例 = 100% | 每日 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在做事件驱动、实际会丢数据的做法

这两种设计在正常流量下完全正常，问题只在故障时暴露。

而故障时正是最需要它们正确的时候。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 消费失败就记录日志并跳过，避免阻塞后续事件 | 不阻塞队列，系统整体可用性更好 | 跳过的事件永远丢失了。正确做法是进死信队列并告警，让它可以被重新处理 |
| 用事件里的业务字段做幂等判断 | 不需要额外的键，实现简单 | 业务字段可能重复也可能被修改。幂等键必须是事件级的、不可变的标识，且要有明确的作用域与过期时间 |

> 两条的共同要求：事件必须可恢复、可重放，而不是尽力而为地处理一次。

### 跨系统数据对不上时按什么顺序查

数据不一致的根因通常在事件处理的某一种边界情况上。按下表逐项排除。

查之前先确认事件本身是否被完整保存——保存不全时任何排查都是猜。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 数据重复 | 幂等键作用域不对 | 检查键的构成与过期时间 |
| 少了一部分数据 | 失败事件被跳过 | 检查是否有死信队列 |
| 状态顺序错乱 | 乱序未处理 | 检查是否有顺序判定逻辑 |
| 通知里出现敏感字段 | 脱敏规则未覆盖新字段 | 比对通知模板与数据分类 |
| 无法恢复到某个时点 | 事件未持久化 | 确认事件保留期与可重放范围 |

> 最后一行决定了前四行能不能修：事件没保存，所有恢复手段都不存在。

### 做一次事件重放演练：约 55 分钟

重放是这一层最有价值的能力。演练一次就能知道它到底存不存在。

1. 选一段历史事件区间，确认它们仍然在保留期内且可读取。
2. 在隔离环境里从该区间起点重放，观察最终状态是否与当时一致。
3. 在重放过程中故意重复投递一条事件，断言副作用只发生一次。
4. 检查重放是否触发了对外通知——多数系统会在重放时误发通知给真实用户。
5. 把重放的范围、执行人、结果写成记录，作为下次故障恢复的操作依据。

**期望结果**：第四步经常给出意外结果：重放会重新触发通知。发现这一点比完成重放本身更有价值。

> ⚠ 重放演练必须在隔离环境，且通知适配器要显式关闭或指向测试渠道。在生产重放而误发通知，是这类演练最常见的事故。

### 这一页的出口判据

这道门禁守的是跨系统一致性。它无法保证不出现不一致，能保证的是不一致会被发现并被修复。

第三段要接受的是最终一致性窗口：三个系统之间总有状态延迟，这个窗口需要被明确而不是被假装不存在。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 重复事件被重复处理的次数 > 0 或被静默丢弃的事件数 > 0 时阻断<br>已发通知缺少对应审计记录的数量 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 对账发现的不一致率按日统计给出 95% CI，环比以区间重叠判定<br>事件样本 < 200 条时一致性结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 跨系统最终一致性的窗口长度，由平台 owner 签字确定<br>对账无法自动修复而需人工介入的场景，由工程负责人列出并接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[cloudevents/spec](https://cloudevents.io/)*

### 带走一份事件边界情况清单

清单六行，每行写明正确行为与必须留下的痕迹。它同时是设计评审和故障复盘的检查表。

能不能重放，是判断这套事件系统成熟与否的单一最强信号。

- 失败事件进死信并告警，不跳过
- 幂等键是事件级不可变标识，有明确作用域
- 重放演练时关闭对外通知适配器

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[AsyncAPI Specification](https://www.asyncapi.com/docs)** — 事件契约描述格式
  - 能证明：事件驱动接口同样可以有机器可读契约：channel、message payload、schema、绑定协议。它把「这个事件长什么样」从口头约定变成可校验工件。
  - 不能证明：不描述投递语义。至少一次、最多一次、乱序、重复、死信这些真正让事件测试变难的性质，规范里没有，必须自己设计场景验证。
  - `asyncapi/spec` · 版本 v3.1.0（2026-01-31） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[WireMock：HTTP 依赖打桩与故障注入](https://wiremock.org/docs/)** — 依赖隔离与故障注入
  - 能证明：把上游依赖替换成可编程的桩，让超时、5xx、慢响应、错误 body 这些平时碰不到的路径变成可稳定重复的用例。稳定性专项里绝大多数场景需要它才能构造。
  - 不能证明：桩的行为是你编的。真实依赖的失败形态可能与你的假设完全不同——桩测试通过不代表真实降级路径有效。
  - `wiremock/wiremock` · 版本 3.13.2（2025-11-14） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Debezium：变更数据捕获（CDC）](https://debezium.io/documentation/reference/stable/index.html)** — 数据迁移与副作用观测
  - 能证明：从数据库事务日志捕获行级变更并投递为事件，使「数据到底改了什么」可被独立于应用代码地观测。迁移对账与副作用取证都可以据此建立独立查询路径。
  - 不能证明：CDC 是至少一次投递，事件可能重复与乱序。把 CDC 流直接当成对账真值而不做去重与排序，会得到错误结论。
  - `debezium/debezium` · 版本 v3.7.0.Alpha2 · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[CloudEvents：跨系统事件的通用信封](https://cloudevents.io/)** — 跨系统事件契约
  - 能证明：事件的元数据（来源、类型、id、时间、关联 id）有统一命名，使跨系统的事件可以被同一套工具消费与关联——质量平台把需求、构建、测试、发布串起来靠的就是这层信封。
  - 不能证明：信封统一不代表语义统一。两个系统都发 `deployment.finished`，含义可能完全不同。
  - `cloudevents/spec` · 版本 ce@v1.0.2（2022-02-06） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
