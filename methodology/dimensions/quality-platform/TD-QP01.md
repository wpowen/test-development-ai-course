## TD-QP01

### 没有 Basis Gate 就会把旧需求变成自动副作用

Webhook 只说明变化发生，不能证明当前 revision、验收条件和冲突责任人已经被核对。

先回读事实，再生成候选，最后由有权限的人批准；每一步都要留下可回链的证据。

| 缺口 | 看起来像什么 | 阻断证据 |
| --- | --- | --- |
| revision 过期 | 需求已更新但仍可执行 | 基于过期 revision 生成的候选全部作废；一次返工的成本是重跑生成加重新人工复核 2 轮 |
| source_ref 缺失 | 摘要完整 | 无 source_ref 的候选无法在 1 次抽查内被证伪，复核成本高于人工重读原文 |
| reviewer 无范围 | 有人点了批准 | reviewer 没有明确范围时，批准的实际覆盖面不可知；事后追责的可判定性为 0 |
| webhook 当事实 | 事件 payload 足够 | webhook 可能丢失、重复或乱序；把它当唯一事实来源时状态错误率不为 0，必须回读 API 核对 |

> Basis Gate 的职责是证明依据可用，不是替 AI 做业务决策。

### 把需求系统接进测试链的四个词

Jira 里的一条需求不是测试依据。它要先变成有版本、有来源、有冲突状态的东西。

| 术语 | 一句话解释 |
| --- | --- |
| 需求事件 | Jira 的创建/变更/状态流转事件；它是触发信号，不是依据本身 |
| Basis Gate | 把事件转成冻结依据的那道门；不通过就不允许生成下游工件 |
| 冲突状态 | 同一规则在多处描述不一致时的显式标记；它必须阻断而不是被合并 |
| 批准权限 | 谁有权让候选方案进入执行；这个人不能是生成方案的那个系统 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[cloudevents/spec](https://cloudevents.io/)*

### 没有 Basis Gate，旧需求会变成自动化的副作用

把需求系统接进测试链的直觉做法是：需求一变更就自动触发下游生成测试方案。这个自动化在需求本身可信时是提效，在需求不可信时是放大器——它会把一份还没定稿、还有冲突、还没被权威人批准的需求，直接变成几十条测试用例和一次流水线运行。

Basis Gate 就是这条自动化链上的准入闸：需求事件进来之后，先判断这份依据能不能用——状态是否已批准、有没有与其他文档冲突、批准人是否有权限、版本是否被冻结。四项全过才进入下游。

冲突状态是这里最需要显式建模的一项。发现冲突时正确的处理不是让模型投票选一个，而是把状态置为 BLOCKED，记录两处精确 locator 与影响范围，交给有权限的人裁决。裁决结果写回依据之后，链路才继续。

批准权限必须来自需求系统本身而不是配置文件里的一份名单——后者会过期，而且过期时没有任何信号。从源系统读取权限，意味着组织变动会自动生效。

*依据：[cloudevents/spec](https://cloudevents.io/) · [ISO/IEC/IEEE 29119 软件测试系列标准](https://www.iso.org/standard/81291.html)*

### 从需求事件到可执行方案的四道关卡

四道关卡按顺序执行，任一不过即停在当前状态，不进入下一道。第四列写的是不设这道关卡时会发生什么。

注意四道关卡全部在生成测试之前。生成之后再筛，成本已经付出，而且错误的方案可能已经被人看到并采信。

| 关卡 | 检查什么 | 不通过时的状态 | 不设这道关卡的后果 |
| --- | --- | --- | --- |
| 事件契约 | 需求事件是否符合信封规范、是否可去重 | 丢弃或进死信 | 重复事件触发重复流水线，浪费且产生冲突产物 |
| 状态准入 | 需求是否已批准、版本是否冻结 | PENDING，等待批准 | 草稿需求被自动展开成几十条用例 |
| 冲突检测 | 与其他文档是否存在互斥描述 | BLOCKED，附两处精确 locator | 模型自行选一个解释继续，冲突被静默消化 |
| 权限核验 | 批准人是否有权批准这一类变更 | REJECTED，回写原因 | 越权批准的需求进入正式测试链 |

> 四道关卡的产出不是「通过」，而是一个明确的状态。状态本身就是要交给人的信息。

*依据：[cloudevents/spec](https://cloudevents.io/) · [ISO/IEC/IEEE 29119 软件测试系列标准](https://www.iso.org/standard/81291.html) · [cucumber/cucumber](https://cucumber.io/docs/gherkin/reference/)*

### 这张图的 7 个节点，本页各交付什么

这张图的关键设计是 webhook 与 REST 回读并存：webhook 只用来触发，事实一律以回读为准。把 webhook 当事实来源是这类集成最常见的错误。

「Basis Gate/Source Pack」是本页的枢纽——它决定了 AI 拿到的依据是不是冻结且带版本的。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| Jira 需求与变更 | 识别哪些事件需要触发质量动作，并记录触发原因 | 事件订阅清单 |
| Webhook Gateway/Inbox | 验签、去重、入库，只作为触发信号不作为事实 | Inbox 与去重记录 |
| Jira REST 回读 | 以回读结果作为事实来源，核对 webhook 声称的状态 | 回读核对结果 |
| Basis Gate/Source Pack | 把依据冻结成带 revision 的 source pack，冲突未决即阻断 | 冻结依据包（含 revision） |
| AI 候选与 provenance | 生成候选并强制携带 source_ref，无引用即丢弃 | 带引用的候选集 |
| Review Console/人工批准 | 由具权限的人在明确范围内批准，批准范围随决定一起留痕 | 批准记录（含范围） |
| Orchestrator/审计与执行请求 | 只执行已批准的候选，全过程可审计 | 执行请求与审计日志 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 从 Jira 事件到可执行方案的五道关卡

需求系统的字段是给人看的，不是给程序消费的。中间必须有五道转换，每道都可能停下来。

右列写的是这道关卡不设时会发生什么——多数是在用例写完之后才暴露。

| 关卡 | 检查什么 | 不设时的后果 |
| --- | --- | --- |
| 事件接入 | 事件类型、issue key、变更字段 | 把评论变更当成需求变更 |
| Basis Gate | 版本、附件、链接文档是否齐全 | 依据不全就开始生成用例 |
| 冲突检测 | 描述、验收标准、评论三处是否一致 | 模型挑一个最合理的说法 |
| 候选生成 | AI 只产候选，标注 source_ref | 候选被当成结论直接执行 |
| 人工批准 | 有权限的人显式批准 | 没人对这次执行负责 |

> 五道关卡的顺序不能换。跳过第二道去做第三道，冲突检测会在不完整的依据上给出错误结论。

*依据：[ISO/IEC/IEEE 29119 软件测试系列标准](https://www.iso.org/standard/81291.html)*

### 这一页的验收口径：依据冻结与批准可追溯

QP01-1 与 QP01-2 检查的是 AI 产出能不能被核对。没有 revision 与 source_ref 时，人工复核的成本会高于自己重写。

QP01-4 要求批准必须带范围——「同意」而不说同意了什么，在事后追责时等同于没有记录。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| QP01-1 | 依据冻结 | 候选携带冻结 revision 的比例 = 100%；基于过期 revision 生成的候选数 = 0 | 每次生成 |
| QP01-2 | 引用完整 | 候选携带可定位 source_ref 的比例 = 100% | 每次生成 |
| QP01-3 | 事实来源 | 以 REST 回读核对 webhook 状态的比例 = 100%；仅凭 webhook 落库的次数 = 0 | 持续 |
| QP01-4 | 批准可追溯 | 批准记录含批准人与批准范围的比例 = 100% | 每次批准 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来打通了需求系统、实际不可追溯的做法

这两种集成都能跑通，也确实减少了手工搬运。

问题是产出物无法回答「这条用例依据什么」。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 监听 Jira webhook，需求一变就自动生成用例 | 实时性好，减少了人工搬运，链路也清晰 | Jira 的描述字段会被反复编辑。没有冻结版本时，同一条用例昨天和今天依据的文本可能不同，且无法回溯 |
| 把 issue key 写进用例注释作为追溯 | 有 key 就能点回 Jira，追溯关系明确 | issue key 指向的是当前状态，不是生成时的状态。追溯需要的是版本或修改时间戳，不只是 key |

> 两条的共同修法：冻结依据时记录版本与内容 hash，而不是只记 ID。

### 用例与需求对不上时按什么顺序查

「用例和需求不一致」在集成场景里九成是版本问题，不是理解问题。

按下表逐项查，通常两步内定位。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 用例依据的描述已被改过 | 未冻结版本 | 检查依据是否记录了内容 hash |
| 同一规则两条用例结论相反 | 冲突未被检出 | 比对描述、验收标准与评论三处 |
| 用例引用的附件已删除 | 附件未快照 | 把附件内容一并冻结 |
| 没人知道谁批准了这次执行 | 批准记录缺失 | 补批准人、时间与批准范围 |

> 第四行经常被跳过：自动化跑起来之后，「谁批准的」这个问题往往到出事才被问。

### 给一条真实需求做一次 Basis 冻结：约 40 分钟

不需要接系统。手工走一遍五道关卡，就能看出当前集成缺哪几道。

1. 选一条最近变更过的真实需求，记录它的 issue key 与当前版本或最后修改时间。
2. 把描述、验收标准、评论、附件四处的内容分别抄出来，各自计算内容 hash。
3. 逐项比对四处对同一规则的描述，把不一致的地方列成冲突清单。
4. 为每条冲突指定升级责任人——不指定就保持 BLOCKED，不进入下游。
5. 最后写下这次执行的批准人与批准范围；写不出来的，说明批准环节尚不存在。

**期望结果**：典型结果是四处描述里至少有一处不一致，且批准环节从未被显式定义过。这两项都是当天可以立项的修复。

> ⚠ 不要把「以描述字段为准」写成规则来消除冲突。优先级规则必须由产品与技术 owner 共同确认，而不是由集成实现方决定。

### 这一页的出口判据

这道门禁作用在 AI 产出进入执行之前。放到执行之后就失去意义——错误的依据已经变成了错误的动作。

第三段要接受的是自动化范围：哪些动作可以由编排器直接执行、哪些必须人工批准，是权限决策不是技术决策。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 无 source_ref 或基于过期 revision 的候选数 > 0 时阻断执行<br>仅凭 webhook 落库未经回读核对的次数 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 候选采纳率按批次统计，环比波动 > 20pt 时排查依据或提示变更<br>单批候选 < 10 条时不据此评估生成质量，结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 可由编排器直接执行而不需人工批准的动作清单，由平台 owner 签字确定<br>冲突需求在裁决前的阻塞时长，由业务 owner 知情接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[cloudevents/spec](https://cloudevents.io/)*

### 带走一份需求接入的五关卡清单

清单的作用是让「我们接了 Jira」变成「我们在哪五个位置做了什么检查」。

最容易缺的是第二道和第五道：依据冻结与人工批准。

- 冻结依据时记录版本与内容 hash，不只记 ID
- 四处描述比对后再进入生成
- 批准人与批准范围显式记录

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[CloudEvents：跨系统事件的通用信封](https://cloudevents.io/)** — 跨系统事件契约
  - 能证明：事件的元数据（来源、类型、id、时间、关联 id）有统一命名，使跨系统的事件可以被同一套工具消费与关联——质量平台把需求、构建、测试、发布串起来靠的就是这层信封。
  - 不能证明：信封统一不代表语义统一。两个系统都发 `deployment.finished`，含义可能完全不同。
  - `cloudevents/spec` · 版本 ce@v1.0.2（2022-02-06） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Gherkin：结构化的行为描述语法](https://cucumber.io/docs/gherkin/reference/)** — 需求转写格式
  - 能证明：自然语言需求可以被约束成 Given/When/Then 这种有固定槽位的结构，从而变成程序可消费的对象。真正的价值不在语法，在于填槽时会暴露出「前置条件没说清」「预期结果其实没定义」这些原文里藏着的空洞。
  - 不能证明：格式正确不等于规则正确。写成 Gherkin 的错误需求仍然是错误需求，权威裁决这一步无法被格式替代。
  - `cucumber/cucumber` · 版本 gherkin/go/v24.1.0（2022-10-10） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[ISO/IEC/IEEE 29119 软件测试系列标准](https://www.iso.org/standard/81291.html)** — 过程框架
  - 能证明：测试过程、文档与技术有一套国际通用的术语与结构，可用于对齐跨组织的口径，尤其在合规与外部审计场景下需要引用条款号而不是内部约定。
  - 不能证明：标准正文需付费获取，且它给的是过程框架不是有效性证明；符合标准不代表测试有检测力。本课程只引用其结构，不复制条文。
