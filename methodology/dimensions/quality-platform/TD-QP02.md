## TD-QP02

### 旧 SHA 的绿色 Pipeline 不能放行当前 MR

Pipeline、JUnit 和 status 必须绑定同一个 current SHA；局部绿灯跨版本传播会让质量门禁失去意义。

先回读 MR HEAD，再聚合报告和 artifact，缺任何绑定都停在 BLOCKED。

| 竞态 | 错误解释 | 复验 |
| --- | --- | --- |
| MR 推送新 commit | 旧 pipeline 仍 success | MR 推新 commit 后旧结果即失效；不绑定 SHA 时用过期结果放行的概率不为 0 |
| JUnit 缺 suite | 部分报告通过 | JUnit 缺 suite 时聚合器会把缺失当成通过；这类假绿在 fail-open 实现下的检出率为 0 |
| artifact digest 变化 | 下载成功 | artifact digest 变化说明产物已不是被测那一份；此时结论与产物的对应关系断裂，可复核性降为 0 |
| status 延迟到达 | 当前状态绿色 | status 延迟到达时保护分支可能已合并；这段窗口内的合并 100% 未经门禁 |

> 状态颜色不是证据，SHA 绑定才是。

### 把证据绑到代码版本的四个词

流水线里最常见的谎言是：报告是真的，但它属于另一个 commit。

| 术语 | 一句话解释 |
| --- | --- |
| SHA 绑定 | 每份证据都记录它对应的 commit SHA；没有它证据无法归属 |
| JUnit 报告 | 标准化的测试结果格式；它只描述结果，不描述覆盖了什么 |
| 外部质量状态 | 来自扫描、评测等外部系统的结论；它常常滞后于当前 commit |
| fail-closed | 证据不完整时阻断而不是放行；这是聚合逻辑的默认行为 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[in-toto/attestation](https://github.com/in-toto/attestation#readme)*

### 旧 SHA 的绿色 Pipeline 不能放行当前 MR

证据与代码版本的绑定关系，是发布门禁能不能成立的地基。绑定断掉之后，门禁仍然会显示绿色——它只是在检查一份与当前代码无关的证据，而这一点从界面上完全看不出来。

断裂的典型形态有三种：流水线跑的是几次提交之前的代码；证据来自另一个分支；外部质量系统（安全扫描、性能基线）的状态是几天前的缓存。三种都会产生「绿色但无效」的结论。

解决办法是让每一份证据都携带它所对应的 commit SHA，并在放行前做一次严格比对：证据的 SHA 必须等于当前待发布的 SHA。不等就是 fail-closed，而不是「大概差不多」。

更强的形式是可验证声明：把「这个制品跑过这些测试」表达成带签名的 attestation，部署时验证签名与绑定关系。这堵住的是另一类问题——证据被人为替换或伪造，而这在有合规要求的场景里是必须防的。

*依据：[in-toto/attestation](https://github.com/in-toto/attestation#readme) · [sigstore/cosign](https://docs.sigstore.dev/cosign/signing/overview/)*

### 证据聚合必须回答的四个问题

四个问题都必须有机器可判定的答案。任何一个只能靠人「看一眼觉得没问题」，门禁就已经失效了。

第三列给出的是实现手段，从最基础的 SHA 比对到可验证签名，按强度递增。

| 必须回答 | 判定方式 | 实现手段 | 答不上来的后果 |
| --- | --- | --- | --- |
| 这份证据对应哪个 commit | 证据里携带 SHA，与待发布 SHA 严格相等 | CI 元数据 + JUnit 报告扩展字段 | 旧代码的绿色结果放行了新代码 |
| 证据是不是这条流水线产生的 | 验证签名与来源 | in-toto attestation + cosign | 证据可被替换或伪造 |
| 外部质量状态是不是最新的 | 状态带时间戳与目标 SHA，超期即失效 | 外部系统 API + 有效期策略 | 几天前的安全扫描结果被当成当前状态 |
| 缺失的检查怎么处理 | 缺失一律判失败 | fail-closed 策略 | 检查未运行被当成通过，这是最危险的一种 |

> 第四行是唯一一条不需要任何工具、只需要一个决定的：把「没有结果」判成失败而不是通过。

*依据：[in-toto/attestation](https://github.com/in-toto/attestation#readme) · [sigstore/cosign](https://docs.sigstore.dev/cosign/signing/overview/) · [slsa-framework/slsa](https://slsa.dev/spec/v1.0/levels)*

### 这张图的 7 个节点，本页各交付什么

这张图的每个节点都绑在同一个 commit SHA 上。一旦某个环节的结论没有绑 SHA，它就可能被用来给另一份代码放行。

「确定性聚合器」必须 fail-closed：报告缺失、格式异常、suite 数量对不上，一律判失败而不是跳过。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| GitLab MR/当前 HEAD | 以当前 HEAD 的 SHA 作为全流程的绑定键 | SHA 绑定规范 |
| Project Webhook/Inbox | 接收流水线事件并去重，只作为触发信号 | 事件 Inbox |
| Pipeline 与 Jobs | 关联流水线与作业到同一 SHA，缺失作业视为失败 | 作业关联记录 |
| JUnit/Artifact Store | 保存报告与产物并记录 digest，保证结论与产物对应 | 报告与 digest 台账 |
| 确定性聚合器 | fail-closed 聚合，报告缺失或不完整一律判失败 | 聚合结论 |
| SHA-bound Status Check | 把结论写回对应 SHA 的状态检查，不允许跨 SHA 复用 | 状态检查记录 |
| MR Approval/Protected Branch Gate | 保护分支要求状态检查通过且 SHA 一致才允许合并 | 合并门禁配置 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 证据聚合必须回答的五个问题

把多个来源的结果聚合成一个结论时，每一份都要能回答自己属于哪个版本。

右列写的是缺这一项时会出现的具体错误——它们都表现为「明明测过却漏了」。

| 要回答 | 靠什么 | 缺失时的错误 |
| --- | --- | --- |
| 这份报告属于哪个 SHA | 报告元数据里的 commit | 把上次的绿色算成这次的 |
| 报告是否完整 | 期望的 job 数与实际数 | 部分 job 没跑却聚合成通过 |
| 外部状态是否新鲜 | 状态生成时间与 SHA | 用几天前的扫描结论放行 |
| 失败是否被吞掉 | job 退出码与报告解析结果 | 解析失败被当成没有失败 |
| 聚合结论怎么来的 | 聚合规则本身 | 无法复核结论正确性 |

> 五个问题都要在聚合器里显式实现。任何一个默认为「有就行」，就会出现属于别的版本的绿色。

*依据：[sigstore/cosign](https://docs.sigstore.dev/cosign/signing/overview/)*

### 这一页的验收口径：SHA 绑定与 fail-closed

QP02-1 是本页唯一真正重要的一条：结论必须绑定到它实际验证过的那个 SHA。跨 SHA 复用是这类集成最隐蔽的失效。

QP02-2 的 fail-closed 决定了缺报告时的默认行为。fail-open 的聚合器在报告缺失时会给出绿灯，而这正是最需要红灯的时刻。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| QP02-1 | SHA 绑定 | 状态检查绑定到被验证 SHA 的比例 = 100%；跨 SHA 复用结论的次数 = 0 | 每次流水线 |
| QP02-2 | fail-closed | 报告缺失或不完整时判为失败的比例 = 100%；被跳过的次数 = 0 | 每次聚合 |
| QP02-3 | 产物一致 | 结论关联的 artifact digest 与被测产物一致的比例 = 100% | 每次流水线 |
| QP02-4 | 合并保护 | 保护分支在状态检查未通过时允许合并的次数 = 0 | 每周 1 次 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在做质量门禁、实际会放过坏版本的做法

这两种做法在 MR 界面上都显示绿色对勾，评审时也不会有人怀疑。

问题是绿色的来源没有被校验。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| Pipeline 全绿即允许合并 | 流水线是标准门禁，绿色也确实代表 job 都成功了 | job 成功不等于测试跑了。测试因环境问题跳过、报告为空、或解析失败时，job 仍然可能退出 0。必须断言期望的用例数 |
| 把外部扫描结论作为 MR 状态展示 | 外部系统更专业，结论也更全面 | 外部结论常常对应更早的 SHA。必须校验状态里的 commit 与当前一致，否则是在用旧结论放行新代码 |

> 两条的共同修法：聚合前先校验每份证据的 SHA 与完整性，不满足就 fail-closed。

### 合并后立刻出问题时按什么顺序查

「门禁是绿的但合并后就坏了」通常不是漏测，是证据属于别的版本或不完整。

按下表逐项查，四行覆盖绝大多数情况。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 门禁绿但功能坏 | 报告属于旧 SHA | 比对报告元数据与合并的 commit |
| 某类测试从未失败过 | job 静默跳过 | 断言期望用例数而不只看退出码 |
| 扫描结论一直很好 | 外部状态滞后 | 校验状态里的 SHA 与生成时间 |
| 失败被吞掉 | 报告解析异常 | 解析失败必须视为不通过 |

> 第二行最隐蔽：一个从不失败的测试集，通常不是质量好，是根本没跑。

### 给一次 MR 做证据完整性核对：约 35 分钟

挑一个最近合并的 MR，把它的绿色拆开看。

1. 取该 MR 最终通过时的 pipeline，列出所有 job 及其退出码。
2. 打开每份 JUnit 报告，检查里面记录的 commit 与该 MR 的最终 SHA 是否一致。
3. 统计报告里的实际用例数，与预期用例数比较；差异超过一成的说明有 job 静默跳过。
4. 检查外部质量状态对应的 SHA 与生成时间，判断它是否覆盖了本次变更。
5. 把上述四项做成聚合器的断言，任一不满足即 fail-closed。

**期望结果**：多数团队第一次核对会发现至少一类证据的 SHA 不一致，或用例数明显低于预期。这两项都是可以立刻加进聚合器的断言。

> ⚠ 不要用「重跑一次就好了」处理解析失败。解析失败意味着这次的结论未知，而未知不等于通过。

### 这一页的出口判据

这道门禁守的是「绿灯确实属于这份代码」。它不评价代码质量，只保证结论与对象的对应关系没有断。

第三段要接受的是状态到达延迟：从流水线完成到状态写回总有窗口，这段时间的合并策略需要显式决定。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 跨 SHA 复用结论的次数 > 0 时阻断<br>报告缺失时被跳过而未判失败的次数 > 0 时阻断，先修 fail-closed | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 状态写回延迟报 p95/p99，均值不得作为判据<br>流水线样本 < 50 次时延迟结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 状态到达窗口期内的合并策略，由平台 owner 签字确定<br>允许人工覆盖门禁的角色范围与留痕要求，由工程负责人确定并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[slsa-framework/slsa](https://slsa.dev/spec/v1.0/levels)*

### 带走一份证据聚合断言清单

清单五条，全部围绕同一个问题：这份绿色属于哪个版本、是否完整。

加进聚合器后，第一周通常会拦下几次此前会被放行的合并。

- 每份证据校验 SHA 与生成时间
- 断言期望用例数，不只看退出码
- 解析失败与证据缺失一律 fail-closed

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[SLSA：软件制品供应链等级框架](https://slsa.dev/spec/v1.0/levels)** — 供应链判据框架
  - 能证明：构建完整性的分级要求（来源可证明、构建过程可复现、防篡改），把「供应链安全」从含糊目标变成可声明的等级。
  - 不能证明：等级描述构建过程的可信度，不评价依赖本身是否有漏洞。
  - `slsa-framework/slsa` · 版本 v2021-04-21 · NOASSERTION · 许可证未能自动判定，按最保守口径只链接不搬代码
- **[in-toto Attestation：可验证的构建与测试声明](https://github.com/in-toto/attestation#readme)** — 证据可验证性
  - 能证明：「这个制品跑过这些测试」可以被表达成带签名、可机器验证的声明，而不是一份任何人都能编辑的报告。质量证据要进入发布决策，这一步是前提。
  - 不能证明：声明可验证不代表声明的内容为真。签名保证的是「谁说的、没被改过」，不保证测试本身有检测力。
  - `in-toto/attestation` · 版本 v1.2.0（2026-03-18） · NOASSERTION · 许可证未能自动判定，按最保守口径只链接不搬代码
- **[cosign：制品与证据的签名验证](https://docs.sigstore.dev/cosign/signing/overview/)** — 证据可验证性
  - 能证明：把测试证据与制品绑在一起签名之后，发布门禁可以在部署时验证「这份证据确实对应这个镜像」，堵住「拿旧证据放行新制品」这条路。
  - 不能证明：签名验证的是绑定关系与来源，不评价被绑定证据本身的质量。一份没有检测力的测试报告，签名之后仍然是一份没有检测力的测试报告，只是现在可以确定它没被篡改过。
  - `sigstore/cosign` · 版本 v3.1.3（2026-08-06） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
