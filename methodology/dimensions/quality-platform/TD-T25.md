## TD-T25

### Capstone 最容易变成一次演示，而不是一次可被复核的交付

把前面所有模块串起来跑通一遍并不难。难的是让别人拿到你的产物之后，能独立判断它证明了什么、没证明什么。

下面三条是 Capstone 常见的三种「看起来完成了」。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 只提交结果不提交依据 | 缺 lineage 的结果无法在半年后被复现；重放所需的 7 类版本字段缺任一项，重放成功率即为 0 | 「我们做完了 Capstone」无法转化成团队可复用的资产 |
| 实验只有绿灯没有红灯 | 只证明能通过说明不了任何问题；缺中间那次故障注入时，检查有效性的证据为 0 | 一套什么都不检查的流程也能全绿通过 |
| 证据边界没有随产物一起交付 | 本课程所有结论都建立在离线夹具上，更高的 4 级成熟度全部 NOT_RUN；不声明时读者会默认它已被验证 | 把夹具级结论当成生产级承诺对外使用 |

> Capstone 的判据不是「跑通了」，是「别人拿到能复核」。

### Capstone 要交付的四个词

这一页不引入新概念，它检验前面所有工件能不能连成一条链。

| 术语 | 一句话解释 |
| --- | --- |
| Release Candidate | 一个可以被评审的完整版本，而不是一堆分散的产物 |
| 工件链 | 从 PRD 到回滚预案的完整链条，每一环都能指向上一环 |
| 证据闭包 | 每个结论都能追到产生它的那次运行 |
| 成熟度声明 | 这份 RC 各项证据分别到了哪一级 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[slsa-framework/slsa](https://slsa.dev/spec/v1.0/levels)*

### Capstone 最容易变成一次演示，而不是一次可被复核的交付

演示与交付的差别不在完成度，在可复核性。演示只需要在演示者的机器上、在演示者选定的输入下跑通一次；交付需要别人拿到工件之后能独立复现同样的结论。

让它成为交付的核心机制是工件链：从依据到结论的每一步都留下可被下一步消费的工件，且每个工件都有 owner、版本、来源与验收规则。链上任何一环缺失，结论就不再可追溯——而 Capstone 的价值恰恰在于展示这条链是完整的。

证据闭包是更严格的要求：交付包里引用的每一个文件都必须在包里，且哈希一致。「见内网某文档」「详见上一次会议纪要」这类引用会让交付包在离开当前环境后失效，而这正是交付与演示的分水岭。

成熟度声明是最后一环，也是最能体现专业性的一环：明确写出哪些结论已被验证、哪些是设计而未运行、哪些是未知。一份把 fixture 结果说成生产验证的交付，技术上再完整也不可信；而一份诚实标注了边界的交付，即使范围有限也可以被采信。

*依据：[slsa-framework/slsa](https://slsa.dev/spec/v1.0/levels) · [in-toto/attestation](https://github.com/in-toto/attestation#readme)*

### 一个可复核的 RC 必须包含的六类工件

六类工件缺任一类，交付包就退化成演示材料。第三列写的是复核者会拿它做什么——这是判断工件是否合格的实际标准。

最后一类最容易被省略，也最能区分专业交付与作业提交。

| 工件类别 | 包含什么 | 复核者拿它做什么 | 缺失的后果 |
| --- | --- | --- | --- |
| 依据与冲突记录 | 冻结的需求依据、冲突项与裁决结果 | 确认结论建立在哪份规则上 | 无法判断结论是否针对正确的规则 |
| 方案与追踪矩阵 | 风险 → 方法 → 用例 → 证据的映射 | 抽查任一风险是否真的被覆盖 | 覆盖率无法被独立核对 |
| 可运行工件 | 脚本、fixture、配置、精确运行命令 | 在自己机器上重跑一次 | 只能相信演示，无法独立验证 |
| 红绿证据 | baseline / fault / repair 三次运行记录 | 确认测试真的有检测力 | 全绿不能证明任何事 |
| 证据闭包清单 | 引用的每个文件都在包内且哈希一致 | 确认交付包离开当前环境仍然完整 | 包在别处打不开，交付失效 |
| 成熟度声明 | 已验证 / 仅设计 / 未知，逐项标注 | 判断哪些结论可以采信到什么程度 | fixture 结果被误当成生产验证 |

> 六类合起来的判断标准只有一条：一个不了解上下文的人，能不能独立得出同样的结论。

*依据：[slsa-framework/slsa](https://slsa.dev/spec/v1.0/levels) · [in-toto/attestation](https://github.com/in-toto/attestation#readme) · [sigstore/cosign](https://docs.sigstore.dev/cosign/signing/overview/) · [ISO/IEC/IEEE 29119 软件测试系列标准](https://www.iso.org/standard/81291.html)*

### 这张图的 7 个节点，本页各交付什么

这张图是全课程的收口：从需求与风险出发，经数据、提示、判据、基准、性能，最后到发布候选与人工门禁。

每个节点都对应前面某个模块的产物。Capstone 的工作不是重做它们，是把它们接成一条可复核的链。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| PRD/Risk/Owner | 汇总需求、风险与具名责任人，作为整条链的依据 | 风险登记册与 owner |
| Dataset/Split/Trace | 整合数据集划分与 trace，保证结论可回溯 | 数据与 trace 清单 |
| Prompt/Input/Schema | 版本化提示、输入与输出 Schema | 提示包版本 |
| Composite Oracle | 组合确定性判据、语义判据与人工复核 | 分层判据配置 |
| Benchmark/CI | 把评测接入 CI 并以退出码阻断 | CI 门禁配置 |
| Performance/Waiver/Rollback | 整合性能结论、有到期的豁免与回滚方案 | 性能与回滚工件 |
| Fixture RC/Human Gate | 产出发布候选并由人签字，明确证据边界 | 发布候选与签字记录 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 一个完整 RC 必须包含的十项工件

缺任何一项，这个 RC 都无法被独立评审——评审人必须来问你才能理解。

右列写的是这一项缺失时评审会卡在哪里。

| 工件 | 回答什么 | 缺失时评审会问 |
| --- | --- | --- |
| 需求契约 | 要做什么 | 这条规则依据什么 |
| 风险登记册 | 为什么测这些 | 为什么不测那些 |
| Oracle 设计记录 | 凭什么判对错 | 期望值从哪来 |
| 数据集与切片 | 在什么样本上测的 | 样本代表什么 |
| Prompt 包 | 模型怎么被调用的 | 换个说法还成立吗 |
| Scorer 与校准 | 分数怎么来的 | 这个分准吗 |
| CI 门禁配置 | 什么会被拦下 | 坏版本能拦住吗 |
| 性能与成本 | 代价是多少 | 高峰扛得住吗 |
| Waiver 台账 | 哪些没达标 | 谁批准的、什么时候过期 |
| 回滚预案 | 出事怎么办 | 演练过吗 |

> 十项里最常缺的是第六与第十：Scorer 校准与回滚演练。它们恰好决定了分数可信度与事故止损能力。

*依据：[in-toto/attestation](https://github.com/in-toto/attestation#readme)*

### 这一页的验收口径：可复核性

本页的指标不测系统质量，测的是交付物本身能不能被别人复核。这是 Capstone 与一次演示的全部差别。

T25-4 的证据边界声明是硬性的：不写清楚没验证什么，等于默许读者把它当成已验证。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| T25-1 | lineage 完整 | 7 类版本字段记录缺失率 = 0 | 交付时 |
| T25-2 | 红绿可复现 | 实验的 0/1/0 三步全部可复现的比例 = 100% | 交付时 |
| T25-3 | 门禁可阻断 | 注入应被拦的变更时 CI 实测拦截率 = 100% | 交付时 |
| T25-4 | 边界声明 | 交付物包含证据成熟度与 NOT_RUN 声明的比例 = 100% | 交付时 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来交付完整、实际无法评审的做法

这两种交付都包含大量产物，工作量也确实很大。

问题是产物之间没有连接。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 把所有测试报告、评测结果与文档打包交付 | 内容全面，覆盖了各个方面 | 报告之间没有引用关系。评审人无法从一个结论追到产生它的输入与版本，只能逐个相信 |
| 写一份总结文档说明各项都已完成 | 有统一视图，阅读成本低 | 总结是断言不是证据。每一条断言旁边必须有可打开的产物链接，否则它只是一次自评 |

> 两条的共同修法：交付的是一张带链接的图，不是一堆文件或一段总结。

### RC 被打回时按什么顺序查

评审打回的理由通常可以归到下面四类。每一类都对应一个可以补的具体产物。

补完之后重新提交，通常不需要重做任何测试。

| 打回理由 | 缺什么 | 补什么 |
| --- | --- | --- |
| 看不出这个结论怎么来的 | 证据闭包 | 补 run_id 与版本 lineage |
| 不知道哪些没测 | 残余风险清单 | 逐条列出并指定接受人 |
| 分数不知道准不准 | Scorer 校准 | 补 Judge Card 或规则来源 |
| 出事怎么办没说 | 回滚预案 | 补演练记录与触发条件 |

> 四类打回都不是「测得不够」，而是「说不清」。这正是 Capstone 要训练的能力。

### 把已有产物组装成一个可评审的 RC：约 3 小时

不需要新增测试。把前面各页的产物按十项清单归位，缺口自然显现。

1. 按十项工件清单逐项归位，写下每项对应的文件路径。
2. 为每一项标注它的上游：这份产物依据哪一份产生。没有上游的项要说明原因。
3. 逐条检查证据闭包：随机抽三个结论，看能否追到具体的 run_id 与版本。
4. 写成熟度声明：十项分别处于哪一级，哪些是 fixture-tested，哪些是 NOT_RUN。
5. 请一位没参与过的同事按清单评审，记录他问的每一个问题——那些就是缺口。

**期望结果**：典型结果是十项里有两三项缺失，且证据闭包在某一环断掉。同事提的问题清单，就是下一版 RC 的工作项。

> ⚠ 不要为了填满清单而临时补写文档。缺失的项如实标为缺失，比补一份没有证据支撑的文档更有价值。

### 这一页的出口判据

这是全课程的出口门禁。它判断的不是你学会了多少，而是你交出的那份东西别人能不能用、能不能查。

第三段是 Capstone 真正的产物：一份说清楚「这证明了什么、没证明什么」的签字记录。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 7 类版本字段记录缺失率 > 0 时阻断交付<br>缺少证据成熟度与 NOT_RUN 声明的交付物数 = 0，违反即阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 所有对外指标附 95% CI；样本不足时结论记为证据不足而非通过<br>跨版本对比以区间重叠判定，不用点估计差值 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 当前成熟度下未验证的四级证据，由交付人明示并由评审人签字接受<br>夹具与真实环境之间的差距，由项目 owner 估计并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[slsa-framework/slsa](https://slsa.dev/spec/v1.0/levels)*

### 带走一个能被独立评审的 RC

判断标准只有一个：没参与过的人能不能只看产物就理解并质疑你的结论。

做不到时，缺的通常不是内容，是产物之间的引用关系。

- 十项工件逐项归位并标注上游
- 随机抽查证据闭包，验证能追到 run_id
- 成熟度逐项声明，缺失如实标记

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[SLSA：软件制品供应链等级框架](https://slsa.dev/spec/v1.0/levels)** — 供应链判据框架
  - 能证明：构建完整性的分级要求（来源可证明、构建过程可复现、防篡改），把「供应链安全」从含糊目标变成可声明的等级。
  - 不能证明：等级描述构建过程的可信度，不评价依赖本身是否有漏洞。
  - `slsa-framework/slsa` · 版本 v2021-04-21 · NOASSERTION · 许可证未能自动判定，按最保守口径只链接不搬代码
- **[in-toto Attestation：可验证的构建与测试声明](https://github.com/in-toto/attestation#readme)** — 证据可验证性
  - 能证明：「这个制品跑过这些测试」可以被表达成带签名、可机器验证的声明，而不是一份任何人都能编辑的报告。质量证据要进入发布决策，这一步是前提。
  - 不能证明：声明可验证不代表声明的内容为真。签名保证的是「谁说的、没被改过」，不保证测试本身有检测力。
  - `in-toto/attestation` · 版本 v1.2.0（2026-03-18） · NOASSERTION · 许可证未能自动判定，按最保守口径只链接不搬代码
- **[cosign：制品与证据的签名验证](https://docs.sigstore.dev/cosign/signing/overview/)** — 证据可验证性
  - 能证明：把测试证据与制品绑在一起签名之后，发布门禁可以在部署时验证「这份证据确实对应这个镜像」，堵住「拿旧证据放行新制品」这条路。
  - 不能证明：签名验证的是绑定关系与来源，不评价被绑定证据本身的质量。一份没有检测力的测试报告，签名之后仍然是一份没有检测力的测试报告，只是现在可以确定它没被篡改过。
  - `sigstore/cosign` · 版本 v3.1.3（2026-08-06） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[ISO/IEC/IEEE 29119 软件测试系列标准](https://www.iso.org/standard/81291.html)** — 过程框架
  - 能证明：测试过程、文档与技术有一套国际通用的术语与结构，可用于对齐跨组织的口径，尤其在合规与外部审计场景下需要引用条款号而不是内部约定。
  - 不能证明：标准正文需付费获取，且它给的是过程框架不是有效性证明；符合标准不代表测试有检测力。本课程只引用其结构，不复制条文。
  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理
