## TD-QP03

### 共享临时环境会把隔离问题变成平台事故

namespace、RBAC、NetworkPolicy、Quota 和 cleanup 必须同时成立；只看到 Pod Running 不代表测试环境安全。

先验证身份和边界，再执行测试，最后按 owner/TTL 回收并复核审计。

| 风险 | 表面绿灯 | 必须保留 |
| --- | --- | --- |
| runner 读 Secret | Job 成功 | runner 能读到超出本次运行所需的 Secret 时，最小权限被破坏；越权可读条目数必须为 0 |
| 跨 namespace 访问 | 服务可达 | 跨 namespace 访问成功即隔离失效；1 次成功访问就足以让并发运行互相污染 |
| 超 quota 创建 | 单次测试完成 | 超 quota 创建会挤占其他运行的资源；缺 quota 时 1 次失控运行即可影响整个集群 |
| cleanup 残留 | 删除命令 0 | owner 资源清单与 receipt |

> 回收和审计是环境完成条件，不是运维附加项。

### 临时测试环境的四个词

每次 MR 起一套环境听起来很贵，但比共享环境的互相污染便宜得多。

| 术语 | 一句话解释 |
| --- | --- |
| 短生命周期 namespace | 为一次运行创建、用完即销毁的隔离单元 |
| ResourceQuota | 限制这套环境能占用的资源上限；防止一次失控拖垮集群 |
| NetworkPolicy | 限制它能访问什么；防止测试环境打到生产依赖 |
| TTL | 到期自动回收；没有它，被遗忘的环境会持续计费 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[loft-sh/vcluster](https://www.vcluster.com/docs)*

### 共享临时环境会把隔离问题变成平台事故

共享测试环境的经典问题是互相干扰：A 的测试改了数据导致 B 的测试失败，而 B 的作者会花半天时间在自己的代码里找原因。这类损耗不会出现在任何报表上，但它是测试体系里最大的隐性成本之一。

按需创建的短生命周期环境从结构上消掉了这个问题：每条分支拥有独立的 namespace，用完即销毁。这不只是「更干净」，它改变了测试的可信度——一次失败可以确定是自己的代码造成的，而不是环境残留。

但按需创建引入了新的失败面：环境创建失败、资源耗尽、TTL 未生效导致环境泄漏。这三项必须有自己的监控，否则平台会在某个周一早上因为累积了几百个未回收的 namespace 而不可用。

ResourceQuota 与 NetworkPolicy 是这套机制的安全边界：前者防止单个测试环境耗尽集群资源，后者防止测试环境访问到生产依赖。第二项尤其重要——一个能连到生产数据库的测试环境，迟早会有人在上面跑一次删除测试。

*依据：[loft-sh/vcluster](https://www.vcluster.com/docs) · [testcontainers/testcontainers-python](https://testcontainers-python.readthedocs.io/)*

### 临时环境必须配齐的五项

五项里前两项是功能，后三项是防护。跳过后三项的临时环境方案，会在规模上来之后变成平台事故的来源。

第四列是不配的具体后果，全部是可预期的、而不是理论上的风险。

| 配置项 | 作用 | 工具 | 不配的后果 |
| --- | --- | --- | --- |
| 短生命周期 namespace | 每条分支独立环境，用完即销毁 | vcluster | 共享环境互相干扰，失败归因成本极高 |
| 可复位的依赖 | 数据库、队列随环境创建与销毁 | Testcontainers | 依赖仍共享，隔离只做了一半 |
| ResourceQuota | 限制单环境资源上限 | Kubernetes 原生 | 一个失控测试耗尽集群，影响所有人 |
| NetworkPolicy | 禁止测试环境访问生产依赖 | Kubernetes 原生 | 测试环境连到生产库，迟早出事 |
| TTL 与回收监控 | 超时自动销毁，回收失败要告警 | 自建控制器 + 告警 | 环境泄漏累积，平台在某天不可用 |

> 前两项决定隔离做没做到，后三项决定这套机制能不能长期运行下去。

*依据：[loft-sh/vcluster](https://www.vcluster.com/docs) · [testcontainers/testcontainers-python](https://testcontainers-python.readthedocs.io/) · [prometheus/prometheus](https://prometheus.io/docs/practices/histograms/)*

### 这张图的 7 个节点，本页各交付什么

这张图描述一次临时测试环境的完整生命周期：申请、创建、限权、运行、回收。它的每一段都可能变成一个长期不被发现的资源与权限缺口。

「TTL/Stop/Cleanup Worker」是最容易被省略也最容易积累成本的一节——没有强制回收的临时环境不会临时。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| MR/Run 请求 | 记录申请来源与用途，作为回收与审计的依据 | 运行申请记录 |
| Namespace Provisioner | 按运行创建独立 namespace，保证并发运行互不影响 | namespace 创建策略 |
| Namespace/RBAC/ServiceAccount | 按最小权限授予，验证越权读取失败 | RBAC 配置与越权测试 |
| Quota/NetworkPolicy | 限制资源与网络出入，防止单次失控运行影响集群 | 配额与网络策略 |
| Test Job/Runner | 执行测试作业，产物写入受控位置 | 作业与产物路径 |
| TTL/Stop/Cleanup Worker | 到期强制回收，验证回收成功率 | 回收记录与成功率 |
| K8s Audit/平台审计 | 保留审计日志，使越权与异常创建可追溯 | 审计日志 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 临时环境必须配齐的六项

少配任何一项，问题都会在几周后以成本或串扰的形式出现。

右列写的是缺失时的典型症状——它们往往不会被归因到环境配置上。

| 必配项 | 作用 | 缺失时的症状 |
| --- | --- | --- |
| 独立 namespace | 隔离 | 测试互相干扰，结果不可复现 |
| RBAC | 最小权限 | 测试身份能读到不该读的资源 |
| ResourceQuota | 资源上限 | 一次失控占满节点 |
| NetworkPolicy | 出入方向限制 | 测试流量打到生产依赖 |
| Job TTL | 自动回收 | 被遗忘的环境持续计费 |
| 审计记录 | 可追溯 | 出事后查不到谁创建了什么 |

> 六项都是声明式配置，一次做好后可以模板化。真正的成本在第一次，不在每一次。

*依据：[loft-sh/vcluster](https://www.vcluster.com/docs)*

### 这一页的验收口径：隔离、限额与回收

QP03-1 与 QP03-2 是安全性质的：越权与跨命名空间访问一次成功即失效，不设容忍区间。

QP03-4 的回收成功率直接决定成本——未回收的临时环境会持续计费，而且通常没有人认领。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| QP03-1 | 最小权限 | ServiceAccount 可读取的越权 Secret 条目数 = 0 | 每次环境模板变更 |
| QP03-2 | 命名空间隔离 | 跨 namespace 访问成功次数 = 0 | 每周 1 次 |
| QP03-3 | 资源限额 | 超出 ResourceQuota 的创建成功次数 = 0 | 每次环境模板变更 |
| QP03-4 | 按时回收 | TTL 到期后回收成功率 = 100%；残留 namespace 数 = 0 | 每日 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在做环境隔离、实际隔不住的做法

这两种做法都比共享单一环境进步，也确实减少了一些冲突。

问题是隔离维度不完整。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 每个 MR 一个 namespace，实现了隔离 | namespace 是 K8s 的标准隔离单元 | namespace 只隔离了 API 对象。没有 NetworkPolicy 时，Pod 仍可访问集群内外的任意地址，包括生产依赖 |
| 测试结束后在流水线最后一步删除 namespace | 清理逻辑明确，正常路径下也确实删掉了 | 流水线被取消或超时时，删除步骤不会执行。必须用 TTL 或独立的回收任务兜底，不能只靠流水线 |

> 两条的共同要求：隔离要覆盖网络维度，回收要有不依赖流水线的兜底。

### 测试结果不可复现时按什么顺序查

不可复现的第一嫌疑永远是环境串扰，而不是测试代码。

按下表逐项排除，前两行占多数。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 单跑通、并行跑挂 | 共享了某个资源 | 检查是否有集群级共享对象 |
| 偶尔连到了错误的服务 | 缺 NetworkPolicy | 限制出方向并显式声明依赖 |
| 资源不足导致 Pod 挂起 | 无 ResourceQuota | 设配额并让超限快速失败 |
| 集群里有大量废弃 namespace | TTL 缺失 | 加 TTL 与独立回收任务 |
| 查不到某环境的来源 | 无审计记录 | 在创建时打上 MR 与创建者标签 |

> 第二行最容易被误判成「网络抖动」，实际是测试打到了不该打的地方。

### 给临时环境补齐六项配置：约 50 分钟

先盘点现状，再补最缺的那两项。不需要一次全做。

1. 列出当前临时环境的创建方式，逐项核对六项配置分别有没有。
2. 优先补 NetworkPolicy：先设默认拒绝出方向，再逐条放通真正需要的依赖。
3. 补 TTL 或独立回收任务，验证在流水线被取消时环境仍会被回收。
4. 在创建时打上标签：MR 编号、创建者、创建时间，供审计使用。
5. 跑一次并行测试，确认两套环境之间没有任何共享资源。

**期望结果**：补完 NetworkPolicy 后通常会立刻发现有测试在访问未声明的依赖——那些依赖此前一直是隐式的。

> ⚠ 默认拒绝出方向会让一批测试立刻失败。这是预期结果：失败的每一条都对应一个此前未被声明的依赖。

### 这一页的出口判据

这道门禁同时守安全与成本。它们看起来是两件事，实际由同一组配置决定：权限、配额、TTL。

第三段要接受的是环境保真度：临时环境与生产总有差距，哪些差异可以接受需要明确。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 越权 Secret 可读条目数 > 0 或跨 namespace 访问成功次数 > 0 时阻断<br>TTL 到期回收成功率 < 100% 时阻断，先修回收链路 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 回收成功率按日统计给出 95% CI 下界与阈值比较<br>运行样本 < 30 次时回收结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 临时环境与生产之间的已知差异，由平台 owner 列出并签字接受<br>TTL 时长与调试便利之间的取舍，由工程负责人确定并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[testcontainers/testcontainers-python](https://testcontainers-python.readthedocs.io/)*

### 带走一份临时环境配置模板

模板一次做好可以复用到所有项目。真正的成本在第一次梳理依赖，不在每次创建。

标签是审计的基础：没有 MR 与创建者标签，环境治理只能靠人记。

- 隔离必须覆盖网络维度，不只是 namespace
- 回收要有不依赖流水线的兜底
- 创建时打标签，供成本与审计追溯

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Testcontainers：用真实依赖容器做集成测试](https://testcontainers-python.readthedocs.io/)** — 副作用层基础设施
  - 能证明：副作用断言需要一个可复位的真实数据库或消息队列。Testcontainers 让「调完接口直接查库」成为可在 CI 里稳定重复的动作，而不是只能在共享测试环境上手工做一次。
  - 不能证明：容器里的数据库不等于生产数据库。版本、扩展、参数、数据量与并发都不同，性能与锁行为结论不能外推。
  - `testcontainers/testcontainers-python` · 版本 testcontainers-v4.15.0（2026-07-24） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
