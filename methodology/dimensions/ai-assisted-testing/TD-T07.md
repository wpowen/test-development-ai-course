## TD-T07

### 选错数据方法，测试量再大也只是在同一个位置反复敲

边界值、组合、性质、模糊测试不是四种风格偏好，是四种失败模型的对应解。用组合测试去测阈值，或者用模糊测试去测业务不变量，投入和产出会严重不成比例。

下面三条说明方法选错之后，工作量花在了哪里。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 用等概率随机去测阈值型缺陷 | 阈值缺陷通常只在边界 ±1 个单位处暴露，随机采样命中该窗口的概率随取值域增大迅速趋近 0 | 跑了 10 万条随机数据没发现问题，得出「边界处理没问题」 |
| 用穷举组合去测高维参数 | 10 个二值参数的全组合是 1024 条，20 个就是 1048576 条，而两两覆盖只需数十条即可覆盖绝大多数交互缺陷 | 为了「覆盖全面」把用例数堆到不可维护，实际交互覆盖并没有更好 |
| 模糊测试不保存 seed 与最小反例 | 缺 seed 时一次崩溃的复现概率接近 0，缺 shrink 时反例往往有数千字节，无法用于调试 | 记录一条「偶发崩溃」，缺陷进不了回归，下个版本原样复现 |

> 共同点：三条都不是执行力不足，是在选方法这一步就已经决定了结果。

### 选数据方法的四个词

造测试数据不是随机生成。先判断失败长什么样，方法才有依据。

| 术语 | 一句话解释 |
| --- | --- |
| 边界 | 阈值附近的取值；适用于有明确分界线的场景 |
| 组合 | 多个参数的取值搭配；适用于参数间互相影响的场景 |
| 属性 | 对任意输入都应成立的性质；适用于有不变量但无唯一答案的场景 |
| Fuzz | 大量随机或畸形输入；适用于输入面未知、要找崩溃与异常的场景 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[HypothesisWorks/hypothesis](https://hypothesis.readthedocs.io/en/latest/)*

### 选错数据方法，测试量再大也只是在同一个位置反复敲

四种数据方法对应四种不同的失败模型，用错了不是效率问题而是覆盖问题——再多的用例也检不出那一类缺陷。边界值针对的是阈值判断错误，组合法针对的是条件交互，属性测试针对的是不变量违反，Fuzz 针对的是解析与健壮性。

判断该用哪一种，先问这个功能最可能怎么坏。有明确阈值的（金额上限、字数限制、时间窗口）用边界值；有多个条件互相影响的（权限 × 状态 × 渠道）用组合法；有可表述不变量的（往返一致、守恒、幂等）用属性测试；接受外部非结构化输入的（文件、协议、用户文本）用 Fuzz。

AI 在这里的作用是加速而不是替代判断。让模型生成 500 条数据很容易，但如果方法选错了，这 500 条全部落在同一个位置上。正确用法是先由人确定方法与失败模型，再让模型在该方法的框架内扩充样本。

组合法有一个实用的成本控制手段：多数交互缺陷只涉及两个条件，因此成对覆盖（pairwise）能用远小于全组合的用例数捕获绝大部分交互缺陷。这是组合爆炸场景下最值得先用的一招。

*依据：[HypothesisWorks/hypothesis](https://hypothesis.readthedocs.io/en/latest/) · [schemathesis/schemathesis](https://schemathesis.readthedocs.io/)*

### 四种方法各自适用什么失败模型

先看第二列判断该用哪一种，再看第三列估成本。方法选对之后 AI 才有用武之地，选错则生成量越大浪费越大。

第四列是 AI 在这一行能做什么——注意它的位置都在「扩充」而不是「决定」。

| 数据方法 | 针对的失败模型 | 工具 | AI 在这里做什么 |
| --- | --- | --- | --- |
| 边界值 | 阈值判断错误：大于写成大于等于、精度截断 | 手工 + 从 Schema 自动提取 | 从需求文本里抽出所有阈值，避免遗漏 |
| 组合（成对覆盖） | 条件交互：权限 × 状态 × 渠道的特定组合出错 | 成对覆盖生成器 | 列出条件与取值，人确认后由算法生成组合 |
| 属性测试 | 不变量违反：往返不一致、守恒被破坏、非幂等 | Hypothesis | 根据业务描述提出候选不变量，由人确认后写成属性 |
| Fuzz | 解析健壮性：畸形输入导致崩溃或异常行为 | Schemathesis（协议层）+ 通用 fuzzer | 从契约自动派生非法输入，覆盖人想不到的形态 |

> 四行的共同结构：方法由人选，样本由工具或模型扩充。反过来做——先让模型生成再找理由——是这一页要避免的。

*依据：[HypothesisWorks/hypothesis](https://hypothesis.readthedocs.io/en/latest/) · [schemathesis/schemathesis](https://schemathesis.readthedocs.io/) · [python-jsonschema/jsonschema](https://python-jsonschema.readthedocs.io/)*

### 这张图的 8 个节点，本页各交付什么

这张图的入口是「批准 Failure Model」而不是「选工具」。先说清楚你预期的缺陷长什么样，方法选择才有依据——这个顺序是本页的全部内容。

右半段的 Shrink 与 Replay 决定了这次测试有没有留下资产：不能回放的失败等于没发现。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 批准 Failure Model | 写明本轮预期的缺陷形态：阈值、交互、不变量违反、还是未知输入面 | 失败模型声明 |
| 合法域与约束 | 定义输入的合法取值域与约束，防止生成大量无效输入淹没真实缺陷 | 输入域与约束定义 |

### 四种方法各自适用什么失败模型

方法选择的依据是「失败长什么样」，不是「哪种方法更高级」。下表按失败模型选。

右列写的是用错方法时的表现——通常是跑了很多用例却什么都没发现。

| 失败模型 | 选哪种 | 用错时的表现 |
| --- | --- | --- |
| 阈值附近判断错 | 边界 | 随机取值极少落在边界上 |
| 参数搭配引发异常 | 组合 | 单参数测试全过，组合出问题 |
| 有不变量但无标准答案 | 属性 | 精确匹配把合法变体判错 |
| 输入面未知、要找崩溃 | Fuzz | 手写用例覆盖不到畸形输入 |

> 四行不是互斥的。一个真实模块常常需要两到三种，按不同的失败模型分别应用。

*依据：[HypothesisWorks/hypothesis](https://hypothesis.readthedocs.io/en/latest/)*

### 这一页的验收口径：可复现性是数据方法的生命线

下面四条里有三条与复现有关。原因是数据方法产出的价值不在于「这次发现了什么」，而在于「下次还能不能再发现」。

T07-2 的两两覆盖是一个成本与覆盖的经典折中：它无法覆盖三因子及以上的交互，选它就意味着显式接受这个盲区。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| T07-1 | 生成可复现性 | seed 记录率 = 100%；同一 seed 重跑得到相同输入集的比例 = 100% | 每次运行 |
| T07-2 | 组合覆盖强度 | 关键参数集达到两两（pairwise）覆盖率 = 100%；三因子交互显式列为已知盲区 | 每次发布 |
| T07-3 | 最小反例质量 | 失败样本 shrink 后可回放率 ≥ 95%，中位长度相对原始样本缩减 ≥ 80% | 每次运行 |
| T07-4 | 回归固化率 | 已确认缺陷转为回归用例的比例 = 100%，未固化即视为该缺陷未闭环 | 每次修复 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来数据很充分、实际发现不了问题的做法

这两种做法都能产生大量测试数据，执行也很快。

问题是数据的分布与失败模型无关。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 用随机生成器造一万条测试数据，覆盖面广 | 数据量大、分布广、成本也低 | 随机数据几乎不会落在边界上。一万条随机金额里可能没有一条恰好等于上限，而错误恰恰发生在那里 |
| 属性测试跑通了就说明不变量成立 | 属性测试确实在大量输入上验证了性质 | 默认生成器的分布往往覆盖不到业务边界。属性测试要配自定义生成器，并保存失败时的最小反例与 seed |

> 两条的共同修法：让数据分布对准失败模型，而不是追求数量或广度。

*依据：[schemathesis/schemathesis](https://schemathesis.readthedocs.io/)*

### 测试数据很多但漏测时按什么顺序查

数据多而漏测，通常是分布问题。按下表逐项查。

第一行的验证很简单：统计有多少条数据落在边界上。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 边界问题反复出现 | 数据未覆盖边界 | 显式构造边界值与其邻域 |
| 组合场景出问题 | 只测了单参数 | 用 pairwise 覆盖参数搭配 |
| 属性测试从不失败 | 生成器分布太窄 | 自定义生成器并加入业务边界 |
| 崩溃只在生产出现 | 缺畸形输入 | 补 Fuzz 并保存最小反例 |
| 失败无法复现 | 未保存 seed | 记录 seed 与最小反例 |

> 最后一行是所有随机方法的共同要求：不保存 seed 的失败等于没发现过。

### 给一个模块选方法并构造数据：约 50 分钟

先写失败模型，再选方法。顺序反了会退化成「用我熟悉的工具」。

1. 选一个模块，列出它可能的失败方式，尽量具体到「什么条件下会错」。
2. 对每种失败方式对照上表选方法，并写下选择理由。
3. 按选定的方法构造数据：边界要显式列出上下界与邻域，组合要列出参数与取值集合。
4. 对随机类方法，固定 seed 并确认失败时能输出最小反例。
5. 跑一遍，对比新数据与原有数据各自发现了什么——通常新方法会立刻抓到一两个此前不知道的问题。

**期望结果**：产出是一份带选择理由的方法记录加一组新数据。最有价值的部分是「为什么不用另外三种」这几句话。

> ⚠ 不要在没有失败模型的情况下先选方法。那样写出的理由会变成事后合理化，下次换人还得重来。

### 这一页的出口判据

这一页的门禁不评价「测得够不够多」，它评价「测出来的东西能不能用」。一条无法回放的崩溃，在工程上等价于没有发生过。

第三段的内容通常是覆盖盲区：选了两两覆盖就放弃了三因子交互，这个取舍必须被写下来并被接受，而不是被默认。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | seed 记录缺失率 > 0 时阻断，该轮结果不可复现即作废<br>已确认缺陷未固化为回归用例的数量 > 0 时阻断修复闭环 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 缺陷发现率按单位用例数统计，与上一轮比较时以区间重叠判定是否有变化<br>运行样本 < 1000 条时不据此评估模糊测试的充分性，结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 选择两两覆盖而放弃更高阶交互的盲区，由测试负责人签字接受<br>长期无法 shrink 的失败样本，由测试负责人明示接受其调试成本 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一份带理由的方法选择记录

记录的价值在于它可以被质疑：别人看到失败模型与方法的对应关系，就能指出哪里选错了。

没有理由的方法选择在半年后会退化成惯例，然后没人敢改。

- 先写失败模型，再选方法
- 边界要显式构造，不靠随机撞上
- 随机类方法固定 seed 并保存最小反例

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Schemathesis：由 OpenAPI 契约驱动的属性测试引擎](https://schemathesis.readthedocs.io/)** — 传统专项工具
  - 能证明：把 OpenAPI 里声明的类型、枚举、边界当成属性，自动生成大量合法与非法请求，检出「实现与自己声明的契约不一致」这一类缺陷——例如声明 int32 实际接受任意长度、声明 required 实际可省略、声明 404 实际返回 500。
  - 不能证明：它的判据全部来自 Schema，因此对「格式合法但业务错误」完全无能为力。金额为负、状态非法转换、退款超过实付都能通过它的全部检查。把 Schemathesis 全绿当成接口测试完成，正是本模块反复拆解的那个陷阱。
  - `schemathesis/schemathesis` · 版本 v4.24.3（2026-07-25） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Hypothesis：Python 属性测试库](https://hypothesis.readthedocs.io/en/latest/)** — 方法学实现
  - 能证明：属性测试的执行机制：从策略（strategy）采样输入、在失败时自动收缩（shrink）到最小反例、用 example database 复现历史失败。收缩是它相对随机测试的关键差异——它把「某次随机跑挂了」变成「这个最小输入必然挂」。
