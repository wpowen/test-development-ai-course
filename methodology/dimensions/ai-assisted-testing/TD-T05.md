## TD-T05

### 让 AI 读需求提风险，最先坏掉的不是准确率，是可追溯性

AI 从 PRD 和代码 Diff 里提风险，产出速度比人快一个量级。问题从来不在它提得少，而在于它提的东西你无法核对——一份没有引用的风险清单，和一份凭印象写的风险清单，可信度是一样的。

它们的共同特征是：产出看起来专业，且不会报错。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 风险候选不带原文引用 | 无引用的候选无法在 1 次抽查内被证伪，复核成本反而高于人工重读全文 | 把 AI 的措辞自信度当成依据强度，把「可能存在并发问题」写进测试设计 |
| 模型编造了 PRD 里没有的业务政策 | 虚构政策在生成结果中的占比虽低，但它拦截率必须是 100%——放过 1 条就足以让整份测试设计建立在假前提上 | 为一条不存在的退款规则设计了 12 条用例，评审时无人发现 |
| Basis 未冻结就反复生成 | 需求文档在一次迭代内被改动 3～5 次是常态；未冻结时两次生成的差异无法归因于模型还是文档，定位一次这类差异的平均代价是重跑 2 轮生成 | 以为调 Prompt 起了作用，实际是有人改了 PRD |

> 三条都不是模型能力问题。它们在流程里被解决：冻结、引用、门禁——顺序不能变。

### 从变更里提风险的四个词

让 AI 读代码 diff 提风险很容易，让它提出的风险可追溯才是难点。

| 术语 | 一句话解释 |
| --- | --- |
| 冻结 Basis | 本次变更所依据的需求、设计与契约的固定版本 |
| 代码 Diff | 本次实际改动；它回答「改了什么」，不回答「该测什么」 |
| 带引用的风险候选 | 每条风险都指向具体的 source_ref 或 diff 行 |
| 虚构政策 | 模型补写的、原文不存在的业务规则；它是本页要阻断的主要失败 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[cucumber/cucumber](https://cucumber.io/docs/gherkin/reference/)*

### 让 AI 读需求提风险，最先坏掉的不是准确率而是可追溯性

模型从需求文档里提风险这件事，效果通常不错——它能列出一堆看起来合理的风险点。问题出现在下一步：这条风险是从文档哪一句推出来的？如果答不上来，这条风险就无法被验证、无法被裁决，也无法在需求变更时被重新评估。

更糟的形态是虚构政策：模型基于常识补出了一条文档里并不存在的规则（「退款应在 7 个工作日内到账」），而这条规则听起来非常合理，因此评审时不会有人质疑。它随后会变成测试用例、变成缺陷、变成一次与产品的无谓争论。

唯一有效的约束是强制引用：每一条风险候选必须携带 source_ref，指向依据里的精确位置。没有 source_ref 的候选一律标为 UNKNOWN，不进入下游，而不是「先用着」。

冻结 Basis 是前提：模型读的必须是一份版本固定、冲突已裁决的依据。让模型读一堆互相打架的文档，它会自行调和矛盾并给出一个自洽的答案——而这个自洽恰恰掩盖了本该被暴露的冲突。

*依据：[cucumber/cucumber](https://cucumber.io/docs/gherkin/reference/) · [ISO/IEC/IEEE 29119 软件测试系列标准](https://www.iso.org/standard/81291.html)*

### 四类输入各自能提出什么风险、各自的可追溯性

第三列是这张表的重点：可追溯性强弱决定了这类风险能不能直接进入下游，还是必须先人工确认。

代码 diff 是可追溯性最强的一类输入，也是最容易被忽略的——多数团队只让模型读需求文档。

| 输入类型 | 能提出什么风险 | 可追溯性 | 处置 |
| --- | --- | --- | --- |
| 冻结的需求依据 | 业务规则边界、例外、状态转换 | 强：可指向具体条款 | 带 source_ref 直接进入候选池 |
| 代码 diff | 受影响模块、调用链、数据结构变更 | 最强：可指向具体行 | 自动关联到回归范围 |
| 历史缺陷与事故 | 同类模式复发风险 | 中：可指向缺陷 id | 作为风险权重输入，不直接生成用例 |
| 模型的通用知识 | 常见的行业性风险 | 无：无法指向任何依据 | 标为 UNKNOWN，必须人工确认后才能使用 |

> 前三行可以自动化流转，第四行必须停下来。把第四行也放进去，就是虚构政策进入测试链的路径。

*依据：[cucumber/cucumber](https://cucumber.io/docs/gherkin/reference/) · [ISO/IEC/IEEE 29119 软件测试系列标准](https://www.iso.org/standard/81291.html) · [semgrep/semgrep](https://semgrep.dev/docs/)*

### 这张图的 7 个节点，本页各交付什么

这张图的关键设计是「独立 Oracle 注册表」与「风险候选生成」并列而不串联：判据来源必须独立于生成过程，否则模型既出题又判卷。

整条链路的产出不是风险清单，是一份可以被业务 Owner 在 30 分钟内逐条核对的候选包。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 冻结需求与设计 | 把 PRD、设计稿冻结成带 hash 的快照，作为本轮生成的唯一依据 | Basis 冻结快照（含 hash） |
| 独立 Oracle 注册表 | 维护与生成过程无关的判据来源，防止模型自出自判 | Oracle 注册表 |
| 版本化代码 Diff | 把代码变更纳入输入，区分「需求变了」和「实现变了」两类风险 | 版本化 Diff 输入 |
| 风险候选生成 | 约束模型只输出带原文引用的候选，不接受无引用陈述 | 带引用的风险候选集 |
| 引用与冲突门禁 | 逐条校验引用是否真实存在、是否与 Basis 冲突，不通过即拦下 | 引用校验报告 |
| 业务 Owner 复核 | 由业务方裁决候选是否成立，裁决结果留痕 | Owner 裁决记录 |
| 测试设计 Backlog | 只有通过门禁并被裁决为成立的候选才进入设计队列 | 可追溯的测试设计条目 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 四类输入各自能提出什么风险

风险不能只从代码来，也不能只从需求来。四类输入各自看到不同的东西。

右列写的是只用这一类时会漏掉什么——四行合起来就是为什么必须都要。

| 输入 | 能提出的风险 | 只用它会漏掉 |
| --- | --- | --- |
| 需求契约 | 业务规则被违反 | 实现引入的新失败 |
| 技术设计 | 接口、状态、副作用 | 需求未授权的行为 |
| Oracle 记录 | 判据本身失效 | 没有 Oracle 的盲区 |
| 代码 diff | 实际改动影响面 | 文档改了代码没改 |

> 第四行是最容易被单独使用的：只看 diff 提风险，会漏掉「需求变了但代码没改」这类问题。

*依据：[cucumber/cucumber](https://cucumber.io/docs/gherkin/reference/)*

### 这一页的验收口径：可追溯性优先于准确率

注意下表没有「风险识别准确率」这一项。原因是它在这个阶段不可测——你没有全集，算不出召回。可测的是可追溯性，而可追溯性不达标时，准确率再高也不可用。

T05-2 是唯一一条要求绝对值的：虚构政策拦截率必须是 100%，因为放过一条的代价是整份测试设计建立在假前提上。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| T05-1 | 候选的引用完整度 | 带可定位原文引用的候选占比 = 100%，无引用候选直接丢弃不进复核 | 每次生成 |
| T05-2 | 虚构内容拦截 | 引用指向 Basis 中不存在内容的拦截率 = 100% | 每次生成 |
| T05-3 | Basis 冻结纪律 | 每轮生成记录 Basis hash，未记录的轮次结果作废，缺失率 = 0 | 每次生成 |
| T05-4 | 复核可行性 | 业务 Owner 逐条裁决单条候选的中位耗时 ≤ 90 秒；超出说明候选粒度过粗 | 每次复核 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在做 AI 风险分析、实际在生成推测的做法

这两种做法都能产出一份看起来专业的风险清单，条目也不少。

问题是清单里的条目无法被核对。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 把 diff 丢给模型，要求列出可能的风险点 | 改动内容确实是风险的来源，模型也确实读懂了代码 | 没有需求作为参照时，模型只能凭常识推测「这样改可能有问题」。产出的是推测清单不是风险清单，无法判断哪条真的重要 |
| 模型补充了需求里没写但业界通用的规则，标注为建议 | 补充让分析更完整，也标注了来源是建议 | 标注为建议的规则仍然会被下游当成依据。原文没写就是 UNKNOWN，要向产品确认，而不是由模型补一条通用做法 |

> 两条的共同修法：每条风险必须能指回具体的 source_ref 或 diff 行，指不回的直接丢弃。

### AI 提的风险用不上时按什么顺序查

「AI 提的风险很多但没用」通常是输入不全或引用缺失，不是模型能力问题。

按下表逐项查，前两行覆盖多数情况。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 风险很泛，像通用清单 | 只给了 diff 没给需求 | 补冻结 Basis 作为输入 |
| 有条目找不到出处 | 引用未强制 | 要求每条带 source_ref，无引用即丢弃 |
| 出现原文没有的规则 | 虚构政策 | 比对原文，标 UNKNOWN 并升级 |
| 同一风险重复出现 | 未与既有登记册去重 | 生成前先喂入现有风险登记册 |

> 第二行是最有效的单条改进：强制引用之后，产出量会明显下降，但可用率大幅上升。

### 给一次真实变更做带引用的风险提取：约 45 分钟

关键是把四类输入都准备齐，并强制每条产出带引用。

1. 准备四类输入：冻结的需求契约、技术设计、现有 Oracle 记录、本次代码 diff。
2. 要求产出每条风险必须包含 source_ref 或 diff 行号；缺引用的当场丢弃。
3. 把产出与现有风险登记册比对去重，只保留新增的。
4. 逐条核对引用是否真实存在——通常会发现有几条引用指向了不存在的位置。
5. 把核对通过的风险按 I×L×D 打分并入登记册，其余标 UNKNOWN 并指定确认人。

**期望结果**：典型结果是产出条目数比不强制引用时少一半，但可直接进入登记册的比例从个位数升到多数。

> ⚠ 不要用模型自己检查引用是否存在。引用存在性是确定性检查，应当用程序校验 source_ref 是否在当前 baseline 中。

### 这一页的出口判据

这一页的门禁全部作用在 AI 产出进入人工复核之前。放在复核之后就失去意义：人一旦开始逐条读，虚构内容就已经消耗了最贵的资源。

第三段要接受的不是「AI 出错」，而是「我们不知道漏了多少」——召回率在这个阶段确实无法测量，这个未知必须被明示而不是被忽略。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 无引用候选占比 > 0 时阻断，该批产出不进入复核<br>引用指向不存在内容的候选数 > 0 时阻断，先修生成约束再重跑 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 候选采纳率按批次记录，与上一批相比波动 > 20pt 时须排查 Basis 或 Prompt 变更<br>单批候选数 < 10 条时不据此评估生成质量，结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 风险召回率不可测这一事实，由测试负责人签字确认并写入报告<br>被判定为不成立的候选中若存在争议项，由业务 Owner 署名裁决 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[ISO/IEC/IEEE 29119 软件测试系列标准](https://www.iso.org/standard/81291.html)*

### 带走一条「无引用即丢弃」的硬规则

这条规则比任何提示词优化都有效：它把产出量换成了可用率。

配套需要一个程序化的引用存在性校验，而不是靠人抽查。

- 四类输入齐备后再生成，不只给 diff
- 每条风险必须带 source_ref，无引用即丢弃
- 引用存在性用程序校验，不用模型自检

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Semgrep：模式化静态分析](https://semgrep.dev/docs/)** — 静态门禁工具
  - 能证明：以贴近源码的语法模式表达规则，使团队专属约定（禁用某 API、必须带超时、密钥不得硬编码）能被写成可执行规则并纳入门禁。
  - 不能证明：模式匹配没有完整数据流理解，跨文件跨函数的污点传播会漏。低误报是靠限制规则范围换来的。
  - `semgrep/semgrep` · 版本 v1.173.0（2026-08-13） · LGPL-2.1 · LGPL-2.1：著佐权许可，只链接与转述，不搬代码
- **[Gherkin：结构化的行为描述语法](https://cucumber.io/docs/gherkin/reference/)** — 需求转写格式
  - 能证明：自然语言需求可以被约束成 Given/When/Then 这种有固定槽位的结构，从而变成程序可消费的对象。真正的价值不在语法，在于填槽时会暴露出「前置条件没说清」「预期结果其实没定义」这些原文里藏着的空洞。
  - 不能证明：格式正确不等于规则正确。写成 Gherkin 的错误需求仍然是错误需求，权威裁决这一步无法被格式替代。
  - `cucumber/cucumber` · 版本 gherkin/go/v24.1.0（2022-10-10） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[ISO/IEC/IEEE 29119 软件测试系列标准](https://www.iso.org/standard/81291.html)** — 过程框架
  - 能证明：测试过程、文档与技术有一套国际通用的术语与结构，可用于对齐跨组织的口径，尤其在合规与外部审计场景下需要引用条款号而不是内部约定。
  - 不能证明：标准正文需付费获取，且它给的是过程框架不是有效性证明；符合标准不代表测试有检测力。本课程只引用其结构，不复制条文。
  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理
