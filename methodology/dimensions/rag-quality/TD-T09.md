## TD-T09

### RAG 答错的时候，一半以上的原因在索引之前就已经埋好了

团队排查 RAG 问题时，第一反应通常是调 Prompt 或换模型。但语料层的缺陷会伪装成生成层的缺陷：模型答得很流畅、引用也给了，只是那份文档三个月前就作废了。

它们都不会在任何一条报错日志里出现。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 同一政策的新旧两版同时在索引里 | 冲突文档共存时，检索命中旧版的概率接近 50%，而回答不会提示存在冲突 | 把「模型有时对有时错」归因于随机性，实际是每次命中了不同版本 |
| 文档删除没有传播到索引 | 删除传播延迟每多 1 天，就多 1 天可能引用已撤回内容；合规场景对此的容忍窗口通常是 0 | 线上仍在引用已下架条款，且没有任何告警 |
| chunk 丢失来源与生效期 metadata | 缺 lineage 的 chunk 无法回答「这句话出自哪份文档的哪一版」，人工核实单条的成本上升到 10 分钟以上 | 引用看起来齐全，实际无法审计，出事时无法举证 |

> 三条的共同点：它们都在索引构建阶段就已经决定，之后无论怎么调生成都修不好。

### 语料治理的四个词

RAG 的问题很多不在模型，在索引之前那一步。

| 术语 | 一句话解释 |
| --- | --- |
| 权威 | 这份文档能不能作为判断依据；同一主题的多份文档要有优先级 |
| 生效期 | 文档从什么时候到什么时候有效；过期文档仍被检索是常见事故 |
| chunk lineage | 每个检索单元能追回原文档的位置；没有它就无法核对引用 |
| ACL 传播 | 文档权限变更后，索引与缓存里的副本是否同步更新 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[run-llama/llama_index](https://docs.llamaindex.ai/)*

### 检索质量的上界在索引之前就已经定死了

RAG 的失败常被归因成「模型没读懂」，但相当大一部分在索引阶段就已注定：文档本身过期、同一事实存在互相矛盾的多个版本、切分把一个完整语义切成两半、权限元数据没有随内容一起进索引。这些问题在检索阶段表现为「召回了错的东西」，在生成阶段表现为「模型胡说」，而根因都在更早。

切分是其中最被低估的一环。一个 chunk 如果丢掉了它的上下文锚点（这是哪份文档、哪个版本、适用于哪个时间段），检索器就只能靠字面相似度匹配，而字面相似度对「2024 版政策」和「2026 版政策」几乎没有分辨力——两者措辞高度相似，而答案完全相反。

chunk lineage 就是这件事的工件形态：每个 chunk 必须能回答自己来自哪份文档的哪一段、该文档的权威级别与生效期、以及它继承了哪些访问控制。缺了它，「引用了文档 X」这句话无法被核验，租户隔离也无从谈起。

ACL 传播是最容易在演示阶段被跳过、在生产阶段变成事故的一项。索引时如果没有把原文档的权限一起带进来，检索阶段就没有任何依据做过滤——于是一个低权限用户可以通过提问间接读到高权限文档的内容，而访问日志上看不出任何异常。

*依据：[run-llama/llama_index](https://docs.llamaindex.ai/) · [beir-cellar/beir](https://github.com/beir-cellar/beir#readme)*

### 索引前这四件事各自靠什么保证

这张表按「索引阶段的四个决定」分行。它们的共同点是：一旦索引建成，后面的检索与生成再怎么调都补不回来。

第四行没有现成工具，因为权限模型是你自己的。但它必须在索引阶段落地，检索阶段才有东西可以过滤。

| 索引前的决定 | 工具 | 它负责什么 | 边界 |
| --- | --- | --- | --- |
| 管线可拆解 | LlamaIndex | 把 RAG 拆成切分 → 嵌入 → 索引 → 召回 → 重排 → 组装上下文，使一次失败可以定位到具体某一段 | 框架提供组件不提供语料治理；切分策略仍高度依赖你的文档形态 |
| 切分与 lineage | 自建 chunk 元数据约定 | 让每个 chunk 能回答自己来自哪份文档的哪一段、权威级别与生效期 | 是工程约定不是工具；缺了它「引用了文档 X」无法被核验 |
| 检索质量基线 | BEIR | 用带位置权重的指标（nDCG@k、Recall@k）建立检索基线，并说明零样本迁移能力不可假设 | 公开语料排名不预测你私有语料的表现 |
| 权限随内容进索引 | 自建 ACL 传播（对照 OWASP LLM 敏感信息泄露） | 索引时携带原文档访问控制，使检索阶段可以按租户与角色过滤 | 跳过这一步则低权限用户可通过提问间接读到高权限内容，且日志看不出异常 |

> 四行都在索引之前。这一页之所以排在检索评测之前，就是因为后面所有的调优都受这四项约束。

*依据：[run-llama/llama_index](https://docs.llamaindex.ai/) · [beir-cellar/beir](https://github.com/beir-cellar/beir#readme) · [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/)*

### 这张图的 7 个节点，本页各交付什么

这张图从左到右是一条准入流水线：文档不是「有就能进」，而是要依次通过权威性、版本冲突、分块 metadata、ACL 四道检查才进索引。

最右侧的「语料 owner」不是装饰节点。语料是唯一一个会随时间自然腐坏的组件，没有具名负责人时腐坏没有下限。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 权威文档源 | 确认文档是权威版本而非转述、草稿或个人整理 | 权威来源清单 |
| 版本/冲突 Gate | 检测同主题多版本共存并阻断，或显式标注优先级 | 版本冲突报告 |
| 分块与 metadata | 分块时写入来源、版本、生效期、失效期等 lineage 字段 | chunk schema 与 lineage |
| ACL 过滤 | 把文档级权限下沉到 chunk 级，防止检索绕过权限 | chunk 级 ACL 映射 |
| 版本化索引 | 索引本身打版本号，使检索结果可关联到具体索引快照 | 索引版本号 |
| 检索 Trace | 记录每次检索命中了哪些 chunk 及其 lineage，使回答可审计 | 检索 trace |
| 语料 owner | 指定具名负责人，负责失效文档的下架与冲突裁决 | 语料 owner 登记 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 索引前必须完成的六项检查

文档一旦进了索引，它的问题就会以「模型答错」的形式出现。六项检查全在索引之前。

右列写的是漏掉这项时的典型表现——它们都很容易被误判为模型能力问题。

| 检查 | 不做时的表现 |
| --- | --- |
| 权威与优先级 | 同一问题检索到两份矛盾文档，模型任选其一 |
| 版本与生效期 | 引用了已废止的政策 |
| 去重 | 同一内容多份副本挤占 top-k |
| chunk 边界 | 关键约束被切在两个 chunk 之间，两个都不完整 |
| chunk lineage | 引用无法回溯到原文位置 |
| ACL 与删除传播 | 权限收回后仍能被检索到 |

> 第四行最容易被低估：按固定长度切分时，一条完整的业务规则常常被拦腰截断。

*依据：[run-llama/llama_index](https://docs.llamaindex.ai/)*

### 这一页的验收口径：语料的四项体检

放到评测阶段才发现语料问题，意味着此前所有检索与生成指标都要重跑。

T09-2 的删除传播是唯一一条带时间窗口的指标：合规场景把它设为 0，非合规场景可以放宽，但必须写明放宽到多少。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| T09-1 | chunk lineage 完整度 | 来源 / 版本 / 生效期三项 metadata 缺失率 = 0 | 每次索引构建 |
| T09-2 | 删除传播时效 | 文档下架到索引移除的延迟 ≤ 15 分钟；合规类文档要求 = 0（同步删除） | 每次删除 |
| T09-3 | 版本冲突 | 同主题多版本共存且未标注优先级的数量 = 0 | 每次索引构建 |
| T09-4 | 权限下沉 | chunk 级 ACL 覆盖率 = 100%；抽样 100 条跨权限检索的越权命中数 = 0 | 每周 1 次 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在治理语料、实际留有漏洞的做法

这两种做法都提高了语料质量，也确实减少了一部分错误。

问题是它们没有覆盖变更这一维。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 入库时校验文档格式与元数据完整性 | 入口把关是标准做法，也拦下了脏数据 | 入库校验只管一次。文档权限被收回、内容被废止之后，索引里的副本不会自动失效。必须有变更传播机制 |
| 按固定 token 数切分文档，保证 chunk 大小均匀 | 均匀切分便于批处理，检索效率也更稳定 | 固定长度会把语义单元切断。一条「已发货订单不得取消，除非…」的规则可能被切成两半，检索到任一半都会得出错误结论 |

> 两条的共同修法：切分按语义边界，治理覆盖整个生命周期而不只是入口。

### 检索到了但回答仍然错时按什么顺序查

「检索命中了但答案错」的原因多在语料层。按下表逐项查。

前两行不需要看模型，只看被检索到的文本。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 引用的内容确实存在但已过期 | 缺生效期字段 | 给文档加生效期并在检索时过滤 |
| 检索到的片段不完整 | chunk 切断了语义 | 改按语义边界切分并加重叠 |
| 同一问题不同时候答案不同 | 多份矛盾文档 | 建立权威优先级并去重 |
| 用户看到不该看的内容 | ACL 未传播 | 检查权限变更后的索引同步 |
| 引用无法核对 | 缺 chunk lineage | 为每个 chunk 保存原文位置 |

> 五行都属于语料治理，不需要动模型也不需要改提示词。

### 给现有索引做一次语料体检：约 50 分钟

随机抽样比全量扫描有效。抽二十条就能暴露大部分问题。

1. 从索引中随机抽取 20 个 chunk。
2. 逐个检查：能否回溯到原文位置、原文是否仍然有效、是否有重复副本。
3. 检查 chunk 边界：有没有把一条完整规则切断的情况。
4. 随机选一份已收回权限的文档，尝试用无权限身份检索，确认它不会出现。
5. 把发现的问题按六项检查归类，统计各类各有多少条。

**期望结果**：20 条抽样通常能发现两到三类问题，最常见的是 chunk 切断语义与缺少生效期字段。

> ⚠ 抽样要覆盖不同来源与不同时间入库的文档。只抽最近入库的，会漏掉历史遗留问题。

### 这一页的出口判据

语料门禁必须在索引构建时执行而不是在发布前抽查。索引一旦建成，带着缺陷的 chunk 会污染其后每一次检索评测的数字。

第三段通常要接受的是覆盖不全：总有一部分知识散落在没人维护的文档里，这个缺口要写下来，而不是靠模型的常识去补。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | chunk lineage 三项 metadata 缺失率 > 0 时阻断索引构建<br>跨权限检索的越权命中数 > 0 时阻断发布，先修 ACL 下沉 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 越权命中率按 100 条抽样给出 95% CI，样本不足 100 条时结论记为证据不足<br>删除传播延迟取 p99 而非均值，均值会被大量快速删除稀释 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 已知未纳入索引的知识范围，由语料 owner 列出并签字接受<br>非合规类文档的删除传播窗口取值，由业务 owner 明示接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[beir-cellar/beir](https://github.com/beir-cellar/beir#readme)*

### 带走一份语料准入与变更检查清单

清单分两段：入库前的六项检查，以及变更时的传播要求。多数团队只做了前一段。

变更传播是 RAG 权限事故的主要来源，也是最容易被架构图忽略的一环。

- 按语义边界切分并保留 chunk lineage
- 给文档加生效期，检索时过滤过期内容
- 权限与删除变更必须传播到索引与缓存

  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理

  - 能证明：RAG 不是一个整体，是切分 → 嵌入 → 索引 → 召回 → 重排 → 组装上下文这条可逐段替换的管线。理解这条管线才知道一次失败该在哪一段查。
  - 不能证明：框架提供组件，不提供语料治理。切分策略与元数据设计仍是决定检索质量的主要因素，且高度依赖你的文档形态。
