## TD-T13

### A/B 比出来的差异，多数时候是实验设计的差异

换 Prompt、换模型、换知识库之后分数变了，这个观察本身几乎没有信息量——因为同时变的往往不止一个东西，而且没变的那次也会有波动。

下面三条是 AI 版本对比里最常见的三种伪差异。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 同时改动 Prompt 与知识库再做对比 | 两个变量同时改动时，归因所需的实验从 1 次变成至少 3 次（各改一个 + 都改） | 「新版本更好」被归给 Prompt，实际贡献来自知识库更新 |
| 两次运行用了不同的评分器版本 | 评分器换版本会整体平移分数，平移量可达 3～5pt，足以掩盖或伪造一次真实差异 | 把评分器的刻度变化读成模型能力变化 |
| 用单次运行的点估计比较 | 单次运行的波动区间通常覆盖 5pt 以上，两个版本 3pt 的差距在统计上无法区分 | 发布了一个实际没有改进的版本，并把资源投向错误方向 |

> 解法是三个「同一」：同一冻结数据集、同一评分协议、同一运行预算，一次只改一个变量。

### 版本 A/B 的四个词

同时改三样东西然后看分数涨了，这个结论无法回滚也无法复用。

| 术语 | 一句话解释 |
| --- | --- |
| 单变量 | 一次实验只改一样：模型、Prompt 或知识库 |
| 锁定字段 | 实验期间必须固定的所有其他配置 |
| confounded | 两个及以上锁定字段同时变化，实验作废 |
| 风险切片 | 按业务风险划分的子集；总分上升不能掩盖切片下降 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/)*

### A/B 比出来的差异，多数时候是实验设计的差异

RAG 系统里可以同时变化的东西太多：模型版本、提示词、检索器、切分策略、重排器、上下文长度、解码参数。一次改两项再看总分，得到的结论无法归因给任何一项——而实践中一次只改一项的纪律极难维持，因为迭代压力总是要求打包发布。

解决办法不是禁止打包，而是**锁定字段**：把所有可变项列成一张清单，每次实验显式声明哪些锁定、哪些变化，并把这份声明与结果一起存档。打包变更仍然可以发，但结论必须写成「这一组变更整体带来了 X」，而不是「新检索器带来了 X」。

混杂（confounded）的隐蔽形态是评测集本身也变了。为了「更贴近现状」而在版本之间更新了评测集，于是分数变化里混着系统改进与题目变简单两件事。这一条是 A/B 里最常见也最难被发现的失效。

风险切片必须单独报。总分持平而高风险切片显著变差，是完全可能的，也是最危险的一种结果——因为总分给了放行的理由。这也是为什么 A/B 的结论必须按切片分别陈述，而不是只报一个总分差。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/) · [iterative/dvc](https://dvc.org/doc)*

### 三类候选变更各自必须锁定什么

这张表按「你想改什么」分行，第三列写的是那次实验里必须保持不变的东西。

最后一行是所有实验的共同前提：评测集必须版本化且在实验期间冻结，否则前面三行做得再严谨也没用。

| 候选变更 | 变的是什么 | 必须锁定 | 常见混杂 |
| --- | --- | --- | --- |
| 模型版本 | 权重或托管别名 | 提示词、检索器、切分、解码参数、评测集 | 别名指向的权重悄悄变了，被记成提示词的功劳 |
| 检索侧 | 切分策略、嵌入模型、重排器、top-k | 模型版本、提示词、解码参数、评测集 | 改切分同时重建了索引，语料也被顺手更新 |
| 生成侧 | 提示词、上下文组装、解码参数 | 模型版本、检索侧全部、评测集 | 提示词长度变化改变了上下文预算，间接影响检索结果数 |
| 评测集 | （不应在实验期间变） | —— | 为「更贴近现状」更新题目，分数变化里混着题目变简单 |

> 第四行本不该是一类变更，把它列出来是因为它在实践中经常悄悄发生，而且发生后前三行的结论全部作废。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/) · [iterative/dvc](https://dvc.org/doc) · [mlflow/mlflow](https://mlflow.org/docs/latest/)*

### 这张图的 6 个节点，本页各交付什么

这张图的每个节点都在消除一种伪差异来源：manifest 消除版本混淆，冻结集消除数据漂移，重复运行消除随机波动，成本台账消除「用更多算力换分数」的隐性作弊。

「Human release gate」在这里的职责很具体：判断这个差异值不值得换版本，因为统计显著不等于业务上值得。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| Versioned A/B manifests | 把两侧的模型、Prompt、知识库、评分器四个版本全部写进 manifest | A/B 版本 manifest |
| Frozen eval set | 两侧使用同一冻结数据集，禁止任何一侧使用更新过的数据 | 冻结评测集版本号 |
| Repeated runner | 两侧按同一 k 值重复运行，记录每次原始结果 | 重复运行原始记录 |
| Slice/Blocker Oracle | 按切片出分并单独标出 blocker 类失败，不并入总分 | 切片与 blocker 结果 |
| Cost/Latency ledger | 记录两侧的 token 成本与延迟，防止用成本换分数被忽略 | 成本与延迟台账 |
| Human release gate | 基于区间与成本共同判断是否换版本 | 换版决策记录 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 三类候选变更各自要锁定什么

三类变更的锁定要求不同。用同一套锁定清单会漏掉关键项。

右列是这类实验中最容易被忽略的锁定项。

| 改什么 | 必须锁定 | 最容易漏掉的锁定项 |
| --- | --- | --- |
| 模型 | Prompt、检索、工具、Scorer、数据 | 模型别名指向的实际版本 |
| Prompt | 模型版本、检索参数、Scorer | few-shot 示例的数量与顺序 |
| 知识库 | 模型、Prompt、检索参数 | 嵌入模型版本与分块策略 |

> 第三行最危险：重建索引时经常顺手换了嵌入模型或分块参数，于是实验变成了三变量同时变化。

*依据：[iterative/dvc](https://dvc.org/doc)*

### 这一页的验收口径：区间不重叠才叫差异

T13-1 是本页唯一真正的判据：两个版本的置信区间不重叠，才可以说它们有差异。重叠时正确的结论是「没测出差异」，不是「新版略好」。

T13-3 把成本纳入判据，是因为 AI 版本对比里最常见的隐性作弊是用更长的输出、更多的重试换取分数提升，而这在成本上不可持续。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| T13-1 | 差异显著性 | 两版本 95% CI 不重叠才判定为有差异；重叠时结论为「未测出差异」 | 每次对比 |
| T13-2 | 单变量纪律 | 一次对比中变动的版本维度数 = 1；多于 1 个时结论不可归因 | 每次对比 |
| T13-3 | 成本可比性 | 两侧单任务 token 成本差异 ≤ 20%；超出时须与质量差异一并报告 | 每次对比 |
| T13-4 | 评分器一致 | 两侧使用的评分器版本相同，不同版本的对比次数 = 0 | 每次对比 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在做对照实验、实际无法归因的做法

这两种做法都产出了前后对比数据，结论也符合预期。

问题是变量控制。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 升级模型同时优化 Prompt，整体分数提升 8 个点 | 两项都是合理改进，一起做也更高效 | 无法知道提升来自哪一项，也无法在其中一项失效时回滚。而且两者可能一正一负，净效果掩盖了真实情况 |
| 总分提升即可发布，切片差异属于正常波动 | 总分是综合判断，个别切片波动确实常见 | 高风险切片的下降不是波动而是 blocker。退款或权限类切片出现错误时，无论总分多高都不应发布 |

> 两条的共同修法：单变量 + 切片 blocker，两者缺一不可。

### A/B 结果无法解释时按什么顺序查

按下表逐项核对，通常前两行就能找到原因。

核对的依据是两次实验的完整配置 manifest，不是记忆。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 提升幅度异常大 | 有其他字段同时变了 | 比对两次的完整 manifest |
| 重跑结果不一致 | 缓存命中率不同 | 关闭缓存或强制两侧一致 |
| 总分好但用户反馈差 | 高风险切片下降 | 按切片分别报告 |
| 模型没换但结果变了 | 别名漂移 | 改用固定版本号 |

> 第二行经常被忽略：一侧命中缓存另一侧未命中时，比较的其实是两种不同的执行路径。

### 做一次严格的单变量 A/B：约 60 分钟

锁定清单是这个实验的全部难度所在。跑起来反而简单。

1. 写下本次要比较的唯一变量，以及所有必须锁定的字段。
2. 为两侧各生成一份完整 manifest，逐字段比对，确认只有一项不同。
3. 关闭缓存或确认两侧命中率一致。
4. 两侧各重复运行足够次数，按任务聚类计算区间。
5. 按风险切片分别统计，标出任何 blocker——有 blocker 时无论总分如何都判定不通过。

**期望结果**：严格执行后经常会发现：此前认为的提升在区间上并不显著，或者提升集中在低风险切片而高风险切片实际变差。

> ⚠ manifest 比对要逐字段做，不要靠记忆。最常见的漏项是嵌入模型版本与 few-shot 示例顺序。

### 这一页的出口判据

这一页的门禁会拒绝大量看起来有结论的对比。这是它的价值所在：一个「未测出差异」的诚实结论，比一个基于噪声的换版决定便宜得多。

第三段是业务判断：即使统计上显著，3pt 的提升是否值得承担迁移成本与新版本的未知风险，这只能由人决定。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 一次对比中变动的版本维度数 > 1 时阻断，结论不可归因<br>两侧评分器版本不一致的对比次数 > 0 时阻断，结果作废 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 以 95% CI 是否重叠判定差异，禁止用点估计差值宣布改进<br>每侧重复次数 k < 3 或样本 < 100 条时结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 统计显著但幅度较小的差异是否值得换版，由产品 owner 署名决定<br>新版本带来的成本上升，由业务 owner 在知情前提下接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/)*

### 带走一份锁定字段清单

清单按变更类型分列，每类写明必须锁定哪些字段。它可以直接变成实验前的检查项。

加上切片 blocker 规则后，A/B 结论才能直接支撑发布决定。

- 一次只改一个变量，两侧 manifest 逐字段比对
- 缓存命中率必须一致或全部关闭
- 风险切片有 blocker 时总分再高也不通过

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[HELM：多场景、多指标的整体性评测](https://crfm.stanford.edu/helm/)** — 评测方法学
  - 能证明：单一准确率无法描述模型能力。HELM 的做法是把场景（scenario）与指标（metric）做成正交的两维，同一个场景同时报准确率、校准度、鲁棒性、公平性、效率——「模型 A 比 B 好」这句话必须指明在哪个场景的哪个指标上。
  - 不能证明：覆盖的是公开场景，不覆盖你的业务分布。榜单名次不能迁移到企业任务上。
  - `stanford-crfm/helm` · 版本 v0.5.16（2026-04-30） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[MLflow：实验、模型与版本的登记体系](https://mlflow.org/docs/latest/)** — 版本与血缘
  - 能证明：模型、参数、数据版本与评测结果可以被登记成可检索的关联记录，使「这个结论对应哪个模型的哪次运行」成为可查询事实而不是靠人记。回滚与事后归因都依赖这条记录。
  - 不能证明：登记的是元数据不是质量。记录齐全的模型同样可以是差模型。
  - `mlflow/mlflow` · 版本 v3.15.1（2026-08-03） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[DVC：数据与流水线的版本控制](https://dvc.org/doc)** — 数据版本
  - 能证明：评测集必须与代码一样可版本化：同一个 commit 能取回当时用的那份数据。缺了这一条，历史评测分数之间不可比，回归判断也就不成立。
  - 不能证明：版本可追不代表数据集设计合理；污染与分布偏移不会因为版本化而消失。
  - `iterative/dvc` · 版本 3.67.1（2026-03-31） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
