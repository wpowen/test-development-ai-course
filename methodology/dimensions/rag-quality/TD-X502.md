## TD-X502

### 用英文平均分外推其他语言，是本页要拆掉的唯一一个假设

多语言支持最常见的验收方式是：英文测充分，其他语言抽查。这个做法隐含一个从未被验证的假设——模型能力在语言之间是可迁移的。

而后者恰好是用户最容易遇到的地方。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 用英文指标外推低资源语言 | 同一任务在高资源与低资源语言之间的表现差距常达 20pt 以上，且差距随任务复杂度放大 | 宣布「支持 30 种语言」，其中 20 种从未被单独测过 |
| RTL 与复杂字形只做了显示测试 | 阿拉伯语、希伯来语的双向文本在截断、拼接、光标定位处会出错，这类缺陷在纯显示检查中 100% 漏过 | 界面看起来正常，用户编辑时才发现文字顺序错乱 |
| 可访问名称与视觉标签不一致 | 屏幕阅读器读到的名称与视觉标签不一致时，键盘用户完成任务的成功率会大幅下降，而这类缺陷在纯视觉测试中 100% 漏过 | 把可访问性当成视觉对比度问题，实际是语义标注问题 |

> 本页的产物是一张 locale × 任务的矩阵，它的作用是把「支持哪些语言」这个模糊承诺变成可核对的清单。

### 多语言与可访问性的四个词

英文测试通过不代表其他语言可用。这四个维度各自独立。

| 术语 | 一句话解释 |
| --- | --- |
| locale | 语言与地区组合；它影响日期、数字、货币与排序 |
| script 与 RTL | 文字系统与书写方向；RTL 会改变整个布局逻辑 |
| 可访问名称 | 辅助技术读到的名称；它常常与视觉文字不同 |
| 翻译语义 | 译文是否保持了原文的约束强度，而不只是字面对应 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[open-compass/opencompass](https://opencompass.readthedocs.io/)*

### 英文平均分不能外推到其他语言，原因不止是训练数据多少

把英文表现当成整体能力的代表，隐含了一个假设：语言只是同一能力的不同外壳。这个假设在多个层面上不成立，而且失效方式各不相同。

第一层是能力差异：低资源语言的训练数据少，同样的任务准确率显著更低，而且下降幅度与任务类型相关，不是一个可以整体折算的系数。第二层是书写系统：RTL 语言的排版、组合字符的分词、CJK 的无空格切分，都会让 token 计数、截断位置与文本处理逻辑出现英文里不存在的错误。

第三层最隐蔽：翻译语义。同一个提示词翻译过去之后，语气、正式程度与隐含约束可能完全改变——「请简要回答」在某些语言里的直译会带有命令语气，从而改变模型的行为。因此多语言评测不能靠翻译评测集，必须由母语者审校。

可访问性与多语言在这里交汇：可访问名称必须随 locale 变化，而自动化定位器如果绑在可见文案上，换一种语言就全部失效。这一条把 UI 专项的语义定位器纪律直接延伸到了多语言场景。

*依据：[open-compass/opencompass](https://opencompass.readthedocs.io/) · [Web Content Accessibility Guidelines (WCAG) 2.2](https://www.w3.org/TR/WCAG22/)*

### 四个维度各自的典型失败与验证手段

四行的失败形态完全不同，因此不能用一套用例覆盖。这张表的用途是决定要为哪些 locale 单独建样本。

第三行的翻译语义无法自动检出，必须母语者参与——这是多语言评测里唯一不可省的人工环节。

| 维度 | 典型失败 | 验证手段 | 边界 |
| --- | --- | --- | --- |
| 能力差异 | 低资源语言准确率显著更低，且降幅因任务而异 | 按 locale 分别建评测集，分别报分 | 不能用一个折算系数从英文推算 |
| 书写系统 | RTL 排版错乱、组合字符分词错误、CJK 截断位置不当 | 针对 script 构造样本，检查 token 计数与截断 | 问题在文本处理层，模型换了也不会好 |
| 翻译语义 | 提示词直译后语气与隐含约束改变 | 母语者审校，不用机器翻译评测集 | 无法自动检出，这是唯一不可省的人工环节 |
| 可访问名称 | 定位器绑可见文案，换语言即全部失效 | 用语义定位器 + 按 locale 校验可访问名 | 页面本身无障碍属性缺失时会退化成文本匹配 |

> 四行合起来说明一件事：多语言不是把评测集翻译一遍，而是为每个目标 locale 单独建一套证据。

*依据：[open-compass/opencompass](https://opencompass.readthedocs.io/) · [Web Content Accessibility Guidelines (WCAG) 2.2](https://www.w3.org/TR/WCAG22/) · [dequelabs/axe-core](https://github.com/dequelabs/axe-core/blob/develop/doc/API.md)*

### 这张图的 7 个节点，本页各交付什么

这张图从「用户任务」而不是从「语言列表」出发。原因是同一种语言在不同任务上的表现可以差很多，按语言笼统验收会掩盖任务级的失败。

「键盘/名称 Oracle」是可访问性验收唯一可靠的判据来源：它检查的是语义标注，而不是渲染结果。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 用户任务 | 从真实用户要完成的任务出发定义验收项，而不是从语言清单出发 | 任务清单 |
| Locale/Script 矩阵 | 建立 locale × 书写系统 × 任务的覆盖矩阵，标出已测与未测 | 覆盖矩阵 |
| 语义等价 | 验证翻译后的语义等价而不只是字符串存在 | 语义等价检查结果 |
| 键盘/名称 Oracle | 以可访问名称与键盘可达性为判据，不以视觉渲染为判据 | 可访问性判据集 |
| 切片运行 | 按 locale 分片运行并分别出分，禁止合并平均 | 分语言切片结果 |
| 本地化 Owner | 为每个 locale 指定具名负责人，负责语义争议裁决 | locale owner 登记 |
| 阻断/接受 | 明确哪些 locale 达标可发布、哪些标记为未验证 | 发布范围声明 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 四个维度各自的典型失败

这四个维度的失败方式完全不同，不能用一套用例覆盖。

右列写的是只测英文时会漏掉的具体问题。

| 维度 | 典型失败 | 只测英文会漏掉 |
| --- | --- | --- |
| locale | 日期格式解析错误 | 非英语地区的日期被误解析 |
| script 与 RTL | 布局错乱、光标位置错 | 阿拉伯语等 RTL 语言完全不可用 |
| 可访问名称 | 读屏读出无意义内容 | 视觉正常但辅助技术不可用 |
| 翻译语义 | 约束强度被弱化 | 「必须」被译成「建议」 |

> 最后一行在 AI 场景特别危险：安全约束的译文如果弱化了强度，模型在该语言下的行为会明显不同。

*依据：[open-compass/opencompass](https://opencompass.readthedocs.io/)*

### 这一页的验收口径：按 locale 分片，不做平均

X502-1 的「禁止合并平均」是本页最关键的一条纪律。加权平均会让占比小的语言彻底消失在报告里，而那些语言的用户遇到的问题是 100% 的。

X502-4 是一条诚实性指标：未测语言必须被显式标注为未验证，而不是默认为支持。这一条不改变系统质量，但它改变了承诺的边界。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| X502-1 | 分语言达标 | 每个已声明支持的 locale 单独出分，任务成功率 ≥ 80%；禁止跨 locale 合并平均 | 每次发布 |
| X502-2 | 双向文本正确性 | RTL 场景下截断、拼接、光标定位的错误数 = 0 | 每次 UI 变更 |
| X502-3 | 可访问名称一致 | 可访问名称与视觉标签不一致的控件数 = 0；键盘可达率 = 100% | 每次 UI 变更 |
| X502-4 | 承诺边界诚实性 | 未单独验证的 locale 标注为「未验证」的比例 = 100% | 每次发布 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来覆盖了国际化、实际没有的做法

这两种做法都增加了语言覆盖，也确实发现了一些问题。

问题是覆盖方式与失败模式不匹配。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 把英文用例机器翻译成十种语言批量执行 | 覆盖语言数大幅增加，成本也可控 | 机器翻译会改变约束强度，也不会构造该语言特有的输入（如 RTL、特殊字符、不同日期格式）。执行的是十份英文用例的影子 |
| 用英文任务的平均分推断整体多语言能力 | 有统一基准，也便于跨语言比较 | 不同语言的训练数据量差异巨大。英文平均分对低资源语言没有任何预测力，这种外推是最常见的多语言评测错误 |

> 两条的共同修法：每种目标语言用该语言的真实任务测，不外推。

### 某语言下体验明显更差时按什么顺序查

按四个维度逐项排除。前两个维度不需要语言能力就能查。

查完之后才需要涉及模型在该语言上的能力。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 日期或金额被解析错 | locale 配置 | 检查格式化与解析的 locale 设置 |
| 界面错位或光标异常 | RTL 支持 | 在 RTL 语言下走一遍关键旅程 |
| 读屏读不出关键信息 | 可访问名称缺失 | 检查控件的可访问属性 |
| 模型在该语言下更容易越界 | 翻译语义弱化 | 比对约束在该语言下的表述强度 |

> 最后一行需要懂该语言的人参与。找不到人时正确做法是标注该语言未验证，而不是假设通过。

### 给一种非英语语言做真实任务验收：约 60 分钟

选一种你的用户真实使用的语言，用该语言的真实任务测。

1. 选一种目标语言，收集该语言的真实用户任务，不用翻译英文任务。
2. 用该语言执行关键旅程，记录 locale 相关的格式问题。
3. 若是 RTL 语言，专门检查布局、光标与输入顺序。
4. 用读屏工具走一遍，记录可访问名称缺失或错误的控件。
5. 比对关键约束在该语言下的表述强度，确认没有被弱化。

**期望结果**：典型结果是每个维度都能发现一到两个问题，且它们在英文下完全不存在。这证明了外推是不成立的。

> ⚠ 没有该语言使用者参与时，第四步无法完成。此时应当把该语言标注为部分验证，而不是全部通过。

### 这一页的出口判据

这一页的门禁不要求支持所有语言，它要求你说清楚支持了哪些。承诺范围超出验证范围，是这个领域最常见也最容易被追责的失败。

第三段是本页真正的决策点：哪些 locale 达标即发布，哪些带着已知缺陷发布，哪些暂不宣称支持。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 可访问名称与视觉标签不一致的控件数 > 0 时阻断<br>键盘可达率 < 100% 时阻断，存在纯鼠标可达的功能即不合规 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 各 locale 任务成功率给出 95% CI，样本 < 30 条时只报区间不报点估计<br>locale 间差距报告预注册效应量与分层/聚类 95% CI；任务不配对时只作描述性比较，不以区间重叠作显著性判定 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 带已知缺陷发布的 locale 清单，由本地化 owner 逐个签字接受<br>暂不宣称支持的语言范围，由产品 owner 确认并同步到对外文案 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[Web Content Accessibility Guidelines (WCAG) 2.2](https://www.w3.org/TR/WCAG22/)*

### 带走一张按语言的验收矩阵

矩阵按语言列出四个维度的验证状态，未验证的如实标注未验证。

它同时防止了最常见的外推错误：用英文结果代表所有语言。

- 用目标语言的真实任务测，不翻译英文用例
- 四个维度分别验证，不合并成一个通过
- 没有该语言使用者时标注部分验证

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[axe-core：无障碍规则引擎](https://github.com/dequelabs/axe-core/blob/develop/doc/API.md)** — 无障碍专项工具
  - 能证明：一组可自动判定的无障碍规则（对比度、名称缺失、ARIA 误用、结构层级），并区分 violations / incomplete / passes 三类结果。incomplete 这一类是它诚实的地方：明确标出机器判不了、需要人工看的项。
  - 不能证明：自动化规则只覆盖 WCAG 中可机器判定的一部分，键盘陷阱、焦点顺序合理性、屏幕阅读器实际朗读效果多数落在自动化之外。零 violations 不等于无障碍合规。
  - `dequelabs/axe-core` · 版本 v4.13.0（2026-08-05） · MPL-2.0 · MPL-2.0：弱著佐权，可短引并署名，不整段搬入本仓库
- **[Web Content Accessibility Guidelines (WCAG) 2.2](https://www.w3.org/TR/WCAG22/)** — 无障碍判据来源
  - 能证明：无障碍要求的权威条款与分级（A / AA / AAA），以及每条成功准则的判定方式。合规结论必须引条款号，而不是引工具输出。
  - 不能证明：标准不指定实现与测试方法。哪些条款能自动化、哪些必须人工，需要自己映射。
  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理
- **[OpenCompass：面向中文与多语言的评测体系](https://opencompass.readthedocs.io/)** — 评测执行器
  - 能证明：评测配置（数据集、模型、推理参数、后处理）可以完全声明式表达并版本化，使跨模型、跨版本的对照在配置层面就可审计，而不是靠人记得当时怎么跑的。
  - 不能证明：中文基准同样存在污染与分布偏移问题；配置可复现不等于结论可迁移。
  - `open-compass/opencompass` · 版本 0.5.3（2026-06-29） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
