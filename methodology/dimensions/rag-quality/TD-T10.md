## TD-T10

### 把检索故障和生成故障混在一起，你会一直在调错的那一半

RAG 答错只有两种可能：该给的证据没检索到，或者证据检索到了但没用好。这两类的修复方向完全相反，而端到端评测把它们合成了一个数字。

下面三条说明不拆开会付出什么代价。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 只看端到端正确率，不看 Recall@k | 检索未命中时生成层无论怎么调都无法答对，这部分失败占比在语料治理不佳的系统里常达 40% 以上 | 反复调 Prompt 和温度，而问题在检索侧一步都没动 |
| top-k 取值凭经验设定 | k 从 3 提到 10 通常能提升 Recall 但同时引入更多干扰 chunk，两者的净效果必须实测，不能假设 | 把 k 调大当成免费的改进，实际 faithfulness 下降了 |
| 没有 miss reason 归因 | 一次未命中至少有 4 种原因：语料没有、分块切碎、查询改写偏了、排序压下去了；不归因就无法分派 | 检索指标下降 8 个点，没人知道该找谁修 |

> 本页的核心动作只有一个：在检索层建立独立于生成层的评测，让两类故障各自有分母。

### 检索评测的四个词

把检索和生成分开评，是 RAG 归因的第一步。

| 术语 | 一句话解释 |
| --- | --- |
| gold document | 这个问题的正确答案所在的文档；它由人标注，不由模型判定 |
| Recall@k | 前 k 个结果里包含 gold 的比例；它回答「找到了吗」 |
| MRR | gold 出现位置的倒数均值；它回答「排得够靠前吗」 |
| miss reason | 没检索到的原因分类；它比 recall 数字更有行动价值 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[beir-cellar/beir](https://github.com/beir-cellar/beir#readme)*

### 检索和生成必须分开测，否则你会一直在调错的那一半

端到端看一个 RAG 回答对不对，得到的是一个混合信号：可能是检索没找到，可能是找到了但模型没用，可能是找到了模型也用了但理解错了。三种情况的修法完全不同——第一种改索引与召回，第二种改提示词与上下文组装，第三种可能只能换模型。

拆开的办法是引入 gold document：对每个问题标注「正确答案应当来自哪一段」。有了它，检索层可以单独用 Recall@k 与 MRR 度量，生成层可以在「已给定正确上下文」的条件下单独度量。这两个数字合起来才能指出该调哪一半。

Recall@k 与 MRR 回答的问题不同。Recall@k 只问正确文档有没有进候选集，MRR 还问它排在第几位——因为上下文窗口有限，排在第 20 位的正确文档实际上等于没召回。只看 Recall@20 很好看的系统，Recall@3 可能很差。

miss reason 是把指标变成行动的关键一步：召回失败要归类成「语料里根本没有」「切分把答案切散了」「查询与文档用词不匹配」「被权限过滤掉了」。四类的修法互不相同，而只看一个 Recall 数字时，这四类是不可区分的。

*依据：[beir-cellar/beir](https://github.com/beir-cellar/beir#readme) · [explodinggradients/ragas](https://docs.ragas.io/) · [truera/trulens](https://www.trulens.org/)*

### 把混合信号拆成两个可独立行动的数字

这张表的结构就是拆分本身：前两行度量检索，后两行度量生成，最后一行把两者接回一起。

TruLens 的三角分解是这一页最值得先看的一个模型——它把「RAG 答错了」这句话拆成三条可以分别测量的边。

| 测哪一半 | 工具 | 它负责什么 | 边界 |
| --- | --- | --- | --- |
| 检索基线 | BEIR | 用 nDCG@k、Recall@k 这类带位置权重的指标建立可比基线 | 公开基准排名不迁移到你的私有语料与切分策略 |
| 检索失败归类 | 自建 miss reason 标注 | 把召回失败分成语料缺失 / 切分切散 / 用词不匹配 / 权限过滤四类 | 需要人工标注，但它是把指标变成行动的唯一通路 |
| 三角分解 | TruLens | 把失败定位到问题↔上下文、上下文↔回答、问题↔回答三条边中的哪一条 | 反馈函数由模型实现，误差可能与被测模型相关 |
| RAG 专属指标 | Ragas | 上下文精确率 / 召回率、答案相关性等指标的可计算定义 | 多数指标由模型计算，未经人工校准前只能看趋势不能当验收线 |

> 四行的目的是同一个：让「RAG 效果不好」这句不可行动的话，变成一个指向具体某一段的数字。

*依据：[beir-cellar/beir](https://github.com/beir-cellar/beir#readme) · [truera/trulens](https://www.trulens.org/) · [explodinggradients/ragas](https://docs.ragas.io/)*

### 这张图的 7 个节点，本页各交付什么

这张图是检索链路的完整分解。评测的关键在于它可以在任意一个节点截断取样——只有能截断，才能定位失败发生在改写、过滤、召回还是排序。

「Gold comparison」是这条链路唯一需要人先投入的节点：没有 gold document 映射，后面所有指标都算不出来。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| Query slices | 按查询类型分片（事实型、比较型、时效型、模糊型），禁止只报总体指标 | 查询切片集 |
| Query rewrite | 评估改写是否改变了原意，记录改写前后的命中差异 | 改写影响报告 |
| ACL/metadata filter | 验证过滤条件本身不会误伤应当命中的文档 | 过滤误伤检查 |
| Retriever | 在固定语料版本上测召回，与排序解耦 | Recall@k 结果 |
| Top-k ranking | 测排序质量，观察正确文档是否被压到 k 之外 | MRR / Precision@k |
| Gold comparison | 维护查询到 gold document 的映射，作为检索层的判据 | gold 映射表 |
| Miss reason/owner | 对每次未命中归因到 4 类原因之一并指派责任人 | miss 归因表 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 四类 miss reason 各自的修法

Recall 低只是症状。真正有用的产出是「为什么没检索到」的分类。

右列的修法互不通用——查询改写解决不了文档缺失。

| miss reason | 含义 | 修法 |
| --- | --- | --- |
| 文档不存在 | 语料里根本没有 | 补语料，与检索无关 |
| 切分丢失 | 内容被切断了 | 改切分策略 |
| 向量不匹配 | 语义相近但嵌入距离远 | 换嵌入模型或加关键词召回 |
| 排序靠后 | 检索到了但排在 k 之外 | 调排序或增大 k |
| 权限过滤 | 被 ACL 挡掉 | 确认是正确行为还是配置错误 |

> 五类里只有第三、四类属于「检索算法问题」。把全部 miss 都归为检索效果不好，会让优化方向完全错误。

*依据：[truera/trulens](https://www.trulens.org/)*

### 这一页的验收口径：检索层独立出分

下面的阈值都按切片分别计算。总体 Recall@5 达到 90% 而时效型查询只有 55% 是常见形态，只报总体会完全掩盖它。

T10-4 的归因率比前三条更重要：Recall 告诉你有多差，归因告诉你该找谁——只有后者能转成工作项。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| T10-1 | 召回充分性 | 每个查询切片 Recall@5 ≥ 85%，且切片间最低值与最高值差距 ≤ 20pt | 每次语料或检索变更 |
| T10-2 | 排序质量 | MRR ≥ 0.7；正确文档落在 top-3 的比例 ≥ 80% | 每次检索变更 |
| T10-3 | 改写安全性 | 查询改写导致原本命中变未命中的比例 ≤ 2% | 每次改写策略变更 |
| T10-4 | 未命中归因率 | 未命中样本归因到 4 类原因之一的比例 ≥ 90%，其余标记 UNKNOWN | 每次评测 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

*依据：[beir-cellar/beir](https://github.com/beir-cellar/beir#readme)*

### 两种看起来在优化检索、实际优化错对象的做法

这两种做法都会让某个数字变好，也都很容易被立项。

问题是它们优化的不是主要失败来源。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| Recall@5 只有 62%，换更强的嵌入模型 | 召回率是检索的核心指标，换模型是直接手段 | 如果多数 miss 是「文档不存在」或「切分丢失」，换嵌入模型不会有任何改善。要先做 miss reason 分类 |
| 把 k 从 5 提到 20，Recall 明显提升 | 召回更多确实提高了命中概率，成本也可接受 | 更大的 k 会把无关内容塞进上下文，稀释关键信息并增加成本。要看的是 MRR 而不只是 Recall |

> 两条的共同前提是同一件事：先分类 miss reason，再决定优化方向。

### RAG 回答不准时先判断是检索还是生成

这是 RAG 排查的第一个分叉。判断方法很简单，不需要任何工具。

判断错了，后面所有优化都会做在错误的组件上。

| 检查 | 如果 | 结论 |
| --- | --- | --- |
| gold 在检索结果里吗 | 不在 | 检索问题，做 miss reason 分类 |
| gold 在但排很后 | 是 | 排序问题，看 MRR |
| gold 在且排前 | 是 | 生成问题，转到忠实度评测 |
| gold 本身不存在 | 是 | 语料问题，与检索无关 |

> 四行按顺序判断，第一个「是」就是分叉点。多数团队跳过这一步直接优化生成，方向常常是错的。

### 建一个最小检索评测集：约 60 分钟

三十条标注就能给出可用结论。关键是 gold 由人标注。

1. 收集 30 个真实用户问题，覆盖常见、长尾、歧义三类。
2. 由熟悉业务的人标注每个问题的 gold document，不用模型标注。
3. 跑检索，记录每个问题的 top-k 结果与 gold 是否命中、排第几。
4. 对未命中的逐条分类 miss reason，按五类归档。
5. 统计 Recall@k、MRR，以及各类 miss reason 的占比。

**期望结果**：典型结果是 miss reason 中「文档不存在」与「切分丢失」占比不低。这两类都不该由检索算法负责，但常常被算成检索效果差。

> ⚠ gold 标注不能由生成答案的同一模型完成。那样会把模型的偏差写进评测基准。

### 这一页的出口判据

检索门禁在生成门禁之前执行。检索不达标时生成层的分数没有解释力——你无法区分模型答不好和它根本没拿到材料。

第二段的切片比较要用区间。切片样本天然较小，用点估计比较不同切片的高低几乎一定会得出错误排序。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 任一 P0 查询切片的 Recall@5 < 70% 时阻断，先修检索再谈生成<br>查询改写导致的命中丢失率 > 5% 时阻断改写策略上线 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 切片指标一律带 Wilson 95% CI；单切片样本 < 30 条时只报区间不报点估计<br>版本间检索对比预注册效应量/非劣界；对同任务配对差值做任务级或聚类 bootstrap 95% CI，不以两个 CI 是否重叠判定 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 长尾查询切片的低召回，由产品 owner 签字接受或列入下一轮语料补充<br>top-k 取值在召回与干扰之间的取舍，由检索 owner 写明理由并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一份 miss reason 分布

分布比 Recall 数字有用得多：它直接告诉你该改语料、改切分还是改检索。

Recall 与 MRR 要一起报——只看 Recall 会让人不断增大 k。

- 先判断是检索还是生成问题，再动手
- 未命中逐条分类 miss reason
- Recall 与 MRR 一起报，避免盲目增大 k

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Ragas：RAG 指标的参考实现](https://docs.ragas.io/)** — RAG 指标实现
  - 能证明：忠实度、答案相关性、上下文精确率/召回率这些 RAG 专属指标可以被拆成可计算的定义，而不是停留在「回答质量好不好」这种不可判定的说法上。
  - 不能证明：多数指标本身由模型计算，因此指标带有与被测系统同源的误差；未经人工标注校准前，它的绝对值不能当验收线，只能看趋势。
  - `explodinggradients/ragas` · 版本 v0.4.3（2026-01-13） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[TruLens：RAG 三角评测与反馈函数](https://www.trulens.org/)** — RAG 评测方法
  - 能证明：RAG 的失败可以定位到三条边：问题↔上下文（检索对不对）、上下文↔回答（有没有编）、问题↔回答（答没答）。三条边分开测，才能区分「检索错了」和「检索对了但模型没用」。
  - 不能证明：反馈函数由模型实现，误差与被测模型可能相关；三角分解定位问题层，不给出修复方案。
  - `truera/trulens` · 版本 trulens-2.12.0（2026-08-06） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[BEIR：零样本检索评测基准套件](https://github.com/beir-cellar/beir#readme)** — 检索评测基准
  - 能证明：检索质量必须用 nDCG@k、Recall@k 这类带位置权重的指标衡量，且同一个检索器在不同领域的表现差异极大——零样本迁移能力不可假设。
  - 不能证明：公开语料上的排名不预测你私有语料上的表现；企业检索还受切分策略、元数据过滤与权限裁剪影响，这些不在基准里。
  - `beir-cellar/beir` · 版本 v2.2.0（2025-06-04） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点

  - 能证明：RAG 不是一个整体，是切分 → 嵌入 → 索引 → 召回 → 重排 → 组装上下文这条可逐段替换的管线。理解这条管线才知道一次失败该在哪一段查。
  - 不能证明：框架提供组件，不提供语料治理。切分策略与元数据设计仍是决定检索质量的主要因素，且高度依赖你的文档形态。
