## TD-X501

### 多模态的失败不在单个模态里，在模态之间的关系里

图能认对、文字能读对，两者放在一起的关系仍然可能是错的。多模态评测最常见的设计缺陷，是把它当成两个单模态评测的加总。

下面三条给出关系层的失效形态——它们在任何单模态指标上都表现正常。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 分别评图和评文，不评两者的对应关系 | 图文分别正确而对应关系错误的样本，在关系型任务中可占错误总量的 30% 以上 | 两个模态的指标都在 90% 以上，端到端却达不到可用水平 |
| 缺模态时系统照常输出 | 输入只有文字没有图时仍给出基于图的描述，属于典型编造；这类场景的拒答率必须单独测，实测中未做专项设计的系统拒答率常低于 20% | 把「鲁棒」读成「缺什么都能跑」，而它实际是在编 |
| 矛盾注入场景完全没测 | 图文互相矛盾时系统应报冲突而非择一；未测系统在这类输入下的择一比例接近 100% | 以为系统会指出矛盾，实际它默默选了一个 |

> 共同解法：把「关系」本身设为被测对象，并用配对 fixture 与矛盾注入去验证它。

### 多模态评测的四个词

多模态的失败往往不在单一模态，而在模态之间的关系上。

| 术语 | 一句话解释 |
| --- | --- |
| 跨模态关系 | 图与文、音与画、视频与时序之间应当成立的对应关系 |
| 矛盾场景 | 两个模态给出不一致信息；正确行为通常是指出矛盾而不是二选一 |
| 缺模态 | 某个模态缺失或不可读；模型应当说明而不是脑补 |
| 独立 Oracle | 不依赖被测模型的判据，如图像元数据、字幕时间轴 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/)*

### 多模态的失败不在单个模态里，在模态之间的关系里

把多模态评测做成「图像任务测一遍、文本任务测一遍」是最常见的做法，它会系统性地漏掉真正的失败：模型看图说了图里没有的东西、文本与图像冲突时选错了一边、少了一个模态时不声不响地拿剩下的猜。

这三类失败的共同点是它们只在**关系**里显现。单模态指标全部正常，跨模态一致性可以完全崩掉——因为没有任何一个单模态指标在度量「这两个输入说的是不是同一件事」。

因此评测设计必须刻意构造矛盾场景：给一张图配一段与图矛盾的说明，看模型选哪一边、有没有指出矛盾。这类样本不会自然出现在流量里，必须人工构造，而它们恰恰是判断跨模态能力的唯一有效样本。

缺模态是另一类必测场景：图片加载失败、音频截断、OCR 返回空。正确行为是明确报告缺失并降级，而不是用剩下的模态硬答。这一条与 RAG 的「无答案能力」是同一个原则在多模态上的形态。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/) · [confident-ai/deepeval](https://deepeval.com/docs/getting-started)*

### 三类跨模态关系各自需要什么样的样本

这张表的第三列全部是「必须人工构造」。多模态评测的成本大头不在执行，在样本构造——这一点在排期时经常被低估。

最后一行的独立 Oracle 是关键：判断跨模态一致性时，不能再用同一个模型来判，否则它对自己的错误是盲的。

| 跨模态关系 | 要测什么 | 样本从哪来 | 边界 |
| --- | --- | --- | --- |
| 一致 | 两个模态描述同一事实时，回答是否同时用到两者 | 从真实流量采样即可 | 自然样本里一致占绝大多数，无法暴露问题 |
| 矛盾 | 两个模态冲突时，是否指出矛盾而不是默默选一边 | 必须人工构造：图文刻意不符 | 构造成本高，但这是判断跨模态能力的唯一有效样本 |
| 缺失 | 少一个模态时是否明确报告并降级 | 人工构造：图片加载失败、音频截断、OCR 空 | 与 RAG 的无答案能力同一原则 |
| 独立判据 | 跨模态一致性由谁判 | 人工标注 + 与被测模型不同源的判据 | 用同一个模型自判，它对自己的错误是盲的 |

> 四行里有三行的样本必须人工构造，这是多模态评测与单模态评测成本结构上的根本差别。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/) · [confident-ai/deepeval](https://deepeval.com/docs/getting-started) · [UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/)*

### 这张图的 7 个节点，本页各交付什么

这张图的核心节点是「跨模态关系」——它是被测对象，不是中间产物。左侧两个节点为它准备输入，右侧三个节点为它准备判据与复核。

「独立 Oracle」在多模态场景里格外重要：用同一个多模态模型去判另一个多模态模型的输出，几乎必然带入同类偏差。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 任务/模态合同 | 写明本任务涉及哪些模态、它们之间应当满足什么关系 | 模态关系合同 |
| 配对 Fixture | 构造成对的图文/音画样本，包含正例与关系错配的负例 | 配对夹具集 |
| 跨模态关系 | 把关系正确性设为独立被测项，与单模态识别分开出分 | 关系正确率结果 |
| 独立 Oracle | 用与被测模型不同来源的判据判定关系，规避同类偏差 | 独立判据集 |
| 矛盾注入 | 构造图文互相矛盾的输入，验证系统报冲突而非静默择一 | 矛盾注入结果 |
| 切片指标 | 按模态组合、语言、清晰度等切片分别出分 | 切片报告 |
| 人工复核 | 对争议样本与关系判定分歧做人工裁决并留痕 | 人工裁决记录 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 三类跨模态关系与各自的独立判据

多模态评测最容易退化成「让模型描述一下」。有独立判据才能判对错。

右列是不依赖模型的判据来源——它们通常来自元数据而非内容理解。

| 关系 | 要验证什么 | 独立判据来源 |
| --- | --- | --- |
| 图文一致 | 描述与图像内容对应 | 图像标注或元数据 |
| 音画同步 | 声音与画面时间对齐 | 字幕时间轴、时间戳 |
| 视频时序 | 事件先后顺序正确 | 镜头切换记录、帧时间 |

> 三类的共同点：判据都来自元数据而不是另一个模型的理解。用模型判模型在这里尤其危险。

*依据：[stanford-crfm/helm](https://crfm.stanford.edu/helm/)*

### 这一页的验收口径：关系正确率独立出分

本页最重要的设计是 X501-1：关系正确率必须与单模态识别率分开报告。合并报告会让关系层的问题被识别层的高分掩盖。

X501-3 的缺模态拒答率与 TD-T12 的拒答率是同一个原理在多模态上的应用：缺输入时应当拒答，而不是用另一个模态去猜。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| X501-1 | 跨模态关系正确率 | 关系正确率 ≥ 85%，且与单模态识别率分开报告，禁止合并出分 | 每次发布 |
| X501-2 | 矛盾检出 | 图文矛盾场景下报冲突的比例 ≥ 95%，静默择一次数 = 0 | 每次发布 |
| X501-3 | 缺模态拒答 | 缺失必需模态时拒答率 ≥ 98% | 每次发布 |
| X501-4 | 判据独立性 | 使用与被测模型同族 Oracle 的评测项占比 = 0 | 每次评测设计 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在测多模态、实际只测了单模态的做法

这两种做法都用了多模态输入，输出也确实结合了多个模态。

问题是判定只用了其中一个模态。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 给模型一张图和一段文字，判断输出描述是否合理 | 输入是多模态的，输出也综合了两者 | 「合理」由文本判定时，实际只测了文本流畅度。图文矛盾的场景会被判为合理，因为文字本身自洽 |
| 用另一个多模态模型给输出打分 | 评判方也理解多模态，能力更匹配 | 两个模型可能共享同类偏差。跨模态判定必须有来自元数据的独立判据，不能是模型对模型 |

> 两条的共同修法：判据来自元数据，且必须专门构造矛盾与缺模态场景。

*依据：[confident-ai/deepeval](https://deepeval.com/docs/getting-started)*

### 多模态输出看起来对但不可靠时按什么顺序查

按三类关系与两类特殊场景逐项排查。多数问题出在特殊场景上。

特殊场景需要专门构造，真实数据里很少出现。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 描述通顺但与图不符 | 只测了文本 | 加入图像元数据作为判据 |
| 矛盾输入时随便选一个 | 缺矛盾场景样本 | 专门构造图文矛盾样本 |
| 模态缺失时编造内容 | 缺模态场景样本 | 构造缺图或缺音样本 |
| 时序描述错乱 | 缺时间轴判据 | 用帧时间或字幕时间轴校验 |

> 第二、三行的样本必须人工构造。真实数据集里矛盾与缺失都很罕见，但生产中并不罕见。

### 构造矛盾与缺模态场景：约 50 分钟

这两类场景决定了系统在异常输入下的行为，而它们只能人工构造。

1. 选一批已有的图文样本，人工制造矛盾：把文字描述改成与图像不符。
2. 跑一遍，观察模型是指出矛盾、还是选了其中一个、还是自行调和。
3. 再构造缺模态样本：移除图像或音频，只保留另一个模态。
4. 观察模型是说明模态缺失，还是根据剩余模态脑补。
5. 把两类的正确行为写成判据，并保留全部原始工件供人工复核。

**期望结果**：典型结果是模型倾向于自行调和矛盾并脑补缺失内容，很少主动指出问题。这两个行为都需要在提示与门禁上处理。

> ⚠ 人工构造矛盾时要保持两个模态各自内部自洽。否则模型可能因为单模态异常而报错，测不出跨模态判断。

### 这一页的出口判据

多模态评测的成本高于单模态，因此它的门禁更需要聚焦：只守关系层和缺模态两件事，单模态识别率交给各自领域的既有方法。

第三段要接受的通常是覆盖度：模态组合数随模态数量组合增长，全覆盖不现实，必须明示测了哪些组合、没测哪些。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 缺失必需模态时的拒答率 < 95% 时阻断<br>使用同族模型作为 Oracle 的评测项数量 > 0 时阻断，判据须替换 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 关系正确率按模态组合切片给出 95% CI，单切片 < 30 条时只报区间<br>与上一版本比较以 CI 重叠判定，不用点估计差值 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 未覆盖的模态组合清单，由测试负责人列出并签字接受<br>关系判定存在人工分歧的样本比例，由业务 owner 确认可接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走两类专门构造的场景样本

矛盾与缺模态是多模态系统最容易出错、也最少被测试的两类场景。

它们的正确行为都是「说明情况」而不是「给出答案」，这一点要写进判据。

- 判据来自元数据，不用模型判模型
- 矛盾与缺模态场景人工构造
- 保留原始工件供人工复核

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[DeepEval：pytest 风格的 LLM 评测框架](https://deepeval.com/docs/getting-started)** — AI 侧断言执行器
  - 能证明：LLM 评测可以直接寄生在 pytest 生态里：用例、fixture、参数化、CI 集成全部复用既有工程习惯，降低把评测接进流水线的成本。
  - 不能证明：指标默认阈值是框架给的示例值，不是你业务的验收线。
  - `confident-ai/deepeval` · 版本 v4.1.7（2026-07-29） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Inspect：任务 / solver / scorer 分层的模型评测框架](https://inspect.aisi.org.uk/)** — 评测框架
  - 能证明：评测可以拆成三个独立可替换的部件：dataset 定义问什么、solver 定义怎么问、scorer 定义怎么判。三者分离之后，换模型不用改判据，改判据不用改数据集——这是把一次性评测脚本变成可回归资产的结构条件。
  - 不能证明：框架不提供判据。scorer 写得对不对、数据集有没有覆盖你的风险切片，框架一概不管，全绿只说明流程跑通了。
  - `UKGovernmentBEIS/inspect_ai` · 版本 release/2025-11-28 · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[HELM：多场景、多指标的整体性评测](https://crfm.stanford.edu/helm/)** — 评测方法学
  - 能证明：单一准确率无法描述模型能力。HELM 的做法是把场景（scenario）与指标（metric）做成正交的两维，同一个场景同时报准确率、校准度、鲁棒性、公平性、效率——「模型 A 比 B 好」这句话必须指明在哪个场景的哪个指标上。
  - 不能证明：覆盖的是公开场景，不覆盖你的业务分布。榜单名次不能迁移到企业任务上。
  - `stanford-crfm/helm` · 版本 v0.5.16（2026-04-30） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
