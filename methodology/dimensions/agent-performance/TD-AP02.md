## TD-AP02

### 只有一个端到端时长的报告，除了「慢」之外说明不了任何事

用户等待的那一段时间由排队、首 token、逐 token、工具调用与重试共同构成。它们的优化手段完全不同，成本也完全不同。

下面三条是不做分段时会付出的代价。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 只报端到端 p99 | 端到端时长由 4 段以上构成；不分段时归因正确率接近随机，优化常落在占比不足 10% 的那一段 | 投入几周优化推理，而真正的瓶颈在工具依赖上 |
| 用端到端时长代表体感 | 流式输出下用户在首个 token 出现时就开始获得价值；TTFT 可以是 1 秒而端到端总时长是 30 秒，两者相差 1 个数量级以上 | 总时长超标被当成体验问题，而用户实际抱怨的是首字慢 |
| 重试被合并进原调用计时 | 重试不单列时，一次任务的实际模型调用数可能是记录值的 2～3 倍，调用放大与成本同时不可见 | 成本超支找不到来源，容量模型也偏乐观 |

> 分段不是为了报告好看，是为了让「变慢了」这个结论能落到某一段上。

### 四个最常被混用的性能词

Agent 的「慢」有六个来源，而多数报告只报一个总时长。下面四个词决定你能不能把等待拆开。

| 术语 | 一句话解释 |
| --- | --- |
| TTFT | 从请求到第一个 token 的时间；它决定流式体验，但在 Agent 里通常发生在若干次工具调用之后 |
| TPOT / ITL | 生成阶段每个 token 的平均间隔；总时长 ≈ TTFT + 输出长度 × TPOT |
| Goodput | 满足 SLO 前提下的成功吞吐；裸吞吐上升而 goodput 下降是最常见的容量假象 |
| Good task | 一次既完成业务终态、又满足延迟与成本约束的任务；它是 SLI 的分子 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[vllm-project/vllm](https://docs.vllm.ai/)*

### 一个端到端时长说明不了任何事，因为它是六段之和

用户等待的总时长在 Agent 系统里至少由六段构成：入口排队、规划（模型调用）、工具调用、模型生成、步骤间编排开销、结果组装。六段的修复手段完全不同，而一个总时长把它们全部抹平。

实践中最常见的误判是把总时长归因给「模型慢」。实际拆开之后，相当一部分系统的时间大头在工具调用与编排开销上——而这两项的优化成本远低于换模型，也不需要牺牲质量。

Goodput 在任务级的定义要重述：分母是满足 SLO 的**任务**数，不是请求数。一个任务里有一次模型调用超时但重试成功、最终按时完成，这个任务是 good task；反过来所有调用都很快但任务没在期限内完成，它不是。

拆段的前提是 trace 完整。缺少某一段的 span，那一段的耗时会被摊到相邻段上——于是排查会指向错误的方向，而且指得非常自信，因为数字看起来是精确的。

*依据：[vllm-project/vllm](https://docs.vllm.ai/) · [open-telemetry/opentelemetry-specification](https://opentelemetry.io/docs/specs/otel/)*

### 六段各自的观测方式与优化方向

这张表是把「慢」变成可行动结论的分解表。先量出六段的占比，再决定优化哪一段。

第四列的成本差异很大：编排与工具调用的优化通常是最便宜的，换模型是最贵的，而后者常常是第一个被提出来的方案。

| 耗时段 | 怎么观测 | 常见根因 | 优化方向 |
| --- | --- | --- | --- |
| 入口排队 | 到达时刻与开始处理时刻的差 | 容量不足或调度策略 | 加实例、分级队列 |
| 规划（模型调用） | 规划 span 的耗时 | 上下文过长导致 prefill 慢 | 裁剪上下文、启用前缀缓存 |
| 工具调用 | 工具 span 耗时与调用次数 | 下游慢，或调用次数超出预期 | 并行化、缓存、减少不必要调用 |
| 模型生成 | TTFT 与 TPOT 分开量 | 输出过长或并发竞争 | 限制输出长度、限并发 |
| 编排开销 | 相邻 span 之间的空隙 | 串行化、序列化、状态持久化开销 | 并行化、减少 checkpoint 频率 |
| 结果组装 | 最后一段 span | 后处理逻辑重 | 流式返回、异步组装 |

> 六段量完之后，「系统慢」这句话会变成「工具调用占了 60%，其中 80% 是同一个接口」——后者可以直接行动。

*依据：[vllm-project/vllm](https://docs.vllm.ai/) · [open-telemetry/opentelemetry-specification](https://opentelemetry.io/docs/specs/otel/) · [prometheus/prometheus](https://prometheus.io/docs/practices/histograms/) · [Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)*

### 这张图的 6 个节点，本页各交付什么

这张图把用户感受到的那一段等待，拆成了五段各自可测的时间。归因必须落到其中某一段上，否则「变慢了」这个结论无法转成工作项。

最后一个节点是 Goodput 门禁：吞吐提升如果伴随成功率下降，它不算改进。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 计划到达时间 | 以计划到达而非实际发出计时，避免协调遗漏把排队折叠掉 | 计划到达记录 |
| Queue wait | 测量准入与排队耗时，与执行耗时分开 | 排队分位数据 |
| Prefill/TTFT | 测量首 token 延迟，作为体感主指标 | TTFT 分位数据 |
| Decode/TPOT | 测量逐 token 间隔，作为生成速度指标 | TPOT 分位数据 |
| Tool/Retry/Step | 测量工具调用、重试与步数的耗时占比，这一段常被忽略却占比很高 | 工具与重试耗时分解 |
| Task Goodput Gate | 以达标完成的任务数判定，吞吐与质量联合出结论 | Goodput 判定 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 把用户等待拆成六段，每段有各自的修复手段

「慢」不是一个可以修的问题。只有拆成六段之后，才知道该加机器、改并发、还是改重试策略。

右列写的是这一段变慢时真正有效的动作——注意没有一段的答案是「换更快的模型」。

| 等待来源 | 怎么测 | 这一段变慢时的有效动作 |
| --- | --- | --- |
| 排队 | 入队到出队时间 | 调并发上限或扩容，不是优化 Prompt |
| 首 Token | 出队到首 token | 看 prefill 与上下文长度，缩短系统提示 |
| 逐 Token | 首 token 到末 token | 看输出长度分布与批处理策略 |
| 工具调用 | 每次 tool attempt 耗时 | 超时与依赖治理，与模型无关 |
| 重试 | 重试次数 × 单次耗时 | 收紧重试预算；重试是延迟放大器 |
| 编排 | span 之间的空隙 | 查调度与串行化，通常是最被忽略的一段 |

> 六段之和应当接近端到端时长；差额本身是信号，说明有未被观测的等待。

*依据：[open-telemetry/opentelemetry-specification](https://opentelemetry.io/docs/specs/otel/)*

### 这一页的验收口径：分段可归因

AP02-1 是本页的核心：端到端时间必须能拆到各段并且相加吻合。拆不开的延迟无法归因，只能靠猜。

AP02-4 把吞吐与质量绑在一起判定，防止「提高并发换吞吐」这种表面收益。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| AP02-1 | 分段完整 | 端到端时间可分解到排队 / prefill / decode / 工具四段的比例 = 100%，各段之和与总时长偏差 ≤ 5% | 每次压测 |
| AP02-2 | 体感延迟 | TTFT 的 p95 < 2 秒；p99 < 5 秒 | 每次压测 |
| AP02-3 | 重试可见 | 重试调用在 trace 中单独成 span 的比例 = 100%；被合并计入原调用的次数 = 0 | 每次压测 |
| AP02-4 | 联合判定 | 并发提升时 task 成功率下降 ≤ 2pt，超出即判定吞吐提升无效 | 每次容量评估 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

*依据：[Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)*

### 两种看起来在优化性能、实际在制造假象的做法

这两种做法都能让报表变好看，而且都能给出「改进前后」的对比数据。

它们的共同问题是：优化的对象不是用户感知的那个量。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 提高并发以提升 QPS，QPS 涨了 40% | 吞吐是标准性能指标，涨了就是变快了 | 并发上去后超时与重试增加，goodput 可能反而下降。分母必须是 good task，不是 request |
| 把 TTFT 从 2s 优化到 0.8s，体验大幅改善 | 首字时间是流式体验的核心指标，优化正确 | 如果任务总时长里工具调用占八成，TTFT 优化对用户几乎无感。先拆六段，再决定优化哪一段 |

> 共同根因：在没有拆分的情况下优化一个局部指标。

### 用户说慢但指标正常时按什么顺序查

「指标正常但用户抱怨」几乎总是口径问题：测的位置不对，或者分母不对。

先确认端到端时长是从用户按下按钮算起，而不是从模型调用算起。

| 症状 | 先怀疑 | 下一步检查 |
| --- | --- | --- |
| p95 正常但投诉集中 | 是否按任务类型分桶 | 把长任务单独成桶再看分位 |
| 吞吐涨了但满意度降了 | goodput 而非裸吞吐 | 用 good task 做分子重算 |
| 六段之和远小于端到端 | 编排空隙未被观测 | 补 span 之间的时间戳 |
| 偶发极慢 | 重试放大 | 统计重试次数分布而不是均值 |
| 同样负载今天慢明天快 | 缓存命中率变化 | 把命中率写进每次报告 |

> 第三行最容易被忽略：观测不到的那段等待，通常就是最长的那段。

### 给一条真实任务做一次六段拆解：约 30 分钟

不需要压测。挑一条端到端偏慢的真实 trace，把它的时间线画出来即可。

1. 选一条 p90 附近的真实任务 trace，记下端到端总时长。
2. 在时间线上标出六个区间：排队、首 token、逐 token、每次工具调用、每次重试、span 之间的空隙。
3. 六段求和，与端到端总时长比较。差额如果超过一成，说明有未被观测的等待。
4. 找出占比最大的那一段，写下针对它的有效动作（对照上面的表，不要写「优化模型」）。
5. 把同一条任务在低峰再跑一次，比较哪一段变了——变化最大的那段就是与负载相关的瓶颈。

**期望结果**：你会得到一张六段时间线和一个占比排序。多数团队第一次做完会发现：占比最大的一段不是模型推理。

> ⚠ 不要用平均值做拆解。六段各自都是长尾的，平均之后所有段都会看起来差不多。

### 这一页的出口判据

这道门禁拒绝不可分解的延迟数字。一个只有总时长的报告，除了「慢」之外说明不了任何事。

第三段要接受的是各段阈值之间的取舍：压缩排队通常要以资源冗余为代价。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 分段之和与端到端总时长偏差 > 10% 时阻断，说明存在未被记录的耗时<br>重试未单独成 span 的比例 > 0 时阻断，成本与放大倍数不可见 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 各段延迟一律报 p95/p99，禁止用均值<br>单档位样本 < 500 个任务时该档位结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 各段延迟阈值的取值与所需资源冗余，由容量 owner 签字确定<br>工具与检索耗时中不可优化的部分，由架构 owner 明示接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一本能被别人查的指标字典

指标字典的作用不是列出指标，而是固定口径：每个指标的分子分母、测量位置、分桶方式各是什么。

口径不固定时，两次报告之间的涨跌没有意义——你不知道是系统变了还是算法变了。

- 每个指标写清分子、分母与测量位置
- goodput 用 good task 做分子，不用 request
- 按任务类型分桶后再报分位数

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)** — 判据框架
  - 能证明：SLI/SLO/错误预算的定义方式，以及为什么用分位而非均值、为什么阈值必须来自业务而非工具默认值。性能与稳定性两页的验收口径都建立在这套框架上。
  - 不能证明：书里的示例数字是示例。任何直接照抄的 SLO 都没有经过你自己业务成本的校准。
  - 版本 未锚定 · 许可证见原站 · 非代码资料，按链接引用与转述处理
- **[OpenTelemetry Specification](https://opentelemetry.io/docs/specs/otel/)** — 可观测性协议
  - 能证明：trace / metric / log 三类信号的统一数据模型与上下文传播机制。跨服务、跨语言归因之所以可能，依赖的是同一个 trace context 而不是同一个日志格式。
  - 不能证明：接入 OTel 不等于可归因。采样率、缺失的 span 属性、断掉的上下文传播都会让链路在最需要的时候断在中间。
  - `open-telemetry/opentelemetry-specification` · 版本 v1.60.0（2026-08-07） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Prometheus：指标采集与查询](https://prometheus.io/docs/practices/histograms/)** — 指标实现
  - 能证明：直方图与分位数的实际计算方式，以及为什么跨实例平均分位数在数学上是错的（分位不可加）。这一条直接决定了 p95 报表是否可信。
  - 不能证明：指标是聚合信号，无法回答单次失败发生了什么。归因必须回到 trace 与日志。
  - `prometheus/prometheus` · 版本 v3.13.2（2026-07-30） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[vLLM：高吞吐推理服务引擎](https://docs.vllm.ai/)** — 推理服务实现
  - 能证明：生成式服务的延迟由两个阶段构成：prefill 处理输入、decode 逐 token 产出。连续批处理会把不同请求混在同一批里，因此单个请求的延迟取决于同时在跑的其他请求——这是传统 QPS 模型解释不了生成式服务表现的根本原因。
  - 不能证明：引擎指标反映的是服务端状态，不等于用户体感；托管 API 通常不暴露这些指标，此时只能从客户端阶段指标推断并标记未知。
  - `vllm-project/vllm` · 版本 v0.27.1（2026-08-11） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
