## TD-AP03

### Trace 断链会怎样误导容量与质量结论

Trace 缺父子关系时，失败仍然可能被包装成成功文本，性能、工具安全和重试成本会同时失去归因。

先把缺口分到传播、采集、存储或脱敏层，再决定修复；不要用增加采样率代替结构修复。

| 失效点 | 看起来像什么 | 可核查的代价 |
| --- | --- | --- |
| tool span 无 parent | 模型正常、工具偶发失败 | 无法区分参数错误与依赖错误；这类失败的归因成功率降到 0，只能记为 UNKNOWN |
| retry 未单列 | 任务最终成功 | 调用放大与真实成本被隐藏；一次任务的实际模型调用数可能是记录值的 2～3 倍 |
| 高危动作低采样 | 观测成本下降 | 关键失败样本永久缺失；按 1% 均匀采样时，高危动作的失败样本命中概率同样只有 1% |
| 脱敏删除结构 | 隐私更安全 | 无法在不暴露原文的情况下重放；这类 trace 的可重放率为 0，缺陷进不了回归集 |

> Trace 的价值是可归因闭包，不是字段数量。

### Trace 相关的四个词

归因能力完全取决于 trace 的结构。结构不对时，你只能知道「失败了」，走不到「第几步坏的」。

| 术语 | 一句话解释 |
| --- | --- |
| Task Root | 一次任务的根 span；一条任务对应一个根，是所有归因的挂载点 |
| Span 类型 | generation、tool、retry、handoff 四类；类型不分开就无法按类型统计耗时与失败 |
| 标准字段 vs 本地扩展 | 前者跨系统可比，后者承载业务语义；混在一起会让 trace 无法迁移 |
| 可重放 | 凭 trace 就能还原一次运行；不可重放的失败 trace 无法归因，也就无法修 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[open-telemetry/opentelemetry-specification](https://opentelemetry.io/docs/specs/otel/)*

### Trace 断链会让容量与质量结论同时失真

在 Agent 系统里 trace 不是调试工具，是主要的度量数据源：任务耗时、调用次数、成本、失败归因全部从它算出来。因此断链不只是「排查不方便」，而是直接产出错误的数字。

断链的典型后果有两个方向。一是低估：某一段的 span 缺失，那段耗时被摊给相邻段，容量分析指向错误的瓶颈。二是漏统计：某类失败的 span 根本没上报，失败率被系统性低估，而这类失败往往正是最需要关注的那类（超时、崩溃、被中断）。

上下文传播是断链的主要发生点，且集中在三处：异步边界（消息队列、后台任务）、跨语言调用、以及第三方 SDK 内部。这三处需要显式处理，默认自动埋点通常覆盖不到。

「可重放」是 trace 的更高要求：除了时序，还要记录足够的输入信息使这次执行可以被重新构造。它的价值在事故复盘时才显现——没有可重放能力时，线上偶发问题只能靠猜，而 Agent 的偶发问题占比远高于传统系统。

*依据：[open-telemetry/opentelemetry-specification](https://opentelemetry.io/docs/specs/otel/) · [open-telemetry/semantic-conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/)*

### 一条可用的 trace 必须能回答的五个问题

把这五个问题当成 trace 的验收清单：任选一条线上 trace，五个问题都答得上来才算接入完成。

第三列写的是答不上来时会得出什么错误结论——这比「不方便」更能说明为什么必须补齐。

| 必须能回答 | 靠什么字段 | 答不上来的后果 | 工具 |
| --- | --- | --- | --- |
| 这次任务一共花了多久 | Task Root span 的完整时间跨度 | 只能用日志时间戳凑，异步场景必错 | OTel trace context |
| 时间花在哪几段 | 各类型 span 的耗时与嵌套关系 | 缺失段的耗时被摊给相邻段，瓶颈判断错误 | OTel span 类型规范 |
| 调了几次模型、花了多少 token | GenAI 语义约定的 token 与模型字段 | 成本无法归因到任务，单位成功成本算不出 | OTel GenAI 语义约定 |
| 失败发生在哪一步、什么原因 | span status + 错误属性 + stop_reason | 失败率被低估，且无法分类 | 自建 stop_reason 约定 |
| 能不能重放这次执行 | 输入快照、版本 Manifest、随机种子 | 线上偶发问题只能靠猜 | Langfuse / Phoenix 持久化 |

> 五个问题里前三个靠标准约定，后两个需要自己补。后两个恰恰是事故时最需要的。

*依据：[open-telemetry/opentelemetry-specification](https://opentelemetry.io/docs/specs/otel/) · [open-telemetry/semantic-conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/) · [langfuse/langfuse](https://langfuse.com/docs) · [Arize-ai/phoenix](https://arize.com/docs/phoenix)*

### 这张图的 6 个节点，本页各交付什么

这张图是一条 trace 的结构定义：一个任务一个根，排队、生成、工具尝试各自成子 span，终态作为事件落在根上。

这个结构不是记录偏好，它决定了哪些问题事后还能被回答——父子关系一旦丢失，归因就只能靠猜。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| invoke_agent root | 一次任务一个根 span，作为全部子 span 的归属 | 根 span 规范 |
| queue.wait span | 排队单独成 span，使排队与执行可分离 | 排队 span 定义 |
| gen_ai generation span | 每次模型生成成一个 span，记录 token 数与模型版本 | 生成 span 字段规范 |
| execute_tool attempt span | 每次工具尝试（含重试）单独成 span，使调用放大可见 | 工具尝试 span 规范 |
| task.finalize event | 把业务终态作为事件记在根上，作为成功判定依据 | 终态事件定义 |
| Metric/Trace/Log 存储与访问 | 定义采样、保留与脱敏策略，保证高危动作不被采样掉 | 采样与脱敏策略 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 一条可用的 trace 必须能回答的五个问题

trace 不是日志的另一种写法。它的唯一目的，是让一次失败能被追到具体的那一步。

如果下面五个问题里有任何一个答不上来，这条 trace 在归因时就是无效的。

| 必须能回答 | 靠哪个字段 | 缺失的后果 |
| --- | --- | --- |
| 这次任务的完整边界在哪 | task root span 的起止 | 无法计算端到端时长 |
| 第几步开始出错 | span 序号 + 状态 | 只能知道失败，不能定位 |
| 调用了哪个工具、什么参数 | tool span 的入参出参 | 无法区分工具错误与参数错误 |
| 重试了几次、为什么 | retry span 与原因码 | 把重试成功当成一次成功 |
| 当时的工具描述是什么 | 工具清单快照 hash | 无法证明没被 rug-pull |

> 最后一行同时服务于性能归因与安全检测——它是两条链的交点。

*依据：[open-telemetry/semantic-conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/)*

### 这一页的验收口径：结构完整优先于采样率

AP03-2 是本页最关键的一条：高危动作必须全采样。按统一比例采样时，最需要看到的失败恰好最可能被丢掉。

AP03-4 要求脱敏保留结构——把整段内容删掉确实更安全，但也让这条 trace 失去了全部归因价值。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| AP03-1 | 父子完整 | 子 span 有正确 parent 的比例 = 100%；孤儿 span 数 = 0 | 每日 |
| AP03-2 | 高危全采样 | 高危动作相关 trace 的采样率 = 100%；常规流量采样率 ≥ 1% | 持续 |
| AP03-3 | 重试可见 | 重试尝试单独成 span 的比例 = 100% | 每日 |
| AP03-4 | 脱敏保结构 | 脱敏后仍可重放的 trace 比例 ≥ 95%；因脱敏导致不可重放的数量 = 0（高危动作） | 每周 1 次 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

*依据：[triton-inference-server/server](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/)*

### 两种看起来 trace 很完整、实际归因不了的设计

这两种设计在技术评审里都很难被质疑：字段多、覆盖全、存储也不小。

问题出在结构而不是数量——trace 的价值来自结构，不来自字段数。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 每次模型调用打一条完整日志，字段有三十多个 | 覆盖非常全，出事时有得查 | 没有 task root，三十条日志之间没有归属关系。你能看到每次调用，但拼不出一次任务 |
| 为控制成本，trace 采样率设为 5% | 采样是可观测性的标准做法，成本可控 | 高危动作与失败任务恰好是少数。5% 采样意味着大部分需要归因的场景根本没有记录。高危必须 100% |

> 第二条的正确做法是分层采样：常规低采样，失败与高危全量。

### 拿到失败 trace 却查不下去时按什么顺序查

查不下去通常不是分析能力问题，是 trace 结构缺了一环。下表按缺失概率从高到低排列。

补齐字段的成本远低于反复复现问题的成本——这是可观测性投入最容易算清的一笔账。

| 症状 | 先怀疑 | 下一步检查 |
| --- | --- | --- |
| 能看到调用看不出任务 | 缺 task root | 补根 span 与 trace_id 贯穿 |
| 知道失败不知道哪步 | span 无序号或无状态 | 给每个 span 加序号与终态 |
| 无法区分工具错与参数错 | tool span 未记入参 | 补入参出参，注意脱敏 |
| 重试被当成一次成功 | retry 未单列 span | 把重试建成独立 span 并记原因 |
| 无法在测试环境复现 | 缺可重放五要素 | 补模型版本与种子、完整 prompt、工具快照、时间戳 |

> 五行的共同点：都不是分析方法的问题，都是采集设计的问题。

### 用一条失败 trace 做可重放自检：约 25 分钟

不需要改代码。拿一条真实失败 trace，逐项对照可重放五要素即可。

1. 取一条最近的失败任务 trace，不要挑最容易的那条。
2. 逐项检查五要素：模型版本与种子、完整 prompt（含 system）、工具清单快照与 description hash、每次调用的入参出参、时间戳。
3. 缺失的项逐条列出，并标注它属于「采集没做」还是「脱敏时被删掉」——这两种的修法完全不同。
4. 尝试仅凭这条 trace 在测试环境重放一次，记录卡在第几要素上。
5. 把结果写成一条可观测性缺口清单，交给研发 owner，并写明补齐后能多回答哪个问题。

**期望结果**：多数团队第一次做完会卡在「工具清单快照」这一项上——它是最少被采集、也是唯一能证明工具描述未被篡改的字段。

> ⚠ 脱敏不是删除。把整个入参删掉会让 trace 失去归因价值；正确做法是字段级脱敏并保留结构。

### 这一页的出口判据

这道门禁守的是「事后还能不能查」。它不改善性能，但没有它，其余七页的结论都无法被复核。

第三段要接受的是观测成本：全采样高危动作、保留可重放结构都要花存储，这个额度需要有人认领。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 孤儿 span 数 > 0 或高危动作采样率 < 100% 时阻断<br>高危动作 trace 因脱敏而不可重放的数量 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 可重放率按 20 条抽样给出 95% CI 下界与阈值比较<br>抽样 < 20 条时可重放性结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 常规流量的采样率与观测成本，由 SRE 与测试负责人共同署名<br>脱敏策略中被判定为必须删除的字段，由数据 owner 逐项确认 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[open-telemetry/opentelemetry-specification](https://opentelemetry.io/docs/specs/otel/)*

### 带走一份 Trace Schema 与字段治理表

治理表要把标准字段与本地扩展分列，并对每个字段标注隐私等级与保留期。

分不开时会出现两种事故：迁移时本地字段丢失，或敏感字段被长期保留。

- 一条任务一个 task root，四类 span 分开
- 高危动作与失败任务 100% 记录，不采样
- 可重放五要素逐项检查，缺口交给研发 owner
