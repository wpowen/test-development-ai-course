## TD-AP01

### 压测单位选错，后面每一个数字都在描述另一个系统

Agent 压测里最贵的错误发生在第一步：把「一次请求」当成压测单位。一次任务可能包含十几次模型调用与工具调用，两者之间没有固定比例。

下面三条都是这一个错误的不同表现，它们共同的后果是得到一个既好看又无法换算成业务量的数字。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 用入口 2xx 代表任务成功 | 网关返回成功时任务可能仍在后台失败；两者的差额在异步 Agent 上通常不为 0，且不体现在任何入口指标里 | 可用性 99.9% 与用户完成率之间出现无法解释的落差 |
| 按平均输入输出长度构造请求 | 输出长度是长尾分布，p99 常达 p50 的数倍；按均值压测时 KV Cache 与显存压力完全没有出现 | 容量数字高估 2～5 倍，扩容后仍然排队 |
| 只压最短工具路径 | 多跳路径的累积延迟与失败率随跳数上升，只压 1 跳时这部分完全不可见 | 把生产上的超时归因为「模型变慢了」，实际是路径分布与压测不一致 |

> 三条的根因是同一个：压测单位从 task 退化成了 request。

### 先把 workload 这个词说清楚

Agent 压测里最贵的错误发生在第一步：把「一次请求」当成压测单位。下面四个词决定了你后面所有数字算在什么对象上。

| 术语 | 一句话解释 |
| --- | --- |
| Task | 一次有业务终态的完整工作，可能包含十几次模型调用与工具调用；它才是 Agent 的压测单位 |
| Workload 模型 | 任务类型、上下文长度、工具路径、允许终态与故障分布的组合；它是版本化工件，不是脚本里的常量 |
| 允许终态 | 一次任务被认为「完成」的所有合法结果，含成功、转人工、安全拒绝；只认成功会把正确的拒绝算成失败 |
| 入口 2xx | 网关返回成功，但任务可能仍在后台失败；用它代表可用性是最常见的假绿 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[grafana/k6](https://grafana.com/docs/k6/latest/)*

### 压测单位选错，后面每一个数字都在描述另一个系统

传统压测的单位是请求：QPS、请求延迟、请求成功率。Agent 系统的单位必须是任务：一个任务可能触发几十次模型调用与工具调用，耗时以分钟计。用请求做单位，测出来的是内部调用的性能，而用户感知的是任务的性能——两者可以完全脱钩。

更具体地说：一个 Agent 系统可以有很漂亮的单次调用延迟，同时任务完成时间长得不可接受，因为它调用了太多次。只看请求级指标，这个问题完全不可见。

「允许终态」是任务级建模的另一半。传统请求只有成功与失败两态，任务有更多：完成、部分完成、安全拒绝、转人工、达到上限终止。哪些算成功必须显式声明——把「转人工」算成失败会低估系统价值，算成成功会掩盖自动化率不足。

入口 2xx 与任务成功是两件事，这一条在 Agent 系统上尤其危险：提交任务的接口返回 202 之后，任务在后台可能失败、可能一直跑、可能悄悄终止。用入口状态码统计成功率，得到的是一个恒等于 100% 的漂亮数字。

*依据：[grafana/k6](https://grafana.com/docs/k6/latest/) · [langchain-ai/langgraph](https://langchain-ai.github.io/langgraph/)*

### 任务级 workload 必须分开建模的五个变量

五个变量各自独立变化，混在一起建模就得不到可复现的负载。第三列写的是不分开建模时会发生什么。

第五行常被忽略：不同任务类型的资源消耗可以相差一个数量级，用平均任务做压测会同时高估和低估。

| 变量 | 怎么建模 | 不分开建模的后果 | 工具 |
| --- | --- | --- | --- |
| 任务到达率 | 固定到达率（开放模型），不用固定并发 | 系统变慢时自动降压，看不到拐点 | k6 constant-arrival-rate |
| 任务复杂度分布 | 按真实分布混合简单与复杂任务 | 全用简单任务会严重高估容量 | 自建任务生成器 |
| 每任务调用次数 | 作为观测量而不是配置量 | 调用次数失控时表现为「变慢」，实际是循环 | trace 统计（OTel GenAI） |
| 允许终态集合 | 显式声明哪些终态算成功 | 转人工被算成失败或成功，两个方向都失真 | 工程约定 |
| 任务类型权重 | 按业务实际比例混合 | 用平均任务压测，同时高估简单场景与低估复杂场景 | 自建任务生成器 |

> 五个变量固定之后，一次 Agent 压测才是可复现的实验；否则每次跑出来的数字都在描述一个略微不同的系统。

*依据：[grafana/k6](https://grafana.com/docs/k6/latest/) · [langchain-ai/langgraph](https://langchain-ai.github.io/langgraph/) · [open-telemetry/semantic-conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/) · [locustio/locust](https://docs.locust.io/en/stable/)*

### 建 workload 时必须分开建模的六个变量

压测结论能不能用，取决于 workload 是否还原了真实分布。固定长度、单一任务类型的压测得到的容量数字，在生产上通常高估两到五倍。

下表左列是必须建模的变量，右列是省略它之后会得到的错误结论——每一条都在真实项目里发生过。

| 必须建模的变量 | 省略它会得到什么错误结论 |
| --- | --- |
| 任务类型混合比 | 只读查询和写操作混算，写操作的失败被大量查询稀释 |
| 输入 token 分布 | 按平均长度压测，p99 长上下文的显存与延迟完全没测到 |
| 输出 token 分布 | 输出长度可变是 Agent 与传统 API 最大的差别；固定输出等于没压 |
| 工具路径分布 | 只压最短路径，多跳路径的累积延迟与失败率不可见 |
| 允许终态集合 | 把「转人工」算作失败，得到一个悲观且无法行动的成功率 |
| 故障注入比例 | 没有故障的压测只能证明晴天可用 |

> 六个变量都要写进版本化 workload 文件并打 hash；换任一变量即视为换了一次实验。

*依据：[grafana/k6](https://grafana.com/docs/k6/latest/)*

### 这一页的验收口径：workload 本身的合格标准

本页不出性能结论，它出的是「性能结论的前提」。下面四条检查的是 workload 建得对不对，而不是系统跑得快不快。

AP01-4 是最容易被跳过的一条：把「转人工」「安全拒绝」算成失败，会得到一个悲观且无法行动的成功率。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| AP01-1 | 压测单位 | 以 task 为单位的压测占比 = 100%；以 request 为单位的容量结论数 = 0 | 每次压测 |
| AP01-2 | 分布还原度 | 输入输出长度的 p50/p90/p99 来自不少于 200 条生产采样；使用生成数据代替采样的次数 = 0 | 每次 workload 变更 |
| AP01-3 | 版本可复现 | workload 文件 hash 记录缺失率 = 0 | 每次压测 |
| AP01-4 | 终态定义完整 | 允许终态集合覆盖率 = 100%；未分类终态数 = 0 | 每次 workload 变更 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

*依据：[langchain-ai/langgraph](https://langchain-ai.github.io/langgraph/)*

### 两种看起来在压 Agent、实际在压网关的做法

下面两种做法都能跑出漂亮的 QPS 曲线，也都能通过评审。它们的问题不在执行，在于压测单位选错了。

遮住第三列先自己判断——判断不出来的那条，就是你下次压测最可能得到的假结论。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 用固定 Prompt 打入口接口，统计 QPS 与 p99 | 这是压测的标准做法，工具现成，数字稳定 | 入口返回 2xx 时任务可能还在后台跑。你测的是网关吞吐，不是任务完成能力。真正的分母是 good task 不是 request |
| 按平均输入输出长度构造请求，保证可比性 | 控制变量、结果可复现，符合实验规范 | Agent 的输出长度是长尾的。按均值压测时 KV Cache 与显存压力完全没出现，容量结论会高估到不可用 |

> 两条的共同根因是同一个：压测单位从 task 退化成了 request。

### 压测数字对不上生产时按什么顺序查

压测与生产不一致时，先查 workload 再查系统。多数情况下系统没问题，是实验设计与现实脱节。

一次只改一个变量，并把改动前后的 workload hash 都记进报告——否则你无法说清是哪一处让结论变了。

| 症状 | 先怀疑 | 下一步检查 |
| --- | --- | --- |
| 压测容量是生产的三倍 | 输入输出 token 分布 | 用生产采样重建长度分布再压一次 |
| 压测无错、生产大量超时 | 工具路径分布 | 把多跳路径按真实比例加入 workload |
| 成功率压测高、生产低 | 允许终态定义不一致 | 核对「转人工」「安全拒绝」在两边是否都算完成 |
| p99 压测好看、用户抱怨慢 | 压测单位是 request 不是 task | 改按任务端到端计时，含全部工具与重试 |
| 每次压测结果差异很大 | workload 未版本化 | 给 workload 打 hash，比较两次实验的差异字段 |

> 五行里有四行的根因在 workload 而不在被测系统——这就是为什么它必须是第一页。

### 用一份真实采样重建 workload：约 40 分钟

这一页不需要压测工具。你需要的是一份生产采样和一张纸——先把分布还原对，压测工具才有意义。

1. 从生产日志或 trace 里随机抽 200 条真实任务，只抽不改。
2. 逐条记录五项：任务类型、输入 token、输出 token、工具调用次数、最终终态。
3. 算出任务类型混合比、输入输出长度的 p50/p90/p99、工具跳数分布，并列出全部出现过的终态。
4. 把「转人工」「安全拒绝」这类终态单独标出来，明确它们算完成还是算失败，并写下这个判断的 owner。
5. 把上述结果写成一个 workload JSON 并打 sha256；这个 hash 从此进入每一份性能报告。

**期望结果**：你会得到一份带 hash 的 workload 文件，以及一个通常令人意外的发现：输出长度的 p99 往往是 p50 的数倍，而此前的压测一直按 p50 在跑。

> ⚠ 不要用模型生成「典型任务」来代替采样。生成的分布会向中间集中，恰好抹掉最贵的那条尾巴。

### 这一页的出口判据

这道门禁在压测开始之前执行。workload 不合格时，后面跑出来的所有数字都没有解释框架，重跑的成本远高于事前检查。

第三段要接受的是合成与真实之间的距离——它永远不为零，能做的是把它估出来并写进报告。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | workload 文件 hash 缺失率 > 0 时阻断压测<br>未分类终态数 > 0 时阻断，成功率的分母未定义即无法出结论 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 长度分布以 p50/p90/p99 描述，禁止用均值代表分布<br>采样样本 < 200 条任务时分布还原结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 合成 workload 与生产分布的已知差距，由容量 owner 估计并签字接受<br>「转人工」「安全拒绝」是否计入完成，由业务 owner 确定并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一份可以被别人复现的 workload

workload 文件的价值不在于精确，而在于可被质疑：别人看到 hash 和字段，就能说出你的结论适用于什么、不适用于什么。

没有 workload hash 的性能数字不可复用——半年后没人能说清那次压测到底压的是什么。

- 用 200 条真实采样重建分布，不要用生成数据
- 把允许终态写清楚并指定判断 owner
- 给 workload 打 hash 并写进每份性能报告
