## TD-AP06

### 跨层重试会把一次抖动放大成副作用事故

gateway、SDK、Agent 和 tool 各自设置重试时，局部恢复可能换来全局雪崩；写工具还会重复产生不可逆副作用。

预算必须在 task 层统一核算，并为超预算定义可审计的安全终态。

| 失效组合 | 表面收益 | 实际风险 |
| --- | --- | --- |
| 四层各重试 3 次 | 短时成功率提高 | 最坏 81 倍调用放大 |
| 所有超时都 30 秒 | 配置简单 | 全链路统一 30 秒会让下游超时晚于上游，上游已放弃而下游仍在计费；这段浪费的算力占比不为 0 |
| 写工具无幂等键 | 失败可再试 | 写工具无幂等键时，重试必然导致副作用重复执行，1 次重复即构成业务事故 |
| 降级只返回错误 | 实现省事 | 降级只返回错误等于没有降级；可用性在依赖故障期间直接降到 0，而只读或转人工本可保住一部分 |

> 先算预算和副作用，再谈可靠性。

### 超时与重试的四个词

多层重试是 Agent 延迟失控最常见的原因。下面四个词决定你能不能把它算清楚。

| 术语 | 一句话解释 |
| --- | --- |
| 总 deadline | 一次任务允许的最长时间；所有层的超时之和必须小于它，否则外层永远等不到内层结束 |
| 重试预算 | 一次任务允许的重试总次数；它是任务级的，不是每层各自的 |
| 重试放大 | 网关、SDK、Agent、Tool 各自重试三次，最坏情况是 81 次调用 |
| 安全降级 | 超预算时的可接受终态，如只读结果、转人工、明确拒绝；它不是失败 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[App-vNext/Polly](https://www.pollydocs.org/)*

### 跨层重试会把一次抖动放大成事故

重试放大是一个纯粹的乘法问题：如果客户端重试 3 次、网关重试 2 次、SDK 重试 2 次、Agent 编排层再重试 2 次，那么一次用户请求在最坏情况下会变成 24 次下游调用。这个倍数在正常时不可见，在下游抖动时全部释放出来——正好在系统最脆弱的时刻施加最大压力。

各层独立配置重试是这个问题的根源，而它非常难被发现，因为每一层单独看都很合理：「重试 3 次」听起来是个保守配置。只有把整条链路的重试次数相乘，问题才显现出来。

解决办法是重试预算而不是重试次数：整条链路共享一个预算，通常表述为「重试请求不得超过总请求的 X%」。预算耗尽后直接失败，不再重试。这样在故障期间重试量有上界，不会随失败率线性增长。

总 deadline 是另一半：一个请求从入口开始就有一个绝对截止时间，每一层的超时都从剩余时间里扣。这样即使某层配置错误，也不会出现「调用方已放弃、被调用方还在算」的资源浪费——在按 token 计费的场景里，这直接对应账单。

*依据：[App-vNext/Polly](https://www.pollydocs.org/) · [resilience4j/resilience4j](https://resilience4j.readme.io/docs)*

### 四层重试如果各自独立，最坏会放大多少

这张表的用途是做一次实际的乘法。把你系统里每一层的重试次数填进去，看看最坏倍数是多少——多数团队第一次算完会感到意外。

最后一列是修法，四行的修法合起来就是「预算 + deadline」这两件事。

| 层级 | 典型配置 | 对总倍数的贡献 | 修法 |
| --- | --- | --- | --- |
| 客户端 SDK | 自动重试 2～3 次，常为默认值且不易察觉 | ×2～3 | 显式关闭或纳入统一预算 |
| 网关 / 服务网格 | 重试 1～2 次 | ×2～3 | 只对幂等方法重试，且带预算 |
| 应用层弹性库 | 重试 3 次 + 退避 | ×3 | 改为预算制，按比例限制 |
| Agent 编排层 | 步骤失败重试 2 次，且会重放整条工具链 | ×2，且每次代价最高 | 不可逆动作禁止重试，其余走总预算 |

> 四行相乘就是最坏放大倍数。把它算出来贴在架构图旁边，是这一页最便宜也最有效的产出。

*依据：[App-vNext/Polly](https://www.pollydocs.org/) · [resilience4j/resilience4j](https://resilience4j.readme.io/docs) · [Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/) · [Shopify/toxiproxy](https://github.com/Shopify/toxiproxy#readme)*

### 四层重试如果各自独立，最坏会放大多少

每一层的重试策略单独看都合理，叠加之后就成了乘法。这不是假设——这是重试相关事故的标准剧本。

右列写的是把它算清楚之后的正确做法：预算在任务级统一分配，不在各层各自设定。

| 层 | 单层重试 | 独立设定的后果 | 正确做法 |
| --- | --- | --- | --- |
| 网关 | 3 次 | × 3 | 只做一次，或不做 |
| SDK | 3 次 | × 9 | 关闭或纳入总预算 |
| Agent | 3 次 | × 27 | 从任务级预算中扣减 |
| Tool | 3 次 | × 81 | 按依赖幂等性单独授权 |

> 81 这个数字不是极端假设，它是四层各自「合理」设置三次的直接结果。

*依据：[resilience4j/resilience4j](https://resilience4j.readme.io/docs)*

### 这一页的验收口径：预算归口与降级可用

AP06-1 检查的是预算有没有归口：各层各自重试三次，实际总重试次数是乘积而不是和，这是超时链最常见的失控方式。

AP06-3 为每条降级路径设质量下限，防止降级变成「悄悄给出更差的结果而没人知道」。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| AP06-1 | 预算归口 | 各层重试计入同一任务预算的比例 = 100%；独立计数的层数 = 0 | 每次配置变更 |
| AP06-2 | deadline 单调 | 内层 deadline 均短于外层的比例 = 100%；被重置的次数 = 0 | 每次配置变更 |
| AP06-3 | 降级质量下限 | 每条降级路径定义并实测质量下限；未定义下限的路径数 = 0 | 每次发布 |
| AP06-4 | 不可逆保护 | 不可逆动作在无幂等键情况下发生重试的次数 = 0 | 每次发布 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在提高可靠性、实际在制造事故的配置

这两种配置都能在短期内让成功率上升，也都很难在评审中被否决。

它们的代价要到一次高峰或一次依赖抖动时才会显现。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 每层都加重试，成功率从 92% 提到 98% | 重试是标准容错手段，数字也确实改善了 | 四层独立重试最坏放大 81 倍。依赖抖动时它会把一次小故障放大成雪崩，而且非幂等工具会产生重复副作用 |
| 超时统一设为 30 秒，简单一致 | 统一配置便于维护，也留足了余量 | 外层 30 秒、内层也 30 秒时，外层永远等不到内层的超时结果。超时必须逐层递减，且总和小于任务 deadline |

> 两条的共同要求是同一件事：把超时与重试当成任务级预算来分配。

### 压力下延迟或副作用异常时按什么顺序查

重试相关的故障有一个特征：平时完全正常，一旦依赖变慢就急剧恶化。

查的时候先算最坏放大倍数，再看幂等保护。

| 症状 | 先怀疑 | 下一步检查 |
| --- | --- | --- |
| 依赖稍慢就雪崩 | 多层重试放大 | 算最坏倍数，把预算收到任务级 |
| 出现重复副作用 | 非幂等工具被重试 | 检查幂等键与重试授权 |
| 外层超时从不触发 | 超时未逐层递减 | 让内层超时明显小于外层 |
| 降级后用户看到报错 | 降级终态未定义 | 把只读/转人工/拒绝定义为合法终态 |
| 成功率高但成本翻倍 | 重试吃掉了预算 | 把重试成本单列进成本报告 |

> 第四行是体验问题也是数据问题：降级被算成失败时，SLI 会低估系统的真实可用性。

### 给一条任务链算一次重试预算：约 35 分钟

这一步是算术，不是压测。把四层配置抄下来相乘，多数团队会在这一步发现问题。

1. 把网关、SDK、Agent、Tool 四层的重试次数与超时值分别抄下来，注明配置在哪里。
2. 相乘得到最坏调用次数，再乘以单次耗时上界，得到最坏总时长。
3. 把最坏总时长与任务 deadline 比较。超出的部分就是当前配置下必然发生的超时。
4. 逐层检查超时是否递减，且总和小于 deadline；不满足的层列为待修。
5. 为每个可写工具确认幂等键存在，并明确它是否允许被自动重试；不允许的必须在重试层排除。

**期望结果**：多数团队第一次算完会发现最坏调用次数在两位数以上，且至少有一层的超时没有递减。这两项都是可以当天提交的修复。

> ⚠ 不要用「实际上很少同时重试」来跳过这个计算。重试放大恰恰在依赖抖动时同时发生，那正是你最需要它不发生的时刻。

### 这一页的出口判据

这道门禁依赖故障注入。一个从未被触发过的降级路径，与不存在的降级路径在工程上等价。

第三段要接受的是降级带来的体验损失——每条降级路径都意味着用户拿到的东西变差了。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 不可逆动作在无幂等键情况下重试的次数 > 0 时阻断<br>内层 deadline 长于外层的配置项数 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 降级路径质量下限按 95% CI 下界与阈值比较<br>故障注入样本 < 30 次时该故障类型结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 三重预算的具体取值，由业务 owner 签字确定<br>各降级路径的质量下限与体验后果，由产品 owner 知情接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)*

### 带走一张任务级的超时与重试预算表

预算表要写清每一层分到多少次重试、多少秒超时，以及超预算后进入哪个降级终态。

把降级终态写清楚同样重要——否则安全降级会被 SLI 算成失败，团队就会去掉降级。

- 重试预算在任务级统一分配，不在各层各设
- 超时逐层递减且总和小于 deadline
- 把只读、转人工、拒绝定义为合法终态
