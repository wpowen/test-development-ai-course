## TD-AP08

### 把压测结论留在报告里，它三个月后就只是一份归档文件

性能工作最常见的终点是一份 PDF。它无法在凌晨三点告诉值班的人该做什么，也无法阻止同一个问题下个季度再来一次。

下面三条是性能结论没有接进运行时的后果。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| SLI 用请求成功率而不是 good task | 入口成功率可以在任务大量失败的情况下保持 99%以上，两者的差额就是被掩盖的失败 | SLO 长期达标，用户投诉持续存在 |
| 只有单窗口告警 | 单窗口要么太灵敏产生大量误报，要么太迟钝错过快速烧尽；多窗口 burn-rate 才能同时覆盖这 2 种情况 | 告警要么被静音，要么在错误预算已经烧完之后才响 |
| 事故没有回流成 workload | 未回流的事故场景在下次压测中的覆盖率为 0，同类问题会原样复发 | 每次事故都当成新问题重新排查一遍 |

> 本页的做法：以 good task 为 SLI，多窗口 burn-rate 告警接 runbook，事故回流成 workload 与回归。

### SLO 与告警的四个词

性能工作的最后一步是让数字变成可执行的响应。下面四个词决定告警是有用还是被静音。

| 术语 | 一句话解释 |
| --- | --- |
| SLI | 服务质量指标；Agent 场景应以 good task 为分子，而不是 HTTP 成功率 |
| 错误预算 | 允许违反 SLO 的额度；它把「要不要发布」从争论变成算术 |
| Burn rate | 错误预算的消耗速率；多窗口组合可以同时兼顾快响应与低误报 |
| 止血 vs 修复 | 先恢复用户可用性，再定位根因；两者的 owner 与时限不同 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)*

### 把压测结论留在报告里，它三个月后就只是一份归档文件

压测得到的容量拐点、瓶颈位置、重试放大倍数，如果只写进报告，会在下一次架构变更后静默失效——而没有人会因此收到通知。让它持续有效的唯一办法，是把结论转成线上的 SLO 与告警。

SLI 的选择必须与压测时用的指标一致。压测量的是任务级 goodput，线上却只监控请求级成功率，两者对不上，压测结论就无法验证也无法维持。这个断层非常常见，因为压测和监控通常由不同的人做。

错误预算把「达没达标」变成了「还剩多少可以花」。它的实际作用是给发布节奏提供一个客观依据：预算充足时可以激进发布，预算见底时冻结变更。没有它，发布节奏只能靠争论决定。

多窗口 burn-rate 告警解决的是单阈值告警的两难：阈值紧则误报多、会被静音，阈值松则事故已经发生才响。多窗口的做法是同时看短窗口与长窗口的预算消耗速率，两者同时超标才告警——快速大量消耗立刻响，缓慢持续消耗也不会漏。

*依据：[Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/) · [prometheus/prometheus](https://prometheus.io/docs/practices/histograms/)*

### 把压测结论转成线上告警的四个环节

四个环节按顺序执行。跳过第一环直接配告警，会得到一组与压测结论无关的阈值，两边各说各话。

第三列是这一环最容易出错的地方，全部来自实际发生过的失败模式。

| 环节 | 做什么 | 最容易出错的地方 | 工具 |
| --- | --- | --- | --- |
| SLI 对齐 | 线上监控的指标与压测用的指标保持同一口径 | 压测量任务级、线上监控请求级，两边对不上 | OTel + Prometheus |
| SLO 定阈值 | 阈值来自业务承受度与压测拐点，不用工具默认值 | 照抄示例数字，等于没有校准 | SRE Workbook 框架 |
| 错误预算 | 把达标与否变成「还剩多少可花」，绑定发布节奏 | 算出来了但不与发布决策挂钩，等于没算 | 预算计算 + 发布流程 |
| 多窗口 burn-rate 告警 | 短窗口与长窗口同时超标才告警 | 单阈值告警要么误报被静音，要么太晚才响 | Prometheus 多窗口规则 |

> 四环做完，压测就从一次性活动变成了持续生效的约束——这是这一页与前七页的关系。

*依据：[Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/) · [prometheus/prometheus](https://prometheus.io/docs/practices/histograms/) · [open-telemetry/opentelemetry-specification](https://opentelemetry.io/docs/specs/otel/) · [argoproj/argo-rollouts](https://argo-rollouts.readthedocs.io/)*

### 多窗口 burn-rate 告警怎么配才不会被静音

单窗口告警只能二选一：要么漏报慢烧，要么在抖动时狂响。多窗口组合是为了同时避免这两件事。

右列写的是每条告警对应的响应动作——没有动作的告警最终一定会被静音。

| 窗口组合 | 捕捉什么 | 响应动作 |
| --- | --- | --- |
| 短窗 + 长窗，高倍率 | 突发严重故障 | 立即止血，考虑回滚 |
| 中窗 + 长窗，中倍率 | 持续劣化 | 当班排查，准备降级 |
| 长窗，低倍率 | 缓慢消耗 | 排期修复，不打断当班 |
| 预算耗尽 | 本周期已超支 | 冻结高风险发布 |

> 每一行都必须有具名 owner 与时限；没有 owner 的告警在第三次响起后就会被关掉。

*依据：[Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)*

### 这一页的验收口径：SLI 定义与闭环率

AP08-1 决定了整套 SLO 有没有意义：分子用 good task 还是用入口 2xx，会得到差距很大的两个数字。

AP08-4 的事故回流率是本模块的收口指标——它衡量的是这套性能工程有没有在积累资产。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| AP08-1 | SLI 分子定义 | 以 good task 定义 SLI 的比例 = 100%；以入口 2xx 定义的 SLI 数 = 0 | 每次 SLO 变更 |
| AP08-2 | 告警窗口 | 同时配置快窗与慢窗 burn-rate 告警的 SLO 比例 = 100% | 每次 SLO 变更 |
| AP08-3 | 告警可动作 | 每条告警绑定 runbook 与具名责任人的比例 = 100%；无处置动作的告警数 = 0 | 每月 1 次 |
| AP08-4 | 事故回流 | 性能事故回流成 workload 或回归用例的比例 = 100%；未回流即事故不得关闭 | 每次事故 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来监控完善、实际不响或响个不停的配置

这两种配置在监控评审时都很难被质疑：一个覆盖全，一个响应快。

它们的失效方式相反，但根因相同——SLI 的分子选错了。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 用 HTTP 5xx 率作为 SLI，超过阈值告警 | 这是最标准的可用性指标，工具原生支持 | Agent 任务失败时接口往往返回 200。用 5xx 做 SLI 会让最典型的失败完全不告警。分子必须是 good task |
| 把告警阈值调低以便早发现问题 | 早发现是监控的目的，调低更敏感 | 低阈值在正常抖动时频繁触发。三次误报之后告警会被静音，然后真故障也不会响。用多窗口 burn-rate 替代单一低阈值 |

> 告警的可用性不取决于灵敏度，取决于每次响起时人知道该做什么。

### 事故复盘时按什么顺序检查告警链

复盘的目的不是追责，是找出这次为什么没有被更早发现。按下表逐项走一遍，每一项都对应一个具体改进。

把改进写成回归资产——性能事故也要走 Trace-to-Regression。

| 复盘问题 | 检查什么 | 改进方向 |
| --- | --- | --- |
| 为什么没告警 | SLI 分子是否为 good task | 改用任务级 SLI |
| 为什么告警晚 | 窗口组合是否缺短窗 | 补短窗高倍率规则 |
| 为什么没人响应 | 是否有具名 owner 与时限 | 补 owner 与升级路径 |
| 为什么止血慢 | 降级与回滚是否演练过 | 把演练列入发布准出 |
| 为什么复发 | 是否补了回归用例 | 把事故样例回流为固定回归 |

> 第五行最容易被跳过：性能事故往往只修配置不补回归，于是半年后同样的高峰再来一次。

### 给一次真实事故补完告警链：约 40 分钟

挑一次最近的性能事故，按复盘表逐项走一遍。不需要工具，需要的是事故当时的时间线。

1. 还原时间线：用户首次受影响、监控首次异常、告警首次触发、人首次响应、止血完成、恢复完成，各记时刻。
2. 计算三个差值：受影响到告警、告警到响应、响应到止血。哪一个最大，改进就先做哪一个。
3. 检查当时的 SLI 分子是不是 good task。如果是 HTTP 成功率，这就是「为什么没告警」的答案。
4. 为每条告警补上具名 owner、响应时限与升级路径，并删掉没有响应动作的告警。
5. 把这次事故的输入与版本做成一条固定回归用例，并在下一次发布前跑一遍。

**期望结果**：产出是一份带三个时间差的复盘表加一条新增回归用例。三个差值里最大的那个，就是下个季度最值得投入的方向。

> ⚠ 不要在复盘中把「监控没覆盖到」当作结论。它是症状；结论应当是具体哪个 SLI 的分子选错了，或者哪个窗口缺失。

### 这一页的出口判据

这是 TD-M11 的出口门禁：它判断的是这套性能工程有没有接进运行时，而不是某一次压测跑得好不好。

第三段要接受的是 SLO 目标值本身——它是业务承诺，不是技术推导出来的数字。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 以入口 2xx 定义的 SLI 数 > 0 时阻断，须改用 good task<br>未回流成 workload 或回归用例的性能事故关闭数 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | SLI 按风险切片分别统计并给出 95% CI，禁止只报整体<br>观测样本不足以支撑 SLO 判定时结论为「证据不足」，不得记为达标 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | SLO 目标值与错误预算大小，由产品 owner 签字确定<br>暂不纳入 SLI 的任务类型，由容量 owner 列出并接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[prometheus/prometheus](https://prometheus.io/docs/practices/histograms/)*

### 带走一份 SLO 与事故 Runbook

Runbook 的价值在凌晨三点体现：当班的人能不能在不理解全系统的情况下完成止血。

所以每条告警旁边必须写清第一个动作是什么，而不是写它意味着什么。

- SLI 用 good task 做分子，不用 HTTP 成功率
- 多窗口 burn-rate 替代单一低阈值
- 每条告警有具名 owner、时限与第一个动作
