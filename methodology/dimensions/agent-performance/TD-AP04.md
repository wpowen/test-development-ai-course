## TD-AP04

### 协调遗漏会把排队时间藏起来

闭环压测变慢后自动少发请求，报表仍可呈现漂亮的 p99；这不是系统变快，而是最坏样本没有进入分母。

open 与 closed 必须使用同一 workload 和截止时间，差异才可归因到到达模型。

| 错误口径 | 假象 | 必须补的证据 |
| --- | --- | --- |
| 按实际发出计时 | 延迟稳定 | 系统变慢时闭环自动降速，排队时间被折叠进「没发出去的那段」，实测排队 p99 可被低估数倍 |
| 只报 achieved rate | 吞吐看似饱和 | 只报实际达成速率会掩盖计划到达与实际完成的差额；这个差额就是协调遗漏，实测中它可占计划量的 10% 以上 |
| 隐藏压测端队列 | 服务端无排队 | 压测端自身排队时，被测系统看到的到达率低于设定值；偏差超过 2% 即说明测的是压测端不是被测系统 |
| 用 closed 承诺 SLO | p99 偏乐观 | open 模式的截止时间分布 |

> 遗漏样本本身就是性能证据。

### 开环、闭环与协调遗漏

这一页只讲一件事：你的压测工具在系统变慢时会不会自动降速。会，就测不出真实延迟。

| 术语 | 一句话解释 |
| --- | --- |
| 闭环负载 | 固定并发数，前一个请求完成后才发下一个；系统变慢时发压速率自动下降 |
| 开环负载 | 固定到达率，不管系统是否处理得完；它才能还原真实用户不会因为你慢就少来的事实 |
| 协调遗漏 | 闭环压测在系统变慢时少发了请求，最坏的那批延迟从未被记录 |
| 计划到达 vs 实际完成 | 前者是应当发出的时刻，后者是实际结束的时刻；两者差值才是用户真正的等待 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[grafana/k6](https://grafana.com/docs/k6/latest/)*

### 协调遗漏会把排队时间从报告里抹掉

闭环负载生成器（固定并发的虚拟用户）有一个内建缺陷：它只在上一个请求返回之后才发下一个。系统变慢时，它自动发得更少——于是真实的到达压力从未施加，排队从未形成。

协调遗漏（coordinated omission）是这个缺陷在指标上的表现：本该在第 1 秒发出的请求因为上一个还没回来，实际在第 3 秒才发出，于是它「等待」的那 2 秒完全没有被计入延迟。报告里的 p99 因此系统性偏低，而且偏低的幅度在系统承压时最大。

修正办法有两条。一是改用开环模型（固定到达率），让请求按计划时间发出，不受系统响应影响；二是如果必须用闭环，则按「计划到达时刻」而不是「实际发出时刻」计算延迟，把被吞掉的等待补回去。

这一条在 Agent 系统上尤其致命，因为任务耗时以分钟计，闭环模型下的到达率坍塌会非常严重——你以为在压 10 任务/分钟，实际只压了 2。据此得出的容量结论会高估系统能力好几倍。

*依据：[grafana/k6](https://grafana.com/docs/k6/latest/) · [Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)*

### 两种负载模型在同一个 workload 上的差别

同一套任务、同一个系统，两种负载模型会给出完全不同的结论。这张表把差别列出来，用途是识别别人的压测报告用的是哪一种。

第四列是判断依据：拿到一份压测报告时，先问这三个问题，就能知道结论能不能用。

| 维度 | 闭环（固定并发） | 开环（固定到达率） | 怎么判断报告用了哪种 |
| --- | --- | --- | --- |
| 到达压力 | 随系统变慢自动下降 | 不受系统影响，按计划施加 | 问：系统变慢时到达率变了吗 |
| 排队现象 | 几乎不形成，被自我调节掉 | 真实形成，可观测队列增长 | 问：报告里有队列长度曲线吗 |
| 延迟统计 | 协调遗漏，p99 系统性偏低 | 包含完整等待时间 | 问：延迟从计划时刻算还是发出时刻算 |
| 容量拐点 | 曲线平缓，看不到拐点 | 拐点清晰可见 | 问：有没有压到失败为止 |
| 适用场景 | 已知并发上限的内部系统 | 面向用户的服务、容量规划 | —— |

> 闭环不是错的，它只是回答另一个问题。错在于用闭环结果回答容量问题，而这是绝大多数压测报告在做的事。

*依据：[grafana/k6](https://grafana.com/docs/k6/latest/) · [locustio/locust](https://docs.locust.io/en/stable/) · [Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/) · [prometheus/prometheus](https://prometheus.io/docs/practices/histograms/)*

### 这张图的 6 个节点，本页各交付什么

这张图并排画了两个调度器：开环按固定到达率发，闭环等前一个返回再发下一个。同一个系统在两者下会给出不同结论。

本页要证明的正是这一点——如果只用闭环压测，系统变慢时压测端会自动降速，最严重的排队问题永远不会出现在报告里。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 固定 workload | 两个调度器使用完全相同的 workload，保证差异只来自调度方式 | 共享 workload hash |
| Open arrival scheduler | 按固定到达率发起，不受系统响应影响 | 开环压测结果 |
| Closed VU scheduler | 固定并发数，前一个完成才发下一个 | 闭环压测结果 |
| 同一 Agent fixture | 被测侧完全一致，排除自身漂移 | 被测配置快照 |
| 计划/实际到达记录 | 同时记录计划到达与实际完成，差额即协调遗漏 | 协调遗漏度量 |
| Queue/Goodput 对照 | 对照两种调度下的排队与有效产出，得出结论适用范围 | 开闭环对照报告 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 同一 workload 在两种负载模型下的差别

同一份 workload，用闭环和开环各压一次，得到的结论可以差一个数量级。这不是工具误差，是模型选择。

右列是两种模型各自能回答的问题——它们不能互相替代，也不能只跑一种。

| 对比项 | 闭环（固定并发） | 开环（固定到达率） |
| --- | --- | --- |
| 系统变慢时 | 发压自动降速 | 到达率不变，队列堆积 |
| 能回答的问题 | 系统在这个并发下的表现 | 系统在这个流量下会不会崩 |
| 延迟统计 | 被协调遗漏污染，偏乐观 | 接近真实用户感知 |
| 适合场景 | 容量摸底、瓶颈定位 | SLO 验证、容量规划 |
| 典型误用 | 用它得出的 p99 去承诺 SLO | 用它做长稳测试导致成本失控 |

> 两种都要跑。只跑闭环会低估延迟；只跑开环会难以定位瓶颈。

*依据：[grafana/k6](https://grafana.com/docs/k6/latest/)*

### 这一页的验收口径：两种负载都要跑

AP04-1 要求两种调度都执行。只做一种时，你无法知道自己看到的是系统的真实表现还是压测端的自我限速。

AP04-2 的协调遗漏量是本页的核心产物：计划到达与实际完成之间的差额，直接说明闭环结论被低估了多少。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| AP04-1 | 双调度覆盖 | 同一 workload 下开环与闭环均执行的比例 = 100%；仅做闭环的容量结论数 = 0 | 每次容量评估 |
| AP04-2 | 协调遗漏量 | 报告给出计划到达与实际完成的差额；未量化该差额的报告数 = 0 | 每次压测 |
| AP04-3 | 压测端自身瓶颈 | 压测端实际发出速率与设定速率偏差 ≤ 2% | 每次压测 |
| AP04-4 | 结论适用范围 | 报告声明该结论适用于开环还是闭环的比例 = 100% | 每次报告 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来严谨、实际低估延迟的压测

这两种做法都出现在标准压测教程里，也都能产出可复现的报告。

它们的问题只在一个地方：延迟统计的起点选错了。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 用 100 并发压测，统计每个请求的响应时间 | 并发数明确、结果稳定、可复现 | 系统变慢时压测工具自动少发了请求，最坏的那批延迟根本没产生。这就是协调遗漏，p99 会被系统性低估 |
| 延迟从请求发出时刻开始计时 | 这是响应时间的标准定义 | 应该从「计划到达时刻」开始计。请求在压测工具的发送队列里等了 3 秒，用户是要算进等待的 |

> 两条都指向同一件事：把压测工具自己的排队算进用户等待。

*依据：[locustio/locust](https://docs.locust.io/en/stable/)*

### 压测延迟明显好于生产时按什么顺序查

这类差异九成来自负载模型而不是环境差异。先排除协调遗漏，再考虑硬件与网络。

确认方法很简单：把同一份 workload 用开环重跑一次，看 p99 是否显著上升。

| 症状 | 先怀疑 | 下一步检查 |
| --- | --- | --- |
| 压测 p99 远好于生产 | 闭环协调遗漏 | 改开环固定到达率重跑 |
| 压到某点后延迟不再上升 | 发压端已成瓶颈 | 检查压测机的 CPU 与连接数 |
| 延迟分布异常集中 | 从发出时刻计时 | 改从计划到达时刻计时 |
| 加并发吞吐不涨 | 系统已过拐点 | 看队列深度与超时丢弃率 |
| 两次压测差异大 | 到达模式不同 | 固定为泊松或阶梯并记录 |

> 第二行值得单列：压测机本身成为瓶颈时，所有结论都是关于压测机的。

### 用同一 workload 跑开闭环对照：约 45 分钟

不需要新工具。多数压测框架同时支持两种模式，关键是把两次的延迟统计口径对齐。

1. 取上一页产出的 workload 文件，确认 hash 一致——两次实验必须压同一份负载。
2. 第一轮闭环：固定并发数，记录 p50/p95/p99 与吞吐。
3. 第二轮开环：把第一轮的实际吞吐作为固定到达率，记录同样的分位数。
4. 两轮的延迟统计都改成从「计划到达时刻」开始计，而不是从请求发出时刻。
5. 比较两轮 p99 的差值。差值越大，说明此前的闭环结论被协调遗漏污染得越严重。

**期望结果**：典型结果是开环 p99 显著高于闭环。这个差值就是你此前的 SLO 承诺被高估的幅度。

> ⚠ 开环压测在系统已过拐点时会迅速堆积，务必设总时长与队列上限，否则会把测试环境压垮。

### 这一页的出口判据

这道门禁拦的是「只跑了闭环就下容量结论」。这类结论在报告里最常见，也最容易在真实峰值到来时被推翻。

第三段要接受的是两种结论的差距——它通常不小，选用哪一个作为容量承诺是业务决策。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 仅做闭环压测即给出容量承诺的次数 = 0，违反即阻断<br>压测端发出速率与设定值偏差 > 5% 时阻断，先修压测端 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 开闭环结果分别给出 95% CI，禁止合并成单一容量数字<br>单调度方式样本 < 500 个任务时该结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 作为容量承诺采用的调度方式，由容量 owner 选定并署名<br>两种调度结论之间的差距，由产品 owner 在知情前提下接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一份开闭环对照报告

报告的核心不是两个数字，而是它们的差值——那是你的 SLO 承诺此前被高估的幅度。

此后所有对外的延迟承诺都应基于开环结果，闭环结果只用于内部瓶颈定位。

- 同一 workload hash 跑两种负载模型
- 延迟从计划到达时刻开始计
- 对外承诺用开环，定位瓶颈用闭环
