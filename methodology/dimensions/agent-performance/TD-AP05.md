## TD-AP05

### 没有首个失败门禁就没有容量结论

最大吞吐、goodput 和 SLO 容量回答的是不同问题。把它们混成一个数字，会让后续扩容和上线决策失去边界。

容量卡先锁定负载、版本和 SLO，再找第一个失败台阶，最后才讨论瓶颈归因。

| 错误结论 | 为什么诱人 | 修正后的证据 |
| --- | --- | --- |
| 120 task/min 就是容量 | 曲线有最高点 | 单点数字无法说明是拐点还是平台期；至少需要 3 个相邻压力档位才能判断曲线形状 |
| synthetic goodput 可上线 | 主要路径已覆盖 | 合成 workload 与真实流量存在分布差距，synthetic goodput 只能用于横向比较；把它当生产容量承诺时高估 2～5 倍是常见结果 |
| TTFT 上升等于模型瓶颈 | 模型指标最显眼 | TTFT 上升有排队、prefill、准入 3 个可能来源，不分段时归因正确率接近随机 |
| 一次优化后拐点右移 | 结果变好了 | 一次优化后拐点右移，但若 workload hash 变了则两次不可比；变更字段数必须为 0 才能直接对比 |

> 容量是带条件的实验结论，不是服务固有属性。

### 容量相关的四个词

「能扛多少」这个问题有四种不同答案，取决于你用哪个量作为容量定义。

| 术语 | 一句话解释 |
| --- | --- |
| SLO 拐点 | 延迟或成功率开始违反 SLO 的那个负载点；容量指的是它，不是最大吞吐 |
| Synthetic goodput | 合成负载下满足 SLO 的成功任务吞吐；它只对这份合成负载成立 |
| prefill / decode | 首 token 前的上下文处理阶段与逐 token 生成阶段；两者的瓶颈完全不同 |
| 阶梯加压 | 按台阶逐级提升负载并在每级稳定观察；比连续加压更容易定位拐点 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[vllm-project/vllm](https://docs.vllm.ai/)*

### 没有首个失败门禁，就没有容量结论

容量结论的形式必须是「在 X 到达率下，第一个越线的是 Y 指标」。只说「压到 X 没问题」是不完整的：不知道余量多少，也不知道超过之后先坏哪里——而这两件事决定了扩容策略与告警设置。

阶梯加压是取得这个结论的标准做法：逐级提高到达率，每级稳定运行足够长时间，记录全部指标，直到某个 SLO 被突破。突破的那个指标就是「首个失败门禁」，它指出了当前架构的瓶颈所在。

Agent 系统的瓶颈信号分布在五个位置，而且它们的出现顺序本身就是信息：如果先崩的是 KV 缓存，说明上下文长度是瓶颈；先崩的是工具下游，说明 Agent 的调用放大倍数太高；先崩的是编排层，说明状态持久化成为热点。三种情况的扩容方案完全不同。

synthetic goodput 是 Agent 场景下的必要修正：任务级的有效吞吐必须扣掉那些「完成了但结果不可用」的任务——达到步数上限被截断的、降级到人工的、超出 SLO 才完成的。不扣掉这部分，容量数字会包含大量无效产出。

*依据：[vllm-project/vllm](https://docs.vllm.ai/) · [grafana/k6](https://grafana.com/docs/k6/latest/)*

### 五类瓶颈信号与它们指向的扩容方向

阶梯加压时先崩的那一个决定了下一步该做什么。这张表把信号与动作对应起来，避免默认「加机器」。

第四列的成本差异很大，而最贵的那个（换模型或加卡）常常是最先被提出来的。

| 瓶颈信号 | 先出现的现象 | 指向的瓶颈 | 扩容方向 |
| --- | --- | --- | --- |
| 排队时间上升 | 队列长度线性增长，计算时间不变 | 实例数不足 | 水平扩容（成本最低） |
| KV 缓存抢占计数上升 | 延迟突发长尾，伴随重算 | 上下文长度或并发上限 | 限制上下文、调并发上限 |
| 工具下游错误率上升 | Agent 本身正常，下游 429/超时 | 调用放大倍数过高 | 减少调用次数、加缓存、下游扩容 |
| 编排层延迟上升 | span 间空隙变大，状态存储变慢 | checkpoint 与状态持久化成热点 | 降低 checkpoint 频率、换存储 |
| decode 速度下降 | TPOT 与并发正相关 | 批内竞争 | 限并发、隔离长任务 |

> 五行按扩容成本从低到高排列。先确认不是前两行，再考虑后面的方案。

*依据：[vllm-project/vllm](https://docs.vllm.ai/) · [sgl-project/sglang](https://docs.sglang.ai/) · [grafana/k6](https://grafana.com/docs/k6/latest/) · [prometheus/prometheus](https://prometheus.io/docs/practices/histograms/)*

### 这张图的 6 个节点，本页各交付什么

这张图从阶梯到达率进入，沿准入、调度、模型、工具四段观测，最后到 Goodput 门禁。瓶颈必须落在中间四段的某一段上。

找拐点的方法是逐级加压直到失效，而不是压到目标值就停——压到目标只能证明目标达成，证明不了余量还有多少。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 阶梯到达率 | 逐级加压并在每档保持足够时长，至少覆盖 3 个相邻档位 | 压力阶梯设计 |
| Admission/Queue | 观测准入拒绝与排队增长，作为第一个瓶颈候选 | 准入与排队信号 |
| Agent Scheduler | 观测调度并发与等待，区分调度瓶颈与模型瓶颈 | 调度信号 |
| Model Prefill/Decode | 观测 prefill 与 decode 的分别饱和情况 | 模型分段信号 |
| Tool Dependency | 观测下游工具的饱和与超时，常是真正的瓶颈所在 | 工具依赖信号 |
| Goodput Gate 与瓶颈对照 | 以 Goodput 不再上升定位拐点，并给出瓶颈证据 | 容量拐点与瓶颈结论 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 五类瓶颈信号与对应的阶段

找到拐点只是第一步，真正的产出是「拐点由什么造成」。下表把可观测信号映射到具体阶段。

一次只改一层，并把改动前后的信号都记下来——否则你无法证明是这一层造成的。

| 信号 | 指向哪个阶段 | 验证方式 |
| --- | --- | --- |
| 队列深度持续增长 | 调度与并发上限 | 调并发看队列是否回落 |
| TTFT 上升而 TPOT 稳定 | prefill / 上下文长度 | 缩短系统提示重压 |
| TPOT 上升 | decode / 显存与批处理 | 看 KV Cache 命中与逐出 |
| 工具 span 耗时上升 | 外部依赖 | 单独压该依赖 |
| 重试次数上升 | 超时阈值过紧 | 放宽超时看重试是否回落 |

> 五类信号可以同时出现；此时按队列 → prefill → decode → 工具 → 重试的顺序逐层排除。

*依据：[vllm-project/vllm](https://docs.vllm.ai/)*

### 这一页的验收口径：拐点与瓶颈证据

AP05-1 要求至少三个相邻档位，理由很直接：两个点无法区分「拐点」和「还在线性区」。

AP05-3 要求瓶颈结论必须有分段信号支撑，而不是推测。没有信号的瓶颈判断在下一次优化后往往被证伪。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| AP05-1 | 阶梯充分 | 覆盖的压力档位数 ≥ 3；每档持续时长 ≥ 10 分钟 | 每次容量评估 |
| AP05-2 | 拐点判定 | 以 Goodput 不再上升定位拐点；以单点数字宣称容量的次数 = 0 | 每次容量评估 |
| AP05-3 | 瓶颈证据 | 瓶颈结论附对应分段信号的比例 = 100%；无信号支撑的推测数 = 0 | 每次评估 |
| AP05-4 | 跨次可比 | 两次压测的 workload hash 变更字段数 = 0 才可直接对比 | 每次对比 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来找到了容量、实际不能用的结论

这两个结论都会被写进容量规划文档，也都能给出压测曲线支撑。

它们的问题是把一个条件性结论当成了系统属性。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 报告最大吞吐 120 task/min 作为系统容量 | 这是压出来的极限值，有曲线为证 | 最大吞吐点上延迟可能已经远超 SLO。容量应当报 SLO 拐点，通常显著低于最大吞吐 |
| 合成负载下 goodput 达标，可支撑上线 | 合成负载覆盖了主要任务类型 | goodput 只对这份合成负载成立。必须在报告里写明 workload hash 与适用范围，否则它会被当成系统属性反复引用 |

> 容量永远是条件性结论：在哪份负载、哪个 SLO、哪个版本下成立。

### 加压时找不到清晰拐点按什么顺序查

拐点模糊通常说明实验设计有问题：台阶太密、稳定时间太短，或者压测端先到了瓶颈。

先确认发压端没问题，再怀疑被测系统。

| 症状 | 先怀疑 | 下一步检查 |
| --- | --- | --- |
| 曲线平滑无拐点 | 台阶太密或稳定期太短 | 加大台阶间隔，每级至少稳定观察数分钟 |
| 吞吐早早封顶 | 发压端瓶颈 | 查压测机 CPU、连接数与出口带宽 |
| 拐点每次不同 | 缓存命中率不一致 | 固定缓存状态或记录命中率 |
| 延迟涨但队列不涨 | 单请求变慢 | 查 prefill 与上下文长度 |
| 成功率先掉延迟后涨 | 超时阈值触发在前 | 把超时与 SLO 阈值对齐后重压 |

> 第二行最容易被忽略：吞吐封顶时先证明压测机不是瓶颈，否则测的是压测机。

### 阶梯加压找拐点并给出瓶颈证据：约 90 分钟

这是本模块唯一需要真实压测环境的演练。若暂无环境，可以用离线 trace 做归因练习，但必须标注为未运行。

1. 用固定 workload 与固定 SLO 定义开始，两者都记录 hash 与取值。
2. 按台阶加压：每级提升固定比例，每级稳定观察数分钟后再进下一级。
3. 记录每级的 p95/p99、成功率、goodput、队列深度、TTFT、TPOT、工具耗时与重试次数。
4. 找到第一个违反 SLO 的台阶，把它记为 SLO 拐点——不要报最大吞吐。
5. 对照五类信号表判断瓶颈阶段，然后只改这一层再压一次，验证拐点是否右移。

**期望结果**：产出是一条容量曲线加一张瓶颈证据卡，卡上必须写明 workload hash、SLO 定义、拐点值与瓶颈阶段。

> ⚠ 不要在共享环境做阶梯加压。它会影响其他团队，而且邻居的负载会污染你的拐点。

### 这一页的出口判据

这道门禁拒绝没有证据的瓶颈判断。「我觉得是 GPU」和「decode 段在第 4 档饱和而排队未增长」是两种不同性质的结论。

第三段要接受的是合成 goodput 与生产容量之间的距离——本页给出的是可横向比较的数字，不是生产承诺。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 压力档位数 < 3 时阻断，无法判断曲线形状<br>workload hash 变更字段数 > 0 却直接对比两次结果时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 各档位 Goodput 给出 95% CI，拐点判定以区间不再上升为准<br>单档位样本 < 500 个任务时该档位结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | synthetic goodput 与生产容量之间的差距，由容量 owner 估计并签字接受<br>瓶颈结论中仍存疑的部分，由架构 owner 标记为待验证并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[grafana/k6](https://grafana.com/docs/k6/latest/)*

### 带走一张有适用范围的容量卡

容量卡的关键不是数字，而是数字旁边的限定条件：哪份 workload、哪个 SLO、哪个版本、哪次实验。

没有限定条件的容量数字会在半年后被当成系统属性引用，然后在一次真实高峰中失效。

- 报 SLO 拐点而不是最大吞吐
- 把 workload hash 与 SLO 定义写进容量卡
- 改一层验证一次，证明瓶颈判断成立

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[k6：以到达率为模型的负载测试工具](https://grafana.com/docs/k6/latest/)** — 性能专项工具
  - 能证明：开放模型（constant-arrival-rate）与封闭模型（VU 并发）的区别，以及为什么用固定并发数压测会掩盖真实容量拐点——并发模型下系统变慢会自动降低到达率，形成自我保护假象。
  - 不能证明：工具产出的是客户端观测。真实容量还取决于依赖、缓存命中、数据规模与限流策略；任何教学阈值都不能照抄。
  - `grafana/k6` · 版本 v2.2.0（2026-08-10） · AGPL-3.0 · AGPL-3.0：著佐权许可，只链接与转述，不搬代码
- **[Prometheus：指标采集与查询](https://prometheus.io/docs/practices/histograms/)** — 指标实现
  - 能证明：直方图与分位数的实际计算方式，以及为什么跨实例平均分位数在数学上是错的（分位不可加）。这一条直接决定了 p95 报表是否可信。
  - 不能证明：指标是聚合信号，无法回答单次失败发生了什么。归因必须回到 trace 与日志。
  - `prometheus/prometheus` · 版本 v3.13.2（2026-07-30） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[vLLM：高吞吐推理服务引擎](https://docs.vllm.ai/)** — 推理服务实现
  - 能证明：生成式服务的延迟由两个阶段构成：prefill 处理输入、decode 逐 token 产出。连续批处理会把不同请求混在同一批里，因此单个请求的延迟取决于同时在跑的其他请求——这是传统 QPS 模型解释不了生成式服务表现的根本原因。
  - 不能证明：引擎指标反映的是服务端状态，不等于用户体感；托管 API 通常不暴露这些指标，此时只能从客户端阶段指标推断并标记未知。
  - `vllm-project/vllm` · 版本 v0.27.1（2026-08-11） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[SGLang：结构化生成与前缀复用的推理引擎](https://docs.sglang.ai/)** — 推理服务实现
  - 能证明：前缀缓存命中率会显著改变延迟分布：相同系统提示词的请求可以复用 KV 缓存。这意味着压测时构造的请求是否共享前缀，会直接决定你测出来的容量数字。
  - 不能证明：缓存收益高度依赖真实流量的前缀分布，实验室里构造的高命中率不可外推到生产。
  - `sgl-project/sglang` · 版本 v0.5.17（2026-08-08） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
