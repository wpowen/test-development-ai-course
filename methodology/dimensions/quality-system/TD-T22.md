## TD-T22

### 线上出过的问题如果没进回归集，它一定会再出一次

生产失败是质量系统最贵也最真实的输入。多数团队会修复它，但不会把它转成回归用例——于是同一个问题在下一个版本原样复现。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 修复但不固化为回归用例 | 未固化的缺陷复发率显著高于已固化的；一次固化的成本通常在 1 小时以内，一次复发的成本远高于此 | 「这个问题上个月修过了」成为复盘里反复出现的一句话 |
| 生产 trace 未脱敏就进测试环境 | 生产 trace 含真实用户数据；未脱敏引入测试环境即构成数据违规，可接受次数为 0 | 为了复现方便直接拷贝生产数据，埋下合规风险 |
| 用完整 trace 而不是最小失败样例做回归 | 完整 trace 通常包含大量无关步骤，回归执行时间可达最小样例的 10 倍以上，且脆弱性同步上升 | 回归集越加越慢，最终被裁剪，裁掉的往往是最近加的那些 |

> 本页的做法是建一条闭环：隔离 → 脱敏 → 最小化 → 判据 → 回归集 → CI 重放 → 事件关闭。

### 生产失败回灌的四个词

每个逃逸缺陷都应该变成一条不会再让它复发的测试。

| 术语 | 一句话解释 |
| --- | --- |
| 脱敏 Trace | 移除敏感信息后的生产运行记录；它是重建故障的原料 |
| 最小回归样例 | 能稳定复现该缺陷的最小输入集合 |
| 检测力验证 | 用变异确认这条新用例真的有效，而不是恰好变红 |
| 同类反查 | 找出与它同类但尚未暴露的风险 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[Arize-ai/phoenix](https://arize.com/docs/phoenix)*

### 线上出过的问题如果没进回归集，它一定会再出一次

回归资产的建设速度，决定了一个系统是在积累质量还是在原地打转。每一次生产事故如果只是被修复而没有沉淀成一条可重复执行的用例，那么同一类问题会在下一次重构、下一次模型升级时重新出现。

AI 系统的回灌比传统系统多两个步骤。第一是脱敏：生产 trace 里包含真实用户数据，直接进回归集会造成合规问题，必须先做脱敏且脱敏本身要可验证。第二是**检测力验证**：把样例加进回归集之后，必须确认它真的能检出那个问题——把当时的缺陷版本跑一遍，这条用例必须红。

第二步最常被跳过，后果也最隐蔽：一条不能检出任何东西的回归用例会永远是绿的，看起来回归集在增长，实际检测力没有变化。这与自愈把用例修绿是同一类失效。

同类反查是把一次事故的价值最大化的手段：找到这个问题之后，用同样的模式在历史数据里搜索，看还有多少同类案例没被发现。一次事故通常不是孤例，而这个搜索的成本远低于等它们逐个发生。

*依据：[Arize-ai/phoenix](https://arize.com/docs/phoenix) · [langfuse/langfuse](https://langfuse.com/docs)*

### 回灌六步与各自的产出

六步按顺序执行，每一步都有明确产出。第三步与第五步是 AI 系统特有的，也是最常被跳过的两步。

第四列写的是跳过之后会发生什么——注意它们全部是静默失效，不会有任何报错。

| 步骤 | 做什么 | 产出 | 跳过的后果 |
| --- | --- | --- | --- |
| 1 捕获 | 从生产 trace 定位到失败案例的完整上下文 | 原始 trace 快照 | 只有一句用户描述，无法复现 |
| 2 脱敏 | 移除真实用户数据，且脱敏可被验证 | 脱敏后样例 + 脱敏校验记录 | 回归集本身成为合规风险 |
| 3 最小化 | 裁剪成能复现问题的最小输入 | 最小回归样例 | 样例过大，失败时无法定位 |
| 4 入集 | 加入回归集并标注风险切片 | 版本化的回归集 | —— |
| 5 检测力验证 | 在缺陷版本上跑，确认这条用例会红 | 红绿验证记录 | 回归集在增长但检测力没变，静默失效 |
| 6 同类反查 | 用同样模式搜索历史数据找同类案例 | 同类案例清单 | 同一类问题逐个发生，逐个救火 |

> 第五步是这六步里唯一能证明前四步有效的一步。省掉它，回归集的规模就成了一个与质量无关的数字。

*依据：[Arize-ai/phoenix](https://arize.com/docs/phoenix) · [langfuse/langfuse](https://langfuse.com/docs) · [iterative/dvc](https://dvc.org/doc) · [hcoles/pitest](https://pitest.org/)*

### 这张图的 7 个节点，本页各交付什么

这张图是一条单向闭环：生产失败从左边进来，经过隔离与脱敏后被最小化，最后作为回归用例进入 CI，事件才算关闭。

「生产 Trace 隔离区」是第一个节点也是合规底线：生产数据不得直接进入测试环境，必须先进隔离区完成分类与脱敏。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 生产 Trace 隔离区 | 生产 trace 先进隔离区，禁止直接进入测试环境 | 隔离区与访问控制 |
| 字段分类/脱敏 | 对字段做敏感度分类并脱敏，验证脱敏不可逆 | 脱敏规则与验证结果 |
| 最小失败抽取 | 从完整 trace 中抽取能复现失败的最小步骤集 | 最小失败样例 |
| 业务/安全 Oracle | 为最小样例配上明确判据，说明什么算修好了 | 回归判据 |
| Regression Dataset | 把最小样例并入回归集，记录来源事件号 | 回归集条目（含来源） |
| CI 重放 | 在 CI 中重放该用例，验证修复有效且不再复发 | CI 重放结果 |
| 修复与事件 Closure | 只有回归用例入库并通过后，事件才允许关闭 | 事件关闭记录 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 回灌的六步与各自的产出

缺任何一步，这次回灌都会退化成「修了一个 bug」而不是「加了一道防线」。

右列写的是跳过这一步的后果。

| 步骤 | 产出 | 跳过的后果 |
| --- | --- | --- |
| 捕获 | 完整脱敏 Trace | 无法在测试环境重现 |
| 复现 | 复现率 M/N | 不知道是否真的抓住了问题 |
| 归因 | 五层中的具体一层 | 修错地方 |
| 回归用例 | 能稳定变红的用例 | 同样问题会再发生 |
| 检测力验证 | 变异杀死结果 | 用例可能恰好变红而无检测力 |
| 同类反查 | 新增风险条目 | 只修了这一个实例 |

> 第五步最常被跳过：新用例在当前缺陷上变红，不代表它对同类变化有检测力。

*依据：[langfuse/langfuse](https://langfuse.com/docs)*

### 这一页的验收口径：闭环率与时效

T22-1 的固化率是本页最重要的一条：它把「修复」重新定义为「修复 + 固化」，没有固化的修复不算完成。

T22-2 的脱敏是合规红线，可接受次数为 0。这一条与质量无关，与合规有关，因此不设容忍区间。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| T22-1 | 回归固化率 | 生产缺陷转为回归用例的比例 = 100%；未固化即事件不得关闭 | 每次事件 |
| T22-2 | 脱敏合规 | 未脱敏生产数据进入测试环境的次数 = 0 | 持续 |
| T22-3 | 最小化程度 | 最小失败样例的步骤数相对原始 trace 缩减 ≥ 80% | 每次抽取 |
| T22-4 | 闭环时效 | 从事件发生到回归用例入库的中位耗时 ≤ 5 个工作日 | 每月 1 次 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来完成了回灌、实际没有的做法

这两种做法都在事故后做了动作，也确实关闭了工单。

问题是它们没有留下能防止复发的东西。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 修复代码并在原有测试中增加一条断言 | 问题修了，也补了测试，流程完整 | 没有验证这条断言的检测力。如果它恰好只对这次的具体值成立，稍有变化的同类缺陷仍会逃逸 |
| 把生产 trace 直接作为回归用例回放 | 用真实数据最贴近生产，也省了构造成本 | 生产 trace 包含大量无关内容，且可能含敏感信息。回归用例应当是脱敏后的最小集合，否则维护成本极高且不稳定 |

> 两条的共同修法：提取最小样例，并用变异验证它的检测力。

### 同类问题反复出现时按什么顺序查

反复出现说明回灌链某一步断了。按下表逐项回溯。

第四行是最常见的：只修了这一个实例，没有反查同类。

| 症状 | 哪一步断了 | 补什么 |
| --- | --- | --- |
| 无法在测试环境重现 | 捕获不完整 | 补可重放五要素 |
| 修完仍不确定原因 | 归因未做控制实验 | 补单变量验证 |
| 新用例从不失败 | 检测力未验证 | 用变异确认 |
| 换个场景又出现 | 未做同类反查 | 按风险类别反查并补条目 |

> 四行按回灌步骤排列。修复的方式就是把断掉的那一步补上，而不是再修一次代码。

### 给一个真实逃逸缺陷走完六步：约 60 分钟

选一个最近的逃逸缺陷，按六步走一遍，记录在哪一步卡住。

1. 取该缺陷的生产 trace，脱敏后确认能在测试环境重现，记录复现率。
2. 按五层归因法定位到具体层，并用改一个变量的方式验证。
3. 从 trace 中提取最小输入集合，写成回归用例并确认它变红。
4. 修复后确认用例转绿，然后用变异验证它对同类变化仍然敏感。
5. 按风险类别反查：还有哪些同类场景尚未被覆盖，逐条补进风险登记册。

**期望结果**：典型结果是第二步或第五步卡住。前者说明可观测性不足，后者说明回归用例的检测力未被验证过。

> ⚠ 脱敏时不要删掉结构。把整个字段删除会让 trace 失去重现价值，正确做法是字段级替换。

### 这一页的出口判据

这一页的门禁改变了「事件关闭」的定义：修好不等于关闭，进了回归集才算关闭。这一条会让事件关闭变慢，但会让复发变少。

第三段要接受的是无法复现的生产失败：总有一部分失败在测试环境无法重建，这部分必须被显式记录而不是悄悄关闭。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 未脱敏生产数据进入测试环境的次数 > 0 时阻断，并按数据事件流程上报<br>未固化为回归用例的事件关闭数量 > 0 时阻断关闭流程 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 缺陷复发率按季度统计并给出 95% CI，与上季度以区间重叠判定<br>事件样本 < 20 起时复发率结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 无法在测试环境复现的生产失败清单，由测试负责人列出并签字接受<br>闭环时效超过 5 个工作日的事件，由工程负责人说明原因并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[hcoles/pitest](https://pitest.org/)*

### 带走一份回灌闭环记录

记录六步各自的产出，特别是复现率、归因层次与变异验证结果。

它同时是缺陷逃逸台账的输入：本应被哪一层门禁拦下，为什么没拦住。

- 提取最小样例，不直接回放生产 trace
- 用变异验证新用例的检测力
- 按风险类别反查同类，不只修这一个

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Langfuse：LLM 应用可观测与评测平台](https://langfuse.com/docs)** — AI 侧观测
  - 能证明：模型调用的输入输出、成本、延迟与评分可以被持久化为可检索的 trace，使线上样本回流成评测集成为常规动作而非一次性导出。
  - 不能证明：记录不等于判断。平台里的 score 仍来自你配置的评测器，评测器本身的可信度需要单独证明。
  - `langfuse/langfuse` · 版本 v4.10.0（2026-08-12） · NOASSERTION · 许可证未能自动判定，按最保守口径只链接不搬代码
- **[Phoenix：LLM 应用的 trace 与评测一体化](https://arize.com/docs/phoenix)** — AI 侧观测与评测
  - 能证明：线上 trace 与离线评测可以共用同一份数据模型，使生产样本直接成为评测集，而不需要一次性导出再手工整理。
  - 不能证明：许可证未被自动判定，按仅链接处理；平台记录能力不等于判断能力，评测器的可信度仍需单独证明。
  - `Arize-ai/phoenix` · 版本 arize-phoenix-v20.2.0（2026-08-13） · NOASSERTION · 许可证未能自动判定，按最保守口径只链接不搬代码
- **[PIT：JVM 变异测试](https://pitest.org/)** — 检测力判据
  - 能证明：覆盖率只说明代码被执行过，不说明被检查过。变异测试往代码里植入语义变更，看测试会不会红——存活的变异体就是一条被执行却没有被断言的路径。这是「测试有没有检测力」目前唯一可自动判定的口径。
  - 不能证明：变异算子覆盖的是语法层面的常见错误，覆盖不到业务逻辑错误；等价变异体（语义未变）会造成无法消除的存活率下限。
  - `hcoles/pitest` · 版本 1.25.9（2026-08-04） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[DVC：数据与流水线的版本控制](https://dvc.org/doc)** — 数据版本
  - 能证明：评测集必须与代码一样可版本化：同一个 commit 能取回当时用的那份数据。缺了这一条，历史评测分数之间不可比，回归判断也就不成立。
  - 不能证明：版本可追不代表数据集设计合理；污染与分布偏移不会因为版本化而消失。
  - `iterative/dvc` · 版本 3.67.1（2026-03-31） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Evidently：数据与模型漂移检测](https://docs.evidentlyai.com/)** — 漂移检测
  - 能证明：输入分布漂移可以在没有标注的情况下被检出，因此可以作为线上早期告警——真实质量下降往往先表现为输入分布变了，而标注要几天后才有。
  - 不能证明：漂移不等于质量下降，反之亦然。它是调查触发器，不能直接作为阻断门禁。
  - `evidentlyai/evidently` · 版本 v0.7.21（2026-03-10） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
