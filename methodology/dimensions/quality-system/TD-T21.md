## TD-T21

### 半年后有人问「这个 87 分是怎么来的」，你要么答得出，要么这个分数从此无效

AI 系统的版本不是一个数字，是七个组件的组合。任何一个组件没有被记录，历史分数就退化成一个无法解释的数字。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 只记录代码版本 | AI 系统的版本至少由代码、提示、数据、知识库、模型、判分器、运行时 7 个组件共同决定；只记 1 个等于没记 | 代码没变分数变了，被归因为「模型不稳定」 |
| 判分器版本未纳入 lineage | 判分器换版会整体平移分数 3～8pt，且方向不固定；不记录时这个平移无法被识别 | 把判分器的刻度变化当成模型能力变化，做了错误的版本决策 |
| 历史运行无法重放 | 重放需要 7 个组件全部可还原；缺任一项则重放成功率为 0 | 一次重要的回归无法复现，缺陷进不了回归集，问题反复出现 |

> 本页的产物是一份 Run Manifest：任何一个分数都能通过它回到当时的完整环境。

### Lineage 的四个词

每个分数都要能回到当时的版本，否则它半年后就无法解释。

| 术语 | 一句话解释 |
| --- | --- |
| 版本账本 | 一次运行涉及的全部组件版本记录 |
| 可回放 | 凭账本能重现当时的运行；它是归因的前提 |
| 七要素 | Dataset、Prompt、模型、知识库、工具、Scorer、运行环境 |
| 漂移 | 版本未变但行为变了；它只能通过账本对比被发现 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[mlflow/mlflow](https://mlflow.org/docs/latest/)*

### 半年后有人问「这个 87 分怎么来的」，答不出它就从此无效

评测分数的价值来自可比较：这一版比上一版好还是差。可比较的前提是两次评测的条件相同，而「条件相同」这件事只能靠记录证明，不能靠记忆。

版本账本要记的七要素是：模型版本、提示词版本、检索索引版本、评测集版本、评测配置、代码 commit、运行环境。七项里最容易漏的是提示词版本与检索索引版本——它们通常不在代码仓库里，也不在模型仓库里。

可回放是比可追溯更高一级的要求：不仅知道当时用了什么，还能把当时的条件重新搭起来跑一遍。它的价值在争议出现时才显现——当两个团队对同一个分数有分歧时，可回放是唯一能终结争论的东西。

漂移检测是账本的自动化延伸：定期用同一份固定输入重跑，比对结果是否变化。托管模型的权重可能在没有任何通知的情况下变更，这是唯一能发现它的手段——而发现它的时机，决定了你是主动排查还是被用户投诉推着排查。

*依据：[mlflow/mlflow](https://mlflow.org/docs/latest/) · [iterative/dvc](https://dvc.org/doc)*

### 七要素各自记录什么、记在哪

这张表是账本的字段清单。建议直接照着建表，缺项在这一列里就是空白，一眼可见。

第三列标出了「最容易漏」的三项，它们的共同点是不属于任何一个现成仓库。

| 要素 | 记什么 | 是否容易漏 | 工具 |
| --- | --- | --- | --- |
| 模型版本 | 权重版本或别名的实际解析结果 | 中：只记别名是常见错误 | MLflow model registry |
| 提示词版本 | 系统提示词与模板的版本号或哈希 | 高：通常不在任何仓库里 | Langfuse prompt management |
| 检索索引版本 | 索引构建时间、语料快照、切分参数 | 高：索引重建后无记录 | 自建索引元数据 |
| 评测集版本 | 数据集版本与是否 holdout | 低 | DVC |
| 评测配置 | 解码参数、scorer 版本、样本量 | 中 | 评测框架配置文件 |
| 代码 commit | 评测与推理两侧的 SHA | 低 | Git |
| 运行环境 | 依赖版本、硬件、并发设置 | 高：几乎从不记录 | 容器镜像摘要 |

> 七项里有三项「高」——它们恰好都不属于任何一个现成仓库，因此必须显式设计存放位置，否则一定会缺。

*依据：[mlflow/mlflow](https://mlflow.org/docs/latest/) · [iterative/dvc](https://dvc.org/doc) · [langfuse/langfuse](https://langfuse.com/docs) · [evidentlyai/evidently](https://docs.evidentlyai.com/)*

### 这张图的 7 个节点，本页各交付什么

这张图列出的就是必须进 lineage 的七个组件。它们不是并列的可选项，而是全集——少记一个，这次运行就不可重放。

「Run Manifest/决策」把前六项汇总成一条可引用的记录，并把发布决策也写进去：不仅要知道分数是怎么来的，还要知道当时据此做了什么决定。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 代码 Commit | 记录应用代码与评测代码的提交号 | 代码版本记录 |
| Prompt/Input/Schema | 记录提示模板、输入构造逻辑与输出 Schema 的版本 | 提示与 Schema 版本 |
| Dataset/Split | 记录数据集版本与划分方式 | 数据集版本记录 |
| Knowledge/Tool | 记录知识库快照与工具清单 hash | 知识与工具版本 |
| Model/Runtime | 记录模型版本、温度、种子与运行时环境 | 模型与运行时快照 |
| Scorer/聚合 | 记录判分器版本与聚合方式，这是最容易被漏记的一项 | 判分器版本记录 |
| Run Manifest/决策 | 汇总七项并记录据此做出的决策 | Run Manifest |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 七要素各自记录什么

少记任何一项，都会出现「这个分数当时是怎么来的」无法回答的情况。

右列是这一项变化时的典型影响——它们都会让跨时间对比失效。

| 要素 | 记录什么 | 变化时的影响 |
| --- | --- | --- |
| Dataset | 版本与切分 | 绝对值不可比 |
| Prompt | 版本与完整内容 | 行为可能完全不同 |
| 模型 | 精确版本号非别名 | 能力基线改变 |
| 知识库 | 快照 ID 与分块参数 | 检索结果改变 |
| 工具 | 版本与描述 hash | 可用能力改变 |
| Scorer | 版本与阈值 | 分数尺度改变 |
| 运行环境 | 并发、缓存、批处理 | 性能与部分行为改变 |

> 第六行最容易被忽略：Scorer 换了之后，新旧分数不在同一把尺子上，任何趋势图都失去意义。

*依据：[langfuse/langfuse](https://langfuse.com/docs)*

### 这一页的验收口径：可重放即可信

T21-1 的七项完整度是本页唯一的硬指标。它不是「记得越多越好」，而是「少一项就不可重放」——这是一个二元属性。

T21-2 的重放验证必须真的执行，而不是假设可以。声称可重放与验证过可重放之间的差距，通常在第一次需要重放时才被发现。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| T21-1 | lineage 完整度 | 七个组件的版本记录缺失率 = 0 | 每次运行 |
| T21-2 | 重放可行性 | 随机抽取 20 次历史运行，成功重放并复现原结果的比例 ≥ 95% | 每月 1 次 |
| T21-3 | 判分器可追溯 | 每个分数关联到具体判分器版本的比例 = 100% | 每次评测 |
| T21-4 | 决策留痕 | 每次发布决策关联到具体 Run Manifest 的比例 = 100% | 每次发布 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

*依据：[evidentlyai/evidently](https://docs.evidentlyai.com/)*

### 两种看起来记录充分、实际无法回放的做法

这两种做法都保存了不少信息，也确实比什么都不记好。

问题是记录的粒度不足以支撑回放。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 记录模型名称与评测日期 | 这是最常见的记录方式，也能大致定位 | 模型名称不含版本。同一名称在两个日期可能指向不同版本，而日期本身不能反推版本。必须记精确版本号 |
| 把配置文件存进结果目录 | 配置完整，也与结果放在一起 | 配置文件不包含运行时的实际取值：环境变量覆盖、默认值、缓存状态都不在里面。要记录的是实际生效的配置 |

> 两条的共同修法：记录实际生效值而不是声明值，记录精确版本而不是名称。

### 历史分数无法解释时按什么顺序查

按七要素逐项核对两次运行的差异。缺记录的项就是当前账本的缺口。

核对完之后，把缺失的项补进账本，下次就不会再遇到同样问题。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 同配置结果不同 | 模型别名漂移 | 改记精确版本号 |
| 趋势图突然跳变 | Scorer 换版 | 为 Scorer 版本打点标注 |
| 无法重现历史结果 | 环境未记录 | 补并发、缓存、批处理配置 |
| 检索结果对不上 | 知识库快照未记 | 记录索引快照 ID 与分块参数 |

> 四行都可以通过补记录预防，成本远低于事后考古。

### 给一次历史运行做回放尝试：约 40 分钟

尝试回放是检验账本完整性最直接的方法。

1. 选一次三个月前的评测运行，找出它当时的全部记录。
2. 按七要素逐项核对，标出哪些能查到、哪些查不到。
3. 尝试用这些记录重现当时的运行，记录卡在哪一要素上。
4. 把缺失的要素补进当前的账本模板。
5. 验证：用新模板跑一次，确认七要素全部被记录且可读。

**期望结果**：多数团队会在「运行环境」或「Scorer 版本」上卡住。这两项是最少被记录、也最容易造成不可比的。

> ⚠ 回放不必得到完全一致的结果。目标是确认所有输入都能被还原；输出差异本身是有价值的信息。

### 这一页的出口判据

这一页的门禁看起来是流程要求，实际上是能力要求：它决定了你能不能在事故发生后还原现场。

第三段要接受的是存储成本：完整 lineage 的存储开销不低，保留期限是成本与可追溯性之间的取舍。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 七项 lineage 记录缺失率 > 0 时阻断，该次运行结果不得用于决策<br>无法关联到 Run Manifest 的发布决策数量 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 重放成功率按 20 次抽样给出 95% CI 下界，与 95% 比较用下界<br>抽样 < 20 次时重放能力结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | lineage 的保留期限与存储成本，由工程负责人签字确定<br>无法完整记录的外部依赖（如第三方 API 的内部版本），由架构 owner 列出并接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

### 带走一份七要素账本模板

模板的价值在于它把「记录什么」这个问题固定下来，不再依赖每个人的判断。

加一条硬规则：模型和 Scorer 记精确版本号，不记名称。

- 七要素全部记录，缺一项即不可回放
- 记实际生效值而不是配置文件里的声明值
- 模型与 Scorer 记精确版本号

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Langfuse：LLM 应用可观测与评测平台](https://langfuse.com/docs)** — AI 侧观测
  - 能证明：模型调用的输入输出、成本、延迟与评分可以被持久化为可检索的 trace，使线上样本回流成评测集成为常规动作而非一次性导出。
  - 不能证明：记录不等于判断。平台里的 score 仍来自你配置的评测器，评测器本身的可信度需要单独证明。
  - `langfuse/langfuse` · 版本 v4.10.0（2026-08-12） · NOASSERTION · 许可证未能自动判定，按最保守口径只链接不搬代码
- **[MLflow：实验、模型与版本的登记体系](https://mlflow.org/docs/latest/)** — 版本与血缘
  - 能证明：模型、参数、数据版本与评测结果可以被登记成可检索的关联记录，使「这个结论对应哪个模型的哪次运行」成为可查询事实而不是靠人记。回滚与事后归因都依赖这条记录。
  - 不能证明：登记的是元数据不是质量。记录齐全的模型同样可以是差模型。
  - `mlflow/mlflow` · 版本 v3.15.1（2026-08-03） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[DVC：数据与流水线的版本控制](https://dvc.org/doc)** — 数据版本
  - 能证明：评测集必须与代码一样可版本化：同一个 commit 能取回当时用的那份数据。缺了这一条，历史评测分数之间不可比，回归判断也就不成立。
  - 不能证明：版本可追不代表数据集设计合理；污染与分布偏移不会因为版本化而消失。
  - `iterative/dvc` · 版本 3.67.1（2026-03-31） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Evidently：数据与模型漂移检测](https://docs.evidentlyai.com/)** — 漂移检测
  - 能证明：输入分布漂移可以在没有标注的情况下被检出，因此可以作为线上早期告警——真实质量下降往往先表现为输入分布变了，而标注要几天后才有。
  - 不能证明：漂移不等于质量下降，反之亦然。它是调查触发器，不能直接作为阻断门禁。
  - `evidentlyai/evidently` · 版本 v0.7.21（2026-03-10） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
