## TD-T20

### CI 里有评测但从不阻断，等于把评测做成了一份日报

很多团队已经在 CI 里跑 AI 评测，但结果只是打印出来。没有非零退出码，就没有门禁——它不改变任何人的行为。

下面三条是评测入 CI 却不生效的三种形态。

| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 评测结果不影响退出码 | 不阻断的评测对合并行为的影响为 0；它的唯一效果是产生日志 | 「我们 CI 里有 AI 评测」被当成质量保障已建立 |
| 所有评测都放在同一层 | 完整语义评测通常需要 30 分钟以上，放进每次提交会让 CI 时长不可接受，最终被关掉——关掉后门禁强度归 0 | 为了 CI 速度关掉了评测，于是回到零门禁状态 |
| 高风险用例与普通用例同等对待 | 高风险 smoke 只需 20～30 条用例即可在 10 分钟内跑完，与 2 小时的完整回归混在一起会被一起推迟 | 最该快速反馈的那部分，反馈得最慢 |

> 解法是分层：L0 确定性秒级、L1 高风险分钟级、L2 夜间回归、L3 发布前 holdout，各层有各层的阻断权。

### 分层门禁的四个词

门禁不是一个开关，是几层各自负责不同风险的检查。

| 术语 | 一句话解释 |
| --- | --- |
| 快速层 | 每次提交都跑，分钟级，只做确定性检查 |
| 评测层 | 合并前跑，覆盖风险切片与语义评测 |
| 完整层 | 发布前跑，含全量评测、安全与性能 |
| fail-closed | 检查本身失败时视为不通过，而不是跳过 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[promptfoo/promptfoo](https://www.promptfoo.dev/docs/intro/)*

### CI 里有评测但从不阻断，等于把评测做成了一份日报

很多团队的 AI 评测停在「跑起来了」这一步：每次提交都跑，结果输出到报告里，没有人看，也从不阻断。这种状态下评测消耗着算力与维护成本，却不产生任何约束——它已经不是门禁，是一份没人订阅的日报。

不敢阻断的真实原因通常是：评测太慢（跑一次要一小时）、太贵（每次几十美元）、太抖（同样的代码时红时绿）。这三个问题都不能靠「决心」解决，只能靠分层。

分层的做法是把检查按成本与稳定性分成三层：快速层（秒级、确定性、每次提交跑，如结构断言、禁用词、格式）；评测层（分钟级、小样本、每次 MR 跑，只看明显退化）；完整层（小时级、全量样本、发布前跑，带统计判据）。前两层必须 fail-closed，第三层可以带人工裁决。

fail-closed 是这一页的核心纪律：检查本身出错（评测服务不可用、超时、配置缺失）时必须判为失败，不能判为通过。fail-open 的门禁在最需要它的时候——基础设施出问题时——恰好是失效的。

*依据：[promptfoo/promptfoo](https://www.promptfoo.dev/docs/intro/) · [confident-ai/deepeval](https://deepeval.com/docs/getting-started)*

### 三层各自放什么检查、跑多久、能不能阻断

分层的目的是让每一层都敢阻断。一层里混进了慢的或抖的检查，整层就会被降级成「仅告警」。

第四列是判断依据：一个检查能不能进快速层，只看它是不是确定性的、是不是秒级完成。

| 层级 | 放什么检查 | 时长与频率 | 阻断策略 |
| --- | --- | --- | --- |
| 快速层 | 结构断言、schema 校验、禁用词、格式、静态规则 | 秒级，每次提交 | fail-closed，无例外 |
| 评测层 | 小样本评测，只看明显退化（超出噪声底线） | 分钟级，每次 MR | fail-closed；样本不足时判为「证据不足」并阻断 |
| 完整层 | 全量样本、统计判据、公平性切片、成本核算 | 小时级，发布前 | 统计门禁 + 具名风险接受 |
| 检查自身失败 | 评测服务不可用、超时、配置缺失 | 任意层 | 一律判为失败（fail-closed） |

> 第四行是最容易被写成 fail-open 的一行，也是最不该的一行——它在基础设施出问题时决定门禁还有没有效。

*依据：[promptfoo/promptfoo](https://www.promptfoo.dev/docs/intro/) · [confident-ai/deepeval](https://deepeval.com/docs/getting-started) · [UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/) · [semgrep/semgrep](https://semgrep.dev/docs/)*

### 这张图的 7 个节点，本页各交付什么

这张图是一条从提交到发布的分层门禁链。分层的依据是「反馈速度 × 阻断代价」：越快的层跑得越频繁，越慢的层拦得越重。

「Artifact/退出码」是让门禁真正生效的技术关键：非零退出码是 CI 唯一听得懂的语言。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| PR/候选版本 | 每个提交或候选版本触发分层门禁，记录触发原因 | 触发记录 |
| L0 确定性 Gate | Schema、权限、格式类确定性检查，秒级，每次提交必跑 | L0 检查结果 |
| L1 高风险 Smoke | 高风险场景的小样本快速验证，分钟级 | L1 smoke 结果 |
| L2 Nightly 回归 | 完整回归与语义评测，夜间执行 | L2 回归报告 |
| L3 RC/Holdout | 发布候选阶段在封存集上的最终验收 | L3 验收报告 |
| Artifact/退出码 | 把结论转成非零退出码与可归档产物，使门禁真正阻断 | 退出码与归档产物 |
| 人工发布 Gate | 最终由人基于四层结果做发布判断 | 发布判断记录 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 三层各自放什么检查

把所有检查堆在一层，要么太慢没人等，要么太松拦不住。分层的依据是反馈速度与风险等级。

右列的时间预算是设计约束——超出预算的检查要下沉到更慢的层。

| 层 | 放什么 | 时间预算 |
| --- | --- | --- |
| 快速层 | Schema、权限规则、静态检查 | 分钟级 |
| 评测层 | 风险切片评测、语义 Oracle、变异 | 半小时级 |
| 完整层 | 全量评测、攻击集、性能、成本 | 小时级 |

> 三层的时间预算决定了它们的内容。把小时级的检查放进快速层，结果是所有人开始绕过它。

*依据：[UKGovernmentBEIS/inspect_ai](https://inspect.aisi.org.uk/)*

### 这一页的验收口径：门禁必须真的会拦

T20-1 是本页唯一重要的一条：门禁的阻断有效性必须被验证，方法是故意提交一个应当被拦的变更，确认它确实被拦下。

T20-2 的时长约束不是性能指标而是可持续性指标：超时的门禁最终会被关掉，关掉的门禁等于不存在。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| T20-1 | 阻断有效性 | 注入应当被拦的变更时，各层实测拦截率 = 100%（逐层验证） | 每次门禁变更 |
| T20-2 | 反馈时效 | L0 ≤ 60 秒；L1 ≤ 10 分钟；L2 ≤ 2 小时 | 每周 1 次 |
| T20-3 | 分层覆盖 | 高风险用例进入 L1 的比例 = 100%，不得只存在于 L2 | 每次用例变更 |
| T20-4 | 门禁可用性 | 因门禁自身故障导致的误阻断率 ≤ 2%；超出会促使团队绕过门禁 | 每月 1 次 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来门禁很严、实际会被绕过的做法

这两种设计在评审时都显得很负责，也确实覆盖了很多检查。

问题是它们在实际使用中会被削弱。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 把全部检查放进每次提交的流水线，确保无遗漏 | 覆盖最全，也不会有人跳过某一层 | 流水线跑一小时时，人会开始批量提交、跳过本地验证、或申请豁免。门禁的有效性取决于它被遵守的程度，不只是它检查了什么 |
| 检查脚本异常时跳过该项，避免阻塞开发 | 环境问题不应该阻塞交付，跳过更务实 | 检查失败意味着这一项的结论未知，而未知不等于通过。必须 fail-closed，否则一次环境故障就能让整层门禁静默失效 |

> 两条的共同修法：按反馈速度分层，并且任何执行失败都视为不通过。

### 门禁存在但坏版本仍然通过时按什么顺序查

按下表逐项核对。第一行是最常见也最容易验证的。

验证方式：拿一个已知的坏版本跑一遍，看能不能被拦下。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 从未拦下过任何提交 | 检查未真正执行 | 注入已知坏版本验证 |
| 某类问题从不报警 | 该层缺对应检查 | 按风险清单补检查 |
| 经常有人申请豁免 | 层次划分不合理 | 把慢检查下沉到更慢的层 |
| 检查失败被当成通过 | 未 fail-closed | 把执行失败改为阻断 |

> 第三行是信号而非问题：频繁豁免说明门禁与开发节奏不匹配，要调层次而不是加强纪律。

### 用已知坏版本验证门禁：约 45 分钟

这是验证门禁有效性的唯一可靠方法。不需要等真实缺陷。

1. 从历史逃逸缺陷中选三个，各自构造一个包含该缺陷的版本。
2. 让三个版本分别走完整个门禁流程，记录每个在哪一层被拦下。
3. 没被拦下的，说明对应层缺少检查——这是最有价值的发现。
4. 检查每一层的实际耗时，与预算比较，超出的项考虑下沉。
5. 把检查执行失败的处理改为阻断，并验证这个改动生效。

**期望结果**：典型结果是三个坏版本里有一到两个能一路通过。这直接说明了门禁的真实覆盖范围。

> ⚠ 验证要用真实的历史缺陷，不要用人为构造的明显错误。后者太容易被拦下，验证不出实际能力。

### 这一页的出口判据

这一页的门禁是关于门禁的门禁。它要回答的问题只有一个：如果有人提交了一个危险的变更，你的系统会不会真的停下来。

第三段要接受的是误阻断成本：门禁越严，误拦越多；误拦率过高时团队会想办法绕过，反而更危险。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 任一层的实测拦截率 < 100% 时阻断该门禁上线<br>高风险用例未进入 L1 的数量 > 0 时阻断 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 误阻断率按周统计并给出 95% CI 上界，与 2% 比较用上界<br>门禁触发样本 < 50 次时有效性结论记为证据不足 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 误阻断带来的开发效率损失，由工程负责人签字接受<br>暂不纳入门禁的评测项及其理由，由测试负责人列出并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[promptfoo/promptfoo](https://www.promptfoo.dev/docs/intro/)*

### 带走一份分层门禁配置与验证记录

配置写明每层放什么、时间预算多少、失败如何处理。

验证记录写明用哪些历史缺陷验证过、各在哪层被拦下。没有验证记录的门禁是未经检验的。

- 按反馈速度分层，超预算的检查下沉
- 执行失败一律视为不通过
- 用历史逃逸缺陷定期验证门禁有效性

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[Semgrep：模式化静态分析](https://semgrep.dev/docs/)** — 静态门禁工具
  - 能证明：以贴近源码的语法模式表达规则，使团队专属约定（禁用某 API、必须带超时、密钥不得硬编码）能被写成可执行规则并纳入门禁。
  - 不能证明：模式匹配没有完整数据流理解，跨文件跨函数的污点传播会漏。低误报是靠限制规则范围换来的。
  - `semgrep/semgrep` · 版本 v1.173.0（2026-08-13） · LGPL-2.1 · LGPL-2.1：著佐权许可，只链接与转述，不搬代码
- **[promptfoo：Prompt 与 Agent 的断言式评测](https://www.promptfoo.dev/docs/intro/)** — AI 侧断言执行器
  - 能证明：把断言写成配置：确定性断言（contains、is-json、javascript）、语义断言与模型评判可以在同一个用例里组合，并按矩阵跑多模型多 prompt。它让「AI 输出」进入与传统测试相同的红绿流程。
  - 不能证明：模型评判本身有误差，需要与人工标注校准后才能作为门禁判据。
  - `promptfoo/promptfoo` · 版本 0.122.0（2026-08-04） · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
- **[DeepEval：pytest 风格的 LLM 评测框架](https://deepeval.com/docs/getting-started)** — AI 侧断言执行器
  - 能证明：LLM 评测可以直接寄生在 pytest 生态里：用例、fixture、参数化、CI 集成全部复用既有工程习惯，降低把评测接进流水线的成本。
  - 不能证明：指标默认阈值是框架给的示例值，不是你业务的验收线。
  - `confident-ai/deepeval` · 版本 v4.1.7（2026-07-29） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Inspect：任务 / solver / scorer 分层的模型评测框架](https://inspect.aisi.org.uk/)** — 评测框架
  - 能证明：评测可以拆成三个独立可替换的部件：dataset 定义问什么、solver 定义怎么问、scorer 定义怎么判。三者分离之后，换模型不用改判据，改判据不用改数据集——这是把一次性评测脚本变成可回归资产的结构条件。
  - 不能证明：框架不提供判据。scorer 写得对不对、数据集有没有覆盖你的风险切片，框架一概不管，全绿只说明流程跑通了。
  - `UKGovernmentBEIS/inspect_ai` · 版本 release/2025-11-28 · MIT · MIT：宽松许可，可整段引用源码并保留出处与版本锚点
