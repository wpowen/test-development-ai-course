## TD-X805

### 灰度发布如果没有预设的回滚触发条件，它只是把事故推迟了几小时

渐进发布的价值在于「小流量时发现问题并停下」。如果没有预先定义什么情况算问题、谁有权停，那么小流量阶段只是在积累证据而不会触发动作。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 没有预设 MDE 就开实验 | 未计算最小可检测效应时，样本量往往不足以分辨真实差异；此时无论结果如何都不构成结论 | 小流量跑了 3 天没看出问题，被当成「新版本没问题」 |
| 分流不稳定 | 同一用户在不同请求间落到不同实验组时，实验结论与用户体验同时被破坏；分流一致性低于 99.9% 即不可用 | 指标波动被归因于新版本，实际来自分流抖动 |
| guardrail 只看总体指标 | 总体指标平稳而最坏切片恶化 20pt 以上的情况很常见；只看总体时这类恶化在扩量前不会被发现 | 小流量一切正常，全量后特定用户群集中投诉 |

> 本页要交付的是一套渐进发布控制：假设与 MDE、稳定分流、离线门禁、guardrail、人工抽样、预置回滚。

### 渐进发布的四个词

AI 变更的发布不是开关，是一段有观察窗的过程。

| 术语 | 一句话解释 |
| --- | --- |
| 稳定分流 | 同一用户始终落在同一组；否则对比会被稀释 |
| 离线 blocker | 上线前必须通过的硬条件；它与在线观察是两回事 |
| guardrail 指标 | 小流量阶段用于快速止损的少数关键指标 |
| 代表性人工样本 | 按风险切片抽取的人工复核样本，不是随机抽 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

### 灰度如果没有预设的回滚触发条件，它只是把事故推迟了几小时

灰度发布的价值来自「小范围先暴露问题」。但这个价值只有在两个条件下才成立：一是小范围里真的能观察到问题，二是观察到之后真的会回滚。缺任一条，灰度就只是把全量发布推迟了几小时。

第一个条件常被忽略：如果分流比例太小或分流不稳定，某些低频问题在灰度期根本不会出现；如果 guardrail 指标选得不对，问题出现了也看不到。所以灰度设计的第一步是确认「这个比例、这段时间，能不能观察到我关心的那类问题」。

稳定分流是可观察性的前提：同一个用户必须稳定落在同一侧，否则用户会在新旧版本之间来回跳，既影响体验也让指标无法归因。基于用户 id 哈希分流是标准做法，而按请求随机分流是常见错误。

回滚触发条件必须在发布**之前**写死，且是自动的。事后判断「这算不算严重到要回滚」会受沉没成本影响——已经发了一半，回滚意味着承认失败。预设条件把这个决定从争论变成了执行。

*依据：[argoproj/argo-rollouts](https://argo-rollouts.readthedocs.io/) · [open-feature/spec](https://openfeature.dev/specification/)*

### 四个阶段各自的进入条件与观察项

每个阶段的进入条件必须在发布前写死。第四列是该阶段特有的观察项——它们在上一阶段的流量下观察不到。

第一阶段的离线 blocker 是唯一一个完全不依赖线上流量的门槛，因此它必须最严格。

| 阶段 | 进入条件 | 分流比例 | 该阶段特有的观察项 |
| --- | --- | --- | --- |
| 离线 | 全量评测通过，无 blocker 级问题 | 0% | 统计判据、公平性切片、成本核算 |
| 内部灰度 | 离线通过 + 回滚路径已演练 | 内部用户 | 真实交互下的异常形态，评测集里没有的用法 |
| 小比例灰度 | 内部无 blocker + guardrail 指标已配 | 1%～5%，按用户 id 稳定分流 | guardrail 指标趋势、成本、长尾延迟 |
| 逐步放量 | 小比例期无触发回滚 + 人工样本抽检通过 | 阶梯放大 | 低频问题、跨用户交互、容量拐点 |

> 四行的进入条件是累加的。跳过任何一行直接放量，等于把前面几行的观察机会全部放弃。

*依据：[argoproj/argo-rollouts](https://argo-rollouts.readthedocs.io/) · [open-feature/spec](https://openfeature.dev/specification/) · [evidentlyai/evidently](https://docs.evidentlyai.com/) · [Implementing SLOs（Google SRE Workbook）](https://sre.google/workbook/implementing-slos/)*

### 这张图的 7 个节点，本页各交付什么

这张图从「假设/MDE」开始：先说清楚要验证什么、能分辨多小的差异，再决定放多少流量、跑多久。顺序反过来就是在浪费流量。

「扩量/回滚」是唯一的出口节点，且它的触发条件必须在实验开始前就写死——事中再商量等于没有条件。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 假设/MDE | 写明要验证的假设与最小可检测效应，据此计算所需样本量与时长 | 实验设计文档 |
| 稳定分流 | 保证同一用户稳定落在同一组，验证分流一致性 | 分流一致性验证 |
| 离线门禁 | 上线前先过离线 blocker，不合格不进灰度 | 离线门禁结果 |
| 小流量 Canary | 以极小流量先跑，观察是否出现硬红线级问题 | canary 观测结果 |
| Guardrail/最坏切片 | 同时监测总体 guardrail 与最坏切片，任一越界即触发 | guardrail 与切片监测 |
| 人工抽样 | 对灰度流量做代表性人工抽样复核，补足自动指标看不到的问题 | 人工抽样结果 |
| 扩量/回滚 | 按预置条件自动扩量或回滚，条件在实验前写死 | 扩量与回滚条件及执行记录 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### 四个阶段各自的进入条件与观察项

每个阶段的进入条件必须提前写好，否则会在压力下被临时放宽。

右列是这个阶段最该看的指标——阶段不同关注点不同。

| 阶段 | 进入条件 | 主要观察 |
| --- | --- | --- |
| 离线 | 全部 blocker 通过 | 风险切片与安全 |
| 影子 | 离线通过且零副作用已验证 | 输出差异分布与成本 |
| 小流量 | 影子期无 blocker 类差异 | guardrail 指标与投诉 |
| 放量 | 小流量观察窗无异常 | 容量与成本曲线 |

> 影子阶段的「零副作用已验证」最容易被跳过——它要求专门测试新版确实没有产生任何写操作。

*依据：[open-feature/spec](https://openfeature.dev/specification/)*

### 这一页的验收口径：预置条件与最坏切片

X805-1 的 MDE 预计算决定了这次实验有没有意义：样本量不足以分辨你关心的差异时，实验做完也得不出结论。

X805-3 把最坏切片纳入 guardrail，是因为总体指标对小群体的恶化极不敏感——而小群体的用户感受到的是 100% 的恶化。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| X805-1 | 实验设计充分性 | 开始前完成 MDE 与样本量计算的比例 = 100%；样本量不足时不启动 | 每次实验 |
| X805-2 | 分流稳定性 | 同一用户跨请求落入同一实验组的比例 ≥ 99.9% | 每次实验 |
| X805-3 | Guardrail 覆盖 | 总体 guardrail 与最坏切片 guardrail 均配置的比例 = 100% | 每次实验 |
| X805-4 | 回滚预置 | 扩量与回滚条件在实验开始前写定的比例 = 100%；回滚执行耗时 ≤ 5 分钟 | 每次实验 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在渐进发布、实际观察不到问题的做法

这两种做法都遵循了渐进发布的形式，节奏也很规范。

问题是观察设计不足以发现问题。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 小流量 1% 观察一天，无异常即放量 | 流量小、时间短、风险可控，节奏也快 | 1% 一天的样本量往往不足以观察到低频但严重的问题。观察窗要按事件频率而不是按时间设定 |
| 影子阶段发现新旧输出不一致，判定新版本有问题 | 输出不一致确实是差异信号，谨慎也没错 | AI 输出不一致是常态，措辞变化就会造成差异。必须先用 Oracle 判定差异性质，否则每次模型升级都会被拦下 |

> 两条一个太松一个太紧，共同点是缺少对差异性质的判定。

### 渐进发布过程中出现异常时按什么顺序查

按下表逐项排查。前两行是设计问题，后两行是执行问题。

设计问题要在下次发布前修，执行问题当次就能处理。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 新旧组结果差异很大但说不清好坏 | 缺 Oracle 判定差异性质 | 用判据分类差异 |
| 小流量看不出问题，放量后暴露 | 观察窗按时间而非事件频率设定 | 按目标事件数设观察窗 |
| 同一用户体验前后不一致 | 分流不稳定 | 改为按用户 ID 稳定哈希 |
| 回滚不及时 | 无自动触发条件 | 预置 guardrail 阈值与自动回滚 |

> 第二行是最常见的设计缺陷：低频严重问题需要足够的暴露量才会出现，而它恰恰是最需要被发现的。

### 给一次发布设计观察窗：约 45 分钟

关键是按事件频率而不是按时间来定观察窗长度。

1. 列出这次变更可能影响的关键事件类型及其在生产中的发生频率。
2. 按最低频的关键事件计算：要观察到足够多次，需要多少流量乘以多长时间。
3. 据此设定小流量比例与观察窗长度，而不是凭经验定「1% 一天」。
4. 选三到五个 guardrail 指标，并为每个设定自动回滚阈值。
5. 按风险切片抽取人工复核样本，明确抽样规则与复核人。

**期望结果**：按事件频率算出来的观察窗往往比凭经验设的长得多。这个差距就是此前渐进发布可能漏掉问题的原因。

> ⚠ guardrail 指标不要超过五个。过多的指标会让自动回滚频繁误触发，最后被关掉。

### 这一页的出口判据

这是 TD-M05 的出口门禁，也是整个质量系统从「发布前保证」转向「运行时保证」的交接点。

第三段要接受的是灰度期间真实用户承担的风险：小流量意味着少数用户先承受可能的问题，这个取舍必须被明确接受。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | 回滚条件未在实验开始前写定的实验数量 > 0 时阻断启动<br>分流一致性 < 99.9% 时阻断，先修分流再做实验 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 实验结论以预注册的 MDE 与显著性水平判定，禁止事后调整判据<br>样本量未达到 MDE 计算值时结论为「证据不足」，不得据此扩量 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 灰度期间真实用户承担的风险范围，由产品 owner 签字接受<br>guardrail 阈值的取值，由业务 owner 与 SRE 共同确定并署名 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[argoproj/argo-rollouts](https://argo-rollouts.readthedocs.io/)*

### 带走一份按事件频率计算的观察窗

观察窗长度由关键事件频率决定，不由日程决定。这是渐进发布最容易做错也最容易修正的一项。

配套需要少数几个 guardrail 指标与预置的自动回滚阈值。

- 观察窗按事件频率计算，不按天数拍定
- 输出差异先用 Oracle 判定性质再决定阻断
- guardrail 控制在五个以内并预置自动回滚
