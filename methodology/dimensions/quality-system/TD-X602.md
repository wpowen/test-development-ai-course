## TD-X602

### 模型更新之后分数变了，而你说不清是数据、基座还是超参

训练与微调把可变因素从 1 个（提示）扩展到 5 个（数据、基座、代码、超参、随机性）。任何一个没有被锁进 lineage，这次更新的效果就无法归因。



| 失效形态 | 可核查的数字 | 它导致的错误结论 |
| --- | --- | --- |
| 数据、基座、超参同时变动 | 3 个变量同时变动时，完整归因需要至少 7 次实验（各改 1 个 + 各改 2 个 + 全改） | 把提升归给数据清洗，实际主要来自基座升级 |
| 没有封存 holdout 就宣布提升 | 在参与过调优的数据上评估，分数虚高；封存 holdout 每版本至多开封 1 次是唯一的无偏来源 | 内部评估提升 8pt，上线后用户感知为 0 |
| 回滚目标未预先指定 | 事故发生时才寻找回滚目标，平均耗时会显著增加；预先指定可把回滚耗时压到 5 分钟以内 | 把「可以回滚」当成「能快速回滚」 |

> 本页要交付的是一条 lineage：从批准目的到最终注册或回滚，中间每一环都有版本号。

### 模型更新验收的四个词

训练或微调产出的新模型，是一个需要完整验收的新被测系统。

| 术语 | 一句话解释 |
| --- | --- |
| lineage | 训练数据、基座、代码、超参、评测集的完整版本链 |
| holdout | 训练与调参全程未接触过的评估集 |
| 候选模型 | 已训练完成但尚未被接受的模型；它默认不可用 |
| 回滚目标 | 出问题时要退回到哪个具体版本，而不是「上一个」 |

> 更完整的中英对照见方法论 02 术语表；这里只收本页判断真正依赖的几个。

*依据：[mlflow/mlflow](https://mlflow.org/docs/latest/)*

### 模型更新之后分数变了，凭什么说清是哪一项造成的

一次模型更新通常同时动了三样东西：训练数据、基座模型、超参数。分数变了之后要归因给哪一项，取决于这三项当时有没有被分别记录——如果没有，这个问题在事后是无解的，只能重跑。

lineage 的作用就是让这个问题在事后可解：把训练数据版本、基座版本、超参、评测集版本、评测配置、代码 commit 六项绑成一条可检索的记录。六项齐全时，回答「87 分是怎么来的」只需要一次查询；缺任何一项，答案就只能是重跑一遍。

候选模型与回滚目标必须同时存在。上线一个新模型时，旧模型不能立刻下线——它是回滚目标，也是对照基线。很多团队在上线后立刻回收旧模型资源，于是发现问题时既无法回滚也无法对照，只能向前修。

holdout 在这一页的作用与数据集设计那一页一致，但更严格：模型更新的验收必须用一份**没有参与过任何训练与调参**的数据。用参与过训练的数据验收新模型，得到的分数与真实能力无关，且总是偏高。

*依据：[mlflow/mlflow](https://mlflow.org/docs/latest/) · [iterative/dvc](https://dvc.org/doc)*

### lineage 必须锁定的六项，各自记在哪

六项缺任一项，模型更新的归因都会退化成重跑。这张表的用途是核对你现在记到了第几项。

第三列是常见的缺失位置——多数团队记住了前两项，后四项散落在各处或根本没记。

| lineage 要素 | 记什么 | 常见的缺失位置 | 工具 |
| --- | --- | --- | --- |
| 训练数据版本 | 数据集快照的版本号或哈希 | 数据在对象存储里被原地覆盖，无版本 | DVC |
| 基座模型版本 | 权重版本或托管别名的实际解析结果 | 只记了别名，别名指向的权重已变 | MLflow model registry |
| 超参数 | 全部训练超参，含随机种子 | 只记了主要几个，种子没记 | MLflow run params |
| 评测集版本 | 验收用的数据集版本与是否为 holdout | 评测集与训练集混用，且无版本 | DVC + 访问控制 |
| 评测配置 | prompt 模板、解码参数、scorer 版本 | 散在脚本里，未随实验记录 | 评测框架配置文件 |
| 代码 commit | 训练与推理两侧的代码版本 | 只记了训练侧，推理侧未记 | Git SHA + MLflow tag |

> 六项合起来才能回答「这个分数怎么来的」。这个问题在半年后必然会被问到，而那时补记已经不可能。

*依据：[mlflow/mlflow](https://mlflow.org/docs/latest/) · [iterative/dvc](https://dvc.org/doc) · [evidentlyai/evidently](https://docs.evidentlyai.com/)*

### 这张图的 7 个节点，本页各交付什么

这张图从「批准目的」开始，是刻意的：训练与微调成本高、影响面大，先说清楚为什么做，才能在结束时判断做到了没有。

「独立 Owner」这个节点的存在理由是防止自评：训练的人和验收的人不应是同一个，否则封存 holdout 的纪律很难被真正执行。

| 架构节点 | 本页负责的部分 | 出口工件 |
| --- | --- | --- |
| 批准目的 | 写明本次训练要解决什么问题、成功标准是什么 | 训练目的与成功标准 |
| 数据 lineage | 记录训练数据来源、版本、清洗规则与授权状态 | 数据 lineage 台账 |
| 基座/代码/超参快照 | 锁定基座模型、训练代码、超参与随机种子 | 训练配置快照 |
| 封存 Holdout | 封存一份未参与任何调优的数据，控制开封次数 | 封存集与开封记录 |
| 候选比较 | 在关键切片上比较候选与现网模型，输出区间 | 候选比较报告 |
| 独立 Owner | 由独立于训练方的角色执行验收判断 | 独立验收记录 |
| 注册或回滚 | 把候选注册为新版本或执行回滚，并预先指定回滚目标 | 注册/回滚决策与目标 |

> 第一列的节点名与页面架构图逐字一致，由门禁双向校验：引用图上没有的节点、或图上画了却没解释的节点，都会让构建失败。

### lineage 必须锁定的六项

六项任一未锁定，这次训练就不可复现，也就无法解释为什么变好或变差。

右列写的是缺失时无法回答的问题。

| 锁定项 | 记录什么 | 缺失时无法回答 |
| --- | --- | --- |
| 训练数据 | 版本、快照 ID、采样规则 | 这次学到的是什么 |
| 基座模型 | 精确版本号 | 能力上限从哪来 |
| 训练代码 | commit SHA | 流程有没有变 |
| 超参 | 完整配置 | 这次和上次差在哪 |
| holdout | 版本与封存记录 | 这个分数可信吗 |
| 评测协议 | Scorer 与聚合方式 | 跨版本可比吗 |

> 第五项最容易出问题：holdout 在多轮迭代中被反复使用后，它给出的分数就不再是泛化能力的估计。

*依据：[mlflow/mlflow](https://mlflow.org/docs/latest/)*

### 这一页的验收口径：lineage 完整与无偏评估

X602-1 的 lineage 完整度是本页的地基。缺失任何一项，后面的比较都无法归因，模型也无法在半年后被复现。

X602-4 的回滚演练是唯一能证明回滚可用的手段。一个从未演练过的回滚方案，在事故时的可用性是未知的。

| 编号 | 测什么 | 关键指标 | 复测频率 |
| --- | --- | --- | --- |
| X602-1 | lineage 完整度 | 数据 / 基座 / 代码 / 超参 / 种子五项记录缺失率 = 0 | 每次训练 |
| X602-2 | 无偏评估 | 封存 holdout 每版本开封次数 ≤ 1；在参与调优数据上得出的结论标记为有偏 | 每次候选评估 |
| X602-3 | 切片不退化 | 关键业务切片相对现网模型的下降幅度 ≤ 2pt，超出即阻断注册 | 每次候选评估 |
| X602-4 | 回滚可执行 | 回滚演练成功率 = 100%；回滚耗时 ≤ 5 分钟 | 每次注册前 |

> 阈值一律是起点不是终点：带来源的按来源引用，其余是结构默认值，必须用你自己前三个版本的实测分布重标定后才能作为验收线。

### 两种看起来在验收新模型、实际结论不成立的做法

这两种做法都用了评估集，也确实做了前后对比。

问题是对比条件不成立。

| 看起来合理的做法 | 为什么它看起来是对的 | 它实际上漏掉了什么 |
| --- | --- | --- |
| 在验证集上分数提升即接受新模型 | 验证集是标准做法，提升也确实存在 | 验证集在调参过程中被反复使用，模型已经间接拟合它。必须用从未接触过的 holdout 做最终判断 |
| 整体指标提升即发布，个别切片下降属正常 | 整体提升是主要目标，局部波动难以避免 | 高风险切片下降是 blocker 而非波动。而且模型更新常常在特定切片上出现系统性退化，它不会体现在整体指标里 |

> 两条的共同修法：用未开封 holdout 做最终判断，并按风险切片单独设 blocker。

### 新模型上线后不如预期时按什么顺序查

按下表逐项排查，前两行覆盖多数情况。

排查依据是两个版本的完整 lineage，不是印象。

| 症状 | 先怀疑 | 下一步 |
| --- | --- | --- |
| 离线好线上差 | 评估集与生产分布不符 | 用近期生产采样重建评估集 |
| 某类任务明显退化 | 训练数据分布变了 | 比对两次的数据采样规则 |
| 分数一直在涨但体验没变 | holdout 被反复使用 | 重建 holdout 并重测 |
| 无法回滚到稳定版本 | 回滚目标未明确 | 为每次发布记录具体回滚版本 |

> 最后一行在模型场景尤其重要：模型文件、Prompt、检索索引必须成组回滚，只退模型会退到未测过的组合。

### 给一次模型更新补齐 lineage：约 50 分钟

不需要重新训练。把上一次更新的六项记录补出来，缺口自然显现。

1. 找出最近一次模型更新，逐项查找六项 lineage 记录。
2. 查不到的项标为 INTERNAL-UNKNOWN，并写明该向谁获取。
3. 检查 holdout：它是否在这次调参过程中被使用过？使用过几次？
4. 按风险切片重新统计新旧模型的对比结果，标出任何切片下降。
5. 为这次更新写下具体的回滚目标，含模型、Prompt、索引三项版本。

**期望结果**：典型结果是六项里有两三项查不到，且 holdout 曾被多次使用。这两项决定了此前的验收结论有多可信。

> ⚠ holdout 被使用过时不要试图「补救」。正确做法是重建一个新的 holdout，并如实标注旧结论的局限。

### 这一页的出口判据

模型注册是本课程里影响面最大的一次变更：它会同时改变所有下游行为，而且不像提示那样可以逐步灰度。

第三段要接受的是切片间的取舍：几乎不存在所有切片都提升的候选模型，哪些切片可以退化是业务决策。

| 门禁段 | 判据 | 不满足时的处置 |
| --- | --- | --- |
| 第一段 · 硬红线（任一条不满足即阻断，无例外） | lineage 五项记录缺失率 > 0 时阻断注册<br>回滚演练成功率 < 100% 时阻断注册，先修回滚链路 | 阻断发布，不进入后续两段 |
| 第二段 · 统计门禁（看置信区间，不看点估计） | 候选与现网的比较按切片给出 95% CI，以区间重叠判定是否有差异<br>单切片样本 < 30 条时该切片结论记为证据不足，不得据此宣布提升 | 样本量不足时结论为「证据不足」，不是「通过」 |
| 第三段 · 风险接受（不是通过/失败，是具名决策） | 允许退化的切片及其退化幅度，由业务 owner 逐项签字接受<br>训练数据中已知的分布偏差，由数据 owner 列出并接受 | 由具名 owner 签字接受剩余风险后放行 |

> 三段顺序执行：红线不过不看统计，统计不过不进风险接受。第三段永远需要人，不能由脚本代签。

*依据：[iterative/dvc](https://dvc.org/doc)*

### 带走一份模型更新验收清单

清单六项 lineage 加两条判据：未开封 holdout 做最终判断，风险切片单独设 blocker。

再加一条：回滚目标必须是具体版本组合，不是「上一个」。

- 六项 lineage 全部锁定并记录
- 最终判断用未开封 holdout
- 回滚目标含模型、Prompt、索引三项版本

### 来源与延伸阅读

版本号、许可证与最近提交由 GitHub API 在构建时抓取，不是手抄的。
「不能证明」一列比「能证明」更重要：拿工具给结论背书，是本模块反复拆解的错误。

- **[MLflow：实验、模型与版本的登记体系](https://mlflow.org/docs/latest/)** — 版本与血缘
  - 能证明：模型、参数、数据版本与评测结果可以被登记成可检索的关联记录，使「这个结论对应哪个模型的哪次运行」成为可查询事实而不是靠人记。回滚与事后归因都依赖这条记录。
  - 不能证明：登记的是元数据不是质量。记录齐全的模型同样可以是差模型。
  - `mlflow/mlflow` · 版本 v3.15.1（2026-08-03） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[DVC：数据与流水线的版本控制](https://dvc.org/doc)** — 数据版本
  - 能证明：评测集必须与代码一样可版本化：同一个 commit 能取回当时用的那份数据。缺了这一条，历史评测分数之间不可比，回归判断也就不成立。
  - 不能证明：版本可追不代表数据集设计合理；污染与分布偏移不会因为版本化而消失。
  - `iterative/dvc` · 版本 3.67.1（2026-03-31） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
- **[Evidently：数据与模型漂移检测](https://docs.evidentlyai.com/)** — 漂移检测
  - 能证明：输入分布漂移可以在没有标注的情况下被检出，因此可以作为线上早期告警——真实质量下降往往先表现为输入分布变了，而标注要几天后才有。
  - 不能证明：漂移不等于质量下降，反之亦然。它是调查触发器，不能直接作为阻断门禁。
  - `evidentlyai/evidently` · 版本 v0.7.21（2026-03-10） · Apache-2.0 · Apache-2.0：宽松许可，可整段引用源码并保留出处与版本锚点
