# 03 生命周期总览

## 3.1 九阶段测试生命周期

传统 V 模型把测试压在开发之后。AI 系统把被测面从"代码"扩展到"代码 + 数据 + 模型 + 提示词 + 工具 + 策略"，因此生命周期必须以**证据流**而非**开发阶段**组织。

```text
S1 依据冻结 ──► S2 需求契约 ──► S3 技术契约 ──► S4 风险与策略
                                                      │
                                                      ▼
S9 生产闭环 ◄── S8 执行与归因 ◄── S7 环境与自动化 ◄── S5 Oracle 设计
     │                                                 │
     │                                          S6 用例与数据设计
     └──────────── Trace-to-Regression ────────────────┘
```

每个阶段的产出是**下一阶段的准入条件**。跳过任一阶段，不是"提速"，而是把不确定性推给后面用返工偿还。

## 3.2 阶段契约表

这是本手册最核心的一张表。每一行都可以直接抄进你的《测试策略》文档。

| # | 阶段 | 输入 | 核心活动 | 输出工件 | 准入 | 准出 | 负责人 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **S1** | 测试依据冻结 | PRD、技术方案、接口契约、状态机、术语表、历史缺陷 | 登记版本/owner/hash/敏感级；分配稳定 `source_ref`；识别冲突 | Test Basis Pack、`source-manifest.json` | 需求进入评审状态 | 文件可访问、版本唯一、坐标稳定、优先级规则已确认、敏感数据已处理 | 测试开发 |
| **S2** | 需求契约化 | S1 产物 | 抽取角色/前置/触发/状态/不变量/异常/副作用/NFR/未知 | `requirement-contract.json` | S1 准出通过 | 每条规则有 `source_ref` 或明确 `UNKNOWN`；每个 `UNKNOWN` 都有 `unknown_class`、`stage`、`risk_level`、`unknown_scope`、owner、下一证据、到期和升级动作；只有低/中风险 `DISCOVERY` 可继续结构化，发布/风险/Oracle/准出未知一律 `DECISION_CRITICAL` 并阻断关闭；结构与语义分两道门禁 | 测试开发 + 产品 owner |
| **S3** | 技术契约化 | S2 产物 + 技术文档 | 抽取组件/接口/状态数据/失败恢复/安全/可观测；建需求—技术矩阵 | `technical-contract.json`、`requirement-design-matrix.json` | S2 准出通过 | 需求与组件/接口/状态/观察点双向可追；幂等与回滚有 owner | 测试开发 + 研发 owner |
| **S4** | 风险分析与策略 | S2 + S3 | 风险识别与打分、测试层级分配、方法选择、深度与预算 | 风险登记册、《测试策略》、方法选择记录 | S3 准出通过 | 每条高风险有指定层级、方法与 Oracle；不可行组合已记录残余风险 | 测试开发（裁决） |
| **S5** | Oracle 设计 | S4 | 为每个测试条件选定六层 Oracle 中的组合；标注独立性 | Oracle 设计记录 | S4 准出通过 | 关键金额/权限/状态有**独立于被测实现**的判据；无 Oracle 项显式 `BLOCKED` | 测试开发 + 领域 owner |
| **S6** | 用例与数据设计 | S5 | 用例生成、数据构造、切片与 holdout 划分、评测集构建 | 测试用例集、数据集与切分说明、评测集 | S5 准出通过 | 用例可追溯到 risk；数据有授权与脱敏记录；holdout 已封存 | 测试开发 |
| **S7** | 环境与自动化 | S6 | 环境登记与隔离、Mock/契约、自动化分层实现 | 环境登记册、自动化代码与流水线配置 | S6 准出通过 | 环境可重建、可回收、有审计；自动化在已知缺陷上能变红 | 测试开发 + 平台 |
| **S8** | 执行、证据与归因 | S7 | 基线执行、故障注入、失败归因、缺陷提交 | Run Receipt、缺陷记录、归因报告 | S7 准出通过 | 每次结果有完整 lineage；未知不得被编造成根因 | 测试开发 |
| **S9** | 发布判断与生产闭环 | S8 | 准出评估、Waiver、发布决定、生产监控、回归回灌 | 发布决定书、Waiver 记录、回归资产 | S8 准出通过 | 剩余风险已具名接受；回滚预案可执行；逃逸缺陷已转回归 | 发布 owner / SRE |

## 3.3 AI 增量：哪些阶段被改变了

| 阶段 | 传统做法 | AI 系统上的增量 |
| --- | --- | --- |
| S1 | 读需求文档 | 增加：模型/Prompt/知识库/工具清单也是"依据"，同样需要版本与 hash |
| S2 | 写验收标准 | 增加：把"不确定"显式建模成 `UNKNOWN`，因为模型会替你补写 |
| S3 | 读架构图 | 增加：必须问"这个状态可观察吗"，Trace/Span 是可测性前提 |
| S4 | 风险矩阵 | 增加：非确定性风险、数据漂移风险、注入与越权风险三类新风险源 |
| S5 | 写期望值 | **根本改变**：多数场景没有唯一正确答案，主力从"精确匹配"转向变形关系 + 复合 Oracle |
| S6 | 造测试数据 | 增加：切片、封存集、污染防护；数据本身成为受控版本对象 |
| S7 | 搭环境 | 增加：模型沙箱、工具录制回放、成本预算护栏 |
| S8 | 跑用例看红绿 | **根本改变**：单次结果无意义，必须重复运行并报告分布与区间 |
| S9 | 上线看监控 | 增加：持续评估（模型会漂移），在线抽样人工复核 |

## 3.4 工件流转与依赖

```text
source-manifest.json
   └─► requirement-contract.json ──┬─► risk-register.csv
   └─► technical-contract.json  ───┘        │
                                            ├─► test-strategy.md
                                            ├─► oracle-design-record.md
                                            │        │
                                            │        ├─► test-cases/
                                            │        └─► datasets/ (+ sealed holdout)
                                            │                │
                                            ├─► environment-register.md
                                            │                │
                                            └────────────────┴─► run-receipt.json
                                                                      │
                                                       ┌──────────────┼──────────────┐
                                                       ▼              ▼              ▼
                                              defect-records   release-decision   regression-assets
```

**闭包规则**：任一工件缺失，其下游工件即使存在也不得作为发布证据。校验脚本 `scripts/validate_handbook.py` 会检查这条闭包。

## 3.5 迭代节奏：这套流程要跑多久

阶段不等于甘特图上的一段时间。在迭代式交付中，S1–S5 随需求批次滚动，S6–S9 随构建滚动。

| 节奏 | 触发 | 必跑阶段 | 典型耗时（占位，需按团队校准） |
| --- | --- | --- | --- |
| 需求批次 | 新需求进入评审 | S1 → S5 | 1–3 天 / 批次 |
| 每次提交 | MR / PR | S8（快速层） | < 10 分钟 |
| 每日 | 定时 | S8（完整层）+ 漂移检查 | < 60 分钟 |
| 版本候选 | RC 打包 | S6 → S9 | 1–2 天 |
| 生产事件 | 逃逸缺陷 | S9 → S1 回灌 | 事件后 5 个工作日内 |

⚠ 表中时间是占位示例，不是行业基准。首次使用时按你团队三次真实迭代的实测值替换。

## 3.6 最小可用起步（如果你只有一周）

不要一次铺开九个阶段。按这个顺序拿到第一条完整证据链：

1. **Day 1**：只对**一个**高风险需求做 S1 + S2，产出 `source-manifest.json` 和一份 requirement contract。
2. **Day 2**：做 S4，只写这一条需求的风险与方法选择，不写全量策略。
3. **Day 3**：做 S5，为它选定 Oracle，明确哪一部分必须人工。
4. **Day 4**：做 S6 + S7，写 3 条用例 + 1 个故障注入。
5. **Day 5**：做 S8 + S9，跑出 baseline / fault / repair 三段结果，写一份发布决定书。

一周后你手上有一条**端到端可复现的窄证据链**。之后是横向复制，不是重新设计。这比"先花一个月写完整套模板"成功率高得多。
