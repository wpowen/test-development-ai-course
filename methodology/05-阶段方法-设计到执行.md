# 05 阶段方法：S5 Oracle 设计 → S8 执行与归因

---

## S5 Oracle 设计

### 为什么它必须先于用例

先写用例、再想"期望结果是什么"，几乎必然写出**自洽但无效**的测试：期望值来自被测实现本身，或来自本次模型输出。这类测试永远绿，永远不发现问题。

**规则：先固定 Oracle，再生成测试。**

### 六层 Oracle 模型

从下到上，独立性递增、成本递增。一个测试条件通常需要**多层组合**（复合 Oracle）。

| 层 | Oracle 类型 | 判断什么 | 独立性 | 成本 | 典型实现 |
| --- | --- | --- | --- | --- | --- |
| L1 | **传输层** | 能否收到响应、状态码、超时 | 高 | 极低 | HTTP 断言 |
| L2 | **结构层** | 字段、类型、枚举、必填 | 高 | 低 | JSON Schema |
| L3 | **来源层** | 引用是否真实存在且相关 | 高 | 低 | 指针存在性校验 |
| L4 | **规则层** | 是否满足业务规则与不变量 | 高 | 中 | 规则引擎、对账、状态机 |
| L5 | **语义层** | 内容是否正确、忠实、可接受 | **低** | 中 | LLM Judge、相似度、变形关系 |
| L6 | **人机层** | 高风险决定是否可接受 | 最高 | 高 | 领域 owner 复核 |

### 三条硬性约束

1. **L5 不得单独放行任何 blocker**。语义层受措辞、长度、位置、模型版本影响，只能辅助定位与批量筛查。
2. **关键金额、权限、状态、合规、不可逆副作用**必须由 L4 规则或 L6 人工判定。
3. **被测者不能出现在自己的 Oracle 里**（公理 4）。用生成答案的同一模型做 Judge，等于让考生自己批卷。

### 无标准答案时怎么办

这是 AI 测试与传统测试最大的分野。三条可用路径：

**路径 1｜转成不变量**
"回答要好"不可测；"回答不得包含其他用户订单号"、"引用必须存在于检索结果中"、"金额不得超过实付金额"可测。

**路径 2｜转成变形关系**
不问"答案对不对"，问"输入这样变，输出应该怎样变"。见 04 章变形关系表。

**路径 3｜转成分布判定**
不看单次结果，看重复 N 次的成功率分布是否落在约定区间。此时 Oracle 是"区间"而非"值"。

### Oracle 设计记录（每条测试条件一行）

```text
条件 ID     : TC-CANCEL-007
风险 ID     : R-003（已发货订单被错误取消，RPN=100）
Oracle 组合 : L2 Schema + L4 状态机不变量 + L6 领域复核
独立来源    : OPENAPI-v7#/cancel + 状态机 v2 + 财务 owner
不使用      : L5 Judge（涉及资金，禁止语义层放行）
无 Oracle 项: 无
```

若某条件**找不到独立 Oracle**，状态为 `BLOCKED`，不得用"人工目测一下"代替。

### 准出检查

- [ ] 每个关键条件的 Oracle 独立于被测实现与本次模型输出
- [ ] L5 未被用于放行任何 blocker
- [ ] 无 Oracle 的条件已显式 `BLOCKED` 并有升级路径

## S6 用例与数据设计

### 6.1 用例设计

用例必须能回答三个问题，否则不合并：

1. 它覆盖哪条 **risk id**？（无法回答 → 只能标 `EXPLORATORY`，不计入覆盖）
2. 它的期望值来自哪个 **Oracle**？
3. 它能杀死哪个**已知变异**？

**AI 生成用例的验收流程**（不要直接接受生成结果）：

```text
1. 生成候选           → 记录 Prompt 版本与输入
2. 去重与合并          → 与既有用例做语义去重
3. 追溯绑定            → 每条绑定 risk id 与 Oracle，绑不上的丢弃
4. 变异证明            → 在已知缺陷集上运行，测杀死率
5. 人工抽检            → 高风险条目逐条复核期望值
6. 合并                → 只有通过 4、5 的进入回归集
```

⚠ 典型失败：AI 生成 300 条用例，覆盖率报表很好看，变异杀死率 12%。这不是提效，是给回归集注水。

### 6.2 测试数据管理

数据是**受版本控制的一等工件**，不是脚本里的常量。

| 数据类别 | 来源 | 授权要求 | 版本要求 | 风险 |
| --- | --- | --- | --- | --- |
| 合成数据 | 规则或模型生成 | 无 | 生成脚本 + seed | 分布失真 |
| 脱敏生产数据 | 生产导出 | 需数据 owner 授权 + 脱敏审计 | 快照 ID + 脱敏规则版本 | 脱敏不彻底、再识别 |
| 人工标注数据 | 领域专家 | 标注协议 | 标注版本 + 标注员 ID | 标注不一致 |
| 公开数据集 | 外部 | 许可证核对 | 版本 + 校验和 | **污染**（可能已进训练集） |

**四条硬规则**：

1. **禁止**在测试中使用未脱敏的真实个人信息、真实支付账号、生产密钥。
2. **切分必须先于调优**：dev 用于迭代，sealed holdout 只在发布判断时开封一次。反复开封的集合不再是 holdout，必须重建。
3. **切片必须按业务风险划分**，不是随机划分。平均分永远会掩盖高风险切片。
4. **污染检查**：公开数据集要检查是否可能已被训练；自建集要检查是否被写入 Prompt 示例。

**切片设计示例（订单取消）**：

```text
slice:normal_cancel       常规未发货取消          权重 40%
slice:paid_refund         已支付需退款            权重 25%   ← 资金风险
slice:shipped_reject      已发货应拒绝            权重 15%   ← blocker 切片
slice:non_owner           非本人操作              权重 10%   ← 权限 blocker
slice:concurrent          并发重复取消            权重 10%   ← 幂等
```

**blocker 切片规则**：标记为 blocker 的切片一旦出现失败，即使总分上升也不得发布。

### 6.3 评测集构建（AI 特有）

一个可用的评测集必须包含**五类样本**，缺一类就有对应的盲区：

| 类别 | 作用 | 最低占比（占位） |
| --- | --- | --- |
| 正例 | 常规能力 | 40% |
| 边界例 | 阈值、长度、极值 | 15% |
| 负例 | 应当拒绝或报错 | 20% |
| 冲突/缺失例 | 应输出 `BLOCKED`/`UNKNOWN` | 15% |
| 越权/攻击例 | 应被授权层拒绝 | 10% |

另需单独记录**期望拒答（REFUSED）** 与**期望截断（INCOMPLETE）** 的样本及其判定规则——这两类不是失败，是正确行为。

### 准出检查

- [ ] 每条用例可追溯到 risk 与 Oracle
- [ ] 生成用例已通过变异杀死率验证
- [ ] 数据有授权、脱敏、版本记录；holdout 已封存且未被使用
- [ ] 切片按业务风险划分，blocker 切片已声明
- [ ] 评测集五类样本齐备

## S7 环境与自动化

### 7.1 测试环境管理

| 环境级别 | 用途 | 数据 | 隔离要求 | 回收 |
| --- | --- | --- | --- | --- |
| L0 本地 | 单元、契约 | 合成 | 进程级 | 即时 |
| L1 CI 临时 | 集成、评测 | 合成 + 固定夹具 | 容器/命名空间级 | 任务结束即销毁 |
| L2 共享测试 | 系统、E2E | 脱敏快照 | 租户级 | 定期重置 |
| L3 预发 | 验收、性能 | 脱敏近生产 | 网络级 | 版本周期 |
| L4 生产影子 | 影子流量 | 真实（只读） | **强制只读 + 审计** | 不适用 |

**环境登记册必填字段**：`env_id`、`用途`、`数据来源与授权`、`可写权限范围`、`创建方式(IaC 路径)`、`回收策略`、`owner`、`成本归属`。

**三条硬规则**：

1. 环境必须**可重建**（IaC 或脚本），不允许存在"只有某人知道怎么搭"的环境。
2. 测试环境**默认无生产写权限**；需要写时走临时凭据 + 审计。
3. 临时环境必须有**自动回收**，否则成本会在三个月内失控。

### 7.2 外部依赖策略

| 依赖类型 | 首选策略 | 何时用真实 |
| --- | --- | --- |
| 内部服务 | 契约测试 + 消费者驱动 | 集成层关键路径 |
| 第三方支付/短信 | 沙箱 + 录制回放 | 预发验收一次 |
| **大模型 API** | 录制回放 + 确定性夹具 | 模型集成层（L2 成熟度）专门跑 |
| 向量库 | 本地实例 + 固定快照 | 检索评测 |
| 消息队列 | 真实中间件 + 可控注入 | 幂等与重投必须真实 |

⚠ 模型调用**不要**默认打真实 API：不可复现、有成本、有速率限制、有数据外发风险。默认走录制回放，真实调用作为独立的、被显式声明的一层。

### 7.3 自动化分层

投入产出比排序（从高到低）：契约 > 集成 > 单元 > 评测 > E2E > 性能。**不要**从 E2E 开始。

**自动化的准入门槛**（写在流水线里）：

```text
一个自动化用例可以合并，当且仅当：
  1. 在预埋缺陷上稳定变红（≥3 次连续）
  2. 在干净基线上稳定变绿（≥3 次连续）
  3. 失败信息足以定位到层（输入/模型/检索/环境/Scorer）
  4. 运行时间在其所属层级预算内
  5. 不依赖执行顺序、不依赖上次残留状态
```

**Flaky 治理**：连续 5 次运行中出现 ≥1 次非确定性失败的用例，自动标记 `quarantine`，移出阻断集但**保留运行并统计**。禁止直接删除或加 retry 掩盖。

### 7.4 CI 分层门禁

| 层 | 触发 | 预算 | 阻断范围 |
| --- | --- | --- | --- |
| Gate-1 | 每次提交 | < 10 min | 静态检查、单元、契约、Schema |
| Gate-2 | MR 合并前 | < 30 min | 集成、关键 E2E、评测冒烟、安全扫描 |
| Gate-3 | 每日/RC | < 2 h | 完整评测、变异、性能、攻击集 |
| Gate-4 | 发布前 | 人工参与 | holdout 开封、人工抽检、发布决定 |

**fail-closed 原则**：门禁执行失败（脚本挂了、环境没起来）等同于**不通过**，不得视为跳过。

### 准出检查

- [ ] 环境可重建、可回收、有 owner 与成本归属
- [ ] 模型调用默认走录制回放；真实调用被显式标注为独立层
- [ ] 每个自动化用例满足五条准入门槛
- [ ] Flaky 用例进入 quarantine 而非被删除
- [ ] 门禁失败等同不通过

模板：`templates/09-environment-register.md`、`checklists/04-automation-merge.md`

## S8 执行、证据与归因

### 8.1 一次有效执行的三段结构

任何"我验证过了"都必须能拆成三段，缺一段即无效：

```text
① baseline   干净版本 → 期望全绿      exit 0
② fault      注入已知缺陷 → 期望变红   exit 1（且指名 failed_oracle_ids）
③ repair     修复/重置 → 期望恢复绿    exit 0
```

只有 ① 的绿色不证明任何事：它可能是因为测试根本不检查。**0/1/0 精确退出码**是本方法论对"可运行"的定义。

### 8.2 Run Receipt（运行收据）

```json
{
  "run_id": "<uuid>",
  "timestamp": "<ISO8601>",
  "trigger": "mr-1234 | scheduled | manual",
  "code_version": "<git sha>",
  "input_baseline_id": "order-cancel-2026-08-10",
  "dataset_version": "eval-v3",
  "dataset_split": "dev",
  "model": {"provider": "<name>", "id": "<model-id>", "params": {"temperature": 0}},
  "prompt_version": "task-v1.2",
  "tool_versions": {"retriever": "v7", "scorer": "v2"},
  "repetitions": 5,
  "results": {"pass": 47, "fail": 3, "blocked": 0, "refused": 1},
  "slice_results": {"shipped_reject": {"pass": 9, "fail": 1, "blocker": true}},
  "failed_oracle_ids": ["ORC-CANCEL-004"],
  "cost": {"tokens": 128000, "usd": 0.00},
  "latency": {"p50_ms": 0, "p95_ms": 0},
  "verdict": "FAIL",
  "decided_by": "<name/role>",
  "evidence_paths": ["reports/baseline.json", "traces/run-xxx.jsonl"]
}
```

Schema：`schemas/run-receipt.schema.json`。**缺少 `model`、`dataset_version`、`prompt_version` 三者之一的收据不得作为发布证据。**

### 8.3 五层归因法

失败时**按顺序**排查，一次只改一个变量：

```text
L1 输入与数据   输入变了吗？数据集版本变了吗？夹具被污染了吗？
L2 模型/Prompt  模型别名漂移？Prompt 版本？参数？缓存命中差异？
L3 检索与工具   索引重建？分块变了？工具版本？权限变了？
L4 执行环境     环境差异？并发？超时？依赖服务状态？
L5 Scorer/阈值  Judge 版本？阈值？聚合口径？
```

若**无法区分**这五层，正确输出是 `UNKNOWN + 升级人工`，而不是让模型补一个听起来合理的根因。这是本阶段最重要的一条纪律。

### 8.4 缺陷管理

**Severity（后果）与 Priority（紧急度）是两个独立字段，禁止合并。**

| Severity | 定义 | 示例 |
| --- | --- | --- |
| S1 阻断 | 不可逆资金损失、大范围数据泄露、核心链路不可用 | 已发货订单被自动退款 |
| S2 严重 | 主要功能错误、数据错误可恢复、权限越界（无泄露） | 退款金额计算错误 |
| S3 一般 | 次要功能异常、体验受损、有绕行方案 | 状态提示文案错误 |
| S4 轻微 | 文案、样式、非关键日志 | 按钮对齐 |

**AI 系统特有缺陷分类**（传统分类装不下，必须单列）：

| 类别 | 定义 | 归属判定 |
| --- | --- | --- |
| `HALLUCINATION` | 输出无来源支持的事实 | 检查 `source_refs` 存在性 |
| `UNFAITHFUL` | 有检索证据但结论与之矛盾 | 忠实度 Oracle |
| `REFUSAL_WRONG` | 该答的拒答 / 该拒的回答了 | 期望拒答集 |
| `SCHEMA_DRIFT` | 结构化输出不符合契约 | Schema 校验 |
| `TOOL_MISUSE` | 错误工具、越界参数、越权调用 | 工具策略层 |
| `NON_DETERMINISM` | 同输入结果不稳定超出约定区间 | 重复运行分布 |
| `DRIFT` | 相同版本随时间行为变化 | 持续评估基线 |
| `INJECTION` | 不可信内容改变了执行 | 攻击集 |
| `LEAKAGE` | 跨租户/敏感字段泄露 | DLP + 授权断言 |
| `COST_REGRESSION` | 质量持平但成本/延迟显著劣化 | 单位成功成本 |

**缺陷记录必填**：`severity`、`priority`、`分类`、`复现步骤或 run_id`、`风险 ID`、`归属层(L1–L5)`、`是否可复现(含重复次数)`、`Oracle 依据`。

⚠ 非确定性缺陷必须写明"N 次中复现 M 次"，禁止写"偶现"。

### 8.5 去重与聚类

AI 失败常常成百上千条。允许用模型做**聚类候选**，但：

- 聚类结果必须保留**每条原始证据**，不得只留摘要；
- 被聚为一类的样本中，**至少抽检 3 条**确认同因；
- 无法归类的样本进入 `UNKNOWN` 桶并单独跟进——`UNKNOWN` 桶不允许被清空以求好看。

### 准出检查

- [ ] 每次结论都有完整 lineage（数据/Prompt/模型/工具/Scorer 五要素）
- [ ] 0/1/0 三段结果齐备
- [ ] 失败已定位到层，或明确标记 `UNKNOWN` 并升级
- [ ] Severity 与 Priority 分别填写
- [ ] AI 特有缺陷已使用专门分类
- [ ] `UNKNOWN` 桶非空时不得声明"已全部归因"

模板：`templates/10-defect-severity-taxonomy.md`、`schemas/run-receipt.schema.json`
