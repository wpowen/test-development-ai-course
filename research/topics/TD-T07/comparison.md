# TD-T07 双运行比较

## Agreements
两次运行都拒绝“随机生成越多越完整”。边界值适合有序域和阈值，组合测试适合多个离散因子交互，property-based testing 适合能表达跨输入成立的不变量，fuzzing 适合面向解析器、协议与未知输入的探索。所有生成方法都需要合法域、禁止状态、资源预算与 Oracle。发现失败后必须保存输入、seed、工具版本、系统版本，并优先收缩为最小反例，才能转成稳定回归。

## Disagreements
方法选择运行强调 NIST t-way 覆盖和 covering array 可系统压缩组合；复现性审查提醒 t-way 不是业务完整性，约束错误会生成无效组合。前者认为固定 seed 足以复跑生成序列，后者指出时间、依赖、调度、数据库和工具版本仍可能漂移。前者把 fuzz 视作扩大未知空间的手段，后者强调对生产写接口、付费调用和个人数据缺少授权时，fuzz 会制造安全与合规事故。

## Adjudication
裁决先写 failure model，再选择最小充分方法：阈值错误用 boundary；有限规则交互用 decision/combination；可表达不变量用 property 并开启 shrink；未知字节/语法面且有隔离授权时才用 fuzz。可组合方法，但必须分别报告覆盖口径。当前 fixture 选择 boundary、decision table 与 property，明确拒绝无约束随机 fuzz；故障注入破坏退款幂等性，固定 seed 生成反例并收缩到 key+repeat。它证明回放合同可执行，不证明数据代表真实流量或生产 fuzz 安全。

裁决还保留“停止生成”这一合法结果：当业务状态机没有批准版本、跨字段约束互相冲突、Oracle 只能从当前实现推导或环境含不可逆副作用时，增加样例会扩大噪声和风险。此时应先补 basis、权限和隔离，而不是让 AI 猜测合法域。生产迁移需要把 discard rate、无效输入率、收缩重放率与副作用事故数一起报告，避免只展示发现数量。
