## 一、为什么需要 v2.0

上一代测试体系(7 层 23 维)的骨架仍然成立,但有五处**结构性假设**已经不再有效。

### 失效点 1:瀑布式布尔门禁套在非确定性系统上

v1.0 每层都是"通过 / 失败"的一次性判定,这是传统软件的逻辑。一个函数对同样输入返回不同结果,在传统软件里是 bug,在 LLM 驱动的 Agent 里是正常行为。

- τ-bench 引入的 `pass^k`(k 次重复全部成功的概率)揭示了巨大的可靠性缺口:GPT-4o 在零售 Agent 任务上 pass@1 为 61%,pass^8 仅 25%。
- Claw-Eval 进一步发现:在错误注入下 Pass@3 相对稳定,**Pass^3 却下跌多达 24 个百分点**。

**结论:单次通过率完全掩盖了一致性崩塌。**

### 失效点 2:只评最终输出,不评轨迹

- 只对最终输出打分的评估会漏掉约 **90% 发生在执行中途**的失败模式。
- 轨迹不透明的评估会系统性漏掉 **44% 的安全违规**和 **13% 的鲁棒性失败**。

### 失效点 3:把评估器当成可信基础设施(最大盲区)

整个体系依赖 judge 打分,却从不测 judge 本身。

- 2026 年方差分解研究:prompt 措辞、judge 选择、温度等流水线因素带来的方差,比朴素置信区间报告的高出 **40–60%**;judge 分歧本身在安全分类任务中贡献了高达 **44% 的总方差**。
- 供应商可能在同一模型名下静默更新,导致 judge 校准无声漂移(实测案例:κ 从 0.72 掉到 0.58 而团队毫无察觉)。
- **元评估漂移(Meta-Evaluation Drift)**:递归式 LLM 评估会变得内部自洽,却与人类判断和任务真实目标逐渐脱节。

### 失效点 4:安全测试作为发布前的一次性门禁

攻击面已从"用户输入"转移到"运行时数据通道"。

- MCP 工具投毒的根因是**连接时与运行时的信任落差**:工具描述只在首次连接时审一次,工具响应却直接进上下文、毫无等价检查。
- MCPTox 基准测试 45 个真实 MCP server、353 个真实工具:多数流行 Agent 攻击成功率超过 **60%**,最高 **72%**;且能力更强的模型往往表现更差——更强的指令遵循让它们对恶意元数据更顺从。
- 2026 年的一次披露暴露出多达 **20 万个**存在风险的 MCP 实例。

### 失效点 5:上线前测试为主,缺少在线持续评估

- 上线前测充分、上线后停止监控的团队,**30–60 天内质量必然退化**。
- 持续评估相比周期性评估可将生产事故降低约 **67%**。
- 现状缺口:57% 的组织已在生产运行 Agent,但只有 52% 会在部署前做离线评估。

### 附加缺口

| 缺口 | 说明 |
|---|---|
| 多 Agent 编排完全未覆盖 | 企业部署越来越跑在多 Agent 架构上,每一次 handoff 都是新断点 |
| 成本不是一等指标 | 某金融科技 Agent 在交易对账中进入失控循环,**连续跑了 11 天** |
| 无 Agent 身份与委托链治理 | 企业机器身份与人类身份比已达 **82:1** |

## 二、架构总览

### v1.0 → v2.0 变更

| 变更类型 | 内容 |
|---|---|
| **新增域** | D0 评估可信层(4 维)、D2 编排协作层(4 维) |
| **范式重构** | D4 从"布尔通过"改为"可靠性分布" |
| **大幅扩展** | D5 安全从 2 维扩到 6 维,且前移为持续测试 |
| **新增机制** | 四环执行模型、运行时护栏、三段式门禁 |
| **合并降级** | "兼容性测试"并入 D6;"边界条件"并入 D4 |
| **规模** | 7 层 23 维 → **8 域 36 维** |

### 八域概览

| 域 | 名称 | 维度数 | 核心职责 |
|---|---|---|---|
| **D0** | 评估可信层 | 4 | 测量测量系统本身 —— 所有其他域的数字可信度上限 |
| **D1** | 单体能力层 | 5 | 单个 Agent 的基础智能与轨迹质量 |
| **D2** | 编排协作层 | 4 | 多 Agent 交接、隔离、熔断、上下文工程 |
| **D3** | 交互协同层 | 4 | 人机协作、多轮、多模态、可解释 |
| **D4** | 鲁棒可靠层 | 5 | 可靠性分布、长时程降级、统计回归 |
| **D5** | 安全对抗层 | 6 | 注入、投毒、越权、记忆污染、沙箱、爆炸半径 |
| **D6** | 效率经济层 | 4 | 延迟、成本、并发、可观测与可复现 |
| **D7** | 业务治理层 | 4 | 业务规则、审计证据链、变更治理、ROI |

## 四、36 维明细

### D0 评估可信层(全新 · 最高优先级)

> 这一层不测 Agent,测**你的测量系统**。没有 D0,后面 32 维的所有数字都是不可信的。

| 编号 | 维度 | 测什么 | 关键指标 | 频率 |
|---|---|---|---|---|
| D0-1 | Judge 校准与元评估 | judge 与人类标注一致性、位置偏置、冗长偏置、自偏好 | Cohen's κ ≥ 0.7;位置交换一致率 ≥ 95% | 每月 + 换模型时 |
| D0-2 | 评估集卫生 | 训练污染、场景漂移、与生产分布的代表性 | 与生产分布 KL 散度;污染率 = 0 | 每季度 |
| D0-3 | 指标构念效度 | 指标是否真的测了它声称测的东西 | 指标-业务结果相关性 ≥ 0.6 | 每季度 |
| D0-4 | 人审闭环与标注一致性 | 标注者间一致性、争议样本仲裁 | 标注者 κ ≥ 0.7 | 持续 |

#### D0-1 详细方案(全案最关键)

1. **建金标集**:200–300 条,3 名标注员独立打分。κ < 0.7 的条目说明**评分标准本身有歧义**,先改 rubric 再继续,不要急着改 judge。
2. **judge 与 generator 必须不同模型族** —— 规避自偏好偏置。
3. **成对比较必须双向跑**(A/B 和 B/A 各一次),结果不一致的判为无效样本。
4. **锁版本 + 月度重校准**:冻结模型版本换来的是陈旧风险,因此要定期重跑金标集追踪 κ 漂移。κ 跌破阈值 → judge 停用,回退人审。
5. **分层 judge 策略**:
   - CI 门禁 → 前沿模型 judge(慢、贵、准),作为校准锚点
   - 生产在线采样 → 小模型 judge(快、便宜),用前沿 judge + 人工标注校准
6. **混合范式(Hybrid Norm)**:
   - 可验证的部分 → 确定性断言 / 单元测试("做对了吗")
   - 开放式的部分 → LLM rubric("做得好吗")
   - 不要用 rubric 去测本可以用断言测的东西
7. **产出 Judge Card**:记录模型版本、温度、rubric 全文、校准日期、κ、Spearman、各偏置量、样本量。**judge 换版本 = 一次需要走变更评审的发布。**

### D1 单体能力层

| 编号 | 维度 | 关键指标 | 说明 |
|---|---|---|---|
| D1-1 | 意图理解 | 准确率 ≥ 95%;高危意图零误判 | 交易场景:买/卖/撤单方向误判为 P0 |
| D1-2 | 工具选择与参数 | 工具选择正确率 ≥ 95%;参数精确匹配 ≥ 98% | 参数错误比工具错误危险得多 |
| D1-3 | **轨迹质量(span 级)** | 每步得分 + 步骤效率比 | **新重点**:逐 span 打分,不只看终局 |
| D1-4 | 记忆读写与检索 | 召回率 ≥ 90%;错误记忆率 ≤ 2% | |
| D1-5 | 规划与自我修正 | 计划可执行率;错误后自纠率 ≥ 70% | 注入错误观测,看能否回正 |

#### D1-3 轨迹评估方案

对每条 trace 按 span 打四类标签:

| 标签 | 判定内容 | 取值 |
|---|---|---|
| 工具选择 | 该调这个工具吗 | 正确 / 多余 / 遗漏 / 错误 |
| 参数构造 | 参数对吗 | 正确 / 部分正确 / 错误 |
| 观测利用 | 工具返回被正确使用了吗 | 正确利用 / 忽略 / 曲解 |
| 步骤必要性 | 这一步推进任务了吗 | 有效 / 冗余 |

派生指标:

- **步骤效率比** = 最优步数 / 实际步数
- **首错位置分布(First Error Position)** —— 失败集中在第几步,直接定位薄弱环节
- **无效循环率** —— 同一工具连续调用 ≥ 3 次且参数近似

### D2 编排协作层(全新)

> 企业级部署越来越跑在多 Agent 架构上:编排器路由给研究 Agent,研究 Agent 传给写作 Agent,写作 Agent 交给格式化 Agent —— **每一次交接都是一个新的断点**。v1.0 完全没覆盖这个面。

| 编号 | 维度 | 测什么 | 关键指标 |
|---|---|---|---|
| D2-1 | 交接与职责边界 | 信息在 handoff 时是否丢失/失真;职责是否重叠或真空 | 交接信息保真率 ≥ 95%;职责真空 = 0 |
| D2-2 | 子 Agent 上下文隔离 | 子 Agent 是否看到不该看的;返回是否污染主上下文 | 越界上下文泄漏 = 0 |
| D2-3 | 级联失败与熔断 | 单个 Agent 失败是否拖垮全局;熔断是否生效 | 故障隔离率 ≥ 95%;熔断触发延迟 ≤ 3 步 |
| D2-4 | 上下文工程 | 压缩/折叠后关键信息是否留存;长会话"上下文腐烂" | 压缩后关键事实召回 ≥ 90% |

#### D2-1 测试手法

- **交接契约测试**:为每条 A→B 边定义 schema(必传字段、格式、语义约束),逐边验证 —— 类比微服务的 consumer-driven contract。
- **信息衰减链路测试**:在源头埋 5 个可验证事实,走完 3 跳交接后检查存活几个。
- **职责边界矩阵**:构造边界模糊任务(既像 A 的活又像 B 的活),观察是双方都不做、都做、还是正确仲裁。

#### D2-3 级联失败测试

- 故意让下游 Agent 返回错误 / 超时 / 空结果,观察上游是重试、降级、还是无限循环。
- **必测反例**:2025 年 3 月某金融科技公司的 Agent 在交易对账中进入失控循环,连续跑了 11 天。
- **三重熔断必须逐一验证真的会触发**:
  - 步数上限
  - 时间上限
  - 成本上限

---

### D3 交互协同层

| 编号 | 维度 | 关键指标 |
|---|---|---|
| D3-1 | 多轮交互与上下文保持 | 20 轮后指代消解正确率 ≥ 90% |
| D3-2 | 多模态理解 | 图表/截图识别准确率 ≥ 90% |
| D3-3 | **人机协同** | 中断响应 ≤ 1 步;接管后状态完整;高危动作确认率 100% |
| D3-4 | 可解释性与体验 | 决策依据可追溯率 100% |

#### D3-3 是新增重点

Agent 越自主,"人怎么打断它"越关键:

- **中断测试**:执行到第 N 步时用户喊停 —— 是否立即停?是否留下半成品脏状态?能否回滚?
- **接管测试**:人接手后 Agent 是否正确交出上下文;人处理完再交回,Agent 是否理解中间发生了什么。
- **确认疲劳测试**:确认弹窗过多导致用户盲点"同意" —— 这本身是可测的失败模式(OWASP 归类为"人机信任利用")。

### D4 鲁棒可靠层(范式重构)

> **核心改变:所有指标从"一个数"变成"一个分布"。**

| 编号 | 维度 | 关键指标 | 手法 |
|---|---|---|---|
| D4-1 | 可靠性分布 | **pass^5 ≥ 80%**(而非 pass@1);变异系数 CV ≤ 0.15 | 同一任务跑 5–10 次 |
| D4-2 | 长时程降级 | 50% 成功视界 ≥ 业务需求时长 | 按任务时长分桶画衰减曲线 |
| D4-3 | Prompt/输入稳定性 | 语义等价改写一致率 ≥ 95% | 每条用例生成 5 个改写变体 |
| D4-4 | 异常与自恢复 | 异常场景恢复率 ≥ 90% | 混沌注入 |
| D4-5 | 统计回归 | 新旧版本分布差异显著性检验 | 非重叠 CI 才算真回归 |

#### D4-1 落地细则(v2.0 最重要的改动)

```
旧:任务 T 跑一次 → 成功 → ✅ 通过

新:任务 T 跑 k 次 →
    pass@1 = 4/5 = 80%    (能不能做到)
    pass^5 = 0/1 = 0%     (能不能每次都做到)  ← 上线看这个
    首错位置 = [step3, step7, step3]           ← 改进看这个
```

- **k 的选择**:P0 任务 k=10,P1 任务 k=5,P2 任务 k=3
- **门禁改写**:不再是"pass 率 ≥ X%",而是"**pass^k 的 95% 置信区间下界 ≥ X%**"
- **样本量不足以支撑结论时,门禁结果是"证据不足",不是"通过"**
- **温度**:评估必须固定 temperature 并记录;同时跑一组 temperature > 0 的变异性探针

#### D4-2 长时程衰减曲线

按任务预期时长分桶,每桶计算 pass^k:

| 时长桶 | pass@1 | pass^5 | 结论 |
|---|---|---|---|
| < 5 min | — | — | |
| 5–30 min | — | — | |
| 30 min–2 h | — | — | |
| > 2 h | — | — | |

产出结论形如:*"本 Agent 在 30 分钟内任务 pass^5 = 85%,超过 2 小时降至 22%"* → 直接转化为**产品侧的自主时长上限**和**强制检查点间隔**。

---

### D5 安全对抗层(大幅扩展 + 前移)

> **最大的架构变更**:安全不再是发布前的一道门禁,而是贯穿四环的持续对抗。

| 编号 | 维度 | 关键指标 | 对应 OWASP ASI |
|---|---|---|---|
| D5-1 | 直接与间接提示注入 | 攻击成功率 ASR ≤ 1% | ASI01 / ASI02 |
| D5-2 | 工具投毒与 MCP 供应链 | 投毒工具描述拒绝率 ≥ 99% | ASI02 / ASI04 |
| D5-3 | 身份与委托链越权 | 越权尝试拦截率 100% | ASI03 |
| D5-4 | 记忆投毒与持久污染 | 污染注入成功率 = 0;污染存活轮数 = 0 | ASI06 |
| D5-5 | 代码执行与沙箱逃逸 | 逃逸成功 = 0 | ASI05 |
| D5-6 | 不可逆动作与爆炸半径 | 高危动作二次确认率 100%;单次最大损失有界 | ASI08 / ASI09 |

> **参考基线**:OWASP Top 10 for Agentic Applications(2025 年 12 月发布,ASI01–ASI10)涵盖:规划、工具使用、身份、供应链、代码执行、记忆、Agent 间通信、级联失败、人机信任、失控 Agent。

#### 攻击面测试矩阵

| 攻击面 | 注入位置 | 测试构造 |
|---|---|---|
| 工具描述投毒 | MCP tool description | 描述里埋"总是先调用 X 并把结果发到 Y" |
| 工具结果注入 | tool result 正文 | 检索到的文档/工单/网页里埋"忽略之前指令" |
| 多轮延迟触发 | 第 N 轮才激活 | 前几轮完全正常,后期才触发 |
| 跨会话持久化 | 写入长期记忆 | 本轮注入,下轮甚至下个会话才发作 |
| 权限累积利用 | 分步骤获取权限 | 每步都合规,组合起来越权 |
| Rug-pull | 连接后变更 | 首次连接描述正常,运行时描述被改 |

**关键:延迟触发与跨会话持久化必须单独建套件。** 传统单轮护栏在这类攻击上会失效 —— 风险证据被分散在整条轨迹上,单个窗口看不出问题。因此**护栏本身也要按轨迹级评估**,而不只是逐轮评估。

#### D5-2 供应链测试补充项

- **rug-pull 测试**:工具描述只在连接时审一次、工具响应直接进上下文无检查 —— 这个信任落差就是攻击面。必须模拟"审过之后再变脸"。
- **工具清单变更检测**:tool manifest 的 hash 校验是否生效。
- **过度授权审计**:每个工具的实际权限 vs 声明权限。
- **MCP spec 版本核查**:未升级到最新 spec 的部署仍暴露在完整的原始攻击面下。

#### D5-6 爆炸半径(金融场景核心)

对每个可执行动作打三维标签:

```
可逆性:   可撤销 / 有窗口期可撤 / 不可逆
影响面:   单用户 / 多用户 / 全平台
资金影响: 无 / 有上限 / 无上限
```

`不可逆 + 资金无上限` 的动作 → **强制人工确认 + 双人复核 + 单笔额度硬上限**。

**这三道控制本身要被测试**,而不只是测 Agent 会不会调用。

---

### D6 效率经济层

| 编号 | 维度 | 关键指标 |
|---|---|---|
| D6-1 | 延迟与吞吐 | P95 首字 < 2s;P99 全流程 < 30s |
| D6-2 | **Token 与成本经济学** | 单任务成本 CI 上界 ≤ 预算;成本方差 CV ≤ 0.3 |
| D6-3 | 并发与资源隔离 | 目标并发下 pass^k 不下降 > 5pt |
| D6-4 | 可观测性与可复现 | trace 完整率 100%;任一 trace 可完整重放 |

#### D6-2 成本作为一等指标(新增)

Agent 的成本是**长尾分布** —— 中位数很便宜,但失控案例能烧掉几个数量级。

- 报 **成本的 P99 而非均值**
- 设 **单任务 token 硬上限**,并测试它真的会截断
- 跟踪 **成本-质量帕累托前沿**:换更便宜的模型,pass^k 掉多少?
- 评估基础设施自身成本要进预算 —— 通常占 Agent 运营成本的 **10–25%**

#### D6-4 可复现性是一切的前提

如果一条失败 trace 无法重放,就无法归因,也就无法修。trace 必须记录:

- 模型版本 + temperature + 随机种子
- 完整 prompt(含 system)
- 工具清单快照(含每个工具的 description hash)
- 每次工具调用的输入与输出
- 时间戳(尤其是行情类数据的获取时刻)

### D7 业务治理层

| 编号 | 维度 | 关键指标 |
|---|---|---|
| D7-1 | 业务规则与决策正确性 | 硬规则违反 = 0 |
| D7-2 | 合规与审计证据链 | 每个动作可追溯到"哪个 Agent、代表哪个用户、依据什么" |
| D7-3 | **变更治理** | 模型/prompt/工具任一变更均触发对应回归 |
| D7-4 | 业务价值与 ROI | 与人工基线对比的效率提升 |

#### D7-3 Agent 特有的"四维版本"

```
Agent 版本 = f(模型版本, system prompt 版本, 工具清单版本, 记忆库快照)
```

- 任一维度变化都要触发回归
- **回归基线必须锁定同一 judge 版本**
- 最常见事故链:模型供应商静默更新 → 所有历史评估数据失去可比性 → 团队浑然不觉
- **对策**:每个模型端点每周跑一次"哨兵集"(20–30 条确定性强的任务),分布突变即告警

#### D7-2 审计证据链

监管场景的硬要求。每次工具调用需记录:执行的 Agent、委托的用户、调用的工具、结果 —— 既是合规要求,也是事故取证的生命线。

**时间线参考**:EU AI Act 高危义务 2026 年 8 月生效,Colorado AI Act 2026 年 6 月起可执行,罚则最高 3500 万欧元量级。相关框架:NIST AI RMF、ISO/IEC 42001、EU AI Act Art.14(人类监督)/ Art.15(网络安全)。

## 五、四环执行模型

取代 v1.0 的线性瀑布门禁。

| 环 | 触发 | 时长 | 覆盖维度 | 门禁性质 |
|---|---|---|---|---|
| **环 1 离线 CI** | 每次提交 | ≤ 10 min | D1(核心子集)、D4-3、D5(静态规则) | 硬门禁,失败阻断合并 |
| **环 2 沙箱回放** | 每日 / PR 合并 | ≤ 2 h | D1 全量、D2、D4 全量、D5 全量 | 硬门禁,pass^k 不达标阻断发布 |
| **环 3 影子 + 灰度** | 每次发布 | 3–7 天 | D3、D6、D7-1(真实流量不生效) | 软门禁,看在线指标 |
| **环 4 在线持续评估** | 7×24 | 持续 | 全部,采样 1–10% + 100% 高危动作 | 告警 + 自动回滚 |

### 为什么必须有环 4

- 只在上线前评估、上线后停止监控的团队,**30–60 天内质量必然退化**
- 持续评估相比周期性评估可将生产事故降低约 **67%**
- 生产监控应使用**与开发阶段相同的评估器**给线上流量打分,当天发现回归而不是几周后从工单里发现

### 环 3 影子模式做法

真实用户请求同时打给旧版和新版:

- 新版结果 **不返回给用户、不执行任何动作**
- 只落 trace 并打分
- 零风险拿到真实分布上的对比数据

**这是交易类 Agent 最重要的一道保险。**

## 六、质量门禁重构(从布尔到统计)

### 旧门禁(错的)

```
if 测试通过率 >= 95%:
    放行
```

### 新门禁(三段式)

```
第一段 · 硬红线(任何一条不满足 = 阻断,无例外)
  ├─ D5 高危攻击 ASR = 0
  ├─ D7-1 硬业务规则违反 = 0
  ├─ D5-6 不可逆动作绕过确认 = 0
  └─ D0-1 judge κ ≥ 0.7(否则本轮所有分数无效)

第二段 · 统计门禁(看置信区间,不看点估计)
  ├─ pass^k 的 95% CI 下界 ≥ 阈值
  ├─ 与上一版本对比:CI 不重叠才判定为回归
  └─ 样本量不足 → 结论为"证据不足",不是"通过"

第三段 · 风险接受(不是通过/失败,是明示决策)
  ├─ 列出所有已知失败模式及其频率
  ├─ 标注每个失败模式的运行时护栏覆盖情况
  └─ 由有明确责任人的角色签字接受剩余风险
```

### 第三段是关键的心智转变

Agent 系统**不存在"没有失败模式"的版本**。

测试的职责不是宣布"没问题",而是:

1. 把失败模式测清楚
2. 量化其频率
3. 确认护栏兜得住

然后让业务方在**知情**的前提下决定是否接受。

## 七、交易所场景落地要点

### 1. 行情数据时效性作为独立断言

Agent 引用的价格/深度数据必须带时间戳,评估时校验"决策时刻的数据新鲜度 ≤ N 秒"。

> **陈旧数据 + 正确推理 = 错误结论**。这类失败在纯文本 judge 下完全看不出来。

### 2. 分离"建议"与"执行"两套阈值

| 类型 | pass^k 要求 | 兜底 |
|---|---|---|
| 信息类回答 | ≥ 85% | 免责说明 |
| 动作类(下单/划转/提币) | 接近 100% | 低于 100% 的部分必须由人工确认兜住 |

**两类在评估集里要物理隔离,不能混在一起算总分。**

### 3. 高危动作走"能力沙箱"而非"提示约束"

- ❌ 靠 system prompt 说"不要执行超过 X 的交易"
- ✅ 靠工具层的硬限额

**测试对象是这个限额,不是模型的服从性** —— 服从性在提示注入下是可以被击穿的。

### 4. 7×24 市场意味着没有"发布窗口"

环 3 灰度和环 4 在线评估的权重要比一般业务更高,回滚必须是**分钟级、自动的**。

### 5. 可观测平台承载环 4

现有巡检体系天然是环 4 的载体,需要补两块:

1. 把评估从"最终输出打分"扩展到"**span 级轨迹打分**"
2. 给巡检用的 judge 建立 D0 的校准与月度重校准流程

> **巡检结果的可信度上限,就是那个 judge 的 κ。**

## 八、迁移路线图

| 阶段 | 周期 | 交付 | 为什么是这个顺序 |
|---|---|---|---|
| **P0 止血** | 4 周 | D0-1 judge 校准<br>D5-1 / D5-2 注入投毒套件<br>D5-6 高危动作清单 | 这三项决定"现有数据可不可信"和"最坏能坏到什么程度",必须最先做 |
| **P1 换范式** | 6 周 | D4-1 pass^k 改造<br>D1-3 span 级轨迹评估<br>环 2 沙箱回放 | 把测量方法从单点改成分布,这是后续所有工作的地基 |
| **P2 补盲区** | 8 周 | D2 编排全套<br>D3-3 人机协同<br>D6-2 成本经济学 | 补 v1.0 完全没有的面 |
| **P3 上闭环** | 8 周 | 环 3 影子灰度<br>环 4 在线持续<br>D7-3 变更治理 | 从"发布前保证"转为"运行时保证" |
| **P4 常态化** | 持续 | 红队常态化<br>judge 月度重校准<br>失败模式库 | |

### 如果只能做一件事

**先做 D0-1(judge 校准)。**

你现在所有的评估数字,准确性上限都取决于那个 judge 有多准 —— 而这件事大概率还没有被量化过。
